## 正文(PRD / 提案全文)

### Motivation.

DFlash2 on ROCm is slower than it should be, and at high concurrency on main it is slower than not speculating at all. Measured on one MI355X, Qwen3.8-27B with `z-lab/Qwen3.8-27B-DFlash2` and 7 draft tokens, using MRV2 and ShareGPT with 512 output tokens at temperature 0. Output tok/s:

| | c=1 | c=16 | c=64 |
|---|---|---|---|
| main, no speculative decoding | 91.7 | 940.8 | 2855.4 |
| main, DFlash2 | 239.4 | 1829.9 | **2641.3** |
| DFlash2 + #61433 | 266.8 | 2392.4 | 4065.3 |
| DFlash2 + #61433 + #61434 (`--no-enable-prefix-caching`) | 262.2 | 2511.4 | 4456.2 |

The acceptance length is 4.0–4.3 in every DFlash2 row. The #61434 row is compared against #61433 with `--no-enable-prefix-caching`, which gives 262.9 / 2377.9 / 4027.9.

Since #61855 (merged), ROCm runs spec decode through a Triton port of the fused GDN MTP decode kernel by default, so #61434 now applies only with `VLLM_GDN_DECODE_KERNEL=triton`. #64325 adds the same deferred state to the fused kernel. On image `nightly-rocm100-5d35ce39` (includes #61855), default attention backends and `--no-enable-prefix-caching`, mean of 2 runs:

| | c=1 | c=16 | c=64 |
|---|---|---|---|
| main, DFlash2 | 245.7 | 1835.3 | 2648.7 |
| + #64325 | 245.2 | 1948.1 (+6.1%) | 2865.8 (+8.2%) |

GPU time at c=64 with #61433 applied, from a rocprofv3 kernel trace of an offline run. The run uses 64 ShareGPT prompts, 256 output tokens each, and prefix caching on (the default), so the window includes prefill.

| | share |
|---|---|
| GEMM (hipBLASLt), including the split-K epilogue at 2.5% | ~61% |
| GDN recurrent update, `fused_sigmoid_gating_delta_rule_update` | 18.3% |
| Inductor-fused norm, activation and RoPE | ~8% |
| Copies (elementwise, cat, `copyBuffer`) | ~4% |
| Full attention, target and drafter | 3.2% |
| GDN `causal_conv1d_update` | 1.5% |
| Vocab top-k (`torch.topk`) | 0.8% |
| DFlash2 grouped conv | 0.3% |

This issue tracks the plan: what is already up for review and what comes next. ATOM (ROCm/ATOM) and the aiter kernels were used as references.

**#61433.**
- Draft, paused in review until vLLM's aiter pin includes ROCm/aiter#6661 (released in aiter v0.1.27; main pins v0.1.26). Before that, `ROCM_AITER_UNIFIED_ATTN` gives wrong output on gfx950 for some KV cache sizes (#62606). #62813 is the interim change, and #61433 drops its gfx950 rule after the bump.
- `ROCM_ATTN` runs its prefix-prefill Triton kernel for every multi-token query, which here is 1 + 7 tokens per request.
- On hybrid models its block size (832 here) is not a power of two, so even single-token decode misses the HIP paged-attention path.
- After the change, the target picks `ROCM_AITER_UNIFIED_ATTN`. The non-causal DFlash drafter picks `TRITON_ATTN`.
- An explicit `--attention-backend` still wins, and dense models without speculative decoding keep the current order.

**#61434.**
- The GDN state is 48 heads × 128 × 128 fp32, about 3 MiB per layer per sequence.
- Today it is written once per draft position (8 times per step), and only one copy is used.
- The replay is exact for fp32 SSM state.
- It currently applies only when `mamba_cache_mode` is `none`, i.e. with `--no-enable-prefix-caching`.
- It changes `fused_sigmoid_gating_delta_rule_update`. Since #61855 that kernel runs spec decode on ROCm only with `VLLM_GDN_DECODE_KERNEL=triton`, or as the fallback when the fused MTP op does not support the model.

**#64325.**
- Same records and replay as #61434, in `fused_gdn_decode_post_conv_mtp_triton`, which is what ROCm runs by default after #61855.
- Enabled on ROCm with an fp32 state and `mamba_cache_mode` `none`. The CUDA op is unchanged.
- Spec rows of mixed batches (`_forward_core`) use the same update kernel, so every step of a request sees the same state layout.
- The two PRs are independent: each changes a different kernel, and the layer picks one of them at init.

**ROCm/aiter#7069.**
- vLLM calls this kernel only for non-speculative decode with `VLLM_ROCM_USE_AITER=1`, so the flag is for other users of aiter's GDN decode op.
- Opt-in flag, default off; requires fp32 state and 2D `ssm_state_indices`.

**#61760.**
- The DFlash2 drafter attends non-causally over its 8-token block with a 2048-token sliding window. Its rows were excluded from split-K, so at B=1 the 2D launch has 8 programs (one per KV head), and each walks the whole window.
- Separately, when split-K is used with a sliding window, the segments split `[0, seq_len)`. At long context only one or two of them overlap the window. This affects causal sliding-window decode and verify as well, which get 2–9.6× at B ≤ 8 and long context.
- ShareGPT is unchanged because its prompts mostly fit within the window.
- The larger beneficiary is a sliding-window target model. Gemma-4 is forced onto `TRITON_ATTN` on ROCm (head sizes 256/512), so its 25 sliding layers take this path by default: 16k random output +32% / +28% / +9% at c=1/4/16, 4k c=1 +11%, ShareGPT unchanged, GSM8K 0.708 → 0.711.
- The drafter regression at B=16, ctx 512 (0.86×) is fixed by a minimum segment size that scales with the batch: now 1.06×. Causal with ctx ≤ window at B=2–4 stays at 0.94–0.98×; it is codegen, not the tile bounds, which are identical to main's.
- The earlier +17% / +16% under `TRITON_ATTN` is superseded by the default-backend run.

**#61429.**
- At these batch sizes the top-k is a small part of the step.
- The PR is kept because it is exact, deterministic and much faster than `torch.topk` for larger draft batches.
- aiter's top-k APIs were compared and are not a better fit (see "Any Other Things").

#### Closed

- #62381 (skip the AITER packed GDN path under spec decode) was closed as superseded by #61855. Since #61855, `forward_hip` skips that path whenever the fused GDN spec decode kernel is enabled, which is the default on ROCm with speculative decoding. The remaining case (`VLLM_GDN_DECODE_KERNEL=triton`, or a model that the fused kernel does not support) was not measured.
- #62415 (zero out-of-window V in `ROCM_ATTN`'s sliding-window kernels) was closed. The NaN it fixed (#62828) no longer occurs on main since #60767.

#### Next

The first three items are planned in this order.

1. **GDN deferred state with prefix caching (`mamba_cache_mode=align`).**
   - With prefix caching on, which is the default, the GDN update is still 18% of GPU time, because neither #61434 nor #64325 applies there.
   - `align` reads per-token states at block boundaries in `preprocess_state`. The plan is to replay the records before that copy, so the deferred path also covers the default configuration.
2. **One GDN state slot per request.**
   - This follows the idea of ROCm/ATOM#1883 (ReplaySSM).
   - Speculative decoding currently keeps 1 + `num_speculative_tokens` state slots per request. For Qwen3.8-27B that is 48 GDN layers × 3 MiB ≈ 144 MiB per slot, or about 1.15 GiB per request with 7 draft tokens. This is an estimate from the config, not a measurement.
   - Building on #61434's records, a single checkpoint plus the per-token records would be enough, and the freed memory could go to the KV cache and larger batches. Measuring the memory and throughput gain comes first.
3. **Split-KV for `ROCM_AITER_UNIFIED_ATTN` at small batch and long context.**
   - On gfx950, aiter's `unified_attention` defaults to its gluon backend. That backend always takes the 2D launch for query_len > 1, which has no split-KV.
   - With B=1, query_len=8 and 4 KV heads, that is about 20 programs on 256 CUs, so the time grows linearly with context.
   - aiter's `backend="triton"` path switches to 3D in that regime. It is 1.4–4.3× faster per call when B ≤ 4 and ctx ≥ 2k, or B ≤ 8 and ctx ≥ 3k; gluon is better at B ≥ 16.
   - At c=1 with an 8k context that is about 3.8 ms per step across the 16 attention layers.
   - Options: choose the aiter backend per batch size in `rocm_aiter_unified_attn.py`, or add split-KV to the gluon 2D path in aiter. The aiter fix addresses the root cause.
   - This is the target-side counterpart of #61760, which does the same for `TRITON_ATTN`.
4. **GEMM tuning for the verify step (tuned and measured; next is contributing the configs to aiter).**
   - The target sees M = 8 × num_seqs. GEMMs are about 61% of GPU time, and at M=8 they take about 11.4 ms per step, which is mostly weight streaming.
   - vLLM's default dispatch is within 1–4% of the best of `torch`, aiter `tgemm` (untuned) and aiter Triton at these M values. Untuned aiter therefore has nothing to offer.
   - aiter's bf16 tuner (`gemm_a16w16_tune`) was run on:
     - Qwen3.8-27B + DFlash2 at every capture size;
     - >300B targets and their DFlash drafters at TP 1/4/8: Kimi-K2.5, Qwen3.5-397B-A17B, GLM-5 and GLM-5.3-Flash.
   - The tuner times each candidate on its own, so a candidate within ±5–8% of hipBLASLt wins or loses by noise. The raw tuned CSV gave no end-to-end gain. Each tuned row was therefore re-timed against `F.linear`, alternating the two in one process over cold weight copies, and kept only if it is at least 1.03× faster.
   - **Qwen3.8-27B + DFlash2**, AITER linear env, all with #61433. Output tok/s, mean of 2–4 runs with GPUs swapped:

     | | c=1 | c=16 | c=64 |
     |---|---|---|---|
     | without AITER | 262.1 | 2418 | 3985 |
     | AITER, shipped configs + #62381 (closed, see above) | 264.3 | 2387 | 3958 |
     | AITER, verified configs + #62381 (closed, see above) | 273.0 (+4.2%) | 2407 (−0.5%) | 3991 (+0.2%) |

     The gain is at c=1. The biggest verified wins are `gate_up` (N=34816) with a Triton kernel at M=8/16 and `lm_head` at M=64 with FlyDSL.
   - **>300B shapes.** 338 of 442 tuned rows were kept; none of these shapes is in aiter's shipped gfx950 configs. Summed time of each distinct layer shape (not weighted by layer count), `F.linear` → verified configs, at M=8. These are GEMM microbenchmarks, not end-to-end numbers:

     | model | TP1 | TP4 | TP8 |
     |---|---|---|---|
     | Qwen3.5-397B-A17B | +30% | +33% | +17% |
     | GLM-5.3-Flash | +10% | +33% | +19% |
     | Kimi-K2.5 | +14% | +5% | +9% |
     | GLM-5 | +3% | +22% | +31% |

     The largest wins are small-K layers such as the shared-expert `down` and GLM-5.3-Flash's KDA `f_b_g_b` projection (1.5–1.9×), and the Qwen3.5-397B `lm_head` at TP1 (466 → 339 µs, 1.37×).
   - aiter issues found on the way:
     - A multi-path `AITER_CONFIG_GEMM_BF16` (and the default, which merges `model_configs/`) is merged into one fixed file, `/tmp/aiter_configs/bf16_tuned_gemm.csv`. Every process in the container shares it, so parallel processes with different configs read each other's. On duplicate shapes the merge also rewrites the source CSVs. Passing one pre-merged file avoids both.
     - The prebuilt opus module only contains the kernel ids used by the shipped configs. A tuned opus row with another id makes vLLM fail at startup ("kid N is not compiled"), so those rows were dropped.
     - The tuner's FlyDSL JIT caches keep one weight copy per compiled candidate, so tuner workers grew to about 285 GiB.
5. **QK-norm + RoPE + gate fusion on ROCm.**
   - `Qwen3NextAttention` only uses vLLM's `fused_qk_rmsnorm_rope_gate` on CUDA/XPU. #51406 (open, approved, needs a rebase) allows it on ROCm (`is_cuda_alike()`). The kernel test passes on MI355X.
   - Per layer it is 6.3× faster at 8 tokens (about 14 → 2.2 µs) and 2.1× at 512 tokens.
   - End to end on top of #61433, mean of 2 runs with GPUs swapped: 267.8 → 269.5, 2382.7 → 2400.3, 3956.3 → 3981.0 tok/s at c=1/16/64, i.e. +0.6–0.7%. That is below the 1–1.5% spread between runs. Acceptance length is unchanged. GSM8K (5-shot, 1319 questions) is 0.792 → 0.785 (8 questions).
   - aiter's `fused_qkv_split_qk_norm_rope_cache` additionally fuses the KV-cache write. It is 1.2–2.3× faster than vLLM's fused kernel + `reshape_and_cache_flash`, but that saves only about 25 µs per target step (16 attention layers, about 0.15%). Using it would also require the attention layer to skip its own cache write, and it has no mrope. So the plan is #51406, not aiter.

#### Not planned, with reasons

- **`ROCM_AITER_FA` for this model.** With aiter enabled it is 6–8% slower than `ROCM_AITER_UNIFIED_ATTN` + `TRITON_ATTN`. Its non-causal path (`mha_v3` kvcache) is 4–10× slower than `TRITON_ATTN` for the drafter.
- **aiter's ASM paged-attention fast paths.** The `pa_fwd_asm` MTP kernels and `pa_persistent_fwd` cover head 128 with GQA 8/16, or FP8 KV. Qwen3.8-27B uses head 256, GQA 6 and bf16 KV.
- **`pa_decode_gluon`.** It needs query_len ≤ 4, and DFlash2 here verifies 8 tokens.

### Any Other Things.

**Environment.**
- Image `vllm/vllm-openai-rocm:nightly-rocm100-0cbac6cd1305f710e12193596b27488397bcb205`, which ships amd-aiter 0.1.23. main now pins v0.1.24.post1.
- The PRs above change only Python and Triton files. Each PR description has a Reproduction section with the serve command, the benchmark loop and a kernel microbenchmark.

**aiter top-k comparison.** V=248320, k=16, bf16, which is what the candidate head produces. Times in µs on MI355X:

| rows | `torch.topk` | #61429 Triton | `aiter.topk_plain` | `aiter.ops.topk_select.topk_select` |
|---|---|---|---|---|
| 7 | 82.3 | **17.2** | 49.3 | 84.3 |
| 112 | 197.2 | **44.8** | 72.9, duplicate indices | 135.1 |
| 448 | 575.6 | **112.6** | 114.9, duplicate indices | 276.0 |
| 1792 | 2072.6 | 383.6 | **175.1** | 888.5 |

- `topk_select` serves k > 1 in fp32 only, so bf16 must be cast first. It returns int32 indices.
- `aiter.ops.triton.topk.topk` raised a GPU memory-access fault at this shape.
- The `topk_plain` duplicates come from `topk_filter_kernel`.
  - It handles a whole row per block (`len_per_block = len`, marked `TODO: Consider multiple blocks`), yet it can still be launched with several blocks per row.
  - For bf16/fp16, the element-wise tail loop of an extra block re-reads the last `blockDim.x` columns of the row, and the merge then counts them twice.
  - Repro: set one column near the end of every row to the maximum. With 112 or 448 rows, every row returns that index twice. fp32 is unaffected.
  - The code is unchanged in v0.1.24.post1. The fix is ROCm/aiter#6586.

**aiter GDN decode kernels for spec decode.** Checked on aiter main for this model (H=16, HV=48, K=V=128, T=8, fp32 state):
- FlyDSL `flydsl_gdr_mtp` (chain mode) is the only one that follows vLLM's contract (roll back to slot `num_accepted - 1`, store every token) with vLLM's state layout. It does not fuse the conv or the norm and needs a uniform T. Recurrence only, µs at 1 / 16 / 64 / 128 sequences: FlyDSL 12.1 / 77.4 / 380.6 / 754.2, vLLM Triton per-token 15.2 / 92.2 / 393.1 / 745.2, vLLM Triton deferred (#64325) 13.1 / 55.8 / 205.3 / 411.3. FlyDSL is faster only at ≤ 4 sequences, so the plan stays with the Triton kernel.
- Gluon `fused_gdn_decode_qkvz` (gfx950) fuses split, conv, recurrence and norm, but handles one token per sequence only.
- HIP `fused_split_gdr_update` uses a swizzled state layout, and `gdr_decode_packed_bf16` is fixed to 8/32 heads with a bf16 state.
- The `fused_kda_decode*` kernels (including the ReplaySSM mode) are for KDA, not GDN.
