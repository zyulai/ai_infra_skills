# [RFC]: Fast-Track Merging for Model Optimization PRs

### Motivation.

Frontier coding models have become extremely proficient at inference model optimization and efficient GPU kernel development. The frequency of new vLLM PRs is rapidly increasing, and is outpacing reviewer bandwidth.
Powered by fully autonomous optimization loops (e.g. "autoresearch"), optimization development can be scaled horizontally across a wide range of models, hardware architectures, and deployment scenarios.

The potential speedups are extremely large, but careful steps must be taken to ensure that vLLM's code quality, usability, and reliability is not sacrificed in the process -- this is why we have a comprehensive review process. Striking a balance between contribution barriers and performance upside is critical.

The fundamental goal of the fast-track is to merge PRs faster, with the same standard of quality. The way to achieve this is by systematically verifying aspects that ordinarily require manual reviewer verification (correctness, performance, no risk of breaking other workloads, etc.). By focusing on a subset of PRs whose changes are strictly contained to an isolated module (namely, the "model forward pass") we can tailor guardrails to decrease reviewer involvement while maintaining a high bar for stability.

### 1. Proposed Change.

I propose a relaxation of the review and merge requirements, limited to cases where changes are contained, comprehensively validated, and provably limited to explicitly validated deployment scenarios.

The remainder of the RFC details the following:
1. Process changes we can make to more efficiently merge "safe" optimization PRs
2. How we can systematically ensure that an eligible PR is "safe to merge"

#### 1.1: One-Touch Merge ("LGTM")

Reviewers often need to revisit PRs multiple times throughout review: one pass to leave comments, another pass to approve and enable CI, additional passes to rerun/retry CI, and possibly a final force-merge request must be made.

For contained model optimizations, much of this can be prevented:
- If no comments are required, a single reviewer action approves the PR and starts an automated procedure to merge: CI runs and executes an automated procedure of rebase and retry until the PR goes in (up to 3 times) or a fallback force-merge is automatically requested. 
- If only trivial edits or conflict resolution are requested, a reviewer may submit a "conditional approval" on the requested changes. After the changes are made the automated merge procedure begins. The "conditional approval" persists through rebase, conflict resolution, acceptance of reviewer-suggested edits, and changes localized to tests/, provided the changes preserve the approved behavior. An amount of trust is delegated to the contributor in the event of a conditional approval.

The CI runs should hopefully not be an obstacle in these cases as changes should be contained to localized files/directories which will mitigate the range of detected test cases.

In cases when a maintainer decides nontrivial changes are needed, the maintainer closes or demotes the PR and the contributor is responsible for updating and re-opening or re-requesting review.

#### 1.2: Primary-Maintainer Merge

One common issue that blocks merge is when the primary maintainer of a feature makes a small PR to update an aspect of that feature which they themselves have the most expertise with. In such cases it can be difficult to find a dedicated second reviewer who can confidently approve the changes.

To resolve this I propose we permit core committers to merge their own PRs, provided they follow the validation and isolation requirements of the fast-track specification below.

#### 1.3: Priority Review

I propose that eligible fast-track PRs be automatically labelled as such, and that maintainer review is prioritized towards fast-track PRs. This will involve slack integration, an automated tracking dashboard, and escalation when fast-track-eligible PRs are "stale" for more than N=7 days.

Because fast-track model optimizations are targeted towards a specific model (or small family of models), there should be a small set of assigned reviewers who can be held more directly responsible for triaging fast-track PRs. This burden will be opt-in, but should not be too heavy as triaging fast-track PRs should be very easy by design.

#### 1.4: PR Template

Similar to the [PR-Checklist](https://github.com/vllm-project/vllm/pull/57084) change which updated the PR template, there will be a dedicated template for fast-track PRs which formalizes the requirements and streamlines review. PR will follow the RFC within a few days.

### 2. Validations and Confidence

#### 2.1: Isolation of Code Changes

The primary risk of merging code tailored to optimize one use-case is impact to other deployments. Performance regressions, breaking other features, or correctness violations are all common side-effects of a seemingly harmless change.

The first pillar of raising confidence in safety is _isolation_: limiting code changes to a specific deployment scenario.

I propose the initial prototype require that fast-track changes be limited to "flat model" subdirectories (e.g. all diff is within a folder such as `vllm/models/deepseek_v41/nvidia`). 

#### 2.2: Bounded Impact on Deployments

Optionally, changes can be further gated programmatically (e.g. a kernel fusion only enabled at small input sizes). The more isolated a change is, the smaller the potential impact. By placing rigid bounds on the changes, we can limit the impact to a very small set of deployment scenarios which can be tested explicitly.

Naturally, limiting the scope in this way also reduces the net improvement per PR: other excluded scenarios might benefit from the changes as well. This may also increase code duplication and redundancy. However, it creates a clear path toward improving stability and scalability as we accelerate the pace of optimizations with coding agents.

[TensorRT-LLM has merged a design](https://github.com/NVIDIA/TensorRT-LLM/pull/19056) which isolates/replicates model code for each model, hardware, and parallelism triple (e.g. gpt-oss TP1 on SM103). This is a fairly extreme flavor of replication, but it highlights an architectural direction we can move towards for if the initial results from vLLM's flat-model design prove sufficiently maintainable.

#### 2.3: Explicit Validation of Affected Deployments

Once an isolated and bounded deployment is established for a contribution, what remains is to run sufficient validations against a representative set of configurations.

Since reviewers are still involved in the process, there is some flexibility in the extent of validation: some changes might warrant testing every parallelism configuration or testing on multiple hardwares, while others might be sufficient with only a single parallelism/HW configuration. If a contribution is not sufficiently validated, reviewers may request additional validation and approve conditionally (see 1.1) or they may demote the PR from the fast-track and/or close it as necessary. Submissions following the fast-track accept a higher evidence standard and a higher risk of reviewers closing low-quality PRs wholesale without discussion.

To codify expectations, I propose the following requirements:

- **E2E Correctness Evaluation:**
  - `GSM8k` and `GPQA-Diamond` be run for all proposed model optimizations
  - A long-context benchmark such as `MRCR v2 256K (8-needle)` and/or a long-generation benchmark such as `AIME25`/`AIME26` (pass@1 avg1) should be included when changes affect sensitive token-mixing operations such as FMHA or SSM.
  - A "hard" correctness benchmark such as `AIME25`/`AIME26` (pass@1 avg4+) or `HLE` or `TerminalBench (any)` should be included when changes include a "high correctness risk factor": low-level CUDA C++ or PTX/SASS or equivalent, or new communications kernels for which race conditions cannot be ruled out by formal verification.
  - All correctness evaluations should use at least "high" reasoning effort, where supported. All evaluations should compare against a known "good" baseline, either referencing official vendor reported numbers or those from a vLLM reference run. Running your own baseline on the vLLM main branch to compare against is acceptable. Measured scores should exceed or match the reference within one percentage point (absolute delta, after accounting for run-to-run variance).
  - Correctness validation runs should ensure that the deployment scenario is reproduced. For example, if adding a small-batch fusion, GSM8k should run at a correspondingly low batch size (to trigger the change and contribute coverage to the diff).
- **Kernel Correctness Evaluation:**
  - New kernels should be exhaustively validated for correctness on a broad range of inputs. This includes multiple possible input shapes as well as input distributions.
    - If bit-exactness is not maintained, it should be justified and validated with a strict tolerance.
    - If quantization or lossy optimizations are used, this is considered a "high correctness risk factor" and warrants additional E2E validation (see above).
  - For low-level CUDA kernels, include [compute-sanitizer](https://developer.nvidia.com/compute-sanitizer) tests such as `memcheck`, `racecheck`, and `synccheck` sanitization are required where applicable.
  - Note, committed tests should be a small subset of validation performed during development. These should exist strictly for regression checks, not for comprehensive reproduction. We do not want to run exhaustive correctness testing in CI every time we make a model change.
- **Performance Evaluation:**
  - PRs should include a "headline" speedup on a specified "target" workload. This is required but not sufficient for performance validation.
  - Performance change should also be swept across the range of bounded-affected-workloads: multiple concurrencies should be benchmarked almost always, as well as high/low sequence length when applicable. Any throughput or latency regression exceeding 1% for any measured configuration is unacceptable and disqualifies the PR from the fast-track.
    - For MoE models, ensure real prompts (such as speed-bench throughput_8k) are used so that expert balance is realistic.

### Discussion Areas

1. Do we want to further solidify the requirements from sec. 2.3 into a structured requirement matrix? Or do we want to leave it flexible for reviewers to decide on a per-PR basis if validation is sufficient?
2. How strict should we be about isolating code changes? Are minor one-liner integration patches in core files acceptable, or do we require rigid file-structure-based guarantees about isolation? Can we build static linting tooling (possibly AI powered) that can enforce or verify that changes are limited to the claimed workloads?
3. Is committer self-merge a good idea, or is it too permissive?
4. How much control are we comfortable delegating to automated verification systems, versus committer judgement? Should we be more/less aggressive in automating merge workflows?
