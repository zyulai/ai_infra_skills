### Motivation


## Summary

This RFC proposes an optional KV compression path for Prefill-to-Decode transfer over Mooncake RDMA. SGLang would manage layout preparation, bounded buffers, transfer metadata, and asynchronous completion through a small internal interface for compression backends. Attention would continue to read the existing GPU KV format after received data has been restored.

The initial implementation targets lossless P/D transfer on one explicitly supported MHA/GQA layout. The architecture also includes a path toward reusing compressed payloads and integrating with HiCache, with those capabilities delivered as separate extensions.

This is a design proposal. No compression ratio or serving speedup has been established. The immediate review request concerns the integration boundary and validation plan; broader support would depend on correctness and measurable benefit.

## Motivation and Scope

In P/D serving, KV transfer can delay the handoff from Prefill to Decode. Compression can reduce the transferred bytes, but adds computation, memory traffic, synchronization, and temporary storage. Whether it helps depends on the actual KV distribution, effective network bandwidth, and concurrent model execution.

The appropriate algorithm can change with the workload and hardware. Integrating each algorithm directly into the transfer path would repeat page extraction, buffer management, length publication, restoration, and failure handling. A small shared interface would allow these mechanisms to remain in SGLang while the data transformation can be replaced and evaluated independently. Its value must be demonstrated through a real backend rather than assumed from generality alone.

For scale, [[Qwen3-8B’s configuration](https://huggingface.co/Qwen/Qwen3-8B/raw/main/config.json)](https://huggingface.co/Qwen/Qwen3-8B/raw/main/config.json) has 36 layers, eight KV heads, and a head dimension of 128. BF16 K and V therefore occupy 144 KiB per valid token, or 1.125 GiB for 8,192 tokens at TP=1, excluding padding and metadata. If the transferred bytes were reduced by 20%, the ideal network saving would be approximately 9.66 ms at 200 Gb/s or 4.83 ms at 400 Gb/s. These are illustrative calculations, not measurements or predictions of compressibility; the additional critical-path cost must fit within the actual saving.

The first validation target is Qwen3-8B with BF16 KV, one Prefill worker and one Decode worker, TP/PP/CP/DCP set to one, and GPU LZ4 through nvCOMP. The experiment would pin the attention backend, KV pool layout, page size, dependency versions, and block-size policy. CPU execution, topology conversion, MLA, hybrid state, speculative decoding, HiSparse, and compressed storage are subsequent validation scopes.

P/D compression does not require HiCache or persistent offloading. It does not reduce the KV capacity or per-step KV reads required by active attention. GPU compression preserves attention’s input format but still competes for compute and memory bandwidth.

## Proposed Design

### Overall Architecture

<img width="1280" height="965" alt="Image" src="https://github.com/user-attachments/assets/926e0ea6-064f-48e2-a2bf-93ae38ffaf25" />

*Figure 1. The complete proposed architecture. The initial implementation covers P/D compression and restoration. Compressed HiCache storage and payload reuse are later extensions. Cache class names illustrate an existing integration route rather than a required configuration.*

The Scheduler and GPU Executor retain their existing control flow. On Prefill, the GPU KV pool contains reusable prefix pages and KV generated for missing input tokens. A GPU prefix hit reuses existing pages; a future compressed L2 hit would restore the prefix needed for computation. Prefill then writes newly generated KV into the same pool.

The P/D adapter selects the ranges Decode still needs and prepares them after their writes complete. KVSender transfers the selected representation through Mooncake. KVReceiver restores the payload into Decode’s allocated KV pages, and the request becomes runnable only after restoration and existing metadata and rank-level checks complete.

Compression operations are local to each worker. The design introduces neither a separate compression service nor another request scheduler. Existing cache management retains prefix lookup, allocation, references, and eviction. The omitted Decode-side compressed L2 branch is a scope boundary; it does not imply that existing Decode configurations cannot use HiCache.

### Component Boundaries and Backend Interface

<img width="1440" height="970" alt="Image" src="https://github.com/user-attachments/assets/aadd8be7-3760-40b0-860d-2be52b700860" />

*Figure 2. P/D and future HiCache integrations retain their own ownership and completion rules. Orange borders mark proposed additions or extensions. Shared contracts do not imply a stable public plugin ABI.*

The layout adapter organizes selected KV into independently recoverable blocks within one layer and local shard. A block may contain multiple allocation pages. The backend transforms those packed blocks; it does not traverse cache trees, register RDMA memory, allocate model KV pages, or interpret request state. The P/D adapter owns transfer descriptors, buffer leases, and restoration completion. A later HiCache adapter would own cache admission and byte accounting under the existing cache lifecycle.

The proposed internal backend contract is:

```python
class KVCompressionBackend(Protocol):
    def supports(self, spec: BatchSpec) -> SupportResult: ...

    def buffer_requirements(
        self, operation: Literal["compress", "decompress"], spec: BatchSpec
    ) -> BufferRequirements: ...

    def compress_into(
        self, src: PackedBatch, dst: BufferBatch, workspace: Workspace,
        *, context: ExecutionContext,
    ) -> CompressionOperation: ...

    def decompress_into(
        self, src: EncodedBatch, dst: BufferBatch, workspace: Workspace,
        *, context: ExecutionContext,
    ) -> CompressionOperation: ...


class CompressionOperation(Protocol):
    def poll(self) -> OperationSnapshot: ...
```

`BatchSpec` describes block count, decoded sizes, packed layout, format parameters, and device requirements. `SupportResult` includes a rejection reason. `BufferRequirements` supplies finite output and workspace bounds, alignment, and metadata requirements for the requested operation. Buffers remain caller-owned, with explicit sizes, capacities, and memory locations. `ExecutionContext` provides the execution stream or worker context and input dependencies.

`OperationSnapshot` separates outcome from resource safety. The outcome is pending, succeeded, or failed. Success means outputs, actual lengths, and per-block status are available without synchronizing the scheduler. A separate `quiescent` property means the operation will perform no further accesses to its supplied buffers. Success requires this property for the operation’s own work; failure may precede it. Downstream transfer and restoration hold independent references.

GPU length and status publication is part of the operation, using batched results and bounded host metadata storage where needed. Scheduler polling observes published state rather than reading synchronizing size accessors. The layout adapter’s restore completion additionally covers the final scatter into destination pages.

These interfaces are provisional. Uncompressed pass-through provides an integration control group; a second real compression backend would help validate the abstraction before stabilizing it. No new user-facing HTTP API is proposed.

### Block Representation and Transfer Metadata

<img width="2880" height="1550" alt="Image" src="https://github.com/user-attachments/assets/a5b21cc1-dda5-49ab-b36e-03a78830136b" />

*Figure 3. Logical token order is independent of physical page indices. Reusable representation metadata is separate from each transfer’s envelope. The diagram shows a compression attempt; the adapter can select an uncompressed payload.*

Only valid KV bytes enter a block, excluding unused tail-page capacity. Blocks are submitted in batches to limit launch and metadata overhead. Compression granularity is separate from allocation-page size and would be selected through measurement.

```text
Representation metadata
    UNCOMPRESSED or COMPRESSED
    format identifier, version, and decoding parameters
    packed layout, dtype, layer, shard, and valid logical range
    block boundaries, encoded lengths, and decoded lengths

Transfer envelope
    protocol version, session, room generation, and chunk sequence
    receive lease identifier, generation, payload offset, and length
    receiver-approved destination mapping reference
    representation metadata for the transferred blocks
```

These fields describe the contract rather than a finalized wire encoding. The receiver validates block counts, lengths, layout, and destination coverage against its granted capacity and allocation state. Reserved buffer capacity is distinct from the actual bytes transmitted. Physical addresses and request IDs do not identify reusable cache content.

`UNCOMPRESSED` means literal packed KV bytes. It is distinct from [[nvCOMP’s ](https://docs.nvidia.com/cuda/nvcomp/py_api.html)`[BitstreamKind.RAW](https://docs.nvidia.com/cuda/nvcomp/py_api.html)`](https://docs.nvidia.com/cuda/nvcomp/py_api.html), which still contains compressed data. The sender selects compression only when its complete wire size is smaller than the uncompressed representation under the same protocol. This avoids an inflated compressed payload, but does not eliminate metadata overhead or the cost of attempting compression relative to the existing direct-transfer path.

### Transfer Execution and Completion

<img width="1440" height="1255" alt="Image" src="https://github.com/user-attachments/assets/71285c98-3a94-45eb-87d0-95c3089c7e58" />

*Figure 4. Transformation, network transfer, and KV restoration have separate completion boundaries. Capabilities and layout are agreed before this sequence.*

The prototype uses the existing Mooncake engine and P/D work queues with a bounded, registered byte pool for compression traffic. Current staging already provides patterns for allocation, chunk-arrival notification, asynchronous scatter, and credit return. Its layout-dependent assumptions cannot automatically describe variable-size compressed blocks. The implementation would reuse matching mechanisms while keeping compression metadata above the byte-transfer engine. The first supported configuration excludes simultaneous use of the existing layout-conversion staging mode.

Decode grants a receive lease with a known session, generation, capacity, and destination range. The sender reserves input, worst-case output, and workspace capacity before submitting work. It waits for source writes, packs selected KV, and compresses outside scheduler polling. The selected payload must fit the granted slot; each lease authorizes one payload submission.

After actual lengths are available, Mooncake transfers the selected byte ranges. A descriptor and data-ready notification follow successful transfer completion. Restoration must respect the transfer backend’s device-visibility guarantees before reading the received bytes. Decode validates the descriptor, decompresses when necessary, and writes the destination pages. Slot credit returns only after network writes and local payload accesses have finished.

Restore-pending maps to the existing `KVPoll.Transferring` state, restore failure to `Failed`, and completed restoration permits `Success` only when the other request conditions hold. This gate is applied before rank-wide status aggregation. Required metadata still completes even when prefix reuse leaves no KV bytes to transfer. Existing local-cache restoration, when enabled in a supported combination, remains part of admission.

### Resource Lifetime and Failure Handling

<img width="1440" height="1070" alt="Image" src="https://github.com/user-attachments/assets/9f060533-e8fd-4612-b3e5-a11e5c39df8b" />

*Figure 5. Ownership extends through the last access. Bar lengths express ordering, not measured durations. The source reference shown belongs to the compression task; request and cache references remain independent.*

Source KV stays protected until packing or compression finishes reading it. Packed input remains valid through compression, the send buffer through RDMA source reads, and the receive buffer through restoration. Workspace, pointer and length arrays, host metadata, and quarantined buffers all count toward configured budgets. Destination pages remain governed by existing request and cache ownership.

Cancellation stops new submissions and drains existing accesses before releasing memory. A generation check rejects stale control messages but cannot stop an already submitted RDMA write. A timeout is therefore not proof that a receive address can be reused. If quiescence cannot be confirmed, affected buffers are quarantined; exhausting that budget stops affected admissions or fails the session. Partial restoration never publishes valid cache entries. Duplicate notifications must neither repeat restoration nor return credit twice.

### Prefix Reuse and Future HiCache Integration

<img width="1440" height="1120" alt="Image" src="https://github.com/user-attachments/assets/c93a4d35-971e-4028-892f-d497404007b3" />

*Figure 6. Future cache integration separates reuse for computation from reuse for transmission. The transfer path is evaluated only for ranges Decode still needs.*

A GPU prefix hit avoids repeated Prefill computation but may still require compression for transmission. A compatible compressed L2 hit can supply a payload directly to the network while a separate restore makes the prefix available to local attention. Sending does not require that local restore to finish. The object holds independent send and restore references.

Persistent identity follows existing prefix and model-isolation semantics, with representation compatibility added. A new request receives a new transfer envelope. Direct reuse requires complete compatible blocks; a partial hit inside an opaque compressed block requires recovery or reorganization with its cost accounted for. Only stable complete pages are eligible for persistent admission.

HiCache integration would separately introduce logical handles backed by actual compressed-byte allocation, avoiding a fully allocated original host pool plus an extra compressed copy. Publication follows successful backup and cache admission. Loading must preserve layer-wise completion, including `L2TransferEngine`’s `on_layer_done` ordering. A future CPU backend must cover CPU work, H2D, and destination writes before reporting readiness. These are extension requirements, not capabilities established by the initial P/D interface.

## Configuration and Compatibility

Compression is disabled by default. Enabling it selects a backend, format options, block-size policy, and sender/receiver memory budgets. The effective configuration must be observable. nvCOMP is an optional dependency loaded only when requested; an unavailable explicitly selected backend or unsupported enabled layout produces an actionable initialization error. The disabled path allocates no compression buffers.

The prototype requires matching builds and explicit configuration at both ends. Protocol selection precedes commitment to destination ownership. Requests assigned to the existing raw path retain it. Once a request enters the new protocol, an incompressible block uses `UNCOMPRESSED` with the same lease and restoration lifecycle; it cannot silently switch to legacy direct writes. Buffer exhaustion after admission causes bounded backpressure or controlled failure.

Mixed-version support requires discovery that is safe for legacy parsers and is a separate compatibility gate. The proposal does not append fields to an unversioned message and assume rolling upgrades will work. CPU execution, host staging, and persistent storage remain separate capabilities; enabling compression does not implicitly enable them.

## Source Integration

The integration points below are based on upstream commit [[444b29c93225](https://github.com/sgl-project/sglang/tree/444b29c932253d82b14ad4e09c4260b3d200bfbc)](https://github.com/sgl-project/sglang/tree/444b29c932253d82b14ad4e09c4260b3d200bfbc).

On Prefill, `send_kv_chunk()` continues to select KV ranges and resolve page mappings. Packing and compression would be submitted through the work queue used by `MooncakeKVSender.send()`, after source writes complete and with the source pages protected until their last read.

The Mooncake transfer layer remains responsible for moving bytes. `MooncakeKVManager._transfer_data()` receives buffer addresses and actual payload lengths; compression formats and restoration stay in the P/D adapter.

On Decode, restoration must finish before the receiver reports success. The integration follows the existing staging completion pattern and preserves the metadata and rank-wide checks used by `DecodeTransferQueue.pop_transferred()`.

GPU LZ4 through [[nvCOMP](https://docs.nvidia.com/cuda/nvcomp/c_api.html)](https://docs.nvidia.com/cuda/nvcomp/c_api.html) would be the initial backend, with a pinned dependency version and explicit block format. Its compression ratio and serving benefit remain to be measured.
## Validation and Performance Evaluation

Correctness requires byte-identical recovery of valid KV, including page boundaries, tail ranges, multiple chunks, prefix hits, and mixed compressed/uncompressed blocks. Tests cover page reuse, stale and duplicate descriptors, exhausted buffers, cancellation, disconnects, and failed restoration. They also verify disabled behavior, rejection of unsupported configurations, and metadata-only handoff. Real generation and task evaluation remain necessary to detect integration errors beyond the transformation itself.

Performance compares the existing raw P/D path, the new path with uncompressed payloads, and the compressed path. The first comparison measures framework overhead; the second explains compression’s contribution. The final benefit must be measured against the existing raw baseline.

For original bytes `S`, compressed wire bytes including metadata `Sc`, and effective bandwidth `B`, the approximate network saving is `(S - Sc) / B`. It must exceed the additional critical-path cost of packing, compression, result publication, restoration, synchronization, queueing, and contention. Network time is counted once. Overlapping stage durations are interpreted using the observed request path rather than blindly summed.

Initial evidence should pair raw handoff profiles with real model-generated KV compression measurements. Block and batch-size sweeps report wire reduction, uncompressed fallback frequency, and complete transformation cost. End-to-end tests vary prompt length, concurrency, prefix reuse, and network conditions while fixing model revision, KV format, parallelism, generation settings, and comparable cache state.

Measurements include handoff latency, first Decode continuation delay, TTFT, ITL, and throughput under a stated SLO, with P95/P99 and run-to-run variation. TTFT alone is insufficient because Prefill may return the first token before handoff completes. Traces distinguish KV availability, submission, transfer, and restore completion; cross-host timing requires a reliable time basis or correlation method.
