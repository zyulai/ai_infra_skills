## Overview

There is no fused MoE config for the NVIDIA L4 (AWS g6) in `vllm/model_executor/layers/fused_moe/configs/`. So Qwen3-30B-A3B-FP8 at TP2 on L4 runs on the default heuristic and logs `Using default MoE config. Performance might be sub-optimal!`. This PR adds a tuned L4 config for that shape:

- `E=128,N=384,device_name=NVIDIA_L4,dtype=fp8_w8a8,block_shape=[128,128].json`

Other Qwen3-30B-A3B FP8 checkpoints with the same expert shape load the same file, for example Qwen3-Coder-30B-A3B-Instruct-FP8. I only measured Qwen3-30B-A3B-FP8.

## Claims

- **Kernel.** Fused MoE kernel time is 1.2-5.4% lower for 7-240 and 385-528 tokens in every run, and 0.6-1.6% lower for 4 and 6 tokens. 5 tokens is equal.
- **Main's config elsewhere.** All other batch sizes (1-3, 241-384 and 529 and up) use exactly main's config. I checked this by computing the lookup for every batch size up to 16384.
- **Serving, concurrency 8.** Throughput is +2.2% and median TPOT is -4.0% (medians of 3 runs; Qwen3-30B-A3B-FP8, TP2, 2x L4).
- **Serving, concurrency 32.** No measurable change.
- **Serving, concurrency 1.** This runs main's config (1-token decode, 1024-token prefill), so it only shows the noise floor.
- **Accuracy.** GSM8K is unchanged.

## Validation

Setup:
- NVIDIA L4 24 GB, driver 580.159.04: AWS g6.12xlarge for tuning and serving, g6.xlarge for the kernel A/B.
- torch 2.14.0+cu132, Triton 3.8.0.
- vLLM main at feed3a4475. The MoE config lookup, `get_default_config` and the FP8 Triton MoE path are unchanged between that commit and this branch.

Tuning (default search space and batch sizes):

```bash
python benchmarks/kernels/benchmark_moe.py --model Qwen/Qwen3-30B-A3B-FP8 --tp-size 2 --dtype fp8_w8a8 --tune
```

**Kernel.**
- `benchmark_moe.py` without `--tune` on 1x L4: once without the file, and once with `VLLM_TUNED_CONFIG_FOLDER` pointing at it.
- 4 runs per arm in ABBA order (main, PR, PR, main, main, PR, PR, main).
- The batch sizes cover both edges of every range where this file's config differs from main's, and the points where main's default changes (5, 9, 17, 65). They also include spot checks where the config is main's.
- The command and raw output are in the comments.

**Serving.**
- Each run used a fresh `vllm serve Qwen/Qwen3-30B-A3B-FP8 -tp 2 --seed 0`, with 3 runs per arm, alternating between arms.
- The server log confirmed which config each arm loaded: `Using configuration from ...NVIDIA_L4...` versus `Using default MoE config`.
- The serving runs and GSM8K used the first commit's file. The second commit only changes 241-384, 529-768 and 1281-1792 tokens to main's config. Decode at concurrency 1, 8 and 32, and the 1024-token prefill chunks, use the same entries in both versions.

```bash
vllm bench serve --model Qwen/Qwen3-30B-A3B-FP8 --dataset-name random \
  --random-input-len 1024 --random-output-len 256 --random-range-ratio 0.0 \
  --num-prompts {30,100,200} --max-concurrency {1,8,32} --ignore-eos --seed 42 --num-warmups 4
```

The raw `vllm bench serve` output of every run is in the comments, with the GSM8K output.

**Accuracy.** `python tests/evals/gsm8k/gsm8k_eval.py --port 8000` (5-shot, 1319 questions, temperature 0): default 0.889, this PR 0.893.

## Details

The lookup picks the nearest key (ties go to the lower key), so each entry serves a range of batch sizes:

- **Tuned:** 4-240 tokens (keys 4 to 128, and 224) and 385-528 tokens (key 512).
- **Main's default config:** 1-3 tokens (keys 1, 2), 241-384 tokens (key 256), and 529 tokens and up (keys 544, 768, 1024, 1536, 2048, 3072, 4096).

- **Why the default above 240 and 528 tokens.** The tuned configs there use `BLOCK_SIZE_M` 16 (up to 256) and 32 (512). They lose once the average tokens per expert passes the M tile: up to 6% slower at 320 tokens, up to 14% at 384, and 2-5% at 640. So keys holding the default end each tuned range where it is still faster in every run.
- **The 224 key.** It holds the config the tuner chose for 64, 96, 128 and 256. This lets the 256 key hold the default.
- **1 and 2 tokens.** The tuned configs were faster in `benchmark_moe.py` but not end to end: decode at concurrency 1 was about 0.7% slower with them. The benchmark replays the same inputs, and the active experts' weights (at most 16 experts, about 38 MB) fit in the L4's 48 MB L2. So the default is kept.
- **1536-4096.** The tuned configs were not measurably faster, so the default is kept.
