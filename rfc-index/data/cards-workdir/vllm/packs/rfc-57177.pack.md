# RFC #57177: [RFC]: Retain MRV2 DBO CUDA Graph replay under DP imbalance through real-token staging

## 正文(PRD / 提案全文)

### Motivation.

I am investigating eager fallback under imbalanced data-parallel (DP) decode workloads with MRV2 DBO, building on #51700 and the original RFC #50738.

Consider a 128-token FULL CUDA Graph with two microbatches, each having a capacity of 64 tokens.

For DP ranks with token counts [63, 97], the smaller rank's second microbatch contains only padding.

The existing guard:

2 * min_tokens < descriptor.num_tokens

rejects the microbatched graph and falls back to eager execution across the DP group.

This preserves correctness but potentially sacrifices CUDA Graph replay even when the real tokens could be redistributed across the existing captured input layout.

The goal is to retain FULL CUDA Graph replay without changing the captured graph shape or the number of microbatches.

### Proposed Change.

Introduce real-token staging before CUDA Graph replay.

Instead of placing all 63 real tokens in the first microbatch and leaving the second microbatch empty, redistribute the real tokens across the two captured regions.

The proposal would reuse the existing graph capacity while ensuring that both microbatches contain real tokens.

The implementation must preserve token-to-request mappings, positions, attention metadata, KV-cache indexing, MoE dispatch/combine mappings, and output ordering.

The existing eager fallback should remain available for unsupported or unsafe cases.

The intended scope is limited to eligible decode workloads where the redistribution can be performed safely.

Preliminary Benchmark Results

I compared three configurations:

E: Original implementation, eager execution.
G: Original implementation, CUDA Graph enabled. MLA uses FULL_DECODE_ONLY in practice, and fallback still occurs.
A: Proposed DeepSeek adaptation with CUDA Graph and real-token staging.
