# Summary

Fixes #43096.

Add opt-in grouping for the **Detokenizer → TokenizerWorker** return path. Requests from one already-produced output are grouped by their original `http_worker_ipc` and sent once per destination instead of once per request.

**Measured benefit: +2.1% whole-machine client output throughput**, from a trace-free, single-variable, 16-round comparison on DeepSeek-V4-Pro (see "Benchmark evidence" below). The same change cuts return-hop IPC sends by ~94% and roughly halves return-worker CPU.

1. Register `SGLANG_OPT_DETOK_TOKENIZER_GROUP_SEND` as `EnvBool(False)` and read it once when the multi-HTTP-worker detokenizer event loop starts.
1. Reuse `_handle_output_by_indices()` from the merged Router grouped-send change (#42238); do not duplicate, downgrade, or modify the current message-field slicing logic.
1. Group only when at least two requests share a destination; when every request has a distinct owner, keep the original per-request path unchanged.
1. Construct every destination payload before sending the first one. If the splitter raises `_CannotSplitBatch`, fall back for the entire output to the original per-request path.
1. Keep send failures outside the fallback handler so an earlier successful send is never duplicated by a fallback/retry.

Enable before launching the service:

```bash
export SGLANG_OPT_DETOK_TOKENIZER_GROUP_SEND=1
```

Unset or `0` preserves the existing per-request path. The benchmark prototype used `SGLANG_DETOK_TOKENIZER_GROUP_SEND`; this upstream extraction uses the canonical `SGLANG_OPT_*` name and the typed `Envs` API. The prototype name is not an alias in this patch.

# Dependency and scope

The Router hop is addressed by #42238 (`[Perf] Reduce multi-detokenizer router IPC sends`), which is **merged into main** (merge commit `cb9bd1d`, 2026-10-09). This commit is its follow-up: it reuses the merged `_handle_output_by_indices()` helper and does not modify it, so the Router path is unchanged.

The incremental commit changes only:

1. `python/sglang/srt/environ.py` — default-off optimization switch.
1. `python/sglang/srt/managers/multi_tokenizer_mixin.py` — owner-grouped return sends and event-loop wiring.
1. `test/registered/unit/managers/test_multi_tokenizer_mixin.py` — actual message-class regression coverage.
1. `docs/docs/references/environment_variables.mdx` — environment-variable documentation.

Excluded: HTTP listener/reuse-port changes, Scheduler diagnostics or admission changes, output-chain trace/profiling, changes to the Router routing rule, and deployment-specific code.

Preserved: per-request owner, intra-destination order, first-destination order, current single/control request handling, watchdog behavior, and default-disabled behavior. No cross-message merge, delay window, or new output protocol is introduced.

# Benchmark evidence

Measurements use SGLang 0.5.17 at `29481685462732237d80d86076d6563e1f658102`: DeepSeek-V4-Pro, TP8/DP8, no MTP, 32 tokenizer and 32 detokenizer workers, decode graph maximum 310, maximum running requests 2480, memory fraction 0.96859, server seed 81095743. Upstream Router grouping was enabled for every run.

Client settings were identical: aiakperf streaming generate API, random dataset, concurrency 4960, 79,360 requests, input/output 60,000/1,000, 16 client processes, seed 0, temperature 0, top-p 1, fake bootstrap and ignore EOS enabled.

## Measured end-to-end benefit

1. **Trace-free whole-machine client output throughput (clean net gain).** Default shared-listener configuration, no tracing and no in-process probes, three runs each, only this switch changed (2026-10-11): disabled `42,297.97 / 42,564.88 / 42,306.00 token/s`; enabled `43,740.88 / 43,106.29 / 43,025.66 token/s`. Derived from the three-run means, **+2.13%**. Total duration moved from `1876.21 / 1864.45 / 1875.86 s` to `1814.32 / 1841.03 / 1844.48 s`.
1. **Instrumented A/B six-run** (all runs with output-chain tracing enabled; three disabled followed by three enabled): disabled `42,463.52 / 42,350.61 / 42,426.76 token/s`; enabled `43,547.89 / 42,816.95 / 43,280.41 token/s`. Derived from the three-run means, **+1.89%**. Reported separately from item 1 because reducing sends also reduces instrumentation work.
1. **Return-hop IPC calls:** disabled `79,376,257 / 79,376,257 / 79,376,257`; enabled `4,790,103 / 4,325,743 / 5,063,191`. The same `79,376,257` output events were carried in each run, so the enabled condition reduced actual return-hop send calls by approximately 93.62%-94.55%. Send counters include warmup/non-formal output events.
1. **Return-worker CPU:** detokenizer p50 decreased from `288.56% / 276.91% / 289.95%` to `107.51% / 99.74% / 105.75%`; TokenizerWorker p50 decreased from `731.38% / 732.34% / 730.86%` to `373.87% / 384.82% / 364.64%`. Percentages use single-core process-group CPU units.
1. **Batchsize and preallocation:** per-rank Batchsize p50 was `309 / 309 / 309` disabled and `310 / 310 / 310` enabled; p10 was `235 / 209 / 178` disabled and `307 / 215 / 307` enabled. The preallocation-queue p50 was `151 / 176 / 168` disabled and `282 / 293 / 284` enabled; `#transfer-req` was zero in all six runs.
1. **Correctness and completion:** all formal requests succeeded in all runs; output-stage request IDs were conserved and output lengths were 1,000. Text/token-ID bitwise equivalence was not measured.

## Qualification

1. The benefit is **conditional on the default HTTP listener topology**. When new connections are spread across HTTP workers per-worker (SO_REUSEPORT or an equivalent multi-listener server), grouping stops paying off: a same-workload comparison measured grouping enabled versus disabled at `42,733` versus `42,764 token/s` (means of three runs each) under per-worker listeners, compared with `43,291` versus `42,390` under the default shared listener. Grouping helps when one output batch concentrates in few HTTP workers, which is what the default listener produces; it does not itself fix connection imbalance.
1. This does not claim uniform latency improvement: median TTFT was `33.12 / 39.85 / 37.33 s` disabled versus `52.06 / 52.44 / 52.53 s` enabled; median E2EL was `86.02 / 92.89 / 89.93 s` versus `104.96 / 105.27 / 105.31 s`. Remaining HTTP-worker ownership imbalance and long tails are outside this patch.

# Validation and unit-test benefit

The unit tests demonstrate send-count reduction at the component level, not a timed performance speedup: the noncontiguous three-request/two-owner case produces two sends instead of three; the two-request/same-owner case produces one send instead of two. When every request has a different owner, the send count and per-request payloads remain unchanged. No standalone CPU microbenchmark or unit-test throughput gain was measured.

They also provide regression protection for the correctness and failure-boundary properties that make the optimization safe to enable:

1. They verify noncontiguous owner grouping preserves first-destination order, per-destination request order, and the original `http_worker_ipc` ownership.
1. They verify current string and token-ID message classes are grouped correctly, and that an embedding batch falls back to the per-request path (the shared splitter only covers `BatchTokenIDOutput`/`BatchStrOutput`), including optional wire fields through both pickle and msgpack round trips.
1. They verify the input output object is not mutated, unique-owner batches preserve the original per-request payload behavior, and outputs from separate messages are never accumulated together.
1. They verify `_CannotSplitBatch` falls back for the whole output before any grouped send, while a send error propagates without resending an earlier successful payload.
1. They verify the default-off behavior and the event-loop switch behavior.

Tests run separately in their own CPU Python processes:

PYTHONPATH=python python -m pytest test/registered/unit/managers/test_msgpack_ipc_roundtrip.py -q
```

1. The return-path component tests and the existing IPC serialization tests pass, run separately in their own CPU Python processes. (The local CPU environment is Python 3.10 / torch 2.5.1, which cannot import current `main`; the suite is re-run in CI.)
1. Repository-selected Ruff checks (`F401,F821,F823,UP037`) plus `F811`, Ruff formatting, isort and `git diff --check` passed.

Added coverage checks noncontiguous owner grouping and ordering, unique-owner equivalence with the original per-request path, no input mutation, no cross-message accumulation, latest optional fields through both pickle and msgpack, token-ID grouping with embedding fallback, default-off and enabled event-loop behavior, fallback after an earlier group has been constructed but before any send, and send errors without resending earlier results.
