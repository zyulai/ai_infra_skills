## 正文(PRD / 提案全文)

### Motivation.

LLM inference, especially for smaller and middle-size models, still fails to attain the theoretical maximums in TFLOPs and memory bandwidth. There are many reasons for this, from CPU overheads and kernel launch overheads to other pipeline bubbles like tail latencies in GPU kernel execution. While CUDA Graphs help to some extent, one promising approach is compiling megakernels that use precision scheduling. A megakernel is a single GPU kernel where SMs read and execute “tasks” corresponding to different compute or memory operations. This can eliminate a lot of the aforementioned latencies due to better overlapping of operations, reduced memory load, and higher hardware utilization.

MPK/Mirage is a megakernel compiler that takes in model definitions in its custom DSL and produces a single megakernel for the full model forward pass. This RFC proposes adding Mirage as an experimental torch.compile-based backend to vLLM. According to [the Mirage blog post](https://zhihaojia.medium.com/compiling-llms-into-a-megakernel-a-path-to-low-latency-inference-cf7840913c17), Mirage demonstrates a 20-25% improvement in forward pass latency over vLLM. I would kindly like to ask the Mirage team to add more thorough benchmarking results in the comments of this RFC to further motivate this integration.

### Proposed Change.

I propose adding a new Dynamo-based backend to vLLM that compiles the `fx.Graph` into an MPK megakernel. It would consist of a compatibility layer, which would convert the vLLM-produced graph into a Mirage-friendly graph, and a Mirage-based backend that would compile the second graph into a megakernel. The compatibility layer would live in vLLM and the backend would live in the `mirage` pip package. In the future, this compatibility layer can absorb any changes to Mirage or vLLM without requiring changes to the other.

Mirage prefers to receive information about higher level ops (RMSNorm, RoPE, quant) as opposed to low level torch operations. For good separation of concerns, the compatibility layer will convert vLLM custom ops into Mirage high-level ops (e.g. `torch.ops._C.rms_norm` -> `torch.ops.mirage.rms_norm`). If there are other differences in the Mirage / vLLM representation, they can all be handled in the compatibility layer, requiring no changes to either Mirage or (the rest of) vLLM when the other is changed.

Another important implementation detail is Paged Attention. I propose we add a new attention backend for Mirage. This backend does not execute attention operations (or just falls back to flex attention or manual torch implementation for correctness), but it produces a Mirage-friendly representation of attention when traced with Dynamo. We use the attention metadata builder in the same way as full cudagraphs, where static buffers are populated ahead of the forward pass, so that Mirage does not need to worry about any of the CPU logic for passing around attention metadata.

There are two possible ways to pass the static attention buffers to Mirage:
1. We fully trace all attention inputs to make sure they’re accessible in the `fx.Graph`.
1. We manually pass those buffers to Mirage at compile time, separate from the `fx.Graph`.

I believe we should start with approach 1 and fall back to 2 if we can’t get 1 to work, but I’m happy to hear alternative opinions.

I believe this integration would not require any changes to the compilation logic. When using Dynamo (and not vLLM compile), a custom Dynamo backend is already accepted, and we should be able to pass the compatibility layer object if `“mirage”` is passed as `CompilationConfig.backend`. I recall issues with the `DYNAMO_ONCE` torch compilation level (mode after #20283) where shape information was not correctly propagated, and this might need to be addressed. Because we’re skipping `VLLM_COMPILE`, there will be no caching, but that can be discussed in a later RFC, as it will likely require caching support in Mirage.

If the Mirage backend cannot compile certain regions, it should be able to execute their `fx.Graph` representations and still achieve correct results. We could also manually pass those regions to Inductor if they prove common. For easier debugging, it might be helpful to add a way to only compile specific subgraphs with Mirage and execute the rest with Dynamo. Finally, cudagraph capture is not necessary as we’re only launching a single kernel. However, with #20059, we should be able to use full cudagraphs anyway, which might be helpful if we have to split the graph on unsupported operations, generating multiple megakernels.

The infrastructure can be reused in the future for other experimental compilers using precision scheduling, megakernels, or any other experimental approach.

### Not considering
There are a couple of alternative approaches that could be used to integrate Mirage into vLLM that I believe are inferior to this proposal, but I list them here for completeness and to hear other perspectives.

Mirage could act as an Inductor backend instead of a Dynamo backend. That way, it would receive normalized IR, but AFAIU Inductor does not support passing the `fx.Graph` to a separate backend, only custom passes that modify the graph. I suppose we could replace the graph with a call to a single op, but that seems more trouble than it’s worth. 

We could also use the pattern matcher to replace specific patterns in the graph with Mirage ops. I believe this would be faster in the short run but provide only incremental benefits and end up being more fragile and harder to maintain in the long run. Mirage has demonstrated end-to-end correctness and performance, and I believe the benefits are the greatest at that level, so we should just begin with the end-to-end implementation.

There is also the alternative where we have separate Mirage-based model definitions in vLLM. That seems less preferable as it would mean we only support some models and it would likely have more integration issues with the rest of vLLM or at least require duplicate efforts.

Finally, megakernel precision scheduling allows for making batching and scheduling decisions on the GPU. I believe that is still too experimental and requires too many changes to vLLM to be part of this RFC. However, if it proves successful and async scheduling still suffers from CPU overhead, there’s no reason we can’t consider it in the future. It would require a new Mirage-based scheduler, `GPUModelRunner`, and `GPUWorker`, but the rest of the codebase could likely stay the same.
