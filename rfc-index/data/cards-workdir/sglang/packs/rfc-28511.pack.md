## 正文(PRD / 提案全文)

## Summary

[ReplaySSM](https://dao-lab.ai/blog/2026/replayssm/) (Dao AI Lab, 2026) is a technique that makes the **recurrent decode step of linear-attention / SSM layers faster** by turning a *read + write* of the full recurrent state every step into a *read-only* step plus a periodic *flush*. The recurrent update is linear, so the state can be reconstructed on demand from a checkpoint plus a tiny ring buffer of the last `L` steps' `(d, k, g)` records — and the output can be read out **without ever materializing the full state matrix** on non-flush steps.

This is a **bandwidth** optimization for a **memory-bound** kernel: GDN decode at batch ≥ 64 runs at 70–79% of peak HBM bandwidth, so halving per-step state traffic translates almost directly into speedup.

This RFC tracks porting ReplaySSM to SGLang in two independently-shippable parts:

| Part | Scope | Resource won | Status |
|------|-------|--------------|--------|
| **A** | Buffered output-only GDN **decode** kernel + integration | HBM **bandwidth** → decode speedup | **Implemented** — [#28451](https://github.com/sgl-project/sglang/pull/28451) |
| **B** | ReplaySSM **spec-decode** verify (chunked, ring across verify steps) | bandwidth at high batch | **Implemented** — [#28695](https://github.com/sgl-project/sglang/pull/28695) |
| (rel.) |  Compact linear spec cache | spec-decode **memory footprint** | **In review** — [#27658](https://github.com/sgl-project/sglang/pull/27658) |

Upstream reference: vLLM ReplaySSM (commit `3c85112`), files `fused_recurrent_replayssm.py` (decode) and `gdn_replayssm_spec_decode.py` (spec).

## Background & motivation

### The problem

GDN (Gated DeltaNet, the Qwen3.5 / Qwen3-Next lineage) and KDA (Kimi Delta Attention) decode maintain a fixed-size recurrent state `S` of shape `[HV, V, K]` per slot per layer (~1 MB in bf16 for `HV=32, K=V=128`). The standard packed decode kernel reads `S` from HBM, applies a rank-1 update, and writes `S` back **every** decode step — roughly `2 * |S|` of state traffic per step (read + write).

This kernel is **memory-bound** at serving batch sizes. Measured on H20-3e (peak copy bandwidth ~3.8 TB/s):

| batch | achieved HBM bandwidth |
|-------|------------------------|
| 1     | 2% (launch/latency bound) |
| 16    | 29% |
| 64    | **70%** |
| 256   | **79%** |

When a kernel is this bandwidth-bound, **reducing bytes moved per step ≈ reducing runtime**.

![Latency breakdown showing the SSM decode step is dominated by state memory traffic](https://dao-lab.ai/assets/img/2026-06-15-replayssm/motivation-latencybreakdown.png)

*Latency breakdown (Nemotron-3-Super-120B-A12B-NVFP4, batch 256, single B300) — the recurrent state traffic dominates the step. From the [Dao AI Lab ReplaySSM blog](https://dao-lab.ai/blog/2026/replayssm/).*

### The idea

Keep the last flushed state `S0` (the **checkpoint**) frozen, and a small per-slot **ring buffer** of the last `L` steps' `(d, k, g)`. On a non-flush step, append the new `(d, k, g)` and reconstruct the readout from `S0` + the ring. Only every `L` steps **flush**: fold the ring into `S0` and write the full state back.

`S0` is still **read** every step, but the full-state **write** is amortized from every step to every `L` steps. Per-step state traffic drops from read+write (`~2|S|`) to read-only (`~|S|`) plus tiny ring appends — roughly halved. The ring records are negligible compared to the `[V, K]` state.

![ReplaySSM caches recent SSM inputs in a ring buffer and reconstructs state on the fly, writing back only on flush](https://dao-lab.ai/assets/img/2026-06-15-replayssm/headline_approach.png)

*ReplaySSM caches recent SSM inputs instead of storing the recurrent state every step, reconstructing states on the fly and writing back only when the buffer is full. From the [Dao AI Lab ReplaySSM blog](https://dao-lab.ai/blog/2026/replayssm/).*

## Core algorithm

Single head, single decode step (matches `fused_recurrent_gated_delta_rule_packed_decode` exactly):

$$\alpha = \exp(g)$$
$$d = \beta (v - \alpha (S k))$$
$$o = \alpha (S q) + d (k^\top q)$$
$$S' = \alpha S + d k^\top$$

Because the state update is **linear** in `S`, after `m` buffered steps the state before the current token unrolls to:

$$S = A \cdot S_0 + \sum_{j} w_j \cdot d_j k_j^\top$$

$$A = \prod_i \alpha_i \qquad\text{(total decay)} \qquad w_j = \prod_{i > j} \alpha_i \qquad\text{(replay decay of entry } j)$$

The bookkeeping is one rule: the checkpoint `S0` is decayed by **all** buffered `\alpha`; each older entry `j` is decayed by every `\alpha` that came **after** it.

**Output-only readout.** The output needs only `S q` and `S k`, both matrix-vector products. Substituting the unrolled `S`:

$$S q = A (S_0 q) + \sum_j w_j (k_j^\top q) d_j$$

`(k_j^\top q)` is a **scalar**, computed first; the `[V, K]` outer product `d_j k_j^\top` is **never built in HBM** on a non-flush step. The reconstruction sum is a small GEMM, run on **tensor cores** (see Precision below).

![Two routes to the same output: build the full state then read it, versus form the key-query scalar first](https://dao-lab.ai/assets/img/2026-06-15-replayssm/output_only.png)

*Two routes to the same output. The state-and-output route builds the full state then reads it; the output-only route forms the scalar key-query product first, so the state matrix is never materialized. From the [Dao AI Lab ReplaySSM blog](https://dao-lab.ai/blog/2026/replayssm/).*

**Degenerate L=1.** The ring is always empty and every step is a flush, so the reconstruction term vanishes, `A = 1`, and the kernel reduces *algebraically and numerically* to the baseline packed decode — a bit-exact anchor for testing.

## Scope & work breakdown

### Part A — buffered output-only GDN decode (implemented)

A standalone decode kernel plus full runtime integration. **Implemented in [#28451](https://github.com/sgl-project/sglang/pull/28451).**

- New kernel + wrapper: `fused_recurrent_gdn_replayssm_decode(...)`, ported from vLLM `3c85112` with SGLang's packed GDN decode layout.
- Memory pool: per-slot ring buffers `replayssm_{d,k,g}` and a persistent `replayssm_write_pos`; reset at slot alloc and on COW.
- Backend dispatch: `TritonGDNKernel.packed_decode` routes to the ReplaySSM kernel when ring kwargs are present.
- CUDA-graph safety: static per-bs `write_pos` buffer, refreshed/advanced outside capture.
- Radix coordination: device-side `force_flush` aligned byte-for-byte to the mamba radix track snapshot condition (zero off-by-one), so the ring is folded into the checkpoint on exactly the step the radix cache reads `temporal[slot]`.
- Server args: `--enable-gdn-replayssm`, `--gdn-replayssm-cache-len` (default 16).

Files touched: the new kernel/test/bench, `mem_cache/memory_pool.py`, `attention/hybrid_linear_attn_backend.py`, `attention/linear/gdn_backend.py`, `attention/linear/kernels/gdn_triton.py`, `attention/mamba/mamba2_metadata.py`, `configs/mamba_utils.py`, `server_args.py`.

### Part B — ReplaySSM spec-decode verify (proposed, gated)

The upstream `gdn_replayssm_spec_decode.py` is **not** a state-cache tweak — it is a full **chunked verify forward** kernel that:

- computes verify outputs for all draft tokens via the chunked delta-rule UT-transform `(I + A)^{-1}`,
- reconstructs the carried state output-only from a **circular ring carried across verify steps**,
- flushes the full state only **every `L` committed tokens** (not every verify step),
- runs the reconstruction on tensor cores.

This would convert spec-decode's full-state write from **every verify step** to **every `L` committed tokens** — a bandwidth win at high batch. It also makes rejected-draft rollback a pointer move on the ring rather than a state write-back:

![ReplaySSM caches each draft's raw inputs, so rolling back rejected drafts is a pointer move with no state write-back](https://dao-lab.ai/assets/img/2026-06-15-replayssm/rollback_solution.png)

*ReplaySSM caches each draft's raw inputs, so rolling back rejected drafts is just a pointer move with no state write-back. From the [Dao AI Lab ReplaySSM blog](https://dao-lab.ai/blog/2026/replayssm/).*

**Relationship to #27658 (important).** #27658 ("compact linear spec cache replay") already captured the **memory** half of this idea for spec-decode: it stores compact `(k, Δv, decay)` per draft token instead of full intermediate states (2.32 GB → 0.06 GB), replays the accepted state once at the accept boundary in full fp32, and integrates the radix track snapshot + KDA. It explicitly reports **no throughput change** (verify was not bandwidth-bound at its 32–64-concurrency test point). Part B is **complementary, not a replacement**: it would add the bandwidth/speed half on top of #27658's memory/correctness infrastructure.

**Decision gate (do this before writing Part B code).** Measure the achieved HBM bandwidth of the spec-decode verify GDN forward at the *target* serving batch:
- ≥ ~70% → the full-state-write amortization is a real speedup; Part B is worth prototyping.
- < ~30% → same conclusion as #27658; the rewrite buys no time. Do not build it.

The upstream blog's own breakdown shows where the spec-decode gain comes from (kernel vs verify forward vs full decode step) and the orthogonal concurrency benefit — useful priors for what to expect:

![Speedup over the spec-decode baseline at kernel, verify-forward, and full-decode-step levels](https://dao-lab.ai/assets/img/2026-06-15-replayssm/spec-speedupbreakdown.png)

*Speedup over vLLM's speculative-decoding baseline at the kernel, verify forward pass, and full decode step levels. From the [Dao AI Lab ReplaySSM blog](https://dao-lab.ai/blog/2026/replayssm/).*

![Maximum decode concurrency under a fixed HBM budget with speculative window 4](https://dao-lab.ai/assets/img/2026-06-15-replayssm/spec-maxconcurrency.png)

If built, Part B should: base on #27658's branch / its successor in `main` (**not** the Part A decode branch — Part A shares no spec logic with #27658, only the abstract idea; the real spec infra lives in #27658); reuse #27658's compact cache / radix track / KDA wiring; port the **early-flush invariant** exactly (`max_cache_len >= 2 * max_spec_len`, flush one window early so the circular cache never overflows the spec window — an overflow feeds the rejection sampler an uninitialized logit and desyncs the committed state); be gated behind a flag and default off.

### Out of scope (possible follow-ups)

- KDA decode (shares the backend; different gating — not wired in Part A).
- Lower-precision (bf16/fp8) ring/checkpoint to stack additional traffic savings.
- Batch-adaptive `L` (fall back to `L=1` at small batch where ReplaySSM cannot help and its extra reconstruction compute would otherwise be a small net loss).

## Design & integration concerns

The kernel is the easy half; the hard part is wiring a stateful, ring-buffered kernel into continuous batching + CUDA graphs + the radix prefix cache.

1. **`write_pos` is a per-slot decode cursor, not derivable from `seq_len`.** It must track the physical mamba slot (reset to 0 at slot alloc, when the post-prefill checkpoint is correct and the ring is logically empty), and advance **once per forward** (shared by all GDN layers of a step), not per layer.
2. **CUDA-graph safety.** `write_pos` is a static per-bs buffer captured by the graph and advanced in-place outside capture; the advance is guarded by `not in_capture` so warmup/capture do not corrupt the persistent counter.
3. **Radix `force_flush` alignment.** The radix cache snapshots `temporal[slot]` at fixed track boundaries; between flushes the checkpoint is stale. `force_flush` forces a flush on exactly those steps, computed from the identical condition the scheduler uses (zero off-by-one). `cache_valid` still uses the true `write_pos` — never fake `write_pos = L-1` to force a flush, or the kernel reads uninitialized ring entries.
4. **COW reset.** On a prefix-cache hit, `MambaPool.copy_from` copies the (always-flushed) snapshot into the private slot and resets that slot's `write_pos` to 0 so the destination ring starts empty.

## Precision & correctness

- **Mathematically lossless** — the reconstruction is an exact algebraic identity.
- **Not bit-exact in floating point** — the reconstruction GEMM runs on tensor cores (TF32 for fp32, bf16 tensor cores for bf16) and reassociates the recurrence, so it differs from the sequential baseline at the `~1e-4` (TF32) / `~1e-3` (bf16) level. This matches the upstream vLLM kernel, which uses the same tensor-core path and validates at the same tolerances (fp32 `atol 1e-4`, bf16 `atol 2e-2`).
- **Accuracy-neutral end-to-end** — per-step decay `\alpha < 1` attenuates old reconstruction error (bounded, re-anchored at each flush). Note that baseline GDN inference is already non-bit-exact across batch/chunk sizes; this introduces no new error class.
- Forcing IEEE precision on the reconstruction dot would make it bit-exact but disables tensor cores and makes the kernel **10–20× slower** — bit-exactness and the speedup are mutually exclusive by construction.

## Validation methodology (Part A)

Layered, weakest-to-strongest:

| Layer | Method | Result |
|-------|--------|--------|
| Kernel math | unit test vs `..._packed_decode` | fp32 `L=1` bit-exact (`atol 2e-6`); `L>1` within tensor-core tolerances; `force_flush` mid-buffer passes |
| Integration plumbing | short greedy decode, flag-on vs baseline | byte-identical (eager / CUDA-graph / radix all on) |
| **End-to-end correctness** | **GSM8K, radix + CUDA-graph on** | **flag-on 0.900 vs baseline 0.850 — within noise, no regression** |
| Performance | microbench + bench_serving | see below |

The standalone kernel test caught the tensor-core trap (an `input_precision="ieee"` dot that silently disabled tensor cores → 15× slowdown) **before** any integration work.

## Performance (honest, model-dependent)

- **Kernel microbench:** 1.2–1.5× at batch ≥ 16 with `L=8`; slightly slower at batch 1 (overhead-bound, not an operating point — the reconstruction compute is not hidden when there is no bandwidth pressure).
- **End-to-end (Qwen3.5-35B-A3B, 128 concurrent):** ~2.3% TPOT improvement.

The e2e gain is much smaller than the kernel gain because Qwen3.5-35B-A3B is **MoE-heavy**: the GDN linear layers (where the kernel wins) are a small fraction of decode cost, diluted by MoE and full-attention layers. **GDN-dense models would gain substantially more.** This is a model-dependent optimization, not a universal speedup.

The theoretical ceiling is `~0.57×` traffic (`L=8`) → `~1.75×`; the realized 1.2–1.5× reflects <100% bandwidth utilization, the still-every-step `S0` read, the added reconstruction compute, and ring traffic.

For reference, the upstream blog reports the same shape — strong kernel-level speedup that dilutes to a smaller end-to-end gain on MoE models, and a clear dependence on buffer size `L` and batch:

## Open questions / risks

1. **Is spec-decode verify bandwidth-bound at realistic serving batch?** This single number decides whether Part B is worth building (see Decision gate). Spec-decode is often latency-focused (low batch), where the win may be marginal.
2. **Part B integration risk is high** — it is a forward-kernel rewrite (~650 lines, chunked UT-transform) with a subtle early-flush correctness invariant, not a surgical cache swap like #27658.
3. **Tensor-core precision** — accepted as accuracy-neutral (GSM8K parity), but worth a config escape hatch for anyone who needs the slow bit-exact path.
4. **Scope of models** — Part A is GDN-only; KDA shares the backend but has different gating.
