## Purpose

Co-authored by: ErinYin <liang.yin@daocloud.io>

Humming grouped MoE currently retains permutation scratch in every layer, so its persistent memory grows with the number of layers. Marlin lock buffers are also owned by individual layers or kernels, tying their lifetime to weight preparation and reload.

This PR gives both resources a shared owner in `WorkspaceManager`:

- Add `get_persistent_resource(key, factory)` for objects with stable storage and `get_persistent(...)` for fixed-shape tensors. Resources are cached separately for each `(ubatch, lane)` and must exist before workspace locking.
- Share compatible Humming `MoEPermuteScratch` objects across sequential layers. Compatibility includes capacity, routing dimensions, device, hidden size, and dtype.
- Acquire Marlin locks at execution time, with separate buffers for concurrent CUDA streams as well as ubatches and lanes. Zero-initialize once; successful Marlin calls restore their counters to zero.
- Resolve dense Marlin workspace lookup inside a runtime custom op so `torch.compile` does not trace execution-context selection.
- Preserve standalone allocation when no workspace manager exists and support explicit Marlin workspaces.

### Relationship to existing work

This combines the direction of #50626 and #56764 with a general resource API. #50626 is the earlier tensor-only Marlin implementation; #56764 adds a Humming-specific cache and accessor to `WorkspaceManager`. Here, the manager handles resource lifetime and execution-slot isolation, while each backend defines its own resource and compatibility key. The intent is to consolidate both changes around that shared API.

Addresses the memory issue in #56759 and relates to the runtime-storage ownership discussion in #48312. Searches for those issues and for `marlin workspace`, `workspace persistent`, and `humming scratch` found the related PRs above; the distinction is the combined, backend-independent resource API.

#55105 remains complementary: its dispatch-capacity and runtime-dtype fixes can feed into the shared scratch accessor, while its activation-buffer fixes stay in Humming. Those fixes are not included here.

PyTorch 2.13.0+cu130, CUDA 13.0, FlashInfer 0.6.17.

Live PyTorch GPU allocation immediately after initialization, in GiB (2^30 bytes):

| Max batched tokens | Before | After | Saved |
| --- | ---: | ---: | ---: |
| 2048 | 33.412 | 30.953 | **2.459** |
| 8192 | 41.352 | 31.516 | **9.836** |

The number of scratch objects falls from 40 to 1. At 8192 tokens, their storage falls from 10330.684 MiB to 258.267 MiB: **97.5% less scratch memory**. Each distinct configuration or concurrently active execution slot still needs separate storage. Fixing the KV-cache budget keeps vLLM from consuming the saving as a larger KV cache.

The 8192-token pair ran sequentially on the same reserved GPU, with fresh processes. The 2048-token baseline and repeated full baseline used another B300 of the same model. These measurements do not establish a latency improvement.
