## 正文(PR 描述)

## Purpose

This keeps multimodal PrefixLM batches on the native FlashInfer backend. It is the vLLM adapter for FlashInfer's mm-prefix batch-prefill wrapper: it builds per-query `[start, end]` rows from request metadata, decides when the path is eligible, and calls the wrapper, whose attention variant evaluates `(causal AND sliding_window) OR mm_prefix` on every KV tile. No `O(qo_len * kv_len)` mask is materialized; the ranges are one `int32 (N, 2)` buffer sized by scheduled tokens, 128 KiB at 16384 tokens. The prefill still traverses the full rectangle, so the gain is memory, not FLOPs.

The wrapper comes from [FlashInfer #5189](https://github.com/flashinfer-ai/flashinfer/pull/5189) and has shipped since 0.7.1, so main's pin already has it. FlashInfer builds the variant's JIT module when the wrapper is constructed.

The mm-prefix wrapper is planned beside the regular prefill path rather than replacing it, so text-only batches, decodes and layers whose ranges are cleared at forward time (Gemma 4 full-attention groups) keep trtllm-gen or FA3 with main's query dtype and scales. On the SM100 family `TRITON_FLASHINFER` stays the automatic choice; an explicitly selected `FLASHINFER` serves the ranges natively and does not advertise large pages. An SM100 NVFP4 cache keeps its V scale factors in the trtllm-gen swizzle, so native mm-prefix accepts it only when FlashInfer's wrapper takes `v_sf_swizzled` and rejects it otherwise. That option comes from [FlashInfer #7012](https://github.com/flashinfer-ai/flashinfer/pull/7012), which shipped in FlashInfer 0.7.3, the version main has pinned since #65930. One predicate, `_native_mm_prefix`, decides eligibility for selection and the builder's range state, so the composite's FlashInfer child keeps main's routing and allocates no range buffers. On SM90 the automatic priority still prefers the `TRITON_FLASH_ATTN` composite; this PR leaves that priority unchanged, while native FlashInfer can be selected explicitly. For native mm-prefix, FlashInfer rejects `fp8_e5m2`, `nvfp4_4over6`, sinks and DCP at selection, and `logits_soft_cap` at engine start.

An `fp8` or `fp8_e4m3` cache takes the native path too. fa2 has no FP8 query or output, so only the mm-prefix call adapts: a query the layer already quantized to FP8 goes back to the model dtype losslessly with its q_scale, and a fused FP8 output is quantized after the call. Native mm-prefix models are offered FP8 output fusion only, as the composite is.

#47118 also enables FlashInfer for Gemma 4 multimodal models, but only for text-only requests; this PR serves the mm-prefix batches.

## Test Result

On sm_80 with FlashInfer 0.7.2, the first command gives 24 passed and 22 skipped (FA4 mask_mod), the selector tests give 25 passed with the Hopper and Blackwell cases skipped, and the Gemma 3 E2E test passes with both the automatic backend and `FLASHINFER`. The selector tests cover the SM100 automatic composite against an explicit `FLASHINFER` for no-quant and FP8 KV, and an NVFP4 cache with and without `v_sf_swizzled`. Before the review cleanup, code equivalent to `37c1fa3980` also passed GPU tests against a dense float32 reference on sm_80 and sm_103, including an FP8 KV cache; those were replaced by the E2E test in review. pre-commit passes.

On sm_103 with `RedHatAI/gemma-4-12B-it-NVFP4` and an FP8 KV cache, explicit `FLASHINFER` was measured against `TRITON_FLASHINFER` with one run per configuration, with code equivalent to `37c1fa3980`, before the cleanup. Text throughput was 0.2% lower at concurrency 32; image throughput was 0.8% lower at concurrency 1 and 0.5% and 1.6% higher at 32 and 128; ChartQA (500 examples, relaxed accuracy) was 68.2 against 66.8. These numbers describe this run only. The compiler-fused FP8 output path has not been verified on a full model. Gemma 3 4B with an NVFP4 KV cache, which `TRITON_FLASHINFER` rejects on SM100, scored 43.8 on the same ChartQA set against 43.6 with FP8 KV.

- The concurrency-32 FlashInfer figure is the mean of three seeds (10032/10033/10034: 426.6 / 427.0 / 426.7, spread 0.09%). The `TRITON_ATTN` figure on that row is a **single seed**, so its 2.6% lead carries an unmeasured seed-variance error bar and should not be read as a real difference. Concurrency 1 and 128 are single-seed on both sides.
- At concurrency 32, the measured inputs are 1295-1297 tokens with 1024 output tokens, putting the maximum full-request footprint at approximately 74K tokens, above either KV budget; concurrency 128 is more constrained. Scheduling and cache pressure can therefore affect these rows, and they do not isolate attention-kernel cost.
- The two arms do not get identical KV budgets: FlashInfer reserves its attention workspace during profiling and lands at 49,593 tokens against the baseline's 51,515. The FlashInfer configuration is therefore measured with approximately 3.7% less KV capacity.
