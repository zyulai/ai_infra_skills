## 正文(PR 描述)

## Motivation

Under `--enable-dp-attention`, a decode step can compute its token at a RoPE position one past the row's own KV slot, with a causal window one token too wide. This corrupts generation for every request in flight on an affected step. Bisected to #36288 (`ff5578eb4e`), which added the DP decode->extend conversion.

`convert_decode_to_extend` derived the extend prefix from the request's token list:

```python
delta = 0 if self.enable_overlap else -1
self.prefix_lens = [len(r.origin_input_ids) + len(r.output_ids) + delta for r in self.reqs]
```

That assumes `output_ids` always trails `seq_lens` by one step under overlap. It doesn't: `seq_lens` advances only on an iteration that runs `prepare_for_decode`, while a pending result lands regardless, so an iteration that runs prefill instead of decode drains the lag. Extend positions are `arange(prefix_len, prefix_len + extend_len)`, so a 1-token extend needs `prefix_len == seq_len - 1`; with the lag drained the old formula gives `prefix_len == seq_len`.

How often that fires is a property of the traffic: it takes an iteration that runs prefill while a request is mid-decode, so it is common under concurrent load with continuous arrivals and rare on an otherwise idle server. Instrumentation at 512-way concurrency caught it on ~31% of converted requests (1226 / 3986).

The DP-padding decode->extend path already encodes the right invariant (`extend_prefix_lens = self.seq_lens - 1`); this makes the scheduler side agree.

## Modifications

1. **`convert_decode_to_extend`**: derive `prefix_lens` and `extend_range` from `seq_lens_cpu`. Also removes a contradiction the two carried by construction (`prefix_lens` said the prefix was `full_len`, `extend_range` put the new token at `full_len - 1`). Sliced to `bs` because `append_beam_tail` adds rows without reqs, and `zip(strict=True)` so any other divergence raises.
2. **`_local_prefill_cuda_graph_vote`**: reject beam requests. Two hazards — member rows have no req for the reqs-aligned lists, and `process_batch_result` dispatches on `forward_mode`, so a converted batch commits beam requests via `commit_prefill` instead of the batch-level `commit_decode` fold. The second applies whenever `beam_group` is set, so the predicate is the scan, not `beam_tail`.
3. **`mix_with_running`**: same convention, same point in the loop, same contradiction — derive it the same way. **Hardening, not a measured fix**: gsm8k over `--enable-mixed-chunk` shows no delta (94.47/94.16 before, 94.24/94.54 after), since that workload never blocks the mix so the lag never drains. Spec branch is bit-for-bit the old `delta = -1`. Happy to drop this hunk if reviewers prefer a minimal PR.

Tests: new registered CPU test pinning both halves of the geometry in the lag-present and lag-drained states plus beam alignment and the strict-zip failure (all four fail pre-fix); both directions of the beam gate in `test_dp_attn.py`; and a fixture fix in `test_schedule_batch_out_of_place.py`, whose `seq_lens_cpu` was left at the auto-filled `arange(1)` and never read by the old code. Nothing in `test/` covered `convert_decode_to_extend` before.

## Accuracy Tests

gsm8k, 1319 examples, temperature 0, `--num-threads 512 --max-tokens 512`. `Qwen/Qwen3-30B-A3B-Instruct-2507`, 4x GB300, `--tp-size 4`. DP adds `--dp-size 4 --enable-dp-attention`.

|---|---|---|
| main | 94.24 / 94.39 / 94.24 | **71.34 / 70.20 / 70.43** |

Reverting, gating off, and fixing all recover the same ~94.2, so the conversion is the sole source. `test/registered/unit/managers/`: 630 passed, 4 skipped, 610 subtests.

## Speed Tests and Profiling

Same runs as above; completion-token counts are within 0.5% across variants (~293k), so latency is comparable.

| DP attention | latency | output tok/s |
|---|---|---|
| this PR | 15.1 / 15.1 / 15.2 s | 19323 / 19452 / 19253 |
| conversion gated off | 34.2 / 33.2 / 34.0 s | 8550 / 8873 / 8634 |
| #36288 reverted | 33.4 / 34.2 / 32.0 s | 8793 / 8611 / 9200 |

The conversion is worth ~2.2x, so fixing the geometry beats reverting: a revert is correct but drops DP attention below plain TP (15.1 s). Against the broken build (20.4k tok/s) this is ~5% slower, but that build produces wrong output and is not doing the same work.
