# [RFC] Directory Structure Does Not Align with Non-PyTorch Implementations

## Motivation

We are implementing a MindSpore backend for SGLang. Meanwhile, we have also been monitoring developments related to sglang-jax. We anticipate that SGLang will subsequently integrate more models implemented with non-PyTorch frameworks. Therefore, we aim to establish a unified organization and management solution that maintains compatibility with the existing PyTorch-based model implementations while preserving the simplicity and usability of the SGLang framework.

## Current Status

### Current SGLang Architecture

We expect the unified changes to model management to be highly generalizable, enabling seamless integration of models implemented with different frameworks. However, we have observed significant differences between the current implementation approach of sglang-jax and the MindSpore implementation we are developing.

* **sglang-jax**: Provides a complete SGLang framework implemented entirely with JAX, and naturally includes corresponding JAX-based model implementations as a result.
* **MindSpore Implementation**: Aims to maximize compatibility with the existing PyTorch-based implementations in the SGLang framework, with only necessary input/output conversions performed at the model invocation stage.

Currently, model implementations are primarily concentrated in the `sglang.srt.models` module. Models are registered via a registry using the `EntryClass` defined in each model implementation. Additionally, a unified Transformers fallback interface is provided to handle cases where a registered model cannot be found. And of course, these model implementations heavily depend on the `sglang.srt.layers` module and many other SGLang infra.

### Current MindSpore Implementation Approach

Since the MindSpore implementation reuses the core workflow of the SGLang framework, it only needs to focus on model integration. Drawing inspiration from the Transformers fallback method, we have added a dedicated `mindspore.py` file in the `models` module to serve as the primary entry point for MindSpore.

* Specific MindSpore model implementations are placed in a separate directory named `mindspore_models`.
* This directory also contains various required layer implementations and wrappers for the SGLang framework (e.g., components for fetching communication groups).

For detailed implementation logic, please refer to our initial PR: #9234.

### Key Issues

While adding a dedicated module within the `models` directory can address the current MindSpore integration needs, this approach fails to meet long-term design requirements for the following reasons:

1. As MindSpore support evolves—with increasing model complexity and expanded feature coverage—more layer implementations and conversions for infra from the inference engine will be required. These components are not suitable for permanent placement within the `models` module.
2. Integration approaches for other frameworks into SGLang will not all align with MindSpore’s approach. For example, if sglang-jax is to be merged with the main SGLang codebase, it will introduce various new implementations beyond the `models` directory, rather than being confined to a single `models` folder.

## Proposal

We hope to collaborate with the community to discuss and finalize a solution for integrating multi-framework implementations into SGLang. A preliminary proposal is outlined below:

### 1. Framework-Specific Directory Structure

Create dedicated directories under `sglang.srt` for different framework implementations (e.g., `sglang.srt.mindspore`, `sglang.srt.jax`). These directories will serve as implementation paths for third-party framework support (in addition to PyTorch), allowing developers to work within their respective framework-specific paths—whether implementing conversion solutions for SGLang’s native workflow or rebuilding components based on new frameworks. Conversion or reimplementation of existing components can be carried out as needed.

Within the core SGLang framework, only minimal references to each `sglang.srt.PLATFORM` will be retained. For instance, the `mindspore.py` file in the `models` module will be kept as the primary entry point for MindSpore.

```shell
sglang
├── eval
├── lang
└── srt
    ├── mindspore  	# Platform support for MindSpore
    ├── jax			# Platform support for JAX, if necessary
    ├── ...	  		# Platform support for any other framework
    ├── layers
    ├── distributed
    ├── models
    ├── ......		# other srt modules
```

### 2. Conditional Dependency Installation

During the installation phase, different dependency options can be provided based on various application scenarios (e.g., `srt_mindspore` for MindSpore support). This allows users who need MindSpore model implementations to install the required dependencies via the command below, while all other usage methods (e.g., API calls, configuration) remain consistent with SGLang’s original implementation:

```shell
pip install -e python[srt_mindspore]
```

## Summary

The above outlines our current thoughts on unifying the multi-framework model management architecture for SGLang. We would greatly appreciate feedback from the community, including:

* Whether there are existing architectural adjustment designs related to this topic that we should align with;
* Any suggestions for optimizing the proposed directory structure or dependency installation approach;
* Other considerations we may have overlooked for long-term framework extensibility.
