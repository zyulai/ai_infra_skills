## 正文(PR 描述)

## Motivation

Several invalid sampling values pass request parsing and only fail later, in serving or in the scheduler. Chat output-limit handling also used `max_completion_tokens or max_tokens`, so an explicit `0` fell back to the legacy limit.

Observed on a live server (Qwen2.5-0.5B-Instruct, vocab size 151936):

- A huge `n` is rejected only after the request has been expanded `n` times: `/generate` with `n=3,000,000` took ~113 s and grew server memory by ~18 GB before returning 400. On `main`, `n=300,000` did not complete within 15 minutes and server memory passed 90 GB. `n=0` was not rejected with a clear message.
- `top_logprobs` above the vocab size (for example 200000) kills the server, because `torch.topk` fails past the vocab size. A list or negative `top_logprobs_num` garbles a batch. A request with logprobs off can crash it too: its count is not checked, but the scheduler takes `topk` over every request's count when any request in the same prefill batch wants logprobs.
- A large `logit_bias` overflows to `inf` in the float32 bias tensor, or after the sampler divides by a temperature below 1, and NaNs the softmax. A sampled request with a `1e39` bias, or `3e38` at `temperature=0.5`, returns garbage tokens (`[0, 0, 0, 0]`) and, with `top_p`, kills the scheduler.
- A stop id outside the vocab (for example `-1` or `999999`) kills the server with a CUDA device-side assert once the `min_new_tokens` penalizer runs. The penalizer covers the whole batch when any request sets `min_new_tokens`, so the stop id and the `min_new_tokens` can come from different requests. With beam search, a stop id from `2**63` to `2**64 - 1` fails the scheduler's int64 tensor build and kills the server.
- An explicit `max_completion_tokens=0` is ignored.

## Modifications

- `n` is validated by one function, `sampling_params.validate_n`. It requires an `int` (`bool` rejected) of at least 1, at most `SGLANG_MAX_BATCH_REQS_PER_HTTP_REQ` (default 4096, the limit the Rust server already applies to `n`). A negative value disables the upper bound, as in the Rust server. `GenerateReqInput._handle_parallel_sampling` calls it before any input is multiplied by `n`, for dict and list `sampling_params`, and `SamplingParams.verify` calls it as a backstop.
- The chat and completions request models keep OpenAI's limit, `OPENAI_MAX_N = 128` (`protocol.py`). OpenAI requests then also pass `validate_n`, so their effective limit is the smaller of the two.
- `top_logprobs_num` must be an integer in `[0, vocab_size]` when logprobs are requested (checked next to `token_ids_logprob` in `tokenizer_manager`). When logprobs are off the count is not checked and is forwarded to the scheduler as `0`, so it cannot reach a shared `topk`.
- `SamplingParams.verify` validates `logit_bias` values (numeric, finite, `|bias| <= 1e30`). The sampler divides by a temperature of at least `1e-6`, so this bound keeps the float32 bias finite.
- The `min_new_tokens` penalizer and beam search drop stop ids outside `[0, vocab_size)` before building their tensors. Such ids can never be sampled, so they are accepted and never match, as before, and no longer crash the server.
- Chat `top_logprobs` and `temperature` reject negative values, and `temperature` rejects `inf`/`nan`.
- `ChatCompletionRequest.effective_max_tokens` gives `max_completion_tokens` precedence, including an explicit `0`. Chat conversion and the context-length check both use it. `max_tokens` and `max_completion_tokens` must be non-negative and are not booleans (lax integer parsing would read `false`/`true` as a 0- or 1-token limit).

### Deliberately not enforced

OpenAI documents `temperature` in 0-2, `top_logprobs` <= 20, `logit_bias` values in [-100, 100], and `top_logprobs` only with `logprobs=true`. SGLang does not enforce these. The engine applies those values correctly (`temperature=3` flattens the sampled distribution, `top_logprobs=50` returns 50 entries, a `-1e4` bias suppresses the token) and existing clients rely on that, so rejecting them would only break working requests. `ChatCompletionRequest` carries a comment saying so. Happy to revisit if maintainers prefer strict OpenAI parity on the OpenAI routes.

### Behavior changes

| Request | Before | After | Routes |
|---|---|---|---|
| `max_completion_tokens=0` | runs with the default limit | 0 tokens, `finish_reason=length` | chat |
| `max_tokens=5, max_completion_tokens=0` | 5 tokens | 0 tokens | chat |
| `max_tokens=-1, max_completion_tokens=1` | 200, 1 token | 400 | chat |
| `max_tokens` or `max_completion_tokens` set to `true`/`false` | read as a 1- or 0-token limit | 400 | chat |
| `n` > 128 | accepted (for example 256 choices) | 400 | chat, completions |
| `n` > `SGLANG_MAX_BATCH_REQS_PER_HTTP_REQ` (default 4096) | accepted, expanded `n` times | 400, checked before inputs are expanded | `/generate`, `Engine.generate` |
| `n=0` | no clear error | 400 with a clear message | chat, completions, `/generate` |
| `top_logprobs` / `top_logprobs_num` > vocab size, negative, or non-integer, with logprobs requested | scheduler crash or garbled batch | 400 | chat, `/generate` |
| `top_logprobs` / `top_logprobs_num` > vocab size with logprobs off, in a prefill batch with a logprob request | scheduler crash | count ignored, no crash | chat, `/generate` |
| `logit_bias` with `\|bias\| > 1e30` | accepted; garbage output or scheduler crash when sampling | 400 | all |
| `logit_bias` non-numeric or non-finite value | rejected only by the request parser where one applies | 400 from `SamplingParams.verify` | native `/generate`, completions |
| `stop_token_ids` outside `[0, vocab_size)` | ignored, but the server crashes when the batch uses `min_new_tokens` (or beam search gets an id from `2**63` to `2**64 - 1`) | ignored, no crash | all |

Notes:

- A single negative `max_tokens` or `max_completion_tokens` already returned 400. Only the combined case above changes.
- `max_tokens=0` alone already produced an empty completion. Chat now accepts `0` for both fields, while `/v1/completions` and the Anthropic route still require `> 0`.
- The same filter covers stop IDs supplied by the model (the `generation_config` EOS, tokenizer additional stop IDs).
- Native `n` from 129 to 4096 behaves as before. Raise or disable the limit with `SGLANG_MAX_BATCH_REQS_PER_HTTP_REQ`.

### Known limits (not in this PR)

- The opt-in Rust HTTP server (`SGLANG_RUST_SERVER=1`, `rust/sglang-server`) does not go through `tokenizer_manager`, so these admission checks do not apply there. The stop-id filters run in the scheduler, so they cover it too. It reads the same `SGLANG_MAX_BATCH_REQS_PER_HTTP_REQ` limit for `n` and rejects `max_tokens=0`. Mirroring the other checks in Rust is a separate change.
- `batch_size * n` is still unbounded, and `max_tokens` / `max_completion_tokens` have no upper bound.
- Zero-length generation with speculative decoding enabled is not covered by tests. In-tree senders (`lang/ir.py`, `benchmark/serving.py`) only send these fields with real values.

## Accuracy Tests

No model forward or kernel change. Request-level checks on a live server (single H200, Qwen2.5-0.5B-Instruct, `--sampling-backend pytorch`), against `main` at e109bc1832 and this branch (stop-id rows re-run on 2026-10-29 against `main` f59cc7e45f, the main merged into this branch):

| Request | `main` | This PR |
|---|---|---|
| `/generate` `n=300000` (main) / `n=3000000` (PR) | no reply, server killed | 400 in ~3 ms, server healthy |
| chat `top_logprobs=200000` with `logprobs=true` | server dies | 400, server healthy |
| `top_logprobs_num=10000000` with logprobs off, in one prefill batch with a logprob request (`/generate` and chat) | server dies (`selected index k out of range`; measured on this branch before the fix, 46f3d08505, which forwarded the count unchanged like `main`) | 200, server healthy |
| `stop_token_ids=[-1]` with `min_new_tokens=2` | server dies | 200, id ignored, server healthy |
| `stop_token_ids=[999999]` sent while another request with `min_new_tokens=2` is decoding | both requests lost, server dies | both 200, outputs unchanged, server healthy |
| beam search (`beam_width=2`) with `stop_token_ids=[2**63]` | server dies (`Overflow when unpacking long long`) | 200, same output as without the id, server healthy |
| `logit_bias` `1e39` (sampled) | garbage output `[0, 0, 0, 0]` | 400 |
| `logit_bias` `3e38` at `temperature=0.5` | garbage output | 400 |
| same, with `top_p=0.9` | server dies | 400 |
| chat `max_completion_tokens=0` | 45 tokens | 0 tokens |

Unchanged on both: `n=1, 3, 128` return the expected number of outputs; `temperature=3`, `top_logprobs=50` (with or without `logprobs`), and a large `logit_bias` on chat, completions and native all return 200; `logit_bias` of `+-1e30` at `temperature=0.0005` still works.

Reproduction (synthetic input only):

```bash
# huge n: rejected before the request is expanded
curl -s localhost:30000/generate -H 'Content-Type: application/json' \
  -d '{"text":"Hi","sampling_params":{"max_new_tokens":1,"n":3000000}}'

# top_logprobs above the vocab size
curl -s localhost:30000/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"m","messages":[{"role":"user","content":"Hi"}],"max_tokens":2,"logprobs":true,"top_logprobs":200000}'

# stop id outside the vocab, with min_new_tokens: kills main, ignored here
curl -s localhost:30000/generate -H 'Content-Type: application/json' \
  -d '{"text":"Hi","sampling_params":{"max_new_tokens":8,"min_new_tokens":2,"stop_token_ids":[-1]}}'

# logit_bias beyond the float32-safe bound
curl -s localhost:30000/generate -H 'Content-Type: application/json' \
  -d '{"text":"Hello","sampling_params":{"max_new_tokens":4,"temperature":0.5,"logit_bias":{"0":3e38}}}'
```
