## PR body
```markdown
## Motivation

Follow-up to #45154. The GLM-5.3 Python chat template still renders the prompt to one string, which `parallel_prompt_encode` then has to take apart again. It scans the text for added tokens to find cut points, only engages at `SGLANG_PARALLEL_PROMPT_ENCODE_MIN_CHARS` (32,768 characters) and above, and probes once whether `encode_batch` really runs in parallel. Shorter prompts are encoded with a single tokenizer call, and every request re-encodes its whole prompt, even though in function-calling and agent workloads most of it (system prompt, tool list, earlier turns) repeats from request to request.

The renderer already knows where each turn's special tokens go. This PR hands those positions to the encoder: the text between them is encoded in one `encode_batch` call at any prompt length without scanning the prompt, and its token ids are cached, so the parts that recur are encoded once.

## Modifications

- **`parser/glm53_chat_template.py`**: `render_glm53_segments` / `render_glm53_flash_segments` return the prompt as the list of strings it concatenates, with `[gMASK]`, `<sop>`, `<|system|>`, `<|user|>`, `<|assistant|>`, `<|observation|>` and the generation prompt's `<think>` as items of their own. `render_glm53` / `render_glm53_flash` join them, so the rendered prompt is unchanged byte for byte.
- **`parser/python_chat_template.py`**: `PythonChatTemplate.render_segments`. The installed `apply_chat_template` and the new `render_chat_segments` share one render path. `render_chat_segments` returns `None` when `chat_template_kwargs` holds an argument of `apply_chat_template` itself (`chat_template`, `continue_final_message`, `documents`, ...), so those requests keep the original path, errors included.
- **`entrypoints/openai/parallel_prompt_encode.py`**: `encode_prompt_segments(tokenizer, segments, encode_kwargs)`, a drop-in for `parallel_prompt_encode(tokenizer, "".join(segments), encode_kwargs)`.
  - A segment that is a whole added token is a cut point if no added token can match across it (`_cuts_at`, checked once per token). The text between cut points goes through one `encode_batch` call, whatever the prompt length, and the prompt itself is not scanned.
  - The ids of that text are kept in a per-tokenizer LRU (up to 1M tokens, entries up to 128K tokens), so a recurring system prompt, tool list or earlier turn is encoded once.
  - Uncached text of at least `SGLANG_PARALLEL_PROMPT_ENCODE_MIN_CHARS` is still split with `split_prompt`, so a long document stays parallel on its first request.
  - It uses the same one-time tokenizer validation (the per-tokenizer plan) and per-call checks as `parallel_prompt_encode`, and falls back to it for everything else: no plan, post-processor specials, truncation / padding / `encode_special_tokens` left on the backend, `SGLANG_PARALLEL_PROMPT_ENCODE=0`, other encode kwargs.
- **`entrypoints/openai/serving_chat.py`**: `_render_and_encode_chat_template` takes the segment path when a Python chat template is active. Jinja templates, and every model without a Python template, keep `apply_chat_template` + `parallel_prompt_encode` unchanged.

## Accuracy Tests

- **Token-id identity on the real tokenizers** (GLM-5.3 and GLM-5.3-Flash): 6,608 comparisons, 0 mismatches. Segment-path ids equal `tokenizer.encode(rendered_prompt)` for randomized conversations whose content contains special-token spellings, partial spellings next to the cut points, and unicode, plus a 150K-character document and the 128-tool prompt below, each encoded a second time from the cache. 600 of them are also compared with Jinja `apply_chat_template` ids.
- **Online A/B** (this PR vs. `main`, GLM-5.3-Flash, greedy decoding): identical `prompt_token_ids`, status and outputs for 24 cases. They cover chat, `reasoning_effort`, multi-turn reasoning, `clear_thinking`, tools (`auto` / `required` / named / `none`), out-of-order tool results, inline system messages, `continue_final_message`, images, streaming, `/v1/responses`, `/v1/messages`, and the 400 error cases.
- **Unit tests**:
  - `test_parallel_prompt_encode.py::TestPromptSegments`: id identity on fuzzed segment lists, text encoded once with no length threshold, long text split, tokens another added token can overlap are not cut points, fallbacks, cache budget.
  - `test_glm53_chat_template.py`: segments join to what `apply_chat_template` renders, turn tokens are segments of their own, routing back to `apply_chat_template`. With `SGLANG_TEST_GLM53_CHECKPOINT` / `SGLANG_TEST_GLM53_FLASH_CHECKPOINT` set, segment-encoded ids are also compared with the checkpoints' tokenizers.
  - `test_serving_chat.py`: the serving wiring.

## Speed Tests and Profiling

**Render + encode per request** (what `_render_and_encode_chat_template` does), median ms with the GLM-5.3-Flash tokenizer. The last message differs on every request. *Cold* has nothing cached: the first request with a given tool list and history. *Warm* has the tool list and earlier turns cached: the next request of a conversation, or another request with the same tools.

| Scenario | Prompt chars / tokens | `main` | This PR, cold | This PR, warm |
|---|---|---|---|---|
| chat, 1 turn | 103 / 23 | 0.050 | 0.065 | 0.038 (1.3x) |
| 8 tools, 1 turn | 2,312 / 596 | 0.730 | 0.601 (1.2x) | 0.083 (8.8x) |
| 128 tools, 1 turn | 82,925 / 20,238 | 2.835 | 2.918 | 1.003 (2.8x) |
| agent: 8 tools, 18 tool-call rounds | 38,262 / 7,997 | 1.559 | 1.447 (1.1x) | 0.357 (4.4x) |
| agent: 8 tools, 8 rounds × 3 parallel calls | 25,053 / 5,276 | 7.596 | 1.160 (6.5x) | 0.233 (32.6x) |

- The 8 × 3 agent prompt is below 32,768 characters, so `main` encodes it with a single tokenizer call. The segment path batches it at any length, so it is 6.5x faster even with nothing cached.
- The 128-tool prompt is above the threshold, so `main` already encodes it in parallel, and cold the two paths are on par. Warm, the remaining ~1 ms is the Python render.
- A cold request whose new text is two or more tiny segments pays rayon's dispatch (+15 µs in the first row), once per conversation.

**End to end**, client-side TTFT p50 in ms. Setup: GLM-5.3-Flash FP8, TP4 / EP4 on 4×B200, EAGLE MTP (5 / 1 / 6, adaptive), `--reasoning-parser glm45 --tool-call-parser glm47`. `main` and this PR ran side by side with the same checkpoint and flags. Requests are streamed with `max_tokens` 512 and temperature 1.0, with no cache flush and a unique nonce in the last message of every request: the radix prefix cache is warm, and the whole-request render cache misses. 20 requests at concurrency 1, 64 at concurrency 16.

| Scenario | Prompt tokens | c=1: `main` → this PR | c=16: `main` → this PR |
|---|---|---|---|
| 128 tools, 1 turn | 20,247 | 185.3 → 159.1 (−14.1%) | 550.3 → 422.9 (−23.1%) |
| agent: 8 tools, 18 tool-call rounds | 8,006 | 77.6 → 65.7 (−15.3%) | 142.4 → 122.0 (−14.3%) |
| agent: 8 tools, 8 rounds × 3 parallel calls | 5,285 | 73.6 → 66.1 (−10.2%) | 103.0 → 108.4 (mean 136.3 → 123.6) |
| 8 tools, 1 turn | 606 | 54.5 → 55.0 | 129.4 → 127.5 |

- With this PR, the 128-tool request comes within 3 ms of the ~156 ms measured when the render cache returns the whole prompt for a repeated request.
- The 8-tool prompt has under 1 ms of preprocessing to save, so its TTFT is unchanged.
- Environment: Intel Xeon 6960P (144 threads), Python 3.12.15, transformers 5.19.0, tokenizers 0.23.2.
```
