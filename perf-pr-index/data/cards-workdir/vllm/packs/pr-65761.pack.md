## Overview

When encoder CUDA graphs are on and the model accepts video, every captured graph is sized for `max_batch_size x max_frames_per_video` frames, including the graphs for small token budgets. For GLM-4.1V that is 64 x 600 = 38,400 frames, so even the smallest graph computes at least 38,400 tokens, and every image or video request replays a graph far larger than its input.

This PR caps each graph's frame slots at its token budget.

## Claims

- **GLM-4.1V** (encoder graph on, video allowed, which is the default):
  - Median image request: 470–481 ms → 31–32 ms.
  - Median video request: 475–484 ms → 35–36 ms.
  - Eager takes 57 ms (image) and 61 ms (video). Before this PR the graph path was ~8x slower than eager; after it, it is faster.
- **Qwen2.5-VL-7B at 128k context:**
  - Median image request: 30–33 ms → 27 ms.
  - Median video request: 32–33 ms → 30–31 ms.
- **Video outputs are unchanged:**
  - GLM-4.1V: graph outputs match eager bit for bit.
  - Qwen2.5-VL: graph outputs match main's graph outputs token for token.
  - Both hold for single videos and for 4-video batches replayed as one graph.
- **No effect** when video is disabled, or when `max_frames_per_batch` is at most the budget.

## Details

**Root cause.** `EncoderCudaGraphManager` passes one `max_frames_per_batch` to every budget's capture. That value is `max_batch_size * max_frames_per_video`, which became the default in #40445.

Qwen2/2.5/3-VL and GLM-4.1V build their capture layout from it: each item gets `frames_per_item = max_frames_per_batch // max_batch_size` frames, and each frame has at least one token. The captured size is therefore at least `max_frames_per_batch` tokens, whatever the budget.

How badly a model is affected depends on where its frame limit comes from:
- **GLM-4.1V:** the limit is a constant 600 frames per video, so every budget captures at least 38,400 tokens.
- **Qwen:** the limit is derived from `max_model_len` and the video limit, so the graphs grow only with long contexts. For example, Qwen2.5-VL at 128k context gets 896 frame slots, which inflates the 64–512 budgets.

**Fix.** Every frame yields at least one output token, so a batch that fits budget `B` has at most `B` frames. Concretely:
- Each graph is captured with `min(max_frames_per_batch, B)` frame slots.
- That value is stored in `BudgetGraphMetadata`.
- Replay pads `cu_seqlens` to the same per-graph value.

The model capture layouts are unchanged; they shrink because they derive from the value passed in.

Every auto or validated configuration keeps `B >= max_batch_size`, so a graph never gets fewer frame slots than `max_batch_size`, and image replays are unaffected.

`EncoderCudaGraphManager` is shared by Model Runner V1 and V2 (`vllm/v1/worker/gpu/mm/encoder_runner.py`), so both get the fix. The change adds no host sync.

**Related: GLM-4.1V image outputs (not changed by this PR).**
- On main, with video enabled, GLM-4.1V image replays are numerically wrong. GLM registers no `cu_seqlens` padding, so the replay buffer's tail is filled with zeros.
- Measured at the encoder output on main, graph vs eager has a relative L2 error of up to 169% for a 576-token image. Eager vs eager in a different batch varies by only 0.2–2.7%.
- This PR does not fix that: 576-token images are still wrong with it. #65453 registers the padding and fixes it; with both applied, the error is back within the eager variation.

**Not a duplicate:**
- #60112 (open) falls back to eager when a replay exceeds a capture buffer.
- #43403 (closed draft) proposed an eager fallback for `T > frames_per_item`.
- #65453 (open) registers `cu_seqlens` padding for GLM-4.1V and Kimi-K2.5.

None of these changes the capture size. #65453 touches the same padding path but no lines in common; with this PR, capture and replay still use the same per-graph frame count.
