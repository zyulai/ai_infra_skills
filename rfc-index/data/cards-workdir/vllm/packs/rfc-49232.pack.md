## 正文(PRD / 提案全文)

### Motivation.

> This RFC also serves as the tracking hub for ReplaySSM across vLLM, FlashInfer, and TensorRT-LLM. Status tables are kept live as work lands; PRs are linked rather than duplicated. It supersedes [RFC #47572](https://github.com/vllm-project/vllm/issues/47572)

[ReplaySSM](https://dao-lab.ai/blog/2026/replayssm/) ([vllm#47576](https://github.com/vllm-project/vllm/pull/47576)) is a memory-bandwidth optimization for the decode kernels of state space model (SSM) and linear-attention layers. It was developed concurrently and independently by @Johnny-Liou at Dao AI Lab and @hnover-nv at NVIDIA. A concurrent cross-framework implementation is in [TensorRT-LLM (#14203)](https://github.com/NVIDIA/TensorRT-LLM/pull/14203), developed by @hnover-nv.
 
SSM decode is memory-bound: today each step reads and writes back the full recurrent state. ReplaySSM instead keeps a single checkpoint state and caches recent SSM inputs in a ring buffer. It reconstructs the state only when needed, computing the output directly from the checkpoint plus cached inputs on every other step, and writes the full state back only once every `L` steps.
 
This helps two cases:
 
1. **Standard decode.** Writing the state back once every `L` steps instead of every step roughly halves the dominant memory traffic in the bandwidth-bound SSM kernel.
2. **Speculative decode.** The SSM state update is irreversible, so today's implementation keeps a separate recurrent state per draft token (~`(1 + num_spec)×` the state). Caching inputs instead makes rollback a ring-buffer pointer move — `O(1)` instead of `O(T)` — and enables verifying a draft window in one shot rather than by serial recurrence, improving both latency and maximum concurrency.
Gains are largest at high serving batch sizes, where the kernel is fully memory-bound, and for hybrid models at short-to-medium output lengths, where the SSM layers dominate latency.

### Proposed Change.

The full implementation lands first as a single large draft PR ([vllm#47576](https://github.com/vllm-project/vllm/pull/47576)) containing everything below, for end-to-end review and alignment; it is then split into smaller, self-contained PRs for merging.
 
### Scope
 
- Mamba2 and Gated DeltaNet (GDN) SSM layers.
- Standard and speculative decode.
- Stochastic rounding (SR) and prefix caching supported from the initial PRs.
- New Triton kernels plus vLLM integration (mixer dispatch, attention-metadata cursors, state-shape sizing). The conv path reuses vLLM's existing `causal_conv1d_update` unchanged.
- Integration of CUDA kernels from FlashInfer for a selected set of architectures.
### Config flags (all default off)
 
- `--use-replayssm` — Mamba2/GDN standard cached decode.
- `--use-replayssm-spec` — speculative cached decode (requires speculative decoding and `--mamba-cache-mode none`).
- `--replayssm-buffer-len` — history buffer length (default 16).
### Integration
 
The feature is opt-in through config flags that default to off; when off, the decode path is byte-for-byte the baseline. ReplaySSM caches are added as extra tensors on the existing paged mamba state, reusing vLLM's paged-block allocation and block-table indexing (continuous batching, per-request allocation/eviction, prefix caching). Only small per-block cursors live in the metadata builder.
 
Speculative decode uses two device-routed launches (verify and flush), with the flush decision and rollback computed on-device, so the launch sequence is fixed and one captured CUDA graph per batch size covers the path. Only state-building inputs are cached; the output read vector (Mamba2 `C`, GDN `q`) is taken from current activations. The ring buffer is sized `B + T` and flushes when `history + T > B` (`B` = buffer length, `T = num_spec_tokens + 1`).
 
### Two kernel tracks
 
By design there are checkpointing kernels in both Triton and CUDA:
 
- **Triton (vLLM)** — broad coverage across a wider class of SSM types.
- **CUDA (FlashInfer)** — tuned and specialized for Mamba2 / GDN ([flashinfer#3975](https://github.com/flashinfer-ai/flashinfer/pull/3975), [flashinfer#3324](https://github.com/flashinfer-ai/flashinfer/pull/3324/)).
The kernel↔runtime contract (accepted-token count, CUDA-graph compatibility, cache shapes/dtypes) is fixed so any conforming kernel can be dropped in. The approach is orthogonal to precision, so kernels port across FP16/BF16/FP8/INT8 as needed.

## Performance (reference numbers)
 
### Standard decode
 
Whole-model per-step speedup (baseline / ReplaySSM), FP32 state, buffer length 16:
 
| Model (SSM, HW) | bs 1 | bs 32 | bs 128 | bs 512 |
|---|---|---|---|---|
| Nemotron-Nano-4B (Mamba2, H100) | 0.99 | 1.17 | 1.40 | 1.55 |
| Qwen3.5-4B (GDN, H100) | 0.99 | 1.08 | 1.21 | 1.31 |
| Nemotron-Super-120B (Mamba2, B300) | 0.98 | 1.10 | 1.27 | 1.67 |
| Qwen3.5-122B (GDN, B300) | 0.98 | 1.07 | 1.14 | 1.20 |
 
### Speculative decode
 
End-to-end throughput at `(B, T) = (16, 4)`, B300, MTP drafter. `c/std` = ReplaySSM-spec / baseline-spec; `c/AR` = ReplaySSM-spec / no-spec autoregressive.
 
| Model | c/std bs 1 | bs 32 | bs 256 | c/AR bs 1 | bs 32 | bs 256 |
|---|---|---|---|---|---|---|
| Nemotron-Super-120B (Mamba2) | 1.09 | 1.07 | 1.88 | 2.12 | 1.90 | 2.21 |
| Qwen3.5-122B (GDN) | 0.99 | 1.19 | 1.80 | 1.90 | 1.93 | 1.85 |
