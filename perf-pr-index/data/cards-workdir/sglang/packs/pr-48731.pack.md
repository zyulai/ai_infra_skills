## Motivation

`engram_gather`'s local kernel (`_engram_gather_kernel`) runs one Triton program per looked-up row. Each program is a chain of dependent loads (id, then payload and scales) ending in a 512-byte store. In a DeepSeek-V4.1 DP prefill a forward makes two such calls of `ranks x tokens x 24` rows: 3.1M programs at 32K tokens per rank on 4 ranks. Per-program latency, not bandwidth, bounds the kernel. On 4x VR200 at 32K tokens per rank each call took 1.67 ms, about 1.5% of the forward.

The peer-read kernel (`_engram_gather_peer_kernel`, #46180) already runs 8 rows per program. This PR batches rows the same way for the local gather, 16 per program. On `main` the local gather runs for the lookups that are not peer reads: all-reduce, reduce-scatter and all-to-all lookups, host-table placement, and TP groups that span nodes.

## Modifications

- `_engram_gather_kernel` takes `ROWS` rows per program as a 2-D `[ROWS, DIM]` tile through the existing `_dequant_rows`, with a ragged last program masked. The MXFP4 decode, the destination permutation (`sort_ids`) and the shard bounds stay as they were. Values are bitwise those of one row per program.
- `_gather_rows_per_program()` picks 16 on SM103 and SM107, where it was measured. Other GPUs keep one row per program: the grid and per-program work there are unchanged.

## Accuracy Tests

The change is bitwise; no model-level accuracy run is needed.
- VR200 (SM107), this branch against `main`'s kernel: 8 and 16 rows per program equal `main`'s one-row kernel bit for bit (bf16 outputs compared as int16). The check covered fp8 and packed MXFP4 tables, sorted and unsorted ids, zero e8m0 exponents, and 1 to 196,613 rows, against a 1M-row shard of a 4M-row table: 0 mismatches.
- New unit test, `test_engram_gather_rows_per_program_bit_exact`: 2, 8 or 16 rows per program equal one row per program bit for bit, for fp8 and packed MXFP4 tables, sorted and unsorted ids, ids outside the shard, and ragged last programs (1 to 4099 rows).

- The pre-commit hooks pass.

## Limitations

- Gated to SM103 and SM107 because those are the GPUs we measured. The cost being bounded is per-program latency, so B200 and Hopper are likely to gain too; the gate can be widened with numbers from those GPUs.
- On a default single-node DEP deployment the lookup resolves to `peer_read`, which this PR does not change.
