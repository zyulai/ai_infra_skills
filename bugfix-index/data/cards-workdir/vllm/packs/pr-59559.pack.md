## 正文(PR 描述)

## Purpose

Fix a DP hang and simplify DP wave control. After this change, the engines alone start DP waves, and the front-end no longer sends `FIRST_REQ`.

**The bug.** Before this change, a front-end sent `FIRST_REQ` whenever it believed the engines were idle. The coordinator then broadcast `START_DP_WAVE`, and the rank that received the request assumed its peers had been woken. That assumption fails when a peer is still paused, because a paused rank drops `START_DP_WAVE`. With two API servers A and B and two ranks X and Y, all paused:

1. B sends an ADD to X and a `FIRST_REQ` to the coordinator.
2. The coordinator sends `START_DP_WAVE` to Y. Y is still paused and drops it.
3. A resumes both ranks. Neither rank has work, so both stay idle.
4. B's ADD reaches X. Its wave is current, so X does not announce, steps alone, and blocks in the DP collective forever.

Nothing orders these three sockets (B→X, coordinator→Y, A→X/Y). The same false assumption ("a sent wake took effect") was removed from the coordinator in #51481.

**The fix, from first principles.** Only the rank that is about to step knows it is about to step. So an idle, unpaused rank that receives a request now always announces `start_wave`. The coordinator already deduplicates these announcements and broadcasts to the other ranks. With that in place, the front-end wake carries no correctness role and only adds an optimistic running flag that can go stale. This PR removes it.

## Change

- **Engine** (`DPEngineCoreProc.add_request`): an idle, unpaused rank always announces the wave. Previously it announced only for a stale wave.
- **Python front-end** (`DPAsyncMPClient`): no longer sends `FIRST_REQ` and no longer sets `engines_running` optimistically. The PAIR socket now carries only elastic EP scale notices, so it is renamed `scale_*`.
- **Python coordinator**: the front-end wake handler is removed.
- **Rust front-end**: removes `CoordinatorCommand::FirstRequest`, `notify_first_request`, the command channel, and the external wakeup message. The in-process coordinator now relays only engine `StartWave` and `WaveComplete`.
- **Unchanged**:
  - `ignore_start_dp_wave`, so a paused rank still drops `START_DP_WAVE`. A new unit test pins this.
  - Rank 0's `start_wave` after the collective, which covers waves started by resume with queued work or by an elastic EP switch.
  - The request `current_wave` stamp and the coordinator's deduplication.
- **Messages per idle→busy transition**:
  - Before: `FIRST_REQ`, one broadcast, and rank 0's mirror.
  - After: one announcement, one broadcast, and rank 0's mirror.
- **Compatibility**: a new front-end needs engines that include this change. The front-end and engine ship together, so a normal deployment always meets this. An old Rust front-end still works with new engines; the coordinator logs and ignores its wake message.

## Why not a duplicate

No open PR changes this. #54762 (wave-0 bootstrap) and #55229 (idempotent resume) touch DP wave state but not the wake path. This came out of review of #51488. #51488 now builds on this PR instead of adding a request field.

  Each front-end ran 10 cold starts, 3 bursts of 16 requests from idle, and four pause/resume cycles (abort, wait, keep, abort) with requests in flight, sent while paused, and sent right after resume. The Python front-end also ran sleep/wake. Every request had to complete.

**Under Poisson load at 4 req/s** (`max_tokens=16`, wakes are frequent):
- DP=16: this PR is consistently 1.5–2 ms slower at p50. It measured 76.2 vs 74.6 ms over the BAAB rounds and 77.7 vs 75.5 ms over the ABBA rounds, and pinning the target rank gave the same result.
- DP=8: no difference (25.95 vs 25.92 ms).

**Where the cost comes from.** The table shows target-rank time from ADD to the end of the first DP sync, p50 in ms over ~70 wakes per cell. Each duration is measured on one host's clock.

| request lands on | main | this PR |
|---|---|---|
| coordinator's node | 8.28 | 8.26 |
| remote node | 8.35 | 9.68 |

- On the coordinator's node, the PR adds one in-node hop (rank → coordinator) before the peers wake. The cross-node sync hides it.
- On the remote node, the cost is real. On main, the front-end's `FIRST_REQ` wakes peers in parallel with the ADD. With this PR, the target first notifies the coordinator across the network, and the coordinator then wakes the remote peers back across it. That adds about two cross-node one-way trips.

The cost is paid once per idle→running transition. Only the first request after idle pays it, and only when it lands on a remote-node rank. It does not grow with DP size, and it is zero while the engines are running.

Two pre-existing observations from the same traces:
- The first cross-node DP all-reduce after idle takes 6–7 ms even after every rank has reached it. That is most of the idle wake time, in both versions.
- Main broadcasts `START_DP_WAVE` twice per wake (360 broadcasts for 180 wakes), because the front-end's running flag lags and a second `FIRST_REQ` goes out. With this PR, each wake broadcasts once.

Failures seen in the same runs also occur on main with identical results, so they are unrelated to this change:
- `test_async_llm.py::test_multi_abort[DELTA]` fails on main too, 3 of 3 runs on each side.
- Tests that need a model not cached offline, or that fork CUDA, fail on both sides.
