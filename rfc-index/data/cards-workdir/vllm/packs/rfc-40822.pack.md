## 正文(PRD / 提案全文)

# Motivation.

### Why?

With growing size of models, inference becoming faster, one thing is stagnating. Weight transfer in RL workloads is usually done with a single NCCL broadcast where every rank loads the full model weights through an iterator and does the whole post-processing logic itself. This is wasteful and also can become a bottleneck. This requires creating a global process group, requires a lot of synchronization and utilizes at most 1 NIC (50GB/s). A lot of work has been done on using RDMA-like transport for weight reloading. This process is (almost) synchronization free and utilizes direct memory writes/reads from remote GPU memory, through IB/EFA/etc. This can significantly speedup the transfer, as there is no synchronization involved, trainers exchange metadata with inference and then either trainers push, or inference engines pull the required weights from its corresponding memory addresses. The issue here becomes the knowledge of how the weights are laid out in inference/trainer memory.

### Checkpoint x Kernel format

Currently, weights get loaded from disk from a `HF`-like checkpoint, go through processing and end up in a so-called `kernel format`. This format is how the weights exist during the engine life-time. Some notable examples being

- quantized into FP8, scales rearranged into TMA friendly format
- `qkv`/`gate_up` fusion
- `ColumnLinear` for TP

This itself seems okay, but the issue is deeper - this format depends on the runtime configuration. Let's say you want to inference GLM5 FP8. Depending on if you end up using `DeepGemm` FP8 MoE or `Cutlass` FP8 MoE, your gate-up projection might end up like `w1w3` or `w3w1` - and this is just a single example, there is way more of them that I'm not familiar with. You might see the issue here, trainer needs to know the layout of the inference weights, if they were quantized, if they were padded, etc (endless options here) to be able to either directly load them or directly write them to the inference engine. Having this information is non-trivial in most cases


# Proposed Change.

## Example use-case
I have done some exploration into how would such transfer engine look like, the results are quite amazing honestly, cutting transfer of 800B model from ~40-50sec to 1sec.

## Approach
The approach can be split into 2 different paths, depending if the main use-case would be with `PUSH` or `PULL`. As for implementation details, we have ended up using [nixl](https://github.com/ai-dynamo/nixl?tab=readme-ov-file) to do the memory writes/reads

## 1. `PUSH` - this diagram is taken from our design that we have done in [prime-rl](https://github.com/PrimeIntellect-ai/prime-rl/pull/2326)
```
trainer rank 0           orchestrator              inference (all ranks)
     │                         │                         │
     ├── touch STABLE ─────────▶                         │
     │                         ├── /pause ───────────────▶
     │                         │◀── ack all ─────────────┤
     │                         ├── touch NIXL_READY      │
     │◀── see NIXL_READY ──────┤                         │
     │                                                   │
     ├───────── dist.barrier() across all trainer ranks ─│
     │                                                   │
     ├─────────── RDMA WRITEs (every rank) ─────────────▶│
     │                                                   │
     ├──────── spg.barrier() across trainer+inference ───│
     │                                                   │
     │                         │◀── /resume ─────────────┤
     │                         ├── resume ──────────────▶│
```

This is a preliminary design, focused on correctness, not performance (viz the extensive synchronization), but still cuts the transfer to 1.5sec across ~200+ GPUs

This approach depends on pre-exchanged metadata between trainer and inference. This metadata includes but is not limited to addresses and lengths of the remote pointers. Trainer also needs to be aware of the conversion format itself, that brings us to the first proposition 

### Proposition 1
Document the whole translation between `checkpoint -> kernel` formats. This can look as such (obviously extended to all the possible uses in processing) - open to discussion.

```python
    ConversionSpec(
        "mlp.gate_up_proj.weight",
        ("mlp.gate_proj.weight", "mlp.up_proj.weight"),
        quantization=QuantizationSpec(torch.float8_e4m3fn, ".weight_scale_inv"),
    ),
    ConversionSpec(
        "mlp.down_proj.weight",
        ("mlp.down_proj.weight",),
        quantization=QuantizationSpec(torch.float8_e4m3fn, ".weight_scale_inv"),
    ),
```

### Disadvantages

- This would require extensive changes to the whole model processing logic in VLLM, where every operation above the tensors loaded from the checkpoint format would have to be recorded and added into a graph composed of operations as such. RL frameworks would then have to replay this graph to construct their weights matching the VLLM format

### Advantages

- This is fairly framework agnostic, RL frameworks would extend VLLM workers to initialize what they need in their RDMA framework/lib of choice, then when ready submit a write to pre-exchanged tensor pointers and would be done with things.


## 2. `PULL`
This proposition approaches the problem from the other side. If we had Workers pull from the trainer itself. I haven't thought of this approach that much as it doesn't suit our proposal that much, but open to discussion here.

### Proposition

Make VLLM weight loading `RDMA` aware. This would be as easy as to replay the current full weight loading logic, but not reading local tensors, but remote ones.

### Disadvantages

- The tensors to load from have to be pre-registered on static memory addresses, which wouldn't be able to change without extra metadata exchange
- This would also lead to the requirement of having a scratchpad with weights on a trainer side or a parameter server, where the weights would have to be stored in checkpoint format
- This would also lock VLLM to a single `RDMA` framework

### Advantages
- easier on the trainer side

I'm strongly leaning towards `PUSH` based semantics and proposition 1, but open to discussion
