## Overview

With `--mm-encoder-attn-backend FLASHINFER`, the GLM-4.1V/4.5V, GLM-OCR and GLM-5.3-Flash vision encoders fail on main, in eager mode and with encoder CUDA graphs alike.

This PR fixes their attention so FlashInfer runs and matches the other ViT backends. The default backend's output does not change.

## Claims

- **FlashInfer now works on all three models.** On main, every forward asserts `sequence_lengths is not None`. With this PR, FlashInfer's output differs from FlashAttention's by the same amount as `TORCH_SDPA`'s does.
- **Batching is now correct.** With only the assert fixed, every sequence after the first in a batch read the wrong `v`:
  - outputs were off by 166% relative L2, or NaN;
  - capturing a 1024-token encoder graph hit an illegal memory access.
  
  With this PR, an image's output in a batch matches its output alone within 0.2%, in either batch order.
- **Default backend unchanged.** FlashAttention outputs are bitwise identical to main. Encoder latency is 1.5% lower, since `v` is no longer copied.

## Details

**Root cause.** The FlashInfer ViT path, `flashinfer_wrapper` (cuDNN batch prefill), needs two things these models did not provide.

1. **`sequence_lengths`.**
   - GLM-4.1V's `prepare_encoder_metadata` already computes it, but the vision transformer never passes it to its blocks.
   - GLM-OCR and GLM-5.3-Flash do not compute it in eager mode either. They also build plain `cu_seqlens` there, rather than FlashInfer's offset layout from `maybe_recompute_cu_seqlens`.
2. **The `v` layout.**
   - `maybe_recompute_cu_seqlens` gives q/k token offsets of `hidden_size` and v offsets of `3 * hidden_size`. It expects `v` to be a view into the fused qkv output, as in Qwen2.5-VL and Qwen3-VL.
   - The GLM attention made `v` contiguous, so its token stride was `hidden_size`. Every sequence after the first then read `v` at three times its real offset.

**Fix.**
- Thread `sequence_lengths` through the GLM vision attention and blocks.
- Keep `v` as a view: `.contiguous()` now applies only to `q` and `k`, which RoPE copies anyway.
- On the eager paths, build FlashInfer's metadata when FlashInfer is selected:
  - GLM-5.3-Flash reuses its existing `prepare_encoder_metadata`;
  - GLM-OCR calls the same `MMEncoderAttention` helpers inline, because its inherited `prepare_encoder_metadata` needs position embeddings that GLM-OCR removes.
- Other backends keep their existing code paths.

**Not covered.** GLM-5.3-Flash with encoder CUDA graphs was not run end to end: the full checkpoint was not available. Its graph path uses the same metadata keys as GLM-4.1V, which was tested.

**Related.** #65453 aligns FlashInfer's `cu_seqlens` between capture and replay for GLM and Kimi-K2.5. It touches different lines and composes with this PR; the graph results above hold with and without it.

**Not a duplicate.** No open PR adds FlashInfer ViT support for the GLM vision encoders. #65453 assumes FlashInfer already runs on these models.
