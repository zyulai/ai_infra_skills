## Motivation

The `WasmThreadPool` currently uses the raw WASM binary (`Vec<u8>`) as the key for its internal `component_cache`. This approach is inefficient for two main reasons:

1. **Memory Overhead**: For large WASM components, storing the full binary as a key in the LRU cache significantly increases memory consumption in every worker thread.
2. **CPU Overhead**: Every request lookup requires hashing and potentially performing a byte-by-byte comparison (`O(N)`) of the entire binary to verify a cache hit.

This PR transitions the system to use the SHA-256 hash which is already calculated and stored in the module metadata during registration as the unique identifier for cache lookups, turning an  comparison into a constant-time  operation.

## Modifications

* **Wasm Runtime**: Updated the `WasmTask` enum in `src/wasm/runtime.rs` to include a 32-byte `wasm_hash` field.
* **Cache Optimization**: Refactored the `WasmThreadPool` and its worker loop to use `LruCache<[u8; 32], Component>` instead of `LruCache<Vec<u8>, Component>`.
* **Module Manager**: Modified `execute_module_interface` in `src/wasm/module_manager.rs` to retrieve the pre-calculated `sha256_hash` from the `WasmModuleMeta` and pass it to the runtime during execution.
* **Worker Logic**: Updated `execute_component_in_worker` to utilize the 32-byte hash for efficient lookups. The raw `wasm_bytes` are now only used for compilation on a cache miss and are dropped immediately after.

## Benchmarking and Profiling

Performance was measured using a ~1MB WASM component to simulate the overhead of large binary comparisons.

* **Baseline (Pre-optimization)**: ~1.16 ms per hot lookup.
* **Post-optimization (Hash-based)**: ~429 µs per hot lookup.
* **Result**: ~2.7x speedup in the cache lookup hot path, accompanied by a significant reduction in memory pressure across the thread pool.
