## Background

MetaX is dedicated to delivering full-stack GPU chips and solutions for heterogeneous computing, which are widely applicable in cutting-edge domains such as Intelligent Computing, Cloud Computing, Autonomous Vehicles. These solutions provide robust computational support for the advancement of the digital economy.

MetaX develops full-stack GPU chips and will launch the MetaX N-series GPUs for inference, MetaX [C-series GPUs](https://www.metax-tech.com/en/goods/prod.html?cid=2) for general-purpose computing, and MetaX G-series GPUs for graphics. All MetaX products are based on proprietary GPU IP, featuring a fully independent instruction set and architecture, as well as a comprehensive software stack (*MXMACA*) that maintains compatibility with mainstream GPU ecosystems.

### i. MXMACA

MXMACA (hereinafter referred to as *maca*) is a heterogeneous computing platform introduced by MetaX, utilizing a general-purpose parallel computing architecture. It incorporates a self-developed Instruction Set Architecture (ISA) and a parallel computing engine within the GPU.

This platform provides a user-friendly, C-like programming language for developing applications targeting the MXMACA architecture. The language is simple, flexible, readable, and expressive, and is designed to be highly compatible with mainstream C/C++ heterogeneous computing languages, such as CUDA.

More information is available at [MetaX](https://www.metax-tech.com/en/about/about.html).

## Motivation.

Since version 0.6.6, [MetaX](https://www.metax-tech.com/en/about/about.html) has been committed to enabling robust vLLM support on MetaX GPGPU, successfully running a variety of mainstream models with strong performance. Initially, this support was achieved through direct modifications and patching for each new vLLM release. However, as vLLM’s architecture evolved and became more complex, maintaining these patches proved increasingly challenging and unsustainable.

With the introduction of the *[[RFC]: Hardware pluggable](https://github.com/vllm-project/vllm/issues/11162)* earlier this year, MetaX migrated its backend implementation to a plugin-based approach starting from v0.8.5. This transition allowed for more modular integration and easier maintenance, although some compatibility adjustments were still required.

MetaX now aims to officially integrate *maca* as a supported backend in vLLM, ensuring long-term maintainability, streamlined CI/CD processes, and ongoing compatibility with upstream vLLM developments. This will enable the MetaX plugin to keep pace with new features and optimizations, benefiting both MetaX users and the broader vLLM community.

## Some Limitations on MetaX Backend

Several limitations and challenges were encountered during the adaptation of the MetaX plugin. Below, we outline main issues for further discussion and potential solutions in our plugin.

### i. package adaptation

Running vLLM on the MetaX platform is constrained by several customized components maintained internally:

<img width=60% alt="Image" src="https://github.com/user-attachments/assets/bcadd0f2-52f0-4a44-8bac-7e1b884d7d9f" />


Most of these packages ensure API compatibility with the official upstream and will periodically distributed by MetaX .

Except for PyTorch. Only even-numbered PyTorch versions are supported by MetaX, such as `torch==2.4`, `torch==2.6`, and the upcoming `torch==2.8`.

Fetures on odd-numbered version of PyTorch may be incompatible with vLLM on maca. For example:

```python
# infer_schema in torch 2.6 does not support the op_func parameter as Optional[list[int]],
# which is supported in torch 2.7 in the latest vLLM.
torch.library.infer_schema(...)
```
> For this situation, we have a temporary patch solution in our design doc.

### ii. custom op for plugin

Another limitation is that *maca* is highly compatible with CUDA. The MetaX backend should be classified as ***cuda-alike*** (similar to ROCm).

MetaX requires recompilation of **all** kernels for *maca*. The main challenge is the lack of a mechanism to load specific libraries via the plugin when importing `_custom_ops.py` during vLLM initialization. Kernel libraries, such as `_C.so` and `_moe_C.so`, must be manually copied to the vLLM site-packages during plugin build.

### iii. `forward_oot` for plugin

MetaX does not set its `Platform` tag to `PlatformEnum.OOT`, but rather to `PlatformEnum.CUDA`. This is because nearly all platform-selection code paths (such as `forward_cuda`) should default to CUDA, similar to ROCm, as well as `is_cuda()`.

Otherwise, it would be necessary to re-inherit all `CustomOp` classes and override `forward_oot` to `forward_cuda` instead of `forward_native`, which would be a significant and cumbersome change for the plugin.

This can be easily addressed in vLLM(non-plugin) by adding an if-else branch to redirect `forward_maca` to `forward_cuda`.

Other related limitations are discussed in [issue 19161](https://github.com/vllm-project/vllm/issues/19161) too.

Developers can quickly get started with MetaX GPU. All MetaX hardware-related toolkits are available on the [MetaX Developer Platform](https://developer.metax-tech.com/softnova/index).
