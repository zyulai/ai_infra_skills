## 正文(PR 描述)

## Purpose

Scheduler can deadlock under KV memory pressure with MTP + KV connector --- encountered in production deployment of GLM5.2

### Example

- 2 requests A (needs 4 blocks + 1 for mtp), B (needs 3 blocks + 1 for mtp)
- Total blocks 7

#### Step 1 — A and B arrive and get added to `skipped_waiting` queue

A is admitted (4 blocks), popped from `waiting` -> `skipped_waiting`, `status → WAITING_FOR_REMOTE_KVS`
B is admitted (3 blocks), popped from `waiting` -> `skipped_waiting`, `status → WAITING_FOR_REMOTE_KVS`

- result: 
```
skipped_waiting = [A, B]
waiting = []

A.status = WAITING_FOR_REMOTE_KV
B.status = WAITING_FOR_REMOTE_KV
```

#### Step 2 — A's transfer lands. 

Schedule the `skipped_waiting` queue first. Peek `skipped_waiting` → A.

`_is_blocked_waiting_status(WAITING_FOR_REMOTE_KVS)` is True → `_try_promote_blocked_waiting_request(A)` succeeds → `A.status=WAITING` 

Then, schedule A. Need to allocate for the MTP blocks [these are only allocated after async load]. We need 1 block, but there is 0 left. `allocate_slots` returns None and we `break` (end attempting to schedule.

- result:
```
skipped_waiting = [A, B]
waiting = []

A.status = WAITING
B.status = WAITING_FOR_REMOTE_KV
```

As we can see, the queues are in the same state as before this step, and will continue to be in this state (trying to schedule A, asking to allocate blocks) forever.

#### Step 3 onward — Same cycle

Peek `skipped_waiting` → still A, now status WAITING. _is_blocked_waiting_status(WAITING) is False, so no promotion branch; straight to allocation; fails; break. Spin forever.

## Root Cause

Async KV load is allocated without lookahead slots (see `limit_lookahead_tokens`), and `_request_remaining_blocks()` -- which backs the `_inflight_prefill_reserved_blocks()` admission gate -- does not count them either. 

Then, after the `WAITING_FOR_REMOTE_KV` is done, we ask `allocate_slots()` for the lookahead margin on top ---> if this block is not available, we `break` --- with this request at the front of the `skipped_waiting` queue. If no requests are running, then no new blocks come free and we deadlock in this loop

**So there is a mismatch in the blocks reserved and what is actually needed to start running**
