## Overview

Cut the per-call host overhead vLLM adds in front of FlashInfer dense GEMMs (BF16, FP8 per-tensor and block-scale, MXFP8, NVFP4, W4A16) and their activation-quantize ops in eager mode, e.g. prefill without CUDA graphs. Companion to flashinfer-ai/flashinfer#7788 (merged), which removed 25–50 µs from FlashInfer's own dispatch.

## Claims

- Eager host time per linear call drops by 31–53 µs (MXFP8 q_b 142 → 91 µs, NVFP4 q_b 130 → 97 µs; table below).
- The same bypass applies to the other FlashInfer GEMM ops: FP8 `bmm_fp8` and W4A16 `flashinfer_mm_bf16_fp4` save ~10–16 µs per call in an isolated op microbenchmark, and the quantize ops save 2–5 µs.
- Under `torch.compile`, the ops that were `torch.library.custom_op` now go through `direct_register_custom_op`, about 17–23 µs cheaper per call for the MXFP8 GEMM.
- No behavior change: op names, schemas and fake impls are unchanged, eager outputs are bit-identical, and compiled graphs still record the custom ops.

## Validation

Host µs per call (enqueue rate, warm, no per-call sync), FlashInfer cute-dsl backend (the SM100 default), Kimi K3 projection shapes (public config) at M=4096, FlashInfer with #7788. 15 interleaved rounds × 150 calls, medians; IQR ≤ 2 µs.

| path | shape (N×K) | bare FlashInfer call | vLLM `layer(x)` main | this PR | saved |
|---|---|--:|--:|--:|--:|
| MXFP8 | q_b 18432×1536 | 75.8 | 141.7 | **91.0** | 50.7 |
| MXFP8 | o_proj 7168×12288 | 69.7 | 136.8 | **85.4** | 51.4 |
| NVFP4 | q_b 18432×1536 | 63.3 | 130.3 | **97.3** | 33.0 |
| NVFP4 | o_proj 7168×12288 | 66.1 | 134.5 | **101.8** | 32.6 |

The cutlass backend shows the same savings (31–51 µs), and M=8 is within a few µs of M=4096.

- `torch.library.opcheck` (`test_schema`, `test_autograd_registration`, `test_faketensor`, `test_aot_dispatch_dynamic`) passes for `vllm::mm_mxfp8` and `vllm::flashinfer_mm_fp4` as re-registered, with `NvmlCudaPlatform` / dispatch key `CUDA`.
- Outputs of the eager path, the op path, and the direct FlashInfer call are bit-identical (`torch.equal`) for MXFP8 (cutlass, cute-dsl) and NVFP4 (cutlass, cute-dsl).
- `torch.compile(fullgraph=True)` over the MXFP8 linear still records `vllm.mxfp8_quantize` and `vllm.mm_mxfp8` without graph breaks.

**Limitations:** these numbers come from a harness that replicates the vLLM call path line by line (`ColumnParallelLinear.forward` / `RowParallelLinear.forward` → `ModelOptLinearMethod.apply` → the FlashInfer linear kernels in `kernels/linear/`), on an SM100 part. It is not an end-to-end serving benchmark. vLLM's compiled extension was not available in that environment, so for NVFP4 the C++ `scaled_fp4_quant` was substituted with an equivalent-schema op that launches FlashInfer's FP4 quantize kernel. Absolute NVFP4 numbers may therefore be high by up to ~13 µs, while the before/after delta is unaffected. Relying on CI for the existing tests, including `tests/kernels/quantization/test_flashinfer_mxfp8_trtllm.py`, which opchecks `vllm::mm_mxfp8`.

## Details

Root cause: `vllm::mm_mxfp8` and `vllm::flashinfer_mm_fp4` were registered with `@torch.library.custom_op`, the slow registration path that `direct_register_custom_op` exists to avoid. Every eager linear call went through them, plus `vllm::mxfp8_quantize`. A no-op with the same signature costs 8.3 µs as a `custom_op`, 3.2 µs via `direct_register_custom_op`, and 0.15 µs as a plain call. The real GEMM costs 32–35 µs more through the op than called directly, because FlashInfer's Python dispatch also runs slower under the dispatcher.

Changes:
- Add `eager_bypass_custom_op()` next to `direct_register_custom_op` in `vllm/utils/torch_utils.py`. It wraps a registered op so that only Dynamo tracing goes through the dispatcher, where the op is needed as a graph boundary; eager calls go straight to the implementation. `vllm/ir/op.py` uses the same idea for `enable_torch_wrap`.
- Move the FlashInfer `torch.library.custom_op` ops (`mm_mxfp8`, `flashinfer_mm_fp4`, `bmm_fp8`, `flashinfer_mm_bf16_fp4`, `flashinfer_mxfp4_quantize`, `flashinfer_nvfp4_quantize`, `flashinfer_mxfp8_quantize_8x4`) to `direct_register_custom_op`, keeping the same names, schemas and fake impls, and call them through the bypass. Do the same for the already directly-registered BF16 (`cuda_flashinfer_bf16_gemm`) and FP8 block-scale ops, and for `mxfp8_e4m3_quantize`.
- Cache the "use FlashInfer's MXFP8 quantize or fall back" decision (2 imports, a capability query and `has_flashinfer()` per call).

Not included, because these change semantics or are out of scope:
- `skip_check=True` on the FlashInfer GEMM, which would save a further 8–15 µs but drops FlashInfer's per-call validation.
- Folding quantize + GEMM into one op. That only helps compiled mode (~2–4 µs), and for NVFP4 it would hide `_C.scaled_fp4_quant` from the attention/quant fusion passes.

+def eager_bypass_custom_op(
+    op_name: str,
+    op_func: Callable,
+    target_lib: Library | None = None,
+) -> Callable:
+    """Wrap a registered custom op so that only Dynamo tracing goes through
+    the dispatcher, where the op is needed as a graph boundary; eager calls
+    go straight to `op_func`. Use it on host-bound hot paths such as
+    per-linear GEMM calls, where dispatch costs several µs per call."""
+    op = getattr(getattr(torch.ops, (target_lib or vllm_lib).ns), op_name)
+
+    def wrapper(*args, **kwargs):
+        if torch.compiler.is_compiling():
+            return op(*args, **kwargs)
+        return op_func(*args, **kwargs)
+
+    return wrapper
