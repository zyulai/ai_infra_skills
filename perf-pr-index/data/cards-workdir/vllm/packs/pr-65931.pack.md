## PR body
```markdown
## Overview

Related to #65569 and the batch-invariance performance tracker #27433. Add Hopper BF16 persistent-matmul configs, in the format of #62219, for the bf16 Linear shapes that popular models send through `linear_batch_invariant` under `VLLM_BATCH_INVARIANT=1`: GLM-5.3, DeepSeek-V4.1, gpt-oss-20b and gpt-oss-120b. In GLM-5.3 and DeepSeek-V4.1 everything else is FP8/FP4 and uses other kernels, so the bf16 layers are the routers, the sparse-attention indexer projections, DeepSeek-V4.1's compressor and `lm_head` (per rank at TP=8 and TP=4). gpt-oss-20b's and gpt-oss-120b's unquantized attention, routers and `lm_head` run this kernel since #35404. The Triton path is unchanged; nothing is routed to cuBLAS.

## Claims

- Invariance: each shape uses one `BLOCK_K` across all M buckets. A row multiplied alone vs. inside batches of M = 1..1024 and every 16th M up to 8192 (first 8, last 8 and 4 middle rows): 0 of 438,030 rows differ over all 15 shapes.
- Kernel speed on H100: the tuned configs are 1.08x-3.04x faster than the default config at every bucket of every shape (table below).
- End to end on one H100 (`vllm bench serve`, 3 alternating rounds, raw logs in the comments below): gpt-oss-20b: decode-heavy output throughput +4.3% over main (faster in 3 of 3 rounds; loss against batch invariance off 22.8% -> 19.5%), prefill-heavy request throughput +2.4% (faster in 2 of 3 rounds); gpt-oss-120b: decode-heavy output throughput +1.9% over main (faster in 3 of 3 rounds; loss against batch invariance off 22.1% -> 20.6%), prefill-heavy request throughput +0.9% (faster in 2 of 3 rounds). The gains are modest because gpt-oss's MoE experts use another kernel; the same will hold for GLM-5.3 and DeepSeek-V4.1, where only the layers above are bf16.
- New test `test_hopper_tuned_linear_batch_invariance` checks config selection and exact first/last-row equality on both sides of every bucket boundary for all 15 shapes. `tests/v1/determinism/test_matmul_batch_invariant.py` on H100: 50 passed (15 new cases).

## Validation

H100 80GB HBM3 (SXM), torch 2.14.0+cu130, Triton 3.8.0, vLLM nightly 0.33.0rc1.dev454 with this diff applied. Tuning: for each shape and `BLOCK_K` in {64, 128}, the fastest (BLOCK_M, BLOCK_N, num_warps, num_stages) per bucket, timed at the bucket's largest M; the `BLOCK_K` kept has the lowest mean log time ratio to cuBLAS.

```bash
pytest -v tests/v1/determinism/test_matmul_batch_invariant.py -k hopper_tuned
```

Serving (gpt-oss-20b and gpt-oss-120b): fresh `vllm serve` per run, `--max-model-len 4096 --no-enable-prefix-caching`, `vllm bench serve --dataset-name random --max-concurrency 32 --request-rate inf --ignore-eos --seed 20261105 --num-warmups 20`, 2,000 prompts per run; decode-heavy 512 in / 256 out, prefill-heavy 1,024 in / 4 out; main and patch alternate which goes first, batch invariance off measured in every round.

## Not yet measured

End-to-end runs of GLM-5.3 and DeepSeek-V4.1 need a full 8-GPU H200/H100 node, which takes days to get on our cluster; in progress. H200 uses the same `hopper` table but was not benchmarked.

Tuning script and raw outputs: https://github.com/imthomp/vllm-batch-invariance (`src/tune_bi.py`, `results/tune`, `results/serve_gptoss`, `results/serve_gptoss120b`).
