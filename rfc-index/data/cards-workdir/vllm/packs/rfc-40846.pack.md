## 正文(PRD / 提案全文)

### Motivation

vLLM has always had a strong python bias to make it accessible to a wide range of contributors, and to exploit ML libraries including pytorch, triton, etc.

Historically, we have managed the inherent performance downsides of python, which include garbage collection and restricted parallelism due to the GIL. The measures taken include resorting to multiprocessing for CPU parallelism, which includes the capability to scale out the API server process.

As GPU latency continues to fall, request concurrency grows, and large-scale deployments become the norm, the CPU parts of the system have again become a bottleneck in many situations. This is often seen in the front-end process where the asyncio event loop can’t keep up.

Further, our front-end python code has become increasingly complex and fragile as it has evolved organically.

With the advent of coding agents, the python vs rust contributor accessibility issue is minimized.

It seems the time is right to explore a rust-based alternative to the python front-end process:

- It will allow us to eliminate the local api server process scale-out pattern which imposes some awkward limitations and is the source of significant complexity
- It is an excuse to restructure the front-end code cleanly “from scratch”
- It can be implemented as a “drop in” alternative to the existing front-end api server process transparently to users
- It’s much better suited for maintainable production software:
    - It’s much harder to write bad code in rust - our current code has a seemingly endless number of edge case / latent bugs. Rust reduces the likelihood of these.
    - It’s much harder to write slow code in rust.

We have experimented with an initial version of this, which is a drop-in alternative to the python api-server process and so can be used with the existing vllm serve entrypoint. The python launcher process will manage the various subprocesses as it currently does in the multi api-server case.

It’s currently enabled via a `VLLM_USE_RUST_FRONTEND` environment variable. Without this, the python path is used exactly as before.

## Performance Benchmarks

All benchmarks: Qwen3-0.6B, DP=4 on 4x GB200 GPUs, vllm 0.19.0, request_rate=inf. Results shown at concurrency=1024. asc = `--api-server-count`. These is obviously not a realistic real-world configuration  but chosen to emphasize the ceiling imposed by the current python implementation. We'll continue to benchmark with other models/workloads.

**Benchmark 1 — Decode/streaming-sensitive** (`--backend vllm`, random completions, input_len=32, output_len=512, prefix caching disabled)

| Frontend | Throughput (req/s) | P50 TTFT (ms) | P90 TTFT (ms) | P50 TPOT (ms) | P90 TPOT (ms) |
|---|---|---|---|---|---|
| Rust | 559.79 | 50.51 | 67.71 | 3.29 | 3.32 |
| Python (default, asc=4) | 509.56 | 165.95 | 206.52 | 3.39 | 3.74 |
| Python (asc=16) | 521.80 | 58.97 | 80.77 | 3.54 | 3.68 |

Rust achieves 10% higher throughput than default Python and 3.3x lower P50 TTFT. Even with 16 api-server processes, Python can't match Rust throughput and has 4% higher TPOT.

**Benchmark 2 — Preprocess-hot** (`--backend openai-chat`, speed-bench ~10K token chat prompts, output_len=16, prefix cache pre-warmed)

| Frontend | Throughput (req/s) | P50 TTFT (ms) | P90 TTFT (ms) | P50 TPOT (ms) | P90 TPOT (ms) |
|---|---|---|---|---|---|
| Rust | 837.00 | 596.92 | 807.64 | 39.90 | 46.42 |
| Python (default, asc=4) | 162.23 | 6076.09 | 7936.50 | 1.96 | 9.77 |
| Python (asc=32) | 785.98 | 657.15 | 1211.37 | 38.89 | 46.66 |

With prefix cache fully warm, the frontend becomes the bottleneck. A single Rust frontend matches or exceeds 32 Python api-server processes. Default Python saturates at only 19% of Rust throughput with 10x worse P50 TTFT.

## What’s implemented so far?

Most core functionality for completions, chat completions and generate APIs, with the exception of a handful of parameters including n and beam_search.

We are iterating quickly and it won’t take long to fill in additional functionality.

## Where would the rust code live?

There are two options - either within the vllm repo, or a separate repo within the vllm org (e.g. vllm-rs). My current preference is that the code lives in a rust dir within the vllm repo because:

- It can be built as a complete project
- This is an internal component of vLLM, tightly coupled to other parts of the system. Changes to some internal interfaces/types will need to span the python and rust code.
- It’s a common / well-established pattern, and we already have native C code / kernels within the repo.
- In future we may want to implement some other internal components / libraries in rust

## How will it affect users/developers?

For users it should be transparent, whether they are using the docker container or pip install. The (small) rust binary would be packaged as part of the wheel.

For doing development pip install -e, there would be a choice of:

- Excluding rust altogether (of course the env var then won’t work at runtime)
- Use precompiled rust binary (`VLLM_USE_PRECOMPILED_RUST=1`)
- Build the rust crates too (needed of course for changes to rust code)
    - One line toolchain install: `curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh`

## Would this replace the python front-end?

No, not for the time being. The hope is to include this as experimental/preview and see how things go.

### Proposed Change.

Since there is a decision about whether the code should be part of the vLLM repo or not (see above), and to minimize the integration PR diff, we have created it in a separate repo for now:
- https://github.com/Inferact/vllm-frontend-rs

See also corresponding integration PR: https://github.com/vllm-project/vllm/pull/40848
