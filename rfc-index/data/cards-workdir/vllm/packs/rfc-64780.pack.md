## 正文(PRD / 提案全文)

### Motivation.

**I (@algebra-MCX) propose to add DBO support for the FlashInfer NVLink all-to-all backends (`flashinfer_nvlink_one_sided`, `flashinfer_nvlink_two_sided`), starting with single-node H200/B200, and to lead the implementation and validation, subject to maintainer feedback.**

These backends are vLLM's NVLink-native EP path, but `--enable-dbo` cannot be combined with them today. Users of these backends lose the option to overlap the all-to-all with the other microbatch's compute, which DeepEP and NIXL EP users already have.

#### Current vLLM behavior

At `dc4dd5a2217bc757232e9fa4d8a8b59e207ca068`:

| Layer | Behavior |
| --- | --- |
| Config | On CUDA, [`use_ubatching`](https://github.com/vllm-project/vllm/blob/dc4dd5a2217bc757232e9fa4d8a8b59e207ca068/vllm/config/vllm.py#L2196-L2220) allows only `deepep_low_latency`, `deepep_high_throughput` and `nixl_ep`. |
| Modular kernel | Both prepare/finalize classes keep the default `supports_async() == supports_dbo() == False`, so [`_prepare`](https://github.com/vllm-project/vllm/blob/dc4dd5a2217bc757232e9fa4d8a8b59e207ca068/vllm/model_executor/layers/fused_moe/modular_kernel.py#L1258) and [`_finalize`](https://github.com/vllm-project/vllm/blob/dc4dd5a2217bc757232e9fa4d8a8b59e207ca068/vllm/model_executor/layers/fused_moe/modular_kernel.py#L1447) would assert under DBO. |
| Per-step state | One-sided stores [`runtime_max_tokens_per_rank`](https://github.com/vllm-project/vllm/blob/dc4dd5a2217bc757232e9fa4d8a8b59e207ca068/vllm/model_executor/layers/fused_moe/prepare_finalize/flashinfer_nvlink_one_sided.py#L99) on the instance; the two-sided manager owns a [single workspace](https://github.com/vllm-project/vllm/blob/dc4dd5a2217bc757232e9fa4d8a8b59e207ca068/vllm/distributed/device_communicators/all2all.py#L707-L710). Two microbatches in flight would share both. |

(The DBO rejection in `flashinfer_moe_ep.py` belongs to the SM100/103 FlashInfer MoE EP megakernel and is out of scope here.)

#### Hardware: GB200 is not required for the first slice

From static reading of FlashInfer 0.7.2 and the vLLM source above (not yet run on H200):

| Aspect | Finding |
| --- | --- |
| Memory sharing | `MnnvlMemory` falls back from FABRIC handles to POSIX file descriptors when the device has no fabric cluster, so a single NVSwitch node works. |
| Kernels | The default `backend="trtllm"` (legacy) kernels have no Python architecture gate; the MNNVL comm JIT module targets SM 9.x/10.x. Only the opt-in `backend="cake"` requires SM 10.0/10.3. |
| Multi-node | Needs FABRIC handles (MNNVL, e.g. GB200 NVL72). Out of scope for the first slice. |
| CI | These backends' kernel tests already run on `b200-k8s`. |

### Proposed Change.

**Scope of the first slice:** single node, DP/EP over NVLink, CUDA, eager DBO (prefill and decode). FULL CUDA graph DBO, multi-node MNNVL and `backend="cake"` come later.

1. **Execution model.** The FlashInfer APIs used here do not expose a send/receive hook pair, so follow the existing synchronous pattern of [`naive_dp_ep._comm_region`](https://github.com/vllm-project/vllm/blob/dc4dd5a2217bc757232e9fa4d8a8b59e207ca068/vllm/model_executor/layers/fused_moe/prepare_finalize/naive_dp_ep.py#L145-L173): under DBO, yield and run dispatch/combine on the comm stream, then switch back. `supports_dbo()` returns True; `supports_async()` stays False so shared-expert placement is unchanged.
2. **Per-microbatch state.** Index per-step state (`runtime_max_tokens_per_rank`, dispatch handles/metadata) by `dbo_current_ubatch_id()`. Allocate one FlashInfer workspace per microbatch so two in-flight collectives never share buffers or completion flags.
3. **SM budget.** Run the comm-stream kernels within the existing DBO comm-SM budget, and confirm that a spinning receive cannot starve the peer microbatch's sender (deadlock check).
4. **Config.** Add the two backends to the CUDA DBO allow-list only after (1)–(3) pass.

Out of scope: changing FlashInfer kernels, async hooks inside FlashInfer, SBO ([#64776](https://github.com/vllm-project/vllm/issues/64776)).

#### Completion criteria

- [ ] DBO off: code path and outputs unchanged for both backends.
- [ ] Unit tests: per-microbatch state indexing, workspace ownership, `supports_dbo`, config allow-list.
- [ ] 2× and 8× H200 (and B200 if available), DP/EP, eager DBO: identical outputs/logprobs with DBO on/off for one MoE model (e.g. DeepSeek-V2-Lite and a DeepSeek-V3-class model); no hang across repeated steps with uneven microbatches.
- [ ] Note: four tests in `tests/distributed/test_mnnvl_alltoall.py` skip without `SYS_PTRACE` in `CapEff`; validation must run them on a host where they execute, and skips are not counted as passes.
- [ ] `vllm bench serve` throughput/TPOT with DBO on/off, plus a trace showing the all-to-all overlapping the peer microbatch's compute.

### Any Other Things.

Questions for maintainers:

1. Is the synchronous comm-stream pattern (as in `naive_dp_ep`) acceptable for these backends, or should vLLM wait for FlashInfer send/receive hooks?
2. Should per-microbatch workspaces live in the all2all manager or in the prepare/finalize objects?
3. Is a single-node H200/B200 qualification sufficient for the first slice, with GB200 MNNVL as a follow-up?

No implementation, GPU run or performance result exists yet. AI assistance was used for investigation and drafting.
