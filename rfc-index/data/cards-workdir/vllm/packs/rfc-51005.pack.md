## 正文(PRD / 提案全文)

### Motivation.

The upstream fused MoE factory owns the priority rules that select a Router, but out-of-tree (OOT) accelerators sometimes need a different device-specific Router implementation after that choice. Without a construction extension point, a plugin must patch constructed Router methods, patch the factory, or copy its growing selection logic and constructor arguments.

The original version of this RFC proposed a qualified Backend class, a subclass-only result, and per-class caching. Draft #51006 now uses one direct Platform constructor hook. It also permits a compatible sibling Router, so this revision supersedes the Backend-class and subclass-only design.

Goals:

- Keep the upstream factory's Router selection priority and constructor arguments.
- Let a Platform supply a constructor for the already-selected Router branch, including a compatible sibling implementation.
- Require a callable constructor and a `FusedMoERouter` result before the model starts serving.
- Keep Platform lookup and constructor selection out of Router forward execution.
- Preserve built-in CUDA/ROCm Router construction when the Platform does not customize it.

Non-goals:

- Giving a Platform a second Router factory or permission to reorder upstream selection.
- Requiring the returned Router to subclass the selected concrete class.
- Adding a Backend registry, discovery cache, class mutation, or a universal forward-time callback.
- Owning EPLB configuration, expert mapping, load recording, communication, or weight transfer; those are addressed independently in #49702 and draft #49700.

### Proposed Change.

#### 1. Platform constructor contract

After an upstream factory branch selects its concrete Router class, it calls `Platform.get_fused_moe_router_constructor(selected_cls)`. The default implementation returns `selected_cls`, preserving existing construction. An OOT Platform may return any callable that accepts the same branch's constructor arguments and produces a `FusedMoERouter`.

The hook receives the selected class, not the factory's raw routing configuration. It can choose a subclass, a compatible sibling Router, or the selected class unchanged. Core validates that the result is callable, invokes it with the existing arguments, and checks that the constructed object implements the common `FusedMoERouter` base contract. Core does not require a subclass relationship to the selected concrete class.

#### 2. Selection and lifecycle ordering

The ordering is fixed: upstream evaluates its existing priority rules, chooses the Router branch, asks the Platform for a constructor, passes the branch's original arguments, and validates the returned Router before serving. The current CPU branch is included. A Platform hook may run once for each Router constructed during model initialization; there is no Backend discovery or per-class cache. Router forward execution then uses the constructed object's ordinary methods without another Platform lookup.

Allowing siblings widens the extension contract but does not transfer factory ownership. A Platform constructor must preserve the selected branch's externally relevant routing semantics, optional state, and accepted constructor arguments. Core can prove the base type, not numerical equivalence; that obligation belongs in OOT integration tests.

#### 3. Independence from EPLB

This constructor hook works with or without EPLB. It receives no EPLB policy, load window, communicator, mapping, or transfer object. If the upstream factory already passes an optional `eplb_state`, it remains among the unchanged constructor arguments. Draft #49700 separately provides EPLB state and per-layer device-operation hooks. A customized Router may consume that state, but neither RFC makes Router construction the owner of EPLB control flow.

#### Alternatives considered

1. **Keep replacing methods on Router instances.** This depends on private method signatures, binding behavior, and construction order.
2. **Let each Platform provide a complete Router factory.** This duplicates upstream priority rules and must track every new Router branch.
3. **Require a Backend class and cache resolved subclasses.** The earlier design adds machinery without a demonstrated need: model construction, not forward execution, is the variation boundary.
4. **Permit only subclasses of the selected concrete Router.** A compatible sibling may implement the same factory branch contract without that inheritance relationship.
5. **Dispatch through a global or forward-time callback.** Global mutation is import-order sensitive, while forward-time dispatch adds a hot-path lookup.

#### Risks and mitigations

- **A Platform returns a non-callable or non-Router object.** Validate both at construction time.
- **A sibling Router changes branch semantics or mishandles arguments.** Keep upstream argument selection unchanged and require OOT routing and model-output equivalence tests.
- **Factory priority or the CPU branch is accidentally skipped.** Apply the hook after every final selection branch and test representative branches.
- **Platform selection reaches the hot path.** Perform the call only during Router construction; do not add a runtime registry or lookup.

#### Test strategy and acceptance

- Fake Platforms must demonstrate default construction, a compatible sibling, and unchanged behavior for branches they do not customize.
- Contract tests must reject non-callable constructors and objects outside `FusedMoERouter`, and retain the upstream factory's representative selection order and arguments.
- Built-in Router suites must retain numerical behavior and construction compatibility.
- A downstream OOT integration must replace private instance-method adaptation, preserve optional EPLB state where used, and demonstrate equivalent routing and model output on real accelerator hardware before the draft is considered ready. Combined EPLB integration should also exercise the separate #49700 mapping and recording contract.

### Any Other Things.

Draft implementation: #51006. This RFC remains separate from the EPLB device-operation RFC #49702 and draft #49700. This revision replaces the original Backend-class, subclass-only, and caching commitments; the issue edit history remains the record of that earlier design.

The motivating Ascend integration currently adapts constructed Router instances in vllm-project/vllm-ascend#12804; a downstream follow-up can use this constructor hook instead of patching those instances.
