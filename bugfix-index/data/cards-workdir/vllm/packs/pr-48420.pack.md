## 正文(PR 描述)

## Summary

Fixes #48383

`use_audio_in_video=True` can be requested by a caller that doesn't know in advance whether a given video has an audio track. When the video has no audio, no audio items are extracted from it, but `Qwen3OmniMoeThinkerProcessingInfo._call_hf_processor` forwarded `use_audio_in_video=True` to the underlying HF `Qwen3OmniMoeProcessor` regardless.

The upstream HF processor assumes `use_audio_in_video=True` implies at least one audio item per video, and raises an unguarded `StopIteration` from `replace_multimodal_special_tokens` (`next(audio_lengths)` on an exhausted iterator) when that assumption doesn't hold. vLLM's processing context (`InputProcessingContext.call_hf_processor`) then wraps that in a generic `ValueError`, which is what's reported in #48383.

## Root cause (verified by reproduction)

Reproduced directly against `transformers.models.qwen3_omni_moe.processing_qwen3_omni_moe.Qwen3OmniMoeProcessor` with a synthetic no-audio video matching the shape reported in the issue (`(16, 3, 480, 256)`):

```
File ".../transformers/models/qwen3_omni_moe/processing_qwen3_omni_moe.py", line 247, in replace_multimodal_special_tokens
    audio_token_indices = np.arange(next(audio_lengths))
StopIteration
```

Confirmed that calling the same processor with `use_audio_in_video=False` instead succeeds cleanly with no audio data, producing the expected output keys (`input_ids`, `attention_mask`, `pixel_values_videos`, `video_grid_thw`, `video_second_per_grid`).

## Fix

In `_call_hf_processor`, when no audio was extracted (`audios` is empty) but `use_audio_in_video=True` was requested, fall back to `use_audio_in_video=False` for that call — there's nothing to interleave, so forwarding the mismatched flag to the HF processor only produces a crash instead of a usable result.

## Test plan

- Added `tests/models/multimodal/processing/test_no_audio_track_in_video.py`, following the existing pattern in `test_audio_in_video.py`, covering a video with no audio track + `use_audio_in_video=True` for both `Qwen2.5-Omni-3B` and `Qwen3-Omni-30B-A3B-Instruct`.
- `ruff check` / `ruff format --check` pass on both changed files.
- `python -m py_compile` passes.
- Root cause and fix mechanism reproduced directly against the real HF processor (see above); full in-repo test execution requires GPU/model weights and will run in CI.
