# Vectorize `alloc_extend_naive`

## The contract

For each request `i`, `alloc_extend_naive` fills `out_indices[start_pos[i] : end_pos[i]]`
(the request's extend span) with up to three consecutive runs of KV-cache slot
indices:

1. **Finish the current partial page** — up to `num1` tokens, continuing directly
   after `last_loc[i]` (i.e. `last_loc[i] + 1, last_loc[i] + 2, ...`). This only
   exists if `prefix_lens[i]` isn't already page-aligned.
2. **Whole new pages** — `num2` tokens (a multiple of `page_size`), each new page's
   slots taken in order from `free_pages`.
3. **Start of one final new page** — `num3` tokens, the remainder from the last
   page this request touches.

`num1 + num2 + num3 == extend_lens[i]` always, and each phase is skipped when its
count is 0. This rewrite computes exactly this, with no behavioral change — it
just computes every request's phases in parallel instead of in a Python loop.

## Phase-by-phase mapping (loop -> vectorized)

The old loop, per request `i`:

```python
num1 = min(seq_lens[i], ceil(prefix_lens[i])) - prefix_lens[i]
if num1: out_indices[start_pos[i]:start_pos[i]+num1] = last_loc[i] + 1 + arange(num1)
if prefix_lens[i] + num1 == seq_lens[i]: continue
num2 = (floor(seq_lens[i]) - ceil(prefix_lens[i]))
if num2: out_indices[...] = free_pages[start_new_pages[i]:end_new_pages[i]-need_page[i]] * page_size + arange(page_size) broadcast
if prefix_lens[i] + num1 + num2 == seq_lens[i]: continue
num3 = seq_lens[i] - floor(seq_lens[i])
if num3: out_indices[end_pos[i]-num3:end_pos[i]] = free_pages[end_new_pages[i]-1] * page_size + arange(num3)
```
(`ceil(x) = ceil_div(x, page_size) * page_size`, `floor(x) = (x // page_size) * page_size`.)

The new code computes, once, for the whole batch:

- `num1 = clamp(seq_lens, max=ceil_prefix) - prefix_lens` — identical formula,
  vectorized (`min` -> `torch.clamp(..., max=...)`).
- `done_after_1 = (prefix_lens + num1) == seq_lens` — this is exactly the loop's
  first `if ... == seq_lens[i]: continue` condition, computed for every request
  instead of tested per-iteration.
- `num2 = where(done_after_1, 0, floor_seq - ceil_prefix)`,
  `num3 = where(done_after_1, 0, seq_lens - floor_seq)` — identical formulas to
  the loop's `num2`/`num3`, but masked to 0 whenever the loop would have hit
  `continue` before computing them (so a request that finishes in phase 1 never
  contributes phantom phase-2/3 tokens or page demand — this is what makes
  `pages_per_req` below match the loop's actual page consumption, not the
  unconditional `num_new_pages` formula the loop computes up front but only
  partially uses).
- `pages_per_req = num2 // page_size + (num3 > 0)`, then
  `start_new_pages`/`end_new_pages` via cumsum — same role as the loop's
  `start_new_pages[i]`/`end_new_pages[i] - need_page[i]` (for phase 2) and
  `end_new_pages[i] - 1` (for phase 3); page assignment order across the whole
  batch is unchanged because it derives from the same running total of pages
  consumed so far, now computed once as a cumsum instead of incrementally by
  the loop.

Then, per **output slot** `j` (not per request):

- `owner = torch.searchsorted(end_pos, j, right=True)` maps slot `j` to its
  owning request `i` — `end_pos` is the exclusive-cumsum of `extend_lens`, so
  this is precisely "which request's `[start_pos[i], end_pos[i])` range contains
  `j`". `local = j - start_pos[owner]` is the offset within that request's
  extend, i.e. the loop variable that ranges implicitly over
  `pos_in_page[:numK]` / `arange(numK)` inside each `if numK:` block.
- `is_phase1 = local < num1_g`, `is_phase2 = ~is_phase1 & (local < num1_g + num2_g)`,
  else phase 3 — this is exactly which of the three loop branches slot `j`
  would have landed in.
- `val_phase1 = last_loc_g + 1 + local` — identical to the loop's phase-1 RHS.
- `val_phase2 = free_pages[start_new_pages_g + (local - num1_g) // page_size] * page_size + (local - num1_g) % page_size`
  — the loop's phase-2 RHS was `(free_pages[start:end].view(-1,1) + pos_in_page.view(1,-1)).view(-1)`,
  i.e. page `(local - num1) // page_size` of the slice, offset `(local - num1) % page_size`
  within it. Same page, same offset, computed directly instead of via a 2D
  broadcast + reshape.
- `val_phase3 = free_pages[end_new_pages_g - 1] * page_size + (local - num1_g - num2_g)`
  — identical to the loop's phase-3 RHS (`free_pages[end_new_pages[i]-1]`, offset
  `local` within the final page, which is `rel3` here since `num1+num2` tokens
  were already consumed).
- `out_indices = where(is_phase1, val_phase1, where(is_phase2, val_phase2, val_phase3))`
  selects the one formula that actually applies, per slot — this replaces the
  loop's `if numK:`/`continue` control flow with a per-slot select.

## Edge cases preserved

- **Zero-length extends** (`extend_lens[i] == 0`): contributes no slots to `j`
  (its `[start_pos[i], end_pos[i])` range is empty), exactly as the old loop's
  body would do nothing meaningful for it (there are no output indices to write).
- **Prefix exactly on a page boundary** (`prefix_lens[i] % page_size == 0`):
  `ceil_prefix == prefix_lens[i]`, so `num1 = 0` and phase 1 is skipped for
  every slot of that request — same as the loop never entering its `if num1:`
  block.
- **`num1 == 0`**: `is_phase1` is `False` for all of that request's slots;
  `val_phase1` is still computed (torch.where doesn't short-circuit) but never
  selected.
- **`num2 == 0`**: `is_phase2` is `False` for all of that request's slots
  (`num1_g + num2_g == num1_g`); `val_phase2` is still computed but never
  selected.
- **Tight free-page pool** (`free_pages` sized to exactly `num_new_pages.sum()`):
  `page_idx2`/`page_idx3` land exactly in `[0, free_pages.numel()-1]` for every
  slot whose phase actually needs a page, by construction of `start_new_pages`/
  `end_new_pages` as a running cumsum over the same total.

## Two bugs this surfaced, and why the fix is a host-side shape guard

`torch.where` evaluates **both** branches for every element — unlike the loop's
`if num2:` / `if num3:`, which never touch `free_pages` at all when a phase is
absent for a given request. So `val_phase2`/`val_phase3` are computed for every
slot regardless of whether that phase is ever selected there, which means the
index expressions feeding `free_pages[...]` must be valid for *every* slot, not
just the ones where the branch is live.

A 20,000-case randomized differential test against the original loop (see
below) initially crashed with `IndexError: index is out of bounds for dimension
with size 0`. The generator explicitly includes the shapes that produce this:
every request's extend fitting entirely inside its already-partially-used page
(so `pages_per_req.sum() == 0` and, for a tight pool, `free_pages` is empty),
the same shape mixed with requests that do need real pages in the same batch,
and `page_size=1` with an empty pool. Root-caused to two instances of the same
defect:

- `page_idx2` was clamped only on the upper bound (`max=free_pages.numel()-1`),
  which is `-1` when `free_pages` is empty, and `free_pages[-1]` on an empty
  tensor raises.
- `page_idx3`, which the fix was first modeled on by analogy, had the *identical*
  defect in the other direction (`min=0`, no upper bound) — and reproducing it
  in isolation confirmed indexing an empty `free_pages` at index `0` raises just
  as much as at index `-1`. **No amount of clamping rescues an index into a
  zero-length tensor** — there is no valid index into an empty array.

The actual fix is a host-side shape guard:

```python
if free_pages.numel() == 0:
    out_indices.copy_(last_loc_g + 1 + local)
    return
```

`free_pages.numel()` is static shape metadata, not a value read off the tensor's
data — reading it costs no host<->device sync on any backend, so this doesn't
reintroduce the kind of stall the rewrite is trying to remove. The guard is
correct because **`free_pages.numel() == 0` at this call site can only mean
every request in the batch needs zero new pages** (verified below, not
assumed), in which case every output slot is phase 1 by construction and no
`free_pages` read is needed. `page_idx2`/`page_idx3` are also now defensively
`min`/`max`-clamped to `[0, free_pages.numel()-1]` for the surviving (non-empty)
path — this is a no-op for well-formed inputs (the cumsum construction already
keeps them in range), it just closes the same class of gap if that ever stops
holding.

**Verifying the invariant, not assuming it.** Both real callers of
`alloc_extend_naive` guard the call:

- `python/sglang/srt/hardware_backend/npu/allocator_npu.py` (`alloc_extend`):
  `if num_new_pages_item > len(self.free_pages): return None` before calling
  `alloc_extend_naive` with `self.free_pages` unchanged.
- `tools/sglang-simulator/.../mem_cache_allocator.py` (`_alloc_extend_cpu`):
  same pattern, `if num_new_pages > len(self.free_pages): return None`.

So by the time either caller reaches `alloc_extend_naive`, `free_pages.numel() >=
num_new_pages.sum()` always holds; `free_pages.numel() == 0` therefore implies
`num_new_pages.sum() == 0`. If a caller ever violated that contract instead
(passed a `free_pages` smaller than actually needed), **the original loop is
already broken for that input too** — confirmed directly: passing a
genuinely-too-small `free_pages` to the original raises `RuntimeError: The
expanded size of the tensor (16) must match the existing size (0)` from the
phase-2 slice-assignment shape mismatch. The new code fails differently (either
via the shape guard's now-safe path, if the whole-batch-zero case doesn't apply,
or via the same class of crash the clamps guard against), but it does not
silently produce wrong output for contract-violating input — it was never a
supported input for the old implementation either, and this PR does not try to
make it one.

## Measured speedup (CPU, `torch.set_num_threads(1)`)

| bs   | page_size=1 | page_size=16 | page_size=64 | page_size=128 |
|-----:|------------:|-------------:|-------------:|--------------:|
| 1    | 0.86x       | 1.15x        | 1.13x        | 0.94x         |
| 8    | 3.42x       | 5.20x        | 4.46x        | 4.47x         |
| 64   | 9.14x       | 12.61x       | 12.20x       | 12.89x        |
| 256  | 12.00x      | 17.24x       | 14.73x       | 16.00x        |
| 1024 | 11.52x      | 15.40x       | 13.85x       | 13.40x        |

At `bs=1` both implementations take roughly 40-55us/call and the two are within
measurement noise of each other; across repeated runs the vectorized version
came out mildly *slower* for `page_size` in `{1, 128}` (0.84x-0.94x) and mildly
*faster* for `{16, 64}` (1.09x-1.15x). Reporting this honestly rather than
rounding it into a win: there is no consistent speedup at `bs=1`, and for two of
the four page sizes tested it's a small regression. The benefit is entirely a
function of batch size — vectorizing a loop that only ever ran once doesn't pay
for the extra tensor ops it replaces it with, but by `bs=8` it's already a clear
win everywhere, growing to 9-17x by `bs=64` and beyond.

The speedup also depends strongly on **extend length**, not batch size alone,
because the two implementations scale differently: the old loop's cost is
O(batch) Python dispatch and is nearly independent of how many tokens each
request extends by, while the vectorized version's cost scales with the total
token count. Same page_size=16, varying the per-request extend length:

| extend length per request | bs=64 | bs=1024 |
|---------------------------|------:|--------:|
| 1-8 tokens (decode-like)  | 20.3x | 109.5x  |
| 32-64 tokens              | 24.5x |  47.9x  |
| 256-512 tokens (prefill-like) | 5.5x | 4.9x |

So "how much faster" has no single answer: ~5x on long prefill extends, ~100x
on large decode-shaped batches. The table above happens to sit in the middle of
that range. Quoting one headline number in either direction would misrepresent
it.

## No tests added

This PR adds no test file and modifies no test file, per the task's explicit
instruction. Exactness was instead verified out-of-band: a throwaway
randomized differential script (not part of this PR, not committed) ran
**20,000 cases** comparing `torch.equal(out_indices_old, out_indices_new)`
against the original loop implementation (copied verbatim from
`origin/main:python/sglang/srt/mem_cache/allocator/paged.py`), covering batch
sizes 1-256, page sizes `{1, 4, 16, 64, 128}`, prefix lengths including 0 and
exact multiples of `page_size`, extend lengths including 0, free-page pools
both tight (sized to exactly the demand) and slack, and — added explicitly
after the bugs above surfaced, not left to chance — the all-zero-new-pages
shape, a mixed batch of zero- and real-page requests, and `page_size=1` with an
empty pool. **0 mismatches, 0 crashes**, across all 20,000 cases, after the two
fixes described above.
