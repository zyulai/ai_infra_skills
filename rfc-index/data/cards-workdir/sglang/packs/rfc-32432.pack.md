## 正文(PRD / 提案全文)

## Summary

This RFC proposes explicit runtime contracts for dynamic CUDA Graph paths that reuse Graph-static metadata, workspaces, request/KV slots, captured buffers, kernel-produced plans/indices, and alternate streams across asynchronous iterations.

The original motivation came from the DSpark compact ragged target-verify investigations in #31023 / #33356. Since this RFC was opened, that investigation has separated several **different correctness layers** that originally surfaced through similar CUDA illegal-memory / graph failures:

```text
control-plane consistency
  -> kernel-produced plan correctness
  -> capture-initialization ordering
  -> replay-time ownership / stream / lifetime contracts
```

The current evidence is useful precisely because these mechanisms are no longer being conflated:

- **#31195** addresses cross-TP verify-budget / target-Graph-tier consistency.
- **#32467** addresses a producer-side race in `plan_compress_prefill_kernel0` that can emit invalid ragged plans.
- **#33795** proposes the final warmup-to-capture completion boundary for `FullCudaGraphBackend` and has independent H200 evidence.
- **#34286** applies and regression-tests the same capture-initialization invariant for `BreakableCudaGraphBackend`.

The B300 investigation therefore no longer supports treating generic metadata/workspace lifetime reuse as the default explanation for every observed failure. At the same time, the fact that the same warmup-to-capture invariant appears independently in both Full and Breakable graph backends strengthens the case for making these contracts explicit and eventually sharing enforcement where appropriate.

This RFC is **not** a claim that all DSpark failures have one common root cause. It is a proposal to make the assumptions required by asynchronous graph capture/replay reviewable, testable, and enforceable across backends.

## Evidence update — 2026-08-10

### 1. Cross-TP control-plane inconsistency is a separate contract

PR #31195 fixes a real control-plane bug in which TP ranks could independently resolve different verify budgets and therefore choose different target CUDA-Graph tiers for the same decode step.

Observed before the fix:

```text
TP0 target Graph key = 160
TP1 target Graph key = 144
raw batch size = 32 on both ranks
```

After broadcasting TP0's final verify budget, the tested TP8 matrix completed:

```text
no-overlap, same service:          30/30
no-overlap, restart per workload:  30/30
overlap, same service:             30/30
overlap, restart per workload:     30/30
Total:                            120/120

verify_token_budget divergence: 0
sum(verify_lens) divergence:     0
target Graph-key divergence:    0
```

This belongs to a **distributed control-plane consistency contract**, not to workspace ownership or kernel-memory lifetime.

### 2. B300 producer-side plan corruption is directly observed

PR #32467 targets `plan_compress_prefill_kernel0`.

The original kernel initializes every `warp_min` / `warp_max` scratch slot from warp 0 and then lets each warp overwrite its own slot during Stage B. Without ordering between those operations, warp 0 can clobber another warp's already-written reduction result. A genuinely ragged `extend_lens` vector can then appear uniform and select the MTP-uniform fast path, producing `ragged_id` from `B * s_max` rather than the actual ragged row count.

The direct single-GPU B30Z regression originally showed:

```text
unpatched: 2592 bad plans / 6000 calls
patched:      0 bad plans / 30000 calls
```

Characteristic corruption:

```text
rmax = 383 = B * s_max - 1
actual ragged rows = 360
```

Full-model B300/TP8 validation with #32467 alone also passed the tested startup and sustained-replay paths:

```text
startup capture: 3/3 READY, 35/35 shapes each
runtime Gate 1:  320/320, Graph replay observed, no GPU fault
strong path:     512/512, compact + SPS + c256 + 60k/1k, no GPU fault
```

This establishes a producer-side correctness failure **before** downstream Triton / TRT-LLM / DeepGEMM / cuBLAS sites surface the sticky CUDA error.

#### Reviewer simplification: remove the redundant initialization

@DarkSharpness later asked whether the scratch initialization can be dropped entirely, because the launch is structurally 1024 threads / 32 warps and every warp overwrites its own slot before the existing post-reduction `__syncthreads()`.

A same-session A/B/C kernel experiment tested exactly that proposal, 10,000 calls per case / 30,000 per variant:

| Variant | scratch init | extra pre-reduction barrier | OOB plans |
|---|:---:|:---:|---:|
| A: original | ON | OFF | **13111 / 30000** |
| B: current #32467 | ON | ON | **0 / 30000** |
| C: reviewer variant | OFF | OFF | **0 / 30000** |

Inputs:

```text
[4] * 96
[4] * 72 + [3] * 24
[3] * 104 + [2] * 24
```

Core oracle:

```text
max(valid ragged_id) < sum(extend_lens)
```

This supports the simpler no-initialization formulation under the current fixed launch geometry. If that implementation is adopted, the dependency on the 32-warp launch invariant should be made explicit with a comment/assertion so a future dynamic launch change cannot silently invalidate it.

The broader RFC lesson is unchanged: **kernel-produced plans/indices need their own correctness contract**; perfectly stable metadata ownership cannot compensate for a producer that emits an invalid index.

### 3. FullCudaGraphBackend has a separate capture-initialization gap

#33795, authored by @Leoyzen, identifies the following boundary in `FullCudaGraphBackend.capture_one()`:

```text
warmup forward / post_warmup_hook
  -> no final device/TP completion boundary
  -> graph construction / capture
```

The proposed correction is:

```python
self._device_module.synchronize()
self._tp_group.barrier()
# then enter CUDA Graph construction/capture
```

H200/TP4 has independent evidence that this boundary matters in that environment.

On the tested B300/TP8 reproducer, however:

```text
#33795 only: 1/6 READY
#32467 only: 3/3 READY + sustained replay clean
```

Therefore #33795 is not the primary B300 producer fix and should not be used to reinterpret the #32467 kernel evidence. It exercises a separate **capture initialization contract**.

### 4. BreakableCudaGraphBackend has the same structural boundary

#34286 extends the capture-initialization invariant to `BreakableCudaGraphBackend`.

Current structure before the fix:

```text
warmup 1: sync -> TP barrier -> forward -> hook
warmup 2: sync -> TP barrier -> forward -> hook
                                      |
                                      +--> directly construct BreakableCUDAGraph
```

The PR adds:

```text
final warmup / hook
  -> device synchronize
  -> TP barrier
  -> BreakableCUDAGraph construction
```

and adds a CPU-only deterministic ordering regression that requires:

```text
final post_warmup_hook
  < synchronize
  < barrier
  < BreakableCUDAGraph construction
```

The regression was first run against unpatched production code and failed specifically on the missing boundary; after the production change it passed. The relevant runner-backend suite passed 5/5 and pre-commit was clean after rebasing onto current main.

Scope matters: #34286 does **not** claim a natural BCG crash reproducer and does **not** claim to fix the #32467 B300 producer bug. Its value is that the same capture-initialization invariant is now visible in a second backend and protected by a focused regression.

### 5. What this changes for the RFC

Originally, several contracts in this RFC were motivated by a broad search for the cause of #31023. The evidence now supports a cleaner decomposition:

```text
#31195
  distributed control-plane consistency

#32467
  kernel-produced plan/index correctness

#33795
  FullCudaGraphBackend capture initialization

#34286
  BreakableCudaGraphBackend capture initialization

#32432
  shared vocabulary / review contracts / future reusable helpers
```

This makes the RFC stronger rather than weaker: concrete incidents now map to distinct contracts instead of one vague "CUDA Graph lifetime" category.

## Motivation

A dynamic speculative-verification path maps runtime decisions into reusable GPU state:

```text
per-request verify length / layout
  -> verify_lens / qo_indptr / positions / request + KV locations
  -> Graph tier selection
  -> Graph-static metadata + workspace refresh
  -> CUDA Graph replay
```

Overlap scheduling may prepare the next batch while previous GPU work is still in flight:

```text
replay stream:        execute batch N
plan/copy/aux stream: prepare batch N+1
```

Correctness depends on more than Python call order. A safe implementation must make clear:

- which distributed decisions must be identical across ranks;
- which object identities / addresses are capture-stable;
- which contents may change on replay;
- whether updates happen in place or by object replacement;
- who owns reusable storage at each generation;
- which stream produces an update and which stream consumes it;
- when a request slot, KV location, or workspace can be reused;
- whether one-time JIT / module loading / lazy initialization has completed before capture;
- which dimensions require a distinct Graph key versus only larger capacity;
- what structural invariants kernel-produced plans/indices must satisfy.

## Proposed runtime contracts

### 1. Distributed control-plane consistency contract

Before TP/DP/EP ranks enter collectives or select captured Graph variants for the same logical step, all layout-defining distributed decisions must agree.

Examples include:

```text
verify-token budget
graph_num_tokens / target Graph tier
collective token shape
layout mode / path selection
```

Core invariant:

> Two ranks participating in the same logical collective/captured step must not independently choose incompatible layout dimensions.

#31195 is a concrete example of enforcing this contract by broadcasting the final verify budget before Graph-tier selection.

### 2. Graph-static metadata contract

For every metadata field consumed by a captured Graph, define:

- whether Python object identity must remain stable;
- whether backing storage address must remain stable;
- whether contents are refreshed before every replay;
- whether refresh is in-place or object-replacing;
- whether nested metadata is recursively refreshed;
- whether the value is prepared outside the Graph or produced inside capture;
- minimum storage capacity for all layouts sharing the Graph.

Core invariant:

> Before replay starts, every dynamic value consumed by the Graph must be fully initialized, visible to the consumer stream, and backed by storage valid for the complete replay lifetime.

### 3. Workspace ownership contract

Every reusable workspace should expose or internally enforce:

```text
workspace identity
capacity
owner component
owner replay/batch generation
producer stream
consumer stream(s)
reuse-completion condition
```

Core invariant:

> A workspace must not be overwritten, resized, rebound, or reassigned until its last GPU consumer has completed.

Possible implementations include per-stream workspaces, double buffering, generation-tagged ownership, or event-guarded reuse. This RFC does not prescribe one universal mechanism.

### 4. Stream-ordering contract

Cross-stream dependencies should be explicit rather than inferred from host execution order.

A proven dependency may look like:

```python
ready_event.record(producer_stream)
consumer_stream.wait_event(ready_event)
```

The contract should cover:

- metadata / plan preparation streams;
- graph replay streams;
- result / copy streams;
- graph-internal alternate streams used by attention, indexer, compressor, communication, or custom kernels;
- one-time warmup/JIT work before capture.

A host-side event does not automatically prove correctness for graph-internal alternate-stream work, so internal dependencies must remain auditable.

### 5. Capture initialization contract

Backends should explicitly define when capture may begin.

Core invariant:

> All asynchronous work triggered by eager warmup, lazy initialization, module loading, first-use JIT, or warmup hooks that is not capture-safe must complete before entering the capture region; distributed ranks that must capture coherently must rendezvous at the same boundary.

This contract is now exercised independently by:

```text
#33795 -> FullCudaGraphBackend
#34286 -> BreakableCudaGraphBackend
```

This is the strongest current candidate for a future shared backend helper, but extracting one should wait until the exact semantics of both backends are reviewed and the individual fixes land.

### 6. Graph/cache-key contract

Graph state should distinguish:

1. **Capture-shape dimensions** — require a distinct captured graph.
2. **Capacity dimensions** — may share a graph only when static storage/workspaces cover the worst case.
3. **Per-replay mutable contents** — may vary if completely refreshed and correctly ordered.

The audit should consider dimensions such as:

```text
graph_num_tokens
raw batch size
verify_lens distribution
qo_indptr/layout shape
page-table dimensions
workspace requirement
attention/indexer/compressor variant
stream index
backend variant
```

Not every field belongs in the key. If a field is omitted, the implementation should make explicit why sharing is safe.

### 7. Request/KV-slot lifetime contract

Request-pool entries, KV locations, page-table entries, and output-cache locations must not be recycled while any in-flight Graph or alternate-stream consumer can still reference them.

Core invariant:

> CPU/scheduler logical completion is not sufficient for reuse unless GPU consumer completion is also established.

### 8. Kernel-produced plan/index contract

The #32467 investigation demonstrates that Graph metadata may be perfectly owned and ordered while a producer kernel itself emits invalid indices.

For index/plan producers, debug or regression coverage should assert structural invariants such as:

```text
index < backing capacity
ragged_id < real ragged row count
batch_id < batch size
workspace offset < allocated workspace
```

Where possible, these invariants should be testable with small kernel-level regressions rather than only full-model stress tests.

Kernel scratch initialization/reduction assumptions should also be explicit. If correctness depends on fixed launch geometry (for example, every scratch slot being overwritten by exactly one warp), encode that dependency in a static assertion/comment or derive the implementation so the invariant is structurally unavoidable.

### 9. Debuggability contract

Dynamic Graph backends should provide opt-in, synchronization-free tracing for:

```text
replay sequence
rank
Graph key
batch/request generation
metadata identity
data_ptr / shape / stride / storage capacity
workspace identity / capacity / generation
producer and consumer stream identity
```

Debug logging should avoid CUDA tensor `.item()` or unconditional device synchronization because observer effects can suppress timing-sensitive failures.

Observations should be labeled by scope, for example:

```text
PROVEN: covers whole captured graph completion
PARTIAL: does not identify a component's exact last-consumer point
UNKNOWN: internal lifetime not exposed by host instrumentation
```

## Non-goals

This RFC does not propose:

- an unconditional hot-path `torch.cuda.synchronize()`;
- one universal workspace implementation for every backend;
- converting every dynamic layout field into a Graph key;
- treating old diagnostic synchronization switches from #31455 as a production fix;
- claiming that metadata/workspace lifetime caused the #32467 B300 plan-kernel corruption;
- claiming that #32467 explains the independent H200 warmup/capture ordering behavior;
- claiming that #33795 or #34286 explains every DSpark CUDA-Graph failure;
- prematurely merging Full and Breakable capture logic before their backend-specific semantics are reviewed.

## Proposed phased adoption

### Phase 1 — Document and assert local invariants

- document distributed layout decisions that must agree across ranks;
- document metadata ownership and capture-stable addresses;
- document capture-initialization boundaries;
- assert workspace / plan / index capacity assumptions where cheap;
- add deterministic regression tests for known producer bugs such as #32467;
- add ordering regressions for backend capture boundaries such as #34286;
- identify graph-internal alternate-stream dependencies.

### Phase 2 — Localized correctness fixes

When evidence identifies a violated contract, implement the smallest correction:

- cross-rank broadcast / agreement point;
- missing kernel barrier or removal of a racy redundant initialization;
- targeted stream event dependency;
- complete nested metadata refresh;
- workspace ownership/reuse guard;
- capacity correction;
- Graph/cache-key refinement;
- request/KV lifetime correction;
- explicit post-warmup completion boundary.

### Phase 3 — Shared backend helpers

Extract common helpers/interfaces only after the same invariant appears in more than one backend/path and the local semantics are understood.

The Full/Breakable capture-initialization pair (#33795 / #34286) is now a concrete candidate for evaluating this phase.

Potential surfaces include:

- capture-initialization helper;
- Graph-static metadata refresh protocol;
- event-aware reusable workspace wrapper;
- generation/ownership tracing helper;
- Graph-key capacity assertions;
- distributed layout-agreement helper where applicable.

## Open questions

1. Should Full and Breakable CUDA Graph backends share an explicit `finish_warmup_before_capture()`-style helper once #33795 / #34286 semantics are settled?
2. Which ownership/generation state belongs in the Graph runner versus the attention/indexer/compressor backend?
3. Which graph-internal streams are guaranteed by current capture semantics and which need explicit events?
4. Should capacity dimensions participate directly in Graph keys or be enforced through worst-case allocation + assertions?
5. Can request/KV-slot reuse be tied to existing completion events without a scheduler-wide synchronization point?
6. Which index/plan invariants can be checked cheaply in GPU CI?
7. If #32467 adopts the no-initialization variant, where should the fixed 32-warp launch invariant be asserted so future launch changes fail loudly?
8. What tracing can remain compiled into production with near-zero cost while disabled?
