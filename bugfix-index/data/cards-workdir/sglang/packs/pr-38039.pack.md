## 正文(PR 描述)

## Problem
MiniCPM-V-4.6 fails to serve on SGLang with a Triton compile error in the GDN prefill conv1d kernel:

```
AssertionError: Mismatched type for col0 between then block (<['256'], bf16>) and else block (<['256'], fp16>)
```

Root cause: MiniCPM-V-4.6 runs a Qwen3.5 LLM (bf16 conv-state cache) but its vision resampler emits **fp16** activations, so the GDN prefill mixes an fp16 `x` stream with a bf16 conv-state cache. The `col0..col3` sliding-window registers then disagree on dtype across the kernel — the `chunk_offset==0` branch loads them from the bf16 conv-state cache while the `chunk_offset>0` branch and the per-token sliding-window reassignment produce fp16 — and Triton's if/else phi type check aborts.

## Fix
Cast the conv-state loads to `x_ptr.dtype.element_ty` (and keep the zero-init on the same x dtype) so `col*` have a single dtype across the whole kernel. Zero-cost when the dtypes already match (the common case).

## Validation
- MiniCPM-V-4.6 now loads, captures decode CUDA graphs, and serves on RTX 5090 (bf16). Paired throughput 591/1885/5608/8013 tok/s at bs=1/4/16/32. (vLLM 0.28 cannot load this model at all — unrelated `k_proj` vs `qkv_proj` weight-mapping bug — so SGLang is the only working engine.)
- No change for models where x and the conv-state cache already share a dtype (the cast is a no-op).
