## 正文(PR 描述)

## Overview

Removes `_requires_qwen38_tep8_emulation`, which forces OCP MX emulation for Qwen3.8 Flash Next's (`amd/Qwen3.8-Flash-Next-Quark-MXFP4`) routed experts at TEP8 on gfx950 when the fused shared expert is off. The guard was added because AITER padded the MoE width from 640 to 768 for that shape and the native W4A4 kernel lost accuracy. Since #55104 aligns the W4A4 intermediate to 128, Flash Next's width stays at 640 with no pad, and the native kernel is as accurate as emulation and about twice as fast.

Existing work:
* #55104 removed the pad that the guard worked around, and on its own fixes Flash Next's accuracy at EP4 and TEP8 (measured below) and at TP1 (0.9651, #55104 on `nightly-43b4aaea`).
* The first revision of this PR also changed the pad rounding at MoE `tp_size == 1`. With #55104 merged, that is a no-op for Flash Next, so it is dropped here.

## Claims

- At TEP8 with `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=0`, the only configuration where the guard fires, the native AITER W4A4 kernel matches emulation's accuracy (GSM8K 0.9651 vs 0.9629) at 2.3x the output throughput at 8k/1k concurrency 4 (362 vs 158 tok/s) and 1.9x at concurrency 32 (1399 vs 741).
- No change for the checkpoint card's recipe: with the fused shared expert each rank holds 65 local experts, the guard requires exactly 64, so it never fired there.
- No change for any other shape: the guard matched only `E=512, H=2560, N=640` at EP8 on gfx950.

## Details

* **Why the guard is stale.** Its docstring says AITER pads `N` to 768 for this shape. Since #55104 the W4A4 intermediate is aligned to 128, so 640 is stored as is, with no pad. The native kernel at 640 is accurate (first accuracy row), so CK-Tile's `inter_dim % 256` scale issue does not show up for this shape.
* **When the guard fired.** It matches `num_local_experts == 64`. The fused shared expert adds one local expert per rank (`ExpertMapManager`), so with the card's recipe the count is 65 and the native kernel already ran; only `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=0` hit the guard.
* Only the ROCm MXFP4 oracle changes; nothing changes on CUDA.

**Limitations and CI gaps.**

* gfx950 only. The W4A4 MXFP4 MoE path does not run on gfx942.
* The end-to-end image applied the previous revision of this PR, which also changed the pad rounding at MoE `tp_size == 1`. With #55104, Flash Next's pad there is 0, so that part did nothing in these runs; the guard removal is the same code.
* The unit tests run in the AMD kernels CI job. The accuracy and throughput runs happened outside CI.
