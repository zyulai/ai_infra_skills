# Summary

Adds **W8A8 MXFP8** quantization (8-bit weights + 8-bit activations, block_size = 32) for Qwen3 / Qwen3.5 **MoE** (FusedMoE) LLM models on Ascend NPU, continuing the NPU quantization work tracked in #21584. Both **online** (`--quantization mxfp8`) and **offline** (msmodelslim, flagless — selected by the checkpoint's `quant_model_description.json`) paths are supported and share the same fused-experts kernel. Requires Ascend A5 (Ascend 950) — the fused MoE MX kernels (`npu_grouped_matmul_swiglu_quant_v2`, `npu_dynamic_mx_quant`) are A5-only.

> #23795 (dense W4A4) has landed and this branch is merged up to `main`, so the diff is now the MoE MXFP8 delta only. It reuses the merged dense MXFP8 infrastructure — `NPUMXFP8LinearMethod`, the `Fp8Config` NPU dispatch, and `ModelSlimMXFP8Scheme` (from #22352).

**Online quantization (`--quantization mxfp8`)**

- On the **Ascend NPU** backend, `Fp8Config.get_quant_method()` dispatches FusedMoE layers to the new `NPUMXFP8OnlineMoEMethod` (the `isinstance(layer, FusedMoE)` branch, mirroring the existing dense `NPUMXFP8LinearMethod` linear branch). It subclasses `UnquantizedFusedMoEMethod` and overrides only `create_moe_runner`, to attach the MXFP8 per-gmm kernels — weight creation, weight post-processing and the forward pass are the unquantized Ascend ones. On GPU the `FusedMoE` branch is untouched.
- BF16/FP16 expert weights `w13`/`w2` are quantised once at load via `npu_dynamic_mx_quant(dst_type = torch_npu.float8_e4m3fn)` — a 3D `[E, N, K]` input is accepted directly (no per-expert loop) — into `float8_e4m3fn` weights + UE8M0 (`float8_e8m0fnu`) block scales, kept as **non-contiguous transpose views**.
- Forward: on the `ascend_tp` dispatcher, `npu_moe_init_routing_v2` with **`quant_mode=3`** (count `group_list`) — the per-token MXFP8 activation quant is fused directly into routing, so the same kernel launch emits the sorted `float8_e4m3fn` payload *and* its `float8_e8m0fnu` block scale, saving a separate `npu_dynamic_mx_quant` pass — → **gmm1** `npu_grouped_matmul_swiglu_quant_v2` (gate_up + swiglu + requant fused, **cumulative** `group_list`) → **gmm2** `npu_grouped_matmul` (**count** `group_list` + explicit `group_list_type`). The UE8M0 scale dtypes are passed explicitly; the e4m3 `x`/`weight` dtypes are left implicit. DeepEP has no MXFP8 dispatch dtype, so on that path the dispatcher keeps sending BF16 and gmm1 quantizes the hidden states itself via `npu_dynamic_mx_quant` before the fused kernel — both dispatchers reach gmm1 with the same input. Only the `ascend_tp` path is validated end-to-end on A5.
- **Fused-routing quant optimization:** the fused `quant_mode=3` scale comes back flat (`[N, K/32]`) instead of the pair-split `[N, K/64, 2]` layout gmm1 expects, so `_normalize_mxfp_scale` reshapes it before use. Verified via a standalone probe script (`npu_moe_init_routing_v2(quant_mode=3)` vs. the two-step `quant_mode=-1` + `npu_dynamic_mx_quant` reference) to be byte-identical (cos = 1.0) on Ascend A5 + torch_npu 2.10.0.post2, then confirmed end-to-end on the online and offline launch scripts — so this fused path is the only routing-quant implementation kept (no runtime toggle, no two-step fallback branch).

**Offline quantization (msmodelslim pre-quantized weights, flagless)**

- `W8A8_MXFP8` MoE checkpoints are detected from `quant_model_description.json` and handled by the new `ModelSlimMXFP8MoEScheme`, which registers `float8_e4m3fn` expert weights + `uint8` (E8M0, exponent + 127) block scales and delegates weight post-processing + forward to the **same** `NPUMXFP8MoEMethod` kernel (offline branch: reshape `[E, N, K/32] → [E, N, K/64, 2]` + transpose, no re-quant).
- **Router gate:** msmodelslim also quantises `mlp.gate` (`W8A8_MXFP8`). The gate is a `ReplicatedLinear`, so its quantization is now **description-driven** — for the offline `modelslim` path the gate receives the quant config and is dequantised correctly via `ModelSlimMXFP8Scheme`; the online path keeps it in BF16 (unchanged). Previously the fp8 gate was cast to BF16 **without** its block scale, scrambling the router and producing garbage output; this is the fix that makes the offline path usable.

### FRACTAL_NZ weight layout (review item 8)

ND vs NZ on the same benchmark, everything else equal:

| Metric | Online: ND → NZ | Offline: ND → NZ |
|--------|----------------|-----------------|
| **Total Token Throughput (tok/s)** | 2592.53 → 2643.95 (**+2.0%**) | 2552.76 → 2628.72 (**+3.0%**) |
| **Mean E2E Latency (ms)** | 7146.17 → 7004.54 (**-2.0%**) | 7259.02 → 7043.46 (**-3.0%**) |
| **Mean TTFT (ms)** | 144.32 → 134.96 (**-6.5%**) | 145.93 → 136.54 (**-6.4%**) |
| **P99 TPOT (ms)** | 51.58 → 49.60 (**-3.8%**) | 52.73 → 49.81 (**-5.5%**) |

Not the ~10% the int paths saw, but consistent across both modes, so NZ is what this PR
ships. A standalone kernel probe on the same box (gmm1 + gmm2 only, 128 experts) measured
+1.4% on decode-shaped and +3.8% on prefill-shaped inputs against a 0.2-0.3% noise floor,
matching the end-to-end delta.

Two things worth recording, since neither is obvious from the int8 precedent:

- **The cast must precede the transpose.** `npu_grouped_matmul_swiglu_quant_v2` asserts
  that weight and weight_scale carry the same transpose flag (`CheckMXTranspose`), and
  `npu_format_cast` returns a physically retiled, non-transposed tensor — so casting the
  already-transposed view fails outright with `transpositions are true/false`. The int8 MoE
  methods transpose first, but they carry no MX scale to keep in sync; the dense W4A8 path
  already uses the order adopted here.
- **Contiguous weights are not the answer.** Making weight and scale both contiguous is
  numerically correct but measurably slower (-6.2% decode at 128 experts), so the
  transpose views stay. A small-expert-count microbenchmark inverts this conclusion
  entirely (E=4 rates contiguous 58% *faster*), which is why the numbers above come from
  the real 128-expert shape.

# Style / consistency with the merged NPU quant PRs (#22352, #23650, #23795)

- All NPU ops go through `torch.ops.npu.*`; **no top-level `import torch_npu`**, no `current_platform` guards (module stays importable on CUDA/CPU/AMD/XPU CI).
- **Online** returns the method directly from `Fp8Config.get_quant_method` (mirrors dense `NPUMXFP8LinearMethod`). **Offline** subclasses `ModelSlimMoEScheme` and delegates weight post-processing / forward to a `self.kernel` (`NPUMXFP8MoEMethod`), registered in `get_moe_scheme`'s `moe_quant_schemes` list — the same pattern as the int8 / W4A4 / W4A8 MoE schemes.
- MoE weight + scale are kept as **non-contiguous transpose views** (`.transpose(1, 2)` with no `.contiguous()`), with the expert weight cast to **FRACTAL_NZ before** that transpose; gmm1 uses the fused `npu_grouped_matmul_swiglu_quant_v2`; the `group_list` count↔cumulative conversion is explicit (gmm1 cumulative, gmm2 count).
