# MiniMax-M3: allow shared-experts fusion on ROCm gfx942 and newer

`shared_experts_fusion_disable_reason` currently refuses on any non-CUDA device, so ROCm never gets shared-experts fusion even where the hardware supports it. This lifts that guard and gates it at gfx942 instead.

`minimax_m3_vl.py` carries the identical gate. `MiniMaxM3SparseForCausalLM` and `MiniMaxM3SparseForConditionalGeneration` are separate `EntryClass`es with separate `shared_experts_fusion_disable_reason` classmethods, and the served MiniMax-M3-MXFP8 checkpoint is the **VL** variant (`model_type: minimax_m3_vl`, per `configs/minimax_vl.py`) — so patching only one file would be a silent no-op on the model people actually run.

## Measurement status — stated plainly

**This PR has no benchmark or accuracy numbers of its own, and I am not claiming any.**

The earlier combined change (this gate + the alternate-stream overlap + a `prefill_attention_backend=aiter` serving default) measured +46.6%..+55.4% output throughput on 8x MI350X. That number belongs to the bundle, not to this PR, and decomposing it showed the input-throughput share came **entirely** from the serving default, not from either code change.

More importantly: in every run measured, the server reported `shared_experts_fusion=False` on both sides — the fusion this PR enables **never actually engaged**, because it also requires the model config and serving flags to request it. So the throughput effect of *this* gate specifically is unmeasured.

What this PR is, therefore, is an enablement gate: it removes a platform restriction that has no reason to exist on gfx942+. It should be reviewed on that basis, and someone with a configuration that genuinely turns fusion on should measure it before it is treated as a performance change.

The serving-defaults and cookbook half is a separate change and is not part of this PR.
