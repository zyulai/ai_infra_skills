## Motivation
- support decode context parallel(DCP) for Qwen3.5 models, use zigzag format to save kv on different kv rank
- this pr following https://github.com/sgl-project/sglang/pull/14982 and https://github.com/vllm-project/vllm/issues/34018

## Modifications

### DCP Group and Runtime Arguments
- `server_args.py` adds the `dcp_size` field and exposes `--decode-context-parallel-size` / `--dcp-size`.
- `distributed/parallel_state.py` adds `_DCP` and `get_dcp_group()`, and splits each TP group into DCP groups according to `dcp_size`.
- The `graph_capture()` group stack in `parallel_state.py` includes the DCP group, so DCP collectives can participate in CUDA graph capture.
- `model_executor/model_runner.py` stores `dcp_size` / `dcp_rank` and passes `decode_context_parallel_size` into model-parallel initialization.

### KV Cache, Allocator, and Owner Mask

The DCP KV ownership rule is:

```text
owner(abs_pos) = abs_pos % dcp_size
```

- `model_executor/forward_batch_info.py` adds `ForwardBatch.dcp_kv_mask`. In the eager path, the owner mask can be generated from `positions % dcp_size == dcp_rank`.
- `model_executor/cuda_graph_runner.py` adds `DecodeInputBuffers.dcp_kv_mask` as a fallback input for graph replay.
- `MHATokenToKVPool.set_kv_buffer()` in `mem_cache/memory_pool.py` supports `dcp_kv_mask`, and uses `masked_set_kv_buffer_kernel` to write only the tokens KV cache owned by the current DCP rank.
- `HybridLinearKVPool.set_kv_buffer()` in `mem_cache/memory_pool.py` forwards `dcp_kv_mask`, preventing the Qwen3.5 hybrid full/linear attention path from breaking.
- `models/utils.py` disables fused KV writes when `forward_batch.dcp_kv_mask` exists, so the write path does not bypass masked KV writes.
- `model_executor/model_runner_kv_cache_mixin.py` uses enlarged physical page allocation under DCP, allowing the full KV cache physical pages to hold DCP owner shards.
- `mem_cache/common.py` selects paged allocation according to the actual allocator page size, avoiding mismatches between the tree-cache page size and the real allocator page size.
- `managers/scheduler_components/invariant_checker.py` accounts for DCP physical-page slack, avoiding false positives caused by differences between logical token counts and physical page counts.

### Triton Attention DCP

#### Core utilities(layers/attention/utils.py):
- `create_triton_kv_indices_for_dcp_triton()` in `utils.py` builds local KV indices for the current rank from `req_to_token` according to the DCP owner rule. Regular attention reads a contiguous KV range; under DCP, each rank only reads absolute positions satisfying `abs_pos % dcp_size == dcp_rank`. For example, when `dcp_size=2`, rank 0 reads `0,2,4,...`, while rank 1 reads `1,3,5,...`.
- `get_dcp_lens()` in `utils.py` computes the local KV length visible to the current rank for each request. It supports both `start=None` and tensor `start` paths. `start` usually has shape `[batch_size]`, with one KV start offset per request; the actual KV range for request `i` is `[start[i], start[i] + lens[i])`.
- In `utils.py`, the `cp_lse_ag_out_rs()` pipeline is: LSE all-gather -> output rescale -> output all-reduce -> local head slice.

#### Changes in `triton_backend.py`:
- During initialization, the backend stores `dcp_size` / `dcp_rank` and sets `self.num_head` to the number of query heads actually seen by the Triton kernel after all-gather: `local_num_heads * dcp_size`.
- Decode metadata is split by `dcp_size`. Non-DCP continues to use `create_flashinfer_kv_indices_triton()` to generate full contiguous KV indices. Under DCP, `get_dcp_lens()` and `create_triton_kv_indices_for_dcp_triton()` generate only the current rank's KV-shard `kv_indptr` / `kv_indices`.
- `get_num_kv_splits()` uses the local KV-shard length under DCP decode rather than the full global `seq_lens`. 
- Add `_kv_cache_loc()` and `_set_kv_buffer()`. Under DCP, global `out_cache_loc` is mapped to local physical locations with `out_cache_loc // dcp_size`, and the owner mask is generated by `positions % dcp_size == dcp_rank`, so each rank only writes the tokens it owns. When DCP is disabled, `_kv_cache_loc()` returns `out_cache_loc` unchanged.
- KV writes in `forward_extend()` are isolated by DCP. Non-DCP continues to use the main-branch default `token_to_kv_pool.set_kv_buffer()` path. DCP uses `_set_kv_buffer()` so it can apply local locations and owner masks. The MLA path keeps the original manual-scale + direct-write logic; the current DCP changes are mainly for non-MLA models.
- KV writes in `forward_decode()` are similarly isolated. Non-DCP writes directly to `out_cache_loc`; DCP uses `_set_kv_buffer()`. This keeps regular Triton decode away from the DCP masked-write path.

#### Decode path:

- DCP decode first reshapes the current rank's Q to `[tokens, local_heads, head_dim]`, then performs an all-gather along the head dimension within the DCP group so every DCP rank has the full set of Q heads.
- Each rank calls the original Triton decode kernel with its local `kv_indices`, computing partial output and split-dimension partial LSE over the current rank's KV shard.
- The decode kernel's `attn_lse` includes a split dimension, so DCP first applies `torch.logsumexp(..., dim=-1)` over the split dimension to obtain the local LSE for the current rank's KV shard.
- Finally, `cp_lse_ag_out_rs()` performs LSE all-gather, global-LSE rescaling, output all-reduce, and local-head slicing. The final output shape remains the same as regular TP decode.

#### Extend path:

- `triton_ops/extend_attention.py` adds optional LSE output to the existing Triton extend kernel. `_fwd_kernel()` adds `LSE_Extend`, `stride_lse_bs`, `stride_lse_h`, and `STORE_LSE`. When `STORE_LSE=True`, the kernel writes the online-softmax `log(sum(exp(logits)))` value to `LSE_Extend`, which is needed to merge DCP partial outputs across ranks.
- `triton_ops/extend_attention.py` adds two switches to `_fwd_kernel()`: `SKIP_PREFIX` and `SKIP_EXTEND`. When `SKIP_PREFIX=True`, the prefix-KV loop is skipped and only current-chunk causal attention is computed. When `SKIP_EXTEND=True`, the current-chunk loop is skipped and only prefix-KV attention is computed.
- `extend_attention_fwd_with_lse()` is added as a wrapper. It takes `lse_extend`, calls `_fwd_kernel()` with `STORE_LSE=True`, and exposes `skip_prefix` / `skip_extend`. Regular non-DCP extend still uses the original `extend_attention_fwd()` / unified path and passes `STORE_LSE=False`, `SKIP_PREFIX=False`, and `SKIP_EXTEND=False`, preserving the original semantics.
- `forward_extend()` enters `_forward_extend_dcp()` when `dcp_size > 1`, avoiding the Python dense-attention fallback and preventing long-context OOM from constructing dense score tensors with shape similar to `[extend_tokens, heads, context_tokens]`.
- `_forward_extend_dcp()` splits extend attention into current chunk and prefix KV:
  - All DCP ranks first compute the current chunk. The current chunk's K/V still comes from the local tensors produced by this forward pass, so each rank uses its local query heads and calls `extend_attention_fwd_with_lse(..., skip_prefix=True)` to compute its own `current_out/current_lse`. `skip_prefix=True` is not rank-specific; all DCP ranks use it during the current stage.
  - All DCP ranks then compute the prefix shard. Prefix KV has already been sharded in KV cache according to the DCP owner rule, so the prefix stage first all-gathers query heads and then calls `extend_attention_fwd_with_lse(..., skip_extend=True)`. Each rank computes only its own prefix-KV shard's `prefix_out/prefix_lse`.
- Prefix partial output/LSE is merged across DCP ranks through `cp_lse_ag_out_rs(..., return_lse=True)`. The prefix and current parts are then merged with `logaddexp` over LSE and output rescaling with `exp(part_lse - final_lse)`, ensuring the softmax denominator is equivalent to full prefix+current attention.
- If prefix KV is empty, `_forward_extend_dcp()` directly returns the current-chunk result and skips prefix all-gather and cross-rank merge, reducing redundant communication during initial prefill.
- DCP extend currently explicitly rejects `sinks`, custom masks, and sliding-window paths to avoid silently running unverified combinations.

+def create_triton_kv_indices_for_dcp_triton(
+    req_to_token_ptr,  # [max_batch, max_context_len]

+def get_dcp_lens(
+    lens: torch.Tensor,
+    dcp_size: int,
+    dcp_rank: int,
+    start: torch.Tensor | None = None,
+) -> torch.Tensor:
+    if dcp_size == 1:

+def cp_lse_ag_out_rs(
