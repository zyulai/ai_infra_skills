## 正文(PR 描述)

## Motivation

**A distributed weight update can report success and advance the policy version even when only part of the requested weights—or none of them—were received.**

The ordinary receiver iterates `zip(names, dtypes, shapes)`. Unequal list lengths silently truncate the receive set. The scheduler then loads that prefix, reports success, and records the requested version. For RL rollout synchronization, this can advertise a new policy while some weights still belong to the previous policy.

A separate failure occurs when a later dtype, shape or allocation is invalid: the receiver has already posted earlier asynchronous broadcasts before discovering the error, and exits without waiting for those handles.

## Before/after evidence

The same CPU probe was run against upstream `4f8b6867534c8a6632845353997555fca857dd63` and this branch. It calls the **actual scheduler, distributed receiver and weight loader**, using a two-weight CPU model and a controlled broadcast boundary. Both weights start at `1`; successful receives supply `w1=9`, `w2=10`.

| Manifest | Upstream | This PR |
|---|---|---|
| Two names, one dtype | **Success**, records `v2`; `w1=9`, **`w2=1`** | **Failure**, zero receives posted; both weights and version unchanged |
| Two names, one shape | **Success**, records `v2`; `w1=9`, **`w2=1`** | **Failure**, zero receives posted; both weights and version unchanged |
| Two names, no dtypes | **Success**, records `v2`; **neither weight changed** | **Failure**, no new version recorded |
| Invalid second dtype or negative second shape | Failure after posting **one receive, with zero handles waited** | Failure **before posting any receives** |
| Valid two-weight update | Success; `w1=9`, `w2=10`, version `v2` | Same result and received values |

All **three malformed-length scenarios falsely succeeded upstream; zero did with this change**. These are deterministic injected CPU cases, not a measured production failure rate or GPU model-output result.

## Modifications

- Require equal `names`, `dtypes` and `shapes` lengths before allocation or dispatch to either receive format; report all three lengths in the error.
- Prepare every ordinary receive buffer before posting the first broadcast. Existing PyTorch dtype/shape/allocation checks therefore complete before any data collective is entered on that receiver.
- Preserve dtype aliases and `torch.dtype` inputs, scalar and zero-sized shapes, tensor order, the flattened format, and the existing empty ordinary-round no-op.
- Extend the existing registered CPU weight-update test file; no new endpoint, option, wire field or collective.

This complements #50229: that PR propagates TP update outcomes, while this one rejects malformed input before the receive phase starts. It applies independently to main. #42271 adds external receivers and explicitly leaves the default native path unchanged; #48276 adds intentional custom-loader refusal, rather than native manifest preflight.

### Recovery limit

**Receiver-side preflight cannot cancel a trainer that already entered a collective.** Such a sender still needs to observe the failed update and recover its transport. The fix prevents silent prefix acceptance and avoids this receiver starting a partial round; it does not add a sender handshake, rollback, or cross-rank recovery protocol.

## Speed Tests and Profiling

The first ordinary broadcast now starts after all receive buffers are allocated. Valid rounds retain the same tensor buffers, byte count, broadcast order/count and asynchronous waits; the previous implementation already retained all buffers until those waits completed. No extra tensor copy or collective is introduced. This changes allocation/communication overlap on weight-update control operations; GPU update latency and serving throughput were not benchmarked.
