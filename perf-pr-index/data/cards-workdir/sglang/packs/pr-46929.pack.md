## Summary

`_config_for_shape` decides whether FlashInfer's MNNVL CuTe DSL `DEFAULT_CONFIG` serves the current shape or SGLang has to supply a re-targeted single-profile config. It checked `StaticProfile.matches()` without a compute capability.

FlashInfer ships tp=4 hidden=8192 top_k=10 profiles keyed to GB300 (sm_103) and Rubin (sm_107). A profile keyed to one architecture never matches an unspecified (`None`) architecture. So on those GPUs SGLang found no match, discarded FlashInfer's measured tp=4 routes, and served the re-targeted GB300 tp=8 presets instead.

This passes the device's compute capability and uses `MNNVLCuteDSLConfig.find()`. That is the lookup the FlashInfer workspace's `resolve()` performs, so SGLang now re-targets only the shapes FlashInfer ships no profile for on this architecture. It also replaces a stale comment that said `DEFAULT_CONFIG` ships only GB300 H=8192/K=10.

`find()` and the `compute_capability` argument need FlashInfer 0.7.2.post1 or newer. Main has been on 0.7.3 since #48468. The tp=4/H8192/K10 profiles in 0.7.3 are still keyed to `(10, 3)` and `(10, 7)` only.

## Validation

All runs on 4× GB300 (dlcluster, sm_103), using `lmsysorg/sglang:dev` with `flashinfer-python` 0.7.3 and this branch overlaid.

- `test/registered/unit/layer_boundary/test_cutedsl_ar_fusion.py`: 33 passed. That includes the new `test_a_profile_shipped_for_this_arch_is_not_retargeted`, where sm_103 and sm_107 keep `DEFAULT_CONFIG` and sm_100 is re-targeted.
- On the device, `_config_for_shape(DEFAULT_CONFIG, tp_size=4, hidden_size=8192, top_k=10, compute_capability=(10, 3))` returns `DEFAULT_CONFIG`. It logs no "re-targeting" line, and `find()` returns the `(10, 3)` profile.
- Timing at 4 ranks, tp=4, H=8192, top_k=10, bf16, with RMSNorm. The method is the one in FlashInfer's `benchmarks/comm/bench_mnnvl_cutedsl_h5120.py`: 20 calls per CUDA graph, the median of 30 replays, and the max across ranks. It compares the shipped GB300 tp=4 routes (this PR) with the re-targeted tp=8 presets (before). Ratio = before / after, so values above 1 mean this PR is faster. The run was repeated twice, and both runs agree to within about 0.1 µs.
