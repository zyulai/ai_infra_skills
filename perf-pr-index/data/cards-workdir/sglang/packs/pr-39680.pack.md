## Motivation

The CuTe DSL KDA decode kernels (`kda_kernel_small_batch`, `kda_kernel_small_batch_varlen`,
`kda_kernel_large_batch`, `kda_kernel_large_batch_varlen` in
`python/sglang/kernels/ops/attention/cutedsl_kda.py`) stage the recurrent state through shared
memory with a `global (V, K) <-> shared (K, V)` transpose, once to load the state and once to write it
back. The thread -> element mapping for that transpose uses **V as the fast-varying index**:

```python
k_load = flat_idx // TILE_V
v_load = flat_idx % TILE_V
```

But the state tensor is `(pool_size, HV, V, K)` with **K contiguous** and V strided by
`K * sizeof(fp32) = 512 B`. So the 32 lanes of a warp hit 32 *different* 32-byte sectors and use
4 bytes out of each one — roughly 28 sectors per request where ~4 is the ideal for 32 x 4 B. The
same strided pattern is repeated on the write-back. Since the decode step is state-bandwidth-bound
(every token reads and writes the full fp32 `[HV, V, K]` state), this dominates kernel time.

## Modifications

Swap the two index expressions in each of the 8 transpose sites (one load pair + one write-back pair
per kernel variant) so that **K is the fast-varying index**:

```diff
-                    k_load = flat_idx // TILE_V
-                    v_load = flat_idx % TILE_V
+                    k_load = flat_idx % TILE_K
+                    v_load = flat_idx // TILE_K
```

(`TILE_V_SMALL` -> `TILE_K` in the two small-batch kernels, `TILE_V` -> `TILE_K` in the two
large-batch kernels; the `k_write` / `v_write` pairs change identically.)

`flat_idx` ranges over exactly `[0, TILE_K * TILE_V)` in every loop, so both the old and the new
expression are bijections onto the same `(k, v)` tile: the same elements land in the same shared-memory
slots, the existing `if k_load < TILE_K` guards and `v_global < v.shape[3]` bounds checks are
untouched, and no barrier, loop trip count or arithmetic order changes. Consequently the kernel's
**output tensor and the in-place fp32 state update are bit-identical** before and after (verified
below). Nothing else in the file is modified (16 lines, 8 two-line pairs).

Now a warp's 32 lanes read/write 32 consecutive fp32 along K = 128 contiguous bytes = 4 sectors.

### Known tradeoff (shared memory)

The new mapping trades a global-memory win for a shared-memory regression in the transpose itself.
`TILE_V_PADDED = 36` was chosen so the *compute* loop is bank-conflict-free: there a warp covers
`8 k x 4 v` (`k_local = in_warp_tid // V_PER_WARP`, `v_local = in_warp_tid % V_PER_WARP`), and
bank `(36*k + v) % 32 = (4*k + v) % 32` hits 32 distinct banks. In the transpose, however, the new
mapping walks 32 consecutive `k` at fixed `v`, and `(4*k + v) % 32` takes only 8 distinct values —
a 4-way bank conflict on the staging loads/stores. Nsight Compute confirms it (b=32, large-batch
kernel): shared-load bank conflicts 29.6 K -> 4.74 M, shared-store 5.7 K -> 4.74 M, LSU shared
wavefronts 10.9 M -> 15.6 M (ld) and 3.3 M -> 8.0 M (st). The kernel is still ~3x faster end to end,
which bounds the cost of the shared side.

No single padding constant fixes both patterns: the transpose wants `gcd(P, 32) = 1` (odd `P`), the
compute loop wants `P == 4 (mod 32)`. The remaining lever is a swizzled shared-memory layout or a
128-bit vectorized load of 4 consecutive `k` per thread — not a padding tweak. Left as a follow-up to
keep this PR a pure, bit-identical index swap.

## Accuracy Tests

Because the change is a permutation of the thread -> element assignment with no arithmetic change,
the expected result is bit-exactness, and that is what is observed.

A standalone check ran `cutedsl_fused_sigmoid_gating_kda_update` on the stock and patched kernel
across 9 cases covering all four kernel variants, three input classes, and the `pool_idx < 0` pad
path, hashing (sha256) the raw bytes of the bf16 output and of the updated fp32 state, and also
comparing both arms to an independent from-scratch fp32 PyTorch reference of the recurrent step
(`H=HV=96`, `K=128`, non-zero initial state so the load half of the transpose is exercised):

| case | kernel variant | inputs | out sha256 equal | state sha256 equal | rel err vs fp32 ref (out / state) |
|---|---|---|---|---|---|
| b=32,  dv=128 | dense large-batch | randn | yes | yes | 3.1e-3 / 6.6e-4 |
| b=128, dv=128 | dense large-batch | randn | yes | yes | 2.9e-3 / 6.3e-4 |
| b=32,  dv=256 | dense large-batch | randn | yes | yes | 2.3e-3 / 6.7e-4 |
| b=16,  dv=128 | dense small-batch | randn | yes | yes | 3.8e-3 / 6.3e-4 |
| b=64,  dv=128 | varlen large-batch | randn | yes | yes | 2.9e-3 / 6.6e-4 |
| b=8,   dv=128 | varlen small-batch | randn | yes | yes | 2.3e-3 / 6.7e-4 |
| b=32,  dv=128 | dense large-batch | all zeros | yes | yes | 0 / 1.0e-3 |
| b=32,  dv=128 | dense large-batch | range stress (q, k magnitude ~64; v ~256; g from -1e-6 to -40; beta from 1e-6 to 1-1e-6) | yes | yes | 3.2e-3 / 1.6e-6 |
| b=32,  dv=128 | dense large-batch | randn + every 7th `pool_idx = -1` | yes | yes | 2.8e-3 / 5.9e-4 |

All 9 cases: output **and** state bit-identical stock vs patched; reference errors are identical on
both arms (bf16 output rounding), all values finite.

- `test/registered/attention/test_kda_prefill_cutedsl.py` covers the CuTe DSL *prefill* kernel (4-gpu-b200 suite);
- the GDN sibling `test_cutedsl_gdn.py` currently has its precision test skipped.

## Speed Tests and Profiling

Kernel-only timing via CUPTI (10 warmup + 10 timed launches per config), bf16, `dqk = dv = 128`,
`qo_len = 1`, recurrent decode step, single-GPU. `h = 96` (Kimi-K3). All rows are within-box A/B comparisons with **unlocked SM clocks**; the A/B/A protocol
(stock -> patched -> stock) bounds the clock/thermal noise (A-vs-A drift <= 0.03 % on every row,
orders of magnitude below the effect).

The numbers come from a standalone CUPTI harness rather than the in-tree
`benchmark/bench_linear_attention/bench_cutedsl_kda_decode.py` (#21203, Triton vs. CuTe DSL); I can append
that script's stock-vs-patched output on request.

### NVIDIA B200 PCIe

`h = 96`, `dv = 128`; median of 3 per phase.

| batch | stock (us) | patched (us) | delta | speedup |
|---|---|---|---|---|
| 32  | 476.5  | 152.0  | -68.1 % | 3.14x |
| 128 | 1817.7 | 584.5  | -67.9 % | 3.11x |
| 512 | 7171.1 | 2309.5 | -67.8 % | 3.11x |

A wider sweep on the same B200 (`b in {1, 8, 16, 32, 64, 128, 512} x dv in {128, 256, 512}`, both
dense kernel variants) showed a consistent ~-67.8 %.

Only the two **dense** variants are exercised by these shapes (b >= 32 -> `kda_kernel_large_batch`;
the b=16 accuracy case -> `kda_kernel_small_batch`). The two **varlen** variants are covered by the
bit-exactness check above but were not timed; the same 8-lane swap applies to them and the access
pattern is identical.

### Mechanism (Nsight Compute)

B200, `b = 32`, `h = 96`, `kda_kernel_large_batch`, one profiled launch, `--cache-control all`.

| metric | stock | patched |
|---|---|---|
| global load sectors / request (`l1tex__average_t_sectors_per_request_pipe_lsu_mem_global_op_ld`) | 28.39 | 3.68 |
| global store sectors / request (`..._op_st`) | 30.18 | 3.82 |
| L1TEX sectors total (`l1tex__t_sectors.sum`) | 101.0 M | 12.9 M (7.8x fewer) |
| L1TEX throughput (% peak) | 83.75 | 65.79 |
| long-scoreboard stalls / issue | 17.48 | 4.10 |
| DRAM bytes read (`dram__bytes_read.sum`) | 204,564,736 | 204,542,208 (unchanged) |
| DRAM throughput (% peak) | 9.54 | 29.83 |
| registers / thread | 128 | 124 |
| kernel duration | 480.9 us | 151.7 us |

DRAM traffic is unchanged: the kernel already moved exactly the bytes the state-update model
predicts, it was just delivering them through ~8x more L1 sectors than necessary. The predicted
mechanism (sectors/request collapse, L1TEX pressure drops, DRAM bytes flat, DRAM utilization rises
toward the bandwidth roof) is what moved.
