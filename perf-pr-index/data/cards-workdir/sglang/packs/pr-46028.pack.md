## Motivation

Profiling shows substantial device-to-host (D2H) transfer and CPU SHA-256 computation in Cosmos3's conditioning fingerprint path before VAE encoding. Fingerprinting takes **115–614 ms** across the measured 480p–1080p workloads.

SHA-256 benefits from optimized CPU implementations, but sequential block chaining limits GPU parallelism for a single large tensor. Our single-message Triton SHA-256 prototype was **23–28× slower** than CPU SHA-256 including D2H. The existing GPU alternative, `python/sglang/kernels/ops/memory/gpu_tensor_hash.py`, uses a custom **64-bit non-cryptographic hash** with no cryptographic collision-resistance guarantee; a collision could cause incorrect VAE cache reuse.

[BLAKE3](https://github.com/BLAKE3-team/BLAKE3) is a cryptographic tree hash whose independent chunks and tree reductions suit GPU parallelism. BLAKE3-256 targets **128-bit collision resistance** ([specification](https://c2sp.org/BLAKE3)), matching SHA-256's collision-resistance strength ([NIST](https://csrc.nist.gov/projects/hash-functions)). Computing the fingerprint on the GPU avoids transferring the input back to the CPU and returns only a **32-byte digest**.

## Modifications

- Add a Triton implementation of standard unkeyed BLAKE3-256. It hashes the complete tensor contents on the GPU and returns only the 32-byte digest to the CPU.
- Use a Cosmos3-specific VAE conditioning cache key containing the digest, tensor metadata and encoder settings. Reuse the existing cache storage and invalidation mechanisms, preserving CPU and distributed fallbacks.
- Add BLAKE3 correctness tests and a focused Cosmos3 cache-key test.

### Generality and follow-up work

The BLAKE3 kernel hashes raw CUDA tensor bytes independently of Cosmos3's video format. Concrete reuse candidates in the existing conditioning cache paths include:

| Model | Potential integration |
| --- | --- |
| Wan2.1/2.2 I2V, Wan2.2 TI2V-5B | Image-conditioning tensors in the Wan VAE encoding cache |
| FLUX.2 / Klein | Reference-image tensors in the VAE encoding cache |
| Qwen-Image-Edit | Input-image tensors in the VAE encoding cache |
| LTX-2 I2V | Image-conditioning tensors in the video VAE encoding cache |
| MiniMax-H3 | Image/video tensors in the VAE encoding cache, including tiled encoder inputs |

Follow-up work is to discuss shared GPU fingerprinting with the community and evaluate these integrations, retaining each model's tensor metadata and encoder settings in cache keys. Output consistency and E2E benefits require validation for each model.

+    b = _rotr(b ^ c, 7)

+def _blake3_device(tensor: torch.Tensor) -> torch.Tensor:
+    if not tensor.is_cuda or tensor.layout != torch.strided:
+        raise ValueError("BLAKE3 requires a dense CUDA tensor")
+    with torch.cuda.device(tensor.device):
+        data = tensor.detach().contiguous().reshape(-1).view(torch.uint8)
+        n_chunks = max(triton.cdiv(data.numel(), 1024), 1)
+        group = min(triton.next_power_of_2(n_chunks), 128)
+        n_nodes = triton.cdiv(n_chunks, group)
+        nodes = torch.empty((n_nodes, 8), dtype=torch.uint32, device=data.device)
+        _chunk_kernel[(n_nodes,)](
+            data,
+            nodes,
+            data.numel(),
+            GROUP=group,
+            ROOT=n_nodes == 1,
+            ALIGNED=data.data_ptr() % 4 == 0 and data.numel() % 4 == 0,
+            IV=_IV,
+            num_warps=4,
+        )
+        while n_nodes > 1:
+            group = min(triton.next_power_of_2(n_nodes), 128)
+            next_count = triton.cdiv(n_nodes, group)
+            next_nodes = torch.empty(
+                (next_count, 8), dtype=torch.uint32, device=data.device
+            )
+            _parent_kernel[(next_count,)](
+                nodes,
+                next_nodes,
+                n_nodes,
+                GROUP=group,
+                ROOT=next_count == 1,
+                IV=_IV,
+                num_warps=4,
+            )
+            nodes = next_nodes
+            n_nodes = next_count
+        return nodes.view(torch.uint8).reshape(32)

+    Returning bytes synchronizes a 32-byte device-to-host copy.
