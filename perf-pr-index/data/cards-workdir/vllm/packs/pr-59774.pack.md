## Overview

Adds `ROCM_OCTAVE`, an attention backend that keeps the KV cache of
full-attention layers at 3-4 bits per value, with native HIP kernels for
RDNA3 (gfx1100) and MI300X (gfx942). Select it with
`--kv-cache-dtype octave_k3v3`, `octave_k3v4` or `octave_k3v3_compact`
(216, 248 and 196 bytes per slot at head size 256, against 1024 for fp16).

RFC: #59773. `docs/design/rocm_octave.md` describes the format and the
per-architecture contract.

## Claims

- **Capacity:**
  - On 4× RX 7900 XTX with Qwen3.8-27B, 4.6× the KV tokens of fp16.
  - On one MI300X, 1.95× the tokens of AITER's fp8 cache (7.0M vs 3.6M, i.e.
    53 vs 27 concurrent 128k requests).
- **Quality:** GSM8K and a 126k needle-in-a-haystack test match fp16 and fp8
  on both architectures. Next-token NLL at 380k is +0.0009 to +0.0015 nats
  over fp16.
- **Speed:**
  - On MI300X, decode for one request matches AITER fp8. Per layer it is
    faster from 32k on (65 vs 103 µs at 128k).
  - On RDNA3 at 380k, per layer, decode is 4.6× faster than TurboQuant and
    MTP verification 11× faster.
- **Works with MTP and CUDA graphs.** No host syncs in the metadata builder.
  We have served it in production on RDNA3 since October 2, 2026.
- **Guarded to the validated architectures**, gfx1100 and gfx942:
  - CMake builds the sources and registers the ops only for them.
  - `supports_compute_capability` rejects other devices.
  - The tests skip elsewhere.

<details>
<summary>MI300X: NIAH in detail</summary>

The haystack is vLLM's own Python source, cut to 126k tokens. 16 keys are
inserted every ~7.7k tokens, each a line such as
`# PROJECT KEY Aldebaran: WK3DEGZD`, with star names as look-alike labels and
random 8-character values. The same document is cut at 32k, 64k and 126k,
which hold 4, 8 and 16 keys. For each key present the model is asked, thinking
off, for only that key's value; an answer counts if it contains the exact
value. Keys sit between 3% and 95% of the context.

| KV cache | 32k (4 keys) | 64k (8 keys) | 126k (16 keys) | another key's value returned |
|---|---|---|---|---|
| `octave_k3v3` | 4/4 | 8/8 | 16/16 | 0 |
| `octave_k3v4` | 4/4 | 8/8 | 16/16 | 0 |
| `octave_k3v3_compact` | 4/4 | 8/8 | 16/16 | 0 |
| fp8, `ROCM_AITER_FA` | 4/4 | 8/8 | 16/16 | 0 |
| fp16, `ROCM_ATTN` | 4/4 | 8/8 | 16/16 | 0 |

The model saturates this task at 128k. So it shows that the 3-bit cache loses
no retrieval there; it does not rank the formats. The harder test is the 800k
key curve in the RFC, where the keys start to blur only past 640k, because of
the model and not the cache.
</details>

## Details

What changes. Most of the PR is new files:
- `vllm/v1/attention/ops/rocm_octave.py`: the format and its PyTorch
  reference, which defines the byte layout.
- `vllm/v1/attention/backends/rocm_octave_attn.py`: the backend and its
  metadata builder.
- `csrc/attention/octave_*`, the kernels:
  - store, reduce, rotation and a portable decode, shared by both
    architectures;
  - WMMA decode and prefill for gfx1100;
  - MFMA decode and prefill for gfx942;
  - the op registration in `octave_torch_bindings.cpp`.
- Tests, docs, and `--model` plus the new cache dtypes in
  `benchmarks/attention_benchmarks`.

Changes to existing files are small:
- the three cache dtypes in `vllm/config/cache.py`,
  `vllm/utils/torch_utils.py` and `vllm/v1/kv_cache_interface.py`;
- the backend in the registry and in the ROCm platform's selection;
- the sources in `CMakeLists.txt`;
- `customize_spec` now runs under the current vLLM config, because the
  backend needs the model's rotary dims to size the slot;
- in `qwen4_exp` (QSA), Octave as the main cache through a sparse decode,
  with the new fused QSA prepare turned off for an Octave cache, since it
  writes raw BF16 K/V.

Nothing changes for other backends or cache dtypes.

Design choices a reviewer may want to know about:
- **Native kernels only.** There is no Triton fallback; an architecture is
  added once it has its own kernels and passes the tests and an end-to-end
  run. The RFC lists what each one needs.
- **The metadata builder is the backend's own.** It builds the per-query
  maps on the device without host syncs, supports `UNIFORM_BATCH` CUDA
  graphs, and refreshes the maps between fused MTP draft steps.
- **On gfx942**:
  - QK runs on `v_mfma_i32_16x16x32_i8`, with the query split into high and
    low int8 halves.
  - V is widened to fp16 by one `v_perm`: each codebook byte becomes an exact
    fp16 denormal, which the MI300 MFMA keeps.
  - The decode file is built with `-amdgpu-mfma-vgpr-form`, so the
    accumulators do not halve the occupancy.
- **Supported models.** Head size 256 with 64 RoPE dims, i.e. Qwen3-Next and
  Qwen3.5 / 3.6 / 3.8.
  - The decode handles up to 8 query heads per KV head on each GPU.
  - The sparse decode and the exact sink/recent window are QSA-only and
    gfx1100-only for now.
  - Head size 128 is the next step.
- **Size.** This is a large PR: about 1.4k lines of gfx942 kernels on top of
  the RDNA3 ones. Each architecture lives in its own file behind the same
  `octave_prefill` / `octave_decode` entry points, so it can be reviewed and
  later removed on its own.

**Not a duplicate.** I searched open PRs and issues for `octave`,
`turboquant rocm`, `kv cache 3-bit`, `kv cache quantization hip` and
`lloyd-max kv`. The closest are:
- UltraQuant (#57057): FP4 with FlyDSL for gfx950, built on TurboQuant.
- KVarN (#46613 / #46812): Triton, CUDA-first.
- #43835: HIP int8/int4 for CDNA.
- #40396: a Triton TurboQuant decode for MI300X.
- #53231: TurboQuant for Gemma 4 on ROCm.
- #59132: Triton attention for RDNA without KV quantization.

None targets RDNA with native kernels, and none runs below 8 bits with MTP on
ROCm.

+// Walsh-Hadamard butterflies over DPL consecutive dims per lane, then across
+// lanes with xor distance 1..LANE_MASK. Unnormalized.
+template <int LANE_MASK>
+__device__ __forceinline__ void fwht_wave(float (&x)[DPL], int lane) {
+  #pragma unroll
+  for (int h = 1; h < DPL; h <<= 1) {
+  #pragma unroll
+    for (int i = 0; i < DPL; ++i) {
+      if ((i & h) == 0) {
+        float a = x[i], b = x[i + h];
+        x[i] = a + b;
+        x[i + h] = a - b;
+      }
+    }
+  }
+  #pragma unroll
+  for (int m = 1; m <= LANE_MASK; m <<= 1) {
+    const bool hi = lane & m;
+  #pragma unroll
+    for (int i = 0; i < DPL; ++i) {
+      float o = __shfl_xor(x[i], m);
+      x[i] = hi ? o - x[i] : x[i] + o;
+    }
+  }
+}

+  return ((bits[i >> 5] >> (i & 31)) & 1) ? -1.0f : 1.0f;

+// Rotate a lane's 8 dims like K (64-dim blocks) or like V (one 256-dim

+  #pragma unroll

+  fwht_wave<16>(x, lane);
+  #pragma unroll
+  for (int i = 0; i < DPL; ++i) x[i] *= 0.0625f;

+// Midpoints of the int8 codebooks (rocm_octave.LUT), in codebook units.
+__device__ constexpr float kThr3[7] = {-103.f, -62.f, -29.5f, 0.f,
+                                       29.5f,  62.f,  103.f};
+__device__ constexpr float kThr4[15] = {-110.5f, -84.5f, -66.f, -50.5f, -36.5f,
+                                        -24.f,   -12.f,  0.f,   12.f,   24.f,
+                                        36.5f,   50.5f,  66.f,  84.5f,  110.5f};

+// Nearest codebook entry on the group RMS (4- or 3-bit per lane), codes in
+// [0, 2^bits). Returns the stored scale, times LUT_ONE: the one that makes
+// x . x_hat = |x|^2, so quantization does not shrink scores or outputs.
+template <int MASK>
+__device__ __forceinline__ float quantize_group(const float (&x)[DPL],
+                                                int (&codes)[DPL],
+                                                float group_dims, bool four) {
+  float ss = 0.f;
+  #pragma unroll
+  for (int i = 0; i < DPL; ++i) ss += x[i] * x[i];
+  ss = xor_sum<MASK>(ss);
+  const float to_lut =
+      (four ? 46.0f : 59.0f) / fmaxf(sqrtf(ss / group_dims), 1e-12f);
+  float num = 0.f;
+  #pragma unroll
+  for (int i = 0; i < DPL; ++i) {
+    const float y = x[i] * to_lut;
+    int c = 0;
+  #pragma unroll
+    for (int k = 0; k < 15; ++k)
+      c += (four ? y > kThr4[k] : (k < 7 && y > kThr3[k])) ? 1 : 0;
+    codes[i] = c;
+    num += x[i] * (float)(int8_t)(four ? lut4((uint32_t)c) : lut3((uint32_t)c));
+  }
+  num = xor_sum<MASK>(num);
+  return num > 0.f ? ss / num * LUT_ONE : 0.f;
+}

+// 4-bit: one word per 8 dims (lane-local). 3-bit: this lane's contribution to
+// the 2-bit plane word (16 dims, 2 lanes) and the 1-bit plane word (32 dims,
+// 4 lanes); callers OR across lanes.
+__device__ __forceinline__ uint32_t pack4(const int (&c)[DPL]) {
+  uint32_t w = 0;
+  #pragma unroll
+  for (int i = 0; i < DPL; ++i)
+    w |= (uint32_t)c[i] << (8 * (i & 3) + 4 * (i >> 2));
+  return w;
+}
+__device__ __forceinline__ void pack3(const int (&c)[DPL], int idx,
+                                      uint32_t& lo, uint32_t& hi) {
+  lo = 0;
+  hi = 0;
+  #pragma unroll
+  for (int i = 0; i < DPL; ++i) {
+    const int e16 = (idx & 1) * DPL + i;  // dim within the 16-dim lo word
+    const int e32 = (idx & 3) * DPL + i;  // dim within the 32-dim hi word
+    lo |= (uint32_t)(c[i] & 3) << (8 * (e16 & 3) + 2 * (e16 >> 2));
+    hi |= (uint32_t)(c[i] >> 2) << (8 * (e32 & 3) + (e32 >> 2));
+  }
+}

+                 const int* __restrict__ k_signs,

+    }
+  }

+    hi = xor_or<2>(hi);

+      *reinterpret_cast<uint32_t*>(dst + F::OFF_V + 4 * (lane >> 1)) = lo;
+    if ((lane & 3) == 0)
+      *reinterpret_cast<uint32_t*>(dst + F::OFF_V + D / 4 + 4 * (lane >> 2)) =
+          hi;
+  }
+
+  uint16_t* sc = reinterpret_cast<uint16_t*>(dst + F::OFF_SC);
+  if (KC ? lane == 0 : (lane & 7) == 0) sc[lane >> 3] = f_to_half_bits(k_scale);
+  if (lane == 0) sc[F::NUM_KSC] = f_to_half_bits(v_scale);
+}

+// ---------------------------------------------------------------------------
+// Decode stage 1: grid (num_q, num_kv_heads, num_splits), block 128.
+// A block serves up to QG consecutive query tokens of one request (only the
+// first token of each group of a run launches work) and all G query heads of
+// its KV head: ROWS = QG * G attention rows share every K/V load.
+// ---------------------------------------------------------------------------
+constexpr int WAVES = 4;
+constexpr int CHUNK = 32 * WAVES;

+template <int VB, bool KC, int G, int QG, typename QT>
+__global__ void __launch_bounds__(128)
+    decode_kernel(const QT* __restrict__ Q, const uint8_t* __restrict__ cache,
+                  const int* __restrict__ block_table,
+                  const int* __restrict__ q_to_req,
+                  const int* __restrict__ q_to_klen, float* __restrict__ mid_o,
+                  const int* __restrict__ k_signs, float sm_scale_log2,
+                  int num_q, int block_size, int max_blocks, int num_reqs,
+                  int num_phys_blocks, int num_splits, int64_t sq0, int64_t sq1,
+                  int64_t scb, int64_t sch, int64_t sct, int64_t smo,
+                  int64_t smh, int64_t sms) {

+  constexpr int QW = D / 4;  // int8 query words per row

+  __shared__ float S[ROWS][CHUNK];

+  const int kvh = blockIdx.y;

+      if ((qi - s) % QG != 0) return;  // served by the group leader
+      while (nq < QG && qi + nq < num_q && q_to_req[qi + nq] == req) ++nq;
+    }
+  }

+  int klen[QG];

+    kl = min(max(kl, 0), max_kv);
+    klen[j] = kl;
+    kv_max = max(kv_max, kl);
+  }
