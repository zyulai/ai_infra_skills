## Purpose

`FastIncrementalDetokenizer` seeds `DecodeStream` with the whole prompt, so each request's first output token decodes the entire prompt on the output-processing loop, stalling every other stream (17 ms at 100k tokens, ~40 ms with byte-fallback tokenizers). After its first emitted chunk `DecodeStream` keeps only the new ids, so the seed only shapes the first delta. This PR seeds it with a short prompt tail that reproduces that delta exactly:

- the tail holds 5 tokens (`INITIAL_INCREMENTAL_DETOKENIZATION_OFFSET`) that decode to text on their own, since Metaspace, WordPiece and leading-`Strip` decoders treat the start of the text specially;
- if the tail's text ends in U+FFFD (it starts inside the prompt's last character), it is extended by up to 3 tokens; if the prompt itself ends in U+FFFD, or the walk exceeds 256 tokens, the full prompt is used.

No new config or env var.

Tokenizers: one in-process tokenizer per context-dependent decoder (ByteLevel, ByteFallback + Fuse + Strip, Metaspace, WordPiece, BPEDecoder suffix, CTC) and 11 ungated hub tokenizers (byte-level BPE, Llama byte fallback, BERT, T5, XLM-R). ## Notes

- **Prompts ending in U+FFFD (#48853, pre-existing).** If the prompt's text ends in U+FFFD (a token-id prompt cut inside a multi-byte character, or ending in invalid byte tokens), `DecodeStream` streams its whole seed text in the first delta, so main returns the entire prompt text there. Seeding with a tail would only shorten the leaked text, so this PR keeps full-prompt seeding in that case: output is unchanged and the cost stays O(prompt). #48854 routes these requests to the slow detokenizer.
- **Limits.** A decoder that rewrites text across tokens after `Fuse` (e.g. a multi-character `Replace`) could in principle differ; no tokenizer we checked has one. For a token-id prompt whose byte-fallback run is invalid only before the tail, the tail streams the correct text where full-prompt seeding streams the whole prompt.
- **Supersedes #51281 and #57330** (stalled), which truncate to a fixed 32 / 128-token tail. Per @njhill's review, a fixed tail is not always safe: prompts ending in 32+ skipped special tokens lose the first output token's leading space with Metaspace / WordPiece / `Strip` decoders, which this PR avoids by counting only tokens that decode to text. Thanks to @elad-inferize and @cqulilujia for the bounded-tail idea.
- With the fastokens patch applied (`VLLM_USE_FASTOKENS=1`, fastokens 0.3.6), the test file passes for `gpt2` and `Qwen3-0.6B`; fastokens does not load the other hub tokenizers.

+def get_decode_stream_seed(
+    tokenizer: Tokenizer,
+    prompt_token_ids: list[int] | None,

+    """Return the prompt suffix used to prime a `DecodeStream`.
+
+    `DecodeStream` decodes all of its seed ids on the first `step()`, so
+    seeding it with the whole prompt costs O(prompt) time. Once it has emitted
+    text it keeps only the ids that follow, so the seed only shapes the first
+    delta, and a tail reproduces that delta exactly if:
+
+    - It holds `INITIAL_INCREMENTAL_DETOKENIZATION_OFFSET` tokens that decode
+      to text on their own. Metaspace, WordPiece and leading-`Strip` decoders
+      treat the start of the decoded text specially (e.g. drop a leading
+      space), so tokens that decode to nothing, such as skipped special
+      tokens or whitespace that such a decoder strips, must not count.
+    - Its text does not end in U+FFFD, i.e. it does not start inside the
+      multi-byte character or byte-fallback run that the prompt ends with;
+      such a window is extended to the start of the character. If the prompt
+      itself ends in U+FFFD, `DecodeStream` streams its whole seed text in
+      the first delta, so the full prompt is used to keep that output.
+    """

+    for _ in range(_MAX_UTF8_SEED_EXTENSION + 1):

+            start -= 1
+            if tokenizer.decode(

+        if needed > 0:

+        window = prompt_token_ids[start:]
