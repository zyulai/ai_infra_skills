## Overview

Problems with `sparse_nccl` on main:

- **Memory:** a worker keeps every patch on the GPU until the last one arrives, 6 bytes per changed element on every rank whatever the TP size. On the default config the extensible KV cache leaves about 3 GiB free, so a one-shot `send_weights` on Qwen3-30B-A3B at TP4 fails at 1.25% of elements changed, after some weights are already written.
- **Time:** each tensor costs two allocations and two broadcasts, 37,734 per update on this model, and the `empty_cache` at the end of the update then releases thousands of cached blocks. At 3% changed these take 2.2 s of a 4.3 s update.
- **Non-contiguous patch tensors** are broadcast as they are, so the wrong bytes are sent.

This PR sends the update in batches of at most 512 MiB. Both ends cut it at the same patches with one `batches()` over the update's metadata, and a patch above the limit forms its own batch.

- **Memory:** the worker applies each batch before receiving the next, so patch memory is bounded by the batch size instead of the update size.
- **Time:** a batch is one broadcast of all its indices plus one of its values per dtype. The worker receives each into one buffer and splits it into per-patch views, so an update takes a few allocations and broadcasts instead of two per tensor, and leaves few cached blocks for `empty_cache`.
- **Non-contiguous tensors:** the trainer concatenates each batch before sending it, so the wire always carries contiguous bytes.

Since a batch is applied before the rest arrive, a worker whose batch fails to validate or load keeps receiving and raises at the end, so the trainer's broadcasts complete and the group stays usable.

## Claims

- On Qwen3-30B-A3B at TP4 on the default config, main fails at 1.25% of elements changed and this passes up to 50%, the highest tested.
- In one engine, batching cuts the update time by 21% / 33% / 50% at 0.1% / 1% / 3% changed, to about 2.1 s at each.
- Broadcasts per update drop from 37,734 to 2-22.
- Weights and outputs match main.

## Details

**Wire format.** Values go in one run per dtype, in order of first appearance, so input order is kept even when a name repeats in another dtype. The packed helpers don't fit: `unpack_tensor` rejects int32 indices next to BF16 values with odd counts, and a pack can separate a patch's indices from its values.

**Behavior changes**

- Validation is per batch, so an invalid later batch fails after earlier batches landed. The worker stays marked incomplete, and the docs already say to restart or reseed after a partial failure.
- The wire format changes, so the trainer and workers must run the same version. `wire_batch_bytes` in the update info is required, so a mismatched worker rejects the update instead of receiving the wrong layout, though the trainer may already be blocked in a broadcast.
- The trainer concatenates each batch before sending it, so it holds one extra batch: at most 512 MiB, or one larger patch that travels alone.

**Limits.** Two models, TP4, H20 and Triton MoE. Index positions are synthetic. Cross-node transport was not measured.

**Not a duplicate.** No open PR batches the sparse NCCL wire. One open PR fixes non-contiguous patches with a narrower change; this one covers that case too.
