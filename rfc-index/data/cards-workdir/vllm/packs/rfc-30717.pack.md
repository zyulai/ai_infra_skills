## 正文(PRD / 提案全文)

### Motivation.

This RFC proposes implementing a token padding mechanism in the vLLM execution loop to ensure the number of tokens (batch size M) is a multiple of 4 when running FP8 models. This alignment significantly improves performance on NVIDIA B200/H200 GPUs.

FP8 GEMM kernels (both DeepGEMM and CUTLASS-based implementations) exhibit distinct performance characteristics based on input dimensions. Benchmarks on B200 hardware demonstrate substantial throughput degradation when the number of tokens (M) is not aligned to specific boundaries.

### The Problem

Currently, gpu_model_runner.py passes the raw number of tokens to the execution backend. While CUDA Graph capture handles padding for small batches (typically up to 512), it does not guarantee M%4==0 for all graph slots, and it does not handle batches larger than the graph capture limit.

Analysis of production-like traffic (ShareGPT, 3000 prompts, concurrency 100) reveals that for batches > 512 tokens (which bypass CUDA graphs), they constitute a significant part of the engine steps and the remainder modulo 4 is evenly distributed:

```
[Distribution of the unpadded number of tokens]
Counts: 0-63: 1183 | 64-127: 4309 | 128-255: 542 | 256-511: 545 | 512-1023: 554 | 1024-2047: 86 | 2048-4095: 1
Residual Counts (tokens % 4 for tokens > 512): 0: 166 | 1: 163 | 2: 154 | 3: 156
```

Roughly 74% of large batches currently run on unoptimized kernel paths.

### Proposed Change.

We propose introducing a padding logic within `_determine_batch_execution_and_padding` in `gpu_model_runner.py`.

Instead of a blanket if `quantization == "fp8"`, the padding logic should be:

- Selective: Trigger only when the backend kernel benefits from alignment, including DeepGEMM/FP8 and CUTLASS/FP8 on NVIDIA Blackwell/Hopper.

- Alignment: Pad num_tokens to the nearest multiple of 4.

- Safety: Ensure padded "dummy" tokens are masked out or handled such that they do not affect model accuracy or trigger Out-Of-Bounds (OOB) memory access.

### Alternatives Considered

#### Option A: Pad at the Kernel Level

Modify every GEMM kernel invocation to handle padding internally.

- Pros: Keeps Model Runner logic clean.

- Cons: Requires padding input tensors at every layer. For a deep LLM, this results in hundreds of unnecessary copy operations per forward pass, reducing performance gains.

- Verdict: Rejected due to high runtime overhead.

#### Option B: Rely on CUDA Graphs

Expand the CUDA Graph capture range or modify capture steps to enforce alignment.

- Pros: Uses existing infrastructure.

- Cons: CUDA graph capture sizes typically increase in steps of 8 or 16 and by default cap at 512 tokens. Throughput-heavy scenarios often exceed this (large batches). Benchmarks show significant regression for M > 512 when unaligned. Expanding the capture sizes to larger M significantly increases VRAM usage. In addition, steps of 8 or 16 introduce even more computational overhead than enforcing the mod-4 padding.

- Verdict: Rejected, as it requires significantly more VRAM and incurs greater computational overhead than mod-4 padding.
