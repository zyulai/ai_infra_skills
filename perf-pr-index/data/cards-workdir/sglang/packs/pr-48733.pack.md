## Motivation

`index_q_rope_pack_weights` (`index_q_kernel` in `fp4_indexer_rope.cuh`) applies RoPE and two-stage fp4 packing to the DeepSeek-V4.1 indexer query and also writes the head weights. It gives each (token, head) row of 128 bf16 to one warp, which per row means:
- 4-byte loads;
- four 16-lane max reductions and two shuffles;
- two 1-byte payload stores per lane;
- 4-warp CTAs.

That shape was chosen from decode measurements and suits decode. At prefill sizes it runs far from memory bandwidth. On VR200 a 32768-token chunk with 32 index heads (1M rows, ~340 MB of traffic, ~26 us at HBM speed) took 251 us per indexer layer.

## Modifications

- `index_q_block_kernel` gives each 32-element fp4 block to one thread: four threads per row, 256-thread CTAs of 64 rows. Warps 0-3 take the head blocks and warps 4-7 the RoPE blocks, so the RoPE branch is warp-uniform. Each thread does:
  - all of its loads before any math: the input block, plus its `freqs_cis` slice for the RoPE half, as `kMaxVecBytes` vectors (32 bytes on Blackwell);
  - the RoPE of its tail pairs;
  - both block absmaxes as trees seeded with 0;
  - the fake quant up to the e2m1 grid value, then the packer's exponent read from the grid amax's biased exponent (no division) and the e2m1 codes, with the two power-of-two scales folded into one multiply;
  - one 16-byte payload store and one byte of the row's little-endian scale word.

  The row's first thread writes the head weight. The current version of the kernel is @zcnrex's from review (about 10-23% faster than the first version, same bytes).
- **Bitwise:** every fp4 stage of `index_rope_quant_pack` works per element except the block absmax, and a max is exact in any order, so the bytes match the warp kernel's. Both kernels write the RoPE products with `__fmaf_rn` / `__fmul_rn` as `fma(x, fx, -(y * fy))` and `fma(x, fy, y * fx)`, so they match by construction. For `index_rope_quant_pack` (warp kernel and index-K) that is the contraction nvcc already chose, so its bits are unchanged. Left to nvcc, the block kernel contracted the imaginary part the other way and differed in rare last bits.
- **Dispatch:** `IndexQKernel::launch` takes the block kernel for calls of at least 8192 (token, head) rows on SM100-family GPUs (CC 10.x). The gate counts rows, so decode reaches it too: with 4-token speculative verify and 32 index heads, 64 requests per rank make 8,192 rows, and decode graphs at bs >= 64 capture the block kernel (it is also faster at that size). Smaller batches, other GPUs and ROCm keep `index_q_kernel` unchanged. The PDL wait placement is the same as in the warp kernel.
- **Alignment:** on the block-kernel path, `launch` checks 32-byte alignment of `input` and `freqs_cis` and 16-byte alignment of `payload`, so a misaligned view raises a clear error instead of a misaligned-address fault.

## Accuracy Tests

The change is bitwise, so no model-level accuracy run is needed. The new test `test_index_q_rope_pack_prefill_matches_decode_kernel` covers this. It runs 4100 tokens x 32 heads as one call (131,200 rows, block kernel) and as 128-token calls (4,096 rows each, warp kernel), and requires payload, scale words and head weights to be equal. The inputs cover seven families: normal, per-row scales of exp(6 N(0,1)), sparse with signed zeros, below both fp4 amax floors, values on e2m1 rounding ties, per-row scales of 2^U(-150, 126), and 0.3% each of inf / -inf / nan. It runs with int32 and int64 positions, and skips unless the GPU is CC 10.x (elsewhere both calls take the warp kernel). It passed 14/14 on VR200 with this branch.

The updated kernel was also compared directly with the first block kernel of this PR on VR200: payload, scale words and head weights of both Q kernels, plus the index-K slot bytes, on the seven families x 9 shapes (128 / 255 / 256 / 257 / 4100 / 32768 tokens x 32 heads, 2731 x 3, 8193 x 1) x int32 / int64 positions, are identical in all 126 cases.

## Limitations
