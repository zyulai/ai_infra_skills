## 正文(PR 描述)

## Motivation

Fixes #50137.

With data-parallel attention and the default control route (`--enable-dp-attention-local-control-broadcast`
off), an abort of a running request is sometimes lost: `POST /abort_request` returns 200 and the tokenizer
forwards the abort, but the request runs to `max_new_tokens` and finishes with `length`.

Measured at `d800cb859e85` on two GB200 GPUs, Qwen/Qwen3-0.6B,
`--tp-size 2 --attn-dp-size 2 --enable-metrics --mem-fraction-static 0.5 --context-length 4096`; the client pins a
streaming victim (`max_new_tokens=512`, `ignore_eos`) to DP rank 1 with `routed_dp_rank`, keeps a backlog of 128
short requests on DP rank 0, and aborts 0 to 20 ms after submitting:

- 19 of 200 aborts lost (Wilson 95%: 6.2% to 14.4%); by abort delay 0 ms 10/34, 1 ms 5/34, 2 ms 2/33,
  5 ms 0/33, 10 ms 0/33, 20 ms 2/33; every lost abort produced 512 of 512 tokens after `/abort_request`
  returned. With the backlog on the victim's own rank instead: 0 of 60.
- With `SGLANG_SCHEDULER_MAX_RECV_PER_POLL=1` and a 256-request backlog on the victim's rank: 16 of 16 lost.
- Controls: `--enable-dp-attention-local-control-broadcast` 0 of 100 and 0 of 16; victim on DP rank 0, 0 of 12.

Cause. The `DataParallelController` sends `TokenizedGenerateReqInput` to the chosen DP rank's socket, but
`AbortReq` has no entry in its dispatch table and falls back to `send_control_message`, which with DP attention and
the default control route sends to `self._active_workers[::tp_size]`, i.e. DP rank 0 only. The leader of DP rank
0 broadcasts its control list over the whole `tp_group`, and `_broadcast_reqs_across_ranks` replaces every other
leader's control list with that broadcast. So the owner of the request receives the request on its own socket and
the abort through rank 0's broadcast, with no order between the two. When the owner drains its socket just
before the request arrives, it applies the abort first; `Scheduler.abort_request` finds no request with that rid
and keeps no record, and the request is queued in the next iteration and runs to completion. The tokenizer does
not resend an abort (`abort_sent`; see the docstring of `_skip_dispatch_if_aborted`). The interleaving was
derived from a model of the two-socket control route and reproduced on the engine.

## Modifications

- `DataParallelController.init_dispatcher`: route `AbortReq` to `send_to_all_workers`, as `BlockReqInput` and
  `ProfileReq` already are. Every DP rank now gets the abort on its own socket, where ZeroMQ keeps it behind the
  request the tokenizer sent first. With DP attention off, and with local control broadcast on,
  `control_message_step` is already 1, so the abort goes to the same workers as before.
- `SchedulerRequestReceiver._split_work_and_control_reqs` (used only with DP attention): `AbortReq` is kept with
  the work requests, in socket order, and is broadcast inside its DP group. Without this, the copy that arrives
  behind the request on the owner's socket would be replaced by rank 0's control broadcast.

Both changes are needed: with only the first, the owner's own copy is still replaced by rank 0's broadcast; with
only the second, the abort never leaves DP group 0.

What does not change: every DP group already applied every `AbortReq` once (through rank 0's broadcast) and still
does, now from its own socket, so `abort_all` and ranks that do not hold the rid behave as before; the scheduler
stays stateless about rids it has not received, as in #35255 and #47546. This is the route that
`--enable-dp-attention-local-control-broadcast` already gives aborts, applied without changing the route of the
other control messages, and the same principle #47532 applied to the Rust server. It also makes the ordering
assumption of #47693 ("FIFO ordering" behind the request) hold for an abort on this route.

Visible ordering change, DP attention only: within one receive, an `AbortReq` is now applied before the control
messages of that receive (work requests already are), so an abort pulled together with, and after, a
`PauseGenerationReqInput` is applied immediately instead of being held behind the pause.

Test: `TestDPAttentionAbortRoute.test_abort_is_applied_after_its_request_on_the_owner_rank` in
`test/registered/unit/managers/test_data_parallel_controller.py` (CPU). It drives the real dispatch table of
`DataParallelController` and the real `_broadcast_reqs_across_ranks` of two DP-attention leaders through the
losing interleaving (the owner drains its socket before the controller forwards, rank 0 after) and checks that
the owner applies the request before the abort and that every DP group applies the abort exactly once, for the
default control route and for local control broadcast.

The five trials in the last row all had a slow `/abort_request` call (10 to 1711 ms between sending it and its
return; median over the arm 1 ms). That time is spent in the tokenizer process before the abort reaches the
controller, and the client counts every token it receives after the call returns, including tokens generated
while the call was pending: the victim's stream reached the client 95 to 1885 ms after submission in these trials.
In the 84 trials of that arm whose call returned within 8 ms, at most 2 tokens arrived afterwards. With local
control broadcast on, this change does not alter the controller's sends (`control_message_step` is already 1) and
does not alter what the owning rank applies: the abort reaches it on its own socket behind the request, as
before, and its group broadcast is the same function for work and control lists.

To separate the change from the environment, this arm was repeated three times on one node and the same two GPUs,
100 trials each: (a) the unpatched tree, (b) the patched tree, (c) a copy of the patched tree with the two changed
files restored. No abort was lost in any of them (100 of 100 finished `abort` each time).

| Tree | Trials over the 4-token slack | `/abort_request` calls of 8 ms or more | Max tokens after return when the call took under 8 ms |
| --- | --- | --- | --- |
| (a) unpatched | 0 | 1 (46 ms) | 2 |
| (b) patched | 2 (45 and 5 tokens) | 5 (1745, 12, 10, 12 and 12 ms) | 2 |
| (c) patched tree with the change reverted | 1 (5 tokens) | 2 (45 and 11 ms) | 2 |

Every trial over the slack had a slow call, and one occurred without the change (c). So a late count in this arm
goes with slow `/abort_request` calls and is not caused by this PR. The counts are too small to say whether slow
calls are equally frequent in (b) and (c).

## Speed Tests and Profiling

No hot-path code changes. The controller sends one small `AbortReq` per DP rank instead of one in total, only
when an abort is issued; no collective is added or removed.
