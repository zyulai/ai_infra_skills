## Overview

Grouped top-k routers (DeepSeek-V3/V3.2, GLM-4.5+/5, Kimi-K2/K3, MiMo-V2, ...) now give DP and CUDA-graph padding rows expert id -1 by default, as fused top-k routers already do, so modular MoE kernels skip them. Until now they did so only for models that opt in under DeepEP v2 (from #56079). Follows #65972, which did the same for the TRT-LLM block-FP8 / MXFP8 monolithic kernels.

## Claims

- **Higher DP + EP serving throughput, both runs better at nearly every concurrency, on three grouped top-k models and two MoE backends:**
  - GLM-5.3-NVFP4, DP8: +5% to +21% (concurrency 8 to 256);
  - MiMo-V2.6-Flash (MXFP4 experts), DP4: +5% to +7% at 16 / 64 / 256, +2.6% (within noise) at 4;
  - DeepSeek-V3.2-NVFP4, DP4: +3% to +8% at 4 / 16 / 64, +1.5% (within noise) at 256.
- **Accuracy unchanged:** GSM8K at concurrency 4 (every decode step mostly padding) and 256 on all three models, inside launch-to-launch variation.
- **One slower bucket:** DeepSeek-V3.2 at concurrency 256, decode steps with 33-128 rows per rank are 5.6% slower in both runs (13% of step time); throughput there is within noise.
- **No new option.** `VLLM_MOE_SKIP_PADDING=0` turns masking off for all routers, as before.

## Details

**Why padding was not masked.** `GroupedTopKRouter` passes the runner's `is_padding` to its kernel only when `skip_padding` is set, and `FusedMoEFactory` sets it only for models that pass `skip_padding=True` (Kimi-K3) *and* use DeepEP v2 (`layer.py`). Every other grouped top-k model routes padded rows like real tokens, and modular kernels compute them.

**Changes.**
- `GroupedTopKRouter.masks_padding` is `skip_padding or not rocm_aiter_ops.is_fused_moe_enabled()`, matching `FusedTopKRouter` / `FusedTopKBiasRouter`. The mask itself is the one the router already applied under the opt-in: the CUDA kernel's `is_padding`, or `masked_fill` on the other paths. On ROCm AITER the opt-in still applies, since I did not check that AITER experts accept -1.
- `get_moe_padding_mask` returns `None` when the router sees more rows than the local mask covers. This happens when the runner all-gathers rows from every DP rank before routing (`MoERunner._maybe_dispatch`, for quant methods without an internal modular kernel). The local mask does not describe those rows, and the `topk_softmax` and `grouped_topk` CUDA kernels both check `is_padding.size(0) == num_tokens`, so passing it would raise. Those rows are routed without a mask, as before. This also applies to fused top-k routers.
- Docstrings of `skip_padding` and the `VLLM_MOE_SKIP_PADDING` comment updated.

**Affected models.** Every model whose MoE layers are built with `use_grouped_topk=True` and a non-degenerate grouping (`create_fused_moe_router` sends one-group, top-1-group routing that the fused top-k routers can express to them, and they already mask; e.g. LFM2-MoE without expert bias), when it runs a modular MoE kernel on CUDA, XPU or ROCm without AITER fused MoE and the step has padded rows (DP > 1, or CUDA-graph padding):
- DeepSeek-V2/V3/R1 and V3.2 (`DeepseekV2MoE`), and models built on them: Kimi-K2/K2.5, Kimi-VL, Mistral Large 3, A.X-K1, Unlimited-OCR, GLM-4.7-Flash (`glm4_moe_lite`), GLM-5 (`GlmMoeDsaForCausalLM`), plus their MTP/EAGLE drafters;
- GLM-4.5/4.6/4.7 (`glm4_moe`, MTP) and GLM-5.3 (`glm5next`);
- MiMo-V2 Flash/Omni (`mimo_v2`, MTP);
- Hunyuan (`hy_v3` with MTP, `hy_v4`), EXAONE-MoE (MTP), AFMoE, LFM2-MoE, OpenPangu (MTP), Nemotron-H MoE and the models built on it (Nano-Nemotron-VL, Cosmos3-Edge, Nemotron-3.5-Transcribe);
- when the checkpoint config sets `n_group`/`topk_group`: Bailing/Ling (`bailing_moe`, `bailing_moe_linear`), Sarvam, Param2MoE, Beam, and the Transformers-backend MoE;
- Kimi-K3: already masked under DeepEP v2 through its opt-in; now also on other all2all backends.

Not affected: DeepSeek-V4/V4.1 (own routing), LongCat-Flash (zero-expert router), models with plain softmax/sigmoid top-k (already masked by the fused top-k routers), CPU (`create_fused_moe_router` returns `CPURouter` there), ROCm AITER, and monolithic kernels that route from logits.

**Correctness on these models.** Masking changes only padded rows, whose outputs are discarded; the unit tests check that real rows get the same experts and weights. End to end I checked GLM-5.3-NVFP4, MiMo-V2.6-Flash and DeepSeek-V3.2-NVFP4 (GSM8K above); the other listed models rely on the argument below, not on their own runs.

**Why -1 is safe on the newly masked paths.** The expert backend is chosen by the quantization method, not the router, and fused top-k routers (e.g. Qwen3-MoE, MiniMax) already pass -1 for padded rows to the same modular experts and all2all backends by default; the EPLB mapping kernel maps -1 to -1 (`eplb_triton.py`); every grouped top-k implementation already supports `is_padding`.

**Unchanged.** Monolithic kernels that route from logits (they do not call the router; the #65972 path under DP already masked in the runner, and now the router does it instead), ROCm AITER, `VLLM_MOE_SKIP_PADDING=0`.

**Limitations.**
- With sequence-parallel MoE (EP + TP > 1 + DP > 1, e.g. `deepseek_v2.py`), each TP rank routes its own chunk, but `is_padding` stays the full-batch mask, so `[:num_tokens]` gives every TP rank the first chunk's mask. Padding is always at the end of the batch, so this can only leave padded rows unmasked on TP ranks > 0, never mask a real token; fused top-k routers have the same limitation on main. Re-sharding the mask there is left for a follow-up.
- Kimi-K3 was not measured: its verified GB200 layouts are TP8 x PP2 (no DP padding) or DEP with DeepGEMM MegaMoE, which reads `is_padding` itself.
- Only ShareGPT; DeepEP LL/HT not measured.

**Not a duplicate.** I searched open PRs for grouped top-k / padding / `skip_padding` / `is_padding`. #50759 (draft, last updated 2026-09-02) applies a generic `torch.where` mask after every router in `BaseRouter`; its fused top-k and dsv4 parts have since landed on main through other PRs. It does not exclude ROCm AITER or guard rows gathered before routing. This PR only turns on the mask grouped top-k already implements and adds that guard.
