## Disclosure

AI assistance was used. The changes were reviewed and tested manually.

## Overview

This PR removes the requirement to have an original quant method backend available when online re-quantization is used (#55684, #64378). This standardization is required for #61620.

Online re-quantization loads a checkpoint-quantized layer through its checkpoint quantization method, dequantizes it, and re-quantizes it with an online method. There is no need to have an original backend - this skip was left TODO in previous PRs (except #64378 that added it specifically for NVFP4 MOE).

#64378 worked around this for NVFP4 MoE only, by returning the `EMULATION` backend from the NVFP4 oracle: https://github.com/vllm-project/vllm/blob/4e3463c87493ebd2c5d5fbe4be6469911e23e2bf/vllm/model_executor/layers/fused_moe/oracle/nvfp4.py#L226-L232 but it was just temporary.

This PR makes this logic uniform across linear/MOE oracles.

## Claims

- All MoE selectors built on `MoEKernelOracle` (fp8, mxfp8, mxfp4 incl. DeepSeek-V4, nvfp4, int8, wna16, w4a8_int8, unquantized) return `(XxBackend.NONE, RequantizationSourceExperts)` for a requantization source, without probing a compute backend.
- All `init_*_linear_kernel` selectors (fp8, int8, mxfp8, mxfp4, mxfp6, nvfp4, wfp8_a16) return a typed `Fake*LinearKernel` for a requantization source, without dispatch. These placeholders raise on weight processing or compute; selector return types stay unchanged.
- The scope now covers linear layers as well as MoE, and the source's `create_weights`, so kernels selected in a scheme's `__init__` or `create_weights` are skipped too.
**- The NVFP4-only `EMULATION` special case is removed. Layers that are not requantization sources select backends exactly as before.**
- A requantization source no longer fails on checks that assumed a real backend: ModelOpt per-token NVFP4 activation, and compressed-tensors MXFP4 MoE with `--moe-backend b12x|deep_gemm|flashinfer EP`.

Left to other PRs:
- [ ] `oracle/w4a8.py` still dispatches for sources: it does not use `MoEKernelOracle` yet.
- [ ] `choose_mp_linear_kernel` (GPTQ/AWQ/WNA16/W4A8 linear) still dispatches for sources: it returns a kernel class that 9 callers instantiate, and none of those schemes implements `dequantize_weight` yet, so they cannot be sources.
- [ ] The explicit skip call in each `select_*` / `init_*` is marked `TODO: migrate to oracle base method` and should move into the oracle base `select_backend` once the selectors are migrated.
- [ ] `--moe-backend` / `--linear-backend` apply to both the checkpoint and the re-quantized layers; there is no per-layer API, so they can still be rejected by the original method when it does not use the oracle (e.g. the non-oracle branches of CT MXFP4).
- [ ] No end-to-end test on a real checkpoint whose original backend is unavailable.

## Details

- Reviewers should scrutinise the widened scope in `resolve_quant_method` (https://github.com/vllm-project/vllm/blob/4e3463c87493ebd2c5d5fbe4be6469911e23e2bf/vllm/model_executor/layers/quantization/base_config.py#L348-L359): it is entered whenever an online target resolves. This is safe because every path after it returns the online method or raises, so the checkpoint method is never used for compute; but it means the unquantized MoE method of an unquantized checkpoint with an online target now also skips its dispatch.
- Behaviour changes vs `main`: requantization sources get placeholder kernels/experts instead of a compute backend (NVFP4 MoE: `EMULATION` before). Linear placeholders report no pre-quantized input key, preserving the existing fusion interface.
- `NONE` keeps its pre-existing meanings in `Fp8MoeBackend` (no backend on out-of-tree platforms) and `Mxfp4MoeBackend` (Quark OCP-MX fallback to `EMULATION`, kernel-less online MXFP4); this is documented on both enums.
- Rejected: returning `None` from selectors, which propagates optional types into unrelated callers; a decorator for the skip, since explicit calls match the planned oracle migration; and changing `FusedMoEMethodBase` / `LinearMethodBase`.
