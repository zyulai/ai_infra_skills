## 正文(PR 描述)

## Purpose

With `--data-parallel-size N`, the DP world group's rendezvous port comes from `_data_parallel_master_port_list` — probed once at config time and consumed by `get_next_dp_init_port()` when the engines finally call `init_process_group`, **minutes later** (after worker spawn, CUDA init, and model load). Nothing holds the port in between, so any other process — most commonly a sibling vLLM instance cold-starting on the same host, the standard shape in RL rollout fleets — can take it. Startup then fails at its very last step with the engines hanging on:

```
(Worker pid=...) torch.distributed.DistNetworkError: The server socket has failed to
listen on any local network address. port: <n>, ... EADDRINUSE
```

#36330 fixed exactly this defect for the elastic-EP stateless groups: rank 0 binds an ephemeral port, keeps the listening socket, and publishes the port through a coordination TCPStore. This PR extends that mechanism to the last remaining pre-allocated consumer, the world group:

- `launch_core_engines()` creates the coordination store for online DP (dp>1, engine rank 0 local; the initial MoE-only gate was removed in a follow-up commit, see below) when none exists yet, and hands its port to engines through the existing startup handshake (`_coord_store_port`).
- `init_distributed_environment()`: for the DP path, group rank 0 creates the world-group TCPStore on port 0 — the kernel assigns the port and the store owns it from birth — then publishes the resulting port via the coordination store; other ranks read it and connect. All ranks pass the store to `init_process_group` (`store=` argument), so the port is never released between choice and use. Without a coord store the previous behavior is unchanged.

## Design notes for reviewers

Answers to the questions this diff naturally raises.

**Why publish through a TCPStore rather than the handshake or spawn args.** The port does not exist until group rank 0 binds — after every engine has spawned and after the handshake replies have gone out (the frontend replies to each HELLO as it arrives; rank 0 has not bound yet at that point). Delivery therefore needs a channel that (a) works after all startup messages, (b) blocks until the value appears (ranks reach group init in arbitrary order), and (c) is reachable from both consumer levels: EngineCore processes (DP gloo group, store-based since #36330) and workers (world group), which have no handshake connection to the frontend at all. A key-value store with blocking `get` is the smallest thing satisfying all three, and #36330 already built it — this PR only extends where it is created (MP path, before the Ray branch) and adds one consumer.

**Why rank 0 creates the store on port 0 and reads the port back.** Ownership must never gap: the world-group TCPStore itself binds port 0, owns the kernel-assigned port from birth, and `.port` reads it back for publication — the same readback pattern the coordination store (and zmq's `LAST_ENDPOINT`) already uses. The already-bound store is then passed to `init_process_group` via `store=`; torch requires `store` and `init_method` to be mutually exclusive, hence `init_method=None if world_pg_store else distributed_init_method` at both call sites. Rank 0 passes `wait_for_workers=False` because workers can only connect after the port is published, so the master cannot block for them inside its own constructor; PG init synchronizes through store keys as usual. An earlier revision of this PR bound a raw socket manually and handed it to `TCPStore(master_listen_fd=...)`; review simplified it to `TCPStore(port=0)` — same invariant, one layer less, and it drops the fd-adoption/libuv compat surface (cf. the `use_libuv=False` pin in `StatelessProcessGroup.create` for pytorch#150215).

**An externally-built store is equivalent to the torch-built one.** The constructor arguments mirror torch's own `_create_c10d_store` (`world_size`, `is_master=(rank == 0)`, group timeout, `multi_tenant=True`); both paths converge in `_new_process_group_helper`, which cannot tell who built the store. `store=` is the public contract torchelastic uses in production. Two known differences, both benign: (1) `wait_for_workers=False` on rank 0 (see above) moves a missing-worker failure from store-construction timeout to PG-init rendezvous timeout — the behavior torchelastic deployments already run with; (2) torch wraps rendezvous-built stores in `PrefixStore("default_pg")` but takes a passed store raw — harmless because the store is freshly created and dedicated to this group, and all members take the same branch.

**Store-creation guards.** Each condition excludes a deployment where creating the store would be useless or wrong: `dp_size > 1` (no consumer otherwise), `not offline_mode` (scope: offline keeps existing behavior), `dp_rank == 0 and local_engine_count > 0` (the store must bind on the DP master node; an API-server-only frontend would `bind()` an IP that is not its own), `not enable_elastic_ep` (the Ray actor manager creates its own store later, unchanged from #36330). An earlier idempotency check on `_coord_store_port` was dropped: no in-tree writer can set the field before this block runs.

**Fallback path is byte-for-byte the old behavior.** With `_coord_store_port` unset (offline, external launcher / SPMD, elastic, or an older frontend during version skew), `world_pg_store` stays `None` and both changed call sites degrade to their previous form.

**How the store address travels.** One field added to the existing handshake copy-list covers remote (headless) MP engines; local engines receive it in the config at spawn, Ray actors in the actor-constructor config, and workers inherit it when the executor spawns them. Non-MoE MP engines are rewritten to independent dp=1 (`reconfigure_for_independent_dp_rank`) and never consume the store; the non-MoE case that needs it is the Ray DP backend (no such rewrite), which is covered via the actor-constructor config.

**Lifetimes.** The coordination store lives on the `launch_core_engines()` frame, which runs `wait_for_engine_startup()` after its yield — so it stays alive exactly until all engines are ready, then is discarded. The world group's own rendezvous TCPStore is a separate, process-lifetime object. The two are deliberately not merged: reusing the coordination store as the group's rendezvous store would make the frontend process a runtime dependency of every engine collective.

## Reproduction & A/B results

Hardware: single GB200 node (aarch64, 4 GPUs), image `vllm/vllm-openai:nightly` (2026-08-04). Arm "fixed" = same image with this patch applied. Model: a 9-layer MoE test checkpoint with dummy weights (`--load-format dummy`); any small MoE reproduces, e.g. `deepseek-ai/DeepSeek-V2-Lite`.

Two experiments, all rounds on identical images/configs:

1. **Deterministic squatter**: start `vllm serve <moe> -dp 4 -tp 1` with `VLLM_PORT` set (making the config-time probe deterministic); a squatter process waits until the EngineCore processes exist (probe done, world-group bind not yet) and then binds-and-holds `[VLLM_PORT, VLLM_PORT+16)`:

   ```python

   import socket, time
   socks = []
   for p in range(42000, 42016):
       s = socket.socket(); s.bind(("0.0.0.0", p)); s.listen(); socks.append(s)
   time.sleep(600)
   ```

2. **Concurrent cold start (RL shape, no artificial interference)**: two `-dp 2 -tp 1` instances on one node, same `VLLM_PORT`, started simultaneously.

| experiment | main | with this fix |
|---|---|---|
| squatter | **6/6 startup failure** (EADDRINUSE at world-group init, process hangs) | **8/8 healthy** (full band squatted) |

The failure mode on main matches field reports: the server does not exit — it hangs after minutes of model loading, which is the expensive way to fail.

## MI355 CI failure (build 93141) and fix (2026-10-07)

`:amd: (MI355) Distributed DP Extended` hung for 30 minutes in `test_async_llm_dp.py` with DP=2/TP=2 on both attempts, while the L4 run of the same step passed. In each attempt one worker of the DP-rank-1 engine never reached the world-group init: it was stuck on the coordination store (`wait timeout ... keys: /world_pg_port` in the retry), and its three peers then waited 30 minutes on its gloo key.

Root cause: `get_cached_tcp_store_client` caches one connected client per process. `DPEngineCoreProc` populates it in `_init_data_parallel` before it creates the executor, so with the default fork start method every worker inherited the same connected socket, and the two TP siblings of one engine interleaved their requests on it. The L4 run of the same step shows no spawn override either, so it forks as well; whether the interleaving corrupts the stream depends on whether the siblings' requests overlap, and that run did not hit it. The hazard is therefore not ROCm specific. This PR is the first to read the coordination store from workers at init, so the latent cache issue surfaced here.

Fix: the port exchange needs the store once per worker, so it now opens its own short-lived client instead of the process-wide cached one. The cached client itself is still not fork-safe for its other callers (elastic EP); that is pre-existing and left for a follow-up.
