## Motivation

The LTX-2 spatial **`LatentUpsampler`** (`runtime/models/upsampler/latent_upsampler.py`) is auto-loaded as the `spatial_upsampler` component of every LTX-2 two-stage pipeline — Lightricks generates latents at lower spatial resolution and uses this module to upscale them by 2× before VAE decode, so it sits on the critical path of every LTX-2 generation. Its `LatentUpsampler` and `ResBlock` modules use `torch.nn.GroupNorm(32, ...) + torch.nn.SiLU()` at multiple sites, but the existing inline `silu(norm(x))` pattern bypasses the Triton-fused `apply_group_norm_silu` helper that HunyuanVAE already routes through.

This PR plumbs the helper into the three eligible direct-`silu(norm(x))` sites in `latent_upsampler.py`, picking up a **6.5×–14× kernel speedup on H100** (vs eager `silu(group_norm(x))`) without changing model outputs. The speedup factors into a ~1.55× SiLU+GroupNorm fusion win (constant across shapes) and a 4×–9× parallelization win that scales with per-group size; see [Speed Tests and Profiling](#speed-tests-and-profiling) for the decomposition.

This also addresses the "kernel fusion instead of compiler-driven fusion" line under Performance Improvements in [Roadmap] SGLang-Diffusion (26 Q2) (#23035).

## Modifications

- **`python/sglang/multimodal_gen/runtime/models/upsampler/latent_upsampler.py`** — route three `silu(norm(x))` sites through `apply_group_norm_silu`:

  | Site | Class | Hit per `LatentUpsampler.forward` |
  |---|---|---|
  | `initial_norm` + `initial_activation` | `LatentUpsampler.forward` (both 2D and 3D paths) | 1 |
  | `norm1` + `activation` | `ResBlock.forward` (one per ResBlock) | `2 * num_blocks_per_stage` |

  At the default `num_blocks_per_stage=4` this is **9 fused sites per upsampler call** (1 initial + 4 pre-upsample ResBlocks + 4 post-upsample ResBlocks).

  The second norm site inside `ResBlock` (`silu(norm2(x) + residual)` at line 118) is deliberately left on the eager path with an inline comment — the current `apply_group_norm_silu` helper only covers `silu(norm(x))`, not the `silu(norm(x) + residual)` pattern. A follow-up `apply_group_norm_add_silu` kernel would catch those remaining 8 sites per generation (doubling fusion coverage on this module); it's out of scope here.

- **`python/sglang/jit_kernel/benchmark/diffusion/bench_group_norm_silu.py`** — add three LTX-2 latent upsampler shape cases (`ltx2_upsampler_small`, `ltx2_upsampler_pre_720p`, `ltx2_upsampler_post_720p`) at `num_groups=32`, bracketing the production shape range that Lightricks ships in the LTX-2.3 spatial upscaler checkpoints. The `post_720p` case is ~471M bf16 elements (~940 MB), making the kernel asymptotically HBM-bandwidth-bound. This bench is registered with `disabled="standalone benchmark"`, so it never appears in the regular CI memory budget.

- **`python/sglang/multimodal_gen/test/unit/test_latent_upsampler_group_norm_silu.py`** (new file) — 19 unit tests (10 CPU-fp32 wiring + 9 CUDA bf16/fp16 production-path parity, the CUDA tests gated on `torch.cuda.is_available()`).

Geomean kernel speedup on LTX-2 upsampler shapes: **~10.7×**.

**Where the speedup comes from.** A 13.9× speedup deserves scrutiny, so I forced the kernel onto its non-chunked one-pass path (same parallelism as PyTorch's `native_group_norm` CUDA kernel — one block per `(batch, group)` pair) and re-measured. The headline decomposes cleanly into two roughly multiplicative factors:

| case | fusion-only<br/>`native / one-pass` | parallelization<br/>`one-pass / chunked` | total<br/>`native / chunked` |
|---|---:|---:|---:|
| `ltx2_upsampler_small`     | 1.56× | 3.94× | 6.13× |
| `ltx2_upsampler_pre_720p`  | 1.56× | 8.57× | 13.34× |
| `ltx2_upsampler_post_720p` | 1.55× | 8.96× | 13.91× |

1. **Fusion contributes a flat ~1.55×**, constant across shapes — exactly what's expected for collapsing `F.silu(...)` into the apply pass: one full-tensor read + write saved per call, theoretical ceiling 2×.

2. **Chunked Welford parallelization contributes 4× → 9×**, scaling with per-group size. PyTorch's `native_group_norm` CUDA kernel (and Triton's own one-pass fallback) both launch one block per `(batch, group)` pair → **32 blocks on a 132-SM H100, ~24% SM occupancy**, with per-block work serialized across the entire `group_size` (461 K → 14.7 M elements as shape grows). The production `_launch_chunked` path splits each group into 8 192-element chunks reduced in parallel → **~57 600 programs for `post_720p`**, achieving **~2.87 TB/s = 86% of H100 HBM peak**. PyTorch's path tops out at ~12% of HBM peak on the same workload — not a memory-traffic problem, a parallelism problem.

To reproduce the decomposition, override the threshold at runtime:

```python
from sglang.jit_kernel.diffusion.triton import group_norm_silu as gns
gns._LARGE_GROUP_THRESHOLD = 10**10   # force one-pass path
```

**Where this generalizes.** Smaller DiT-side `group_norm` call sites will see only the fusion-only **~1.5×** factor; the 6×+ headline numbers are specific to **large VAE/upsampler-style shapes** where per-group size is large enough that PyTorch's per-group kernel is severely under-parallelized on Hopper. The existing HunyuanVAE wiring that this PR follows has similar (large per-group) shapes, which is why the same kernel pays off there too.

**E2E translation.** Each `LatentUpsampler.forward` call fires the helper 9 times — 5 sites at the pre-upsample resolution (1 initial + 4 pre-upsample ResBlocks) and 4 sites at the post-upsample resolution (4 post-upsample ResBlocks). For a 720p clip, naive multi-site savings:

| Sites | Per-call saved (bf16) | × count | Subtotal |
|---|---:|---:|---:|
| Pre-upsample (initial + 4 pre ResBlocks) | ~3.2 ms | × 5 | ~16 ms |
| Post-upsample (4 post ResBlocks) | ~12.7 ms | × 4 | ~51 ms |

**Total saved per generation: ~67 ms** of `LatentUpsampler.forward` wall time on H100. The latent upsampler is one bounded subsystem of a multi-second LTX-2 generation, so relative E2E gain is small in absolute terms — but it represents 20–45% of the upsampler's own runtime budget, and every LTX-2 generation pays it.
