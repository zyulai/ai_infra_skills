## Overview

Fix a startup illegal memory access in FlashMLA sparse prefill with the extensible KV cache (#56492), reproduced with DeepSeek-V3.2 on B300.

FlashInfer autotuning runs FlashMLA before warmup expands the cache. When a sparse gather includes an invalid (padding) index, FlashMLA reads past the selected rows. With only the null block committed, those reads can reach unmapped memory inside the layer's reserved KV view.

This PR extends the segment alignment introduced in #65225 to caches without an RDMA connector, and commits a second block at allocation for block-outermost layouts (follow-up commit by Nick Hill).

## Claims

- Prevents the reproduced startup crash by keeping memory mapped beyond each layer's initial KV rows.
- Covers block-compact, layer-outermost layouts and block-outermost layouts.
- Preserves logical KV capacity and block strides.

## Validation

<details>
<summary>Kernel reproduction</summary>


On one GPU, place a bf16 KV view near a granule boundary and commit only block 0 (73,728 bytes). The minimum mapped size depends on the indices:

| Inputs | Faults when mapped bytes from the view's start are below |
|---|---|
| Valid indices inside block 0, padded with `-1`, as in the failing startup | Up to about 130 KiB, depending on the query row |
| All indices `-1`, `topk_length=0` | Approximately 100 KiB |
| All indices valid | No over-read detected |

Views fully contained in committed memory do not fault in these tests. The rows above combine our B300 measurements with Nick Hill's on GB300. The following reproduces the all-invalid-indices case:

```python
import torch
from vllm.third_party.flashmla.flash_mla_interface import flash_mla_sparse_fwd
from vllm.utils.extensible_tensor import ExtensibleTensor

BLOCK, D, HQ, TOPK, SQ, G = 64, 576, 64, 2048, 128, 2 << 20
room = 81408  # Mapped bytes from the KV view's start to the granule boundary.
dev = torch.device("cuda")
q = torch.randn(SQ, HQ, D, dtype=torch.bfloat16, device=dev)
indices = torch.full((SQ, 1, TOPK), -1, dtype=torch.int32, device=dev)
topk_length = torch.zeros(SQ, dtype=torch.int32, device=dev)

offset, view_bytes = 4 * G - room, 1024 * BLOCK * D * 2
buf = ExtensibleTensor(
    offset + view_bytes,
    device=dev,
    segment_capacities=[offset, view_bytes],
)
buf.resize_segments_([0, BLOCK * D * 2], zero_new=True)
kv = buf.full_view()[offset:].view(torch.bfloat16).view(-1, 1, D)
flash_mla_sparse_fwd(q, kv, indices, D**-0.5, topk_length=topk_length)
torch.cuda.synchronize()  # Illegal memory access: only 81,408 bytes are mapped.
```

## Details

The allocator previously committed only block 0 while exposing each layer's full reserved KV view. FlashMLA's SM100 sparse prefill kernel reads past the rows selected by the sparse indices when a TMA gather includes an invalid index: about 100 KiB from the view start when every index is invalid, and up to about 130 KiB when only some are. In the failing startup, `model.layers.17` had a 72 KiB null block and only 80,128 mapped bytes from its view start, less than the roughly 128 KiB the kernel read there.

The fix handles the two layouts differently:

- **Block-compact, layer-outermost:** align each layer's segment to a memory granule, so committing the null block maps the full first granule. This reuses the existing RDMA padding path. Padding increases reserved address space without adding physical memory, since each segment's commits already map whole granules.
- **Block-outermost:** layers share one segment, and their views start at different offsets within block 0. Committing two blocks keeps at least half a granule (1 MiB on the tested device) mapped beyond each layer's view start, well above the roughly 130 KiB FlashMLA reads. This can increase the initial physical mapping; logical KV capacity is unchanged.

Layouts that are neither, such as `LHBNC`, keep the current allocation; forcing `LHBNC` with sparse MLA can still fault.

This keeps the allocation policy independent of a hard-coded FlashMLA access size.

AI assistance (Claude Code) was used to investigate the crash, write the change and tests, and draft this description. The submitter reviewed every changed line and ran the tests and evaluations listed above.
