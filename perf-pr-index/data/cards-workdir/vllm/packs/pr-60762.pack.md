## PR body
```markdown
### Summary
On SM120, the DSV41 sparse-MLA backends declare only `[128]`-token kernel blocks (`get_supported_kernel_block_sizes` returns `[64 if family(90) else 128]` / `[128]`), so serving with `--block-size 64` dies in block-size negotiation:

```
ValueError: No common block size for 64 (FLASHINFER_MLA_SPARSE_DSV41: [128]; DEEPSEEK_V41_INDEXER: [128])
```

This declares `[64]` on SM12x for the two sites (indexer backend, sparse MLA backend, FlashInfer sparse backend), mirroring the existing SM90 branch. The SWA/backend selection is untouched.

The approach is @aagallo's (described in #59203); this PR adds the validated matrix below.

### Matrix validation (8x RTX PRO 6000, SM120, TP8)
Stack: vLLM `0.31.1rc1.dev158+gab905a885` + FlashInfer `0.7.1rc5`, `--block-size 64 --kv-cache-dtype fp8 --attention-config '{"indexer_kv_dtype":"fp8"}'`, DeepGEMM switched between PR14 head (`40592bd`) and the current pin (`1e1842a`):

| vLLM tree | DeepGEMM | result |
|---|---|---|
| stock | `1e1842a` | fails negotiation (error above) |
| this PR (uniform `[64]`) | `40592bd` | serves, 17x19=323 |
| this PR (uniform `[64]`) | `1e1842a` | serves, 17x19=323 |
| per-layer variant (`[64,128]` + `64*max(1,cr)` specs) | `40592bd` | serves, 17x19=323 |
| per-layer variant | `1e1842a` | serves, 17x19=323 |

All four patched cells boot in ~90-160 s and answer correctly; zero failures. An earlier `attention.hpp:484` observed with uniform-64 on an older stack (0.30.1rc1.dev738 + FlashInfer main @c11f8ba + DeepGEMM 6901431) does not reproduce on current main with either DeepGEMM build — details in #59203.

Pairs naturally with #57292 (fail-fast when FlashInfer lacks runtime page sizes).

Addresses the SM120 serving failure in #59203.

## Requirements & validation (added after review)

**FlashInfer requirement: `flashinfer-python >= 0.7.1rc5` (runtime page sizes).** Measured end to end on 8x RTX PRO 6000 (SM120):
- pinned `0.7.0.post1` + this PR: does **not** serve — fails in ~110 s with `page_block_size=32 is unsupported; decode kernels are instantiated only for page_block_size=64` (64-token kernel blocks give ratio-2 layers 32-token compressed pages; the pin has no runtime page sizes). Stock fails on the pin as well.
- `0.7.1rc5` + this PR: serves at default and `--block-size 64`; `--block-size 128` does not serve on this stack in either declaration form (see matrix below), so the PR buys default-64 — the only geometry that serves on the default BLHNC layout.

Landing order per review discussion: after the FlashInfer bump (#60948), or together with the #57292 guard.

**Matrix (stock / A=[64] / C=[64,128] x default / 64 / 128, GSM8K n=100):** stock fails both ways (assertions upthread); A and C serve at default and 64 (GSM8K 89-91%, no variant-dependent degradation); 128 fails under both declarations (A: BLHNC layout guard; C: FlashInfer `block_kv == 32 or block_kv == 64`). Decode throughput of the four servable configs is within <1% at c1/c4.

**No unit test, by review:** an earlier revision added `tests/v1/attention/test_dsv41_indexer_block_sizes.py`, but it pinned kernel-support values that will drift (and the block size is asserted in C++ at kernel launch, so a black-box version would need a real kernel anyway). Per review it was removed and each SM12x `[64]` now carries a short inline comment naming the failure it avoids (#59203).

**Revalidation on the final form** — 8x RTX PRO 6000 96 GB (SM120), vLLM 0.33.0 with these two declarations, fp8 KV, no explicit `--block-size`: negotiation reports `Setting kv cache block size to 64 for FLASHINFER_MLA_SPARSE_DSV41/DEEPSEEK_SPARSE_SWA/DEEPSEEK_V41_INDEXER/CompressorBackend`; READY in ~7.5 min (cold JIT); KV cache 2,397,337 tokens at 32,768 max-model-len; 4/4 short-answer probes correct and greedy output byte-identical across 3 runs.

Coordinated with #56509 (same failure, overlapping declarations).
```
