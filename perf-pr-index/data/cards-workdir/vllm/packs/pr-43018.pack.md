## Purpose

This is related to the issue: https://github.com/vllm-project/vllm/issues/44341

In a previous enablement PR https://github.com/vllm-project/vllm/pull/40549, we enabled cpu offloading on ROCm, and we noticed the shortcoming of the hipMemcpyBatchAsync API lacked support on numAttrs paramter.

This PR is to fix that situation. This PR is intended to be future compatible and backward compatible. Below is the details:

For the hipMemcpyBatchAsync API, 
(1) ROCm 7.13 will accept numAttrs > 0 while ROCm 7.2.1 - ROCm 7.2.3 do not.
Prepare the code to accommodate this change so that it works now and after the vllm is upgraded to ROCm 7.13+ base.
While testing, found that the hipMemcpyBatchAsync performance was not really doing any batching.
Issue was discussed internally, and was addressed later and the fix would be packaged to rocm 7.14x.

(2) On rocm 7.14 or rocm 7.15, the hipMemcpyBatchAsync performance is optimized comparing with the non-batching hipMemcpyAsync API.

(3) When testing with a staging rocm 7.15 docker image, found an problem with `count` in the `hipMemcpyBatchAsync`  API. hipMemcpyBatchAsync faults (GPU memory access fault -> abort/segfault) when count > 8192, regardless of copy size, direction, or numAttrs. This is being addressed by runtime team. For now, I added an enviornment variable VLLM_KV_OFFLOAD_MAX_BATCH_DESCRIPTORS to chunk the batch copies to work around this problem. 

It has similar problem on a rocm 7.14 docker.

## Test Plan
(1)
vllm unit test, regression test with vllm nightly image

(1.1) Tested hipMemcpyBatchAsync API in a rocm7.13 container and verified it accepts numAttrs=1.
(1.2) Tested the micro-benchmarking to compare hipMemcpyBatchAsync and hipMemcpyAsync performance, and found the performance issue of hipMemcpyBatchAsync  and filed an internal ticket.
 
(2) Tested with a rocm 7.14 or 7.15 to check the micro-benchmarking to compare hipMemcpyBatchAsync and hipMemcpyAsync performance, after the hipMemcpyBatchAsync  is optimized and packaged.

(3) regression test with vllm nightly, rocm 7.2.3

## Test Result

(1) micro-benchmarking test:

Using a hip program to benchmark the hipMemcpyBatchAsync(numAttrs=1) performance vs hipMemcpyAsync.
In ROCm 7.2.3, the performance of hipMemcpyBatchAsync is almost the same (i.e., 1x) as hipMemcpyAsync, as there is no batching implemented.

The optimization is happening rocm 7.14+. So on a wheel-packaged ROCm 7.15 nightly (8× MI350X, gfx950), `hipMemcpyBatchAsync(numAttrs=1)` is now 6–19× faster than a per-op `hipMemcpyAsync` loop, reproducible across two runs:

(2) agentic workflow test:
On the same rocm 7.15 docker, performed an agentx vllm workflow test, and found an issue with hipMemcpyBatchAsync api when count > 8192, GPU would seg fault. 
Discussed internally, and the fix is on the way, but will not be in rocm7.14x. So, for now, added an env to chunk the batches to avoid the seg fault VLLM_KV_OFFLOAD_MAX_BATCH_DESCRIPTORS .
