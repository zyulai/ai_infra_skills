## PR body
```markdown
> Stacked on top of the Aiter MegaMoEv2 integration, **sgl-project/sglang#35619** — that PR adds the FlyDSL MegaMoEv2 backend but requires `--disable-shared-experts-fusion` on ROCm because of the bug below. This change removes that restriction. Base is the `20260922` image commit; #35619 is bind-mounted on top for the megamoe path.

## Motivation

`select_experts` already computes `num_fused_shared_experts_for_gate` — `0` on the per-rank fused shared-slot / aiter path, because the shared expert is appended afterwards by `_post_process_topk_ids` — and uses it at the **non-grouped** gate call sites. But the two **grouped** call sites (`grouped_topk` / `biased_grouped_topk`) still pass the raw `num_fused_shared_experts`, so on the per-rank fused shared-slot path the gate double-emits the shared marker:

- a routed expert is dropped — the gate is asked for `K_routed = top_k - num_fused_shared_experts` and spends one of those slots on its own marker (top-6 → top-5); and
- that marker lands at id `num_experts`, which the DeepEP per-rank remap shifts one past the end of the expert space (`384 → 392` on EP8, valid ids `0..391`).

DeepSeek-V4 routes through grouped `biased_grouped_topk`, so it hits this path. On the FlyDSL MegaMoEv2 backend (#35619) the out-of-range id faults the dispatch with `HSA_STATUS_ERROR_EXCEPTION 0x1016` — which is exactly why #35619 has to run with `--disable-shared-experts-fusion`, forcing the shared expert to run as a separate per-layer GEMM instead of being fused into the megamoe dispatch/combine chain.

## What changed

* `python/sglang/srt/layers/moe/topk.py`: pass `num_fused_shared_experts_for_gate` (not `num_fused_shared_experts`) to `grouped_topk` and `biased_grouped_topk` in `select_experts`.

Two lines. No-op off the per-rank fused shared-slot / aiter path (there `num_fused_shared_experts_for_gate == num_fused_shared_experts`). No behavior change on CUDA / non-fused-shared-slot paths.

## Validation (MI355X gfx950, DeepSeek-V4-Pro-0813, TP8 / DP8 attention / EP8, `--moe-a2a-backend megamoe`)

With the fix, `--enforce-shared-experts-fusion` boots and serves — no `0x1016`; the dispatch/combine runs at `topk=7, local_experts=49` (48 routed + 1 fused shared per rank), confirming the shared expert is fused into the megamoe chain rather than run as a separate GEMM.

**Accuracy** — 5-shot GSM8K:

| arm | accuracy | invalid |
| --- | -------- | ------- |
| shared-off (`--disable-shared-experts-fusion`) | 0.940 | 0.000 |
| shared-on (`--enforce-shared-experts-fusion`) | **0.970** | 0.000 |

Same fp4-MoE run-to-run band, no regression (200 questions; the gap is within noise).

**Throughput / interactivity A/B** (`random`, ISL/OSL 8192/1024, `num-prompts = 4 × conc`), shared-off vs shared-on:

| conc | out tok/s off → on | Mean TPOT off → on | Δ TPOT |
| ---- | ------------------ | ------------------ | ------ |
| 256  | 2814.5 → 2775.9    | 74.2 → **67.9 ms** | **−8.4%** |
| 512  | 3974.6 → 3873.3    | 90.8 → 90.1 ms     |  (flat) |

Fusing the shared expert removes a separate per-layer GEMM from the decode critical path: a **−8% mean-TPOT (decode interactivity) win at conc256** and +5.5% per-rank decode throughput; flat at conc512 (workload-dependent). Aggregate output tok/s is within noise at ISL 8192 (prefill/TTFT-dominated).
