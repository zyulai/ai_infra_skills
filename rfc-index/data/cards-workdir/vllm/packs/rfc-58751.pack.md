## 正文(PRD / 提案全文)

### Motivation.

Rescope of my initial PR#48980 to a more universal approach.

vLLM runs many Triton kernels whose launch parameters (`BLOCK_*`, `num_warps`, `num_stages`) are shape-, device-, and dtype-dependent. Today these parameters are chosen in three different ways:

1. **`@triton.autotune`** (~50 call sites): Triton times a candidate list lazily the first time it sees each new key, during `profile_run`.
2. **Offline JSON tables** (fused MoE, W8A8 block FP8, LoRA, Mamba `selective_state_update`): a config is looked up by `(shape, device, dtype)`. When no file matches, the kernel silently falls back to a hard-coded heuristic default.
3. **Plain `@triton.jit`** (~500 call sites): not tunable automatically.

The gap is category (2). vLLM only bundles a curated set of shapes and devices. When someone serves a model + accelerator combination that isn't in the table, the kernel quietly uses the heuristic default, which can be significantly slower. The only workaround today is to run a standalone
`benchmarks/kernels/benchmark_*.py` script by hand and drop the result into `VLLM_TUNED_CONFIG_FOLDER`.  Furthermore, users need to maintain many config files for various architectures (including new ones) and would instead like an easy out of the box solution that just picks the right configurations for **all** the kernels being used in the serving model.

FlashInfer already solves the analogous problem with `--kernel-config.enable_flashinfer_autotune`, which tunes at kernel warmup for the model actually being served. There is no equivalent for Triton. This RFC proposes one.

### Proposed Change.

Add an opt-in flag, `--kernel-config.enable_triton_autotune` (default `False`), modeled on `enable_flashinfer_autotune`. When enabled, during kernel warmup — after the model is loaded and the KV cache is allocated, but **before** CUDA graph capture — vLLM tunes every Triton config-table kernel that the served model will actually use **but that has no config yet**, and persists the result to a local cache that later startups reuse without re-tuning. Scope is intentionally limited to category (2) above (kernels that read a JSON config table).

A "family" is one config table / lookup function, not one kernel. Each table implements a small interface:

```python
@dataclass(frozen=True)
class TuningItem:
    table: str        # which table this belongs to
    shape: Hashable   # e.g. (headdim, dstate, dtype, nheads, ...)
    bucket: int       # the varying dimension, e.g. effective batch size

class TunableConfigTable(ABC):
    name: ClassVar[str]

    @abstractmethod
    def pending_items(self, worker) -> list[TuningItem]:
        """Items the served model will look up that have no config yet."""

    @abstractmethod
    def tune(self, item: TuningItem) -> dict | None:
        """Benchmark one item on scratch buffers; None if nothing valid."""

    @abstractmethod
    def commit(self, results: dict[TuningItem, dict]) -> None:
        """Persist results and clear the table's lookup caches. Runs on all ranks."""
```

Every rank must reach every collective and every rank must end up with identical configs (so captured CUDA graphs match across TP/PP ranks). The loop:

1. Each rank computes its own `pending_items` (shapes are per-rank, e.g. after TP sharding, but contain nothing rank-specific like a device index).
2. `all_gather_object` the union of pending items.
3. Deterministically sort the union and shard it `items[rank::world_size]` so each item is tuned exactly once.
4. Each rank tunes its slice; failures are caught so they never skip a collective.
5. `all_gather_object` the results; **every** rank calls `commit`, so all ranks write the same files and clear the same caches.

This runs from `kernel_warmup()` right after the `process_local_only` early return, so it always executes on the normal startup path on every rank and before `capture_model`.

### Persistence

- Results are stored under `VLLM_TRITON_AUTOTUNE_CACHE_DIR` (default `$VLLM_CACHE_ROOT/triton_autotune/triton=<version>/<table>/`), reusing each table's existing on-disk JSON schema (keyed by `shape/device/dtype`) so the same files are also usable via `VLLM_TUNED_CONFIG_FOLDER`.
- The config loader gains one extra lookup path (user folder → autotune cache → bundled default), so a second startup finds the tuned file and skips tuning.
- `VLLM_TRITON_AUTOTUNE_FORCE=1` re-tunes even when a config already exists.
- Curated bundled configs are respected by default; tuning only fills gaps.
