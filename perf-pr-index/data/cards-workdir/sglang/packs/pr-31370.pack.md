## PR body

## Summary

On the aiter **per-rank shared-slot** path (MoRI / DeepEP-class EP, EPLB off), the padded-`topk_ids`
region was zero-filled by a **separate `_fill_padded_rows` Triton launch** immediately before the
fused shared-experts **append + per-rank-shared-slot remap** kernel ran.

This PR **folds that padded fill into the append+remap kernel**: rows `>= num_token_non_padded` get
`pad_fill_id` in every routed slot, computed on the rows already loaded into registers. With
`pad_fill_id=0` the result is **bit-identical** to the old `fill(topk_ids=0) -> remap(0)=0`, and it
removes **one launch-bound kernel per MoE layer per step**. The win shows up in decode TPOT and is
largest at low concurrency (launch/latency-bound), tapering at higher concurrency.

The fold is gated so it only triggers when the fused append+remap kernel will actually run
(`num_fused_shared_experts > 0 and _use_aiter and use_per_rank_shared_slots and not EPLB remap`);
otherwise the separate fill is kept (unchanged behavior).

## What changed

- `kernels/ops/moe/fused_moe_triton_kernels.py`: `_fused_append_remap_shared_experts_deepep_kernel`
  gains `num_token_non_padded_ptr` / `pad_fill_id` / `HAS_PADDING`; the wrapper takes optional
  `num_token_non_padded=None, pad_fill_id=0`.
- `srt/layers/moe/topk.py`: on the HIP/aiter path, skip the separate `_fill_padded_rows` launch when
  the fold will run, and pass `num_token_non_padded` into the fused append+remap call.
- `test/registered/moe/test_fused_append_remap_per_rank_shared_slots.py`: adds
  `test_pad_fold_matches_separate_fill` guarding fold == separate-fill.
