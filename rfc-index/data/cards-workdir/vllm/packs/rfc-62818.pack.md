## 正文(PRD / 提案全文)

### Motivation.

#### Background

In structured-output + speculative decoding, `StructuredOutputManager` handles draft tokens in three
steps:

1. `validate_tokens` checks a draft sequence without committing grammar state and trims it to its grammar-valid prefix
2. `grammar_bitmask` builds a vocabulary mask for every draft + bonus positions without committing grammar state
3. `accept_tokens` commits the verified token to the persistent grammar state

The timing of draft validation depends on scheduling mode:

```
Synchronous scheduling

step N-1:   schedule step N-1
            sample step N-1 and retrieve drafts for step N
            accept_tokens(step N-1 output)
            validate_tokens(step N drafts)
step N:     schedule step N with validated drafts
            grammar_bitmask(step N drafts)
            sample step N with bitmask and retrieve drafts for step N+1
            accept_tokens(step N output)
            validate_tokens(step N+1 drafts)
...
```

```
Asynchronous scheduling

step N-1:   schedule step N-1
step N:     schedule step N with placeholder drafts
            sample step N-1 and retrieve drafts for step N
            accept_tokens(step N-1 output)
            validate_tokens(step N drafts)
            grammar_bitmask(step N drafts)
step N+1:   schedule step N+1 with placeholder drafts
            sample step N with bitmask and retrieve drafts for step N+1
            accept_tokens(step N output)
            validate_tokens(step N+1 drafts)
            grammar_bitmask(step N+1 drafts)
...
```

In synchronous scheduling, validation of step N drafts occurs before scheduling step N. So step N is scheduled with validated drafts.
In asynchronous scheduling, step N is scheduled with placeholder drafts before the drafts for step N are retrieved and validated.
Therefore, step N is scheduled with unvalidated placeholder drafts.

#### Issue

See #60451.
The current lifecycle changes the output distribution under spec decode when structured outputs are enabled.

Suppose we have draft tokens:
```
[valid, invalid, ?, ?]
```

`validate_tokens` truncates it to:
```
[valid]
```

Rejection sampling would correctly sample `valid` but treat `invalid` as a bonus token instead of a rejected token.
It would sample the `invalid` position from the target (verifier model) distribution instead of the residual distribution `max(target - draft, 0)`.

### Proposed change.

#### 1. Preserve the first rejected draft for the rejection sampler

Given,
```
[valid, invalid, ?, ?]
```
make `validate_tokens` truncate to:
```
[valid, invalid]
```
instead of
```
[valid]
```

The rejection sampler will consequently treat the `invalid` position as a rejection (thanks to the grammar bitmask disallowing `invalid`) instead of a bonus position.

Note this creates a small performance regression on the sync scheduling because the target model verifies one more token than before.

#### Optional 2. Do not validate drafts on the asynchronous scheduling path

Calling `validate_tokens` to trim draft tokens on the asynchronous scheduling path is redundant. We've already scheduled the request with unvalidated tokens.

Removing the `validate_tokens` call removes reasoning-end detection and a temporary grammar-state advance and rollback.

#### Implementation and alternatives

https://github.com/vllm-project/vllm/pull/61557 implements the proposed changes:
- Rename `validate_tokens` to `trim_spec_tokens` and ensure the invalid token isn't truncated (change 1)
- Remove the `validate_tokens` call on the async scheduling path (change 2)
- Fix grammar backends to ensure `accept_tokens` remains transactional -- avoid an extra `validate_tokens` call inside `grammar_bitmask`

Alternative: https://github.com/vllm-project/vllm/pull/60690
- Use `SchedulerOutput.num_invalid_spec_tokens` to ensure the invalid token isn't discarded (change 1)
- Add `Request.num_invalid_spec_tokens` for the sync scheduling path such that `num_invalid_spec_tokens` computed by `validate_tokens` on step N is available for step N + 1

Rejected Alternative: remove `validate_tokens` from both the sync and async scheduling
- Technically we achieve both change 1 and 2 if we don't validate draft tokens at all
- However, this leads to a statistically significant performance regression on the sync scheduling path.
