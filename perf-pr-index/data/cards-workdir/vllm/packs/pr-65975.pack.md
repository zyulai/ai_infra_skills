## Overview

Use fast SiLU math (`__fdividef` plus a flush-to-zero `ex2.approx.ftz.f32` exp) in the SiLU-family activation expressions that vLLM passes to Humming's `process_input`, the kernel that fuses the MoE w2 activation with input quantization. Humming compiles this kernel without fast math (`ProcessInputKernel.disable_fast_math = True`, added in vllm-project/humming#80), so SiLU currently compiles to a precise `expf` plus IEEE division. This change only affects the activation expression; Humming's quantization, Hadamard and scale math keep the precise flags.

## Claims

- Humming w2 activation+quant kernel is 16–30% faster at prefill sizes on B300, and up to ~40% for DeepSeek-V4.1-Flash's clamped SwiGLU (see tables).
- gpt-oss-20b end-to-end prefill throughput: +1.9% (MXFP8 activations) / +1.7% (FP8 per-token), n=3, spread ≤0.3%.
- Covers SILU / SILU_NO_MUL, clamped SiLU (SWIGLUOAI, SWIGLUOAI_UNINTERLEAVE), SITU and SWIGLUSTEP. GELU (`erff`) and `tanhf` are unchanged.
- No accuracy regression: GSM8K unchanged within noise; quantized outputs are bit-identical for MXFP4/MXFP8 and differ in ~1e-6 of bytes for FP8.

## Details

- Why not enable fast math in Humming: `--use_fast_math` also implies FTZ, approximate division and approximate sqrt for the quantization/scale code, which vllm-project/humming#80 turned off on purpose. Requesting the intrinsics only in the activation string keeps that change local.
- `__fdividef` is a standard CUDA intrinsic; `ex2.approx.ftz.f32` is a single PTX instruction available on every target, not an arch-specific one.
- Edge cases: for very negative inputs `1 + exp(-a)` overflows and `__fdividef` returns 0, the correct SiLU limit; large positive inputs return `a`. The FTZ change was checked bit-exact against the `__expf` version for every changed activation over all finite bf16 gate values, in bf16 and fp32.
- Follow-up (not in this PR): Humming's `process_input` launch-config heuristic under-picks vector width (and uses multi-token blocks) on large grids on both SM90 and SM100. Fixing it upstream adds another ~1.4–1.9% end to end on gpt-oss-20b (B300) and 10–55% at the kernel level on H200 and B300; that change belongs in vllm-project/humming.
- No duplicate: the closest open PR is #59514, which changes vLLM's own `silu_and_mul_quant` CUDA kernel, not the Humming path.
