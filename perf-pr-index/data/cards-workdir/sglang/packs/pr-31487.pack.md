## Summary

Prefill CUDA graphs replay at the next captured token bucket. When capture buckets are sparse, that can execute far more model work than the request contains and make graph replay slower than an exact-shape eager forward.

This change falls back to eager when the selected capture bucket is more than 2x the raw prefill token count. Replays at or below the 2x boundary remain eligible, so closely matched buckets keep their launch-overhead benefit.

The guard is backend- and model-independent. It applies to every prefill CUDA graph runner that bucket-pads tokens, including dense and MoE language models.

## Root cause

The existing eligibility check only verifies `num_tokens <= max_num_tokens`. `load_batch()` then pads to the next capture bucket without considering how much extra model work that introduces.

For Kimi-K2.7 with capture buckets `[2816, 3072, 8192]`:

- 3208 tokens replayed the 8192-token graph (2.55x work).
- 3353 tokens replayed the 8192-token graph (2.44x work).
- With this guard, both use eager exact-shape forwards.
- A close bucket such as 2700 -> 2816 remains graph-eligible.

## Isolated before/after

Hardware/model: 8x NVIDIA H200, TP8, Kimi-K2.7-Code. The two server builds used the same latest-main integration and the same Marlin specialization; the only code difference was this PR.

Workload: `bench_serving`, `sglang-oai-chat`, request rate 1, seed 301, 8 requests, 4 random JPEG images/request, random resolution 512x512 to 768x1024, output length 64. Each build used three seeded warmup rounds and flushed the cache before every round and measurement.

Relevant server settings: FA3, multimodal DP encoder, CUDA IPC transport (1 GiB reserved), mixed chunk with decode interleave, torch symmetric memory, breakable prefill CUDA graph with `[2816, 3072, 8192]` buckets.
