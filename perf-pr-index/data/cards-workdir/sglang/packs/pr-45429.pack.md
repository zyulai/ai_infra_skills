## Motivation

This PR is powered by [KDA](https://github.com/NVlabs/kda) team. On GB300, the BF16 Muse Spark checkpoint runs TP8 across two nodes of one NVL72 rack. Custom all-reduce v2 supports a multi-node group when all ranks share one NVLink clique, but only if PyTorch's caching allocator is VMM-backed (`custom_all_reduce_v2.py`). The cookbook recipe does not enable that, so the server logs "CustomAllreduce is disabled because this process group spans across nodes" and every decode all-reduce goes through NCCL. At batch size 1 that is 4.4 ms of a 10.0 ms decode step.

Depends on [#45422](https://github.com/sgl-project/sglang/pull/45422): the GB300 BF16 recipe needs that flag to start.

## Modifications

The gb300 bf16 cell of `docs/src/snippets/configs/meta-models/muse-spark.jsx` sets `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`, with a two-line comment that explains why. Custom all-reduce v2 then handles the TP8 group, and the fused MoE finalize + all-reduce turns on as well. There are no code changes. The other cells are unchanged, because single-node groups (B300, B200, NVFP4) already use custom all-reduce

## Accuracy Tests

GSM8K via sgl-eval (1319 questions, temperature 0, reasoning effort xhigh, max tokens 8192, 8 runs per side): 93.65% before and 93.55% after. The paired difference is -0.10 pt, with a 95% CI of [-0.86, +0.65]. Greedy one-token replay matches exactly

## Speed Tests and Profiling

Setup: 2x GB300 nodes, BF16, TP8/EP8, layer-norm SP + MegaMoE, 64 requests per point, two independent jobs per side. "Before" is the recipe with #45422's flag; the two unchanged-recipe jobs agree within 0.6%

TTFT is unchanged

Tested on GB300 only, which is the only cell this PR changes. Measurements used the recipe's High Throughput form (speculative decoding off) without HiCache. The default Low Latency form uses the same all-reduce path, but this change was not measured there separately.

Compatibility:

- On GB300 nodes that do not share one NVLink domain, the fabric-clique check in `can_use_custom_all_reduce_v2` fails. Custom all-reduce then stays disabled exactly as before, and the server keeps using NCCL; the setting only changes PyTorch's allocator mode
- Two known incompatibilities with expandable segments do not apply to this recipe:
  - Mooncake with `MOONCAKE_PROTOCOL=efa`: the cookbook's GB300 PD mode transfers over NVLink
  - The weight-cache daemon process
- The combination with PD disaggregation was not tested
