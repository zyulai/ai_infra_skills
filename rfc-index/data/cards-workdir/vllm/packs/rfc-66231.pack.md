## 正文(PRD / 提案全文)

### Scope: S1 only.

#62150 tracks three ways an RL framework pauses P/D engines to update weights. **This RFC is about S1 only.** S2 and S3 will get their own RFCs. Here we only check that the S1 structures do not make them worse and that they can be reused for them: the "S2/S3 probes" and the "What the other #62150 scenarios reuse" table below. A passing S2/S3 probe means the S1 change did not break that case, not that S2 or S3 is solved.

| | Scenario | Call sequence | In-flight requests and prefix cache | Users | Priority |
| --- | --- | --- | --- | --- | --- |
| **S1** | **Continuous (fully-async) rollout** | `pause(mode="keep", clear_cache=False)` on every P and D, in any order → broadcast weights → `update_weight_version` → `resume` | Keep their KV and continue under the new weights. New rollouts carry a `cache_salt` with the policy version. The cache is never reset. | prime-rl (production, NIXL); miles `in_place` is equivalent | P0, **this RFC** |
| S2 | Synchronous drain | `pause(mode="wait"\|"abort", clear_cache=True)` → [`sleep` → wake weights → update → wake KV, if colocated] → `reset_prefix_cache` → `resume` | Finished (`wait`) or aborted (`abort`). The engine is empty during the update; blocks are reclaimed. | verl, SkyRL (Mooncake), NeMo-RL, miles sync mode | P0, separate RFC |
| S3 | Retract | `pause(mode="keep", clear_cache=True)` → update → `resume` | Kept, but their KV is invalidated and recomputed under the new weights. | miles/SGLang default; no vLLM P/D user yet | P1, needs invalidate-without-reclaim (#64865 / #64900) |

### Motivation.

Fully-async RL frameworks update the policy while rollouts are still generating. On P/D disaggregation the update looks like this. prime-rl runs it in production on GLM-5.x with NIXL, xPyD and DP/EP.

```
pause(mode="keep", clear_cache=False)   on every P and D engine
broadcast the new weights               to every P and D engine
update_weight_version(step)
resume()
```

In-flight requests keep their KV and continue under the new weights. Tokens are labelled with `weight_versions`, and the trainer masks or corrects stale ones. New rollouts carry a `cache_salt` that includes the policy version, so they never hit KV computed with old weights. The prefix cache is never reset. miles/SGLang uses the same scheme (`in_place` pause plus a namespaced radix cache).

For this to work, a keep pause on P/D has to be safe in any order and short. On main it is neither:

1. **A P pause waits for D.** A keep pause completes only when the engine has no work (`EngineCoreProc._pause_complete` → `not has_work()`). On P, prefill requests whose KV is retained for a remote reader keep `Scheduler.has_finished_requests()` true. So P's pause lasts until D has read every export, or until the lease expires.
2. **A paused D goes dark.** In `PAUSED_ALL`, `get_num_unfinished_requests()` returns 0, so D stops stepping. It stops issuing reads, reporting completions, and renewing leases (NIXL and Mooncake both send their D→P renewals from `build_connector_meta`, which only runs inside a step). P reaps leases by wall clock, so a pause longer than the lease frees blocks D will read after resume.
3. **Aborts during a transfer are fragile.** #46240: a completion for a request the scheduler already freed kills EngineCore. On Mooncake, a request aborted before its KV is exported leaves D's pull unanswered (see "Measured" below).

prime-rl works around (1) and (2) by pausing all P engines before any D engine, and around (3) with a monkey-patch. With the ordering, their slowest pause went from 30 s to 14.3 s and "Potentially invalid KV blocks" from 354 to 0 (prime-rl #4059). P's pause still lasts until D has drained P's exports.

### Measured on main, on a glue fix, and on this proposal.

Setup: one H20 node, 1P1D (one GPU each), Qwen3-8B, RoCE, D capped at `--max-num-seqs 32` so that P holds exports D has not read yet (the prime-rl situation), lease 30 s on both connectors (`kv_lease_duration=30` for Mooncake). 600-request load at concurrency 96. A case passes if every control call returns 200, the load finishes, both engines go idle and healthy, and greedy probes with a fresh `cache_salt` match a pre-load reference. S1 cases also require every pause to finish in < 3 s and zero lease expiries.

We built two variants from the same base (main 5cdeea9b1):

- **B, glue:** no change under `vllm/v1/core/`. (B1) `_pause_complete` ignores retained exports for keep without clear (same idea as #59670). (B2) A worker-side thread keeps renewing D's leases while the engine is paused. (B3) Mooncake: an abort before export answers the waiting pull. Plus a worker-mixin dedup for #46240. +275/-9.
- **A, structure:** the three scheduler-side structures in "Proposed Change". +416/-48 excluding tests, of which 15 lines are the Mooncake fix shared with B3.

**S1 matrix** (keep pause, no clear; pause order {concurrent, P→D, D→P} × length {2 s, 45 s} under load, plus two idle cases):

| | main | B (glue) | A (structure) |
| --- | --- | --- | --- |
| Mooncake | 8/8 | 8/8 | 8/8 |
| NIXL | 4/8 | 5/8; 8/8 only with `kv_unclaimed_grace=300` | **8/8** |

- On main with NIXL, every case where D pauses before or with P fails the same way: P's pause takes 31 s (the lease) and 19 leases expire.
- B fixes short pauses (P pause 0.95 s, 0 expiries). Long pauses still expire 10–20 leases, from two blind spots of a worker-side fix. Requests that reach a paused D are never seen by D's worker, so nothing renews them. Requests that D aborts or sleeps through keep being renewed, so P waits forever. Passing all 8 needs a 300 s grace before P reaps unclaimed exports, which only moves the problem. Both blind spots need scheduler state.
- A passes all 8 with no knob: P pause 0.9–1.7 s, D pause 0.03 s, 0 expiries, including the 45 s pauses.
- No cost without a pause: the no-pause load takes 56.5–57.1 s on all three, both connectors.

**S2/S3 probes** (out of scope for this RFC; run to check that the S1 structures do not regress these scenarios and that they extend to them). S2: `abort_P_midxfer`, `pause_wait_clear_P`, `pause_abort_PD`, `sleep1_abort_PD`, `resume_during_wait_D`. S3: `pause_keep_clear_D`.

| | main | B (glue) | A before Mooncake fix | A |
| --- | --- | --- | --- | --- |
| Mooncake | 1/6 | 5/6 | 1/6 | **4/6** + 1 intended 500 |
| NIXL | 6/6 | 5/6 | 5/6 + 1 intended 500 | 5/6 + 1 intended 500 (NIXL code untouched) |

- **Mooncake D wedges on main** under abort mid-transfer, wait+clear on P, pause(abort) and sleep(abort). D waits on a pull that P never answers: `record_send_reqs` drops the aborted transfer without waking the waiter (or raises `KeyError` if the worker never saw it), and a later pull recreates a placeholder that waits `VLLM_MOONCAKE_ABORT_REQUEST_TIMEOUT`. This is a connector bug independent of the pause design. With the 15-line fix (step M, the same code in A and B), all four cases pass on A: pause(abort) of P and D takes 1.7 s / 0.9 s, where main's D pause timed out after 120 s.
- **NIXL sleep(abort) on P and D:** P's sleep takes 33 s on main (until D's leases lapse), >120 s on B (D's worker keeps renewing for requests D abandoned), and 3.8 s on A.
- **`resume` during a pending pause** now fails that pause with 500 "Resumed before the pause completed" instead of a late 200 for a pause that never held. This is intended and counted as a failure in the table. On Mooncake, one run in three also left one request waiting on D forever (544 ok, 55 client disconnects, 1 stuck); two reruns finished cleanly. Not yet root-caused; tracked as a step-2 review item.
- **`keep` + `clear_cache=True` on D** returns 500 on Mooncake everywhere. That is S3, out of scope here.

**Stale-read probes** (added in v3; they check the contract's "no request reads invalid KV"). Twelve copy-task requests ("repeat these 24 random 5-digit numbers") are sent while D is paused, so P exports their KV and D holds them. Then the control sequence runs and D resumes. Each request either errors (an honest failure) or must copy its list exactly. A copy task is used because free-form greedy text is not batch-invariant: in a first version of the probe, 4–8 of 12 free-form outputs differed from the no-load reference by a word or two, also in runs with no abort and no lease expiry. The copy task is 12/12 in a no-pause control on every variant. Sequences:
- `abort`: P pause(abort) and resume while D is paused. Run with and without `clear_cache`.
- `dpause`: D alone stays paused 40–45 s, longer than the lease.
- Each sequence runs once at full KV size and once with P's pool cut to 4096 blocks (65k tokens), with a flood of local requests to P of 1× and 4× its pool before D resumes, so that freed blocks get reused before D reads.

| | main | B (glue) | A |
| --- | --- | --- | --- |
| Mooncake, `abort` | 12 errors (P pause 25 s, leases lapse) | 12 errors | 12 errors (P pause 1.4 s) |
| Mooncake, `dpause` | **12 errors** (leases lapse while D is paused) | — | **12/12 correct** (paused D keeps renewing, P3) |
| NIXL, `abort` | 12/12 correct (P pause 31 s) | 12/12 correct (P pause 30 s) | 12/12 correct (P pause 1.4 s) |
| NIXL, `dpause` | 12/12 correct, 95–119 leases expired | 12/12 correct, 92–118 expired | 12/12 correct |
| silently wrong output | 0 in all runs | 0 | 0 |

- No variant returned a wrong copy in any of these runs, including runs where P had freed and reused the blocks of an export D read later. On NIXL that is not explained yet: on main, P reaps 67–95 leases while D is paused (which should include the probes'), seconds before D reads them, P then serves 4× its pool of other requests, and D's reads still return the right KV. We do not want to rely on this and will instrument D (checksum of the received blocks against P's at export) before calling it safe.
- On Mooncake, a D paused longer than the lease fails every request it holds on main. On A it serves them. This is the S1 contract's "pauses of any length" on the connector where expiry is enforced.
- The other side of the same coin: on A, P's blocks stay reserved for a paused D's backlog for as long as D is paused. With P's pool cut to 65k tokens, D paused alone, and local traffic sent to P, P filled to 99.4% KV usage with 0 running and 37 waiting until D resumed (main and B instead expire the exports at 30 s and keep serving). In S1 every engine is paused, so this does not arise; it matters for a D-only pause with P still serving. See open question 4.

Code for A: [BeichenHuang/vllm `s1-ledger`](https://github.com/BeichenHuang/vllm/compare/5cdeea9b13670c9da832d8ea72d799c8bfbb4552...s1-ledger), one commit per step on main 5cdeea9b1. The harness (`launch_1p1d.sh`, `driver.py`, `run_matrix.sbatch`) and per-case logs are available on request and will be contributed as step 0.

**What we take from the comparison.**
- The glue variant fixes short pauses, but its correctness for long pauses depends on a grace knob, and it made one probe worse. Its gaps need the scheduler to know which transfers are live.
- The structures fixed S1 on both connectors without connector code. Their two bugs found by the probes were fixed by changing one table row each (see "Lessons"), not by adding cases.
- Connector bugs are a separate track either way (Mooncake abort before export; #46240-style late completions are handled by construction in A).
- On Mooncake, where lease expiry is enforced, P3 is what lets a D stay paused longer than the lease: main fails all 12 held requests, A serves all 12.

**Recommendation: A.** It is the only variant that passes the S1 matrix on both connectors with no tuning (8/8 each, P pause 0.9–1.7 s, D pause 0.03 s, no lease expiries, including pauses longer than the lease), and S1 needs no connector code. Its costs, which reviewers should weigh:
- It touches `vllm/v1/core/` (`scheduler.py`, `core.py`, a new `kv_transfer_ledger.py`): +416/-48 excluding tests (15 of them the Mooncake fix, step M), split into separately reviewable PRs (see "Plan"). It needs maintainer agreement on the pause semantics.
- A paused D keeps P's exports alive, so a D-only pause with P still serving can fill P's KV (open question 4). It does not arise in S1, where every engine pauses.
- One `resume_during_wait_D` run on Mooncake left one request stuck on D (1 of 3 runs, not root-caused).
- The stale-read safety on NIXL after an abort is shown by probes, not explained (open question 1).

### Proposed Change.

**Contract.** We define it for `pause(mode="keep", clear_cache=False)` + `resume()` on P/D engines, and test it for every in-tree P/D connector (NIXL and Mooncake):

1. **Order-free.** The driver may pause and resume P and D engines in any order, including concurrently.
2. **Bounded.** A pause completes within one engine step plus device sync, whatever the peer is doing.
3. **Safe.** No KV block is freed or reused while a peer may still read or write it, across pauses of any length, including pauses longer than the lease. After resume no request reads invalid KV. Aborting a request during a transfer never kills EngineCore and never wedges the peer.
4. **Isolated and accounted.** A request with a new `cache_salt` gets zero hits on KV from before the update, on P, D and offload tiers. `weight_versions` stays correct for continued requests.

**Three structures.** All three live in the scheduler / engine core and are connector-agnostic.

*P1. Transfer ledger* (`vllm/v1/core/sched/kv_transfer_ledger.py`). One scheduler-side entry per (request, direction):
- `EXPORT`: this engine holds a finished request's blocks for a remote reader. Opened when `request_finished()` asks to delay the free.
- `IMPORT`: a remote holds KV for this request. `PENDING` at `add_request` with `do_remote_prefill` (no local blocks yet), `OPEN` once it enters `WAITING_FOR_REMOTE_KVS` (a remote writes into local blocks), `CLOSING` on `finished_recving`, closed when the request is promoted.

An entry outlives its request. A completion that arrives for a request that finished meanwhile finds the entry, or finds nothing and is ignored, and blocks are freed only when no entry references them (`_free_if_unreferenced`). That is the #46240 fix by construction. `has_finished_requests()` becomes `finished_req_ids or ledger.has_retained()` instead of `len(requests) > running + waiting`.

The ledger answers three different questions, and conflating them caused both bugs our probes found:

| query | true while | used by |
| --- | --- | --- |
| `needs_driving()` | an export, or an import not yet received | P3: keep stepping |
| `pins_blocks()` | an export, or an `OPEN` import | P2: may a cache reset / memory release proceed |
| `has_retained()` | an export, or an import of a request that already finished | `has_finished_requests()` |

*P2. Mode-keyed quiescence.* `Scheduler.quiesced(mode, clear_cache)` is a table instead of branches spread over `has_requests()`, `has_finished_requests()`, `get_num_unfinished_requests()` and `_pause_complete()`:

| mode | compute | outputs to flush | transfers (ledger) |
| --- | --- | --- | --- |
| `keep` | nothing scheduled | flushed | ignored: they outlive the pause |
| `wait` | drained | flushed | nothing `pins_blocks()` |
| `abort` | drained | flushed | exports dropped, then nothing `pins_blocks()` |
| `keep` + clear | as `wait` (a reset needs every block back) | | |

The engine core keeps the pending pause and re-checks it after every step and in `_notify_idle_state_callbacks`. DP keeps its existing consensus (`_begin_pause` / `_pause_ready`). `resume()` fails a pending pause. `release_kv_cache_memory()` requires `not pins_blocks()`, which is what "all transfers drained" in `base.py` assumes today without checking. The `keep` row is the behaviour #59670 adds with a flag.

*P3. Ledger-driven stepping.* While `ledger.needs_driving()`, the engine keeps stepping with zero compute, in every pause state. This is a one-line change to `has_requests()`. The machinery already exists: `schedule()` with nothing to run still calls `build_connector_meta()`, which is where NIXL and Mooncake package their lease renewals, and the model runner routes zero-token steps through `kv_connector_no_forward()` → `get_transfer_results()`, which collects completions and reaps expired leases. Zero-token batches are not counted as compute (`_has_pending_compute`). So a paused D keeps renewing leases and finishing in-flight reads, and a paused P keeps observing completions and freeing blocks. No lease expires because of a pause, on either connector, with no connector code.

Device activity during a keep pause: with P3, a pull that completes on a paused D still runs `post_process_device_kv_on_receive`. RDMA writes into KV memory already land during a pause today, so we propose to allow it and document that a keep pause guarantees no *model* execution, not an idle KV cache.

**Lessons from the probes** (both fixed in the branch, both are one row of the tables above):
1. *Abort drops exports.* First version: an abort pause waited for exports like `wait`. A reader that is paused or asleep keeps renewing its leases under P3, so the wait was unbounded (NIXL sleep(abort) hung > 120 s). An abort now drops retained exports. See open question 1 for what dropping must also tell the connector.
2. *Pause waits on `pins_blocks()`, not `needs_driving()`.* First version: keep+clear waited until nothing needed driving. With Mooncake, new requests keep arriving at a paused D as `PENDING` imports, so the pause never completed (120 s instead of main's immediate 500). `PENDING` imports pin nothing.
