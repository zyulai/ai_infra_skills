## Overview

Fuse quantization into RMSNorm and attention output.

| producer | consumer (quant key) | kernel |
|---|---|---|
| Gemma add-RMSNorm | attn `qkv_proj`, GDN `in_proj_qkvz` (static FP8 or NVFP4) | new Triton `gemma_add_rms_norm_quant`; for GDN it also writes the bf16 normed input that `in_proj_ba` reads |
| post-attention Gemma add-RMSNorm | MLP `gate_up_proj` (NVFP4 or static FP8). Only used by dense layers | same kernel |
| GDN gated RMSNorm | `out_proj` (static FP8) | FP8-output option on `fused_gdn_gated_rms_norm` |
| attention sigmoid output gate | `o_proj` (static FP8) | FP8-output option on `fused_sigmoid_gate_mul` |

Related:
- #56530 (AR+norm+quant at TP>1, complementary)
- #61073 (same contract for generic `RMSNorm`)
- #45364 / #45855 / #42469 / #61783 / #59553 (other norm+quant fusion efforts).

No open PR covers the Qwen3.5 NVIDIA no-compile path.

**Which checkpoints engage (first-party census)**

| checkpoint | quant layout | fusions engaged |
|---|---|---|
| `nvidia/Qwen3.8-27B-NVFP4` | attn q/k/v/o + GDN in_qkv/z/out static FP8; MLP NVFP4 g16 | all four (192 quant kernels/step, runtime-verified) |
| `nvidia/Qwen3.8-2.4T-A95B-NVFP4` | attn/GDN static FP8; MoE experts NVFP4 | the three FP8 fusions (post-attn norm feeds the bf16 router) |
| `unsloth/Qwen3.8-27B-NVFP4` | dynamic per-token FP8; MLP NVFP4 | NVFP4 norm fusion only |
| `nvidia/Qwen3.5-122B/397B NVFP4` | experts-only NVFP4 | none
| official `Qwen/Qwen3.5-*-FP8`, `Qwen/Qwen3.8-*-FP8` | block-FP8 128x128, dynamic | none |

## Claims

- **1.7–2.0× faster than the unfused norm+quant chain** at decode batch sizes and **1.1–1.6×** at large M, for every fused kernel at every M from 1 to 8192.
- **2.2–6.7% lower TPOT** serving `nvidia/Qwen3.8-27B-NVFP4` on B300 at TP1 (up to 6.5% at TP2 c64)
- **Unchanged accuracy**: full GSM8K within noise of main.
- Everything that does not match the contract (block/per-token/dynamic FP8, padded NVFP4, BF16, W4A16, LoRA, MoE router input) keeps the existing path, verified by the audit matrix in Details.

## Details

Dispatch logic
- Entrypoint: `Qwen3_5DecoderLayer.forward`, per norm, one of three paths:
  - TP>1 with the FlashInfer fused all-reduce+norm: AR+norm wins, quant runs separately. AR+norm+quant in one kernel is #56530's scope.
  - Consumer takes `kFp8StaticTensorSym`, or `kNvfp4Dynamic` with zero K padding and `K % 64 == 0` (the norm writes whole 4-column scale tiles): norm+quant.
  - Otherwise the existing plain norm. Eligibility is checked per call through `get_input_quant_key`, since keys appear after weight loading and LoRA hides them.
- The fused kernels assert on layout violations. One exception: `fused_sigmoid_gate_mul` takes a quantized eager fallback for a strided gate view (num_heads == 1 per TP rank).
- The gate fusion lives in `Qwen3NextAttention`, so a Qwen3-Next checkpoint with a static-FP8 `o_proj` also engages it; the norm fusions are Qwen3.5-only. Only the gated-norm, gate and layer-0 fusions engage at TP>1 (65 of 192 quant kernels/step).

Limitations:
- Per-token and 128x128 block FP8 are not included
- The warp-dispatch rule was swept on GB300 (SM103) only; a B200 re-sweep may move the last few percent.

**PDL.** The fused norm launches with `launch_pdl=True` unconditionally (one fat CTA per
row, `gdc_wait` before the first load, `gdc_launch_dependents` after the stores). A/B on
B300, M = 1..32768, FP8 and NVFP4: neutral-to-faster in self-chain (−0.2% to −15%) and
production-like chains (−0.4% to −3.6%); an adversarial early-trigger predecessor costs
at most +4% at M=128, nothing at M ≥ 1024. Outputs bitwise identical with PDL on/off.
At M ≤ 128 the kernel also launches its dependents immediately after `gdc_wait`,
overlapping the consumer GEMM's weight load (~2% chain win); above that the prelaunched
consumer grid steals SMs (fp8 +4-7% at M ≥ 192), so it is gated by M.

**Warmup.** Not in the dedicated JIT-warmup registry (as before this PR); all reachable
variants compile during the standard dummy-run and capture-size sweeps. The jit-monitor
E2E lane is currently skipped (#49349).

**Follow-ups (not in this PR).** AR+norm+quant at TP>1 (#56530); block-FP8 consumer
contract for the official `Qwen/*-FP8` checkpoints; B200 warp re-sweep; earlier
`gdc_launch_dependents` beyond M=128 if the consumer grid is small; split rows across
CTAs at small M for NVFP4. Also related: #41021 (per-shard FP8 scaling — would turn the
static-per-tensor gate here into a fallback), #41457 (fusing `in_proj_ba` into `in_proj`
would remove the bf16 side output).

+NUM_TOKENS = [1, 7, 128, 129, 384, 385]

+def _fp8_codes(q: torch.Tensor) -> torch.Tensor:
+    """Sign-magnitude e4m3 bytes -> ordered ints (+0 == -0)."""
+    b = q.view(torch.uint8).int()
+    return torch.where(b >= 128, -(b & 0x7F), b)
+
+
+def _fp4_codes(packed: torch.Tensor) -> torch.Tensor:
+    """Packed e2m1 nibbles (low first) -> ordered ints (+0 == -0)."""
+    c = torch.stack([packed & 0xF, packed >> 4], dim=-1).flatten(-2).int()
+    return torch.where(c >= 8, -(c & 7), c)
+
+
+def _swizzled_sf_rows(sf: torch.Tensor, m: int, h: int) -> torch.Tensor:
+    """(m, h // 16) view of a 128x4-swizzled NVFP4 scale tensor."""
+    r = torch.arange(m, device=sf.device)[:, None]
+    k = torch.arange(h // 16, device=sf.device)[None, :]
+    num_k_tiles = (h // 16 + 3) // 4
+    off = (
+        ((r >> 7) * num_k_tiles + (k >> 2)) * 512
+        + (r & 31) * 16
+        + ((r >> 5) & 3) * 4
+        + (k & 3)
+    )
+    return sf.view(torch.uint8).flatten()[off]
+
