> [!IMPORTANT]
> **Plugin / out-of-tree maintainers:** this PR changes the KV cache interface between the worker and the engine core, and removes the policy-typed specs (`FullAttentionSpec`, `SlidingWindowSpec`, ...), `KVCacheSpecRegistry` and `Platform.register_custom_kv_cache_specs`.
> [This gist](https://gist.github.com/LucasWilkinson/bb5cd70fc41357fe4245006214c8f6af) has a drop-in shim that keeps an existing worker / model runner working, plus the full old-to-new mapping. The shim is a stopgap; please move to the new API as soon as you can.

## Overview

Part 2 of #42449: `KVCacheSpec` now describes only a layer's **tensor layout**. **Allocation policy** (windows, recycling, prefix caching, Mamba modes) moves onto the KV cache manager that enforces it. Each manager declares its settings as a frozen `Params` dataclass; layers return `KVCacheLayerConfig(ManagerConfig(manager_cls, params), spec)`, and a group is simply *layers that share a block table*.

**Draft:** CPU and GPU unit tests, plus E2E on GLM-5.3-Flash and DeepSeek-V4.1-Flash; remaining E2E pending.

## The payoff: no more `UniformTypeKVCacheSpecs`

The data structures:

```python
@dataclass(frozen=True)
class ManagerConfig:                # allocation policy
    manager_cls: type[SingleTypeKVCacheManager]
    params: SingleTypeKVCacheManager.Params   # e.g. SlidingWindowManager.Params(sliding_window=128)

@dataclass(frozen=True)
class KVCacheLayerConfig:           # what a layer returns from get_kv_cache_config()
    manager_config: ManagerConfig
    spec: KVCacheSpec               # tensor layout

@dataclass
class KVCacheGroup:                 # layers that share a block table
    kv_cache_specs: dict[str, KVCacheSpec]    # layer name -> layout
    manager_config: ManagerConfig
    block_size: int
    dcp_sharded: bool
```

How they flow:

```python
# 1. Each layer declares its policy and layout.
def get_kv_cache_config(self, vllm_config) -> KVCacheLayerConfig:
    return SlidingWindowManager.layer_config(spec, sliding_window=w)

# 2. The planner groups layers that share manager_config, block_size and
#    dcp_sharded. One group, one block table.
group = KVCacheGroup.from_layers({"layers.0.attn": cfg0, "layers.1.attn": cfg1})

# 3. Each side reads only its half.
group.manager_cls(group, ...)   # scheduler: the manager allocates blocks
group.kv_cache_specs[layer]     # worker: each layer's spec shapes its KV tensor
```

Also:

- **Specs:** 15 classes (8 encoding only policy) become 5 layout classes: `AttentionSpec`, `MLAAttentionSpec`, `HiddenStateCacheSpec`, `MambaSpec`, `HiSparsePageSpec`.
- **Sizing:** `manager_cls.max_blocks_per_request(manager_config, ...) × group.page_size_bytes` replaces per-spec methods and wrapper aggregation.
- **Backend builders:** read what they need from their layers and `vllm_config` (e.g. `MambaBase.get_kv_cache_checkpoint_alignment()`, the layer's sliding window); no backend sees manager params.

Non-test code changes 136 files, +2514 / −3510 lines (`kv_cache_interface.py`: +206 / −945). No compat shims in-tree: out-of-tree specs and platform-registered managers need updating (see the gist above).

## Behavior notes

- Cache-hit lookups batch KV cache groups only when they share a manager config, block size, DCP sharding and layout, the same groups `main`'s core coordinator batches. Layout doesn't affect a lookup, but a batch takes the EAGLE last-block drop if any member does. The layout term can be removed once that drop is gone; #64096 extends lookahead block hashes, which replace it, to KV connectors.
- The Mooncake store coordinator now uses the same rule, so unlike `main` it no longer batches packed groups whose first layers share a spec.
- Pipeline parallelism: a group projected onto a stage keeps the whole group's distinct specs, whether the stage holds none or only some of its layers (`KVCacheGroup.distinct_specs`), as `main`'s group-level spec did. The group's kind, lookup batching, block-ID clipping and the Mooncake / MoRIIO / NIXL checks read that, so they are the same on every stage and in the scheduler.
