## Motivation
There is a bug in SGLang servers that use pipeline parallelism. The bug causes the server to hang for prefill requests due to  `_get_new_batch_prefill_raw` always returning `None` on every iteration of the main scheduler event loop.

I'll run through an example using `Qwen/Qwen3-30B-A3B` with `self.pp_size=2`:

```bash
python -m sglang.launch_server \
    --model-path Qwen/Qwen3-30B-A3B \
    --moe-runner-backend triton \
    --disable-cuda-graph \
    --disable-piecewise-cuda-graph \
    --chunked-prefill-size 64 \
    --max-running-requests 1 \
    --port 30004 \
    --pp-size 2
```

The bug occurs here in sglang/python/sglang/srt/managers/scheduler.py:

```python
        if (
            self.get_num_allocatable_reqs(running_bs) <= 0
            and self.chunked_req is not None
            and not self.enable_priority_preemption
        ):
            self.running_batch.batch_is_full = True
            return None
```

In this SGLang server PP=2, so `get_num_allocatable_reqs = min((pp.max_micro_batch_size - running_bs), self.req_to_token_pool.available_size())`.

`pp.max_micro_batch_size = max(self.max_running_requests // self.pp_size, 1)` so `pp.max_micro_batch_size = 1`.

`self.req_to_token_pool.available_size() = len(self.free_slots)` and the free slots are initialized to `self.free_slots = list(range(size))`.

In ou server's `req_to_token_pool`, `size = max_num_reqs` and `max_num_reqs = min(max_num_reqs // self.dp_size, max(min(int(token_capacity / self.model_config.context_len * 512), 4096), 2048))`

`self.dp_size=1`, which gives us:

`max_num_reqs = min(max_num_reqs, max(min(int(token_capacity / self.model_config.context_len * 512), 4096), 2048))`

This gives us `get_num_allocatable_reqs = min((max(self.max_running_requests // self.pp_size, 1) - running_bs), min(max_num_reqs, max(min(int(token_capacity / self.model_config.context_len * 512), 4096), 2048))`

We have `token_capacity = 4960064` and `self.model_config.context_len = 40960`, which gives us:

`get_num_allocatable_reqs = min((max(self.max_running_requests // self.pp_size, 1) - running_bs), min(max_num_reqs, 4096))`

`max_running_requests=1` so we get:

`get_num_allocatable_reqs = min((1 - running_bs), 1)` before any requests are sent, which will allow the first prefill batch to be returned by `_get_new_batch_prefill_raw`.

If a single large prompt is sent, it will be broken into chunks. The prompt's `Req` instance will be assigned to `self.chunked_req` and a req slot will be allocated in the req_to_token_pool, which started with 1 free slot so now it will have 0 free slots. Thus,

`get_num_allocatable_reqs = min((1 - running_bs), 0 (len(free_slots)) = 0` which means

```python
        if (
            self.get_num_allocatable_reqs(running_bs) <= 0
            and self.chunked_req is not None
            and not self.enable_priority_preemption
        ):
            self.running_batch.batch_is_full = True
            return None
```

will evaluate to True on every iteration of the scheduler's event loop, and no new requests will make progress, nor will the current request. Thus, the server will hang for lots of users.

When pipeline parallelism was first added to SGLang (https://github.com/sgl-project/sglang/pull/5724), this check actually always allowed the next chunk of a chunked prefill prompt to be returned in the new batch, and the check was `not self.chunked_req` instead of `self.chunked_req is not None`, which are logically opposite.

A bug was introduced in https://github.com/sgl-project/sglang/pull/14883 when that check was subtly inverted. The check went from `if not self.chunked_req` to `if self.chunked_req is not None`. 

## Modifications

Change `if self.chunked_req is not None` back to `if self.chunked_req is None`.
