## Motivation

`amd/Qwen3.5-397B-A17B-MXFP4` (Quark) leaves the whole MTP stack in bf16: its `exclude` list has 1547 `mtp.*` entries, including the 512 routed experts of the draft layer. The NVFP4 checkpoint used on the NVIDIA side does the same (`mtp.layers.0*` excluded). With EAGLE/MTP decoding on MI355X this means:

- the draft model loads 7.9 GB per rank at TP2 (6.4 GB of bf16 experts), memory the KV pool could use;
- every draft step and the draft-extend step run the draft MoE through the bf16 ck 2-stage path (E=513, top-11, `QuantType.No`), ~610 us per step at bs ~20 versus ~150-200 us for the MXFP4 a4w4 kernels the target model uses. Three draft steps plus draft extend per decode cycle make this the largest single item of the draft chain at medium and high batch sizes.

SGLang already has the online-requantization plumbing (`--speculative-draft-model-quantization quark_mxfp4`, `REQUANTIZATION_METHODS`, `QuarkConfig(online_scheme="quark_mxfp4")`), but for a draft whose checkpoint carries a Quark config the explicit CLI request was overridden by the "use the draft model's detected quantization" branch, so the flag was silently a no-op for exactly this case.

## Modifications

- `configs/model_config.py`: the draft-model branch that falls back to the checkpoint's detected quantization no longer applies when the draft quantization was given explicitly, is one of `REQUANTIZATION_METHODS`, the build is HIP and the draft is the Qwen3.5 MoE MTP draft (`is_qwen3_5_mtp_draft`, next to the other model predicates: `architectures[0] == "Qwen3_5ForCausalLMMTP"`, which `_config_draft_model` sets before quantization is resolved, and `model_type == "qwen3_5_moe"`). Everything else keeps the previous behaviour.
- `model_loader/weight_utils.py`: `_quark_draft_online_quant_config()` — for that same combination, when the checkpoint's Quark config lists `mtp.layers.0.mlp.experts*` under `exclude`, return `QuarkConfig(online_scheme="quark_mxfp4")` for the draft so its routed experts are quantized online to MXFP4 at load time. Only the draft model is affected; the target model keeps its serialized Quark scheme. The attention projections, shared expert and lm_head of the draft stay bf16 (the online scheme's own exclusion list for `qwen3_5_moe`).
- No change for other models, for CUDA, or when the flag is not passed.

Usage (added to the InferenceX MI355X recipe in the A/B below): `--speculative-draft-model-quantization quark_mxfp4`.

## Accuracy Tests

GSM8K (`few_shot_gsm8k`, 5-shot, all 1319 questions, temperature 0, max new tokens 2048, TP2, real EAGLE decoding, aiter backend, page 16, fp8 KV), draft experts online MXFP4:

| | Accuracy | Invalid |
|---|---:|---:|
| baseline | 0.921 | 8/1319 (0.006) |
| this PR | 0.926 | 5/1319 (0.004) |

GPQA diamond (198 questions, 8 repeats). Accept length = mean over every decode step of the run (server log):

| | Mean score | Unparsable | EAGLE accept length (mean / p50) |
|---|---:|---:|---:|
| baseline, draft experts bf16 | 0.879 | 0.25% | 3.30 / 3.30 |
| this PR, draft experts online MXFP4 | 0.876 | 0.06% | 3.29 / 3.28 |

Per-run standard error of the score is about 0.008 (sample std 0.32), so the two are within noise; the accept length, the only thing the draft's precision can move, is unchanged. Draft model memory at TP4: 2.45 GB per rank.

Speculative decoding leaves the output distribution to the target model's verification; the draft only proposes, so its precision can only move the accept length, which is unchanged here and in the serving runs below (3.39 vs 3.39 at TP2 c32).
