## Motivation
This PR is exactly the one https://github.com/sgl-project/sglang/pull/26722, which had already been merged to `amd/deepseek_v4` branch.
Co-author: @yichiche, @Raiden-Makoto

<!-- Describe the purpose and goals of this pull request. -->
The Triton sparse MLA decode kernel dispatch logic previously had a fallback path to a 2-phase (separate gather + attention) implementation for decode batch sizes in [33, 255] from kernel-level benchmarking. But for real E2E test, this 2-phase path caused significant performance degradation at high concurrency (8k/1k, TP=8, cc=64/128) due to:
- Extra intermediate buffer allocation (gathered_kv)
- Additional kernel launch overhead
- Inability to fuse gather and attention operations
For example, at bs=64, `_unified_sparse_decode_kernel `alone takes ~65% of decode attention time, whereas at bs=4, the fused `_fused_gather_attn_dsv4_dual_scope_kernel `only takes ~29.6%. We should try forcing the fused kernel path even at high concurrency.

## Modifications

<!-- Detail the changes made in this pull request. -->

- Remove 2-phase implementation: Delete 3 files containing the separate gather+attention path since won't be called anymore. (`triton_mla_kernels_decode_common.py`, `triton_mla_kernels_decode_dsv4.py`, `triton_mla_kernels_decode_splitk.py`)
- Simplify kernel dispatch: All dual-scope cases now use fused kernels:
   - Small batches: fused split-K kernel (better GPU utilization)
   - Large batches / extend / prefill: fused no-splitk kernel
   - Previously 2-phase [33, 255] range: now uses fused no-splitk
- Code cleanup: Inline `_bucket_total_tokens`, extract `_decide_splitk_dual_scope` as shared function, remove dead code
