## 正文(PR 描述)

## Purpose

Fixes #57423.

`flashinfer_autotune` persists the FlashInfer autotune cache from rank 0 only and, on the next
engine start, broadcasts that file to every rank. FlashInfer keys persisted MoE entries by
`tp_rank` / `ep_rank` (`MoERunner.get_cache_key_extras`), so only rank 0's lookups can hit. A hit
skips the per-tactic reduce of the synchronized tuning pass (`autotuner.py`: "a cache hit skips
that profile's reduce"), so ranks 1..N-1 block in the reduce while rank 0 spins at the trailing
barrier until the 30-minute timeout. Any second engine start that sees the file trips it: a
container restart with the cache directory on a pod-lifetime volume, or a persistent
`VLLM_CACHE_ROOT`.

Fix: each rank saves and loads its own file (`autotune_configs_dp{dp}_rank{r}.json`), and ranks
load only when every rank has a file, decided by one `all_gather_object` over the CPU group. That
gather replaces the previous broadcast and barrier at the same spot, so no collective is added.
Old single-file caches are ignored by name and re-primed on the next start.

## Field report

Observed on one 8xH100 node (SM90), TP8 + EP8 FP8 MoE model, `vllm/vllm-openai:nightly-8a728663`
(v0.28.1rc1.dev388), FlashInfer 0.6.18, `$HOME` on a pod-lifetime emptyDir.

- The engine died of an unrelated GPU fault. The kubelet restarted the container in place 18 times
  over 8.5 h. Every restart: weights and KV cache fine, then all 8 ranks log
  `Loaded 42 configs from .../flashinfer_autotune_cache/0.6.18/90a/<hash>/autotune_configs.json`,
  rank 0 logs `Config cache hit for trtllm::fused_moe::gemm1 (runner=MoERunner, source=config file)`
  (and `gemm2`), ranks 1-7 sit in `Tuning trtllm::fused_moe::gemm1: k/21 [30:00<...]`, EngineCore
  logs `No available shared memory broadcast block found in 60 seconds` every minute, then
  `torch.distributed.barrier` in `flashinfer_autotune` times out and the API server exits with
  `Engine core initialization failed`. Same signature as the log in #57423.
- During the hang: GPU 0 at 100 % utilization, GPUs 1-7 at 0 %; rank 0's worker at 100 % CPU in
  state R, the other seven sleeping. No other process held GPU 0.
- Mitigation/confirmation: renamed only the `flashinfer_autotune_cache/` directory aside and
  restarted the same container on the same GPUs. Autotune ran for 1 s on all ranks
  (`Saved 42 configs`), engine init took 20 s, READY. 19 identical failures, then one success with
  one variable changed.
- The stale and the fresh cache files hold the same 42 keys and identical `_metadata`; the stale
  one is rank 0's, so its keys only match `ep_rank=0`.

## Note

This is an alternative to #57579 which ensures all ranks load identical files as the leader.
However, the deadlock leading to vLLM being stuck (and subsequently in a crash-loop) on K8s is
caused by non-leader ranks expecting to see their entries in the cache file, so even if all
ranks load files that are identical, you would still run into this issue.
