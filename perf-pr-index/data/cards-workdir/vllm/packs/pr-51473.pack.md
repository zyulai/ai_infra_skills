## Summary

DeepSeek-V4 has a 3072-wide routed-expert intermediate, so effective MoE TP8
owns a native 384-wide MXFP4 shard. The generic ROCm allocation path rounded
that shard to 512 before parameter allocation and checkpoint loading. This was
physical padding rather than failed checkpoint sharding, and it inflated the
routed-expert allocation by 33%.

The rounding rule now lives in the generic MXFP4 oracle beside the existing
Kimi-K3 special case:

- the generic `Mxfp4MoEMethod` passes activation to the rounding oracle;
- AITER BF16/SiLU uses its 128-aligned layout regardless of model or routing
  method, keeping native shards such as I384 at TP8;
- every other activation and backend retains its existing alignment;
- no AMD-specific `RoutedExperts` subclass, quantization method, file, or model
  wiring is needed;
- a focused regression test covers the native I384 allocation.

EP checkpoint loading and expert mapping are unchanged.

## Memory validation

The 64-file checkpoint contains 805.33 GiB of safetensors: 778.148 GiB of
routed-expert tensors and 27.171 GiB of tensors replicated under DPA. The
header-derived per-rank payload for an eight-way routed-expert shard is:

```text
778.148 / 8 + 27.171 = 124.439 GiB/rank
```

Measured with the same no-prefix TP1 x DP8, EP-off configuration on 8x gfx950:

| Revision | Routed layout/rank | Model/rank | KV/rank | KV tokens/rank |
|---|---:|---:|---:|---:|
| Parent `821717118f` | 384 experts x physical I512 | 156.45 GiB | 39.31 GiB | 2,859,796 |
| This change | 384 experts x native I384 | 125.20 GiB | 71.85 GiB | 5,226,632 |

The change saves 31.25 GiB of model memory per rank, increases available KV by
32.54 GiB, and increases KV-token capacity by 82.76%. The I384 model allocation
is within 0.61% of the checkpoint-header prediction.

EP8 is intentionally unchanged. A separate EP8 validation loaded 48 of 384
full-width I3072 experts per rank and measured 124.61 GiB model memory, 69.79
GiB KV, and 5,076,613 KV tokens per rank.

vLLM still reserves total memory according to `gpu_memory_utilization`; the
recovered model memory becomes KV capacity rather than reducing the final
`rocm-smi` allocation. The W2 E8M0 scale columns retain their separate 12-to-16
safety padding.

AIPerf exports TPOT under `inter_token_latency`; it uses the standard
per-request formula `(E2E - TTFT) / (output tokens - 1)`.

The native-I384 arm completed 2,020 profiling requests with zero errors. The
57 requests still in flight at the fixed duration boundary were normal teardown
cancellations and were excluded from the profile. The theoretical trace hit
rate was 97.24% on the parent and 96.69% on I384 because the completed-request
mix differs in a duration-based run; the measured server hit rate nevertheless
improved by 1.97 percentage points.

AIPerf emitted generic counter-reset warnings while exporting warmup metrics.
The warned deltas match the warmup series, not profiling. Server and router logs
show exactly eight one-time starts and no restart, VM fault, OOM, worker death,
engine death, or HTTP 5xx response.

This paired test demonstrates a large end-to-end improvement from the change.
It does not isolate the contribution of additional KV capacity from the reduced
physical MoE width because both are direct effects of removing I512 padding.

## Checkpoint compatibility

Normal Hugging Face/Quark checkpoint loading is unchanged. Existing vLLM
`sharded_state` snapshots whose AITER BF16/SiLU tensors used the generic ROCm
256-alignment must be regenerated when the physical shape changes. For DSV4
TP8, this means regenerating snapshots that stored I512 for the new I384
allocation.
