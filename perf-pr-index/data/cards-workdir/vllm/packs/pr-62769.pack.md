## PR body
```markdown

This carries #56831 by @CedricHwong forward to current main. That PR has been idle since 09-14 and no longer passes CI after the rebase. Cedric's commit is kept unchanged, with his authorship. The two commits on top address the review comments on that PR.

Adaptive verification (DSpark) picks the per-step draft budget on the host from rank-local stale confidences, then picks which slots to keep on the device from rank-local live confidences. If TP ranks disagree on either one, they run different batch layouts: different token counts, or equal totals with different request boundaries. That breaks the collectives that follow and can hang them (#54011). This PR makes TP rank 0 authoritative:

1. `get_num_tokens`: `draft_budget` is broadcast with `broadcast_object` (shm MessageQueue, host only).
2. `reallocate_drafts`: on steps that trim, the per-request `capacities` are broadcast from rank 0 before `cu_num_logits` / `query_start_loc` are built.

Both conditions around (2), `draft_budget == 0` and `draft_budget < scheduled drafts`, depend only on the broadcast budget and scheduler-provided counts. Every TP rank therefore takes the same branch, and the collective cannot be entered unevenly.

### Changes vs #56831

- **Test updates for current main.** #56888 renamed `async_copy_to_gpu` to `async_tensor_h2d`; the old monkeypatch no longer resolved, giving 12 failures, and `cpu.yaml` runs `-x`. #58466 made `reallocate_drafts` also return the admitted draft counts. #63421 replaced the compiled budget assignment with a Triton kernel; the CPU test stands in for it with its global top-k reference. #55939 made `tests/v1/spec_decode` type-checked, so the test now narrows `_batch_budget` before indexing it.
- **Real multi-rank test.** `test_tp_ranks_agree_on_verification_layout[2, 4]` spawns gloo ranks with a real TP `GroupCoordinator` and drives the real `get_num_tokens` / `reallocate_drafts`. The ranks' confidences differ by one fp32 ULP, across three cases: a draft-budget tie, an equal-total boundary split, and 64 randomized steps. Every rank must end up with the leader's budget, capacities, `cu_num_logits` and `query_start_loc`. It replaces the single-process budget emulation.
- **Transport.** The capacities sync uses plain `get_tp_group().broadcast`, i.e. c10d on the TP device group, as in #56831.
  - Routing `GroupCoordinator.broadcast` through the device communicator (PyNCCL) would be about 2x cheaper per call. On CUDA it would also avoid creating the device group's NCCL communicator on the first trimmed step. But it changes every `GroupCoordinator.broadcast` caller (PCP `sync_drafts` too) and needs XPU validation, so it will be a separate PR.

Scope: this covers TP. It also covers DCP when PCP = 1; DCP groups span PCP before TP. With PCP > 1, each PCP slice's TP group has its own leader. Since #61994, DeepSeek-V4.1 on NVIDIA rejects AV + PCP (it requires fixed-length DSpark). The generic `PCPManager` path still admits it, which predates this PR and is a follow-up.

## Test Result

- **Unit tests** (on main `7e3e3f6ab6`): `test_adaptive_verification.py` gives 31 passed and 7 skipped (the CUDA-only kernel tests). mypy and ruff are clean, and the real-rank test passed 10 of 10 runs.
  - **Without the budget broadcast:** the real-rank test fails on the budget tie; 36/64 random steps diverge at TP2, 53/64 at TP4.
  - **Without the capacities broadcast:** the real-rank test fails on the boundary case (4/64 random steps at TP2, 10/64 at TP4: equal totals, different request boundaries). The emulated reallocation tests at TP 2/4/8 fail too.
- **Multi-rank harness:** 0 mismatches on this branch at every world size and drift level.
  - Without the fix, a single fp32 ULP is enough to change the layout. Mismatching steps per 1000 at TP 2/4/8 (capacities or boundaries):
    - 1-16 ULP: 0-2
    - 1e-4 relative: 2-9
    - 1e-2 relative: 65-382
  - Most mismatches have equal totals across ranks but different request boundaries.
- **Per-step cost, MI355X, p50 (p90), slowest rank:**

| | TP2 | TP4 |
|---|---|---|
| `broadcast_object(budget)`: every step that has drafts, host only | 6.7 us (7.5) | 7.9 us (8.2) |
| `capacities` broadcast (c10d, as in this PR): trimmed steps only. Host enqueue + in-stream GPU time; does not depend on num_reqs from 1 to 256 | ~32 + ~25 us | ~33 + ~26 us |
| Worst-case total for a trimmed step, with no overlap | ~64 us | ~68 us (p90 ~76) |

  That is 0.4-1.4% of a 5-15 ms decode step, at most. The host part overlaps GPU work under async scheduling. With PyNCCL (the planned follow-up), a trimmed step costs about 25-29 us.
- **End to end at TP2, measured with the capacities sync on PyNCCL (an earlier revision of this PR); the c10d path still needs an e2e run (GPUs were busy): no measurable regression.** Each delta is within about 1.2 standard deviations; run-to-run CV is 0.2-0.6%.

| conc | output tok/s, main | output tok/s, this PR | delta | TPOT p50, main → PR |
|---|---|---|---|---|
| 1 | 721.0 ± 4.1 | 727.7 ± 10 | +0.9% | 1.311 → 1.314 ms |
| 16 | 5489 ± 12 | 5493 ± 15 | +0.1% | 2.755 → 2.763 ms |
| 64 | 10590 ± 50 | 10585 ± 19 | -0.1% | 5.615 → 5.629 ms |

  Acceptance length is unchanged (±0.7%). There were 0 failed requests in 24 runs. The `capacities` broadcast fired on about 97% of c16/c64 steps and about 7% of c1 steps.
- **Natural divergence was not observed on this setup.**
  - Instrumented main ran 8434 steps at TP2 and 7886 steps at TP4: 0 budget, capacities or confidence mismatches.
  - A separate DeepSeek-V4.1 TP4 MI355X serving trace ran about 478k AV steps, also with 0 mismatches.
  - Here the confidence inputs are bitwise identical across ranks, because the custom all-reduce sums in a fixed rank order. Divergence needs rank-asymmetric numerics, such as rank-order-dependent reductions, non-deterministic kernels, or the TP8 H20 DeepSeek-V4 setup in #54011.
  - The fix is cheap insurance against that: per the numbers above, about 7 us host per step plus about 19 us per trimmed step.

Co-authored with @CedricHwong (original fix, #56831). Supersedes #56831.
```
