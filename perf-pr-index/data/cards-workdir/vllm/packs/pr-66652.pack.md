## Overview

DeepSeek-V4.1 decode spends ~80 Mega mHC launches per step on the shifted mHC boundary (residual update, next sublayer's pre-mix, Sinkhorn, collapse and RMSNorm). At decode batch sizes DeepGEMM's `sm100_mega_mhc_impl` takes 13-19 us per call, far above what its traffic needs.

This adds a CuTe DSL kernel for boundaries of up to 336 tokens, adapted from TensorRT-LLM's DeepSeek-V4.1 mHC boundary (NVIDIA/TensorRT-LLM#21438, Apache-2.0) and reworked to cover more tokens in one wave:

- Sixteen-CTA clusters each own a tile of tokens and split the hidden dimension; the CTAs exchange their partial mixes and sums of squares through distributed shared memory, so the whole boundary is one kernel.
- The mixer GEMM's A fragments stream from L2 in a coalesced layout, prefetched 4 k-steps ahead, instead of a resident 120 KB weight slice. Each CTA then fits in half an SM, so 14 clusters run at once and one wave covers 336 tokens (tile = ceil(M / 14), 24 tile sizes). The launch sets the shared-memory carveout so every tile keeps two CTAs per SM.
- Each `DeepseekV4DecoderLayer` (target and DSpark draft) registers non-persistent buffers for its mixer weights laid out for the kernel (`hc_attn_boundary_weight`, `hc_ffn_boundary_weight`; None where the kernel cannot run), fills them in `process_weights_after_loading`, which every load and reload path runs, in place so captured graphs read updated weights, and passes them to `mhc_shifted_post_pre`.
- `mhc_shifted_post_pre` takes the kernel for batches of up to 336 tokens and keeps Mega mHC for larger ones (where this design no longer wins), for a token tile not compiled before graph capture (each tile compiles on the eager run vLLM makes before capturing a size), and wherever Mega mHC was not used before.

Precision: the mixer weight is rounded to TF32 and split into BF16 high and low parts whose sum is exact, so every product equals the TF32 product of Mega mHC's GEMM (BF16 activations are exact in TF32). Reductions run in a fixed order, so results are deterministic; only the accumulation order differs from Mega mHC.

The port keeps only what vLLM uses; TensorRT-LLM's multi-kernel path for larger batches, its MXFP8 output epilogue, the deferred-Sinkhorn kernel and its NVFP4 quantization kernels are left out.

## Claims

- DeepSeek-V4.1-Flash decode, GB300: 1.5-5.8% lower step time at 48-336 tokens per rank (DSpark k=5, 8-56 requests per rank).
- The boundary op is 1.13-1.47x faster than Mega mHC at 197-336 tokens and 1.41-2.04x faster below 197, at every token count (median of 10 rounds; no round slower).
- Same TF32 products as Mega mHC; the updated residual is bitwise identical to Mega mHC at every token count 1-336. GSM8K is unchanged.
- No change above 336 tokens: same kernel, same GPU time.
