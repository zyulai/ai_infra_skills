## Summary

This PR adds request-wise fixed-token prefill logprob scoring for OPD / top-k distillation:

- `SamplingParams.prompt_logprob_token_ids`: candidate token IDs to score.
- `SamplingParams.prompt_logprob_start`: absolute first causal prompt row to score.

The result is returned through the existing engine-core and `RequestOutput` paths for the V2 GPU runner.

This is M1 of RFC #56860. Per-position candidate lists (M2) are tracked there.

## Design

For a prompt of length `C` followed by student-generated output tokens, the hidden state at row `i` predicts token `i + 1`. Therefore the first output token is predicted by row `C - 1`. An OPD request sets:

```python
prompt_logprob_token_ids=teacher_topk_union
prompt_logprob_start=C - 1
```

This returns exactly the student probabilities needed for the output suffix. It does not score the earlier context rows. The dedicated result is source-row aligned and contains only requested rows; unlike `prompt_logprobs`, it does not add a leading `None` sentinel.

The candidate IDs are request-wise and fixed across positions, matching M1 of #56860. For each scheduled prefill chunk, the runner converts the absolute start into the chunk-relative row range, runs the lm-head only on that range, and gathers the requested IDs. The worker keeps one `[num_scored_rows, num_ids]` buffer per request, allocated on the first prefill chunk and written in place chunk by chunk, and emits it on the last chunk. Nothing is concatenated, and a request whose start is past the last scorable row emits an empty buffer rather than nothing.

This bounds intermediate memory by the requested suffix and candidate width rather than the full prompt. With `prompt_logprob_start=C-1`, the retained result is proportional to the generated output length. The implementation intentionally keeps the existing chunking and output plumbing instead of adding a new sparse protocol.

### Scoring reuses the sampler's kernel

Scoring calls the existing `compute_token_logprobs()` rather than computing `gather - logsumexp` in the logits' own dtype. That kernel already does exactly this gather: it accumulates max and logsumexp in fp32 and emits only the requested columns, so it materializes no `[tokens, vocab]` tensor either.

The kernel indexed `token_ids` as contiguous rows. It now takes a row stride for `token_ids`, as it already did for `logits`, so the request-wise IDs are passed as a broadcast `[rows, num_ids]` view (stride 0) and are never copied out per row. Existing callers pass contiguous tensors and are unaffected.

This matters numerically. Reducing over a 151936-entry bfloat16 vocabulary loses about 1e-1 of accuracy; against vLLM's own `prompt_logprobs` on the same forward pass, an in-dtype reduction disagreed by up to 7.78e-02. Through the shared kernel the values are bit-identical to `prompt_logprobs` (see Verification).

## Naming

The request-side parameters follow the existing `logprobs` / `prompt_logprobs` prefix convention: `SamplingParams.logprob_token_ids` already exists on main (#43463) and scores caller-supplied token IDs at sampled positions, so `prompt_logprob_token_ids` is its prefill counterpart.

The result is named after that parameter: `RequestOutput.prompt_token_id_logprobs`, a plain `[num_scored_rows, len(prompt_logprob_token_ids)]` float32 array whose columns follow the order the IDs were requested in. The IDs are not echoed back: the caller supplied them, so a container pairing them with the scores would carry nothing the caller does not already have, and nothing between the worker and the output needs them either.

Returning `list[dict[int, float]]` instead would cost ~22 MB of Python objects for a 1000-row, 242-ID request against ~1 MB for the array, and callers doing top-k distillation want the array rather than dicts they have to re-flatten.

## Token-in/token-out HTTP and the Rust frontend

`/inference/v1/generate` takes raw `SamplingParams`, so it accepts both parameters; the non-streaming response returns the scores as `prompt_token_id_logprobs`, a base64 `.npy` float32 array (`np.load(io.BytesIO(base64.b64decode(s)))`), the encoding `routed_experts` already uses on this endpoint. Streaming follows `prompt_logprobs`: the Python frontend omits the field, the Rust frontend rejects the request.

`EngineCoreOutput` is `array_like` on the Python side and decoded positionally by the Rust engine-core client (`Deserialize_tuple`), so the field is appended last there too, kept as the wire ndarray with its aux frame resolved in place; the server writes its float32 bytes straight into the `.npy`. The Rust frontend forwards `prompt_logprob_token_ids` / `prompt_logprob_start` and, since it bypasses `InputProcessor`, checks the candidate count against `max_logprobs` and the ids against the vocabulary, as it does for `logprob_token_ids`. Its `.npy` encoder is byte-identical to `numpy2base64`. OpenAI routes are unchanged.

## Limits

The candidate count is bounded by the existing `max_logprobs` (`--max-logprobs`, default 20), not by a new constant. One logprob per requested ID is returned per scored row, which is exactly the quantity that setting already bounds for `logprobs` and `prompt_logprobs`, and `-1` opens it to the whole vocabulary here too. A distillation workload wanting a few hundred candidates therefore needs the operator to raise `--max-logprobs`, the same opt-in the existing full-vocabulary path requires.

Because the default rejects any realistic candidate set, this is the first error most callers of the parameter will meet, so it names the value to set rather than just the setting:

```
Requested prompt_logprob_token_ids of length 242, which is greater than
max allowed: 20. Set max_logprobs (--max-logprobs) to at least 242.
```

Both spellings appear because `--max-logprobs` is not what a caller using `LLM(...)` sets. The sibling errors in `_validate_logprobs` carry no such hint; the asymmetry is deliberate, and easy to drop if reviewers would rather keep them uniform.

The parameter is implemented for the V2 GPU runner only, so the input processor rejects it with a `VLLMValidationError` naming `VLLM_USE_V2_MODEL_RUNNER=1` when that runner is not in use, rather than letting the V1 runner return `None`. `prompt_logprob_start` without `prompt_logprob_token_ids` is likewise rejected instead of being silently ignored.

`logprob_token_ids` keeps its own `MAX_LOGPROB_TOKEN_IDS = 128` because that number is physical: it is the row width `LogprobTokenIdsState` preallocates. Prompt scoring allocates per request, so it has no such structural bound and does not need a constant of its own.

On the output path the result is owned by `LogprobsProcessor` alongside sample and prompt logprobs, and reached through the same single `update_from_output` call. That also gives it the same `RequestOutputKind.DELTA` handling: like prompt logprobs it is popped, so a streaming request carries it on exactly one output at the end of prefill instead of re-attaching the array to every later delta.

It is kept out of `prompt_logprobs_dict` deliberately: `LogprobsTensors` carries an implicit target-token column and a rank column, neither of which is meaningful for a caller-fixed ID set, and `prompt_logprobs` prepends a `None` sentinel for position 0 that this result must not have. Reusing that container would mean populating two columns with placeholder values and then documenting that they are meaningless.

## Relationship to SGLang

SGLang main uses the same two concepts: request-wise `token_ids_logprob` and an absolute `logprob_start_len`. Its scheduler converts the absolute position to a per-chunk pruned range, and its logits processor applies the lm-head only to suffix hidden states. This V2 implementation follows that lifecycle and offset model while reusing vLLM's existing chunk helper and logprob kernel.

SGLang main does not currently expose a per-position candidate-ID API; this PR therefore does not add one. Per-position candidates are proposed as M2 in #56860.

## Scope / non-goals

This is M1 of #56860. It does not add per-position candidate lists (M2 in #56860), streaming updates, a scoring-only lifecycle, speculative/beam support, multimodal scoring, prefix-cache reads, or an OpenAI protocol field. Those can be evaluated separately if a concrete caller requires them.

This is complementary to open PR #39351 (generative scoring with `max_tokens=0`, which targets next-token scoring) and #49171 (skipping logits for unfinished chunk prefills). This PR scores arbitrary fixed IDs at selected prefill positions. No other open PR adds fixed-ID prefill scoring.

### Preemption

Preemption in the middle of a chunked prefill needs no special handling: the V2 scheduler reports a resumed request as a new one, and the runner drops the worker's state on preemption (`finish_requests` runs before `add_requests`), so the partial buffer is discarded and the re-prefill rebuilds it from the first chunk and emits it once. A resumed request whose prefill had already completed is the case that does need a guard:

A request resumed after preemption re-prefills its prompt plus the tokens it already generated. Those rows are not prompt positions, and its scores were emitted before the preemption, so the accumulator has to skip the resumed prefill — the same condition `compute_prompt_logprobs` already guards with `prompt_lens < prefill_len`. An earlier revision of this PR did not, which is not a silent numerical error: the resumed request emits a result on a step that must produce none, and the engine dies on the scheduler's own invariant.

```

AssertionError

### Performance

`Qwen3-30B-A3B-Thinking-2507`, TP4, 8192-token context, median of 5 reps, `prompt_logprob_start` set to score the last N rows:

| Scored rows x candidate IDs | median | vs baseline |
| --- | --- | --- |
| baseline (no scoring) | 75.2 ms | — |
| 1000 x 64 | 77.1 ms | +2.0 ms |
| 1000 x 242 | 77.7 ms | +2.6 ms |
| 1000 x 1024 | 80.6 ms | +5.5 ms |
| 4000 x 64 | 80.7 ms | +5.6 ms |
| 4000 x 242 | 81.7 ms | +6.6 ms |
| 4000 x 1024 | 88.9 ms | +13.7 ms |
| `prompt_logprobs=0`, all 8192 rows | 146.2 ms | +71.0 ms |

Row count dominates: at a fixed 64 IDs, going 1000 -> 4000 rows costs +3.6 ms, while at 1000 rows a 16x increase in candidates (64 -> 1024) costs +3.5 ms. In the intended distillation range the feature is roughly 10x cheaper than the existing full-row path while returning far more per row.

Cost grows with `rows x ids`, and at a wide candidate set it crosses over (separate run, baseline 76.6 ms):

| Scored rows x candidate IDs | median | vs baseline |
| --- | --- | --- |
| 4000 x 1024 | 89.6 ms | +13.0 ms |
| 4000 x 4096 | 108.4 ms | +31.7 ms |
| 4000 x 16384 | 176.0 ms | +99.4 ms |
| `prompt_logprobs=0`, all 8192 rows | 146.1 ms | +69.5 ms |

So 16384 candidates over 4000 rows costs more than scoring every row with `prompt_logprobs=0` — though it returns 16384 candidates per row rather than one target token. The crossover is around 40M `row x id` pairs; beyond that, callers should compare against the full-row path. This is another reason the ceiling is `max_logprobs` rather than a constant of our own: the operator who opens that gate is the one accepting the cost.

## Update 2026-09-20: partially scored prefills

A second review found that a prefill can begin past `prompt_logprob_start`, leaving the leading rows of the score buffer unwritten while the buffer is still emitted at its full shape. Two ways in: a caller passing `skip_reading_prefix_cache=False` explicitly (the force-set in `__post_init__` only applies when the flag is left `None`), and a streaming-input session, which extends its prompt in place and keeps its computed tokens, so the next prefill starts mid-prompt with `prefill_len == prompt_len`.

`prompt_logprobs` degrades on the same paths by returning fewer entries. This path was worse: the shape stayed correct and the leading rows carried uninitialized device memory. With the guard removed, the new regression test shows what a caller would have received:

```
array([[ 1.84094184e-40,  0.00000000e+00,  1.85467457e-40],
       [ 0.00000000e+00,  1.87048122e-40,  0.00000000e+00], ...
       [-2.19386425e+01, -2.27218456e+01, -2.54796581e+01]], dtype=float32)
```

The leading rows are denormals rather than log probabilities, and `exp` maps them to ~1.0 — the worst direction for a distillation target.

The worker now drops a request whose first scoring chunk starts past its first scored row (`chunk_start > req.start`), so the caller gets no scores rather than fabricated ones. This covers both entry points without an admission gate, and the condition is exact: a chunk starting before the first scored row still writes every scored row and is emitted as before.

Also in this update: `trace_decode_token_ids` rejects `prompt_logprob_token_ids` as it already rejects `prompt_logprobs`, and the row convention (row i predicts prompt token i+1, last prompt row excluded, result shape) is stated on the parameter and the result instead of only in the tests.

Verification: `tests/v1/sample/test_logprobs.py -k prompt_logprob_token_ids` 4 passed, correctness 10/10 on the same GB200 setup. The new test is a real regression test: with the guard removed it fails with the array above.

+# Prompt Token ID Logprobs (Teacher Scoring)
+
+In on-policy distillation, the student records its top-K candidate tokens at
+every response position, and the teacher provides the log probabilities of
+exactly those candidates as the distillation target. The caller passes the
+candidates as `prompt_logprob_token_ids`; the teacher runs a single prefill
+over the prompt plus response and gathers their log probabilities on the GPU at
+every scored row, starting from `prompt_logprob_start` (typically the prompt
+length minus one, so only response positions are scored). The result is a
+`[rows, K]` matrix whose row `i` scores prompt token
+`prompt_logprob_start + i + 1` and whose columns follow the candidate order, so
+it lines up position by position with the student's top-K.
+
+## Quick start
+
+```python
+from vllm import LLM, SamplingParams
+from vllm.inputs import TokensPrompt
+
+llm = LLM(model)
+output = llm.generate(
+    TokensPrompt(prompt_token_ids=prompt_ids + response_ids),
+    SamplingParams(
+        max_tokens=1,
+        prompt_logprob_token_ids=candidate_ids,
+        prompt_logprob_start=len(prompt_ids) - 1,
+    ),
+)
+scores = output[0].prompt_token_id_logprobs
+# scores.shape == (len(response_ids), len(candidate_ids))
+# scores[i, j] = log p(candidate_ids[j] | prompt_ids + response_ids[:i])
+```
+
+The same parameters are accepted by the `/inference/v1/generate` HTTP endpoint
+(Python and Rust frontends), which returns the matrix as a base64-encoded
+`.npy` float32 array:
+
+```python
+import base64, io
+import numpy as np
+
+scores = np.load(io.BytesIO(base64.b64decode(response["prompt_token_id_logprobs"])))
+```
+
+The matrix has `max(prompt_len - 1 - prompt_logprob_start, 0)` rows. With a
+logits `--logprobs-mode`, it holds logits instead of log probabilities.
+
+## Requirements
+
+- The V2 model runner (`VLLM_USE_V2_MODEL_RUNNER=1`).
+- `len(prompt_logprob_token_ids)` at most `--max-logprobs`.
+- No `--kv-sharing-fast-prefill`.
+
+The request skips reading the prefix cache (local and KV connector), since
+cached rows have no logits to score.
+
+## Limitations
+
+- One candidate set per request, shared by every scored row; per-position
+  candidates are planned ([#56860](https://github.com/vllm-project/vllm/issues/56860)).
+- Non-streaming only; `stream=true` requests are rejected.
+- Not exposed through the OpenAI-compatible endpoints.
+- If a prefill starts past the first scored row (e.g. `skip_reading_prefix_cache=False`
+  with a cache hit), the result is `None` rather than a partial matrix.
