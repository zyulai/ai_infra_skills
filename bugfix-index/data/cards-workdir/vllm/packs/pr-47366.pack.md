## 正文(PR 描述)

## Purpose

test_eagle_correctness_heavy builds a reference engine and a speculative engine back to back in one process, and its parametrized cases run sequentially. On the AMD "V1 e2e (4 GPUs)" step the TRITON_ATTN Llama-4-Scout cases (llama4_eagle, llama4_eagle_mm) aborted at engine init with HSA_STATUS_ERROR_OUT_OF_RESOURCES ("Available Free mem : 0 MB") right after CUDA graph capture, while the same model passed on ROCM_AITER_FA.

There are two independent problems, both fixed here:

1. Lazy VRAM reclaim between engines. ROCm frees VRAM lazily, so after cleanup_dist_env_and_memory() the next engine can start memory profiling while the previous engine's VRAM is still resident, read inflated free memory, and size the KV pool too large. Fixed by a wait_for_rocm_memory_to_settle() barrier after each engine teardown so the next engine profiles against a clean device (reuses the existing helper; no-op off ROCm).

2. CUDA graph capture memory not reserved on ROCm (root cause of the remaining OOM). The memory profiler skipped CUDA graph profiling on ROCm (#36720), so the KV cache was sized as if capture were free; capture then had to fit in the (1 - gpu_memory_utilization) slack, and when the fixed capture cost exceeded that slack, startup OOMed. #36720 skipped ROCm because torch.cuda.mem_get_info() and graph_pool_handle() produced incorrect/negative estimates. Both causes are gone: #44825 moved the profiler to torch.accelerator.get_memory_info (reliable on ROCm, already used by the AMD-CI mem tests), and graph_pool_handle resolves to the same torch.cuda handle the live capture path already uses on ROCm. So this re-enables CUDA graph memory profiling on ROCm; XPU stays excluded (#39977).

This supersedes the earlier per-model gpu_memory_utilization=0.85 override (addressing @AndreasKaratzas's review): the profiler now reserves capture memory automatically, which is portable across GPU sizes (a fixed byte cost, not a utilization ratio that maps to different absolute headroom on MI300 vs MI325). The override is removed in this PR.

AI assistance (Claude) was used to diagnose and implement this change. Not a duplicate: no open PR re-enables ROCm CUDA graph memory profiling (#46932 fixes negative estimates on NVIDIA unified-memory GPUs, a different platform and failure mode).

## Test Plan

```
pytest -v -s v1/e2e/spec_decode/test_spec_decode.py -k "eagle_correctness_heavy"
```

Hardware: AMD MI300 (gfx942), 4 GPUs, TP=4. Run with `VLLM_WORKER_MULTIPROC_METHOD=spawn`. Reproduced with the `TRITON_ATTN` cases run back to back (the CI ordering that failed).
