## Motivation

This PR improves Triton extend-attention performance for ragged mixed-prefill batches by adding an optional **compact query-tile launch grid**.

The legacy grid is rectangular and sized by `max_len_extend`:

```python
grid = (batch_size, head_num, ceil(max_len_extend / BLOCK_M))
```

In a mixed batch, every short decode/partial-prefill row pays tile work proportional to the longest extend row. The compact path launches only the actual per-request query tiles:

```python
grid = (compact_q_tiles, head_num)
compact_q_tiles = sum_i ceil(extend_len_i / BLOCK_M)
```

and falls back to the legacy grid when compacting would not reduce launch work.

**Framing — this closes a triton-vs-flash-attn gap, it is not a new technique.**
The flash-attention varlen kernels already launch ragged-aware: the aiter backend calls `flash_attn_varlen_func` / `mha_batch_prefill_func` with cu_seqlens (`qo_indptr` / `kv_indptr`), and their internal tile scheduler does work proportional to the *sum* of per-request query tiles — `max_q_len` is only a scalar bound, never a grid multiplier. So the aiter/flash-attn path does **not** pay the rectangular penalty. Only the **triton** extend kernel used a literal `(batch_size, head_num, cdiv(max_len_extend, BLOCK_M))` grid. This PR brings the triton extend kernel up to parity with that ragged-aware launching; it has no effect on (and is not needed for) the aiter backend.

**Why this matters:** Ragged mixed-prefill is production-real. Live serving batches commonly combine requests with different prompt lengths, and mixed chunking combines decode rows with long prefill chunks in the same attention call.

**Platform scope:** The optimization is **AMD/HIP-only** to avoid impacting other vendors. Both the compact grid logic and the optional scheduler tile-budget admission are gated on `_is_hip` / `_IS_HIP`.

**Default behavior:** The feature is **enabled by default** on AMD/HIP platforms (`SGLANG_TRITON_COMPACT_EXTEND_ATTENTION=True`). To disable it for testing or comparison:
```bash
SGLANG_TRITON_COMPACT_EXTEND_ATTENTION=0
```

### Fixed-workload throughput, CUDA graphs ENABLED (mean of 3 seeds)

These are **end-to-end** measurements (prefill + decode) via `sglang.bench_serving` at `--request-rate inf` (all requests fired at once, closed-loop, to fixed-workload throughput). `Tok/s` is total end-to-end throughput; `TTFT` is the prefill latency; `TPOT` is the per-output-token (decode) latency.

**Workload notation `<INPUT>/<OUTPUT>, <N> req`:** `INPUT`/`OUTPUT` are the input and output length parameters, `N` is the number of requests (`--num-prompts`). Actual lengths are sampled uniformly from `[len * range_ratio, len]`:
- **Ragged** = `--random-range-ratio 0.5` → lengths vary (e.g. `4096/128` → inputs in [2048, 4096], outputs in [64, 128], i.e. **64–128 decode iterations** per request).
- **Uniform** = `--random-range-ratio 1.0` → every request is exactly `INPUT`/`OUTPUT` (e.g. `4096/128` → all inputs 4096, all outputs 128).

| Workload | Compact tok/s | Default tok/s | Tok/s delta | TTFT delta | TPOT delta |
|----------|--------------|---------------|-------------|------------|------------|
| Ragged 4096/128, 64 req † | **49,877** | 14,581 | **+242.0%** | -67.2% | -76.2% |
| Ragged 8192/64, 32 req | **50,223** | 16,673 | **+201.2%** | -63.1% | -71.3% |
| Uniform 4096/128, 64 req | **49,610** | 11,976 | **+314.2%** | -72.4% | -80.0% |

**Variance:** Total tok/s CV ≤ 2.5% across 3 seeds — the gap is not seed noise.

**Why graphs matter:** The default path barely improves with graphs because its bottleneck is the rectangular *prefill* grid (not graph-captured). The compact path removes that waste, letting decode graphs take effect.

### Open-loop traffic, production-shaped arrivals

This is the realistic SLA story. With a fixed offered rate of **8 req/s** (CUDA graphs ENABLED, the default deployment), the legacy Triton path cannot keep up — it drains only **3.48 req/s**, so the queue builds and latency collapses. With the compact grid, the *same server on the same hardware* sustains the offered load at sub-second latency.

Config: `--request-rate 8 --max-concurrency 64 --random-input-len 4096 --random-output-len 128 --random-range-ratio 0.5 --num-prompts 128`

### DeepSeek R1 MXFP4 prefill-only validation 

**Test Environment:**
- Model: `amd/DeepSeek-R1-MXFP4` (Quark MXFP4 quantization, DeepSeek V3 architecture, 671B parameters)
- Hardware: 4× AMD MI355X (gfx950), TP=4
- Backend: `--attention-backend triton`
- Requires `forward_mla.py` w_kc None guards for Quark MXFP4
- Workload: **Prefill-only** (large input, 1 output token) — the PR's optimization target

**Open-loop traffic benchmark (4 req/s arrival rate, 64 requests):**

| Metric | Baseline | Compact | Delta |
|--------|----------|---------|-------|
| Sustained throughput | 15,810 tok/s | 16,181 tok/s | +2.4% |
| Sustained request rate | 3.92 req/s | 4.01 req/s | +2.3% |
| Mean latency | 1.25s | 0.83s | -33.8% |
| P50 latency | 1.01s | 0.73s | -27.6% |
| P99 latency | 3.16s | 2.69s | -14.8% |

**Key Findings:**

1. **Compact provides measurable benefit for prefill**: +2.4% throughput, -33.8% mean latency
2. **Both modes sustain 4 req/s** (baseline at 98%, compact at 100% utilization)
3. **Much smaller gain than Qwen** (+2.4% vs +154%) because:
   - Attention is only **12% of DeepSeek prefill time** (profiler-measured)
   - Communication (**42%**) and MoE (**34%**) dominate
   - 671B MXFP4 is memory-bandwidth-bound

**Why Latency Improvement is Larger Than Throughput:**

The -33.8% latency improvement vs +2.4% throughput makes sense:
- At 4 req/s (near saturation), baseline starts queueing requests
- Compact's 2.4% efficiency gain reduces queue wait time disproportionately
- Throughput improvement is limited by system bottlenecks (communication, MoE)
- Latency improvement reflects reduced queueing delays

**Profiling Breakdown (prefill-only, PyTorch profiler):**

Component breakdown for DeepSeek R1 MXFP4 prefill (TP=4, 4096 input tokens):
- **Communication (TP all-reduce)**: 42% (22.85ms)
- **MoE compute**: 34% (18.46ms)
- **Attention (extend_attention)**: **12%** (6.56ms) ← PR's optimization target
- **Weight loading + dequantization**: 12% (6.66ms)

Even in prefill (this PR's target), attention is only ~12% of execution time. A 50-67% reduction in attention tiles (compact grid) would theoretically save 3.3-4.4ms out of 54.5ms (~6-8% end-to-end speedup). The observed +2.4% reflects that:
1. Tile reduction doesn't eliminate 100% of wasted compute
2. DeepSeek R1 is memory-bandwidth-bound, not compute-bound
3. Communication and MoE dominate, not attention

**Mixed Workload Results:**

A testing with 1 prefill + 10 decode iterations showed minimal benefit (+0.1% throughput) because prefill attention is only a small fraction of the overall E2E time when combined with decode. The prefill-only test above correctly isolates the PR's optimization target and shows the measurable +2.4% throughput gain on prefill workloads.

**Conclusion:**

The optimization **works as designed** and provides measurable benefit (+2.4% throughput, -33.8% latency) on DeepSeek R1 MXFP4 prefill workloads, but the gain is modest compared to smaller models because DeepSeek R1's unique architecture (massive MoE + TP communication) means attention is only 12% of prefill time. The compact grid successfully reduces wasted tile launches, but this translates to limited end-to-end impact when the model is dominated by communication and MoE compute rather than attention.

### Caveats

- Large serving wins are for the **Triton** attention backend under mixed prefill. They should not be claimed for the AITER / DeepSeek-R1-MXFP4 path; on that path (uniform 70k prompts, AITER, speculative decode) end-to-end movement is modest, which is expected since the PR targets the Triton extend grid.
