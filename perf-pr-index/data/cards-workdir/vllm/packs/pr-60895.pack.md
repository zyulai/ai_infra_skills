## Overview

Run GLM-5.3-Flash's MoE layers with DeepGEMM's FP8xFP8 MegaMoE (routed and shared experts in one kernel that also dispatches and combines across the EP group), using the official FP8 checkpoint. Enabled by `--kernel-config '{"moe_backend":"deep_gemm_mega_moe"}'` with `--tensor-parallel-size 1 --data-parallel-size N --enable-expert-parallel`.

Related: #55275 (BF16 / MXFP4 MegaMoE for GLM, open), #54049 (FlashInfer NVFP4 mega kernel).

## Claims

- On the AgentX replay at concurrency 96, DEP4 with MegaMoE gives 1.6x the output throughput of DEP4 on the generic MoE path.
- Against TP4 it is about level on throughput (+6%, one run each) and has about a fifth of the TTFT.
- It prefills 1.8x faster than DEP4 generic and 2.5x faster than TP4.
- AIME 2026 Pass@1 matches the generic MoE path (0.934 vs 0.939 with a 131K output cap) and is 0.977 with the 1M context.
- A weight reload, in layerwise or direct mode, restores byte-identical weights at the same addresses.
- No change for any other `moe_backend`.

## Details

- The checkpoint's experts are block FP8 (E4M3, one float32 scale per 128x128 block). DeepGEMM's SM100 MegaMoE feeds scales to the block-scaled MMA and needs UE8M0 scales per row and 32 columns, so the routed and shared expert weights are requantized once at load (`requant_block_fp8_to_ue8m0`).
- This requantization is lossy: about 2.4% relative L2 per weight tensor and about 3.9% on one MoE layer's output (layer 15, real weights, random inputs). The generic TRTLLM path uses the checkpoint's scales as they are. The GSM8K gap above is within one standard error.
- Routing stays outside the kernel: `fused_topk_bias` (sigmoid, score correction bias), with `routed_scaling_factor` folded into the top-k weights. DeepGEMM's Mega Gate only supports `sqrtsoftplus`.
- `Glm5NextMegaMoEExperts` subclasses `DeepGemmMegaMoEExperts`, which is unchanged, with the `MEGA_MOE_MXFP8` format. E4M3 shards load straight into the kernel layout; their float32 block scales are staged in `*_weight_scale_inv`, and the model's `process_weights_after_loading` calls `requantize_block_fp8()`, which rounds every newly loaded shard to UE8M0 1x32 scales in place (main model, multimodal wrapper and MTP drafter).
- A weight update may send an expert weight and its block scale in separate `load_weights` calls; by the end of the load both must be in, or `requantize_block_fp8()` raises.
- Reload and weight transfer finish with that hook (#64357, and direct mode from #64336), so the kernel tensors keep their storage. The derived UE8M0 scales are marked `weight_loader_numel = 0`, so a layerwise reload replays a layer as soon as its checkpoint tensors are in.
- The block-FP8 shared expert is fused the same way: the experts own its weights and the model builds no shared MLP.
- `--prefix-match-unit` matters for this model independently of this PR: the KDA state page makes the KV block 8,960 tokens under DEP4, and without the flag prefix hits land on whole blocks.
- Limitations: `tensor_parallel_size=1` only; SM100 only; no sharded RDT or sparse NCCL updates. Under DEP4 each rank holds 8.8M KV tokens.

+def _block_fp8(real: torch.Tensor, power_of_two: bool = False):
+    """Quantize ``(..., mn, k)`` to E4M3 with one float32 scale per 128x128."""
+    *lead, mn, k = real.shape
+    blocks = real.reshape(*lead, mn // 128, 128, k // 128, 128)
+    scale = blocks.abs().amax(dim=(-3, -1)) / 448.0
+    if power_of_two:
+        scale = torch.exp2(torch.ceil(torch.log2(scale)))
+    full = scale.repeat_interleave(128, -2).repeat_interleave(128, -1)
+    return (real / full).to(FP8), scale

+class Glm5NextMegaMoEExperts(DeepGemmMegaMoEExperts):
+    """MXFP8 MegaMoE experts loaded from GLM-5.3-Flash's block-FP8 checkpoint.
+
+    The checkpoint stores E4M3 weights with one float32 scale per
+    ``weight_block_size`` block; the kernel takes power-of-two UE8M0 scales per

+    stages its block scale in ``*_weight_scale_inv``. Once a load is complete,
+    the model's ``process_weights_after_loading`` calls
+    :meth:`requantize_block_fp8`, which rounds every newly loaded shard to the
+    kernel scales in place. The shared expert is fused the same way.

+
+    def __init__(
+        self,
+        vllm_config: VllmConfig,
+        *,
+        weight_block_size: tuple[int, int],
+        num_shared_experts: int = 0,
+        **kwargs,
+    ):

+        self._num_fused_shared_experts = num_shared_experts
+        # Shards whose weight / block scale arrived since the last requantize.
+        self._new_weights: set[Shard] = set()
+        self._new_scales: set[Shard] = set()
+        super().__init__(vllm_config, weight_format=MEGA_MOE_MXFP8, **kwargs)
+
+    def _fusable_shared_experts(
+        self, shared_experts: nn.Module | None

+        n = self._num_fused_shared_experts

+    def _create_weights(self) -> None:
+        super()._create_weights()

+        self._register_block_scale("w13", (e, 2 * i, h))
+        self._register_block_scale("w2", (e, h, i))
+        if self.has_fused_shared_experts:

+            self._register_block_scale("shared_l1", (2 * s, h))
+            self._register_block_scale("shared_l2", (h, s))

+    def _register_block_scale(self, name: str, shape: tuple[int, ...]) -> None:
+        """Stage the checkpoint's float32 block scales of ``name``. The kernel's
+        ``{name}_weight_scale`` is derived from them and never loaded."""

+        raw = torch.stack(

+                self._kernel_layout_shard(w, w, shard_id, False)[0].reshape(

+                "weights as they are.",
+                *self.weight_block_size,
+            )
