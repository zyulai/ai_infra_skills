## Motivation

Found while adding Beam (#44747), split out of #45256 at review because it is not specific to Beam.

MegaMoE's per-call cost scales with workspace capacity. Startup autotuning prepares small-capacity profiles for decode, but with it off (`--disable-flashinfer-autotune`, or `--flashinfer-autotune-skip-ops flashinfer_megamoe`) every forward uses the main workspace, so small decode batches pay for the full capacity.

Earlier revisions of this PR also fixed MegaMoE startup autotune. That is no longer part of it: the FlashInfer 0.7.3 fixes (enum config fields in the cache key, knob-cache version 2) landed in #49096, and the FlashInfer 0.7.2 output-buffer workaround is not needed on 0.7.3.

## Modifications

- **Optional decode workspace** (`SGLANG_FLASHINFER_MEGAMOE_DECODE_MAX_TOKENS_PER_RANK`):
  - `0`, the default, is off. A positive value is the per-rank capacity of a second workspace profile on the same MegaMoE layer. Only ModelOpt NVFP4 MoE layers request it; that includes `nvfp4_online` and hybrid FP8 + NVFP4 MoE checkpoints, whose MoE layers use the same method.
  - `MegaMoeTunedForward` owns it. The workspace is created on the layer's first forward that runs without startup tuning, and only such untuned forwards use it. Once startup tuning has prepared a layer's profiles, every forward uses them, and tuning after an ordinary forward is already rejected, so the decode workspace never coexists with a tuned capacity. Whether it is used therefore follows whether MegaMoE tuning actually ran for the layer, not when the layer was built: it applies with `--disable-flashinfer-autotune`, `--flashinfer-autotune-skip-ops flashinfer_megamoe` and on draft workers, and is unused (logged once per rank) under default startup autotuning.
  - A forward uses it only when no DP rank extends and every rank's DP-gathered token count fits; otherwise it uses the main workspace. All ranks read the same gathered counts, so they choose the same profile.
- **One forward helper**: `forward_megamoe` in `flashinfer_megamoe_autotune.py` serves the plain path, the tuned profiles and the decode workspace. It passes `return_workspace_view=True` only when the backend supports output views.
- **Startup validation** in `handle_a2a_moe`, during server-args resolution and before weights load:
  - A negative value, or one not below a positive `SGLANG_FLASHINFER_MEGAMOE_MAX_TOKENS_PER_RANK`, raises. When that variable is `0` or unset the main capacity is derived, and the comparison runs when the first MegaMoE layer is built.
  - A warning when the MoE layers do not take the ModelOpt NVFP4 path (e.g. MXFP8 or FP4-expert FP8), since nothing else builds the decode workspace.
- Documented in `environment_variables.mdx`.

## Accuracy Tests

4x GB300 per node, FlashInfer 0.7.3, torch 2.14.1+cu130. The runs used e9a6eb18b5; the later commits change only a comment, the docs and the tests. `reflection/Beam-1.0-501B-A23B-NVFP4` (c5621fc926) on the cookbook high-throughput recipe: TP4, attention DP4, `--enable-dp-lm-head`, EP4, `modelopt_fp4`, `flashinfer_megamoe` for both the all-to-all and the runner, `trtllm_mha`, page size 64, CUDA graphs and overlap on, no speculative decoding. GSM8K is sgl-eval 0.1.3, 1,319 questions, temperature 0.

| Configuration | GSM8K |
|---|---:|
| Autotune off, decode workspace off | 95.98% |
| Autotune off, decode workspace 64 | 96.29% |
| MegaMoE autotune skipped (`--flashinfer-autotune-skip-ops flashinfer_megamoe`), decode workspace 64 | 96.13% |
| Default autotune, cold tuning cache, decode workspace 64 set | 96.44% |

With MegaMoE autotune skipped, no MegaMoE profile was tuned. With default autotune, all 14 capacities were tuned, every rank logged the decode workspace as unused, and no duplicate-capacity error occurred. The four scores span 0.46 points (6 of 1,319 questions); outputs were not compared token by token. Every run also passed a 10-request smoke check.

Startup validation, same setup: `SGLANG_FLASHINFER_MEGAMOE_DECODE_MAX_TOKENS_PER_RANK=-1` exits during argument resolution with `ValueError: SGLANG_FLASHINFER_MEGAMOE_DECODE_MAX_TOKENS_PER_RANK=-1 must be 0 (off) or positive.`, and `=64` with `SGLANG_FLASHINFER_MEGAMOE_MAX_TOKENS_PER_RANK=64` exits with `... must be below SGLANG_FLASHINFER_MEGAMOE_MAX_TOKENS_PER_RANK=64.` Neither loads weights.

Unit tests: `test_flashinfer_megamoe.py`, `test_flashinfer_autotune_sync.py` and `TestFlashinferMegaMoeConfig` in `test_server_args.py` pass on GB300 with FlashInfer 0.7.3 (47 passed, 23 subtests); `test_flashinfer_megamoe.py` also passes on CPU (29 passed). No unit test covers the decode workspace.

## Speed Tests and Profiling

Same setup. `sglang.benchmark.serving` with ShareGPT prompts, 512 output tokens, temperature 0; median TPOT in ms. The autotune-off rows were run twice, back to back on one node; the other two rows ran once on a second node.

| Configuration | c=1 | c=16 | c=64 |
|---|---:|---:|---:|
| Autotune off, decode workspace off | 12.37, 12.37 | 15.94, 15.98 | 20.66, 20.46 |
| Autotune off, decode workspace 64 | 6.94, 6.94 | 10.59, 10.61 | 15.06, 14.98 |
| MegaMoE autotune skipped, decode workspace 64 | 7.07 | 10.71 | 15.12 |
| Default autotune, cold tuning cache, decode workspace 64 set (unused) | 7.10 | 10.67 | 15.20 |

- With autotune off, a 64-token decode workspace makes decode 1.78x, 1.51x and 1.37x faster at c=1, 16 and 64 (ratios of the two-run means). At most 64 requests were in flight across the 4 DP ranks, with no speculative decoding, so every decode batch fit the 64-token profile.
- With only MegaMoE tuning skipped, the decode workspace gives similar TPOT. With default autotune it is unused, and the tuned profiles give similar decode TPOT. What the workspace trades is startup time: the autotune-off servers were ready in 105 s and 120 s, against 900 s for the cold tune.
- A temporary instrumentation of FlashInfer's `MoEEpMegaLayer.create_workspace` and of the decode-workspace selection (same recipe, decode workspace 64) traced the lifecycle. With autotune off, one 64-token workspace was created per MoE layer per rank (196 = 49 layers x 4 ranks), all before CUDA graph capture. Decode graphs for 1-64 tokens per rank were captured with it, the larger ones (72 tokens per rank and up) with the main workspace, and eager prefill forwards used the main workspace. With default autotune, only the 14 tuned capacities were created (196 each, including 64), none during capture, and the untuned path, and so the decode workspace, was never used. Both runs passed the 10-request smoke check with no errors.
