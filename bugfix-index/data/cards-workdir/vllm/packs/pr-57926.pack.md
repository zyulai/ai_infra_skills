## 正文(PR 描述)

## The gap

`profile_run` builds its dummy batch with `InputBatch.make_dummy`, which registers no sampling parameters. Every dummy request therefore leaves `Sampler.needs_logits_processing` False, so `apply_sampling_params` takes its early exit:

```python
if not np.any(self.needs_logits_processing[idx_mapping_np]):
```

and the fp32 logits upcast — plus the logit-bias, penalty and bad-words work behind it — never enters the profiled peak. The KV cache is then sized against a sampler that costs less than the real one.

`warmup_kernels` runs **after** the KV cache has been allocated and uses `SamplingParams.for_sampler_warmup()`, which does engage those parameters. So the first time the expensive path is exercised is the one moment when nothing can be given back, and it can OOM there.

The existing `NOTE(woosuk)` in `_dummy_sampler_run` documents this exact gap. This closes it by profiling with the same helper the warm-up uses, so the two stay in step if that path grows more work later.

## Measurements

One L4 24GB, `Qwen/Qwen2.5-0.5B-Instruct`, `max_num_seqs=256`, `VLLM_USE_V2_MODEL_RUNNER=1`, `max_model_len=2048`. Only this patch differs between the two columns.

| `gpu_memory_utilization` | KV cache before | after | delta |
|---|---|---|---|
| 0.98 | 1,733,440 tokens | 1,710,928 tokens | -1.30% |
| 0.97 | 1,714,176 tokens | 1,691,680 tokens | -1.31% |

The profiler now reserves what the sampler actually costs, so the cache it hands out is smaller by that amount. These four numbers reproduced digit-for-digit on a re-run against current `main`.

### On the OOM, stated precisely

An earlier run - on a different L4, against vLLM 0.29.0 rather than current `main` - had the unpatched build fail outright at 0.98:

```
File "vllm/v1/worker/gpu/warmup.py", line 348, in warmup_kernels
File "vllm/v1/worker/gpu/sample/sampler.py", line 222, in apply_sampling_params
    logits = torch.empty_like(logits, dtype=torch.float32).copy_(logits)
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 150.00 MiB.
GPU 0 has a total capacity of 22.04 GiB of which 127.12 MiB is free.
```

Re-running that A/B against current `main`, **I could not reproduce the hard failure**: both builds start, the unpatched one simply lands closer to the edge (with `enforce_eager=True` it emits a non-fatal `CUDACachingAllocator` OOM and recovers). An earlier revision of this description presented "OOM before, starts after" as the headline result; that overstated it. Read this instead as the profiler under-reporting a real cost, which makes startup fragile near the top of the utilization range. The case rests on the tests below, not on that traceback.

## Cost

KV cache capacity drops about 1.3% at a given `gpu_memory_utilization`, because the profiler now reserves memory it was previously handing to the cache. That is the intended trade: the budget the profiler hands out becomes one the warm-up can actually live within.

## Scope

MRv2 only (`vllm/v1/worker/gpu/model_runner.py`). The MRv1 runner reaches the same wall from a different direction — its sampler warm-up sits after `capture_model` in `gpu_worker.py` — and is not touched here.

This is narrower than #51590, which corrects the CUDA-graph memory estimate. The two are complementary: that PR fixes how much the graph pool is predicted to take, this fixes what the sampler is predicted to take. Neither subsumes the other.

Also reproduced independently on 8x RTX PRO 4500 (32GB, SM120) with gpt-oss-120b MXFP4 at TP=8, where the same class of failure appears at `gpu_memory_utilization=0.95` and clears at 0.90.

### The new tests fail without the change

This is the part worth checking. With the production hunk reverted to its parent and the test files left in place:

```
this branch          3 passed
change reverted      3 failed
```

- `test_gpu_model_runner_v2.py::test_dummy_sampler_run_registers_warmup_params_before_sampling` - CPU only. Asserts every dummy request is registered with `SamplingParams.for_sampler_warmup()` and that `apply_staged_writes()` runs after all of them and before the sampler. The ordering is the point: flush late and the profiled run does not see the params.
- `test_gpu_model_runner_v2_sampler_profiling.py::test_dummy_sampler_run_profiles_the_path_the_warmup_takes` - wires the real `Sampler`, real `InputBuffers` and a probe `LogitsProcessor`. Unpatched the pipeline never runs (`applied_dtypes == []`); patched it runs on the fp32 copy, and the peak grows by at least the size of that copy.
- `test_gpu_model_runner_v2_sampler_profiling.py::test_profiling_residue_does_not_put_serving_on_the_expensive_path` - pins down why no cleanup is needed: a slot is rewritten from the arriving request's own params before anything reads it.

### On not restoring the sampler state

An earlier revision wrapped the profiling in `try/finally` and restored `needs_logits_processing`. That is gone, deliberately. It ran *after* the sampler call, so it never affected the profiled peak; it restored one of the six structures `Sampler.add_request` writes, and not the ones (`top_k`, `top_p`, `temperature`) that are read outside the `needs_logits_processing` gate; and `warmup_kernels` recreates identical residue moments later through the real `add_requests` path, which mainline has always accepted.

No model-evaluation results are included because this change does not alter sampling behaviour or model output - it changes what the memory profiler accounts for, and therefore how large the KV cache is.

If maintainers want other suites run, name them and the results will be posted here.
