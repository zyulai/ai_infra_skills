## 正文(PRD / 提案全文)

### Motivation.

Goal: Implement a solution for getting hidden states from any model layer out of vLLM in a performant way.

Speculative decoding algorithms such as Eagle3 and DFlash take “verifier” model hidden states (from multiple layers) as input. Therefore, training these “draft” models requires a dataset of hidden states, with corresponding tokens. Currently vLLM provides no official approach to extracting these hidden states. In addition, access to hidden states enables research work in RL ([example](https://github.com/hf618/VERL)) and quantization domains.

Existing solutions to this problem typically fall into one of the following categories.

1. Use transformers for hidden states generation. This has two major disadvantages: It loses all of vllm’s performance optimizations, large model/distributed support, etc. and it opens a whole class of potential bugs caused by minor mismatches between transformer and vllm hidden states.
2. Heavy modification and patching of vllm to enable this feature. Solutions typically require manually setting up core vllm components and accessing internal apis. This produces a large maintenance burden as vllm internals are updated. It also means many vllm features (such as prefix caching, auto batching, async server, etc.) are usually disabled to make this possible. [Example 1: vllm-project/speculators](https://github.com/vllm-project/speculators/tree/main/src/speculators/data_generation), [Example 2: hf618/VERL](https://github.com/hf618/VERL/tree/main/hidden_vllm)

In addition to this, a growing area of research for speculative decoding is to regenerate dataset responses using the verifier model, which improves draft model acceptance rates once trained. Currently, this requires a two step process of generating the full responses and then getting the hidden states from the final sequences. A solution that can generate new text while returning hidden states would greatly improve this process.

There have been previous attempts to enable this functionality in vLLM which have failed (because they negatively impact hotpath performance or add too much complexity) [#15434](https://github.com/vllm-project/vllm/pull/15434) or are limited in scope to only the last layer [#24288](https://github.com/vllm-project/vllm/issues/24288) or only pooling models [#26686](https://github.com/vllm-project/vllm/pull/26686).

From this previous work, we’ve determined the following requirements:
- Zero performance cost when disabled
- Minimal added technical complexity in vLLM
- Memory management/allocation for hidden states
- Efficient transfer of hidden states between processes (non-blocking)

### Proposed Change.

Our proposed solution is based on a few key insights:
1. There is already a system (aux_hidden_states) for plumbing hidden states from verifier model layers to Eagle3 draft models (this is used by Eagle3/DFlash inference).
2. There is an extensible public api KV Connector for extracting kv cache data out of vllm with existing implementations for storing to disk, offloading to cpu memory, disagg P/D, etc.
3. Hidden states map to token sequences (1-to-1) in the same way that the KV caches do. This also means that a prefix of hidden states can be reused in the same way that KV cache prefixes are reused.
4. Hidden states are typically the similar sizes to (full attention) K/V states (just reshaped) or a multiple thereof. There also is support in vLLM for non-uniform kv cache page sizes across different layers. 

Therefore, the suggested approach is to create a dummy Eagle3 model which receives the hidden states and stores them in KV caches for dummy attention layers. These can then be extracted efficiently using the KV Connector interface. The dummy Eagle3 model returns a random token prediction (e.g. token 0), which will be rejected by the verifier model.

**We have developed a [working PoC of this approach here](https://github.com/fynnsu/vllm-hidden-states-extractor), using vllm’s plugin system to register all required components. Please note that the current implementation works entirely out-of-tree without requiring any changes to vLLM. Although we can continue to develop and stabilize this system as a vLLM plugin, we wanted to use the RFC to:**

1. Get feedback on the general approach (are there any potential pitfalls, design improvements, etc.?)
2. Determine what would be required to move this (or parts of this) in-tree

FAQ:

**Why insert the hidden states into the KV cache?**

Although we recognize that this is not the intended purpose of the KV cache, it is actually well suited for storing hidden states. 

For performance reasons we’d like to enable vLLM features like the async server, chunked prefill, continuous batching, prefix caching etc. Something like chunked prefill works okay if we have a single synchronous batch and we just concatenate the returned hidden states into one long tensor. However, if we have multiple training processes making requests at the same time then keeping track of which hidden states belong to which request becomes more complicated. The memory requirements for the hidden states also grows and we run into the same memory fragmentation problem that inspired the initial PagedAttention algorithm. Secondly, as mentioned the memory requirements for these hidden states are substantial. By storing the hidden states in the kv cache, we ensure that vLLM accounts for their storage when allocating blocks.

**What if the shapes don’t match?**

[#25101](https://github.com/vllm-project/vllm/pull/25101) solves this issue by allowing layers to have different hidden dimensions, which was in part implemented to explicitly support Eagle3 models with different num_kv_heads ([#22432](https://github.com/vllm-project/vllm/issues/22432)). This should make it possible for the layers to be sized in a way that accommodates the multiple hidden layers. For Eagle3 training we typically require hidden states from 4 layers (3 as input to the model, 1 to recompute target distribution), which is what the PoC currently extracts.

**Which layers can we extract from**

Using the the `eagle_aux_hidden_state_layer_ids` config option, we can select any layers (and any number of layers) from the model to collect the hidden states from.
