## 正文(PR 描述)

CO-OWNER: @bingxche 

## Motivation

On ROCm AITER, the GPT-OSS MXFP4 fused-MoE path was producing silently wrong outputs. With these server flags on MI355X (gfx950):

```bash
SGLANG_USE_AITER_MOE_GU_ITLV=False python3 -m sglang.launch_server \
  --model-path /path/to/gpt-oss-120b/ \
  --tp 1 --trust-remote-code \
  --mem-fraction-static 0.85 \
  --prefill-attention-backend aiter --decode-attention-backend aiter \
  --page-size 64 --disable-radix-cache --port 8000
```

the AITER dispatcher was selecting `module_moe_ck2stages_b16_fp4x2_preshuffle_off_b16_swiglu_per_1x32_mulWeightStage2`, a `preshuffle_off` codegen kernel. But the weights had already been preshuffled by `Mxfp4MoEMethod.process_weights_after_loading`, so the kernel interpreted shuffled bytes as un-shuffled and the model emitted nonsense. lm_eval gsm8k `flexible-extract` dropped from ~0.88 to ~0.21.

There were two root causes:

1. **Wrong shuffle layout.** The old path used `shuffle_weight_a16w4(..., 16, True)` / `shuffle_scale_a16w4(...)`, which produce the **gate/up-interleaved** tile layout (`is_guinterleave=True`). The AITER MXFP4 fused-MoE kernels tuned for GPT-OSS — both the FlyDSL `flydsl_moe1_afp4_wfp4_bf16_*` entries in `gptoss_fp4_tuned_fmoe.csv` (which have `gate_mode="separated"`) and the CK `module_moe_ck2stages_*_preshuffle_on_*` fallback — expect the **separated** (`is_guinterleave=False`) layout, identical to what ATOM uses on the same hardware.

2. **`is_shuffled` flag never set.** `shuffle_weight_a16w4` returns a tensor with `.is_shuffled=True`, but the call site did `layer.w13_weight.data = shuffle_weight_a16w4(...)`. Assigning to `.data` does not copy custom Python attributes, so `layer.w13_weight.is_shuffled` stayed unset. `aiter.fused_moe` reads this via `getattr(w1, "is_shuffled", False)` and, seeing `False`, dispatches the `preshuffle_off` codegen — which assumes the weight bytes are *not* shuffled. With actually-shuffled bytes, this gives garbage output.

The two bugs interact: even if the layout had been correct, the missing `is_shuffled` flag would still have routed to the wrong codegen branch.

## Modifications

- **`Mxfp4MoEMethod.process_weights_after_loading` (`_use_aiter` branch)** — replace `shuffle_weight_a16w4` / `shuffle_scale_a16w4` with `shuffle_weight(..., is_guinterleave=False, gate_up=...)` / `shuffle_scale(..., is_guinterleave=False, gate_up=...)`. This matches the layout `gptoss_fp4_tuned_fmoe.csv` flydsl entries (e.g. `flydsl_moe1_afp4_wfp4_bf16_t32x128x256_w2`) were tuned against, and the same layout ATOM produces. Set `layer.w13_weight.is_shuffled = True` and `layer.w2_weight.is_shuffled = True` after shuffling so AITER picks the `preshuffle_on` codegen.

- **`Mxfp4MoEMethod.apply` (`_use_aiter` branch)** — after `layer.w13_weight.view(torch.float4_e2m1fn_x2)`, re-tag the new view with `is_shuffled = True` (the `.view()` produces a fresh tensor that drops Python attributes). Also forward `swiglu_limit=self.moe_runner_config.swiglu_limit or 0.0` to `AiterMoeQuantInfo` so the OAI swiglu clamp gets through to AITER.

- **`AiterRunnerCore.run`** — gate the `GateMode.INTERLEAVE` selection behind a new env var `SGLANG_USE_AITER_MOE_GU_ITLV` and default to `GateMode.SEPARATED`. The default matches the new weight layout and the gptoss_fp4 tuned config; the env var is only for the rare case where someone shuffles weights into the gate/up-interleaved layout on purpose.

- **`environ.py`** — register `SGLANG_USE_AITER_MOE_GU_ITLV = EnvBool(False)` in the AMD & ROCm section.

## Accuracy Tests

Verified with `lm_eval gsm8k --num_fewshot 3` on gpt-oss-120b @ MI355X:

```bash
lm_eval --model local-chat-completions --apply_chat_template \
  --model_args model=/path/to/gpt-oss-120b/,base_url=http://localhost:8000/v1/chat/completions,num_concurrent=65,max_retries=3,max_gen_toks=2048,tokenized_requests=False \
  --tasks gsm8k --num_fewshot 3
```

| Filter | Before this PR (SGLang) | After this PR (SGLang) | ATOM baseline |
|---|---|---|---|
| `flexible-extract` | ~0.21 (broken) | **0.8810 ± 0.0089** | 0.8825 ± 0.0089 |
| `strict-match` | — | **0.3541 ± 0.0132** | 0.3487 ± 0.0131 |

Both post-fix numbers are within one standard error of ATOM, the working baseline on the same hardware / aiter commit. To cross-check that the fused-MoE inputs really are bit-identical between the two stacks after the fix, I instrumented `aiter.fused_moe.fused_moe_` to dump byte-level signatures of `w1`, `w2`, `w1_scale`, `w2_scale`, `bias1`, `bias2`, `is_shuffled`, etc. for the first two MoE calls per process, and ran both ATOM (`./run_gpt-oss.sh`) and SGLang back-to-back with the same model. Layer 0 and layer 1 produced identical `bytesum` and `head8` for every weight/scale/bias tensor between the two, and `is_shuffled=True` on both sides.

## Speed Tests and Profiling

No perf regression expected — this PR only changes the *layout* of the MXFP4 weights produced at load time and the `is_shuffled` flag carried into AITER. The kernels picked at runtime are the same family (`flydsl_moe1_afp4_wfp4_bf16_*` for `M >= 256`, CK `module_moe_ck2stages_*_preshuffle_on_*` for small-M decode), only now they receive correctly-laid-out inputs. No new ops, no extra copies.

Sample kernel selection from a server log on MI355X (gfx950, `--max-running-requests 128`):

```
[fused_moe] using 2stage (kernelName1='flydsl_moe1_afp4_wfp4_bf16_t64x128x256_w4_bnt0',
  kernelName2='flydsl_moe2_afp4_wfp4_bf16_t64x128x256_atomic') for (256, 16384, 3072, 3072, 128, 4, Swiglu, bf16, fp4x2, fp4x2, per_1x32, True, False)
[fused_moe] using 2stage default for (256, <small M>, 3072, 3072, 128, 4, Swiglu, bf16, bf16, fp4x2, per_1x32, True, False)
```
