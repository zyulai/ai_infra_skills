## Overview

#46849 runs all MRV2 autoregressive draft decode steps from one metadata build in one CUDA graph when every draft attention backend sets `supports_draft_decode_metadata_update`. `ROCM_AITER_UNIFIED_ATTN` does not, so EAGLE and MTP drafters on it log

```
Attention backend(s) ROCM_AITER_UNIFIED_ATTN cannot update draft decode metadata in place; falling back to rebuilding attention metadata eagerly.
```

and rebuild the metadata on the host and replay one draft graph for each of the k−1 draft decode steps. Its metadata holds only views of buffers the fused loop keeps current plus step-invariant values, so this PR opts it in with a no-op `update_draft_decode_metadata`, as the Triton backend and FlashInfer trtllm-gen (#58371) do.

## Claims

- With `ROCM_AITER_UNIFIED_ATTN`, multi-step drafters run the fused draft decode loop, and the fallback line is no longer logged.
- On MI355X the draft decode loop, timed in isolation, takes 16–19% less time at k=3 (571 → 463 µs at batch 1, 697 → 585 µs at batch 8, 678 → 559 µs at batch 32) and 6–8% less at k=7 (1197 → 1108 µs, 1623 → 1530 µs, 1559 → 1464 µs). The saving per loop, 90–120 µs, does not grow with k.
- No end-to-end throughput gain is claimed. At k=3 serving throughput moves by +0.1% and +0.2% at concurrency 1 and 8, and by −0.6% at concurrency 32 (see Details for what the profiler shows there); at k=7 by +1.9%, −0.1% and −0.2%, within the variation between server instances.
- Output quality is unchanged: GSM8K accuracy at k=3 and k=7, GPQA accuracy of gpt-oss-20b at k=4, and acceptance length match main within run-to-run variation.

## Details

**Audit.** The builder inherits `RocmAttentionMetadataBuilder.build()`. Its metadata references the persistent buffers the fused loop keeps current (`seq_lens`, advanced in place, plus `block_table`, `slot_mapping` and `query_start_loc`), and its scalars do not change across draft steps: `max_seq_len` is fixed once per `propose()` to cover every draft step, and `max_query_len` is 1. It has no host plan (`scheduler_metadata` is `None`) and writes no builder-owned tensor; `build_for_cudagraph_capture` only fills the persistent `seq_lens` for capture. The draft decode tests check both properties: `build()` leaves every builder-owned tensor byte-identical, and after the in-place update the metadata equals a fresh build of the replayed batch.

**Scope.** Only `ROCM_AITER_UNIFIED_ATTN` changes; it is opt-in through `--attention-backend` on MI300/MI355 and the default on RDNA with AITER. `ROCM_ATTN` shares `build()` but runs different decode kernels that were not validated here, so it keeps the fallback. Draft-model speculation (`method=draft_model`) does not use this loop. #62749 adds a separate flag for the target model's decode build and composes with this change.

**Concurrency 32.** The serving runs above are blocked by arm, so the state of each server instance is confounded with the arm. Torch profiler runs with the arms interleaved and the order balanced (five servers per arm, 60 steady decode steps each) show no per-step difference:

| per step, median over servers | main | this PR |
|---|---:|---:|
| step | 7432 µs | 7431 µs |
| draft decode segment | 588 µs | 583 µs |
| idle gaps between draft steps | 4.4 µs | 0 µs |
| target `lm_head` GEMM | 241 µs (237–284) | 241 µs (231–292) |

The draft decode segment is faster in every run because the gaps between draft steps disappear. The only kernel whose time moves is the target model's `lm_head` GEMM, which nothing in this change runs alongside; its time varies between server instances by up to 25% in both arms. The −0.6% at concurrency 32 is within that instance-to-instance variation, and the profiles show nothing in this change that costs time. We have not isolated the cause of the `lm_head` variation.

**CI.** `:amd: (MI300) V1 Attention` runs `tests/v1/attention`, which collects the unified builder's cases; elsewhere only the Triton cases run.

Not a duplicate: searched for `supports_draft_decode_metadata_update`, `update_draft_decode_metadata`, the fallback string and "draft decode metadata". #54790, #58371 and #58449 opt in other backends, and #62749 adds a separate target-side flag.
