## PR body
```markdown
## Justification

Block-quantized FP8 fused MoE was locked to `BLOCK_SIZE_N = block_shape[0]` (128) at every batch size — in both the runtime heuristic (`get_default_config`) and the tuner search space. At decode the gate-up GEMM is SM-bound: a 128-wide N tile produces too few thread blocks to fill the GPU.

This was never a kernel requirement. The Triton kernel indexes block scales per N element (`offs_bn // group_n`), so a narrower N tile that divides the quant block is valid and exposes more thread blocks. With the **swap-AB** kernel (#36559, now in main) a 64-wide N tile stays efficient on Hopper down to the smallest batches, so `BLOCK_SIZE_N=64` is the right choice across the whole low-batch range.

Changes:
- **`get_default_config`**: use `BLOCK_SIZE_N=64` (`num_stages=4`) for fp8 block-quant on CUDA up to M=8. ROCm and larger batches unchanged.
- **`benchmark_moe.py` tuner**: relax the block-quant prune filter so `BLOCK_SIZE_N`/`BLOCK_SIZE_K` that *divide* the quant block (e.g. 64 with `block_n=128`) are no longer excluded — they were silently dropped from the search space, so no prior tune could find them.
- **Configs**: retune low-batch keys of affected H100/H200 block-FP8 configs to N=64 (N=32 only where it still wins, on E=256,N=256).

## Validation

Tuned and validated on H100 80GB HBM3 (same 132-SM die as H200, swap-AB active), topk=8, via `benchmark_moe.benchmark_config`. All 29 changed config keys re-measured vs the shipped config — **0 regressions**, +2.2% to +17.5%. Representative:

| config | key (M) | original (N=128) | retuned | speedup |
|---|---|---|---|---|
| H200 E=384,N=128 | 1 | 42.1 µs | N=64 → 38.2 µs | +9.2% |
| H200 E=384,N=128 | 4 | 70.0 µs | N=64 → 63.7 µs | +8.9% |
| H200 E=384,N=128 | 8 | 98.1 µs | N=64 → 90.5 µs | +7.8% |
| H200 E=384,N=128 | 16 | 154.9 µs | N=64 → 144.0 µs | +7.0% |
| H200 E=128,N=768 | 1 | 61.2 µs | N=64 → 50.5 µs | +17.5% |
| H200 E=256,N=256 | 1 | 48.8 µs | N=32 → 44.3 µs | +9.1% |
| H100 E=512,N=256 | 1 | 32.8 µs | N=64 → 30.4 µs | +7.4% |

Swap-AB makes N=64 efficient even at M=8–16, so the win extends well past pure decode (e.g. E=384,N=128 gains 7–9% across all of M=1–16). Swap path verified numerically correct (swap-on vs swap-off rel diff 6.5e-3, within fp8 tolerance).

Scope: benefits the **Hopper block-FP8 TP** path (oracle prefers `TritonExperts`). EP (FlashInfer CUTLASS) and Blackwell (E8M0 DeepGEMM) paths are unaffected.

AI assistance (Claude) was used for the analysis, benchmarking, and edits; all changes were reviewed by the submitter.
```
