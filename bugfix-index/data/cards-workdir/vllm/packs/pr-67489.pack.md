## 正文(PR 描述)

## Overview

Fixes #67307. With prefetch offload on 1 x H100, DeepSeek-V2-Lite runs out of GPU memory inside the FA3 MLA attention call on the first big gsm8k step. The engine dies and the nightly check scores accuracy 0.000. The cause: for decode-path batches larger than the largest captured CUDA graph, `FlashAttnMLAMetadataBuilder` passed `num_splits=0`. FA3 then allocated a large fp32 split-KV buffer that it did not use. This PR passes `num_splits=1` for those batches. KV cache sizing does not change.

Compared with #67296, this fix:

- fixes the reported OOM on this config. #67296's sizing steps never run a large MLA decode-path batch, so its measured reservation growth (0.77 GiB) stays below the 1.42 GiB already kept, the sizing does not change (26766 blocks, 27.93 GiB cap), and the exact failing step still OOMs in the same FA3 MLA call (`Tried to allocate 1.17 GiB ... 27.93 GiB allowed`).
- adds a test that catches the bug. The new test fails on #67296's change just as on the base commit (2,680,138,752 bytes allocated). #67296's own tests check its sizing helper with synthetic allocations and never reach FA3 MLA.

## Claims

- Fixes the engine OOM and the 0.000 gsm8k score in "(H100) [Nightly] DeepSeek V2-Lite Prefetch Offload Accuracy", with the extensible KV cache on (the default).
- Removes the unused split-KV buffer for decode-path batches above the captured CUDA graph size, in every mode that captures graphs (PIECEWISE included). This buffer was 1.2 GiB for the failing step and up to 6.5 GiB for other shapes within the same 8192-token budget.
- At 16 heads per rank the output is bitwise equal. The KV cache size is unchanged (26766 blocks before and after).
- Adds a unit test that fails on the base commit and passes with the fix.

## Details

Root cause:

- `FlashAttnMLAMetadataBuilder.reorder_batch_threshold = 512`, so every request with at most 512 new tokens takes the MQA decode path. A gsm8k 5-shot step of many short prefills over a cached prefix becomes a decode-path batch of about 8000 tokens.
- Above the largest captured CUDA graph size (512 tokens here), `_build_decode` passed `num_splits=0`. It did this in every graph mode. For FA3, `0` does not mean "no split". It means "you choose". For a varlen batch, FA3 plans its split count as if one request held every query. It then allocates an fp32 accumulator of `splits x tokens x heads x 512 x 4` bytes in every layer. For the failing step that is 5 splits, about 1.25 GiB. At 16 heads FA3 then uses one split at run time anyway.
- No warmup step runs this shape. So the extensible KV cache keeps free only the measured transient (1.42 GiB) plus its margin, which lets torch grow 2.0 GiB above its size at sizing time. Once a longer-lived tensor lands in the freed accumulator block, the allocator needs a second block of that size. The step's reserved memory grew by 2.9 GiB, so the call hit the cap. Before the extensible KV cache, the memory that `gpu_memory_utilization=0.92` leaves unused (about 6 GiB) hid this waste.

Fix: the gate is now `if self.max_cudagraph_size:`. Batches within the captured sizes behave as before: `self.max_num_splits` under full graphs, and `0` under PIECEWISE. Larger batches get `1`. With `enforce_eager` or `cudagraph_mode=NONE`, nothing changes. The builder's own NOTE already meant split buffers to exist only for the captured sizes.

Why not more headroom in the KV cache sizing: the buffer grows with the batch shape, so a constant margin does not cover it. With a fixed 3 GiB margin floor on CUDA, a 170 x 48 batch still OOMed (`Tried to allocate 2.42 GiB ... 29.88 GiB allowed`). That margin would also cost 2 GiB of KV cache on every CUDA deployment.

Trade-off: FA3 attention kernel time per call, `num_splits=1` vs the old `0`, for batches above the captured size:

- 16 heads per rank (this model at TP1, DeepSeek-V3/R1 at TP8): at most 1.01x at 1900, 8192 and 32768 tokens of KV. The output is bitwise equal.
- 8 heads per rank: 0.71x to 1.00x. The output is within one bf16 ulp.
- 4 heads per rank (for example this model at TP4): few requests with long queries over long KV get slower, because FA3 would have split them. 8 x 70 tokens: 1.51x / 2.30x / 2.68x at 1900 / 8192 / 32768 tokens of KV (0.310 to 0.831 ms per layer call). 2 x 300 tokens: 1.61x / 1.60x / 1.85x. Other 4-head shapes: 0.85x to 1.02x. FA3 planned only 0.03 to 0.10 GiB for those slow shapes. I kept the simple rule, because keeping splits for such batches would mean copying FA3's heuristic, or keeping an eager buffer that no warmup measures.

Limitations, not addressed here:

- `enforce_eager` / `cudagraph_mode=NONE`: there is no captured size to compare with, and the same 170 x 48 load still OOMs (`Tried to allocate 2.36 GiB ... 27.37 GiB allowed`). Forcing one split on every eager decode would slow down small long-context decodes. This path needs a different rule, such as a bound on splits x tokens.
- With prefill graphs captured up to 8192 tokens (`max_prefill_cudagraph_capture_tokens=8192`), the batch takes the unchanged in-graph branch with 32 splits. It OOMs (`Tried to allocate 7.83 GiB`) both before and after this change.
- `vllm/v1/attention/backends/flash_attn.py` has the same `max_num_splits = 0` block. An unused buffer was measured there for Qwen3 GQA shapes, but no end-to-end OOM was seen, so it is left as is.
- DCP (`decode_context_parallel_size > 1`) was not tested. Only one GPU was used.
