## PR body
```markdown
## Motivation

When CUDA IPC transport is enabled for multimodal models (`SGLANG_USE_CUDA_IPC_TRANSPORT=1`), every scheduler iteration re-opens IPC handles for the same long-lived memory pool via `torch.UntypedStorage._new_shared_cuda()`. While the underlying `cuIpcOpenMemHandle` driver call does reference-count repeated opens, the PyTorch wrapper (`_new_shared_cuda`) adds significant per-call overhead from storage object creation, event management, and Python-level bookkeeping ([pytorch/pytorch#161481](https://github.com/pytorch/pytorch/issues/161481)). Since the pool is allocated once at startup, these repeated calls are redundant.

This overhead is on the scheduler's critical path (`mm_loop`) and blocks both prefill and decode iterations for all in-flight requests.

## Modifications

- Pre-compute the pool's IPC handle once at `MmItemMemoryPool` init instead of per-slice
- Add a process-global `_pool_storage_cache` dict that caches the opened `UntypedStorage` per pool handle (thread-safe via double-checked locking)
- On cache miss or stale entry: invalidate and retry uncached
- Pass pool handle + byte offset through `CudaIpcTensorTransportProxy` so the consumer can slice into the cached pool storage directly
- Gate behind `SGLANG_USE_IPC_POOL_HANDLE_CACHE` env var (default: disabled)

## Benchmarking

**Setup:** Qwen/Qwen2.5-VL-3B-Instruct, 1×H100, 16 tokenizer workers, mixed-chunk ON, CUDA IPC transport ON

**Reproduce:**
```bash
# Set SGLANG_USE_IPC_POOL_HANDLE_CACHE=1 or 0 before launching
python -m sglang.launch_server \
  --model-path Qwen/Qwen2.5-VL-3B-Instruct \
  --enable-multimodal --enable-mixed-chunk \
  --tokenizer-worker-num 16 \
  --max-running-requests 128 --max-prefill-tokens 65536 \
  --host 0.0.0.0 --port 30000

python -m sglang.bench_serving \
  --backend sglang-oai-chat --port 30000 \
  --model Qwen/Qwen2.5-VL-3B-Instruct \
  --dataset-name image --num-prompts 3000 \
  --image-count 1 --image-resolution 360p \
  --random-input-len 128 --random-output-len 32 \
  --max-concurrency 50 --seed 2710
```

**Results (median of 10 runs per configuration):**

| Metric | Cache OFF | Cache ON | Improvement |
|--------|----------|---------|-------------|
| Request throughput | 22.2 req/s | 25.7 req/s | **+16.2%** |
| TTFT mean (p50 / p99) | 965 ms (1020 / 2058) | 838 ms (930 / 1819) | **-13.2%** |
| TPOT mean | 72 ms | 60 ms | **-17.2%** |
| ITL mean (p99) | 67 ms (627) | 56 ms (556) | **-16.2%** |
| E2E latency mean (p50 / p90 / p99) | 1979 ms (1901 / 3329 / 4309) | 1768 ms (1720 / 2831 / 3666) | **-10.6%** |
| Errors | 2-3 / 3000 | 2-3 / 3000 | Similar |

Throughput improves by ~16% and latency drops 10-17% across all percentiles. TPOT and ITL also improve because `mm_loop` is on the scheduler's critical path — a slower `mm_loop` delays decode iterations for all in-flight requests, not just the prefilling one.

## Correctness

Output comparison on 3000 requests with identical inputs (`--seed 2710`):
- 52% of outputs are byte-identical between cache ON and OFF
- Remaining differences are due to non-deterministic batch scheduling at c=50
- Output length distributions are identical (mean=63, median=59 chars)
- No corrupted or garbled outputs

The optimization only changes how the scheduler opens the pool's GPU memory mapping — the same feature tensors reach the scheduler in both configurations.

## Tests

`test/registered/utils/test_cuda_ipc_transport_utils.py`:

- **Cache reuse**: two proxies from the same pool trigger only one `_new_shared_cuda()` call
- **Stale entry recovery**: poisoned cache entry is invalidated and retried uncached
- **Cross-pool isolation**: separate pools maintain independent cache entries; poisoning one doesn't affect the other
