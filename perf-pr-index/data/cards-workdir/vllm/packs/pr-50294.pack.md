# [Kernel][Model] Gemma4: optimize FA4 mm_prefix range lookup and CuTe JIT stability

## Motivation

Gemma4 multimodal models can use FA4 as the backend for all layers, so that both
sliding-attention layers (`head_dim=256`) and global/full layers
(`global_head_dim=512`) use one attention backend. This is required for the
vision `mm_prefix` / PrefixLM bidirectional mask path, and avoids mixing
FlashAttention and Triton attention implementations within the same model.

For video prompts, however, the current FA4 `mm_prefix` implementation scales
poorly when the number of multimodal ranges varies across requests and batches.
In Gemma4 video workloads each frame commonly contributes one range, so batches
may see `max_ranges` values such as 1, 8, 16, 32, 46, or 64 over time.

This is not limited to applications that pre-extract frames outside vLLM. The
native vLLM video ingestion path can also produce variable frame counts. Raw
video inputs are decoded by `VideoMediaIO` / `VideoBackend`, which uniformly
samples up to `num_frames` frames (`32` by default). Long videos usually become
32 sampled frames, but shorter clips, failed frame recovery, JPEG-frame
sequences, multiple videos in one prompt, mixed image+video prompts, or
request-level `media_io_kwargs` such as `fps`, `num_frames=-1`, or a larger
`num_frames` can all change the final number of frames in a batch.

Gemma4 does not have a native video tower in vLLM. After video loading, each
sampled frame is processed as an image and the video placeholder is expanded as:

```text
mm:ss <boi> <|video|>*N <eoi> mm:ss <boi> <|video|>*N <eoi> ...
```

Only the `<|video|>` soft-token positions are marked as multimodal embeddings;
the timestamp, `<boi>`, and `<eoi>` tokens are not. Therefore
`PlaceholderRange.extract_embeds_range()` splits one video into one
bidirectional `mm_prefix` range per frame rather than one range for the whole
video. With default raw video loading, one video typically contributes between
1 and 32 ranges. With multiple videos, mixed images, or caller-provided frame
sequences, the range count can be higher and more variable.

## Problem

The current FA4 `mm_prefix` mask_mod receives a padded tensor of shape
`(batch, max_ranges, 2)` and scans every range for every Q x K score:

```python
for i in cutlass.range_constexpr(max_ranges):
    r_start, r_end = ranges[b, i]
    keep = keep | (q_in_range & k_in_range)
```

This creates two performance problems:

1. `max_ranges` is baked into the CuTe JIT specialization via
   `cutlass.range_constexpr(max_ranges)`. Different video frame counts can
   produce different FA4 compile keys and trigger repeated cold JIT compiles.
2. Even when the kernel is already compiled, the mask work is
   `O(max_ranges)` per score. A request with many frames increases the work for
   every request in the same batch because the tensor is padded to the batch
   maximum.

For Gemma4 video prefill with FA4 and vision `mm_prefix`, this hurts both cold
start and steady state. The GPU can sit idle while CuTe compiles a new
specialization, and the compiled kernel still pays for the range scan on every
masked score.

The old mask work scales roughly as:

```text
sliding_layers * num_heads * L^2 * batch_max_ranges
```

The `batch_max_ranges` term comes from scanning all padded ranges in the
mask_mod. The proposed range-id path keeps the same dense Q x K mask surface,
but each lookup is constant time:

```text
sliding_layers * num_heads * L^2
```

There is a metadata precompute step to allocate and fill the
`(batch, max_seq_len)` range-id tensor:

```text
batch_size * max_seq_len + total_mm_tokens
```

That work happens outside the FA4 score loop. The hot FA4 mask path no longer
scales with the largest frame count in the batch.

## Proposed change

Move range membership lookup from the FA4 mask inner loop into metadata
precomputation:

- Build a per-token range-id tensor with shape `(batch, max_seq_len)`.
- Fill non-mm tokens with `-1`.
- Assign each multimodal range a request-local integer id.
- In the FA4 mask_mod, replace the loop over `max_ranges` with:

```python
q_id = range_ids[b, q_abs]
k_id = range_ids[b, kv_idx]
mm = (q_id >= 0) & (q_id == k_id)
keep = causal_window_keep | mm
```

For Gemma4 sliding layers that clamp the bidirectional block to the sliding
window, keep the existing `(query_abs - kv_idx) < sliding_window` condition on
the `mm` branch.

This preserves the non-overlapping range semantics of the existing
start/end-list implementation while making lookup `O(1)` and removing
`max_ranges` from the FA4 mask_mod compile key.

The complexity reduction is part of the fix, not just a cache workaround. It
removes the range loop from the innermost Q x K masking path, so the FA4 mask
cost no longer scales with the batch's largest video frame count.

## Measured results

The numbers below were measured with the latest vLLM version on one H100 GPU,
using Gemma 4 31B in BF16. The benchmark used FA4 with vision
`mm_prefix`.

This was a pooling embedding workload, not a generation benchmark. That matches
the production use case for this branch, where serving returns pooled scores
rather than generated text. QPS means completed pooling embedding requests per
second.

Workload shape:

- 1000 real requests stress test at concurrency 32.
- Each request has one video and text, in `text + video` order.
- Video frame count varies between 8 and 64 frames, with an average of 48.
- Each frame is 360 x 640.
- The text part averages 885 tokens.

| Path | QPS |
| --- | ---: |
| Existing FA4 `mm_prefix` range scan with CuTe JIT | 0.103 |
| Existing FA4 `mm_prefix` range scan without CuTe JIT | 0.678 |
| FA4 with per-token range ids | 1.307 |
| Triton reference path | 0.743 |

This is a +92.8% QPS improvement over the existing FA4 path and makes FA4 faster
than the Triton comparison path under the same workload.

The gain comes from both parts of the change:

- avoiding repeated FA4 CuTe recompilation when `max_ranges` changes;
- replacing the per-score scan over all padded ranges with an `O(1)` range-id
  equality check.

Correctness checks from the same setup:

- outputs matched bit-exact between old FA4 and range-id FA4.
- Mean absolute difference versus the reference path was about 0.00646, in the
  same range as the historical FA4/Triton difference.

+    out = torch.zeros(len(lens) + 1, dtype=torch.int32)
+    out[1:] = torch.tensor(lens, dtype=torch.int32).cumsum(0)

+def _dense_reference(
+    q,
+    k_per_req,
+    v_per_req,
+    query_lens,
+    seq_lens,
+    mm_ranges,
+    sliding_window_left,
+    scale,
+    mm_clamp_sw=0,
+):
+    """Dense float32 ``(causal AND window) OR mm_prefix`` per request.
+
+    ``mm_clamp_sw`` confines the bidirectional block to the window, reproducing
+    Gemma4's ``mm_prefix_clamp_sliding_window``. Only the past bound applies, so
+    future keys inside a range still pass.
+    """
+    out = torch.empty_like(q, dtype=torch.float32)
+    repeats = q.shape[1] // k_per_req[0].shape[1]
+    q_off = 0
+    for req_idx, (q_len, k_len) in enumerate(zip(query_lens, seq_lens)):
+        ctx = k_len - q_len
+        q_pos = torch.arange(q_len, device=q.device) + ctx
+        k_pos = torch.arange(k_len, device=q.device)
+        delta = q_pos[:, None] - k_pos[None, :]
+
+        keep = delta >= 0
+        if sliding_window_left is not None:
+            keep &= delta < sliding_window_left
+
+        for start, end in mm_ranges.get(req_idx, []):
+            if start >= end:
+                continue
+            q_in = (q_pos >= start) & (q_pos <= end)
+            k_in = (k_pos >= start) & (k_pos <= end)
+            mm = q_in[:, None] & k_in[None, :]
+            if mm_clamp_sw > 0:
+                mm &= delta < mm_clamp_sw
+            keep |= mm
+
+        q_i = q[q_off : q_off + q_len].float().transpose(0, 1)
+        k_i = k_per_req[req_idx].float().transpose(0, 1)
+        v_i = v_per_req[req_idx].float().transpose(0, 1)
+        if repeats > 1:
+            k_i = k_i.repeat_interleave(repeats, dim=0)
+            v_i = v_i.repeat_interleave(repeats, dim=0)
+
+        scores = (q_i @ k_i.transpose(-1, -2)) * scale
+        scores = scores.masked_fill(~keep[None], float("-inf"))
+        out[q_off : q_off + q_len] = (scores.softmax(-1) @ v_i).transpose(0, 1)
+        q_off += q_len
+    return out
