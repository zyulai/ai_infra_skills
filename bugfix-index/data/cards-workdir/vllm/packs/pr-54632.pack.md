## 正文(PR 描述)

## Purpose

Client-supplied embedding payloads are deserialized and then immediately densified:

```python
with check_sparse_tensor_invariants_threadsafe():
    tensor = torch.load(buffer, weights_only=True)
    return tensor.to_dense()          # <-- unbounded
```

`weights_only=True` blocks arbitrary code execution, and
`check_sparse_tensor_invariants()` rejects indices that fall outside the declared
shape. Neither bounds the *declared shape itself*.

A sparse COO tensor holding **one** in-bounds non-zero element with a declared
shape of `(2**20, 2**20)` is a completely valid tensor. It passes the invariant
checks, serializes to about 1.5 KB, and `to_dense()` then asks the allocator for
4 TiB.

To be precise about what I measured: at that size the allocator simply refuses
(`RuntimeError: DefaultCPUAllocator: can't allocate memory: you tried to
allocate 4398046511104 bytes`, peak RSS unmoved). The damaging regime is the
shapes that *fit*, because the dense allocation is bounded by the declared shape
rather than by the request, and the attacker picks the shape. Those are fully
resident, and several concurrent requests sized near the host is what turns that
into an outage. I have not reproduced a kill on a shared machine and am not
claiming one.

Measured amplification on a plain checkout (`torch.save` of a
`(20000, 20000)` sparse tensor with 1 stored element):

```
serialized payload size = 1560 bytes
RSS before to_dense()   = 337 MB
RSS after  to_dense()   = 1866 MB      # +1.49 GiB from a 1.5 KB payload
```

The existing `ndim` validation in `ImageEmbeddingItems` / `AudioEmbeddingItems`
cannot help here, because it runs *after* `to_dense()` — the memory is already
allocated by the time the shape is looked at. The same is true of the
`hidden_size` / `dim()` checks in `safe_load_prompt_embeds`, which are all
sequenced after the `to_dense()` call.

Reachable from:

| Entry point | Requires | Path |
| --- | --- | --- |
| `/v1/chat/completions` content part `{"type": "image_embeds", ...}` | `--enable-mm-embeds` | `parse_image_embeds` → `MediaConnector.fetch_image_embedding` → `ImageEmbeddingMediaIO.load_base64` |
| same, `audio_embeds` / `video_embeds` | `--enable-mm-embeds` | `AudioEmbeddingMediaIO` / `VideoEmbeddingMediaIO` |
| `/v1/completions` with `prompt_embeds` | `--enable-prompt-embeds` | `safe_load_prompt_embeds` |

Both entry points are behind an opt-in server flag, so this is not reachable on a
default server — but on a server that does enable them, any client that can send a
request can trigger it. The dict form of `image_embeds` fans out
(`{k: fetch_image_embedding(v) for ...}`), so one request can carry several such
payloads.

### The fix

Add `safe_to_dense(tensor, *, parameter=...)` in `vllm/utils/sparse_utils.py` and
route all seven `to_dense()` call sites through it. It rejects a payload whose
dense footprint (`numel() * element_size()`) exceeds
`VLLM_MAX_EMBED_DECODE_BYTES` **before** `to_dense()` allocates anything, raising
`VLLMValidationError` so the caller gets a 4xx rather than a dead server.

It also checks that the payload actually deserialized to a `torch.Tensor`.
`safe_load_prompt_embeds` already did this; the three media IO classes did not, so
a non-tensor payload surfaced as an `AttributeError` (500) instead of a 4xx.

On the default: `VLLM_MAX_EMBED_DECODE_BYTES` defaults to 2 GiB, which is a guard
rail rather than a tight bound. 2 GiB is what a legitimate 128K-token float32
`prompt_embeds` at `hidden_size=4096` costs, so anything lower would start
rejecting real requests. The point is to turn "unbounded" into "bounded and
configurable"; deployments facing untrusted clients will want to lower it.
Setting it to `0` disables the check, consistent with the other limits in the
same table in `docs/usage/security.md`.

I checked open and closed PRs/issues for overlap (`to_dense`, `prompt_embeds
sparse`, `image_embeds limit`, `sparse_utils`, `safe_load_prompt_embeds`,
decompression-bomb wording) and did not find an existing fix or report for this.
Happy to change the env var name, the default, or fold the check into the
`MediaIO.get_max_bytes()` mechanism instead if that fits better.

## Test Plan

```bash
pytest tests/multimodal/test_embedding_decode_limit.py -v
```

It covers `safe_to_dense` directly and each of the three
`*EmbeddingMediaIO` classes (the objects reached from `/v1/chat/completions`),
via both `load_base64` and `load_file`:

- an oversized-but-valid sparse tensor is rejected, and the error names the
  offending parameter and the env var
- the attack payload really is small (asserted `< 4096` base64 chars), so this is
  amplification and not just a large upload
- dense tensors and small sparse tensors still load unchanged
- a non-tensor payload is rejected as a validation error
- the limit is configurable, exact at the boundary, and disabled by `0`

+def safe_to_dense(tensor: object, *, parameter: str) -> torch.Tensor:
+    """Densify a client-supplied embedding tensor within a memory budget.
+
+    `torch.load(..., weights_only=True)` prevents arbitrary code execution but
+    not memory amplification: a sparse COO tensor carries its own declared
+    shape, so the dense allocation is bounded by that shape rather than by the
+    request. A 2.6 KB payload declaring `(30000, 30000)` materializes 3.4 GiB,
+    and the shape can be picked to fit whatever host is being targeted. The
+    invariant checks only reject *invalid* tensors (indices outside the
+    declared shape); a single non-zero element inside a `(2**20, 2**20)` shape
+    is perfectly valid and passes them.
+
+    So reject oversized payloads based on the dense size they declare, before
+    `to_dense()` allocates anything.
+    """
+    if not isinstance(tensor, torch.Tensor):
+        raise VLLMValidationError(
+            f"`{parameter}` payload did not deserialize to a torch.Tensor.",
+            parameter=parameter,
+        )
+
+    max_bytes = envs.VLLM_MAX_EMBED_DECODE_BYTES
+    if max_bytes > 0:
+        dense_bytes = tensor.numel() * tensor.element_size()
+        if dense_bytes > max_bytes:
+            raise VLLMValidationError(
+                f"`{parameter}` declares shape {tuple(tensor.shape)}, which "
+                f"would allocate {dense_bytes} bytes "
+                f"({dense_bytes / MiB_bytes:.0f} MiB) once densified, "
+                f"exceeding the {max_bytes} byte limit. Set "
+                f"VLLM_MAX_EMBED_DECODE_BYTES to increase this limit.",
+                parameter=parameter,
+                value=dense_bytes,
+            )
+
