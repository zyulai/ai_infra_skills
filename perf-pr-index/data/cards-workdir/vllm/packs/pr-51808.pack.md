## Overview

Support activation quant key override in online MXFP4 quantization as e.g.:

```bash
--quantization online --quantization-config.targets '{"*experts*":{"weight":"mxfp4","activation":null}}'
# dispatching to AITER_MXFP4_BF16 on ROCm.

--quantization online --quantization-config.targets '{"*experts*":{"weight":"mxfp4","activation":"mxfp8"}}'
# (unsupported on ROCm atm, see below)
```

An activation override that the selected MXFP4 backend cannot compute raises instead of silently running another activation format. For example, `"activation":"mxfp8"` on ROCm (MI350X, `VLLM_ROCM_USE_AITER=1`) raises:

```text
NotImplementedError: online MXFP4 MoE backend 'Mxfp4MoeBackend.EMULATION' cannot honour activation=QuantKey(f8e4m3fn,scale(u8,dynamic,GroupShape(row=1, col=32)),symmetric); it computes activation=QuantKey(u8,scale(u8,dynamic,GroupShape(row=1, col=32)),symmetric).
```

Similarly, e.g. `"fp8_per_tensor_static"` is rejected for online quantization, which has no calibrated activation scales.

**Other online quantization weight keys than MXFP4 still raise `NotImplementedError` in case activation key is overriden. This will be updated once all oracles share the same logic for activation quant key override.**

Currently, activation override for online quantization raises a `NotImplementedError`, but overriding the activation quant key is truly needed to dispatch on preferred MOE backends (e.g. `AITER_MXFP4_BF16`, `AITER_MXFP4_MXFP4`) that can not be selected in any other way.

More context at https://github.com/vllm-project/vllm/issues/52167

## Claims

Only the MXFP4 online methods (`Mxfp4OnlineLinearMethod`, `Mxfp4OnlineMoEMethod`) accept an activation override, which is what the MXFP4 backend dispatch needs. Any other online method raises `NotImplementedError: activation override is not supported for online <method class>` at config-resolution time (`OnlineRequantizationMixin.resolve_activation_quant_key` raises unless the method class sets `accepts_activation_override = True`). Only the MXFP4 online methods take an `activation_quant_key` constructor argument (defaulting to `kMxfp4Dynamic`); other online methods keep their class-level `activation_quant_key`, unchanged from `main`.

An online MXFP4 MoE override that the selected backend does not compute raises `NotImplementedError`, and static activation keys are rejected for every online method.

An explicitly configured `activation: null` requests unquantized (BF16) activations, for `linear` and `moe` alike, on online targets and on pre-quantized checkpoints. On a pre-quantized MXFP4 MoE checkpoint that declares its own activation, an explicit `moe.activation` (`null` included) now overrides the checkpoint's activation with a warning, like linear layers already do, instead of raising.

For the `mxfp4` / `mxfp8` shorthands, which may name either an online scheme or the checkpoint format, the shorthand defaults are merged with `--quantization-config` only once the model is known to be unquantized (`merge_quantization_config` in `get_quant_config`). On a pre-quantized checkpoint, e.g. `--quantization mxfp4 --quantization-config.moe.activation mxfp8` on gpt-oss, an activation override alone therefore no longer online-quantizes the layers the checkpoint leaves unquantized (on `main`, it did so for linear layers).

On a pre-quantized checkpoint, a `targets` spec without a `weight` (e.g. `{"targets": {"*experts*": {"activation": null}}}`) overrides the activation of the matching layers' checkpoint quant method only: `resolve_quant_method` applies it while that method is built, and `user_activation_override` reads it before the global `linear` / `moe` override.

`--moe-backend aiter_mxfp4_fp8` with online MXFP4 MoE is not rejected up front, but it already fails at weight processing, as online quantization has no static activation scales (unchanged from `main`):

```
ValueError: W4A8 (AITER_MXFP4_FP8) requires static input scales, but found w13_input_scale or w2_input_scale is None.
```

Left to other PRs:

- [ ] Add `__str__` method to QuantKey directly.
- [ ] Per-layer `targets` activation overrides on pre-quantized checkpoints only reach the quant methods that select their kernel / backend when they are built. Quark MXFP4 linear (`QuarkOCP_MX`) selects its kernel in `create_weights`, and the Humming MoE input schema is built at weight processing, so both only see the global `linear` / `moe` override. This should be handled in the oracles, independently of the quant methods, rather than per quant method.
- [ ] Let the OCP MX emulation MoE backend compute the requested activation format for online MXFP4. Today, EMULATION only computes MXFP4 activations, so for online MXFP4 MoE any other requested activation key (`null`/BF16, MXFP6, FP8, and `mxfp8` on ROCm) raises `NotImplementedError` ("online MXFP4 MoE backend ... cannot honour activation=...") instead of silently running MXFP4 activations, as before this PR. The oracle hard-codes MXFP4 activations for EMULATION here: https://github.com/vllm-project/vllm/blob/790be385c8a69f45ec9a7a85ef00836d1684060f/vllm/model_executor/layers/fused_moe/oracle/mxfp4.py#L2240-L2250
- [ ] Make the activation override independent of the oracle: today only `Mxfp4OnlineLinearMethod` and `Mxfp4OnlineMoEMethod` support it with this PR. Generalize it so any oracle can accept an activation override, and move some of the logic to oracles rather than online quantization.
