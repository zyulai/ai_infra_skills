## 正文(PRD / 提案全文)

### Motivation.

I am investigating eager fallback under imbalanced DP decode workloads with MRV2 DBO, building on #51700 and the original RFC #50738.

For example, with per-rank token counts [63, 97] and a 128-token FULL CUDA graph, each captured microbatch has a capacity of 64 tokens.

On the smaller rank, the first microbatch contains 63 real tokens and one padding token, while the second contains only padding.

The existing guard:

```python
2 * min_tokens < descriptor.num_tokens
```

therefore rejects the microbatched graph and falls back to eager execution across the DP group.

I would like to investigate whether FULL CUDA graph replay can be retained by redistributing real tokens within each rank's existing captured input layout, without moving requests between DP ranks.

The motivation is to avoid unnecessary eager fallback while preserving graph-visible addresses, physical capacities and collective ordering.

The additional staging, metadata updates and output restoration introduce overhead that must be evaluated against the benefit of retaining graph replay.
