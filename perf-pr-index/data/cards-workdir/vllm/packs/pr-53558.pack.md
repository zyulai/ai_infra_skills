RFC: #62100

## Purpose

Follow-up to #42309. vLLM picks the KV cache grouping of every model with one heuristic in core (`get_kv_cache_groups()`). New hybrid models, drafters, cache precisions and platforms keep needing plans that this heuristic does not give, so each new model changes core, and vllm-ascend monkey-patches core planning to use its own DSV4 plan.

This PR adds an **experimental** pluggable `KVCacheConfigBuilder`. Core keeps one planning flow and checks every plan. A platform selects a builder that decides grouping and placement, and a model can return its own groups. The interfaces can change, in particular when #61452 changes the KV cache group data structure.

<img width="1538" height="740" alt="image" src="https://github.com/user-attachments/assets/26f4c9c9-40e4-4f68-8fdf-679e4009cd10" />

## Changes

- **`KVCacheConfigBuilder`** (`vllm/v1/core/kv_cache_config_builder.py`) with two decisions: `get_kv_cache_groups(vllm_config, kv_cache_spec)` and `get_kv_cache_config_from_groups(vllm_config, kv_cache_groups, num_blocks)`. A platform selects the class with `Platform.get_kv_cache_config_builder_cls`; the default is `DefaultKVCacheConfigBuilder`.
- **Core owns the planning flow.** `get_kv_cache_configs` is a core function, not a builder method: merge specs, group, check, project onto PP stages, apply the block-count override, auto-fit and admission, place, and converge ranks. Platforms make only the two decisions above.
- **Bytes per block come from the builder's placement.** Core places one block and reads its single device backing, so a platform with its own placement does not compute memory separately. A placement with several device allocations overrides the private, transitional `_get_pool_bytes_per_block` (until worker-driven allocation, #42449).
- **Model-owned grouping.** A model class can implement `SupportsKVCacheGrouping.get_kv_cache_groups` (a classmethod). Priority: a platform builder that overrides grouping (it reaches the model hook only through `super()`), then the model hook, then the default heuristic.
- **Every grouping is checked**, from any source, on the planning path and both profiling paths: each layer is in exactly one group.
- **Profiling** passes `num_blocks` directly instead of temporarily setting `num_gpu_blocks_override`.

Bug fixes:

- PP projection now keeps `host_resident`, `role` and `enable_kv_transfer` on partially projected groups.
- `num_gpu_blocks_override` no longer inflates the one-block probe (it gave `500 * C` instead of `C` bytes per block).
- HiSparse keeps the direct bytes computation, because probing its placement would size the host pool before auto-fit. A model hook combined with HiSparse raises a clear error.

## Users

- vllm-ascend#18359 moves the Ascend plans into an `AscendKVCacheConfigBuilder` and removes most of its planning patches.
- wangxiyuan/vllm#2 (stacked on this PR): model hooks for Qwen3.8-Flash-Next and Kimi-K3 (Kimi-K3 + DSpark: 5 groups instead of 20), and golden grouping plans per model.

Not a duplicate: #58638 (#58207, #58380) improves the default heuristic for drafters. That work is complementary; this PR adds the extension point and does not change the default grouping.

+"""Interface and resolution for pluggable KV cache config builders."""

+class KVCacheConfigBuilder(ABC):
+    """Interface for platform KV cache placement.
+
+    .. note::
+        This interface is experimental and subject to change. The exact hooks
+        and the ``num_blocks`` contract may evolve before it stabilizes.
+
+    Subclasses normally inherit from ``DefaultKVCacheConfigBuilder`` and
+    override only the hooks they need. The cross-worker planning flow
+    (:func:`vllm.v1.core.kv_cache_planning.get_kv_cache_configs`) is Core-owned;
+    this builder supplies the placement decisions: how layers are split into
+    groups and how a group list is materialized into tensors for a given block
+    count. Grouping coordination lives in ``DefaultKVCacheConfigBuilder`` (a
+    model implementing :class:`~vllm.model_executor.models.interfaces.
+    SupportsKVCacheGrouping` owns its grouping there); a platform that replaces
+    the builder fully owns its own grouping.
+    """
+
+    @abstractmethod
+    def get_kv_cache_groups(
+        self,
+        vllm_config: "VllmConfig",
+        kv_cache_spec: dict[str, "KVCacheSpec"],
+    ) -> list["KVCacheGroupSpec"]:
+        """Split the given layers into KV cache groups.
+
+        Planning passes all workers' layers; profiling passes one worker's.
+        Core rejects a result that does not put each layer in exactly one group.
+
+        The default builder honors a model's
+        :class:`~vllm.model_executor.models.interfaces.SupportsKVCacheGrouping`
+        declaration here before falling back to the default grouping; a
+        platform-specific builder decides its own grouping.
+        """
+        raise NotImplementedError
+
+    @abstractmethod
+    def get_kv_cache_config_from_groups(
+        self,
+        vllm_config: "VllmConfig",
+        kv_cache_groups: list["KVCacheGroupSpec"],
+        num_blocks: int,
+    ) -> "KVCacheConfig":
+        """Materialize the groups for exactly ``num_blocks`` blocks.
+
+        Each device backing's size is ``bytes_per_block * num_blocks``. All
+        device tensors share one backing allocation unless the builder
+        overrides ``_get_pool_bytes_per_block``. Host-resident tensors, such as
+        HiSparse source storage, are excluded from the device byte accounting
+        and sized independently.
+        """
+        raise NotImplementedError
+
+    def _get_pool_bytes_per_block(
+        self,
+        vllm_config: "VllmConfig",
+        kv_cache_groups: list["KVCacheGroupSpec"],
+    ) -> int | None:
+        """Return the device bytes one block ID consumes, or ``None``.
+
+        Private and transitional; expected to go away with worker-driven
+        allocation (RFC #42449). With ``None`` (the default), Core derives the
+        value from a one-block placement with one device backing. Override it
