## 正文(PR 描述)

## Purpose

Fix garbage outputs from QuIP transforms on Blackwell GPUs under `torch.compile` + CUDA graph capture. Initially observed on RTX 5090 (SM120); since reproduced on B200 (SM100) with the v0.21.0 prebuilt wheel + torch 2.11.0. Addresses the runtime side of vllm-project/llm-compressor#2006.

## Background

The `hadacore_transform` op is declared with a mutable schema:

```cpp
ops.def("hadacore_transform(Tensor! x, bool inplace) -> Tensor");
```

Two interacting issues:

**1. Kernel ignores the `inplace` parameter (latent bug).** In `csrc/libtorch_stable/quantization/hadamard/hadacore/hadamard_transform_cuda.cu`, the kernel always writes to `x.data_ptr()` regardless of `inplace`:

```cpp
torch::stable::Tensor out = inplace ? x : torch::stable::empty_like(x);
hadacore::run_fht<SCALAR_TYPE>(x.data_ptr(), x.data_ptr(), x.numel(), ...);
// `inplace=False` callers receive `out`, but `out` was never written to
return torch::stable::reshape(out, res_shape);
```

The conditional copy-back cannot fire because `out` is only aliased to `x` when `inplace=True`. The path is currently unused in vLLM but is publicly exposed.

**2. Mutable schema causes inductor to elide protective clones.** In `CompressedTensorsLinearTransformMethod.apply()`, the `.clone()` introduced in #26849 for compile robustness:

```python
x[:, start:start+length] = self.output_transform(
    x[:, start:start+length].clone(), part_id=part_id
)
```

Inductor analyzes the `Tensor!` schema, decides the clone is redundant (the op will mutate anyway), and elides it from the FX graph (verified via `TORCH_LOGS="output_code"`). The kernel ends up receiving a slice view aliasing `x`, producing garbage outputs under `torch.compile` + cudagraph. Initially observed on SM120; later also reproduced on B200 (SM100) with the v0.21.0 prebuilt wheel + torch 2.11.0 (QuIP variants: WikiText-2 PPL ~1.4e6; coherent with `enforce_eager=True`). @mgoin's `gsm8k_eval` in #28748 (0.697) used a combination that does not trigger the inductor elision: whether the bug manifests depends on the (torch version x compile/cudagraph) configuration, not the hardware.

| Test | Hardware | Pre-fix | Post-fix |
|---|---|---|---|
| W4A16 + QuIP, compile | RTX 5090 | ❌ Garbage | ✅ Coherent |
| NVFP4A16 + QuIP, compile | RTX 5090 | ❌ Garbage | ✅ Coherent |
| NVFP4A16 only, compile | RTX 5090 | ✅ Coherent | ✅ Byte-identical |
| NVFP4A16 + QuIP, cudagraph, v0.21.0 wheel + torch 2.11 | B200 | ❌ Garbage (PPL ~1.4e6) | N/A |
| Same, `enforce_eager=True` | B200 | ✅ Coherent (6.84) | N/A |
| Kernel sanity (`inplace=True` vs `False`) | B200 | N/A | ✅ max diff 0.0 |
| `gsm8k_eval` @mgoin SpinQuant model | B200 | 0.697 (#28748) | 0.697 |

## Changes

Kernel writes to `out.data_ptr()` instead of `x.data_ptr()` (respects `inplace`); call sites in `module.py` pass `inplace=False` to opt into the non-aliasing path. The existing `.clone()` from #26849 is retained as a defensive layer.

## Reproduction

The bug manifests on any compressed-tensors checkpoint using online Hadamard transforms (QuIP) under vLLM's default `torch.compile` + cudagraph execution. The root cause is in the kernel, independent of the calibration path. It also blocks the MXFP4 W4A4 + MR-GPTQ path (where rotations contribute ~+3 pts PPL recovery vs GPTQ alone on Llama-3.1-8B) and any future recipe relying on online Hadamard rotations.

### Step 1: produce a QuIP-transformed checkpoint

```bash
git clone https://github.com/vllm-project/llm-compressor
cd llm-compressor
pip install -e .

# QuIP + GPTQ + NVFP4A16 example from vllm-project/llm-compressor#2751 (~10 min):
gh pr checkout 2751
python examples/transform/nvfp4_quip_gptq_example.py
# produces Llama-3.1-8B-quip-gptq-nvfp4a16
```

The attached logs were produced with an equivalent minimal datafree variant (`examples/transform/quip_example.py` adapted to the NVFP4A16 scheme, on Llama-3.1-8B-Instruct, producing `Llama-3.1-8B-Instruct-quip-nvfp4a16`). Both recipes trigger the same bug.

### Step 2: reproduce the failure on `main`

```bash

pip install vllm==0.22.1rc1.dev255+g4dcd10eb0 --extra-index-url https://wheels.vllm.ai/nightly

VLLM_USE_FLASHINFER_SAMPLER=0 python validate_nvfp4_quip.py <checkpoint_dir>
```
