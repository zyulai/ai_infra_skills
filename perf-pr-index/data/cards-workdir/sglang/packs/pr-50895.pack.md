## Motivation

A PD decode server streams the prefill-sampled first token as soon as the request is admitted (`process_batch_result_prebuilt`). Under the overlap scheduler, that request's first decode forward is queued behind the forward already in flight, so its next tokens arrive about two decode steps later.

Client TPOT is computed as (e2e - TTFT) / (osl - 1), so this gap is charged to every request's TPOT. On DeepSeek-V4.1 with DEP32 decode, the time to the second token was ~104 ms, against ~92 ms for a steady 32-token chunk.

A decode server that samples the first token in its own first decode step has no such gap.

## Modifications

At admission, the decode server now streams only requests that have already finished, for example `max_new_tokens=1`. A running request's prefill token goes out with its first decode output, which the output streamer sends at once because `send_token_offset == 0`.

This applies to PD decode only. Non-disaggregated serving is unchanged.

## Accuracy Tests

Output tokens are unchanged; only the time at which the first token is sent changes.

## Speed Tests and Profiling

Setup:
- Hardware: GB300.
- Model: DeepSeek-V4.1 with MTP.
- Deployment: PD disaggregation; the prefill worker count and the decode size vary by point (below).
- Workload: agentic multi-turn, 3600 s per run.

Throughput is flat within run-to-run noise at every point, and p90 TPOT improves by 3-6%.

Four 1200 s runs at concurrency 4000 confirm the mechanism:
- Time to the second token, p50: ~104 ms → 92-95 ms.
- TPOT p50: −1.5% to −3.7%.
- Decode step time: unchanged (9.82-9.92 ms vs 9.95 ms).
- TTFT: +~20 ms (one decode step), which is within TTFT noise at this load.
