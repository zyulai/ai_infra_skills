## Purpose

PaddleOCR-VL currently runs its vision encoder and projector once per scheduled image. Under serving load, EngineCore is CPU-bound, running at about one full core in both base and this PR, so this per-image overhead limits throughput. This PR batches the scheduled images into one encoder and projector pass and removes a per-layer device-to-host sync. In H100 benchmarks, EngineCore CPU time per crop fell by 46% and throughput rose by 34–85%, depending on the workload.

## Changes

All changes are in `vllm/model_executor/models/paddleocr_vl.py`:

- **Encoder:** one call over the processor's flat patch tensor for all scheduled images. Position coordinates restart for each image, and cumulative `cu_seqlens` offsets keep attention within image boundaries.
- **Projector:** normalization, linear layers and GELU run on the combined features. The 2×2 spatial merge still runs per image. Outputs are split back in the original image order.
- **FlashAttention `max_seqlen`:** computed from CPU-side `image_grid_thw` metadata, removing the per-layer device scalar read.

Batch size is set by the existing multimodal scheduler and encoder budget, so peak activation memory remains bounded by the profiled encoder budget.

**Relation to #44394:** [#44394](https://github.com/vllm-project/vllm/pull/44394) adds encoder CUDA graph capture and replay with a packed projector path, but its eager `_process_image_input` fallback still calls the encoder once per image. This PR fixes the eager path, which is used whenever encoder CUDA graphs are disabled. The two PRs touch the same model file but different code paths: this one covers eager batching, and #44394 covers graph capture and replay.

## Test Plan

- New unit tests in `tests/models/multimodal/test_paddleocr_vl.py` (7) cover patch packing, attention offsets, positions, per-image spatial merging, FP32 parity with the per-image path, BF16 accuracy against FP32, and cross-image isolation. The existing MRoPE tests in `tests/model_executor/test_paddleocr_vl_mrope.py` (4) also pass.
- Serving with `VLLM_GPU_SYNC_CHECK=error` at TP=1 and TP=2 on 32 public crops: zero request errors and no flagged syncs.
- End-to-end accuracy and throughput on the full public OmniDocBench set, plus repeated `vllm bench serve` runs at four concurrency levels (below).
- `pre-commit` passed (Ruff, mypy, SPDX, CI test wiring).

Setup: H100 PCIe, PaddleOCR-VL-1.6 (`c5630ab`) in BF16. Base is `d9a543c`. Both versions used the same environment, flags and inputs.

## Test Result

The gain on OmniDocBench is larger, likely because its crops are mostly small text regions. More images fit in each encoder step, so per-image overhead is a larger share of the total.

**TP=2 output check.** Compared this patch against stock BF16 vLLM at `d9a543c`, with both servers using `--tensor-parallel-size 2`, the same PaddleOCR-VL-1.6 weights and serving flags. Both received the same 32 public OmniDocBench crops (16 text, 8 formula and 8 table crops) at concurrency 32, with temperature 0, seed 42 and matching token limits. The patched server also ran with `VLLM_GPU_SYNC_CHECK=error`. Both versions completed all 32 requests without errors, blank responses or truncation. Of the paired raw responses, 32/32 were identical.

**Why `-cc.mode=0`:** this PR changes only the vision encoder and projector. They run eagerly in both configurations, because PaddleOCR-VL's encoder is not wrapped with `@support_torch_compile` and `compile_mm_encoder` defaults to `False`. Disabling torch.compile for the language model kept the comparison focused on the encoder path and removed compilation from server startup. Decode still uses CUDA graphs (`FULL_DECODE_ONLY`). The encoder code path is the same under default compilation settings, but the end-to-end numbers above were not measured with them.
