## Motivation

Four changes on the GLM-5.2 decode path on gfx950, found by profiling a
GLM-5.2-MXFP4 TP8/EP1 server at 104k context. They are all the same shape: at
decode batch sizes these kernels leave a 256-CU part mostly idle, and none of
them is made faster by doing less arithmetic.

- two of them launch a handful of workgroups because the tile or the reduction
  was sized for a regime decode never enters;
- one spends more time in launch overhead than in work;
- one lands on torch because a tuned table keyed on `(N, K)` has no entry for
  the shape and does not fall back to a neighbour.

Together they are **+5.7%** end to end on that configuration.

## Modifications

**`moe`: fold the padded-row fill into the shared-expert append kernel.**
`_post_process_topk_ids` bracketed the aiter shared-expert append with two
separate fills over the padded region -- one for the routed ids, one for the
weights -- three launches for a shape whose total work is a couple of
microseconds, once per MoE layer per step. The append kernel already writes
every one of those elements, so it fills the padded region itself. The id fold
requires EPLB remap off, since it relies on `pad_fill_id = 0` commuting with
`remap(0) = 0`; the weight fold additionally excludes the per-rank shared-slot
kernel, which has no shared-slot weights to zero. Where either precondition
does not hold, the separate fills run exactly as before.

**`mla`: size the absorb BMM tiles for decode.** aiter's config table has no
entry for the MLA absorb shapes, so decode falls into a bucket tuned for square
GEMMs (`BLOCK_SIZE_M=64, BLOCK_SIZE_N=256`). The grid is
`(heads, cdiv(M, BM) * cdiv(N, BN))`, so at 16 heads per rank and `N <= 512`
that launches 16-32 workgroups on a 256-CU part: starved of workgroups, not of
bandwidth or flops. This sizes the tile so the grid covers the machine and then
stops -- it does not keep splitting, because the kernel quantizes its own A tile
per token group, so every extra workgroup repeats that work (at M=200/N=512 an
unbounded split is 3.7x slower than the starved table entry).

**`spec`: split the vocab-wide speculative softmax across CTAs.** Speculative
sampling reduces across the vocabulary at every draft step and at verify. torch
reduces each row with one block, so at the row counts speculation actually runs
(1 to 32) a 154880-wide row occupies a handful of blocks, and it is read three
times. `temperature_softmax()` splits each row across CTAs -- partial
max+sumexp, an online-softmax merge, then normalize -- and folds the temperature
divide into the first pass, which drops the separate pass that materialized
`logits / temperatures`. It hands the call back to torch above the row count
where one block per row already fills the GPU, so callers use it
unconditionally.

`fast_sample`'s argmax gets the same treatment by routing it to the existing
`row_argmax()`, which already lands this optimization for the dspark accept
path. No second implementation is added: a split argmax written for this path
is 4.7-42% faster below 32 rows but 3x *slower* above it, where it fell back to
torch, and those are the verify row counts at higher concurrency.

**`linear`: route the bf16 decode shapes aiter's tuned table misses.** The aiter
tuned GEMM keys its table on `(N, K)` and does not fall back to a neighbour, so
a shape the table never saw lands on torch. A decode step hits one of those 79
times -- the MLA q up-projection, `(2048, 2048)` -- where torch runs at 8.4 us
against a 1.05 us weight-bandwidth roofline while aiter's own Triton a16w16
kernel does it in 5.0 us. What is missing is the routing, not a kernel.

The gate is `K` rather than a list of shapes: a list keyed on `(N, K)` is what
makes the aiter table miss these shapes to begin with, and a different tensor
parallel split moves every `N`. It is also bounded in the row count, because
what torch is slow at is the weight-bandwidth-bound regime decode lives in and a
prefill chunk is its opposite -- a 32768-token chunk is 1.25-1.44x *slower* on
the Triton kernel, so prefill must not be routed. `lm_head`, `(19360, 6144)`, is
1.33x slower there and stays where it was.

## Accuracy Tests

Every change is either bit-identical by construction or checked against a
reference before any timing.

| change | property | how it is checked |
|---|---|---|
| moe padded fill | bit-identical | the append kernel already writes those elements; folded only where the preconditions above hold |
| mla absorb tiles | bit-identical | same kernel, different tile; compared at every admitted M |
| `temperature_softmax` | fp32-accurate | vs a float64 reference, not vs torch, which is not ground truth at this width |
| `row_argmax` routing | bit-identical | vs `torch.argmax`, including the sampled index and the `gather` that consumes it |
| linear routing | bit-identical at M=1 | max rel diff 1.7e-4 at M=6, with the error against a float64 reference *equal* to torch's -- not accuracy traded for speed |

## Speed Tests and Profiling

### Kernel level

server or model weights. It runs both arms in one process and interleaves them

the figure reported is the ratio's spread, not either arm's.

### What this does not claim

Neither figure is a position on a published curve. Both are paired A/B deltas on
one configuration, taken with hierarchical cache off, so they are not comparable
to a leaderboard point.

The end-to-end numbers were taken with the local split argmax described above
rather than with `row_argmax`; the difference between the two is ~1.5 us of a
12.6 ms decode step at these batch sizes, so the tables were not re-taken. The
trace-replay arms are one read each, so drift is not bracketed there; only the
first harness has repeat reads (0.59% on the base side) to bound its own noise.

+"""Split-row temperature softmax for low-row-count sampling workloads."""
+
+import torch
+import triton
+import triton.language as tl
+
+# Split low-row-count reductions across CTAs and fuse temperature scaling.
+_MIN_BLOCK = 2048
+_TARGET_CTAS = 512
+ROW_LIMIT = 32
+
+
+@triton.jit
+def _partial_max_sumexp_kernel(
+    logits,
+    temperatures,
+    partial_max,
+    partial_sum,
+    logits_row_stride,
+    vocab_size,
+    num_splits,
+    BLOCK: tl.constexpr,
+):
+    row = tl.program_id(0).to(tl.int64)
+    split = tl.program_id(1)
+    t = tl.load(temperatures + row)
+    offsets = split * BLOCK + tl.arange(0, BLOCK)
+    mask = offsets < vocab_size
+    x = tl.load(
+        logits + row * logits_row_stride + offsets,
+        mask=mask,
+        other=-float("inf"),
+    )
+    x = x / t
+    block_max = tl.max(x, axis=0)
+    # Fully masked splits contribute zero without evaluating -inf - (-inf).
+    safe_block_max = tl.where(block_max == -float("inf"), 0.0, block_max)
+    block_sum = tl.sum(tl.where(mask, tl.exp(x - safe_block_max), 0.0), axis=0)
+    out_offset = row * num_splits + split
+    tl.store(partial_max + out_offset, block_max)
+    tl.store(partial_sum + out_offset, block_sum)
+
+
+@triton.jit
+def _combine_kernel(
+    partial_max,
+    partial_sum,
+    row_max,
+    row_sum,
+    num_splits,
+    BLOCK: tl.constexpr,
+):
+    row = tl.program_id(0)
+    offsets = tl.arange(0, BLOCK)
+    mask = offsets < num_splits

+    s = tl.load(partial_sum + row * num_splits + offsets, mask=mask, other=0.0)
