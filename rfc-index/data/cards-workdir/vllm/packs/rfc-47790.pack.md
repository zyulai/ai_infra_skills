## 正文(PRD / 提案全文)

### Motivation.

vllm/v1/attention/backends/flashinfer.py has grown and supports too many kernels at this point. Each has diverse set of features, [standard attention support matrix](https://github.com/vllm-project/vllm/blob/main/docs/design/attention_backends.md#standard-attention-mha-mqa-gqa-backends) captures the support. 

However, we still have variety of backends within each of these wrappers, that make it too complex to add any new features. 

Broadly, these are the supported features from native flashinfer `BatchPrefill*Wrapper` & `*BatchDecode*Wrapper` api. Note that this api also exposes the trtllm_batch* api when `trtllm-gen` backend is supported. 

  | FlashInfer Prefill API / backend | Arch | FP8 compute | FP8 KV | SWA | NVFP4 KV | LSE return |
  | --- | --- | --- | --- | --- | --- | --- |
  | `BatchPrefillWithPagedKVCacheWrapper`, `auto` (routes to fa2 or fa3) | SM80, SM90, SM100 | Yes | Yes | Yes | Yes | Yes |
  | `BatchPrefillWithPagedKVCacheWrapper`, `fa3` | SM90 | Yes | Yes, only if Q is FP8 | Yes | No | Yes |
  | `BatchPrefillWithPagedKVCacheWrapper`, `trtllm-gen` | SM100, SM103 | Yes | Yes | Causal: Yes; Non-causal + SWA: No | Yes | Yes |
  | `BatchPrefillWithRaggedKVCacheWrapper`, `auto` | SM80, SM90, SM100 | No | Yes | Yes | Yes | Yes |
  | `BatchPrefillWithRaggedKVCacheWrapper`, `fa2` | SM80, SM90, SM100 | No | Yes | Yes | Yes | Yes |
  | `BatchPrefillWithRaggedKVCacheWrapper`, `cutlass` |  SM100, SM110 | Yes | Yes | Yes | No | Yes |

And for decode - 
 
  | FlashInfer API / backend | Arch | FP8 compute | FP8 KV | SWA | NVFP4 KV | LSE return |
  | --- | --- | --- | --- | --- | --- | --- |
  | `BatchDecodeWithPagedKVCacheWrapper`, `auto/fa2` tensor-core | SM80, SM90, SM100 | No | Yes | Yes | Yes | Yes |
  | `BatchDecodeWithPagedKVCacheWrapper`, `fa3` | SM90 | Yes | Yes, only if Q is FP8 | Yes, if FA3 checks pass | No | Yes |
  | `BatchDecodeWithPagedKVCacheWrapper`, `trtllm-gen` | SM100, SM103 | Yes | Yes | Yes | Yes | Yes |

For the standard FlashInfer prefill/decode wrapper paths, backend="auto" resolves to FA3 when FA3 eligibility checks pass, otherwise FA2. It does not auto-select cuDNN, cutlass, cute-dsl, or trtllm-gen. Also note that NVFP4 KV Cache support for attention kernels is available for backend=`fa2` or backend=`trtllm-gen`. In the current code, we only wire through `trtllm-gen`.  When fa2 backend is selected for nvfp4 kv cache, kv is dequantized to `bfloat16` or `float16` for attention compute. This is in place for NVFP4 compatibility with pre-blackwell from flashinfer 0.6.13 and currently not supported through vLLM.


For the trtllm-gen api, the support matrix looks similar to the selected `trtllm-gen` backend.

 | TRTLLM API / backend | Arch | FP8 compute | FP8 KV | SWA | NVFP4 KV | LSE return |
 | --- | --- | --- | --- | --- | --- | --- |
 | `trtllm_batch_context_with_kv_cache`| SM100, SM103 | Yes | Yes | Causal yes; non-causal + SWA rejected | Yes | Yes |
  | `trtllm_batch_decode_with_kv_cache`, `xqa` | SM90, SM120, SM121 | No FP8 Q | Yes | Yes | No | No |
  | `trtllm_batch_decode_with_kv_cache`, `trtllm-gen`| SM100, SM103 | Yes | Yes | Yes | Yes` | Yes |



### Proposed Change.

Phases -

- [ ] 1. Split the backends in place to enable clean separation and phase 1 testing. https://github.com/vllm-project/vllm/pull/47786
- [ ] 2. Add support for flashinfer_gqa api + DCP + spec decode
- [ ] 3. Split to two files flashinfer_gqa.py and trtllm_attention_gqa.py

I will be testing with existing tests that cover flashinfer & trtllm api backends and running gsm8k on three models - 
1. Llama 3.3 70B
2. GPT OSS
3. nvidia/Qwen3.5-397B-A17B-NVFP4

To ensure compatibility, I will test Spec-decode, DCP, FP8 KV Cache, NVFP4 KV Cache features on SM90 and SM103 with both

Based on my local testing, I combine (1) and (3) into a single PR.
