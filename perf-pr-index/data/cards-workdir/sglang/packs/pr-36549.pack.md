# MiniMax-M3: allocate the lightning-indexer K cache in fp8 on gfx95

MiniMax-M3's sparse attention keeps a second, much narrower KV cache — the
lightning-indexer K cache — whose only job is to produce the per-block scores
that pick which KV blocks the main attention reads. It is sized over every
sparse layer at `head_num=1, head_dim=sparse_index_dim`, and on ROCm it was
allocated in the model dtype (bf16) while the main K/V follow
`kv_cache_dtype`. This PR allocates it in `fp8_e4m3fn` on gfx95 (MI350/MI355)
behind `SGLANG_OPT_MINIMAX_M3_FP8_INDEX_CACHE`, exactly halving that pool. It
is a widening mode — bf16 q against fp8 k in the score kernels — which is the
same contract `m3_fp8_attn_gemm_enabled` already uses for the SM100 fp8
attn-GEMM path; this change makes the same `index_dtype=fp8` choice reachable
on gfx95 without requiring fp8 main KV. The Triton qk-norm-rope kernel now
stores into the index cache in *that cache's* dtype rather than q's, so the
value is rounded once from fp32 instead of twice through bf16 (a no-op cast
when the two dtypes match).

The change is **selection-only**: `dtype=self.kv_cache_dtype` for the main
attention K/V is untouched, and only `index_dtype` moves.

## Changes

- `KVCacheConfigurator.minimax_sparse_index_dtype()` is the single source of the
  index dtype. Both the pool builder and `pool_configurator`'s per-token cell
  size call it, so the sizing cannot drift from the allocation (same pattern as
  `is_unified_kv_fp8()` for DSV4).
- gfx95 only: OCP `e4m3fn` is only safe where it is native; on gfx94x sglang's
  fp8 is `e4m3fnuz` (max 224), so MI300 keeps the bf16 index cache and the flag
  is a no-op there.
- The flag defaults to `True`, i.e. on for gfx95 MiniMax-M3 sparse serving.
  This is a precision change, not a free fusion — see Accuracy below. Set
  `SGLANG_OPT_MINIMAX_M3_FP8_INDEX_CACHE=0` for a bf16 index cache.

## Behaviour on other platforms

- **CUDA, default config:** no change. The index dtype still resolves to the
  model dtype and the Triton store cast is an identity.
- **CUDA SM100 with fp8 attn-GEMM mode (`m3_fp8_attn_gemm_enabled`):** the index
  cache was already fp8 there, but the cell-size estimate counted it at bf16.
  It now counts the real fp8 size, so this configuration gets slightly more
  `max_total_num_tokens` at the same `mem_fraction_static`. Not measured.
- **MI300 (gfx94x) / NPU:** no change.

## Memory

The index pool is allocated as
`size x page_size x 1 x idx_head_dim x sizeof(index_dtype)` per sparse KV layer,
so bf16 -> `fp8_e4m3fn` is an exact **2x reduction of the index cache** with no
change to the main K/V pool.

Measured on 8x MI350X (gfx950), MiniMax-M3-MXFP8, TP8,
`--mem-fraction-static 0.80`, one boot per row, identical launch command
throughout (only the flag / the commit under test differs):

| run | index K cache | max_total_num_tokens | available_gpu_mem |
|---|---|---|---|
| baseline (`SGLANG_OPT_MINIMAX_M3_FP8_INDEX_CACHE=0`) | bf16, 43.34 GB | 3189113 | 41.12 GB |
| commit 1 -- fp8 index cache | fp8, 21.67 GB | 3189113 | **62.98 GB** |
| commit 2 -- + cell-size accounting | fp8, 25.05 GB | **3686422** (+15.6%) | 45.22 GB |

Commit 1 halves the index pool exactly (43.34 -> 21.67 GB), but the saving
surfaced as *free GPU memory* rather than capacity: the per-token cell-size
estimate that converts the profiled byte budget into `max_total_num_tokens`
still assumed a bf16 indexer, so the pool was sized as if nothing had been
saved and `max_total_num_tokens` did not move.

Commit 2 makes that estimate use the same dtype the pool is actually built
with. The saving then becomes capacity instead — **+15.6% `max_total_num_tokens`
at the same `mem_fraction_static`** — and free GPU memory returns to roughly the
baseline level, i.e. the freed bytes are spent rather than stranded.
`max_running_requests` is 2048 on all three rows.

Load-tested on the final state at bs44 / 80000 input = 3,520,000 tokens, beyond
the 3,189,113 the first two rows can hold: runs clean, peak token usage 0.95, no
OOM and no retraction.

## Validation

No unit test is added: the sizing/allocation agreement is enforced by the
shared `minimax_sparse_index_dtype()`, and a dtype-selection test would only
restate its condition. Evidence is end-to-end (memory, perf and gsm8k above).
These numbers were measured before the `kvcache.cuh` change was dropped from
this PR (it is no longer touched; the slot assert does not break hipGraph
capture) and before the latest merge of `main`; they have not been re-run.

## Note on the launch command

`--moe-runner-backend aiter` is **not honoured on current `main`** for mxfp8. Arg resolution logs:

```
mxfp8 quantization supports only cutlass, deep_gemm, flashinfer_trtllm,
flashinfer_trtllm_routed, triton backends. Overriding 'aiter'.
```

and falls back to **triton**. Both sides of this A/B therefore ran the Triton MoE runner, so the comparison is apples-to-apples and the deltas stand — but `AITER_CONFIG_FMOE` is inert under this configuration and the aiter MoE path is *not* what was measured. The flag is kept in the command above only because it matches the invocation actually used; anyone reproducing will get triton and should see the same numbers.
