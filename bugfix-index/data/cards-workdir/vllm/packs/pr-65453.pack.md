## 正文(PR 描述)

## Overview

Follow-up to #64984. When an encoder CUDA graph replay has fewer sequences than the capture, the manager's default copy zero-fills the end of `cu_seqlens`. A zero after the real total offset makes the padded sequences negative-length. FlashAttn and the other non-FlashInfer ViT backends then produce wrong encoder output for the real items.

This PR:

- Changes the manager default for cumulative keys (`cu_seqlens`, `cu_window_seqlens`) so it repeats the last value (suggested by @Pb314314). Other buffers are still zero-filled.
- Moves the FlashInfer `cu_seqlens` padding helper to `MMEncoderAttention.get_cu_seqlens_padding_logics`, next to `maybe_recompute_cu_seqlens`, which builds that layout. It uses the same OOT dispatch as `maybe_recompute_cu_seqlens`, so an OOT attention that changes the layout can also override the padding.

## Claims

- Models fixed by the new default:
  - GLM-4.1V/4.5V and the models that inherit its config (GLM-OCR, GLM-5.3-Flash).
  - Qwen2-VL, when `encoder_cudagraph_max_vision_items_per_batch` is set.
  - In both cases, video-enabled capture pads `cu_seqlens` to `max_frames_per_batch`, while image replays pad only to `max_batch_size`.
- FlashInfer backend: the packed two-section layout still needs its own padding. These models now get it from `MMEncoderAttention.get_cu_seqlens_padding_logics`:
  - Qwen2.5-VL and Qwen3-VL, which previously registered `_pad_flashinfer_cu_seqlens_buffer` themselves.
  - GLM-4.1V. With video enabled, image replays used a smaller batch bucket than the capture.
  - Kimi-K2.5. Capture pads to `max_batch_size + 1` but replays are unpadded, so the buckets differ once `max_batch_size >= 8`.
- Refactoring: per-model registrations that are now identical to the default are removed:
  - Qwen2.5-VL, Qwen3-VL and LFM2-VL: `_pad_cumulative_seqlens_buffer`.
  - Kimi-K2.5, DeepSeek-V4.1 and MiniMax-M3: `pad_cu_seqlens`.
- Pixtral, Cohere Compass and MiniMax-M3 also call `get_cu_seqlens_padding_logics`, so every encoder-CG model whose `cu_seqlens` comes from `maybe_recompute_cu_seqlens` takes its padding from one place. Without an OOT override, their padding is unchanged. See Details.

## Details

- Removed registrations are equivalent to the new default:
  - Kimi-K2.5 and DeepSeek-V4.1 truncated with `min(src, dst)` when `src` was longer than `dst`. That branch never runs: each image is one sequence, so a replay has at most `max_batch_size + 1` offsets, and both models capture `max_batch_size + 2`.
- Newly wired models keep their in-tree padding:
  - MiniMax-M3 rejects FlashInfer, so it gets `{}` and the default, as before.
  - Pixtral and Cohere Compass (image-only) capture and replay `cu_seqlens` at the same length. Under FlashInfer, the helper then reduces to a plain copy.
- Not wired: DeepSeek-V4.1, Kimi-K3 and Qwen2-VL build their own `cu_seqlens` instead of calling `maybe_recompute_cu_seqlens`. They rely on the manager default.
- OOT: vllm-ascend overrides `EncoderCudaGraphManager._run_budget_graph` with its own copy of the old lookup, so the new default doesn't apply there. Its FIA path drops non-increasing `cu_seqlens` endpoints, so zero-fill and repeat-last give the same result.
- Not a duplicate: no other open PR changes this padding. #66067 (@Pb314314) is a pure refactor of the grid_thw encoder CG code and does not touch `cu_seqlens` padding.
