## 正文(PR 描述)

## Purpose

Re-lands #53020 (commit `83cadd65d9`), reverted in #59805. The diff is byte-identical to the reverted commit (`git patch-id` matches). Original bug report: #53019. Supersedes #60266, which carries the same diff; thanks @DiegoCao for preparing it.

`NemotronParseForConditionalGeneration` builds a standalone `ParallelLMHead` and only populates it from `lm_head.*` weights. A checkpoint that sets `tie_word_embeddings` and ships no `lm_head.weight`, such as `nvidia/NVIDIA-Nemotron-Parse-2.0`, therefore keeps a randomly initialized output head. Nothing reports it: the server starts, reports healthy, and returns garbage.

## Why this can land now

#59805 did not revert because the fix was wrong. It reverted because the `NVIDIA-Nemotron-Parse-2.0` case added to `test_nemotron_parse.py` failed in the nightly full CI run while loading that checkpoint's tokenizer, before any model code ran:

```
transformers/tokenization_utils_tokenizers.py:120 in convert_to_native_format
    local_kwargs["tokenizer_object"] = TokenizerFast.from_file(fast_tokenizer_file)
E   Exception: DuplicatePatternError: [225, 131, 156] at line 449472 column 1
```

The cause was the CI pin `tokenizers==0.23.1`. The 2.0 `tokenizer.json` uses an NFKC normalizer, and 14 pairs of its added tokens become identical after normalization (for example `ნ` U+10DC and `ჼ` U+10FC both normalize to `e1 83 9c`, the `[225, 131, 156]` in the error). 0.23.1 rejects the duplicates when it builds its matcher; 0.23.2 (daachorse 1.0.1 → 3.0.0, huggingface/tokenizers#2050) accepts them. #59796 bumped the pin.

Under the current CI pins (`tokenizers==0.23.2`, `transformers==5.18.0`), `AutoTokenizer.from_pretrained("nvidia/NVIDIA-Nemotron-Parse-2.0")` loads (`TokenizersBackend`, vocab 72,249).

## Test Plan

- `tests/models/multimodal/generation/test_nemotron_parse.py::test_models`: the `nvidia/NVIDIA-Nemotron-Parse-2.0` parametrization is restored. It is the only coverage of the tied-head path and is the case that must be green before merge.
- That test runs in `Multimodal Models (Extended Generation 1)`, which is `optional: true`, so it did not run on #53020's PR CI and only surfaced in the nightly run. Could a maintainer include that step when triggering CI here?
- `nvidia/NVIDIA-Nemotron-Parse-v1.2` stays in the same parametrization and is unaffected (see below).

## Test Result

Out-of-CI validation on one RTX 6000 Ada, serving the 2.0 checkpoint with `vllm serve … --dtype bfloat16 --trust-remote-code --limit-mm-per-prompt '{"image": 1}'`, one greedy request (50 max tokens) with the model's documented control-token prompt on the deterministic test image from the model repo's `test_golden.py`:

| build | output |
|---|---|
| vLLM v0.30.0 without this patch | `<s><s><s>…` (50 × `<s>`) |
| **v0.30.0 with this patch** | `<x_0.3906><y_0.5969>\begin{tabular}{ccccc}\n\end{tabular}<x_0.6084><y_0.6367><class_Table>` |

The patched output is byte-identical to what the model's own shipped workaround (`vllm_tied_patch/sitecustomize.py` in the HF repo) produces on the same input.

Why v1.2 cannot be affected: the two checkpoints differ exactly where the new branch reads.

| checkpoint | `tie_word_embeddings` (config / `config.decoder`) | `lm_head.weight` in checkpoint | tensors |
|---|---|---|---|
| `NVIDIA-Nemotron-Parse-v1.2` | `false` / `false` | present | 667 |
| `NVIDIA-Nemotron-Parse-2.0` | `true` / `true` | absent | 666 |

The tie goes through `ParallelLMHead.tie_weights()`, so it routes via `quant_method.tie_weights` rather than assigning `.weight` directly.

`ruff check` and `ruff format --check` pass on both files.
