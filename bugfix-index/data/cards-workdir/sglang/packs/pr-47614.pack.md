## Summary

**Fixes #47613.** In asynchronous PP decode, proxy tensors received on a communication stream may be consumed later on the forward stream. When the previous Python reference is dropped before the queued forward uses the data, the CUDA caching allocator can reuse the receive storage and corrupt model outputs. This was observed as long token-0 runs at `--pp-async-batch-depth > pp_size / 2`.

## Changes

- In `_pp_launch_batch`, call `record_stream(self.forward_stream)` for each non-CPU proxy tensor before `run_batch`, protecting storage until the forward stream has finished using it.
- Update the existing idle-counter fixture to return `None` for the simulated first PP stage.
- No global synchronization or new execution-order barrier is introduced: **`record_stream` records allocator lifetime, not stream ordering**.

## Validation

Kimi-K3, 8×B300, fake PD transfer; affected requests were identified by ≥20 consecutive token-0 outputs.

| PP/TP shape | Async depth | Before | After |
| --- | ---: | ---: | ---: |
| PP2 × TP4 | 2 | 51/192 | **0/192** |
| PP2 × TP4 | 3 | 98/192 | **0/192** |
| PP2 × TP4 + DCP4 | 2 | 59/192 | **0/192** |
| PP4 × TP2 | 3 | 6/192 | **0/192** |
| PP4 × TP2 | 4 | 19/192 | **0/192** |

Receive-vs-forward checksums mismatched in the unfixed runs (76 and 378 of ~7,500 comparisons), but not in the fixed runs. A later reported exact-fix comparison and dedicated-communication-stream experiments are documented in the archive below; those evidence groups are **not interchangeable**.

Existing 4×H100 PP GPU tests (2 compatibility + 6 speculative tests), and prior-head Base/AMD CI passed. The mocked-only `record_stream` unit test was removed in review because it could not reproduce allocator reuse.

## Scope and limitations

This is a correctness/lifetime fix, **not a performance optimization**. Historical 8×B300 experiments used v0.5.22 and fake transfer; real two-node PD, all PP event-loop combinations, and full post-merge GPU runtime coverage were not established. Historical CI passes are explicitly scoped to the corresponding tested heads.

## Motivation

Fixes #47613. With `--pp-async-batch-depth > pp_size / 2`, the PD decode loop returns runs of token 0 for many requests (Kimi-K3 PP2 × TP4 depth 2: 51–98 of 192).

A downstream stage gets its proxy tensors from `recv_tensor_dict`, which allocates them on another stream; the forward stream reads them later. `event_loop_pp_disagg_decode` drops the previous reference before posting the next recv. When enough forwards are queued, the allocator gives the next recv the same block and it overwrites data a queued forward has not read yet. Checksums taken right after the recv and right before the forward differ in 76 and 378 of ~7500 comparisons on two runs; with this change they never differ.

## Modifications

- `_pp_launch_batch`: before `run_batch`, call `record_stream(self.forward_stream)` on each non-CPU tensor in `pp_proxy_tensors`. Every PP event loop goes through `_pp_launch_batch`, so they share this fix location; runtime validation did not exercise every loop configuration; the first stage passes `None` and is unchanged.
- Existing idle-counter test: make the mocked proxy receive return `None` for the simulated rank-zero scheduler, matching the real receive path. A bare `Mock()` previously reached the new tensor iteration and caused a fixture `TypeError`.

- The earlier DCP CI fixture correction from mickqian’s [#47736](https://github.com/sgl-project/sglang/pull/47736), source commit `be43d568ca8115e173bd4b9f5d106a3060ae1f8b`, is now included in main and is no longer part of this PR's cumulative diff.

Follow-up runs on 2026-10-31 used `SGLANG_PP_COMM_OVERLAP=1` on v0.5.22, Kimi-K3, 8 × B300, and fake PD. The server log confirmed `PP tensor communication overlap enabled on a dedicated CUDA stream`. Synthetic random-token prompts targeted 64,000 input tokens and 1,000 output tokens, with random range ratio 0. C is maximum request concurrency; N is the number of requests. The output check counted requests containing at least 20 consecutive token 0 (`!` for this tokenizer).

These runs used the earlier CUDA-equivalent fix: `record_stream(current_stream())` inside `forward_stream_ctx`, guarded by `tensor.is_cuda`. This extends the output-level evidence to the dedicated communication-stream configuration; it is not an exact-diff rerun, a main runtime test, or real two-node PD validation. Checksum instrumentation was not enabled in these runs.

## Applicability to main

The lifetime-critical logic is the same in `release/v0.5.22` and main at `2f6e7f347526034a173424cad0e7a72a5fb61ad2`: the disaggregated decode loop clears `pp_proxy_tensors` before the next receive; `_pp_recv_proxy_tensors` wraps the received tensors without recording the forward stream; and `_pp_launch_batch` submits `run_batch` on the forward stream without recording those inputs. Main is therefore expected to be affected by the same allocator-lifetime race based on source comparison. The B300 runtime reproduction and fix validation were completed on v0.5.22; that B300 reproduction was not separately repeated on main. Upstream CPU and PP integration results are listed below. This comparison concerns the bug-relevant lifetime logic, not byte-for-byte identity of the entire scheduler file.
