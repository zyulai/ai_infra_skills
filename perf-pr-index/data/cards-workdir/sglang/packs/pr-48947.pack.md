## Motivation

With `--enable-layernorm-sp` every EXTEND forward runs sequence-parallel. The SP collectives (the entry scatter, all-gather + GEMM and GEMM + reduce-scatter on the attention projections, the routed-expert all-to-all) cost about the same per layer whatever the pass size, so a small extend can be slower sequence-parallel than on the replicated path decode already uses, while a large chunk is faster. Short follow-up turns, small chunks and prefix-cache hits land on the small side.

## Modifications

- New `--layernorm-sp-min-tokens N`: a pass runs sequence-parallel only when it has more than N tokens. It is a server argument because the crossover is a property of the deployment (which all-reduce sizes the replicated path's custom all-reduce covers), not of the model. 0, the default, keeps every extend sequence-parallel.
- `runs_sp(forward_mode, num_tokens)` decides from the pass's token count before the entry scatter, and every in-tree caller passes it (the model entry, the layer-boundary entry, the DFLASH aux-tap gather, the input-embeds exit, `maybe_exit_gather` and ERNIE 5.5's `logits_rows`), so the entry and every exit take the same decision.
- In a captured prefill graph the entry decides on the bucket size while the exit outside the graph sees the real count; they agree because the threshold must be a captured bucket or at or above the largest one. That is checked at argument resolution, together with a negative value and the flag without `--enable-layernorm-sp`. Callers asking about decode / verify passes, which never run SP, may omit the count; an extend pass without it raises.
- Docs: the new argument in `server_arguments.mdx`. Tests: `test_layernorm_sp.py` (the decision per pass size, the bucket check, entry / exit agreement).

## Accuracy Tests

Setup: GB300 x4, `lmsysorg/sglang:nightly-dev-cu13-20261106-858073e4` with this PR's files on top, `meta-models/Muse-Spark-Open-816B-A42B-NVFP4` at TP4 / EP4 with `--enable-layernorm-sp`, DFLASH (`RadixArk/Muse-Spark-Open-DFlash2`, 8 draft tokens, real acceptance), FP8 KV cache, HiCache. Stock and PR arms alternate on the same node. gsm8k through sgl-eval: 1319 questions, temperature 1.0, top-p 1.0, max 16384 tokens, seed 42. gsm8k prompts average about 225 tokens, so with `--layernorm-sp-min-tokens 1280` every gsm8k prefill takes the new replicated path.

## Speed Tests and Profiling

Prefill latency per pass size: `python3 -m sglang.benchmark.serving --dataset-name random-ids --random-range-ratio 1 --random-output-len 1 --max-concurrency 1 --num-prompts 32 --flush-cache`, prompt lengths 128 to 8192, server at `--max-running-requests 16`, after an untimed pass of 8 prompts at each length. TTFT here is one prefill pass. Passes of 1280 tokens or fewer take the replicated path with this PR; longer ones stay sequence-parallel and should match stock. Stock and PR servers alternate twice on the same node (stock, PR, stock, PR) with two repeats per server, so each cell is the mean over four runs of the run's mean TTFT; the fastest of the four runs is in brackets.

Below 1024 tokens the replicated path saves 7-17 %. From 1536 tokens up both arms take the same path, and runs drift by up to 10 % in either arm (at 8192 tokens each run sits at 153-156 ms or at 168-174 ms, whichever arm it is; both PR repeats of the first pair and one stock repeat of the second sat at the slower level). That drift is the +1 to +3 % in the change column there: the fastest runs agree within 1.2 %. At 1024 and 1280 tokens the two paths cost about the same (fastest runs -0.7 % and +3.5 %), so the crossover on this deployment is about 1024 tokens.

The threshold has to be a captured prefill bucket; main's default buckets include every multiple of 256 from 1280 to 4096, so 1280 is valid with the default `--cuda-graph-backend-prefill breakable`.
