## 正文(PR 描述)

## Purpose

The FlashInfer one-shot Lamport all-reduce signals programmatic-dependent- launch (PDL) completion before committing its output buffer when trigger_completion_at_end=False, so the next PDL-launched kernel reads the uninitialized buffer and produces NaN. The fused AR+RMSNorm pass set the flag to `num_tokens <= PDL_ADVANCE_LAUNCH_TOKENS` (#43103) -- exactly the batch=1 / spec-decode shapes, where the one-shot path is always selected -- so every decode step NaNs under tensor parallelism.

Gate on use_oneshot instead: the two-shot path is internally synchronized and keeps the early completion (its perf win); only the one-shot path is forced to complete at the end.

Complementary to vllm-project/vllm#40557 (PDL early-completion perf): its `not launch_with_pdl` is safe on the two-shot path and composes with this one-shot guard.

The standalone communicator (flashinfer_all_reduce.py) shares this kernel with launch_with_pdl=True and wants the same fix, but its workspace sizing can't serve large-hidden models (fails validation before inference), so it is left for a follow-up.

Related one-shot instability in the same kernel: flashinfer-ai/flashinfer#1223.

assisted by claude

## Test Plan

Repro (TP>1 + FlashInfer trtllm fusion; e.g. Kimi-K2.6, eagle3 MTP):

```
  vllm serve <model> --tensor-parallel-size 4 \
    --speculative-config '{"method":"eagle3","num_speculative_tokens":4}' \
    --compilation-config '{"mode":3,"pass_config":{"fuse_allreduce_rms":true}}'
  # then, at concurrency=1:
  curl $URL/v1/chat/completions -d \
    '{"model":"<m>","messages":[{"role":"user","content":"hi"}],"max_tokens":40}'
```

Without the fix, you get a lot of this type of stuff
```
"content": "", "finish_reason": "length", completion_tokens: 40 
```

## Test Result

no more NaN/all decode succeeds

current workaround is `fuse_allreduce_rms: false`
