## Overview

Process the output tiles of the fused Qwen4Exp HC up projection + gate mix kernel (#64898) N-fastest instead of M-fastest, drop the 256B L2 promotion from its TMA descriptors, and move the single-CTA / CTA-pair switch from 1024 to 1600 tokens.

## Claims

- **1.13× at M = 16384** (98.4 → 86.8 µs) and 1.16× at 32768 on GB300; 1.01–1.12× from 512 to 12000. No M is slower.
- **Bitwise-identical** output to `main`: same per-element code and K order; only the tile schedule and L2 fetch size change.
- Dispatch gates (≥ 512 tokens, SM100 family, `VLLM_BATCH_INVARIANT`, LoRA) unchanged.

At M = 16384 that is 63% → 72% of the achievable floor (62.4 µs = 436.5 MB at 7.0 TB/s, measured on-SM copy; compute floor 54.8 µs at the cuBLAS bf16 rate).

**No E2E A/B.** Output is bitwise-identical and only one kernel's tile order and fetch size change, so the E2E effect is the kernel saving: 96 calls × ~11.6 µs ≈ 1.1 ms per 16k-token prefill step (~0.4%), below serving-benchmark noise (#64898: main vs main up to 0.8%). #64898's E2E gain for this op matched its kernel-time prediction, and at this size `xn` (336 MB) far exceeds L2, so cold-L2 kernel time is representative.

## Details

**Why: better L2 reuse of `xn` lines.** A tile reads 128 B of each `xn` row per stream, and `main`'s `xn` tensor map uses 256B L2 promotion, so every fetch also brings in the neighbouring 128 B, which belongs to the next column block.

- M-fastest: the next column block runs only after all row blocks, by which time those lines are evicted (`xn` loads are `EVICT_FIRST`), so the promoted half is fetched from DRAM again.
- N-fastest: neighbouring column blocks run concurrently, so the promoted half is used, and with no promotion each tile fetches exactly its own bytes.

Order × promotion at M = 16384 (32768 in parentheses):

| | 256B promotion (`main`) | No promotion |
|---|---:|---:|
| M-fastest | 97.8 µs (193.0) | 90.6 µs (172.2) |
| N-fastest | 88.4 µs (172.0) | 87.0 µs (167.4) |

Disabling promotion recovers most of the M-fastest loss (all of it at 32768), confirming the over-fetch; N-fastest is faster in both columns, and this PR takes both. `w_up` (6.6 MB, the reason for M-fastest) stays in L2 in either order.

**Promotion per map** (paired A/B, 4 GPUs × 3 rounds, `main`-vs-`main` noise 1.000–1.001×): only `xn` matters (NONE / 64B / 128B all +1.2–2% from M = 16384, +0.6% at 4096); `lowrank`, `w_up` and the output map are flat within noise. NONE for all four maps measured the same as for `xn` alone, so the shared helper uses NONE.

**Threshold.** Crossover lies in 1537..1664 at both 152 SMs and a grid capped to 148 (B200/B300-like); anywhere there is within ~1.5% of the faster config, 1536 or 2048 lose up to 5%. 1600 is the middle.
