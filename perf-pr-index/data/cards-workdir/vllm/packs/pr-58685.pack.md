## Purpose

The JIT monitor is switched on after warmup, and it wraps TileLang's `JITImpl.__call__`. As a result, every TileLang kernel launch pays for the wrapper, including building the cache-miss key, even though nearly all of those calls hit the kernel cache. TileLang's `__call__` only calls `self.compile()` on a cache miss, so this PR hooks `compile` instead. The monitor still catches every post-warmup JIT compile, and cache hits no longer go through it.

This matters for models with many TileLang launches outside CUDA graphs. For example, GLM-5.3-Flash runs ~72 mhc TileLang calls per eager step (prefill / mixed batches).

**Not a duplicate:** I searched open PRs for jit_monitor / TileLang and found nothing related.

## Test Plan

- `pytest tests/jit_monitor/` (the fake `JITImpl` now calls `compile()` on a cache miss, like the real one).
- Microbench: 2000 `mhc_post_tilelang` calls after warmup, with the monitor off and on, on H100.
- E2E: `zai-org/GLM-5.3-Flash`, TP8 on H100, fp8 KV, MTP with 5 speculative tokens, async scheduling. Benchmark: `vllm bench serve` with random 1024 in / 128 out, each point run twice.

## Test Result

Unit tests: 25 passed, 7 skipped.

Microbench (µs per call):

| | monitor off | monitor on |
|---|---|---|
| main (wrap `__call__`) | 15.7 | 25.9 |
| this PR (wrap `compile`) | 15.5 | 15.6 |

That's ~10 µs × ~72 calls ≈ 0.7 ms of CPU per eager step removed on GLM-5.3-Flash.

E2E, mean TTFT / median TTFT / mean TPOT (ms), average of 2 runs:

| | c=1 | c=8 | c=32 |
|---|---|---|---|
| main | 136.6 / 138.8 / 11.09 | 226.2 / 188.6 / 21.87 | 338.2 / 319.9 / 45.04 |
| this PR | 133.0 / 135.5 / 11.11 | 219.2 / 187.0 / 21.45 | 331.3 / 312.8 / 45.04 |

TTFT improves 2–3%. TPOT is within noise because decode runs under CUDA graphs. The change is small, but so is the diff, and the monitor stays functionally the same.
