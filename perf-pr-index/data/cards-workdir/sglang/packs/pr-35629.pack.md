## Motivation

<!-- Describe the purpose and goals of this pull request. -->

DFlash2 ([#35371](https://github.com/sgl-project/sglang/pull/35371)) landed on main as the successor to DFlash. It uses a block-diffusion drafter with local grouped convolutions and a candidate selector.

First-generation DFlash drafts already run on Ascend NPUs ([#23122](https://github.com/sgl-project/sglang/pull/23122), [#31739](https://github.com/sgl-project/sglang/pull/31739)), but DFlash2 checkpoints could not serve on NPU because the target verification path assumed CUDA behavior.

This PR adapts the DFlash2 draft and verification paths for Ascend NPUs while preserving the existing CUDA behavior.

The validated Ascend environment includes `triton-ascend`; this PR assumes Triton is available in the runtime environment.

## Modifications

<!-- Detail the changes made in this pull request. -->


- Fix target verification metadata handling on NPU.
  - Non-NPU devices preserve the existing `skip_attn_backend_init=True` behavior because `prepare_for_verify` has already planned the attention metadata.
  - NPU passes `None`, allowing the target forward path to initialize the required attention metadata.
  - This prevents the NPU graph runner from skipping initialization and accessing an uninitialized `raw_num_token`.

- Align DFlash2 selector verification with the existing NPU behavior of EAGLE and first-generation DFlash.
  - On CUDA, selector sampling verification remains unchanged.
  - On NPU, the full-vocabulary selector sampling verification is skipped and target verification uses argmax.
  - The full-vocabulary path scatters a dense `[batch_size, gamma, vocab_size]` draft-probability buffer and performs vocabulary-wide operations whose cost does not shrink with the verification window.
  - This is an NPU-specific performance policy, not a limitation of the selector algorithm itself: the probability-based path can execute in the validated `triton-ascend` environment, but it added about 6 ms of TPOT on the tested 910C setup and is unnecessary for lossless greedy requests.

- Keep draft proposal and target verification consistent on NPU.
  - Selector sampling support is resolved once as a worker-level capability; graph-captured and eager paths consume that semantic state instead of repeatedly checking the device.
  - The capability is disabled on NPU, forcing both selector draft paths to greedy proposal.
  - `_selector_sample` is staged only when selector sampling is enabled, and acceptance dispatches from that staged state rather than rechecking the hardware.
  - This avoids stochastic draft proposals being verified by a greedy target, which would unnecessarily reduce the acceptance length.
  - CUDA and other non-NPU devices continue to use the original request sampling parameters.

- Handle non-greedy requests on NPU explicitly.
  - The request is currently accepted.
  - Both draft proposal and target verification fall back to greedy.
  - A warning is emitted once to state that the requested sampling distribution is not preserved.
  - Lossless behavior on NPU is currently guaranteed only for greedy requests such as `temperature=0` and `top_k=1`.

- Keep DSpark NPU sampling support outside this PR.
  - This PR does not add a torch chain speculative-sampling implementation or a DSpark NPU sampling fallback.
  - The scope is limited to DFlash2 serving and greedy verification on Ascend NPUs.

- Update the Qwen3.8-27B cookbook with the DFlash2 NPU behavior, validated configuration, greedy-only losslessness boundary, and benchmark setup.

### Why the remaining NPU guards are necessary

The runtime changes contain two direct NPU decisions, each representing a separate backend constraint:

1. Selector sampling policy is decided once when the worker is initialized. Ascend currently uses greedy proposal and verification because selector rejection sampling materializes a dense `[batch_size, gamma, vocab_size]` probability buffer and performs full-vocabulary work. All downstream selector paths use the resulting capability state.
2. Target verification metadata is handled differently on Ascend. Non-NPU `prepare_for_verify()` pre-plans graph or attention metadata, while the NPU path must defer planning until DP/EP padding finalizes runtime shapes. Passing `skip_attn_backend_init=True` on NPU would incorrectly mark uninitialized metadata as ready and can make `NPUGraphRunner` access uninitialized state such as `raw_num_token`.

The existing `is_dflash_sampling_verify_available()` helper cannot replace the selector capability decision: it describes a different target-only verification implementation and using it here would change existing behavior on other backends such as HIP.

### Runtime Validation

- Verified DFlash2 on Ascend NPU with greedy decoding (`temperature=0`, `top_k=1`).
- Three repeated requests with the same prompt produced identical output hashes.
- Verified both NPU graph-enabled and eager (`--disable-cuda-graph`) execution paths.
- Non-greedy requests complete successfully and emit the expected one-time warning before falling back to greedy DFlash2 proposal/verification.
- Full deterministic non-greedy validation was not performed because the test image does not include the NPU `batch_invariant_ops` extension required by `--enable-deterministic-inference`.

### Reviewer question: non-greedy requests on Ascend

DFlash2 currently cannot preserve the requested non-greedy sampling distribution on Ascend because selector verification falls back to argmax.

The current implementation keeps the request valid, emits a warning once, and forces both the draft proposal and target verification to greedy so their behavior remains consistent.

Another option is to reject non-greedy requests explicitly instead of allowing this fallback.

Which behavior would be preferred for this PR?

1. Accept the request, warn once, and run both draft proposal and verification greedily.
2. Reject non-greedy requests on Ascend with an explicit error.

### Speedup

| Concurrency | 1 | 2 | 4 | 8 | 16 |
| --- | ---: | ---: | ---: | ---: | ---: |
| DFlash2 / baseline | 3.05x | 2.66x | 2.37x | 1.87x | 1.75x |

The end-to-end speedup decreases from 3.05x at concurrency 1 to 1.75x at concurrency 16 as target-model batching and speculative-decoding overhead become more prominent at higher concurrency.

Local profiling showed:

- Selector top-k costs approximately 0.04 ms per decode step.
- DFlash2 and NEXTN have matching kernel-level draft behavior.
- The target verification step is primarily bounded by the TP2 per-layer all-reduce floor, with approximately 43 collectives per step.
- The original full-vocabulary selector sampling verification added approximately 6 ms of TPOT on the tested setup: about 51 ms with selector sampling verification versus 45 ms with greedy verification.

Further performance work, including acceptance-length tuning and reducing verify-preparation host overhead, is outside the scope of this PR.
