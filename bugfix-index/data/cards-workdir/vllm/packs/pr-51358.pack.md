## 正文(PR 描述)

## Summary

Fix Mooncake Store persistence for Mamba `align` mode by saving the exact core-selected boundary-state blocks and keeping those physical blocks alive until every worker rank has finished the asynchronous store attempt.

This fixes a correctness bug that could persist null, stale/reassigned, or live speculative Mamba state under a valid prefix hash. A later external prefix hit could then restore poisoned recurrent state and produce garbled or runaway output.

## Root cause

Mooncake's normal save path resolved each group's source block positionally from a worker-side snapshot of the request's block IDs. That is valid for append-only attention block tables, but a Mamba `align` table is sparse and mutable:

- superseded state positions are replaced by the null block and their physical blocks are freed;
- speculative scratch blocks are relocated to different logical positions;
- the connector's block-ID mirror is append-only and does not observe those in-place changes.

Consequently, a positional Mamba save could interpret `NULL_BLOCK_ID` as a physical source, or read a block that had already been freed, reassigned, or was still speculative, while using the correct chained prefix hash as its key. Mooncake's `batch_is_exist` deduplication could then preserve the bad value and prevent a later correct save from replacing it.

The production symptom was exposed by the DSpark/EAGLE lookup path landing on an affected interior key. Without that path, a later valid CoW boundary key could win and mask the corruption.

## Design

- Core emits exact `(group_id, block_id, boundary_tokens)` entries for committed Mamba `align` boundary states, including the CoW target for a sub-block partial tail. The connector never reconstructs these source IDs positionally.
- Mooncake excludes Mamba groups from the normal positional `store_mask`; exact boundary handoffs are the only Mamba writer. The normal path also skips null or missing source IDs for every group as a defense-in-depth guard.
- The scheduler claims each accepted physical block with `BlockPool.touch()` before it can be recycled. Consumer-only roles are gated before claiming or queueing handoffs.
- Each claimed block receives a monotonic handoff ID. A one-ID/one-pin mapping makes reference release and the bounded in-flight capacity exact, even though a request-level batch ID could work while all entries in a request complete together.
- Workers report a cross-rank completion watermark. After seeing its first handoff, a rank reports watermark `0` while that handoff is pending rather than omitting metadata; this prevents aggregation from ignoring a lagging rank and releasing a block early. Dedup, successful upload, pressure drop, cancellation, and store failure are all terminal outcomes for lifetime purposes.
- The scheduler releases the connector-owned refs only through `BlockPool.free_blocks()` after the aggregated watermark says every rank is terminal. The configurable in-flight cap bounds pinned GPU blocks if acknowledgements stop; saves beyond the cap remain best-effort and are dropped.
- Resumed prefills use the tracked prefill/save boundary, not the request's original prompt length, so replayed generated tokens retain the same cross-group save coverage.
- Mamba speculative scratch relocation remains an in-table move, but now fails closed unless `BlockPool.is_block_writable()` confirms the block is non-null, exclusively owned (`ref_cnt == 1`), and unhashed. If shared or pinned speculative blocks become valid in the future, this path must use CoW instead of relocating them.

This implementation is intentionally limited to Mamba `align` mode. Mooncake Store's configuration validation rejects incompatible non-align/`all` Mamba layouts; this PR does not add `all`-mode support.

## Retention semantics

`VLLM_PREFIX_CACHE_RETENTION_INTERVAL` remains effective even though Mooncake's positional `store_mask` is false for Mamba:

1. Core `MambaManager.cache_blocks()` applies the retention policy first.
2. Only retained/materialized states receive a block hash.
3. Handoff emission skips null or unhashed blocks.
4. Mooncake stores the exact retained states from those handoffs.

Therefore dense default retention, sparse interval checkpoints, and replay-boundary behavior are preserved. External persistence is still best-effort: an eligible checkpoint may be absent if the handoff cap is reached or the store operation fails.

## Scope and overlap

This is not duplicate work:

- #50359 validates external lookup boundaries.
- #46896 and #46906 concern Mamba all-mode support and retention policy.
- #51362 independently adds the same defensive null/missing-block check to Mooncake's normal save loop. That check is included here, but this PR also removes unsafe positional Mamba saving and fixes exact source selection, asynchronous lifetime, retention-aware handoff, partial-tail handling, and speculative ownership. In that sense, this PR subsumes #51362's behavior rather than relying on it.
