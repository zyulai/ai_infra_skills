## Summary

`per_token_group_quant_8bit` stages every group through shared memory because it
reads the group twice: once to reduce absmax, once to quantize. At `group_size`
128 a group of 16-bit input is 256 B, which fits in registers, so both the
staging and the `__syncthreads()` separating the two passes are avoidable.

This adds `per_token_group_quant_8bit_register_kernel` for the unpacked float32
scale layout. It is taken when `group_size == 128`, the input is 16-bit, both
buffers are 16 B aligned, and both are contiguous; everything else keeps the
existing shared-memory schedule.

vLLM already has `per_token_group_quant_8bit_packed_register_kernel` with the
same register pipeline, but float32-scale callers cannot reach it: it is
hardwired to UE8M0 exponents packed 4-per-int32 with TMA-aligned strides. Rather
than reshaping those callers, this extends the same idea to the ordinary scale
layout, reusing that kernel's subgroup shuffle mask and UE8M0 exponent bit math
verbatim.

A second, smaller effect of the fixed 256-thread launch: `GetGroupsPerBlock`
falls back to 1 group per block when `num_groups` is odd, leaving 16 active
threads per block. The register path pads the grid and bounds-checks instead, so
it is unaffected — visible below as the `(1, 128)` and `(333, 128)` rows, where
the shared-memory schedule spends ~14 µs almost entirely on launch overhead.

The spread is worth explaining rather than quoting the best number. The register
side converges to ~60–77 µs at (8192, 6144) in all three tables — it is
bandwidth-bound. The differences come from the baseline:

- `c10::Float8_e4m3fn(float)` is a software conversion and costs materially more
  than int8's hardware `cvt`, so the FP8 baseline starts slower (175 vs 118 µs)
  and has more to give back.
- On the register side UE8M0 is ~22% faster than float32 scales because a
  power-of-two scale lets the inner loop multiply by the reciprocal instead of
  dividing per element.

So the ~3× on the UE8M0 FP8 path is three effects stacked (no smem round trip,
reciprocal instead of divide, an expensive baseline conversion), not register
residency alone. INT8 keeps a smaller but consistent 1.26–1.56×.

concurrency 1, `--kv-cache-dtype fp8`. Same server config and same benchmark
script on both sides, run back to back in one window:

| prompt tokens | baseline | with register path | throughput | latency |
|---|---|---|---|---|
| 8192 | 3591.9 tok/s | 3622.5 tok/s | +0.85% | 2.279 → 2.264 s |
| 16384 | 3560.7 tok/s | 3620.9 tok/s | +1.69% | 4.596 → 4.519 s |
| 65536 | 3351.0 tok/s | 3404.3 tok/s | +1.59% | 19.529 → 19.213 s |
| 131072 | 3078.6 tok/s | 3123.9 tok/s | +1.47% | 42.471 → 41.872 s |

The 8k row gains least because at one chunk the fixed per-request costs (HTTP,
tokenization, scheduling, sampling) are the largest share of wall clock, while
the kernel saving scales with token count. From 16k up it settles at 1.5–1.7%.

That is consistent with the profile attribution: at an 8192-token chunk this
kernel accounts for 22.28 ms per step (15.60 ms over 411 calls with column-major
scales plus 6.68 ms over 150 row-major), and the measured 3.03×/3.07× puts it
near 7.3 ms — about 15 ms off a ~800 ms step, or 1.87% of GPU time. End-to-end
lands slightly under that because the denominator also carries non-GPU work.

Measurement caveat, and it biases against this PR: to avoid rebuilding the
prebuilt `_C_stable_libtorch.abi3.so` in that environment, the served run reached
the kernel through a Python-level redirect of the op call, so every call paid an
extra Python frame and predicate. Built normally the dispatch happens before the
launch, so treat 1.5% as a lower bound. Baseline reproducibility was checked
independently: the back-to-back baseline matched an earlier run from several
hours before to within 0.2% at every length.

## Bit-exactness, and why there are no eval numbers

Output is bit-exact with the shared-memory kernel in every configuration tested
below — quantized bytes and scales compare equal with `torch.equal`, not within
a tolerance. Two details carry that:

- The UE8M0 scale is derived with the same exponent bit math
  (`exp_bits + (mant_bits != 0)`) that `per_token_group_quant_8bit_packed_register_kernel`
  already uses, which is equivalent to `exp2f(ceilf(log2f(...)))` on this input
  domain.
- The non-UE8M0 path divides by the scale instead of multiplying by its
  reciprocal. The reciprocal costs an ulp and moves the ~0.05% of values that
  land exactly on an 8-bit boundary. Only the UE8M0 path, where the scale is a
  power of two and the two are equivalent, multiplies.

Because the bytes are identical, an accuracy eval would reproduce `main`'s
numbers exactly and would not be evidence of anything. I have not run one, and
am offering the bit-exactness comparison in its place. Happy to run a specific
eval if a reviewer would rather see it.

## Testing

Extended the existing suite rather than adding a file. `test_per_token_group_quant_fp8`
gained `dtype` parametrization (bf16/fp16) and three shapes that exercise the new
schedule: a single group, an odd token count leaving a partial trailing block,
and a serving-sized shape.

Its assertions are `atol=0.15` against Triton, which cannot see a bit-level
difference, so two dedicated tests pin the path equivalence. Both build a
16 B-misaligned but contiguous input, which falls back to the shared-memory
schedule, and require the two paths to agree exactly:

- `test_per_token_group_quant_fp8_register_matches_smem` (24 cases)
- `test_per_token_group_quant_int8_register_matches_smem` (6 cases) — int8 shares
  the schedule via `per_token_group_quant_int8`, and differs from fp8 in how
  `DST_DTYPE(q)` rounds (truncation toward zero vs round-to-nearest-even), so it
  needs its own guard.

```bash

    -k "register_matches_smem"

pytest tests/kernels/quantization/test_per_token_group_quant.py \
    -k "test_per_token_group_quant_fp8 and not packed and not register_matches"

Kernel-level bit-exactness was measured separately, since the installed vLLM in
my test container does not carry this patch: the new kernel was compiled into a
standalone extension and compared byte-for-byte against
`torch.ops._C.per_token_group_fp8_quant`, with a profiler check confirming the
baseline really executes `per_token_group_quant_8bit_kernel<c10::BFloat16,
c10::Float8_e4m3fn, false, true, float>` rather than falling back to Triton.

- FP8: 72/72 configurations bit-exact across input dtype, UE8M0, column-major,
  and shape
- INT8: 10/10 bit-exact
- 48/48 bit-exact driven through the `per_token_group_quant_fp8` entry point
  itself, which adds `tma_aligned_scales=True` coverage (input dtype ×
  column-major × TMA alignment × UE8M0 × 4 shapes)
- Edge inputs (all-`+inf`, all-`-inf`, `NaN`, all-zero, 1e-30, 1e30): identical
  bytes on both paths

`nvcc -arch=sm_90a` compiles the modified translation unit clean, and
`pre-commit run --files <the three files>` passes.
