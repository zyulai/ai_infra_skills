## Motivation

This PR addresses a critical performance bottleneck in the `route_simple_request` function within the HTTP router. This function is responsible for "fan-out" operations where the location of a request state is unknown (e.g., `get_response`, `cancel_response`) or for broadcasting requests (e.g., `get_server_info`).

**The Issue:**
Previously, the implementation iterated through workers sequentially using a `for` loop and awaited each response inside the loop.

* **O(N) Latency:** The total latency was the sum of all worker response times checked before the target worker.
* **Head-of-Line Blocking:** If a single worker in the cluster was slow or unresponsive (e.g., timing out after 200ms), the entire control plane request would block for that duration, even if the healthy worker holding the data was ready to respond instantly.

**Goal:**
Switch to concurrent execution to decouple router latency from the health of the worst-performing worker.

## Modifications

* **Refactored `route_simple_request`** in `sgl-model-gateway/src/routers/http/router.rs`.
* **Concurrent Execution:** Replaced the serial `for` loop with `futures::stream::iter` combined with `.buffer_unordered(32)`. This allows requests to be sent to all workers simultaneously.
* **Early Return Optimization:** The stream now returns immediately upon receiving the first successful (2xx) response, cancelling pending requests to other workers.
* **Lifetime Fixes:** Explicitly collected futures into a `Vec` before streaming and properly cloned headers/API keys to satisfy Rust lifetime and ownership requirements for the async move blocks.

## Benchmarking and Profiling

A benchmark suite `benches/fanout_routing_bench.rs` was created to simulate a "degraded cluster" scenario:

* **Cluster:** 1 Slow Worker (200ms delay), 1 Target Worker (Instant 200 OK), N Filler Workers (Instant 404).
* **Metric:** Latency to retrieve the successful response.

**Results:**
The fix provides a **~900x to ~1400x improvement** in latency by effectively ignoring the slow worker.

| --- | --- | --- | --- | --- |
| **10 Workers** | P99 Latency | ~203 ms | **0.22 ms** | **~920x Faster** |
| **100 Workers** | P99 Latency | ~203 ms | **0.14 ms** | **~1450x Faster** |
| **1000 Workers** | P99 Latency | ~203 ms | **0.21 ms** | **~960x Faster** |
