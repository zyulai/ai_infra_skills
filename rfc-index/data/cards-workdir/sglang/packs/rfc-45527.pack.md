## 正文(PRD / 提案全文)

## Summary

On a PD prefill server with pipeline parallelism, every PP stage sends the KV of a request's last chunk only when it processes the batch result. The result travels the PP ring one hop per loop iteration, so stage k processes it k iterations after stage 0, and decode cannot start until every stage has reported. Under load, the last stage's report arrives about `pp_size - 1` iterations after the KV it holds was ready.

This RFC proposes that stages 1..N-1 send their last-chunk KV as soon as their own forward of that chunk finishes, without aux data, while stage 0 stays the only stage that writes aux (first token and other metadata) at result-processing time. In a downstream deployment with PP4 prefill this cut steady-state TTFT P90 by about 0.8 s (4.45 s to 3.66 s) with no accuracy change. Since this changes what each stage reports to decode, I'd like to agree on the design before writing the upstream PR.

## Current behavior

On main:

- Non-final chunks are sent from `process_prefill_chunk` at the start of the next loop iteration.
- The final chunk is sent from `process_batch_result_disagg_prefill` (`send_kv_chunk(req, last_chunk=True)`). Under PP this runs from `_pp_process_batch_result`, after the batch's outputs arrive from the previous stage.
- The outputs go around the ring: the last stage sends them to stage 0, and each stage forwards them to the next one in its following iteration. Stage 0 processes the result first; stage k processes it k iterations later.
- Every stage writes the same aux data (`set_buf` + `send_aux`) and reports `KVPoll.Success`. Decode waits until all `required_prefill_response_num` prefill ranks, which include every PP stage, have succeeded before it reads aux and starts decoding.

So the request's TTFT includes the time for the result to reach the last stage, even though that stage finished its forward long before. Each iteration is a full micro-batch forward when the pipeline is busy, so the delay grows with load and with PP depth; at low load the ring turns quickly and the delay is small.

This is a different path from the release consensus (#36781, #45085), which decides when prefill returns its response and frees resources. The proposal here changes when decode can start.

## Proposal

1. **Capture at launch.** When a stage launches a micro-batch, record the requests that run their final chunk in it, together with the launch event. This has to happen at launch: once the next round is scheduled, a chunked request's `extend_end` already points at its next chunk, and a later check would mistake the second-to-last chunk for the last one.
2. **Early send on stages k >= 1.** On the next iteration, for each recorded request:
   - Run `checkpoint_disagg_prefill(req)` first so the pages are final after any radix-tree dedup. Every stage does this at the same point in the loop, so tree state stays identical across stages. The later checkpoint at result processing is then a no-op.
   - Send the last chunk (KV plus per-request state such as SWA, Mamba or DSA state) with the launch event as the transfer wait event. This reuses the existing `_early_send_wait_event` / `TransferKVChunk.wait_event` path, so the scheduler thread never blocks; #45524 already uses it for non-final chunks under PP.
   - Skip `set_buf` and `send_aux`. Report `KVPoll.Success` once the KV is written.
3. **Result processing.** Stages k >= 1 skip the last-chunk send for those requests. Stage 0 keeps today's behavior: it writes aux and sends its last chunk with aux, so its `Success` is posted after the aux write. Decode reads aux only after all stages have succeeded, so the aux it reads is complete.
4. **Fallback to today's path** for requests that are still bootstrapping (optimistic prefill), health-check requests, and any combination not yet covered (see open questions).
5. **Flag.** Start behind an opt-in flag, e.g. `SGLANG_DISAGG_PP_EARLY_LAST_CHUNK`, and turn it on by default after CI coverage.

Aborts, grammar failures and sampling-mask finishes are still decided at result processing, so stage 0 never reports success for a request that prefill drops, even if later stages already did.

## Results so far

These numbers come from an implementation on a downstream branch based on v0.5.12, not on main, so they show the size of the effect rather than prove it for main.

- **Setup:** two prefill instances, each PP4 x CP4 (16 ranks), chunked prefill 4096, `--pp-async-batch-depth 1`; one decode instance with MTP; a large MoE model. Prompts are about 80K tokens, of which 72K is a prefix already cached on prefill and 8K is new, with 1K output tokens. Closed loop at concurrency 64, 1280 requests. The two runs differ only in this change.
- **TTFT** (steady state, first 64 requests excluded):

  | | P50 | P90 | Mean |
  | --- | --- | --- | --- |
  | Before | 3.57 s | 4.45 s | 3.74 s |
  | After | 2.74 s | 3.66 s | 2.97 s |

  A repeat run reproduced the result. KV reached decode about 0.8 s earlier, and TPOT was unchanged.
- **Low load:** no difference, as expected. A single long request took the same time with and without the change.
- **Accuracy:** passcode-retrieval tests 12/12 and GSM8K unchanged (0.960).

The accuracy check needs a special test. Ordinary retrieval tests can pass even when the last chunk's KV is stale, because consecutive requests reuse pages holding similar text. We added a test that puts the passcode inside the last chunk (depth 0.998) and changes it on every request. Our first version had exactly the bug described in step 1, and only this test caught it.

## Alternatives considered

- **Also send stage 0's KV early, and send aux as a separate final message.** This also saves stage 0's last-chunk transfer time, typically tens of milliseconds, but every backend would need an aux-only message type. It could be a follow-up.
- **Let the last stage write aux right after sampling.** This gives the largest saving, because the last stage has the first token before anyone else. But it moves the decision that a request is done ahead of result processing (aborts, grammar, sampling-mask finish), so decode could start a request that prefill later drops.
- **Deliver the outputs from the last stage to every stage directly instead of around the ring.** This would help every consumer of the result, but it is a much larger change to PP communication.

## Open questions

1. Is it acceptable that only stage 0 writes aux under PP? Is any aux content stage-specific today, for example draft state relayed along the ring?
2. If later stages have reported success and stage 0 then fails or aborts the request, does every backend's decode side fail the request cleanly?
3. Backends: Mooncake and Mori already honor the transfer wait event, and NIXL gets it in #43299. NIXL's in-band completion notifications may need their own handling. What about Ascend?
4. How should this interact with the staging buffer, DCP relayout, `prefill_complete` allocation with PP prefill (#45337), and the release-consensus rework (#45085)?
5. Flag name and default.

## Plan

1. PR 1: Mooncake and Mori behind the flag. Unit tests for the launch-time capture and the single aux writer, the last-chunk retrieval test, and a PP4 prefill benchmark on main.
2. PR 2: NIXL (after #43299) and the other backends.
3. Turn it on by default once CI covers it.
