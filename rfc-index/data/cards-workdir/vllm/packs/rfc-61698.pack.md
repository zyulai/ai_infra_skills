## 正文(PRD / 提案全文)

### Motivation.

Reviewing performance- and accuracy-sensitive PRs is frequently bottlenecked on evidence and regression testing. Reviewers routinely ask "can you please provide e2e performance data?", "can you please provide eval results?", or "can you show 8k1k numbers on H100?". Not only are these requests often vague, leaving the submitter unsure exactly how to run the benchmark or eval, but the answers also arrive as screenshots, hand-run `vllm bench` output, or not at all. On the flip side, running a broad eval + benchmark matrix on vLLM-funded CI for PRs does not scale, especially as the volume of AI-generated PRs grows.

AI tools have made producing a PR nearly free, but reviewing one costs as much as or more than it ever did. Maintainer attention is now the scarce resource, and AI generation of PRs is skewing more of the cost of a PR onto the reviewer, who frequently has to validate the PR manually or validate it on other hardware. Asking for evidence that costs GPU time to produce moves some of that cost back to whoever wants the PR merged. It doesn't close the gap, and spending compute doesn't make a PR good, but it pushes in the right direction in two ways:

- the evidence gives the reviewer more confidence, making the PR easier to review;
- spending it signals that someone values the PR.

At the same time, the community has more datacenter hardware than vLLM CI, and more kinds of it (GB300, MI355X, older Hopper/Ampere fleets, and so on). Some of it may be free to help with evals for specific, important PRs, even if its owners aren't ready to commit it to vLLM CI full time by hooking it up as a CI agent.

This RFC proposes a standard, versioned **eval image**, built by vLLM CI when CI is run on a commit, which anyone can run on their own GPUs, coupled with a **public database of results**.

This could also help PRs under the [fast-track merging RFC (#59665)](https://github.com/vllm-project/vllm/issues/59665) by providing the extra evals and benchmarks it asks for.

### Proposed Change.

#### Goals

- Anyone with suitable GPUs can produce results for a commit with a single `docker run`: give the image a request or run spec, and it produces a result bundle.
- Results are reproducible: a bundle records everything needed to re-run it on the same GPU type and get the same result within stated tolerances.
- **Trust-based, with accountability.** Every upload is tied to the submitter's GitHub account.
- Reviewers can ask for a specific configuration, and any community member can donate GPU time to provide it, including hardware the author doesn't have.
- Reuse existing vLLM eval configs (`tests/evals/*`, `.buildkite/lm-eval-harness/configs`) and community benchmark recipes (SemiAnalysis InferenceX and AgentX) rather than inventing new ones.

#### Scope

- **Not in scope yet: hard merge gating.** For now results are informational, an informal gate: reviewers may expect them and may request specific runs, but nothing blocks merging automatically. Once the prototype has shown the results are reliable, we may make some results required for merging certain areas.
- **Non-goal:** replacing pre-merge CI or the existing post-merge performance dashboard.

#### Overview

1. **On the PR.** A maintainer triggers CI on a commit, and CI builds a signed eval image for it. A reviewer asks for results with `/byog request`, or the submitter simply runs the standard suites up front and uploads the results as extra evidence.
2. **On anyone's GPUs.** Anyone with suitable GPUs runs the request with a single `docker run`. The image runs the jobs that fit its GPUs, shows the bundle it produced, then uploads it after a GitHub login.
3. **On the results service.** The service records who uploaded the bundle, stores it, and updates the public dashboard and the PR via a comment.

#### Evals and benchmarks

##### Evals

Every eval costs GPU time, so we want the set that gives the **most signal per GPU-hour**.

**Proposed eval suites,** picked with `eval_suite:`. Listing `evals` in a request replaces the suite. Requesting community input on the contents and time budgets.

| Eval suite | When | Evals | Time |
| --- | --- | --- | --- |
| `smoke` | Quick check that nothing is badly broken | `gsm8k` | minutes |
| `standard` (default) | The general expectation for accuracy-sensitive PRs | `gsm8k`, `mmlu_pro` (300 per subject), `mrcr` (120 samples) | up to ~3 hours |
| `extended` | On reviewer request, for large or risky changes | `gsm8k`, full `mmlu_pro`, `mrcr` (240 samples) | hours |

Each eval in these suites covers a different kind of failure: `gsm8k` catches gross breakage quickly, `mmlu_pro` covers broad knowledge and isn't saturated on large models, and `mrcr` covers long context (attention, KV cache, prefix caching). All run against datasets pinned to a commit and baked into the image.

**Catalog.** Other evals a request can add. Costs are rough orders of magnitude for a typical config (for example a mid-size MoE on one node); reasoning mode and large models move evals up a bucket.

| Eval | What it catches | Existing harness | Cost |
| --- | --- | --- | --- |
| Logprob / KL divergence vs reference logits | Numerical drift from kernels, quantization, attention backends, often before scores move | — (new) | minutes |
| `ifeval` | Chat template, instruction following, stop handling | lm-eval | minutes |
| `chartqa` / `mmmu` | Multimodal pipeline | `.buildkite/lm-eval-harness` | tens of minutes |
| `gpqa_diamond` (×N repeats) | Reasoning quality | `tests/evals/gpt_oss` | tens of minutes → hours |
| `bfcl` / tool-call subset | Tool calling, structured output, parsers | — | tens of minutes → hours |
| `aime25` (×N repeats) | Long-generation reasoning; high variance | lm-eval | hours |
| `livecodebench` | Code generation | — | hours |
| `ruler` / `longbench_v2` | Long context at 128k+ | — | hours |
| SWE-bench Verified / agentic benchmarks | End-to-end agentic quality | — (needs sandboxes) | hours → days |

Greedy decoding is not bit-reproducible across batch composition, so per-eval tolerances come from repeated runs on `main`. High-variance evals (AIME, GPQA) need `repeats` and report mean ± stderr.

##### Benchmarks

Modeled on SemiAnalysis InferenceX, so the results line up with numbers the community already reads.

**Proposed benchmark suites,** picked with `benchmark_suite:`. Listing `benchmarks` in a request replaces the suite. Requesting community input on these too.

| Benchmark suite | When | Benchmarks | Time |
| --- | --- | --- | --- |
| `smoke` | Quick check that serving works and nothing is badly slower | 1k1k at concurrency 1, 64 | minutes |
| `standard` (default) | The general expectation for perf PRs | 8k1k at concurrency 1, 16, 64, 256, plus AgentX at 8, 32 | up to ~2 hours |
| `extended` | On reviewer request, for large or risky changes | 1k1k, 8k1k, 1k8k at concurrency 1–512, plus AgentX at 8, 32, 128 | hours to days |

| Benchmark | Workload | Client | Metrics |
| --- | --- | --- | --- |
| `fixed_isl_osl` | `1k1k`, `8k1k`, `1k8k` random-token, `ignore_eos` | `vllm bench serve` | output tok/s/GPU, TTFT/TPOT/ITL p50/p90/p99, interactivity (tok/s/user) |
| `agentx` | AgentX trace replay: multi-turn Claude Code sessions with subagents and prefix reuse | `aiperf --scenario inferencex-agentx-mvp`, dataset pinned to a dated revision | throughput/GPU vs interactivity, TTFT percentiles, prefix-cache hit rate |

- **Concurrency sweeps.** Each concurrency point is a separate client run against the same server, with its own artifacts. For AgentX, concurrency counts live agent sessions, and each point runs for at least 900 s.
- **Speculative decoding.** InferenceX forces acceptance lengths for cross-framework comparability, which would hide the effect of PRs that change drafting, so BYOG reports natural acceptance by default.
- **Raw records are kept.** Every benchmark keeps its per-request records so results can be recomputed and re-aggregated.

##### Comparing against `main`

There should be a way to compare a PR's results against `main` results for the same spec on the same GPU type, when those exist. Sources include nightly `main` runs and `main` runs anyone submits. The image records the PR's merge-base, so the dashboard can find the closest `main` results. Results well below `main` on the same GPU type are flagged as suspicious, which also catches a misbehaving machine (throttling, misconfiguration) without collecting GPU telemetry; the submitter can then debug it.

#### Trust

The system is mostly trust-based, with accountability through GitHub accounts:

- **Uploads are authenticated with GitHub.** After a run, the image starts a GitHub device-flow login: it prints a code, and the submitter approves it in a browser. The token has no scopes, so it only proves who the submitter is.
- **The service records who uploaded each result.** It checks the token with GitHub and stores the submitter's GitHub user ID and username with the bundle's sha256 and the upload time. Results can't be submitted under someone else's name without access to their GitHub account.
- **Tampering is handled by flagging accounts.** If someone is found tampering with results, their GitHub account is flagged for result tampering and their results are removed. Anyone who doubts a result can re-run it with the bundle's `repro.sh`.
- **The token is kept away from the PR's code.** The job runs the PR's code, so the image only logs in once the job has finished, and refuses if any other process is still running in the container. In that case the bundle is kept, and a fresh `--upload-only` run uploads it.

#### Precedent: MLPerf

Results run on contributors' own hardware have worked elsewhere. MLPerf Inference has published vendor-run results for years. Submitters run the benchmarks on their own systems through a mandated harness (LoadGen). Trust comes from compliance tests, peer review by other submitters, random audits, and a rule that "results that cannot be replicated are not valid results".

BYOG starts from a stronger position. MLPerf submitters bring their own inference engine, so much of MLPerf's process exists to catch engine-level tricks. In BYOG, vLLM CI builds the entire image: the vLLM build under test, the eval and benchmark clients, the harness, and the hardware queries. The only thing a contributor brings is the hardware.

#### How it works

##### 1. The eval image

- **Built when CI is run on a commit**, the same way CI works today: PRs build only on commits where a maintainer triggers "run CI". That trigger doubles as the safety gate, since the image runs PR code on contributors' machines.
- **A thin layer on the CI image.** `docker/Dockerfile.byog` builds on the image CI already pushes for that commit (the `test-ci` target), adding the harness, the eval and benchmark catalog and suites, reference specs, pinned clients (`aiperf`; `lm-eval` is already in the test image), and pinned datasets. Registries deduplicate layers, and the large pieces that rarely change (clients and datasets) come from a separately versioned `byog-tools` image via `COPY --link`, so the per-commit addition is a few MB.
- **Signed and pinned.** Images are signed with cosign (keyless via CI's OIDC identity, or a vLLM-held KMS key) with SLSA provenance linking the digest to the commit. Images are pulled by digest, and the results service rejects bundles whose digest lacks a valid vLLM CI signature.
- **Retention (undecided).** Eval images could be ephemeral, for example expiring after 30 days, since they can be rebuilt from the commit. Rebuilt images get a new digest, though, so images referenced by results, or `main` images that PRs are compared against, may need to be kept longer.

##### 2. Run specs

A **run spec** is a YAML file that fully determines one run: the model, the exact `vllm serve` arguments and environment, the hardware, and the evals and benchmarks to run against that server.

<details>
<summary>Example run spec</summary>

```yaml
schema: byog.spec/v0
name: dsv3-fp8-tp8-8k1k
model:
  id: deepseek-ai/DeepSeek-V3.2
  revision: 4f8c3b1...            # required, full HF commit sha
serve:
  args: --tensor-parallel-size 8 --max-model-len 16384 --kv-cache-dtype fp8
  env:
    VLLM_USE_DEEP_GEMM: "1"
hardware:
  gpu: [H200, B200, B300]         # acceptable GPU types
  count: 8
eval_suite: standard              # smoke | standard (default) | extended
benchmarks:                       # replaces the benchmark suite
  - name: fixed_isl_osl
    scenarios: [8k1k]
    concurrency: [1, 8, 64, 256]
```

</details>

- **Reference specs** live in-tree under `tools/byog/specs/` and are reviewed like code. Their results are comparable across PRs and over time.
- **Custom specs** cover anything a reviewer asks for, such as "this PR with `--enable-expert-parallel` on 4×B200".
- **What actually ran is recorded too:** the server's real command line, the resolved non-default `VllmConfig`, the relevant environment variables, and the exact client commands. Any divergence from the spec is a validation error. Each bundle includes a `repro.sh` with the exact `docker run` command.

##### 3. Requests

Reviewers rarely want a single run. They want "these models × these parallelism schemes × these GPUs". A **request** describes that sweep: its `matrix` section lists the values to try for each setting (models, parallelism, GPUs, ...), and the request expands into one **job** per combination, like a GitHub Actions matrix. Each job is one server configuration. Starting a server is the expensive part, so every eval and benchmark in a job runs against that one server, and concurrency sweeps happen inside the job rather than in the matrix.

<details>
<summary>Example request</summary>

```yaml
schema: byog.request/v0
pr: 61234
title: "fused_moe: FP8 grouped GEMM rewrite"

matrix:                            # one job per combination of values
  model:
    - name: dsv3.2
      id: deepseek-ai/DeepSeek-V3.2
      revision: a7e62ac04ecb2c0a54d736dc46601c5606cf10a6
      serve: {args: --kv-cache-dtype fp8}
    - name: qwen3-30b-fp8
      id: Qwen/Qwen3-30B-A3B-Instruct-2507-FP8
      revision: 5a5a776300a41aaa681dd7ff0106608ef2bc90db
  parallel: [tp8, dp8-ep]          # shorthand for vllm serve parallel flags
  hardware: [H200x8, B200x8]
  variant:
    - name: default
    - name: no-deepgemm
      serve: {env: {VLLM_USE_DEEP_GEMM: "0"}}

exclude:
  - {model: qwen3-30b-fp8, variant: no-deepgemm}

include:                           # one-off jobs outside the matrix
  - model: dsv3.2
    parallel: tp4-dp2-ep
    hardware: B300x8
    variant: default
    evals: [{name: gpqa_diamond, repeats: 4}]
```

</details>

- **Matrix keys are free-form.** Each value sets part of the job: serve args, env, model, hardware, evals, or benchmarks. `exclude` drops combinations, and `include` adds one-off jobs.
- **Combining is strict.** Setting the same flag in two places is an error, as are conflicting env vars, models, or hardware.
- **Parallelism shorthand.** `tp4-dp2-ep` means `--tensor-parallel-size 4 --data-parallel-size 2 --enable-expert-parallel`; `pp`, `dcp`, and `pcp` work the same way.
- **Defaults.** A request only states what differs from the defaults. The smallest useful request is a model and the hardware. With no parallel flags, jobs use tensor parallelism across all their GPUs, and the `standard` eval and benchmark suites. Expansion writes these defaults into each job, so jobs stay reproducible if the defaults change later.
- **Validated before anyone spends GPU time.** Serve args are parsed with vLLM's own argument parser, the parallelism's GPU count must match the hardware, and unknown evals, benchmarks, suites, settings, and unpinned revisions are rejected.

**Running a request.** The image's entrypoint does everything, so the only host requirement is Docker (or Podman) with GPU support:

```bash
docker run --gpus all --ipc host -v $HF_HUB_CACHE:/weights/hub -v $PWD/out:/out -e HF_TOKEN \
    <image>@sha256:... --request /out/request.yaml   # or --job <job_id>, or --spec /out/spec.yaml
```

It expands the request, runs every job that fits the visible GPUs (on 2×B300, the request's B300x2 jobs), downloads any missing pinned weights, and writes one bundle per job. It then prints exactly what is in each bundle, every file with its size and sha256 plus the headline results, and uploads it after a GitHub login (see Trust). Large requests can be split by job across people with different hardware.

`tools/byog/request.py` previews a request without GPUs, listing its jobs and a rough GPU-hour estimate; the example above is 13 jobs and about 329 GPU-hours with the standard suites. On a PR, the request is posted as a `/byog request` comment and the bot replies with the job table.

##### 4. Environment logging

Collected before and after the run. This builds on `vllm/collect_env.py` (`get_env_info()`), adding:

- **GPU:** `nvidia-smi -q -x` (or `amd-smi`): GPU type, VBIOS, driver, CUDA, ECC, MIG, power limit, clocks, PCIe; `nvidia-smi topo -m`; NVLink status.
- **CPU, memory, OS:** `lscpu`, NUMA layout, `/proc/meminfo`, governor, kernel version and cmdline, `ulimit -l`.
- **Logs:** server and client logs.
- **Privacy:** the hostname, GPU UUIDs, and GPU serial numbers are redacted. Everything else is collected inside the container, where host usernames and paths don't appear.

##### 5. Result bundle

`bundle.tar.gz` contains:

<details>
<summary>Bundle layout</summary>

```text
manifest.json          # sha256 + size of every file below
result.json            # byog.result/v0 summary (see tools/byog/examples/result.example.json)
spec.yaml              # run spec, verbatim
spec.resolved.yaml     # with defaults filled in
env/                   # environment snapshots, before and after
server/                # actual command line, env, server log
evals/<name>/          # eval results
bench/<name>/<scenario>-c<N>/   # summary and per-request records
repro.sh
```

</details>

`result.json` is the summary the service indexes; raw artifacts are stored by content hash.

##### 6. PR comment

A bot comment on the PR keeps an up-to-date table: requested jobs, who ran them, PR vs `main` deltas, and links to bundles. Anyone with the hardware can run a request's jobs and submit results; nobody needs permission.

#### Rollout

1. **MVP:** `docker/Dockerfile.byog`, the `tools/byog` harness, suites and reference specs, plus a minimal results service, since uploads are authenticated: a GitHub OAuth app, an upload endpoint that records the submitter's GitHub account, bundle storage, and a simple public list of results.
2. **Service features:** the public dashboard with comparison against `main`, and the PR bot.
3. **Possible hard gating (future):** based on the prototype's track record, decide whether some results should become required for merging, and for which areas.

### Any Other Things.

#### Open questions

1. Which evals catch real regressions that `gsm8k` misses, and are they worth their cost? Examples of past regressions each would have caught are the most useful input.
2. Are smoke / standard / extended the right split for eval and benchmark suites, and is each one's content right for its time budget?
3. How many repeats do high-variance evals need, and should reasoning models be evaluated with thinking on, off, or both?
4. Is a logprob/KL-divergence check against stored reference logits a good cheap first gate for numerics-affecting PRs?
5. Retention for eval images and the CI images under them. Is the `test-ci` image acceptable for perf numbers, or do we need the leaner `vllm-openai` image?
6. Gated models: is it acceptable for reference specs to require contributors to accept licenses (Llama)?
7. Tolerances: who owns calibration per eval and GPU type, and how often is it redone?
8. AMD, TPU, and XPU support from day one, or NVIDIA first?
