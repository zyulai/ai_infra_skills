## Motivation

This PR adds and validates prefill context-parallel (CP) support for DeepSeek-V4 on AMD GPUs, focusing on the unified_kv (Triton) attention path used by DeepseekV4HipRadixBackend with the interleave (round-robin-split) CP strategy. The goal is to improve long-context prefill latency and serving throughput on AMD platforms while preserving model quality.

All changes are restricted to the AMD/HIP path and have zero impact on NVIDIA (B200/H200) execution.

## Modifications

used options: ` --enable-prefill-cp --cp-strategy interleave`, which has been supported in SGLang

CP size calculated by `server_args.attn_cp_size = server_args.tp_size // server_args.dp_size` from https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/arg_groups/deepseek_v4_hook.py#L65, so it no need to set manually.

- `models/deepseek_v4.py`:
  - In `_forward_prepare`, the unified prefill branch originally only computed the local bf16 KV. Because `if unified:` short-circuits ahead of `elif use_cp:`, the cross-rank all-gather was skipped. Fix by add `cp_all_gather_rerange_output`
- `deepseek_v4_backend_hip_radix.py`: 
  - align the logic with NV path: add `self.c4_sparse_raw_indices = torch.empty_like(self.c4_sparse_page_indices)`
  - add per-query metadata local slicing (kv_indptr length = local T+1).
  - round-robin global positions (by `[cp_rank::cp_size]`, `sequential [:T]` will lead to wrong output tokens).
  - write the FULL window into the SWA ring on every rank, otherwise it will cause accuracy error.
- add deepseek v4 context parallel ci test refer to `/sgl-workspace/sglang/test/registered/amd/test_deepseek_v4_pro_fp4.py`

- **All of these changes above restricted by `is_hip`, to make sure it only available on AMD devices**

Context parallel 
- While the baseline slightly outperforms CP for short inputs under low load, CP scales much better with increasing input lengths and concurrency levels, achieving up to 2.97× higher throughput at 1024k thanks to its more efficient prefill processing.
- get 1.33x-3.82x uplift on TTFT and make workload available on long context cases
- Limited by communication overhead, some ITL performance regression(less than 0.26x) is observed under some conditions.

> CP doesn't win by "decoding faster"—it's actually slightly slower at decoding. Its value comes entirely from cutting long prefills on 8 gpus, preventing prefills from blocking ongoing decoding requests for extended periods. 

> In continuous service, new/blocked prefills will interrupt running decodes; the faster the prefill, the shorter the interruption time, and the smaller the "spike" per token.
