## Overview

`cooperative_topk` now also reads BF16 logits. On SM100 the DSA indexer then keeps the paged MQA logits in BF16
instead of upcasting them to FP32 before the decode top-k. Main already does this for `deep_select` and (since
#64138) `persistent`, but `auto` picks `cooperative` for up to 64 rows, which is every decode step in the runs
below (at most 16 requests x 4 tokens). From review, the top-k kernels themselves are also faster now, mostly
for BF16 (Details).

## Claims

- Decode top-k on B300, main (FP32 upcast + FP32 top-k) vs this PR (BF16 top-k): 22% to 57% faster at every
  point of rows {1, 4, 8, 16, 33, 64} x row length {16K, 64K, 128K, 256K, 1M} x k {512, 2048}. The BF16
  top-k alone is 8% to 38% faster than main's FP32 top-k. With FP32 logits (#64580's default) the top-k is up
  to 16% faster and at most 0.2% slower.
- `persistent_topk` with BF16 logits (#64138) is 24% to 31% faster on rows up to 32K, the single-CTA path it
  shares with `cooperative_topk`.
- InferenceX AgentX, GLM-5.3-NVFP4 on 4x GB200: together with #62170 and #62171, decode time per turn
  drops 2.8%, 2.5%, 1.5% and 1.5% at concurrency 1, 4, 8 and 16 (main vs main: within 0.7%). This PR is
  about 1/3 of that. (Measured before the kernel changes from review.)
- No precision changes: DeepGEMM's SM100 logits kernels already return BF16 on main
  ([`mqa_logits_use_mx_scales()`](https://github.com/vllm-project/vllm/blob/c50aca14416ef29f6ed0ed256302f30646726dcd/vllm/utils/deep_gemm.py#L597-L606)), and main only widens them
  ([`as_fp32_logits`](https://github.com/vllm-project/vllm/blob/c50aca14416ef29f6ed0ed256302f30646726dcd/vllm/model_executor/layers/sparse_attn_indexer.py#L304-L305)). BF16 widens to FP32
  exactly, so the top-k selects the same values.
- DCP, top-k backends that take only FP32, and BF16 rows that are not 16-byte aligned still upcast as before.

"""cooperative_topk sweep for vllm#62172: rows x row length x k, timed with triton's do_bench_cudagraph.

usage: python coop_sweep.py TAG OUT_JSON  (from the vLLM tree to test, with its _C_stable_libtorch built)
       SWEEP_ONLY=fp32 times only the FP32 kernel, so both builds make the same allocations.
Logits are torch.randn rounded to BF16 (what DeepGEMM returns on SM100); every row has the full length and the
row stride equals the length. Timed per case (median us of CUDA-graph replays; L2 is not flushed):
  fp32          cooperative_topk on the FP32 widening (main's top-k kernel)
  upcast_fp32   as_fp32_logits(BF16) + cooperative_topk on FP32 (main's SM100 decode stage)
  bf16          cooperative_topk reading BF16 directly (this PR; None where the build rejects BF16)
Each result must select exactly torch.topk's values, with no repeated index. Run main, PR, PR, main in fresh
processes and compare the means of each build's two runs.
"""
import json
import os
import sys

import torch
from triton.testing import do_bench_cudagraph

import vllm._custom_ops  # noqa: F401  (registers torch.ops._C)
from vllm.model_executor.layers.sparse_attn_indexer import as_fp32_logits

tag, out_path = sys.argv[1], sys.argv[2]
ROWS = (1, 4, 8, 16, 33, 64)
LENGTHS = (16384, 65536, 131072, 262144, 1048576)
KS = (512, 2048)
ws = torch.empty(1024 * 1024, dtype=torch.uint8, device="cuda")


def bench(fn):
    return do_bench_cudagraph(fn, rep=100, return_mode="median") * 1000


def exact(logits32, out, k):
    sel = logits32.gather(1, out.long()).sort(1).values
    ref = logits32.topk(k, dim=1).values.sort(1).values
    uniq = all(out[r].unique().numel() == k for r in range(out.shape[0]))
    return bool(torch.equal(sel, ref)) and uniq


# Warm up (clocks, graph capture) on the first shape; the first timed case of a process reads high otherwise.
_x = torch.randn(ROWS[0], LENGTHS[0], device="cuda")
_l = torch.full((ROWS[0],), LENGTHS[0], dtype=torch.int32, device="cuda")
_o = torch.empty(ROWS[0], KS[0], dtype=torch.int32, device="cuda")
torch.cuda.synchronize()
bench(lambda: torch.ops._C.cooperative_topk(_x, _l, _o, ws, KS[0], LENGTHS[0]))

results = []
for rows in ROWS:
    for length in LENGTHS:
        torch.manual_seed(rows * 7 + length)
        logits16 = torch.randn(rows, length, device="cuda").to(torch.bfloat16)
        logits32 = logits16.float()
        lengths = torch.full((rows,), length, dtype=torch.int32, device="cuda")
        # do_bench_cudagraph runs on a side stream that does not wait for these writes.
        torch.cuda.synchronize()
        for k in KS:
            r = dict(tag=tag, rows=rows, length=length, k=k)
            out = torch.empty(rows, k, dtype=torch.int32, device="cuda")

            def fp32():
                torch.ops._C.cooperative_topk(logits32, lengths, out, ws, k, length)

            r["fp32"] = bench(fp32)
            r["fp32_exact"] = exact(logits32, out, k)
            if os.environ.get("SWEEP_ONLY") == "fp32":
                # Same allocations in every build: skip the BF16 variants.
                r["upcast_fp32"] = r["bf16"] = None
                r["upcast_fp32_exact"] = r["bf16_exact"] = True
                results.append(r)
                print(json.dumps(r), flush=True)
                continue

            def upcast_fp32():
                x = as_fp32_logits(logits16, lengths)
                torch.ops._C.cooperative_topk(x, lengths, out, ws, k, length)

            r["upcast_fp32"] = bench(upcast_fp32)
            r["upcast_fp32_exact"] = exact(logits32, out, k)

            def bf16():
                torch.ops._C.cooperative_topk(logits16, lengths, out, ws, k, length)

            try:
                bf16()
                torch.cuda.synchronize()
                r["bf16"] = bench(bf16)
                r["bf16_exact"] = exact(logits32, out, k)
            except RuntimeError:
                r["bf16"] = r["bf16_exact"] = None
            results.append(r)
            print(json.dumps(r), flush=True)
        del logits16, logits32
json.dump(results, open(out_path, "w"))

## Details

- `CooperativeTopKParams`, the TMA staging buffers and the histogram loads are templated on the input type.
- TMA units are 16 bytes (8 BF16 or 4 FP32 elements), so the stride and per-block alignment follow the element
  size.
- Scores are widened to FP32 when binned, so both input types use the same radix keys.
- #59645's exact overflow recovery in `cooperative_topk_overflow.cuh` reads scores through the widening helpers
  #64138 added (`to_float`, `load_score4`), so a BF16 row recovers exactly as its FP32 widening does.
- The extension dispatches on `logits.scalar_type()`.
- `SparseIndexerTopk.takes_bf16_logits` (from #64138) now also returns true for `cooperative`, explicit or as
  `auto`'s choice, when its constraints hold (at most 64 rows; contiguous, 16-byte-aligned rows).
- Candidate-block selection (DeepSeek-V4.1) keeps FP32 block scores for explicit `cooperative`, as main does for
  `auto` and `persistent`. On B300, BF16 and FP32 block scores select the same blocks, including rows where every
  block ties. I could not run that model here.

Kernel changes from review, each A/B'd on B300 against the step before it (same method as above):

| commit | change | effect |
|---|---|---|
| [d8a0039](https://github.com/vllm-project/vllm/pull/62172/commits/d8a0039505edf7c8e1bdbc84b3010ec68c30f45d) | The tie refinement ORs the ties' keys against the first one and runs only the radix-256 rounds over bits they differ in: one for BF16 (keys end in 16 zero bits), usually three for FP32. FP32 keeps the four rounds in the single-CTA path, where the extra pass measured up to 0.9% slower even on rows that refine no ties | with the next row, rows 1 to 64 at 64K and 256K: BF16 -11% to -21%, FP32 -2% to -16% |
| [f45b4b4](https://github.com/vllm-project/vllm/pull/62172/commits/f45b4b4e3cdb53314635213e4172cc340fd52068) | The BF16 hot loops read two staged scores per 32-bit load and bin both with one packed FP16 conversion and key flip. An exhaustive GPU check gives the same bins as the scalar path for all 2^32 inputs | (above) |
| [ff286db](https://github.com/vllm-project/vllm/pull/62172/commits/ff286dbe970d1929f9ec4a97d2450c8f2def8d88) | BF16 keeps twice as many elements resident in the same shared memory | -18% to -20% where rows now fit a single pass (4x1M, 8x512K, 16x256K, 33x256K, 64x128K to 192K), unchanged elsewhere |
| [9970c5a](https://github.com/vllm-project/vllm/pull/62172/commits/9970c5ac5b4e6664400890d11159b19b41f0735f) | The single-CTA register path keeps BF16 packed (four scores per `uint2`) and bins it with two packed conversions; FP32 bins as before | BF16 rows up to 16K: -8% to -19%; `persistent_topk` BF16 rows up to 32K: -24% to -31%; FP32 unchanged |

Measured and not adopted:

- Storing bins instead of recomputing them in the scatter pass: the spare shared memory now holds the extra BF16
  stages, overwriting the staged scores would break the overflow recovery that rereads them, and after the packed
  conversion a bin costs one conversion per two scores.
- A 32K single-CTA limit for BF16 (the registers FP32 uses for 16K): -21% to -25% just past 16K, but up to +40%
  at 32K with k=2048 and +3% at 16K, so it stays at 16K.
- Re-tuning the cluster sizes: forcing each of 2, 4, 8 and 16 on every shape above, the row-count rule is within
  2% of the best in 112 of 120 shapes. The others (16 rows at 512K and 1M, 1 row at 64K) depend on the row
  length, which the launcher does not know: lengths are on the device, and a CUDA graph captures
  `max_model_len`.
- In ncu, FP16 conversions were 2% to 4% of the original BF16 kernel's instructions, while the per-element loop
  (`LOP3`, `ISETP`, `BRA`) was about 45%; the pair loads cut the latter.
