## PR body
```markdown
## Purpose

Reduce the Kimi-K3 single-token AttnRes-to-router latency by loading the first
`ll_bf16` router-weight tiles before the incoming PDL wait.

The optimized kernel is selected from the runtime `M` shape:

- `M == 1`: use the weight-prefetch PDL specialization;
- every other `M`: use the original `ll_bf16` kernel unchanged.

The earlier AttnRes and latent-MoE-tail changes have been removed. AttnRes is
now provided by #54261, which is included in the rebased `main` base.

## Duplicate-work check

Open-PR searches for `ll_bf16 PDL` and `router weight prefetch` found no PR
implementing this optimization. This PR is intentionally limited to the
`ll_bf16` shape dispatch and does not duplicate #54261.

## Implementation

- Add an optional dot-product path that preloads the first eight static
  weight tiles before `griddepcontrol_wait()`.
- Keep separate compiled-kernel caches for the original and prefetch variants.
- Dispatch the prefetch variant only for `hidden_states.shape[0] == 1`.
- Add a unit test covering the `M=1` versus `M>1` dispatch boundary.

## Validation

Hardware: NVIDIA B300 SXM6 AC, CUDA graph, cold L2, SM clock locked at 1980 MHz
for performance measurements.

Tests:

- `.venv/bin/python -m pytest tests/kernels/test_ll_bf16_gemm.py -v`
  - `136 passed`
- `.venv/bin/pre-commit run ruff-check --files ...`
  - passed
- `.venv/bin/pre-commit run ruff-format --files ...`
  - passed
- Incremental `_C_stable_libtorch` build and install against rebased `main`
  - passed

The full kernel suite covers dot-product and split-K shapes, single-token
production shapes, numerical edge cases, deterministic output, CUDA graphs,
and dispatch/cache behavior.

## Performance

Timed region: merged native AttnRes followed by `ll_bf16`, including the PDL
handoff. L2 is flushed before the graph replay; AttnRes then produces the
activation consumed by `ll_bf16`.

For `M=1`, `N in {256, 384, 896}`, and AttnRes block counts `{1, 4, 8}`, all
nine tested production combinations were neutral or faster:

- median speedup range: `+0.26%` to `+20.13%`;
- mean speedup range: `+2.20%` to `+19.05%`;
- `M=1, N=896, blocks=8`: `16.288 us -> 14.240 us` median (`+14.38%`).

A forced prefetch run at `M=4, N=896, blocks=8` regressed from
`16.288 us -> 16.320 us` median (`-0.20%`) and `-1.30%` by mean. Therefore the
production dispatch deliberately keeps the specialization at `M == 1`.

No model-output evaluation was needed because this changes kernel scheduling,
not the mathematical operation; the full numerical suite passed. The previous
TP8 serving result from the broader pre-cleanup diff is not claimed here.

## AI assistance

benchmark analysis. The human submitter must review every changed line and be
able to defend the change end-to-end.
```
