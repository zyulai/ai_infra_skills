## 正文(PR 描述)

## Overview

Fixes https://github.com/vllm-project/vllm/issues/64758: under load, some Kimi-K3 requests turn into streams of token 0 (`!!!!`) until `max_tokens`. This PR moves the FlashKDA and FlashMLA pins to commits with two kernel fixes: https://github.com/vllm-project/FlashKDA/pull/16 and https://github.com/vllm-project/FlashMLA/pull/41.

Both kernel PRs are merged, and the pins point to their upstream merge commits.

## Claims

- FlashKDA prefill no longer copies a NaN from one request into other requests of the same batch. On Kimi-K3 with one injected NaN request, other decodes made bad drop from 96/240 to 0/240.
- FlashMLA's SM90 dense decode kernel now waits for the previous kernel (PDL) before it reads the query. A forced race gives NaN in 49/50 calls on stock and 0/50 with the fix.
- On the natural burst reproducer from the issue, bad requests went from 14 on stock to 0 with both fixes.
- No measurable end-to-end performance cost on Kimi-K3.

## Validation

All runs: `moonshotai/Kimi-K3` @ `f831ab66`, 2 x 8 H200, TP8 x PP2 over InfiniBand, V2 model runner, stock flags from the issue, vLLM `063c0c6` (PR #61867 head). The fixes were applied by swapping only `_flashkda_C` and `_flashmla_C`.

Burst reproducer (`repro_natural_burst.py` in the issue), fresh server per arm, same seed:

| | Stock | FlashKDA fix | FlashKDA fix + FlashMLA fix (no-PDL variant) |
|---|---|---|---|
| Run length | 12.5 min | 10.8 min | 25.0 min |
| First-NaN events | 2 | 1 | 0 (about 2.6 expected, P about 0.08) |
| Bad requests | 14 (groups of 2 and 13) | 1 | 0 |

The last arm used the FlashMLA variant that launches without PDL. The `griddepcontrol.wait` variant pinned here was checked with the forced kernel race (49/50 to 0/50, bit-identical outputs) and in the performance A/B below, but not on the burst reproducer.

With one NaN injected into one request by a debug hook, stock made 96 of 240 other decodes bad and the FlashKDA fix made 0. GSM8K was 0.945 on stock and 0.947 with the fix.

Kernel-level reproducers and tests are in the two kernel PRs.

## Details

**Spread (confirmed): FlashKDA.** Prefill works in chunks of 16 rows. For a sequence's last, partial chunk, it read `beta` and `v` from the rows after the sequence end (the next request in the batch, or the next head) and cancelled them by multiplying by zero. `0 * NaN` is NaN. vLLM runs the decode rows of a mixed step through this kernel together with the prefills, so one NaN request could hit up to 15 decodes and one prefill per step. The fix selects 0 for those rows.

**First NaN (strong suspect, not proven): FlashMLA.** K3's decode path runs `fused_kimi_k3_mla_decode_q_concat_kv_cache_insert`, which writes the query and triggers PDL completion, then FlashMLA's SM90 dense decode kernel. That kernel is launched with PDL but never called `griddepcontrol.wait`, so it could read a query buffer (`torch.empty`) that was not written yet. The fix adds the wait after the prologue. We have not shown that this race causes the natural events; one natural event appeared after the attention output, which it does not explain.

Pin contents:

- FlashKDA: `47fc9fe` (current pin, on upstream `dev`) to `9d9e928`, the merge of vllm-project/FlashKDA#16. No other upstream change comes in.
- FlashMLA: `d1a1c92` (current pin) to `847ef30` on upstream `main`, the merge of vllm-project/FlashMLA#41. It also brings vllm-project/FlashMLA#39, a one-line fix per kernel in the SM100 sparse decode head64 kernels.

Scope and limits:

- The FlashMLA change affects every model that uses the SM90 dense decode kernel, not only Kimi-K3. It adds one wait per CTA and leaves outputs bit-identical. We only measured Kimi-K3.
- CI cannot run Kimi-K3 (two 8 x H200 nodes). The validation above was done outside CI.
- vLLM code is unchanged; only the two pins in `cmake/external_projects/` move.
