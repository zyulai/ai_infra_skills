## Purpose

The dense-MLA prefill spends four kernels per context chunk in
`_compute_prefill_context`:
- `vllm::gather_and_maybe_dequant_cache<bf16,bf16,(0),576,64>`
- `Cijk_…MT192x160x64` (`kv_b_proj` expansion)
- `at::native direct_copy` (`k[..., :128] = k_nope`)
- `at::native direct_copy` (`k[..., 128:] = k_pe`)

AITER ships `gather_kv_b_proj`, which does all four in one launch. `AiterMLAImpl._compute_prefill_context`
now calls it per context chunk, with the per-token KV indices built once per step in the metadata builder.
The fused gather runs only without decode context parallelism (`dcp_world_size == 1`); DCP > 1 keeps
main's DCP prefill path.

`AiterMLAImpl._concat_k_nope_k_pe` now calls the already-merged `fused_kimi_k3_mla_kv_concat` (#51772)
instead of two slice-assign copies, gated on the MLA dims that kernel asserts (`STD_TORCH_CHECK` on
128-wide NoPE / 64-wide rope).

## Test Plan

Unit tests: `tests/kernels/attention/test_rocm_aiter_mla_prefill_fusions.py` (11 cases: fused vs unfused
prefill context, KV indices vs the block table, declined inputs, k concat), all pass on MI355X.

+def _reference_chunk_kv_indices(prefill, chunk) -> torch.Tensor:
+    """Flat per-token cache rows of one chunk, straight from the block table."""
+    block_table = prefill.block_table[chunk.request_slice]
+    cu_seq_lens = chunk.cu_seq_lens.tolist()
+    starts = chunk.starts.tolist()

+        rows.append(

+        )
