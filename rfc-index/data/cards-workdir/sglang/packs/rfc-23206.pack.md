# Rust Server Migration Plan

**Status:** Draft · **Last updated:** 2026-06-18 · **Owner:** Rain Jiang

Migration of the SGLang request front-half (everything from network ingress up to
the point a tokenized request is handed to the GPU scheduler) from Python to a
multi-threaded Rust implementation.

---

## 1. Goals & scope

**Goal.** Replace the Python tokenizer/detokenizer managers and HTTP server with a
single-process, thread-per-core Rust implementation that owns the request lifecycle
up to scheduler submission.

**In scope:** HTTP(S)/gRPC/WS/h2/h3 server, request FSM, tokenizer & detokenizer
managers, multimodal encoder dispatch, control API (abort/flush/weight update etc.),
large tensor zero-copy handoff to the scheduler, cross-dp-group dispatch.

**Out of scope (this plan):** model kernels, attention backends, KV-cache internals,
quantization. The Rust server keeps the existing Python scheduler and GPU worker framework; it does not reimplement them.

**Non-goals:** behavioral changes to the public API. The Rust server must be a
drop-in for the Python one — same endpoints, same request/response schemas, same
streaming semantics — so it can ship behind a flag and be A/B'd against Python.

---

## 2. Architecture summary

The design this phase implement (decided separately; recorded here for context):

- **Two FSMs, one process.** An **ingress FSM** (per request, multi-threaded,
  thread-per-core) carrying a request from `Received` through validation and
  optional encode/tokenize to `Queued`; and an **egress FSM** handling streaming
  (`Streaming` self-loop → `Finalizing` → `Completed`). They are the two halves of
  one request's lifecycle, owned by the same core and meeting at the ring-buffer /
  scheduler boundary — no shared locks.
- **Six thread groups:** (1) **api-server** on an async runtime — accepts
  connections, terminates protocols; (2) **tokenizer-manager** running the
  ingress/egress request FSMs, CPU-core-bound; (3) **encoder** (core-bound);
  (4) **tokenizer** (core-bound); (5) **detokenizer** (core-bound); and
  (6) the python **scheduler** group within main thread. Groups talk only via channels — no shared locks across group boundaries.
- **Channels:** bounded **MPSC** TokenizerManager→Scheduler (`try_send` = backpressure), per-core **SPSC** returns; userspace rings carry the payload, no ZMQ involved. Crossing the Rust→Python boundary, request objects are serialized with **msgpack** so only immutable bytes transfer — keeping the GIL out of the hot path. Tensor data bypasses msgpack entirely and is shared through **pinned memory**, handed across as a handle rather than copied or serialized.
- **Zero-copy:** for encoded multimodal data, Python pre-allocates the pinned buffer pool at startup and Rust writes into slots by index during the encode/tokenize phase. Channels move slot handles (plus small msgpack metadata), never tensor bytes; lifetime is the pool's slot-reuse policy — a slot returns to the free list only after both Python's read and any GPU DMA complete, not Rust's `Drop`.
- **Cross-rank:** For DP attention, the first rank of each DP group runs the Rust server
  *without* the api-server; a single api-server then fans **control** messages to
  every DP group (duplicated, since control must reach all), while **generation**
  requests are **round-robined** across DP groups for load balancing.
- **Streaming:** a single `Streaming` macro state self-loops per chunk; non-streaming
  is just a stream whose frames are accumulated and emitted in `Finalizing`.

See the request-FSM and topology diagrams in the Appendix for detail.

### 3.2 Sequencing & critical path

Items are **not** independent. The dependency spine is:

```
#3 pickle→msgpack  ──►  #4 single-process framework  ──►  #5 tok/detok  ──►  #6 /generate+stream  ──►  #11 API parity
                                              └─►  #10 metrics (parallel)
                                              └─►  #7 encoder (parallel, after #5)
```

**Critical path to a usable July 17 milestone:** 3 → 4 → 5 → 6, with 10 landing in
parallel and 11 close behind. That subset is what makes the Rust server a working,
A/B-testable drop-in for text LLM traffic.

**Recommend deferring out of the July 17 milestone** (track as Phase 1.5 / stretch):
items **8 (PD disaggregation)** and **9 (DP attention + cross-node DP controller)**.
Both are large, both can land after the core path is proven, and bundling them into
the July date puts the whole milestone at risk. Item **12 (unified protocol lib)** is
valuable but is a refactor that can follow once #6 stabilizes the protocol surface.

> **Date reality check.** July 17 is ~4 weeks out and #4 (the foundation) is still
> pending-start. The 3→4→5→6+7 path is achievable in that window if #4 starts
> immediately and 8/9/12 are explicitly descoped. Carrying all 12 to July 17 is not
> realistic; pick the milestone definition deliberately.

### 3.3 Phase 1 exit criteria

- Rust server handles `/generate` (streaming + non-streaming) at parity with Python.
- Tok/detok managers run in-process; detok is incremental and order-correct.
- Encoder path works for at least one multimodal input type.
- Metrics + logs at parity; runs behind a flag, A/B-able against Python.
- Endpoint parity sufficient to route production text traffic.

## 4. Cross-cutting concerns

**Rollout / fallback.** Every phase ships behind a flag with the Python path as the
live fallback. Migrate by traffic slice (shadow → small % → ramp), not big-bang. keep the Python path runnable as the live fallback until the Rust path reaches parity.

**Testing.** Differential testing against Python (same inputs → same tokens/frames)
is the primary correctness gate. Add: FSM property tests (every state has a terminal
exit; post-terminal events are no-ops/idempotent); streaming order + UTF-8-boundary
tests for detok.

**Observability.** Metrics/logging (P1 #10) should land *with* the core path, not
after — debugging the channel/FSM/threading layers without it is painful. Per-state
request counts, queue depths (ring-buffer occupancy = backpressure signal), per-core
load, and control-op latencies.

**Kernel / environment.** io_uring features used (`MSG_RING` 5.18+, `SEND_ZC` 6.0+,
`DEFER_TASKRUN` 6.1+) set a minimum kernel; some hardened/container environments
disable io_uring — keep an epoll+eventfd fallback behind the same loop abstraction.

## 5. Top risks

| Risk                                              | Impact                            | Mitigation                                                                   |
| ------------------------------------------------- | --------------------------------- | ---------------------------------------------------------------------------- |
| July 17 scope (all 12 items)                      | Milestone slips / quality suffers | Descope 8/9/12; define milestone as 3→4→5→6+10.                              |
| #4 framework is the foundation and hasn't started | Blocks 5–7; whole phase waits     | Start immediately; treat as the single highest-priority item.                |
| Rust↔Python boundary in the single-process step   | Perf cliffs, GIL contention       | Keep the boundary narrow (handles, not data); measure early.                 |
| Detok ordering / UTF-8 under streaming            | Corrupt user-visible output       | Shard by `hash(req_id)`; stateful decode offsets; boundary tests.            |
| Slow-client backpressure on egress                | GPU stalls / memory growth        | Bounded egress buffers; treat persistent slow consumer as disconnect.        |
