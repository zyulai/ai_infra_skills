#### Flaky Tests in EAGLE DP

Issue: [#31913](https://github.com/vllm-project/vllm/issues/31913)

This PR resolves the flaky EAGLE DP test in the continuous integration (CI) environment. 
For additional context, related issues and fixes can be found here: https://github.com/pytorch/pytorch/issues/170563.

---

Root Cause: Incomplete batch invariance coverage on L4 GPUs under torch.compile. Two gaps were identified and fixed:

1) UnquantizedEmbeddingMethod.apply (lm_head projection)

UnquantizedLinearMethod.apply (used by all model linear layers) checks VLLM_BATCH_INVARIANT and routes to the deterministic Triton persistent kernel. But UnquantizedEmbeddingMethod.apply (used by ParallelLMHead for the final hidden→vocab logits projection) was missing this check, it always used dispatch_unquantized_gemm() (cuBLAS), which produces batch-size-dependent results on L4.
File: vllm/model_executor/layers/vocab_parallel_embedding.py

2) Batch invariance + torch.compile + CUDA graphs on SM<90 

With enforce_eager=False, both torch.compile and CUDA graph capture are active. On SM<90 (e.g., L4), batch invariance does not work reliably under this combination, the test diverges at varying token positions across runs.
I initially suspected this was due to RMSNorm dispatching to forward_native under custom_ops=["none"], with Inductor codegenning a non-batch-invariant reduction kernel. But an inline repro on L4 in CI showed that torch.compile(rms_norm_native) is actually batch invariant for batch=1 vs batch=4 of the same input row (bitwise_equal: True, max_abs_diff: 0.0), so RMSNorm itself isn't the fault.
This turned out to be a known issue. PR #30018 added enforce_eager=IS_DEVICE_CAPABILITY_BELOW_90 to all 5 batch invariance tests, with the comment in tests/v1/determinism/utils.py:

Note: For devices with SM < 90, batch invariance does not support CUDA Graphs.

The EAGLE DP test was the only batch invariance test that didn't follow this pattern, it had enforce_eager=False unconditionally.
The fix matches the existing pattern: enforce_eager=IS_DEVICE_CAPABILITY_BELOW_90. On L4 (SM89) this disables both torch.compile and CUDA graphs; on H200 (SM90) it stays False since Hopper+ doesn't hit the limitation.
I also tested cudagraph_mode=NONE with enforce_eager=False to isolate which optimization is the actual culprit, the test still failed at token 80. So both torch.compile and CUDA graphs contribute on SM<90, and disabling just one isn't enough. The comment in utils.py may be incomplete, torch.compile is also implicated, not just CUDA graphs. The broader tracking is in [#39096](updated).

Plus, adding the EAGLE DP tests to the Distributed Tests (2 GPUs)(H100) group. The PR includes the relevant changes for this as well.
