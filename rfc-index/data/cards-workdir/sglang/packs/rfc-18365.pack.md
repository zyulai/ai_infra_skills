## 📝 Abstract

This RFC proposes a structural refactoring of the SGLang codebase to migrate Triton kernels currently embedded within the `layer`, `models`, `model_executor`, and `speculative` modules into the dedicated `sgl-kernel` repository.

Currently, Triton kernels are directly integrated into high-level Python logic. Given Triton's deep dependency on hardware-specific characteristics (e.g., register pressure, shared memory size, L2 cache strategies), this tight coupling hampers framework maintainability and complicates cross-platform compatibility (e.g., migrating from NVIDIA CUDA to AMD ROCm or other AI accelerators).

---

## 💡 Motivation

The current architectural coupling between Triton kernels and framework logic introduces several critical pain points:

* **Cross-layer Maintenance Overhead**: Developers modifying high-level `models` logic are forced to manage low-level Triton parameters like `grid`, `num_warps`, and `num_stages`.
* **Hardware Vendor Lock-in**: The `model_executor` should focus on execution flow and scheduling; however, it currently handles hardware-specific Triton compilation and environment checks.
* **Architectural Redundancy**: Similar kernel logic is often duplicated across different layers (e.g., standard inference vs. speculative decoding) due to the lack of a unified kernel management layer.
* **Complex Release Cycles**: Changes in hardware drivers or Triton versions often trigger unnecessary regressions in the main framework instead of being isolated within a kernel library.

---

## 🏗️ Proposed Changes

We propose a "De-Tritonization" of the four core layers, ensuring that high-level Python logic interacts with hardware kernels only through standardized APIs provided by `sgl-kernel`.

### Core Layer Transition Map 📋

| Layer / Module     | Target Architecture                                                                     |
| ------------------ | --------------------------------------------------------------------------------------- |
| **Layer**          | Define abstract layers in the framework; export actual computation to `sgl_kernel.ops`. |
| **Models**         | Retain only parameter loading and architectural orchestration; offload all kernels.     |
| **Model Executor** | Focus on task scheduling; abstract away Triton compilation and environment checks.      |
| **Speculative**    | Extract complex sampling and verification kernels to improve algorithm readability.     |

---

## 🛠️ Technical Approach

### 1. Standardizing Kernel Interfaces

Establish a unified Entry Point mechanism in `sgl-kernel`. This interface will accept essential Tensors and metadata while encapsulating hardware-specific tuning parameters (Auto-tuning) within the kernel library itself.

### 2. Refactoring the Call Chain

* **Current**: `from sglang.srt.layers.kernels.attention import triton_attention_kernel`
* **Proposed**: `import sgl_kernel; sgl_kernel.ops.attention(...)`

### 3. Environment Isolation

Remove the hard dependency on specific Triton internal versions from the main SGLang package. Use `sgl-kernel` as a middleware layer to handle hardware compatibility checks and runtime dispatching.

---

## 🗺️ Implementation Roadmap

| Phase                       | Key Tasks                                                                              | Goal                                            |
| --------------------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------- |
| **Phase 1: Layer & Models** | Migrate general-purpose kernels from `layer` and model-specific kernels from `models`. | Achieve "Pure Python" model definitions.        |
| **Phase 2: Speculative**    | Offload verification and sampling kernels from the speculative decoding module.        | Accelerate iteration on speculative algorithms. |
| **Phase 3: Model Executor** | Strip hardware-aware code from the executor and wrap parameter inference.              | Full decoupling of scheduling and execution.    |

---

## ⚖️ Pros and Cons

### Pros ✅

* **Code Cleanliness**: Significantly reduces the LoC (Lines of Code) in `models` and `layer` modules, making business logic transparent.
* **Independent Evolution**: `sgl-kernel` can evolve independently for performance tuning and hardware porting without affecting framework stability.
* **Multi-backend Potential**: Provides a clear path for SGLang to support diverse AI chips by swapping the underlying kernel implementation.

### Challenges ⚠️

* **Cross-repo Workflow**: Developers will need to manage contributions across two repositories (mitigated via `pip install -e`).
* **API Stability**: The offloaded kernel APIs must maintain backward compatibility to avoid breaking the main framework logic.
