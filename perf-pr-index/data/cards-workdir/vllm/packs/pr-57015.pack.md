## PR body

## Summary

The `wvSplitK` int4 skinny GEMM stages activations into LDS as `s[k_ + K * n]` and reads them back per row. `K` is a runtime value, so the compiler cannot prove the per-row offset `K*n` is 16-element aligned and falls back to paired `ds_load_2addr_b32`/`b64` for the higher rows. But `K` is a multiple of `A_CHUNK` and so is `k_`, so `s[k_ + K * n]` is in fact `sizeof(bigTypeA)`-aligned for every row — annotating the read lets the compiler widen all activation rows to `ds_load_b128`.

That invariant was implicit: `A_CHUNK` is a template argument pinned to 16 by the launch macro, and the host only checks `K % 16 == 0`. The k-loop already relies on it too, since it consumes whole `A_CHUNK` chunks. The host check now uses a shared `kInt4KAlign` constant, each kernel does `static_assert(kInt4KAlign % A_CHUNK == 0)`, and the LDS buffer is declared `alignas(sizeof(bigTypeA))`, so raising `A_CHUNK` fails to build until `kInt4KAlign` is raised with it.

This is a compiler-visibility argument rather than an architectural one, so it is not gated on a specific gfx target. The global fallback read in the medium kernel is deliberately left untouched: `A[]`'s base alignment is not guaranteed there.

LDS load instructions across all int4 instantiations, gfx1151 with ROCm 10.2, counted by disassembling the gfx1151 device image out of the built `_rocm_C.abi3.so`:

| | `ds_load_b128` | `ds_load_2addr_b32` | `ds_load_2addr_b64` | total |
|---|---|---|---|---|
| before | 6864 | 3744 | 624 | 11232 |
| after | 9360 | 0 | 0 | 9360 |

`N=1` and `N=2` were already fully widened by this compiler and come out byte-identical; the change is confined to `N=3,4,5`.

## Measurements

`benchmarks/kernels/benchmark_rdna_hybrid_w4a16_gemm.py`, `--group-size 128`, batch 4, median of 3 passes, TFLOP/s, symmetric / asymmetric:

| K x N | before | after | delta |
|---|---|---|---|
| 2048x2048 | 2.501 / 2.020 | 2.929 / 2.316 | **+17.1% / +14.6%** |
| 2560x2560 | 3.040 / 2.853 | 3.392 / 3.038 | **+11.6% / +6.5%** |
| 8192x2048 | 2.218 / 1.645 | 2.276 / 1.743 | +2.6% / +6.0% |
| 2560x3840 | 3.834 / 3.402 | 3.877 / 3.510 | +1.1% / +3.2% |
| 2048x6144 | 3.301 / 3.122 | 3.275 / 3.077 | -0.8% / -1.4% |
| 2048x16384 | 3.258 / 3.162 | 3.272 / 3.164 | +0.4% / +0.1% |
| 2560x19456 | 3.361 / 3.334 | 3.369 / 3.321 | +0.2% / -0.4% |

The win concentrates on small `out_features`, where the kernel is bound by the LDS read rather than by the weight stream. Batch 1 and 2 are flat everywhere, which is exactly what the instruction counts predict. Only shapes that actually reach the HIP skinny path (`M <= 5` and `K*M <= 32768`) are listed; the rest route to Triton and are unaffected.

Reproducing the asymmetric column needs #57004, without which the benchmark's `hybrid-w4a16-zp` provider raises.

## Model evaluation

GSM8K on gfx1151, full 1319 questions, 5-shot, greedy, seed 42. `max_num_seqs=4` so every decode step runs the `N=3,4` instantiations this change touches (`max_num_seqs=1` would only exercise the unchanged `N=1` path):

```bash
lm_eval --model vllm \
  --model_args pretrained=<model>,max_model_len=4096,max_num_seqs=4,dtype=float16,gpu_memory_utilization=0.75,enforce_eager=False,seed=42 \
  --tasks gsm8k --num_fewshot 5 --batch_size auto --seed 42
```

| model | filter | before | after |
|---|---|---|---|
| `Qwen/Qwen3-8B-AWQ` | strict-match | 0.8582 ± 0.0096 | 0.8590 ± 0.0096 |
| `Qwen/Qwen3-8B-AWQ` | flexible-extract | 0.8613 ± 0.0095 | 0.8620 ± 0.0095 |

Qwen3-8B-AWQ differs by a single question, well inside one stderr. Average output throughput over the eval run is flat (20.9 vs 20.6 tok/s).
