## 正文(PRD / 提案全文)

### Motivation.

> [!NOTE]
> This RFC expands the original request-admission proposal into an end-to-end plan for Model Runner V2 (MRV2) pipeline-parallel feature composition. The original proposal remains Workstream A below, with its prototype in #50410.

MRV2 pipeline parallelism (PP) already overlaps multiple batches to reduce pipeline bubbles (#42187). With asynchronous scheduling, it keeps `pp_size + 1` batch slots in flight, while a decode request becomes eligible again after a `pp_size`-step cadence.

That foundation works for basic generation, but the surrounding features do not yet compose cleanly with PP:

| Area | Current state | Gap addressed by this RFC |
|---|---|---|
| Request scheduling | Basic MRV2 PP works | A burst can fill the global request slots in one batch and leave later PP batches empty |
| MTP speculative decoding | Work is in progress | Drafts produced and applied locally on the last rank must be published to non-last ranks and restored for the still-live rows of the stored step-`T` feedback slot |
| EAGLE3, DFlash, and DSpark | Explicitly rejected with PP in MRV2 today | Auxiliary hidden states may be produced on earlier ranks but are consumed by the proposer on the last rank |
| Index-sharing models | Rank-local buffers work when producer and consumer are colocated | A PP cut may fall between an index producer and a layer that reuses its top-k indices |
| PP + DP/EP topology | Current deployments commonly place complete DP replicas contiguously | On multiple nodes this tends to keep PP local while DP/EP groups cross nodes; a PP-first placement should keep EP/TP inside a node and move PP traffic across nodes |

The common theme is that PP is not only a partition of model layers. It also creates two state-transfer paths with different direction and lifetime:

1. **forward state**, sent from one PP rank to the next for the current microbatch; and
2. **deferred result state**, applied locally on the last rank and published to non-last ranks, which consume the stored `PPHandler` FIFO slot `pp_size` local feedback-ring steps later.

Adding each new tensor with one-off communication code would make ordering, CUDA-graph capture, request-slot reuse, and multi-node topology assumptions increasingly fragile. This RFC therefore proposes both the missing feature support and a small declarative PP transport abstraction that can carry future optional state without redesigning the execution loop each time.

#### Goals

- Balance request admission across concurrent MRV2 PP batches.
- Define correct MRV2 PP composition with MTP, EAGLE3, DFlash, and DSpark speculative decoding.
- Carry auxiliary hidden states and cross-partition index-sharing state when a model partition requires them.
- Define a PP-first multi-node placement in which each node hosts one complete PP stage's DP/EP domain, keeping EP/TP communication intra-node and PP communication inter-node.
- Keep optional communication absent when a model or configuration does not need it.
- Preserve static, graph-friendly buffer schemas and minimize extra collectives.

#### Non-goals

- Changing Model Runner V1.
- Introducing a new speculative decoding algorithm.
- Redesigning DP request routing, real/dummy execution cadence, or wave draining, or migrating live request/KV state between DP lanes.
- Introducing a new pipeline schedule such as interleaved 1F1B.
- Requiring every model to emit auxiliary hidden states or index buffers.
- Enabling adaptive verification with PP in the first rollout; it needs a separate protocol for trimmed shapes, confidence/cost state, and rank agreement.
- Supporting a PP-stage DP/EP footprint that cannot fit in a node-local topology domain in the first rollout.

### Proposed Change.

Implement the RFC as four independently reviewable workstreams over one set of communication and correctness invariants.

```text
                    current-microbatch forward plane
  scheduler  ->  PP rank 0  ->  ...  ->  PP rank N (sample + propose)
                    | IntermediateTensors | aux hidden states | shared indices |
                    |
                    +<---------- deferred result plane ----------+
                       sampled/count metadata and optional drafts
                       (queued in the worker-side PPHandler feedback FIFO)

  PP-first multi-node placement:

  node 0 / PP stage 0: [DP0 ... DPN]  <- EP/TP stays node-local
                              |  PP lanes  |
  node 1 / PP stage 1: [DP0 ... DPN]  <- EP/TP stays node-local
```

#### Workstream A: balance request admission across PP batches

Within each scheduler/DP replica, the scheduler currently applies `max_num_seqs` as one global running-request limit and greedily fills a batch until an existing token, sequence, KV-cache, or model-specific constraint is reached. A burst of short, uniform requests can therefore consume all local request slots before the pipeline has formed multiple useful batches.

For example:

```text
pipeline_parallel_size = 2
max_num_seqs = 25
50 short requests arrive together
```

The current scheduler can produce `25, 0, 25, 0` scheduled requests over four steps. The prototype in #50410 instead caps the next batch at:

```python
num_requests = min(
    max_num_running_reqs,
    get_num_unfinished_requests(),
)
max_num_scheduled_reqs = ceil(num_requests / pp_size)
```

The prototype applies the cap to both requests already in `RUNNING` and admissions from `WAITING`, while all existing token, KV-cache, priority, preemption, structured-output, and model-specific constraints remain authoritative. In the example, the first two useful batches become approximately `13, 12` instead of `25, 0`.

The divisor is `pp_size`, not `pp_size + 1`: the additional asynchronous queue entry covers result propagation and scheduler/worker overlap rather than an additional compute stage. Non-final chunked-prefill chunks remain eligible in adjacent steps because they do not depend on sampled-token feedback.

This is intentionally a PP batch target, not a claim that request count always equals compute. Request count is a useful decode proxy; scheduled tokens are a better prefill proxy.

The proposed MVP differs from the current prototype in one important respect: already-eligible `RUNNING` decode keeps its existing scheduling behavior, while the balance target is a soft cap on **new/resumed admission from `WAITING`**. The target may be exceeded when later phases have no runnable work, at low concurrency, at a KV/capacity boundary, or to prevent priority starvation. This preserves work conservation and avoids delaying active decode solely to make phase widths look uniform.

Every DP replica computes this target locally. Evaluation should decide whether the final policy is request-count based, token based, or hybrid, and whether a persistent phase assignment is worth its complexity around completion, abort, preemption, resume, and priority changes.

#### Workstream B: make PP state transport extensible

Refactor PP state ownership into a small declarative module. `PPTransport`, `ForwardPayload`, and `DeferredResultPayload` below are conceptual names, not a required public API.

One ownership module describes two independent schemas and communicators:

**1. Forward payload: adjacent rank -> adjacent rank, current microbatch**

- opaque model `IntermediateTensors` such as `hidden_states` and `residual`;
- namespaced sidecars for auxiliary hidden states keyed by a global activation-boundary ID and configured slot;
- a namespaced active top-k/index sidecar when the partition boundary crosses an index-reuse dependency.

**2. Deferred result payload: last PP rank -> every non-last PP rank, delayed receiver slot**

- sampled tokens;
- sampled/rejected-token counts;
- optional next-step draft tokens;
- local queued request mappings and generation metadata that associate the received rows with still-live request slots (these do not need to be network fields).

Each adjacent forward edge has its own field/liveness plan; the existing `PPHandler` sibling broadcast has one group-consistent feedback plan. They share descriptor and lifecycle machinery but not communicator, stream, cadence, or participant set. A conceptual field descriptor is:

```python
@dataclass(frozen=True)
class PPTensorSpec:
    name: str
    plane: Literal["forward", "deferred_result"]
    boundary_id: int | None
    slot: int | None
    dtype: torch.dtype
    trailing_shape: tuple[int, ...]
    tp_policy: Literal["replicated", "sharded", "direct"]
    carry: Literal[
        "one_edge", "until_last", "until_consumed", "feedback_group"
    ]
    lifetime: Literal["forward_execution", "delayed_request_state"]
```

The exact fields can differ. The correctness MVP should run the declared plan over the existing tensor-dict path:

- namespace and split opaque model tensors from optional sidecars;
- keep each edge's field presence, key, dtype, slot ordering, carry policy, and TP policy deterministic after initialization;
- export/import sidecars through model-specific adapters;
- retain current tensor-dict metadata and allocation behavior where required for backend compatibility;
- stream/event ownership and buffer reuse centralized in the transport module;
- request generation/slot checks retained for delayed feedback, so an aborted or replaced request cannot consume stale state;
- group-identical feedback row order, row count, dtype/shape, collective order, and whole-collective skip decisions; no branch on rank-local optional-field presence;
- optional fields disabled add no bytes or collectives beyond the existing forward and sampled/count feedback paths.

For forward sidecars, `N` means the execution row count after padding (`num_tokens_after_padding` / the batch execution descriptor), not only logical scheduled tokens. Buffers and wire shapes use `N`; adapters separately track which rows contain real tokens.

For the initial models in this RFC, auxiliary hidden states are TP-replicated, and shared top-k is TP-replicated `[N, index_topk]` `torch.int32`. Existing model tensors such as sequence-parallel residual state retain their direct/sharded policy. Because the current tensor-dict path may automatically slice/all-gather based on tensor size, sidecar policy must be explicit rather than inferred from divisibility.

Model-specific adapters should declare which sidecars a partition boundary needs, export locally produced fields, and import received fields into the correct persistent model buffer. The communication layer should not interpret EAGLE, DSpark, or model-specific index semantics. Namespaced wire keys such as `model/*`, `spec/aux_hidden_states`, and `model/shared_index_topk` can avoid collisions while keeping ordinary model tensors opaque.

A later performance phase may compile a static wire schema, use persistent graph-address-stable receive buffers, and remove per-step CPU metadata. That requires explicit lower-level `GroupCoordinator`/backend protocol work and is not implied by adding the correctness wrapper.

Compatible small fields should be packed when doing so removes latency-sensitive collectives, following the direction explored in draft #47686. Large auxiliary tensors should not be blindly packed with token metadata: grouping must respect direction, dtype, destination, lifetime, TP layout, and performance. The abstraction is unified at the ownership/schema layer, while the two data planes remain separate internally.

#### Workstream C: compose PP with speculative decoding

##### C1. Base MTP draft-feedback synchronization

Under MRV2 asynchronous scheduling, scheduler-side speculative token IDs are shape placeholders: their authoritative values remain in per-worker GPU request state. The speculative proposer runs on the last PP rank. Every stage's sampled/draft/sequence bookkeeping must nevertheless describe the same logical token sequence: the first stage materializes the correct sampled-plus-draft token IDs, while later stages consume the corresponding forward activations and attention metadata.

Here `pp_feedback_step` means a local worker execute/control step that advances the `PPHandler` FIFO. It is not an EngineCore asynchronous batch-queue slot and is not advanced by a MoE DP dummy forward.

#52295 implements the narrow synchronization piece. The last rank applies sampled state locally in feedback step `T`, runs proposal, retains its new draft state, and then publishes one feedback record to non-last ranks. The token wire payload is fixed at `[B, (K + 1) + K] = [B, 2K + 1]` (`int64` sampled plus draft columns), while the existing `[2, B]` (`int32`) sampled/rejected count collective remains. Draft synchronization therefore adds `K` token-ID columns per request but no new collective.

Each non-last rank posts the matching receive in feedback step `T`, queues it with the saved row mapping, need mask, and slot-generation snapshot, and applies the surviving rows at feedback step `T + pp_size`. Sampled and draft rows use the same liveness/generation decision; invalid draft rows are compacted before index-copy because a `-1` destination is not valid for that operation. The association comes from FIFO feedback-step order and the saved step-`T` metadata, not from the composition of the current batch at `T + pp_size`.

The required invariant is:

> The last stage applies its sampling outcome and derived next-step drafts locally in feedback step `T` and publishes them as one causally consistent record. Every non-last stage posts the matching receive in step `T` and applies the stored live rows at feedback step `T + pp_size`, before that request's next verification input is prepared.

#52295 should be treated as the base transport/state-synchronization change, not as the complete enablement of every MTP model. Its transport gate is PP plus any speculative configuration that has already passed validation, so this feedback mechanism should not be duplicated per speculative method. Broader model-specific work in #46994 includes PP capability declarations, model-specific projection paths, weight/embedding ownership, and a same-rank stale sparse-MLA buffer-reference fix. Those requirements should either land with the affected model or be guarded by an explicit support check; the same-rank buffer fix is distinct from the cross-rank dependency in C3.

Fixed wire width also needs an explicit validity/padding protocol for a normal `[B, 1]` no-draft or prefill sampler source; `num_sampled` determines which sampled columns are valid. Existing #52295 coverage consists of two CPU/mock tests for payload splitting/event waiting and draft slot writeback. Real multi-rank communication, fixed-width send/receive, `T -> T + pp_size`, partial abort/reuse, and mixed prefill/decode are merge/enablement criteria, not established behavior. Delaying broadcast until after proposal may also change overlap, so validation must include TPOT and proposer latency.

##### C2. EAGLE3, DFlash, and DSpark auxiliary hidden states

These methods require auxiliary target-model hidden states during proposal. MRV2 currently rejects EAGLE3, DFlash, and DSpark with PP before execution. If those guards were simply removed, each rank would capture only its local auxiliary outputs and a non-last rank would return ordinary `IntermediateTensors` without carrying those outputs, so the proposer on the last rank would still see incomplete state.

For a configured set of auxiliary layers:

1. normalize each capture point to a global **activation-boundary ID** (`0` for the state before the first layer and `layer_idx + 1` for the state after that layer), including method-specific `+1` conversions;
2. map boundary IDs to the draft configuration's fixed slot order rather than numerically sorting IDs;
3. when an auxiliary state is produced, add it to the forward payload;
4. carry it through subsequent PP boundaries with `until_last` liveness;
5. combine upstream and last-rank-local states in configured slot order;
6. pass the ordered states to the proposer on the last PP rank.

Auxiliary states are forward dependencies of the current microbatch, not delayed sampled-token feedback. They should therefore use the adjacent-rank forward plane and must not be added to the last-rank-to-non-last-ranks feedback broadcast.

The schema must support zero, one, or multiple auxiliary tensors, and partition tests must cover auxiliary boundaries on the first, middle, and last PP ranks. Implementations that pack compatible states may use a stable `[N, slots, hidden]` layout where `N` is the padded execution row count, but correctness must not depend on all states having identical shapes. Persistent receive/pack buffers are a performance-phase optimization for avoiding per-step allocation and address changes under CUDA graphs.

Transport is necessary but not sufficient to remove the current PP guards. Model-specific enablement must also normalize activation-boundary IDs and target layer counts to global (not stage-local) coordinates, validate draft embedding/head ownership on the last rank, and remove loader-level PP rejections only after the corresponding model path is tested.

##### C3. Index-sharing state across a PP cut

Some models compute top-k routing/index information in one layer and reuse it in later layers. For example, an index-sharing pattern may contain one producing layer followed by layers that skip top-k computation and read a persistent buffer.

If PP cuts between that producer and a consumer in the same reuse interval, a rank-local buffer on the downstream rank has not been populated for the current microbatch. The forward schema must then carry the active top-k buffer across one or more reuse-only stages until it is consumed or overwritten.

At model/partition initialization, dependency analysis should determine whether a boundary crosses an index-reuse interval:

- if it does not, no extra tensor is registered;
- if it does, register the current contract—TP-replicated `[N, index_topk]` `torch.int32`, where `N` is the padded execution row count—and copy it into the downstream persistent shared buffer before model/graph execution;
- tie buffer validity and lifetime to the forward microbatch/transport handle so data cannot leak between in-flight batches;
- allow future model adapters to declare other trailing dimensions or dtypes without weakening this RFC's concrete acceptance contract.

This cross-rank dependency is distinct from the stale-buffer-reference issue addressed by parts of #46994 when draft and target models share an indexer on the same rank. Both must be correct, but only the former requires PP-boundary transport.

As an initial safety fallback, unsupported partitions may fail early with a precise error. The intended final behavior is to transport the dependency rather than permanently constraining PP cuts to index-reuse boundaries.

#### Workstream D: PP-first DP/EP topology for multi-node serving

This workstream is about **physical partition and placement order**, not a new DP load-balancing, dummy-forward, or drain protocol. Each request remains sticky to one logical DP lane, and that lane still traverses one complete PP pipeline. The proposal first assigns nodes to PP stages, then places the stage's DP/EP (and TP, when used) ranks inside that node.

##### D1. Background: why DP-first placement is suboptimal for multi-node MoE

With a conventional DP-first placement, complete DP replicas are packed before moving to the next node. Consider two 8-GPU nodes with `PP=2`, `DP=8`, and `TP=1`:

```text
default physical placement

node 0: DP0{PP0,PP1} DP1{PP0,PP1} DP2{PP0,PP1} DP3{PP0,PP1}
node 1: DP4{PP0,PP1} DP5{PP0,PP1} DP6{PP0,PP1} DP7{PP0,PP1}
```
