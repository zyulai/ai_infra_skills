## 正文(PR 描述)

**Bug:** 
Currently, vLLM crashes with a `cuMemcpyBatchAsync` segfault when using native KV offloading (`--kv-offloading-backend native`) alongside MTP speculative decoding on long contexts.

**Root cause:** 
I found that the `OffloadingConnectorScheduler` was accidentally including EAGLE/MTP draft-attention groups in both the load and store scheduling paths. Since these draft groups don't have stable block hashes and use tiny `gpu_block_size` values, it caused a massive miscalculation (`num_gpu_blocks = cdiv(420K, small_size) = 105022`). This resulted in an out-of-bounds GPU block index that triggered a silent, hard-to-debug CUDA segfault in `swap_blocks_batch`.

**Fix:** 
- Added an `is_eagle_group` flag to `GroupOffloadConfig` so we can easily spot these groups.
- Updated the scheduler to skip eagle groups entirely in all load/store scheduling loops. 
- As a defense-in-depth measure, I also added a pre-DMA bounds check in `gpu_worker.py`. This ensures that if any out-of-bounds block ID ever slips through in the future, it safely throws a clear Python `RuntimeError` instead of a silent CUDA segfault.

**Accountability:**
I used some AI assistance to help me track down the root cause and write the patches, but I have manually reviewed every changed line to ensure it's correct. I am relying on the GitHub CI to run the full Linux suite since I am developing on Windows.

**Testing:**
Verified the fix locally via a custom standalone regression test suite (8 passing tests ):
- Confirmed `is_eagle_group` correctly populates and defaults to `False` (preserving backward compatibility).
- Verified the load path (`update_state_after_alloc`) and store path (`_build_store_jobs`) appropriately skip MTP groups and correctly return `group_sizes=0` and `block_indices=0`.
- Verified the defense-in-depth bounds check safely catches out-of-bounds IDs before triggering the CUDA call.

Closes #44780
