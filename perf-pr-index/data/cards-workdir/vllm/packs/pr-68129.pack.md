## Overview

Follow-up to #62550. PrimTS SWA attention now keeps speculative verify batches on its paged decode plan for every draft length, instead of only up to four query tokens.

## Claims

- With FP8 KV cache and more than three draft tokens, every SWA layer's verify step previously fell back to the prefill plan. On 4x GB300 with MTP `num_speculative_tokens=6`, this change raises output throughput by 8.2% at concurrency 64 and 3.6% at concurrency 16, with no change at concurrency 1.
- Outputs are unchanged. Draft acceptance and GSM8K stay within run-to-run noise.

## Validation

Step5, TP4 + EP, PrimTS attention, FP8 KV, MTP `num_speculative_tokens=6`, `--block-size 64`, random 1024 in / 512 out, steady-state round. Both arms include #66951, which this configuration needs to start (see Details).

| Concurrency | main (tok/s) | this PR (tok/s) | Speedup |
|---|---|---|---|
| 64 | 1,155 | 1,250 | 1.08x |
| 16 | 474 | 491 | 1.04x |
| 1 | 62 | 61 | 1.00x |

GSM8K (1319 questions): 0.942 → 0.933, within run-to-run noise. Draft acceptance rate is 4.97% vs 4.96%.

The new test `test_prims_ts_swa_verify_beyond_four_tokens_uses_decode_plan` checks a five-token verify batch against an FP32 reference, eagerly and under CUDA graph replay, and asserts that it uses the decode plan. It fails with the old threshold and passes with this change. `pytest tests/models/step5/test_prims_ts_attention.py tests/kernels/test_fused_qknorm_rope_cache.py` passes (36 tests) on GB300 with FlashInfer 0.7.4. CI runs `tests/models/step5` only on H200 and MI355, where these PrimTS tests skip because they need SM100/SM103/SM107.

## Details

`Step5PrimsTSSWA` picked the decode plan only for uniform batches with `qlen <= 4`, while PrimTS routing and Step5 prefill planning treat uniform batches up to `num_speculative_tokens + 1` as decode. On uniform batches, the decode plan was 1.6-22x faster than the prefill plan in a CUDA-graph microbenchmark across 1-64 query tokens, and equal at 128. Its output matched the FP32 reference at 5 and 8 query tokens. The threshold is now `max(4, num_speculative_tokens + 1)`, so non-speculative uniform batches of up to four tokens keep the plan they use today. It stays bounded rather than unlimited because the decode plan is keyed by exact request count and query length.

BF16 KV is unaffected because routing already sends those verify batches to the native path. Step5 MTP requires a multiple of the three MTP modules, so 6 is the first MTP setting that reaches this path. Before #66951 that setting failed at startup for every attention backend, because multi-module MTP re-prefill could produce negative positions.
