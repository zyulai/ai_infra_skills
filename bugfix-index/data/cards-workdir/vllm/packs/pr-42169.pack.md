## 正文(PR 描述)

## Purpose:
It is observed that DeepSeek v4 has numerical issues when passing certain values of `--max-model-len` (e.g., 900000). For instance, the following figure shows the distribution of the number of completion tokens with 100 responses sampled for a selected question from GPQA. It can be seen that the number of generated tokens has a noticeable distribution shift when `--max-model-len 900000` is passed, compared to that not passed. 

<img width="950" height="564" alt="rank_completion_tokens" src="https://github.com/user-attachments/assets/97cf5aef-c770-44c1-91fa-7184b243b574" />

Investigation shows that the root cause is that the indexer persistent topk kernel uses `const int64_t stride = logits.size(1);`. However, the logits produced from [deepgemm's](https://github.com/deepseek-ai/DeepGEMM/blob/891d57b4db1071624b5c8fa0d1e51cb317fa709f/csrc/apis/attention.hpp#L361) `fp8_fp4_paged_mqa_logits` pads the `max_model_len` dimension to align with 256 and later slices the view to `max_model_len`. Thus, when `max_model_len` is not naturally aligned, the logits become incontiguous, thus the stride calculation is incorrect. This PR fixes this bug.

To reproduce the experiment:
```
VLLM_ENGINE_READY_TIMEOUT_S=3600 \
vllm serve deepseek-ai/DeepSeek-V4-Pro \
--kv-cache-dtype fp8 \
--trust-remote-code \
--block-size 256 \
--no-enable-prefix-caching \
--compilation-config '{"cudagraph_mode":"FULL_AND_PIECEWISE","custom_ops":["all"]}' \
--attention_config.use_fp4_indexer_cache True \
--tokenizer-mode deepseek_v4 \
--tool-call-parser deepseek_v4 \
--enable-auto-tool-choice \
--reasoning-parser deepseek_v4 \
--max-cudagraph-capture-size 2048 \
--max-num-batched-tokens 2048 \
--max-model-len 900000 \
--no-enable-flashinfer-autotune \
--tensor-parallel-size 8
```

Set and unset `--max-model-len 900000` to see the difference.
