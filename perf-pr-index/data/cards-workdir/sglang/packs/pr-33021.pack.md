## PR body
```markdown
Dependent on https://github.com/ROCm/aiter/pull/4478, merged and aiter update on 08/21
## Motivation

On gfx95 (MI35x, ROCm >= 7.2) the gfx95 bpreshuffle FP8 block-scale GEMM consumes the per-group activation scale in a **column-major** layout, whereas the fused all-reduce + RMSNorm + per-group-FP8-quant kernel emits it **row-major**. To bridge the two, the fused-quant path in `layernorm.py` currently runs an explicit post-kernel transpose (`materialize_bpreshuffle_fp8_scale`, i.e. `scale.t().contiguous().t()`) on every eligible layer. That `.contiguous()` launches an extra copy kernel per fused-quant call — pure overhead in the decode-latency-bound regime where the model is dominated by many small kernel launches.

aiter's fused kernel already has a compile-time `TRANSPOSE_SCALE` template (ROCm/aiter#3652) that can write the scale directly in the column-major layout the bpreshuffle GEMM wants, at zero extra cost (it only changes the store-index math). This PR plumbs that flag through so the fused kernel emits the transposed scale itself, and drops the redundant post-kernel transpose on the fused-success paths.

The emitted layout is byte-for-byte identical to what `materialize_bpreshuffle_fp8_scale` produced (column-major storage `(num_groups, M)` viewed as `(M, num_groups)`, stride `(1, M)`), so this is a numerics-preserving change.

This is FP8-only. The MXFP4 path uses a different kernel (`custom_fused_ar_rms_mxfp4_quant`) and is untouched.

**Dependency:** requires the paired aiter change that forwards `transpose_scale` through `custom_fused_ar_rms_per_group_quant` / `fused_ar_rms_per_group_quant` / the ops stub to the (already capable) C++ op, plus a bundled-aiter pin bump. Without it, the fused-kernel call falls back (the flag is ignored / raises and is caught), so this PR should land together with / after the aiter bump.

## Modifications

- `python/sglang/srt/distributed/communication_op.py`: add a `transpose_scale` kwarg to `tensor_model_parallel_fused_allreduce_rmsnorm_quant_per_group` and forward it to the group coordinator.
- `python/sglang/srt/distributed/parallel_state.py`: add `transpose_scale` to `GroupCoordinator.fused_allreduce_rmsnorm_quant_per_group` and forward it into the `ca_comm.custom_fused_ar_rms_per_group_quant` call.
- `python/sglang/srt/layers/layernorm.py`: pass `transpose_scale=use_bpreshuffle` to both fused per-group-quant calls (the `keep_bf16=False` attention path and the `keep_bf16=True` GDN emit_bf16 path), and remove the now-redundant `materialize_bpreshuffle_fp8_scale` on the two fused-success return paths.
- The two separate-per-group-quant **fallback** paths intentionally keep `materialize_bpreshuffle_fp8_scale`: `per_1x128_quant`'s own `transpose_scale` byte-shuffles the scale into a different physical arrangement, not the column-major layout this GEMM consumes.
- The FP8 linear consumer (`aiter_w8a8_block_fp8_linear`) is unchanged: the scale layout reaching it is identical, and its own `materialize` call becomes an idempotent no-op (`.contiguous()` short-circuits on an already-column-major tensor).

## Benchmarking and Profiling

**Kernel-level confirmation (conc4 profile, IL8192/OL1024, 8 steps):** the fused kernel template flipped `TRANSPOSE_SCALE` false→true (`allreduce_fusion_kernel_1stage_per_group<…Lb0ELb0E>` → `<…Lb0ELb1E>`, 354 calls; `local_device_load_rmsnorm_quant_per_group_naive` Lb0→Lb1, 59 calls). The removed transpose copy (`elementwise_kernel_manual_unroll<…nocast>`) dropped from **960 → 547 = −413**, exactly `354 + 59` (one `.contiguous()` per fused-quant call). Total GPU kernel launches: 11555 → 11142.

**End-to-end (Qwen3.5-397B-A17B-FP8, TP4, IL8192/OL1024, num_prompts = concurrency × 10):**
```
