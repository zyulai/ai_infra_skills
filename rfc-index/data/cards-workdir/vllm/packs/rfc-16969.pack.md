## 正文(PRD / 提案全文)

### Motivation.


Motivated by "Accelerating LLM Serving for Multi-turn Dialogues with Efficient Resource Management"， the first-come-first-served (FCFS) scheduling policy often leads to head-of-line blocking issues, causing GPU memory resources to be underutilized, especially as prompt lengths increase due to multi-turn interactions. Moreover, I propose  a sjf-based scheduling policy.



### Proposed Change.

**Design**
 
At each scheduling instance, select as many runnable requests as possible from the request queue (i.e., those that the current GPU memory can accommodate), rather than just choosing a single "next runnable request."
In doing so, aim to fill up the idle memory space of the GPU as much as possible, thereby increasing batch size and throughput.

**Implementation Details**

![Image](https://github.com/user-attachments/assets/4980bc35-fa01-45d5-9b2f-72f5b5b6f844)

- Request Sorting: First, sort the requests in the request queue by their required memory size (from smallest to largest). This prioritizes smaller requests that occupy less memory, making better use of fragmented memory.

- Greedy Selection: Starting from the head of the queue, sequentially select requests until the cumulative required memory approaches or reaches the available memory limit of the GPU.

- Dynamic Adjustment: During the scheduling process, continuously update the GPU memory status and reassess which requests in the queue can be added to the current batch based on the remaining memory.

**Preventing Starvation Issues**

To ensure long requests do not get stuck in starvation because they are always skipped, it is still necessary to introduce a priority promotion mechanism. For example:

- If a request has been waiting in the queue for more than a certain threshold, its priority should be increased.

- In some cases, forcibly include long requests in the batch, even if it means preempting part of the memory allocated to short requests.
