## 正文(PR 描述)

## Purpose

Fixes #52907.

A cross-node TP group on pre-Blackwell GPUs can enter
`torch.distributed._symmetric_memory.rendezvous()` during `CustomAllreduce`
construction even though the group cannot use MNNVL. The workers then block
before model-parallel initialization completes.

## Root cause

PR #50000 removed the previous blanket multi-node CustomAllreduce disable and
allowed supported world sizes, including TP=16, to attempt the MNNVL path. The
existing fallback happens only after the symmetric-memory rendezvous. On a
cross-node pre-Blackwell group, that rendezvous itself can block, so the
fallback is never reached.

## Change

Before allocating CustomAllreduce buffers or entering the MNNVL rendezvous:

- require a Blackwell-class CUDA device and PyTorch local multicast support;
- aggregate the local capability bit across the CPU process group with `MIN`,
  so every rank takes the same branch;
- return early and use the existing NCCL fallback when any rank is incapable.

Same-node CustomAllreduce behavior is unchanged. Multicast-capable Blackwell
process groups continue into the existing rendezvous, which remains the final
check that the group actually spans an MNNVL domain.

## Why this is not duplicate work

A live search for open PRs referencing #52907 and for the relevant cross-node
MNNVL / symmetric-memory rendezvous terms found no implementation of this fix.
Nearby work addresses different mechanisms:

- #48075 probes FlashInfer fused all-reduce on single-node bridged NVLink
  topologies;
- #53000 fixes Blackwell MNNVL Lamport mailbox publication and stage cleanup;
- #52778 reports a later cross-node GB200 CUDA-IPC failure after MNNVL
  initialization succeeds.

This PR is limited to preventing unsupported cross-node groups from entering
the `CustomAllreduce` MNNVL rendezvous in the first place.

## Validation

### Original failing topology: independent external A/B

The original reporter validated the production hunk on the exact deployment
class from #52907:

- DeepSeek-R1;
- TP=16 across two DGX H100 nodes;
- the same `vllm/vllm-openai:nightly` image digest in both arms;
- the same vLLM version in both arms:
  `0.26.1rc1.dev1133+gf94666b60`.

Results:

| Arm | Result |
|---|---|
| Unpatched control | Reproduced the exact 30-minute `Application timeout caused pair closure` failure |
| Same nightly with this PR's production hunk | Completed server initialization and all benchmark profiles successfully |

This is a clean matched A/B confirmation that the group-unanimity gate fixes
the reported H100 failure. The external run applied the production hunk to a
newer nightly rather than checking out this PR's exact commit, so it validates
the runtime change and its forward applicability; the test diff and branch
metadata remain covered separately below.

### Independent mechanism validation

`ib0`, a two-layer local Llama config, and `--load-format dummy`:
