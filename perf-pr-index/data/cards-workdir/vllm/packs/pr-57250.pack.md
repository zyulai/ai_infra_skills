## Purpose

DiffusionGemma (and likely other models in vLLM) contains all of the necessary components to build a Jev-like model that provides structured answers with bounded choices. 

By fixing canvas positions in the given structured output format, you can ask the model to provide a token and logprobs (from which a client derives entropy) that can be used to determine the models most likely answer and its confidence in that answer. If entropy does not pass a given threshold, you can perform additional sampling to determine agreement between runs and therefore the actual confidence of the model's answer.

This PR contains a prototype example server for serving the `/v1/systemone` endpoint. It does not implement a standard endpoint in vLLM. 

The model is sufficiently powerful to work with _any_ structured output that follows one limitation: the token choices _must_ be a single token, so that the canvas itself does not shift. The requesting client can always translate multi-token options into single token options, however (ie: "moderation_spam" -> "A"). The choices are always laid out in a system prompt and the model correctly diffuses single-token-slot answers (or makes a guess and flags it with uncertainty).

Why do we require the token IDs in the request? Currently we provide the token slot positions that are unfixed for the model to choose and this allows the two to be matched more accurately. A followup PR will likely add a template syntax. 

The model, using this framework, can answer yes/no ("noul" in Jev parlance), scale, or multiple choice questions, and provides its certainty and error bars with the answer.

The only missing pieces for this to work in vLLM today are in this PR:

 - A way to pre-seed the canvas with the fixed tokens
 - A way to send read-only requests that emit the argmax canvas on the converging step and skip the commit forward (logprobs come from that step at temperature 1)
 - A way to limit the number of steps run (we only want the first step)
 - A bugfix for two parallel DiffusionGemma generations that stomp on each other in lockstep: two concurrent requests with logprobs on where one converges in the same step another commits loses its stash and the request fails with HTTP 500 "list index out of range".

This PR currently contains the machinery to make this model work and a sample interposer server is included to demonstrate end-to-end functionality that is sufficient to serve traffic at reasonable scale.

   | field | type | validation | effect |
   |---|---|---|---|
   | `diffusion_seed_canvas` | `list[int]`, exactly the request's canvas width | ids in `[0, vocab)`, length checked against `diffusion_canvas_length`, else the served `--diffusion-config` | replaces the random canvas after prefill |
   | `diffusion_max_steps` | `int >= 1` | clamped to `max_denoising_steps` | denoise steps before the canvas is emitted |
   | `diffusion_pinned` | `list[int]` of canvas positions | needs a `diffusion_seed_canvas`; positions must lie inside the request's canvas | held at their seed value on every denoise step, and their self-conditioning soft embed is zeroed, so a read past one step denoises the canvas the request seeded instead of one the model rewrote |
   | `diffusion_read_only` | `bool` (the OpenAI server delivers JSON booleans in `vllm_xargs` as 0/1, which is accepted) | caps `max_tokens` at the canvas, sets `ignore_eos` | emit on the converging step, skip the commit forward, temperature-1 logprobs |
   | `diffusion_canvas_length` | `int`, 1 to the served `canvas_length` | validated in `verify`; the seed must be this long | the request runs on a canvas this wide: the scheduler schedules this many draft tokens and the sampler tiles the read at this width, so a short schema on a wide server costs the same as on a server of its own width |
   | `logprob_token_ids` (a request field, not in `vllm_xargs`) | `list[int]`, up to 128 | existing vLLM validation | exact logprobs for those ids at every canvas position. The sampler now honors it on the converging step, so a read asks for its label ids instead of hoping they rank in the top-k (with 26 options only 1-8 did) |
