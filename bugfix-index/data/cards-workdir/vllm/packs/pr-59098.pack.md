## 正文(PR 描述)

## Purpose
A batch can contain a fresh prompt before a request that has cached KV. If the splitter assumes that the first fresh prompt starts the trailing prefill region, it can put the later continuation on a path that ignores its history. The fix changes how the regions are chosen, adds a guard for an all-decode batch whose `max_query_len` is overstated, and sizes the cached-context chunks correctly.
 This PR takes the order-independent split from #63542 (credit @qli88) and adds an all-decode guard for an over-stated `max_query_len`.

## Claims

- Phi-4-mini `niah_single_2` at 30k, 16 concurrent requests: **0.626 → 1.000** on 1× MI300X. Main misses 187 of 500 needles. The earlier three-model run on the same recipe was Phi 0.62 → 1.00, Mistral-7B 0.74 → 1.00, Qwen3-8B 0.99 → 1.00.
- Qwen3-8B, needle planted at token 2048, 64 prompts, concurrency 16: 40k goes from 59/64 to 64/64. 32k stays 64/64 on both arms.
- Short context is unaffected. Qwen3-8B on the same GPU stays within 0.2% at 8k/1k (concurrency 8 and 32) and at 32k/1k. Total tok/s, TTFT, and TPOT all hold.
- The Phi 30k bench is slower on this PR (29,911 → 28,034 tok/s, TTFT 7.27 s → 8.00 s) because main skips the KV. On that bench main leaves 233,430 context tokens unread (28.9% of the KV, 17.1% of prefill attention). This PR reads all 808,402. 574,972 + 233,430 = 808,402.
- The real-backend unordered-batch test fails on `main` and passes here. The all-decode guard is the case #63542 still fails.

## Details

A batch can contain a fresh prompt before a request that has cached KV. If the splitter assumes
that the first fresh prompt starts the trailing prefill region, it can put the later continuation
on a path that ignores its history. This PR changes how the regions are chosen, sizes the
cached-context chunks correctly, and guards one edge case in the decode count.

### Fix 1 — Find the Last Request with Context

The main cause of the lost-context bug is that MRV2 can place a fresh Prefill request before an
Extend request, while the attention splitter assumes all Extend requests come before Prefill
requests.

As a result, the splitter treats every request after that Prefill as a Prefill too, so the Extend
requests among them are attended without their cached KV history.

To fix this, we find the **last request with cached context** and place the Prefill boundary
immediately after it. Any fresh Prefill requests before this boundary are handled by the Extend
path, which can safely process requests with zero cached context.


### Fix 2 — share the cached-context budget correctly

Because Fix A can place context-free rows in the extend region, the workspace divisor must count
only the rows that actually read context:

```python
num_extends_with_context = max(int((computed_kv_lens > 0).sum()), 1)
max_context_chunk = _CP_TOKENS_PER_ITER_ROCM // num_extends_with_context
```

Dividing by `num_extends` reserves workspace for rows that read nothing, which shrinks everyone
else's chunk and raises `num_chunks = cdiv(max_context, max_context_chunk)`. This is a chunking
change only — it does not alter which rows read their context.

### Fix 3 — Handle All-Decode Batches

There is another edge case where all requests in the attention batch are Decode-like, but
`max_query_len` is larger than the actual query lengths, which can happen during adaptive
speculative verification.

In this case, the original code skips the all-Decode fast path and tries to find the first
non-Decode request. Since no such request exists, `argmax()` returns `0`, incorrectly reporting
zero Decode requests.

**Fix:** We check whether all requests are Decode-like and directly return:

```python
return num_reqs, 0, 0, num_tokens, 0, 0
```

Where:
- `num_reqs`: every request in the batch, all of them Decodes.
- `num_tokens`: every token in the batch, all of them Decode tokens.
- The remaining zeros indicate that there are no Extend or Prefill requests or tokens.

This avoids searching for a non-existent boundary and ensures the entire batch is correctly
processed as Decode.
