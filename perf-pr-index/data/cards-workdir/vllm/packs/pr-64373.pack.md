## Overview

GLM-5.3-Flash builds its attention projections (KDA, MLA, DSA indexer) with `quant_config=None`, so online quantization requested with `--quantization-config '{"targets": ...}'` silently skips them. This PR passes the model's quant config to these modules, so they follow the checkpoint's own skip list and the online targets, as other models do. The one special case is the MLA projections of FP8 / Quark checkpoints, which the model already dequantizes to BF16 at load. Related: #59833, #55741 (see Details).

## Claims

- **Online quantization now reaches the BF16 attention projections** when `--quantization-config` names them. On `nvidia/GLM-5.3-Flash-NVFP4`, the targets under Recommended configuration now quantize 196 layers (attention + shared experts) instead of 84 (shared experts only).
- **No change without `--quantization-config`:** on GB300, the default greedy outputs of the NVFP4 checkpoint (with and without MTP) and of the Z.ai FP8 checkpoint match `main` token for token.
- **No GLM-specific quant config:** the KDA and MLA modules get the model's `quant_config`. The Z.ai FP8 checkpoint names its BF16 layers `model.layers.N.self_attn.*` in `modules_to_not_convert`, so the model's `hf_to_vllm_mapper` maps that prefix, and `packed_modules_mapping` lists the shards of the fused KDA `in_proj_qkvbfg_a`. Shared quantization code is unchanged, and there is no new flag.
- **Recommended, behavior-preserving configurations** (MXFP8 on the 128 non-KDA projections for aggregated serving; MXFP8 on all 196 on prefill instances only for disaggregated serving) keep accuracy and output length unchanged on 7 benchmarks, and give +2% output throughput (aggregated) and up to +12% (disaggregated, prefill-bound) on GB300.
- MXFP8 on all 196 projections in aggregated serving is faster still (+8% on GB300), but measurably shortens reasoning; this PR describes it as an opt-in with that disclosure.

## Details

### Why the projections were unreachable

GLM-5.3-Flash loads its attention projections as BF16 in every checkpoint:

- KDA `in_proj_qkvbfg_a`, `f_b_proj`, `g_b_proj`, `o_proj`;
- MLA `fused_qkv_a_proj`, `q_b_proj`, `o_proj`;
- DSA indexer `wq_b`.

The KDA and indexer projections are BF16 in every official checkpoint. The MLA projections are BF16 in the NVFP4 checkpoint and block-FP8 in the Z.ai FP8 checkpoint, which the model dequantizes to BF16 at load (`_try_load_fp8_attn_proj`). The model therefore built all of them with no quant config: MLA passed `quant_config=None`, and KDA cleared `vllm_config.quant_config` around its constructor. Passing the quant config through was not enough by itself: the Z.ai FP8 config lists the BF16 layers in `modules_to_not_convert` as `model.layers.N.*`, while the weights are `model.language_model.layers.N.*`, so none of the 1,509 entries matched vLLM's module names. With `--quantization modelopt_fp4 --quantization-config '{"targets": {...}}'`, composition with the checkpoint method worked for the shared-expert linears (84 layers) but silently skipped the 112 attention projections. No warning was printed.

### What changes

- **KDA and MLA get the model's `quant_config`**, so each projection follows the checkpoint's skip list (`exclude_modules`, `modules_to_not_convert`), and online targets compose with it through the existing `resolve_quant_method` path. Layers that match no online target keep the checkpoint's decision.
- **One special case:** with an FP8-serialized `Fp8Config` or a `QuarkConfig`, MLA keeps `quant_config=None`, because those checkpoints store the MLA projections in FP8 and the model dequantizes them to BF16 at load. As a result, online quantization does not reach the MLA projections of these checkpoints; it still reaches their KDA projections.
- **Name mapping:** the model's `hf_to_vllm_mapper` adds `model.layers.N.self_attn.` → `language_model.model.layers.N.self_attn.` to the GLM-4V prefixes, so the FP8 skip list matches. Only `self_attn` names are mapped: the NVFP4 checkpoint excludes the MTP layer as `model.layers.45*`, and the MTP draft shares the target's quant config, so that entry must keep its name. `packed_modules_mapping` lists the six shards of `in_proj_qkvbfg_a`.
- **The GB300 specialized decode** (#63102, `decode_backend=latency_specialized`) reads the KDA `f_b_proj` (and, with its skinny GEMMs, `in_proj_qkvbfg_a` and `o_proj`) directly as BF16. Its `KdaStage` now checks these weights and fails at startup, naming the projections to exclude from `--quantization-config`, instead of running on quantized weights.

Other effects:

- `kv_b_proj` gets the same config as the other MLA projections. It is excluded in the NVFP4 checkpoint and BF16 under the FP8 special case, and the recommended regexes do not match it. Online quantization of `kv_b_proj` (absorbed into the W_UK / W_UV bmm weights after loading) was not tested.
- The MLA attention module (`self_attn.attn`) now receives the checkpoint config. With the NVFP4 checkpoint it gets `ModelOptKVCacheMethod`; the checkpoint has no attention scale tensors, so the effective scales stay 1.0 with an `fp8_e4m3` KV cache, as on `main` (checked on GB300).
- `--quantization mxfp8` (or another online shorthand) with a BF16 checkpoint now quantizes the attention projections too, like every other linear layer. Use `targets` to choose layers.
- A third-party checkpoint whose skip list omits a BF16 attention projection would now try to load it with the checkpoint method. The official NVFP4 and FP8 checkpoints were checked layer by layer against their real configs.

### Recommended configuration

All measurements use NVIDIA's NVFP4 checkpoint, [`nvidia/GLM-5.3-Flash-NVFP4`](https://huggingface.co/nvidia/GLM-5.3-Flash-NVFP4) (revision `da920bb`). Its routed experts and dense MLPs are NVFP4. The 196 projections studied are BF16:

| group | projections | layers |
|---|---|---|
| KDA (34 linear-attention layers) | `in_proj_qkvbfg_a`, `o_proj` | 68 |
| MLA / DSA (11 layers: 3, 7, ..., 43) | `fused_qkv_a_proj`, `q_b_proj`, `o_proj`, `indexer.wq_b` | 44 |
| shared expert (42 MoE layers) | `gate_up_proj`, `down_proj` | 84 |

We tested MXFP8 (E4M3 values, one E8M0 scale per 32 elements, for weights and dynamic activations). Accuracy holds in every configuration. However, MXFP8 on the **68 KDA in/out projections at decode** measurably changes reasoning behavior: traces get 20-30% shorter on AIME/GPQA, with fewer hesitation and self-correction tokens, and accuracy on hard long-output problems trends lower (not significant). The other 128 projections leave behavior unchanged.

| deployment | recommended config | behavior vs BF16 |
|---|---|---|
| **aggregated (or any decode-serving instance)** | **MXFP8 on the 128 non-KDA projections** (MLA, indexer `wq_b`, shared expert); KDA in/out stay BF16 | unchanged: accuracy and output length match BF16 on 7 benchmarks |
| **disaggregated** | **MXFP8 on all 196 projections on the prefill instances only**; decode instances unchanged | decode, which produces nearly all of the output tokens, runs exactly as today |
| opt-in, aggregated | MXFP8 on all 196 projections | **changed**: shorter reasoning, and a possible 1-2 point cost on hard long-output problems |

- **Where the throughput comes from:** the prefill-heavy, large-M GEMMs. The largest projection is KDA `in_proj_qkvbfg_a` (4096 → 24,896), so excluding the KDA projections keeps only part of the gain in aggregated serving (+2% instead of +8% on GB300).
- **Why prefill-only is behavior-preserving:** the behavior change comes from MXFP8 numerics at decode, which pick each next token. With MXFP8 only on prefill instances, prefill computes the KV cache and KDA state in MXFP8, while every generated token after the first comes from BF16 decode. An aggregated variant with exactly that split (MXFP8 for GEMMs of ≥ 2048 tokens, BF16 weights kept for decode; not part of this PR, it needs a second weight copy) showed no length change and no accuracy change: macro +0.09 pt [-0.43, +0.61] over 8 benchmarks. The disaggregated deployment itself was not accuracy-tested.
- **Use the cuBLASLt MXFP8 kernel** (`--kernel-config '{"linear_backend_per_quant": {"mxfp8": "torch"}}'`). On SM10x, the automatic choice (FlashInfer CuTe-DSL) was markedly slower for these shapes at large M. The kernel priority is a separate follow-up.

Commands for the NVFP4 checkpoint. Each regex covers layers 0-44, so the MTP layer (45) is excluded; the K=128 KDA gate projections, `kv_b_proj`, the indexer `wk_weights_proj` and the dense MLPs never match.

- **Do not use a per-tensor activation scale on these layers at decode.** One scale shared by every row of a decode batch couples all requests. Upstream's online `fp8_per_tensor` uses per-token activation scales on CUTLASS-capable GPUs and does not have this coupling; we did not evaluate it.
- **Per-channel FP8 (`fp8_per_channel`) on all 196** mostly avoids the behavior change but also keeps only a small part of the throughput gain, so it offers nothing over the non-KDA MXFP8 config.

### Not a duplicate

Searched open PRs: "glm5next quantization", "glm online quantization", "online quantization attention", "GLM-5.3 mxfp8", "quant_config=None MLA", "glm5next mxfp8", "GLM-5.3 quantization config", "kda online quantization", "glm5next quant_config", "modules_to_not_convert glm".

- **#59833** (GLM-5.x: load ModelOpt NVFP4 MLA projections into BF16 `fused_qkv_a_proj`) changes how *checkpoint-quantized* MLA weights are loaded into BF16 targets. It does not touch the `quant_config=None` wiring, and it is complementary: such weights could then be online-quantized.
- **#55741** (MLA bmm abstraction and `kv_b_proj` online quantization) makes a generic MLA `kv_b_proj` quantizable through the bmm path. This PR does not change how GLM's `kv_b_proj` is absorbed, so it does not conflict, and GLM could adopt #55741 later.
- **#61457** (per-layer fused shared expert selection, merged; this branch is rebased on it) and **#61662** / **#64121** / **#64245** (ROCm GLM-5.3-Flash MonoKernel decode) edit `glm5next/common/model.py` in unrelated places; the open ones merge cleanly with this branch.
- **#49313** (Quark: online requant of unquantized layers through a `quantization_config` overlay) is a Quark-specific generic mechanism and does not reach GLM's `quant_config=None` projections.

### Limitations

- Hardware-neutral, but validated on NVIDIA only; ROCm uses the same code path (MXFP8 via `RocmDotScaledMxfp8LinearKernel`) and is untested.
- CI covers the config wiring (unit tests); no CI job serves GLM-5.3-Flash (191 GB checkpoint). End-to-end validation was done outside CI as listed above.
- The throughput and accuracy runs used an earlier revision of this PR (a GLM-specific online-only config for these projections). On the NVFP4 checkpoint it quantized the same layers with the same method, which the `Quantizing N layers` counts above confirm for this revision.
- The disaggregated prefill-only configuration was measured for throughput, not for accuracy (see the aggregated equivalent above).
