## 正文(PRD / 提案全文)

## Motivation

`VLLM_BATCH_INVARIANT=1` works on ROCm since #52231, but Kimi-K3.1 (hybrid KDA linear attention + DSA sparse MLA, MXFP4 routed experts, LoRA) is not batch-invariant on MI355X with it alone. In RL, this mode is what lets the rollout's token log-probs match the trainer's exactly ("true on-policy"). On NVIDIA GB300 this already works for Kimi-K3.1 via a set of overlays (Inferact/zero-mismatch-rl); this issue tracks the ROCm counterparts so they can land in vLLM, in small PRs.

Tracking parent: #27433 ("AMD support").

## What breaks on ROCm today (Kimi-K3.1, TP8 + EP8, MI355X)

Found by bisection with a full-model batch-size sweep (same prompt alone vs. inside batches of 1..128):

| Component | Source of batch variance |
|---|---|
| KDA (linear attention) | decode and prefill take different kernels; in mixed batches decode rows go through the prefill path; FLA kernels autotune per shape; KDA state slots can be written twice under CUDA-graph replay after wake |
| DSA indexer | decode logits are computed differently from prefill; top-k tie order |
| Sparse MLA | FlyDSL path only above a token threshold; split-K count follows the number of query rows |
| Routed experts (MXFP4) | AITER CK / FlyDSL MoE choose tiles and splits by token count |
| AttnRes (block residual mix) | first diverging tensor in the full-model probe |
| TP all-reduce | custom all-reduce changes algorithm with message size |
| EP combine | rank partials summed in arrival order |
| Dense LoRA (punica expand) | two BF16 roundings (`bf16(bf16(delta) + base)`) |
| Dense BI matmul at decode M | correct, but on ROCm uses 128x128x64 at every M (no gfx950 entries in the tuned table), so decode is slow |

## Proposed changes (one PR each, all gated on `VLLM_BATCH_INVARIANT`; default path unchanged)

- [ ] **BI matmul: gfx950 tile table** for `batch_invariant` (small-M buckets; BLOCK_K kept at 64 so the K-reduction order and the bits are unchanged; every entry bitwise-equal to the default config at every tested M)
- [ ] **LoRA: single-rounding expand epilogue** under BI (`bf16(fp32(delta) + fp32(base))`); platform-independent
- [ ] **DSA / indexer BI for Kimi-K3.1 on ROCm**: decode logits computed like prefill (row-bounded kernels), deterministic top-k, sparse MLA with one KV split, no FlyDSL dispatch in BI mode, allow the AITER FA MLA prefill in BI mode (related: #65278)
- [ ] **AttnRes BI** (`models/kimi_k3/amd/ops/attn_res.py`)
- [ ] **KDA BI**: pinned FLA `chunk_kda` configs; a decode path that is bitwise equal to the chunk (prefill) form so a token's result does not depend on batch composition; CUDA-graph-capturable decode; KDA state-slot write dedup (last write wins) (related: #42960, #48613 for GDN)
- [ ] **BI two-stage custom all-reduce** for ROCm, bitwise equal to the 1-stage reduction
- [ ] **BI MXFP4 routed-expert MoE**: kernel proposed to AITER as an opt-in deterministic mode (fixed K order, no shape-dependent split), selected by vLLM under BI; includes expert LoRA
- [ ] **Ordered EP combine** (rank-order mode; MoRI side + vLLM flag)
- [ ] **Tests**: batch-size sweep + full-model gate in `tests/v1/determinism` for a ROCm Kimi-K3.1 config

## Evidence so far (out of tree, 2 nodes x 8 MI355X, vLLM rollout + Megatron trainer, LoRA r32 on all modules incl. experts)

- GRPO with `rollout_probs_diff_max == 0` at every step: 30-step run, 3,840 / 3,840 samples, 11,893,214 tokens, max abs diff 0 (checked per token, not only the batch max).
- Cost of BI at NVIDIA's published Kimi-K3.1 RL shape (256 samples/step, 2048 prompt / 6144 response, DAPO-Math-17k), same nodes, crossed design, 3 steps per arm: rollout **+1.0%**, whole RL step **-2.9%** vs. BI off.
- Kernel-level gates: each change above is bitwise-checked against its reference across batch sizes 1..128 before use.

The code is currently out-of-tree plugins + patches (verl draft PR verl-project/verl#8574). We'd like feedback on the split above, especially where maintainers prefer the MoE kernel to live (AITER vs. vLLM) and how KDA BI should be structured relative to the GDN work.
