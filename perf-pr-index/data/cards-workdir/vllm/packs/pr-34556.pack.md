## Introduction

[Humming](https://github.com/inclusionAI/humming/) is a highly flexible JIT quantization kernel library.

It supports inference for the vast majority of quantization types and offers performance superior to the Marlin kernel.

- **Supported Data Types:** W{1-8}A{16/8/4}
- **Currently Compatible Weight Types:** GPTQ / AWQ / FP8 / MXFP4 / NVFP4 / BITNET
- **Unsupported Types (No support planned):** GPTQ with `desc_act=True` / HQQ
- **Fully Supported GPU Architectures (Best Performance):** Turing / Ampere / Ada Lovelace / Hopper
- **Architectures Not Yet Fully Supported:** 
    - Blackwell Datacenter (SM100): UMMA is not yet supported.
    - Blackwell Consumer (SM120): Performance is suboptimal in some cases as blockscale is not yet supported.


## Usage

Humming is currently an experimental feature. You must manually add `--quantization humming` to use this kernel. Beyond basic functionality, Humming currently uses three environment variables to customize advanced behavior.


### `VLLM_HUMMING_ONLINE_QUANT_CONFIG`

This environment variable controls **online quantization** behavior. If a non-quantized model is loaded, it can be quantized into a specific type during model loading to save VRAM and accelerate inference at small batch sizes (BS).

In addition to common FP8 online quantization, Humming supports online quantization for various data types, including INT1-INT8 and FP3-FP8. However, because online quantization is uncalibrated, lower quantization bits will significantly impact model accuracy. Therefore, it is currently recommended to use data types of **6-bit or higher** for online quantization.

- **For FP16/BF16 activations:** Recommended types include float8e2m5 / float8e3m4 / float8e4m3 / float7e2m4 / float7e3m3 / float6e2m3.
- **For FP8 activations:** Recommended types include float8e4m3 / float7e3m3 / float6e2m3.
- **For INT8 activations:** Recommended types include INT8 / INT7 / INT6.

You can also apply different online quantization types to different layers (e.g., using 8-bit quantization for Attention layers and 6-bit for MoE layers).

This variable should be set to a JSON string or a JSON file path. The JSON format is as follows (note: remove comments before use):

```jsonc
{
    // force_requant: By default, we ignore the online quant config if the model is a quantized model.
    // If force_requant is set to true, we would dequant the weight to float32 and
    // then quant it with the online quant config.
    "force_requant": false,
    // dtype: Quantization datatype, e.g., int8 / float8e4m3 / float7e2m4, etc.
    "dtype": "int8",
    // group_size: Use 0 for channelwise; for values > 0, use groupwise (must be a power of 2).
    "group_size": 0,
    // scale_dtype: Supports float8e4m3 / float8e8m0. Defaults to fp16/bf16 if omitted.
    "scale_dtype": "float8e4m3",
    // has_zero_point: Whether to use dynamic zero point (similar to AWQ); applies only to INT types.
    "has_zero_point": false,
    // dynamic: To override config for specific layers.
    "dynamic": {
        // Prefixed with "-:": Corresponding layers will skip online quantization.
        "-:regex1": {},
        // Prefixed with "+:": Corresponding layers use the merged configuration.
        "+:regex2": {
            "dtype": "int6"
        }
    }
}
```



### `VLLM_HUMMING_INPUT_QUANT_CONFIG`


This environment variable controls input quantization. By default, Humming uses FP16/BF16 precision for inference. However, you can use FP8 / FP4 / INT8 / INT4 precision for specific layers (note: FP4 and INT4 precisions have not been strictly tested and will significantly impact the accuracy of uncalibrated models).

This variable should be set to a JSON string or a JSON file path. The JSON format is as follows (note: remove comments before use):


```jsonc
{
    // dtype: Activation datatype, e.g., int8 / float8e4m3 / int8, etc.
    "dtype": "int8",
    // Use 0 for channelwise/tokenwise; for values > 0, use groupwise (must be power of 2). 0 is recommended.
    "group_size": 0,
    // dynamic: To override config for specific layers.
    "dynamic": {
        // Prefixed with "-:": Corresponding layers retain FP16/BF16 activations.
        "-:regex1": {},
        // Prefixed with "+:": Corresponding layers use the merged configuration.
        "+:regex2": {
            "dtype": "float8e4m3"
        }
    }
}
```


### `VLLM_HUMMING_USE_F16_ACCUM`

This environment variable controls MMA (Matrix Multiply-Accumulate) accumulator precision. Set to 1 or 0.

For certain devices (Turing / Ada Lovelace), FP32 accumulator MMA achieves only half the TFLOPS of FP16 accumulator MMA. Enabling this feature can accelerate inference to some extent on these architectures.

Note: This feature only supports fp16 / fp8e4m3 activation types; BF16 is not supported. Additionally, using FP16 accumulation may increase the risk of overflow or underflow; you should monitor the model's performance/accuracy.

+def moe_fused_mul_sum_kernel(
+    inputs_ptr,
+    topk_weights_ptr,
+    outputs_ptr,
+    top_ids_ptr,
+    expert_map_ptr,
+    num_tokens,
+    stride_m,
+    has_expert_map: tl.constexpr,

+    BLOCK_K: tl.constexpr,
+):

+    pid_m = tl.program_id(1)
+

+    offs_k = pid_k * BLOCK_K + tl.arange(0, BLOCK_K)
+

+    k_mask = offs_k < size
+    mask = m_mask[:, None] & k_mask[None, :]
+
+    a_base = inputs_ptr + (offs_m * stride_m)[:, None] + offs_k[None, :]
+    b_base = topk_weights_ptr + offs_m * top_k
+

+

+            expert_mask = tl.load(expert_map_ptr + id_val) >= 0
+            a_vec = tl.load(
+                a_base + n * size,
+                mask=mask & expert_mask[:, None],
+                other=0.0,
+            ).to(tl.float32)
+        else:
+            a_vec = tl.load(
+                a_base + n * size,
+                mask=mask,
+                other=0.0,
+            ).to(tl.float32)

+def _heuristic_config(
