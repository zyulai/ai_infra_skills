## Purpose

`VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1` is silently ignored for GLM-5.3-Flash (`glm5_next`): `Glm5NextMoE` builds `FusedMoE` with `n_shared_experts=None`, so each of the 42 MoE layers still runs the shared expert as a separate MLP (two FP8 block-scale GEMMs, a clamped SiLU and a quant) and adds it to the routed output.

This PR wires the flag up the way `DeepseekV2MoE` does:

- **MoE:** when `resolve_layer_fused_shared_expert()` allows it, `Glm5NextMoE` drops the separate MLP and passes `n_shared_experts` / `fuse_shared_experts` to `FusedMoE`, so the shared expert runs as one more expert inside the AITER fused MoE (`E=289, topk=9`). The routed weights keep `routed_scaling_factor` and the shared slot gets 1.0, so the output is the same `shared + routed` sum as before.
- **Loading:** in both the target and the MTP draft model, the checkpoint's `mlp.shared_experts.*` tensors (FP8 scales included) load into expert slot `n_routed_experts`. `is_model_fused_shared_expert_compatible()` keeps fusion all-or-nothing, and more than one shared expert raises.
- **Gate:** AITER has tuned configs for the fused shape only on gfx950 at TP4 and TP8 (ROCm/aiter#5735, shipped in AITER v0.1.23, already in vLLM's ROCm image since #58867). Like DeepSeek-V4's shared-expert gate, `_fused_shared_experts_tuned()` allows fusion only there, and only without data, prefill context or expert parallelism, which change the per-rank shape. Anywhere else the flag logs a one-time warning with the reason, and the shared experts stay a separate MLP.

Nothing changes unless the flag is set on gfx950 at TP4 or TP8: it defaults to off, and `resolve_layer_fused_shared_expert()` returns False on non-ROCm platforms. gfx942 will follow in a separate PR once its rows (ROCm/aiter#5953) ship; without them the fused MoE would run untuned kernels (4289 µs vs 3033 µs for one 16K-token MoE call on MI325X).

+def _fused_shared_experts_tuned(parallel_config: ParallelConfig) -> bool:
+    """AITER has fused-MoE configs tuned for the fused shared-expert shape
+    (one more expert and one more top-k slot than the routed MoE) only on
+    gfx950, with every expert on each rank and its weights split by TP4 or
+    TP8. Data, prefill context and expert parallelism change that split, so
+    any other GPU or parallel layout would run untuned fallback kernels."""
+    from vllm.platforms.rocm import on_gfx950
+
+    reasons: list[str] = []
+    if not on_gfx950():
+        reasons.append("the GPU is not gfx950")
+    if parallel_config.tensor_parallel_size not in (4, 8):
+        reasons.append(
+            f"tensor_parallel_size is {parallel_config.tensor_parallel_size}"
+        )
+    if parallel_config.data_parallel_size != 1:
+        reasons.append(f"data_parallel_size is {parallel_config.data_parallel_size}")
+    if parallel_config.prefill_context_parallel_size != 1:
+        reasons.append(
+            "prefill_context_parallel_size is "
+            f"{parallel_config.prefill_context_parallel_size}"
+        )
+    if parallel_config.enable_expert_parallel:
+        reasons.append("expert parallelism is enabled")
+
+    if not reasons:
+        return True
+    logger.warning_once(
+        "VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS is ignored for GLM-5.3-Flash: "
+        "%s. AITER has tuned configs for its fused shared-expert MoE only on "
+        "gfx950 at TP4 and TP8, without data, prefill context or expert "
+        "parallelism. Running the shared experts as a separate MLP.",
+        "; ".join(reasons),
