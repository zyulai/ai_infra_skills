## 正文(PRD / 提案全文)

### Motivation.

CI is the foundation for helping every contributor to develop on top of vLLM and gatekeep quality and performance for each release. vLLM’s CI has been in a very worrisome state:
<img width="672" height="81" alt="Image" src="https://github.com/user-attachments/assets/2833dffe-9ba1-402a-a6a7-766e30d8ce80" />

The CI/CD system is plagued by slowness, frequent failures, and an inability to reliably detect correctness and performance regressions in critical models. This has led developers to first suspect CI flakiness rather than code issues when tests fail.

While efforts like https://github.com/vllm-project/vllm/issues/22992 are underway to refactor gold tests, deprecate V0, improve V1 test coverage, and address timeouts, flaky tests, and hardware resource acquisition, we also need to consider fundamental structural and process changes. These changes are crucial to prevent CI from reverting to a detrimental state and turn CI/CD into shared responsibilities of all contributors.

### Proposed Change.

## Principles

1. Trunk should be green >95% time.
2. Flaky tests are worse than no tests.
3. Reduce humans in the loop.
4. Optimize for effective test<>fix loop.
5. Test what is modified.

## Success Criteria
Measured in buildkite CI:

- Reliability > 90%
- Speed < 30min

# Ideal State

Testing the top 10 models across all hardware and every possible inference feature combination is virtually impossible. Our CI/CD pipeline should function as a funnel, prioritizing test types based on time budget and frequency, only scheduling more comprehensive tests once the preceding stage has passed. And only schedule more comprehensive tests when the previous stage has passed. We should not expect 100% test coverage at every stage.

|  | precommit | PR publish | PR ready | Nightly | Release  |
| :---- | :---- | :---- | :---- | :---- | :---- |
| **Time budget** | <2 min | 5-10 min | 15-30 min | 2-6 hours | 2-6 hours |
| **Frequency (x times per week)** | ~100K | ~10K | ~1K | 7 | 0.5 |
| **Issue Coverage** | 20% | 70% | 90% | 95%  | 99% |
| **Criteria** | - Lint <br> - Format | - Unit tests <br> - Component integration tests <br> - Single card model E2E correctness | - 2 multi-node E2E correctness and performance | **P0:** <br> - top 10 model E2E perf and correctness using recommended recipes (including multimodal models) <br> - on Hx00 and GB200 <br><br> **P1:** <br> - numerical stability <br> - on A100, Mi300x, TPU, etc. <br> - all serving paradigms (disagg, multi-node EP, w/ native tool call) <br> - dependency version compatibility (e.g. pytorch, flashinfer, flashattention) <br> - plugin tests <br><br> **P2:** <br> - high load stress test <br> - other inference behavior (e.g. lora) <br> - component compatibility (e.g. RL framework) |  |
| **Action** | Block PR creation | Block running full PR ready tests | Block merge | File ticket to code/test owners | Pick a version from nightly candidates |

# Note in Scope

* Benchmarking. We’d like to enhance continuous and adhoc benchmarking and profiling support but we will not cover that in this proposal.

# Issues & Proposal

## TL;DR

- [ ] Collocate test folders and code folders, automate test selection for unit tests, integration tests and E2E tests 
- [ ] Enable flaky test quarantine
- [ ] Code owners are test owners who are expected to triage test failures
- [ ] Store E2E test run commands in Justfile to allow easy repro 

## Issue 1: Test Selection & Folder Structure

**Problem statement**: PR merging time runs many irrelevant integration tests but does not run relevant unit tests.  
**Root cause**: Tests are opted in folder by folder or file by file in [.buildkite/test-pipeline.yaml](https://github.com/vllm-project/vllm/blob/main/.buildkite/test-pipeline.yaml).  
**Solution**: Refactor vLLM’s folder structure to collocate unit tests and code, which enables easier unit test selection (most existing tests are considered integration tests not unit tests).   
**Solution details**:   
The existing vLLM folder keeps implementation code and tests in separate folders. While this is convenient for small projects but does not work well for big project requiring complex CI setup because there’s no 1:1 mapping around code and tests and the structure is harder to automate.

We propose to 

* Create `tests/` within each individual folder  
* For perf sensitive components, create a `microbench/` folder to continuously run fast (\<1 min) benchmarks (such candidates exist in [benchmarks/](https://github.com/vllm-project/vllm/tree/main/benchmarks))  
* Create an `integration_tests/` folder for tests that require multiple components and may require full model download (most existing tests fall into this category).  
* Create a `e2e_tests/` folder to cover E2E engine behavior, including model eval (e.g. gsm8k/mmlu\_pro for non-reasoning, aime25 for reasoning models, mmmu/chartqa for multimodal models). Exact tests are up for discussion.  
* Delete the big `tests/` folder

Current structure:
```
vllm/
    vllm/
    tests/
    ...
```

Proposed structure: 
```
vllm/
    vllm/
        core/
            tests/
            microbench/
            *.py
            ...
        attention/
            tests/
            microbench/
            *.py
            ...
        distributed/
            tests/
            microbench/
            kv_transfer/
                tests/
                *.py
            *.py
            ...
        ...
    integration_tests/
        engine_core/
        models/
        entrypoints/
        features/
        codebase/
        kernels/
        ...
    e2e_tests/
        eval/
        bench_serve/
        numerics/
        plugins/
        stress_test/
        compatibility/
        ...
    ...
```

Pros: 

* Better test discoverability, encouraging writing tests
* Collocate test and code ownership  
* Easier to refactor folders  
* Tests are usage examples

Cons:

* Clutter code director
* Harder to exclude test folders from build

When do we run all these tests?

* `tests/`, `microbench/`: Tests are selected based on folder structure  
  * Current folder \+ 2 parent folders. For example, when changing code under `distributed/kv_transfer/`, both tests under tests `distributed/` and `kv_transfer/` will be selected.   
  * Set short default timeouts (\~5 mins). See [issue 2: test life cycle management](#issue-2-test-life-cycle-management) for more details  
  * Keep most tests to be CPU by default except for selected folders such as kernels, distributed and model runner.   
  * We can improve target determination based on heuristics and import relations  
* `integration_tests/`:   
  * Most existing entrypoint tests that requires creating a new `RemoteOpenAIServer` or download HF models  
  * Unit tests connect multiple components. Follow governance document https://github.com/vllm-project/vllm/pull/24801 for the initial breakdown.   
* `e2e_tests/`:   
  * Triggering criteria is defined in [ideal state](#ideal-state).  
  * Only PRs touching selected folders (e.g. distributed, kernels, core) will trigger CIs on multiple hardware.

## Issue 2: Test Life cycle management

**Problem statement**: Newly added tests with unknown quality immediately start blocking PR merging without the tests themselves being validated.  
**Root cause**: Test state and its associated action (see below) should be transitioned by system not humans:

<img width="955" height="451" alt="Image" src="https://github.com/user-attachments/assets/837e9ec2-88a6-4f14-9643-da56a5492b18" />

**Solution**: build test state management in CI infra  
**Solution details**: 

1. New tests won’t automatically block PR merging. It’s marked as unknown first. The test will run on PRs but will not trigger any actions.  
2. The tests will be marked as good once it’s consistently passing. We can design criteria for passing. Candidates:  
   1. 20 consecutive runs   
   2. buildkite schedules a stress run the test  
3. Once the test is being identified as flaky – which can be detected criteria like:  
   1. Consistent failure on trunk  
   2. Periodically shadow runs  
   3. User report  
4. Once the test is marked as bad, the test will be skipped in CI and a ticket will be filed to test owners. 

These automation can be built on top of test engine and bktec for more complex orchestration: [test-state-and-quarantine](https://buildkite.com/docs/test-engine/test-suites/test-state-and-quarantine)

## Issue 3: Flaky Test Triage

**Problem statement**: We rely on a very limited number of maintainers to manually stare at a dashboard and listen to slack complaints, then disable or fix flaky tests. The process is not automated and the ownership is not distributed.  
**Root cause**: We don’t rely much on automation.  
**Solution**: Test failures should subscribe code owners automatically. Configuration is available: [test-ownership](https://buildkite.com/docs/test-engine/test-suites/test-ownership)  
**Solution details**:

* If an existing test is failing, [CODEOWNERS](https://github.com/NickLucche/vllm/blob/d8346cd95d76d63f55fd3a9e4dea468b453ec0a2/.github/CODEOWNERS) should be paged.  
* If a new test is failing, author who added the tests should be paged.

## Issue 4: Actionable Test Failure

**Problem statement**: When a test fails, PR authors do not have access to the command or the hardware to reproduce the errors on their PRs, such that they cannot take actions to unblock themselves.  
**Root cause**: 

1. Hardware specific tests got triggered on hardware agnostic code. When it fails, it’s almost always noise.  
2. Users cannot find the exact code to reproduce locally.

**Solution**: 

1. Don’t run them  
2. Leverage Makefile/Justfile to manage actual execution command for more complex integration tests

**Solution details**: Use Justfile as source of truth for storing commands, then test\_pipeline.yamly may look like:
```
steps:
  - label: DeepSeekV3 correctness
    command: just ds-v3-eval
    ...
  - label: DeepSeekV3 single-host performance
    command: just ds-v3-single-perf
    ...
  - label: DeepSeekV3 PD+DPEP performance
    command: just ds-v3-perf-pddpep
    ...
```
