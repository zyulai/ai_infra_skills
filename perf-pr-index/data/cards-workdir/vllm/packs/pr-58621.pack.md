## Purpose

FlashInfer 0.7.0 (already pinned) ships the TRTLLM-GEN DSv4 sparse-MLA **RopeQuant** epilogue (flashinfer-ai/flashinfer#4918): the kernel applies the inverse RoPE to the attention output and casts it to FP8 with packed UE8M0 scales, in the layout DeepGEMM's `fp8_einsum` consumes. This PR uses it on `FLASHINFER_MLA_SPARSE_DSV4` for DeepSeek V4, so `wo_a` reads the kernel's FP8 output directly instead of a bf16 `[T, 128, 512]` output plus a separate `fused_inv_rope_fp8_quant` pass.

It mirrors the pattern the DSv4.1 FlashMLA mega-attention layer already uses (`_alloc_attn_out` returning a `QuantizedActivation` that `_o_proj` consumes whole).

### Changes
- `DeepseekV4Attention` gets an `_alloc_attn_out` hook. The default stays the padded bf16 buffer (still head-sliced before `_o_proj`), so the FlashMLA, SM120, ROCm, XPU and CPU layers are unchanged.
- `DeepseekV4FlashInferMLAAttention` allocates RopeQuant's buffers. `deep_gemm_fp8_o_proj` now also takes a `QuantizedActivation`: it skips `fused_inv_rope_fp8_quant` and feeds the kernel's FP8 output and scales straight to `fp8_einsum`.
- The launcher requires the output's group stride to equal `sum_q` (it has no stride field for O), so a token slice of a shared buffer is rejected. Both the decode and prefill calls therefore span the full, CUDA-graph-padded buffer and select their tokens through `cum_seq_lens_q`; the prefill call's offsets are not rebased. Rows outside `cum_seq_lens_q` are never read or written (checked with garbage pad rows under `CUDA_LAUNCH_BLOCKING=1`).
- `build_flashinfer_mixed_sparse_indices` gains `num_rows` so it can size its outputs for those rows while computing only the real tokens.
- **DSpark non-causal decode (bugfix, affects the unfused path too).** The kernel treats every entry of its active index ranges as a key: the first `min(128, pos + 1)` columns (the query's causal SWA window) and `[128, sparse_topk_lens)`. `-1` is not skipped. DSpark's non-causal decode rows were copied in as one contiguous run with `sparse_topk_lens` set to the full row width. So the `-1` padding past the run was attended as keys, and with fewer than 128 context tokens the causal window also cut out the later block tokens. The builder now fills each row's causal window with the first visible entries, puts the rest from column 128 on, and sets `sparse_topk_lens` to exactly that. Every draft token then sees the whole block at any context length. Because the decode call passes real `seq_lens`, RopeQuant's derived positions match `positions` for the draft too. This is the DSv4 counterpart of #57432, which fixed the same two problems for DSv4.1 only; DSv4 reads neither of the metadata fields it added. #57432 presents each draft token as its own sequence with the full request length. RopeQuant cannot use that, because it derives RoPE positions from `seq_lens`. So this change keeps the real `seq_lens` and lays out each row around the query's causal window instead.

### When it is on
Automatically, with no flag, when all of these hold:
- exactly 128 local query heads (DSv4-Pro at TP1 or with DP attention). The kernel has one fixed 128-head schedule; padding fewer heads up to 128 measured slower;
- per-tensor FP8 KV cache;
- FP8 `wo_a`.

DSv4 has 8 heads per `wo_a` group at every TP size, so 128 local heads always means the kernel's 16 × 8 layout. That is DSv4-Pro at TP1 or with DP attention; Pro at TP2–16 and Flash have fewer heads and keep the existing path.

This includes the non-causal DSpark draft. The one inexact case is a draft block running past `max_model_len`: the draft clamps its positions there and RopeQuant does not reproduce the clamp, which only affects those drafts.

Everything else keeps the existing path.

## Not a duplicate
I searched open and closed PRs for RopeQuant, `dsv4_inv_rope_cos_sin_cache`, flashinfer#4918, and fused inverse-RoPE/FP8 on `FLASHINFER_MLA_SPARSE_DSV4`. No PR wires this epilogue into vLLM. The nearby DSv4 PRs (#57679 query RMSNorm+MXFP8, #57977 MXFP8 activations between DeepGEMM kernels, #55459 indexer Hadamard) touch different paths. #57432 (merged) fixed the DSpark non-causal FlashInfer layout for DSv4.1 only; the DSv4 fix here is the counterpart, done differently so RopeQuant can apply (see Changes).
