## 正文(PRD / 提案全文)

**TL;DR:** vLLM's block-INT8 tuned-config loader silently matched **0 of 39** shipped config files for ~14 months -- a one-character filename typo (`block_shape=[128, 128]` vs the shipped `[128,128]`) meant every block-INT8 model quietly fell back to the heuristic, with no test, warning, or signal. The fix shipped; this RFC proposes a small registry + a CI check so that **class** of bug cannot silently recur for any tuned Triton kernel -- without forcing anyone to tune a kernel that should not be tuned.

_(Reference implementation -- registry, decorator, AST kernel discovery, reasoned allowlist, ratchet, tests -- is built and green. Branch: https://github.com/access2rohit/vllm/tree/rfc/tunable-kernels-A3-B3 .)_

## Motivation

vLLM ships offline-tuned Triton kernel configs (JSON keyed by batch size M) for a handful of
compute-heavy, on-the-hot-path kernels -- MoE expert GEMMs, block-FP8/INT8 GEMMs, the Mamba
selective_state_update decode step -- and loads the best match at runtime, falling back to a fixed
heuristic on a miss. This is high-value: the right tile/num_warps/num_stages for a shape+GPU is a
real speedup, and the env override (VLLM_TUNED_CONFIG_FOLDER) lets operators hot-load new configs
without rebuilding.

Two structural gaps make this fragile:

1. No uniform "make a kernel tunable" mechanism. Each of the 4 tunable kernels hand-rolls its own
   config-file lookup (its own filename f-string + its own load + fallback). There is no shared
   contract and no programmatic list of which kernels are tunable. A newly added compute-heavy
   kernel easily ships with no tuning path at all, and nobody notices.

2. Silent drift, with a concrete 14-month precedent. The block-INT8 loader built its filename with a
   stray space -- `block_shape=[128, 128]` -- while every shipped INT8 config is `[128,128]`. Result:
   0 of 39 configs ever matched; the loader silently fell back to the heuristic from #16366
   (2025-04) until it was found and fixed in the recent hot-load work. No test, no warning, no
   signal -- just quietly lost performance on every block-INT8 model for over a year.

The root cause of both: "is this kernel tunable, and does its loader actually work?" is answered
ad hoc per kernel, with nothing enforcing consistency. We propose a small, idiomatic mechanism +
an opt-out CI check that makes the answer explicit and regression-proof -- without forcing anyone
to tune a kernel that should not be tuned.

Non-goal: deciding which kernels are compute-heavy/in-path. No static check can infer that; the
proposal makes that human judgment explicit and reviewable, not automated.

## Proposed Change

Two pieces -- a registry (mechanism) and a completeness ratchet with a reasoned allowlist (enforcement):

### Part 1 -- A registry of tunable kernels (mechanism)

A single importable source of truth, mirroring vLLM's existing model / attention-backend
registries:

- `vllm/utils/tuned_config_registry.py`: a frozen `TunableKernelSpec(name, applicability, key_fn,
  packaged_dir)`, a `TUNABLE_KERNEL_REGISTRY` dict, `register_tunable_kernel`, `get_tunable_kernels`,
  and a generic resolve+select front-end `get_tuned_config_for(name, M, **shape)` that returns the
  single nearest-M config (or None). `applicability` is an enum
  (COMPUTE_HEAVY_INPATH / OPTIONAL / EXPERIMENTAL).
- A `tunable_triton_kernel(...)` decorator (optional ergonomic front-end) that wraps a kernel's
  config getter to do filename-build + load + fallback AND register the spec at import time.
- The 4 existing tunable kernels are registered by a seed module whose key_fns reproduce each
  loader's exact filename (so the registry's view matches what each kernel actually searches for).

Adoption cost is small and is NOT new: all 4 tunable kernels already have a per-kernel config getter
today; this standardizes them and centralizes the lookup logic that was being copy-pasted (the
copy-paste is exactly what produced the INT8 space bug). Making a kernel tunable does NOT touch the
`@triton.jit` body; the irreducible per-kernel work is a ~3-line filename builder + wiring the
launch site to use the loaded config (intrinsic to "use a tuned value instead of a hardcoded one").

### Part 2 -- A completeness ratchet with a reasoned allowlist (enforcement)

A CI test (`tests/test_tunable_kernels_ratchet.py`) that:

- Enumerates every `@triton.jit` kernel via a static AST walk (`tools/tuned_config/discover_kernels.py`)
  -- no imports, so it is robust to torch/CUDA/platform-gated modules and sees every kernel.
- Requires each discovered kernel to be EITHER registered tunable OR listed in
  `tools/tuned_config/exempt_kernels.py` with a one-line reason.
- Is seeded once with all current kernels (the ratchet baseline), so it is GREEN today and only
  bites a NEWLY added kernel. A new kernel makes CI fail with an actionable message:
  "New @triton.jit kernel(s) [...] must either register a tuned-config loader OR be added to
  exempt_kernels.py with a reason (e.g. 'memory-bound elementwise; tuning <2%')."
- Also runs a generic filename round-trip check on every registered kernel (asserts the key_fn
  output is exactly what the loader searches for) -- this single test structurally prevents the
  INT8-class bug for all current and future tunable kernels at once.
- Rejects empty / "TODO" exemption reasons, so the allowlist cannot become a rubber stamp.

The reasoned allowlist is deliberately the de-coercion mechanism. CI never says "you must tune this
kernel" -- only "tune it OR state, in one reviewed line, why not." That keeps the ~88% of kernels
that are memory-bound (rmsnorm, rope, activation, ...) out of scope by an explicit, reviewed
decision rather than silent omission. The allowlist is what keeps the check from being a blunt
mandate: without it, the test would flag 324 of 328 kernels on the current tree -- almost all
memory-bound kernels that should never be tuned.

### Why both, together

The registry without the ratchet (Part 1 only) catches filename drift on kernels people remember to
register, but a forgotten kernel stays forgotten. The ratchet needs the registry's machine-readable
list to know what is covered. Together they make "tunable or explicitly-not" a property CI
guarantees. The registry doubles as living documentation of every perf-critical kernel and the
tuning status of every other one.

### Rollout / scope

- The 4 existing tunable kernels are migrated onto the registry (behavior-preserving; their current
  tests stay green).
- The allowlist is seeded with all currently-discovered non-tunable kernels, each with a reason
  (specific for known memory-bound kernels, generic otherwise) -- a one-time mechanical step so CI
  starts green.
- No kernel is forced to change. Existing config files and the VLLM_TUNED_CONFIG_FOLDER override are
  untouched.
- A reference implementation (registry + decorator + seed + discovery + allowlist + ratchet + tests)
  is built and passing; happy to open it as a draft PR for review.

## Feedback Period

Two weeks (suggested). Main discussion points we expect:
- The small per-new-kernel contributor friction (register OR exempt-with-reason) vs. the
  silent-drift risk it removes.
- Whether "compute-heavy and in-path" warrants a written definition (FLOPs/byte? on the decode
  path?) to guide allowlist review, or stays reviewer judgment.
- Whether `applicability=COMPUTE_HEAVY_INPATH` should be enforced (must be tunable) or advisory.
- Landing as one PR (registry + ratchet) or two (mechanism first, enforcement second).

## Any Other Things

- This is additive and low-risk: default behavior (env var unset) is unchanged; the ratchet starts
  green; the round-trip test only fails on genuine filename drift.
- The mechanism is forward-compatible with a future tuning service: the registry is exactly the
  machine-readable manifest of "what is tunable, with what key, and how to regenerate it."
- A natural follow-up (separate PR) is bringing additional compute-heavy kernels into the registry --
  e.g. the unified Triton attention kernel, which today selects its tile from a fixed heuristic.
