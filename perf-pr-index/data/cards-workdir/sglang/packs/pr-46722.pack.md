## Motivation

**What**
Cut the Wan VAE decode on gfx1250 (MI450) from 22.5 s to 8.5 s for Wan2.2-T2V-A14B 720p / 193 frames. The changes: run the ROCm batched-Conv2D replacement in NHWC, install the existing Wan VAE fast path (fused RMSNorm+SiLU, DupUp3D+add) on gfx1250, and drop the slow `where` from the gfx1250 math-SDPA VAE attention.

It also keeps that fast path under multi-GPU: with `--num-gpus 2 --enable-cfg-parallel`, Wan's `auto` VAE parallel-decode mode no longer picks spatial-shard decode on gfx1250, and only the main rank decodes. TP2 VAE decode goes from 28.5 s to 9.0 s.

**Why**
A torch profile of the decode showed only ~9 s of the ~20 s of GPU time was convolution. The rest was unfused fp32 elementwise work plus one attention fixup:

- `RocmPlatform.optimize_vae` never installed `wan_vae_cuda_opt`, so every `WanRMS_norm -> SiLU` ran as `linalg_vector_norm` + `div` + `mul` + `silu` (div 4.8 s, mul 3.0 s, silu 2.7 s per decode).
- The fused norm needs a channels_last_3d input, but the ROCm batched-Conv2D replacement produced `[N, T, C, H, W]` memory. Simply making the conv2d channels_last does not help: PyTorch runs MIOpen convs in NHWC only when `PYTORCH_MIOPEN_SUGGEST_NHWC=1` (read on every call). Without it, a channels_last conv2d is transposed to NCHW and back. With it, the VAE convs run 1.4-2.9x faster (34.97 -> 11.89 ms at 96 ch, 720x1280). The conv output then folds back to channels_last_3d without a copy, so the fused norm applies.
- gfx1250 pins VAE attention to the math SDPA backend (AOTriton fails above head_dim 256). 121 of its 131 ms per call is the `where` in `_safe_softmax` that zeroes fully masked rows. There is no mask here, so computing the same ops explicitly (`q*s @ (k*s)^T`, softmax, `@ v`) is bit-identical and skips it.
- Multi-GPU: `WanVAEConfig.auto_parallel_decode_prefers_spatial_shard()` returns True, so with more than one rank the decoder is built for spatial-shard decode, and `_maybe_optimize_wan_family_vae` then skips the fast path (`Wan VAE: spatial-parallel decode; skipping fast path.`). The sharded decode on the slow path takes 28.5 s on 2 ranks, slower than one rank on the fast path. Once `auto` stops sharding there, `AutoencoderKLWan.use_parallel_decode` was still the raw config flag (always True), so `DecodingStage` stayed `REPLICATED` under cfg-parallel and both ranks decoded the same full video (10.0 s).

## Modifications

- `platforms/rocm.py`:
  - On gfx1250, `optimize_vae` installs `maybe_optimize_wan_vae` / `maybe_optimize_qwen_image_vae`.
  - `_replace_conv3d_with_conv2d` keeps a channels_last BF16 2-D weight when the 3-D weight is channels_last_3d, and sets `PYTORCH_MIOPEN_SUGGEST_NHWC=1` with `setdefault` (an explicit user value wins).
  - `_conv3d_as_batched_conv2d` gets an NHWC branch: one copy gathers the Kt frames and casts to BF16 into `[N*T_out, H, W, Kt*C_in]`, and the output reshapes back to channels_last_3d.
- `models/vaes/wanvae.py`:
  - Import the Triton VAE helpers on gfx1250 too.
  - Keep the fused cat+pad away from convs patched by the Conv2D replacement (it would call the unpatched epilogue).
  - Use explicit math attention when `_sgl_math_sdpa` is set and inputs are fp32.
  - `AutoencoderKLWan.use_parallel_decode` is the config flag, except in `auto` mode where it is True only when spatial-shard decode is chosen, so a single-rank decode runs on the main rank alone under cfg-parallel. Explicit modes keep the config flag.
- `configs/models/vaes/wanvae.py`: `WanVAEConfig.auto_parallel_decode_prefers_spatial_shard()` returns `not is_gfx1250_supported()`. An explicit `parallel_decode_mode=spatial_shard` still shards.
- `models/vaes/wan_vae_cuda_opt.py`: allow the exact-tier post-op fusion on HIP. It keeps its first-use `torch.equal` verification and falls back to aten on any mismatch. On ROCm it is only reachable through the gfx1250 install above.
- Scope: all new behavior is gated on `is_gfx1250_supported()`. NVIDIA, MI300, and MI355 paths are unchanged (one extra `hasattr`/`getattr` that evaluates false).
- Tests (`test_rocm_conv3d_patch.py`):
  - The NHWC conv matches the original `WanCausalConv3d` (with `residual=` / `skip_bias=`) and returns channels_last_3d.
  - Explicit math attention is `torch.equal` to the math SDPA backend.
- Tests (`test_vae_spatial_parallel_decode.py`): `auto` does not shard on gfx1250 while explicit `spatial_shard` does; `use_parallel_decode` is False only for `auto` on gfx1250 (`spatial_shard`, `patch`, and non-gfx1250 `auto` are unchanged). The existing Wan assertion runs with gfx1250 patched off.

## Accuracy Tests

Wan2.2-T2V-A14B, 720x1280, 193 frames, 8 steps, seed 42, fp32 VAE decode, single MI450 (gfx1250) partition. The video is compared against main with the same flags, per frame:

| comparison | PSNR mean | PSNR min | last frame |
|---|---|---|---|
| this PR vs main, full 8-step video | 38.45 dB | 35.64 dB | 38.34 dB |
| VAE attention change only vs main | bit-identical | bit-identical | bit-identical |

The difference comes from the NHWC conv algorithm (the BF16 compute was already there) and the fused norm's rounding order (`quality="lossless"`, the default request tier). Against an fp32 `conv3d` reference, the NHWC and NCHW batched-conv2d paths have the same relative error (3.20e-3 / 3.05e-3 / 3.00e-3 at the three decoder resolutions). Frames were checked visually, including the last frame.

Multi-GPU (TP2, `--num-gpus 2 --enable-cfg-parallel`), same prompt and seed, decoded video compared over all frames:

| comparison | PSNR |
|---|---|
| single-rank fast-path decode vs spatial-shard decode (before) | 38.7 dB |
| main-rank-only decode vs both ranks decoding | inf (identical) |

Spatial-shard and single-rank decode were never bit-identical; per-frame PSNR is flat (37.7-38.9 dB), with no shard seams.
