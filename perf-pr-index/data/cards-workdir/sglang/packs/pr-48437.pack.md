## Motivation

On MI355X (gfx950), when Kimi-K3.1 runs TP8 speculative decoding, the target-verify batches go through the Triton split-K kernel in `triton_sparse_mla_fwd`. Each request contributes bs × 6 rows (DFLASH MLA5 draft, 5 draft tokens), so a batch is 16–512 query rows. In a TP8 bs48 decode step, sparse MLA takes about 18% of the step time. The gfx950 HIP sparse MLA prefill kernel is already in the tree, but it runs one CTA per row, which can't fill the GPU at these row counts.

## Modifications

- **`sparse_mla_prefill_gfx950.cuh` / `.py`**: add a split-K mode (`run_split` / `sparse_mla_split_gfx950`). Each row's top-k is split across `splits` CTAs, and the partial results are merged with an fp32 log-sum-exp combine, so the merge adds no extra rounding. `sparse_mla_decode_splits(rows)` picks the split count from the row count (16 / 8 / 4 / 2, from per-shape microbenchmarks; numbers in the docstring).
- **`triton_sparse_mla.py`**: in `triton_sparse_mla_fwd`, batches of 16–512 rows (H ≤ 16, shapes supported by `supports_sparse_mla_prefill_gfx950`) go to the HIP split-K kernel. Smaller batches (6 / 12 rows) stay on the Triton split-K path, which is faster there. Batches above 512 rows keep the existing single-CTA HIP path. Non-DCP only.
- **`environ.py`**: new switch `SGLANG_ROCM_SPARSE_MLA_DECODE_HIP`, on by default; set it to `0` to fall back to Triton.

Kernel time (MI355X, 12 heads, top-2048):

| Rows | Triton split-K (µs) | HIP split-K (µs) |
|---:|---:|---:|
| 24 | 28.6 | 20.5 |
| 96 | 89.5 | 31.2 |
| 192 | 239 | 46.3 |
| 288 | 103 (single-CTA HIP) | 70.8 |
