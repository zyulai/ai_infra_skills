## 正文(PR 描述)

## Overview

`max_num_scheduled_tokens=0` passed config validation. `LLM.generate()` then hung forever with no error. This PR changes the field's bound from `ge=0` to `ge=1`, so `0` is now rejected when the config is built.

Fixes #60349. The bug was introduced by #44207.

## Claims

- `max_num_scheduled_tokens=0` now raises a pydantic `ValidationError` (a subclass of `ValueError`) at config time, instead of a silent hang. The error names the field and the allowed range.
- `0` is rejected on every user route: `SchedulerConfig`, `EngineArgs`, `EngineArgs` with speculative decoding, and `--max-num-scheduled-tokens` on the CLI.
- `None` (the default), `1` and larger values work as before.
- A new unit test fails on the old bound and passes with the fix.

## Details

**Root cause.** `SchedulerConfig.max_num_scheduled_tokens` is `Field(default=None, ge=0)`, so `0` passes. The only other check, `<= 0` in `VllmConfig._set_max_num_scheduled_tokens` (`vllm/config/vllm.py`), runs only when speculative decoding is on. `Scheduler.__init__` keeps the value because it `is not None`. So every `schedule()` call starts with `token_budget = 0`. Both scheduling loops (running and waiting) run only `while token_budget > 0`. No token is ever scheduled, the request stays in `waiting`, and nothing raises. A debug run on the old code, with prints added to the scheduler, showed this on every step:

```
LYUTIY-DEBUG Scheduler.__init__ config max_num_scheduled_tokens=0 max_num_batched_tokens=16384 -> self.max_num_scheduled_tokens=0 speculative_config=None
LYUTIY-DEBUG schedule step=1 start_budget=0 end_budget=0 waiting=1 running=0 total_num_scheduled_tokens=0
```

**Where it came from.** Before #44207 (commit `51e0c579b`), the field had no bound and the scheduler used a truthiness test, so `0` quietly fell back to `max_num_batched_tokens`. #44207 added `ge=0` and changed the test to `is not None`. Its goal was to make the non-speculative path reject bad values the same way the speculative path does. But the speculative path rejects `<= 0` ("does not allow any tokens to be scheduled"), while the new bound rejects only `< 0`. This off-by-one turned `0` into a real zero budget.

**Why a bound and not a scheduler change.** The scheduler treats a zero budget as "paused" on purpose, so its behavior is correct. A budget of zero tokens per step can never make progress, on any model or hardware. The sibling fields `max_num_batched_tokens` and `max_num_seqs` already use `ge=1`. The issue asks for a config-time `ValueError`.

**Not done.**

- I did not map `0` back to the default. That would silently replace a value the user set. The documented default is `None`, and the speculative path rejects `0`.
- I kept the speculative-path `<= 0` check. A user value can no longer reach it, but removing it is cleanup outside this fix.

**Limitation.** Setting the field after construction is not validated, because the `@config` dataclass does not validate on assignment. Today only internal code does this (`vllm/config/vllm.py` sets it to `max_num_batched_tokens`, which is `ge=1`), so no user route can reach the scheduler with `0`.
