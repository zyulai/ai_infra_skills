## 正文(PRD / 提案全文)

### Motivation.

As vLLM is moving towards full PD disaggregation, this allow us to add new optimizations just for prefill workload:

- **Much larger context length on prefill nodes**: As there is no decoding steps in prefill nodes, we can directly store the generated KV caches to CPU instead of GPU. This gives us much much longer context length (about 7x longer).
- **Better scheduling**: Also, since there is no decoding, the time it takes to run each request (aka job completion time) is completely deterministic. This means that we can do better scheduling for prefill nodes by using the job completion time as the input to the scheduler.

Please see more details in https://arxiv.org/abs/2505.07203


### Proposed Change.

## User-facing API

- Add `vllm prefill`, which will only accept prefill requests (`max_tokens=1`) and performs prefill-only optimizations.

## Longer context length

The key technique that enables longer context length is to directly store the generated KV cache to CPU, and also control the peak memory usage for long-context inference. Traditionally this is done by chunked prefill, however it requires keeping the previous KV caches (we want to save it in CPU). Instead, we can prefill the attention layer normally but prefill the FFN modules chunk-by-chunk (we call this **hybrid prefilling**). This can be transparently done via `torch.compile`.

Context length improvement: ~7x on A100 40 GB, model RedHatAI/DeepSeek-R1-DistillQwen-32B-FP8-dynamic

Proposed changes:

- Support a compilation level that only triggers `torch.compile`
- Inside the compilation pass of `torch.compile`, identify the FFN modules and prefill them chunk-by-chunk.
- Support models with hybrid attention patterns

## Memory allocation

To enable longer context legnth, we need to store the KV caches into CPU memory. This makes memory allocation is a bit complicated --- the simple solution is to directly bypass GPU cache, and purely use CPU as the main caching layer for KV caches. But alternatively, we can still enable GPU cache, and only use CPU when the request is too long to fit its KV caches completely in GPU. Both design makes sense and we are open for feedback.

## Better scheduling

The job completion time of prefill-only request can be simply estimated by # of input tokens - # of cache hit tokens.

Proposed changes
- Add `get_num_computed_blocks` that returns just the number of cache hit tokens instead of a list of blocks. This allow us to use binary search to reduce cost.
- Add a new scheduler that performs scheduling based on # of input tokens - # of cache hit tokens. It can be a greedy scheduler that does shortest remaining job first, or it can also be a scheduler that tries to maximize the rate of SLO fulfillment.
