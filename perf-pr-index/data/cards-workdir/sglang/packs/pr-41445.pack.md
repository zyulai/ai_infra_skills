## PR body

## Motivation

`--linear-attn-prefill-backend ptx_kda` only runs on SM103 (B300 / GB300) today: the extension is built with `-gencode arch=compute_103a,code=sm_103a` and `PtxKDAKernel.supports_prefill` checks for compute capability (10, 3). On B200 / GB200 the backend silently falls back to Triton.

Nothing in the kernel needs SM103:
- All of its inline PTX is available on sm_100a:
  - tcgen05 `cta_group::1`: alloc, ld, st, mma (`kind::f16` and `kind::tf32`), commit, wait and fence.
  - TMA (`cp.async.bulk.tensor`), mbarrier, `mma.sync`, `ldmatrix`, `cp.async`, `prefetch`.
- There is no `ld.red` or other sm_103-only instruction.
- The route and piece-budget cost model reads `multiProcessorCount` at runtime.

On B200 the kernel gives the same speedup over the default Triton path as it does on B300.

## Modifications

- `kernels/ops/attention/linear/kda_ptx_prefill/__init__.py`:
  - Add `SM_ARCHS = {(10, 0): "100a", (10, 3): "103a"}`.
  - Build for the running device's arch. Arch-specific cubins do not run across the two.
  - Name the JIT extension per arch (`kda_prefill_ptx_sm100a` / `kda_prefill_ptx_sm103a`), so a shared `TORCH_EXTENSIONS_DIR` can keep both.
- `srt/layers/attention/linear/kernels/kda_ptx.py`: `supports_prefill` is true on SM100 and SM103.
- `srt/layers/attention/linear/kda_backend.py`: update the fallback and error messages.
- `kernels/jit/csrc/attention/kda_prefill.cu`: update the build comment only. The kernel code is unchanged.
- `test/registered/kernels/ops/attention/test_kda_prefill.py`:
  - The two ptx cases now also run on SM100.
  - The B200 runner now JIT-builds the extension, so its `est_time` goes from 180 to 300 s. The measured time on B200 is 146 s, including the build.

The default KDA prefill backend is unchanged (`triton`). `ptx_kda` stays opt-in.

## Benchmarking and Profiling

- Hardware: B200 (148 SMs), torch 2.13 + cu130, triton 3.7.1.
- Method: `PtxKDAKernel.extend` against `TritonKDAKernel.extend`, called the way `KDAAttnBackend.extend` calls them.
- Inputs:
  - q, k, v and the raw gate are bf16 with shape `[1, B·T, H, 128]`.
  - beta is raw (the kernel applies the sigmoid).
  - `A_log` and `dt_bias` follow the Mamba/KDA init.
  - The state pool is fp32.
- Timing: CUDA events including wrapper overhead, median of 10 runs. Latency is in µs.
- "Max diff" is the maximum absolute difference from the Triton output.

With `lower_bound = -5` (safe gate, as in Kimi-K3):

| B × T × H | triton | ptx_kda | speedup | max diff |
|---|---|---|---|---|
| 1 × 8192 × 32 | 968 | 761 | 1.27× | 3e-2 |
| 1 × 32768 × 32 | 3442 | 2498 | 1.38× | 3e-2 |
| 1 × 32768 × 8 | 1835 | 766 | 2.40× | 3e-2 |
| 1 × 32768 × 4 | 1583 | 510 | 3.10× | 3e-2 |
| 4 × 8192 × 32 | 2884 | 1677 | 1.72× | 3e-2 |
| 16 × 2048 × 32 | 2675 | 1798 | 1.49× | 3e-2 |
| 4 × 8192 × 8 | 965 | 808 | 1.19× | 3e-2 |

For comparison, B300 with the same script gives 1.09–2.98×. The absolute ptx_kda times on B200 and B300 are within ±6% of each other.

Without `lower_bound` (plain softplus gate, as in Kimi-Linear), ptx_kda is 1.34–3.21× faster than triton on the same shapes. One shape produces NaN, see Notes.

The biggest gains are at few heads per GPU (TP-sharded) with long prompts. There the Triton `chunk_h` recurrence is latency-bound, taking about 2.3–2.4 µs per 64-token chunk on B200 whether H = 32 or H = 4. ptx_kda splits the sequence into pieces and composes their affine state maps.
