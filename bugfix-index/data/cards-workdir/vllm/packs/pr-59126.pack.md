## 正文(PR 描述)

## Purpose

Fix two independent ways an image request takes down the engine in the GLM-5.3-Flash (`Glm5NextForConditionalGeneration`) vision tower.

**1. Every image trips the GPU sync check.** `rot_pos_emb` builds `pos_ids` on the host and copied it with `.to(device, non_blocking=True)` from pageable memory, and the eager `forward` did the same with `cu_seqlens`. A non-blocking copy from pageable memory can block the host, so with `VLLM_GPU_SYNC_CHECK=error` the first image raises `Implicit GPU<->CPU sync detected - use a pinned, densely laid out CPU tensor, or wrap with gpu_sync_allowed()` and the engine dies.

Fix: stage both copies through pinned memory with `async_tensor_h2d`, as `Glm4vVisionTransformer` does for its position tables. The eager and CUDA-graph forward paths are otherwise unchanged. The `max_seqlen` read-back in the ViT attention wrappers already runs under `gpu_sync_allowed()`, so nothing else in the eager path trips the check.

**2. Slim images overflow the vision rope table.** Since vllm-project/vllm#57387, images go through the transformers `Glm5NextImageProcessor`, whose `smart_resize` bounds them by token budget only, with no aspect-ratio cap. A slim image therefore gets a grid side beyond the hardcoded `max_position=8192`. For example, with the checkpoint's `processor_config.json`, a 200000×20 px image is accepted at 7143 tokens with `image_grid_thw = [1, 2, 14286]`, and `cos[pos_ids]` reads past the table: an `IndexError` on CPU, a device-side assert on GPU.

Fix (suggested in review): size the table from `text_config.max_position_embeddings`. For GLM-5.3-Flash that is 1,048,576 rows, about 64 MiB in bf16 per GPU.

For every grid that fit the old table, the vision tower's output is bit-identical to before.

Neither bug depends on quantization or KV-cache dtype: the tower is built with `quant_config=None` and uses no KV cache, and the `RedHatAI/GLM-5.3-Flash-NVFP4` vision weights are BF16, as in `zai-org/GLM-5.3-Flash`.

**Not a duplicate:** On 2026-09-29 and 2026-10-02 I searched open vllm-project/vllm PRs for `glm5next`, `rot_pos_emb`, `GLM-5.3-Flash image`, `glm5next sync` and `VLLM_GPU_SYNC_CHECK vision`, and issues for GLM-5.3-Flash image crashes. Nothing addresses either bug. The two closest PRs have since merged, and both bugs are still on `main`:
- vllm-project/vllm#57387 replaced the vendored processor with the transformers one. Slim images still reach the tower; the example above was re-run through it.
- vllm-project/vllm#55389 added input normalization ahead of the patch embedding.

## Test Result

- **Overflow test on `main`:** `IndexError: index 8192 is out of bounds for dimension 0 with size 8192`. **With this PR:** passes; 30 of 30 consecutive runs on the previous revision, whose `rot_pos_emb` is byte-identical to this one.
- **Suites (CPU):** 10 passed, 1 skipped (the CUDA-only test).
- **Old vs. new:** forward output and rotary tables bit-identical for `[1, 78, 138]` (a 1920×1080 image), a mixed batch including a two-frame item, and the boundary `[1, 2, 8192]`. The tower was built without transformer blocks, which need Triton; the GPU image request below covers them.
- **Lint:** all pre-commit hooks and the CI mypy 3.12 hook pass.
- **GPU:** not run yet; no GPU was available where this was developed. Still to run: `test_image_forward_has_no_implicit_gpu_sync`, and an image request to GLM-5.3-Flash served with `VLLM_GPU_SYNC_CHECK=error`.

**Model evaluation:** Not run. Output for every input that worked before is bit-identical; only inputs that previously crashed the engine take a new path.
