## PR body
```markdown
Add a FlashInfer `moe_ep` compute path for the DeepSeek-V4 mega-MoE experts, selectable at runtime alongside the existing native `deep_gemm_mega_moe` backend.

- New module `vllm/utils/flashinfer_moe_ep.py`: model-agnostic plumbing only — backend registry and predicates, flashinfer `moe_ep` runtime bootstrap/finalize (bootstrap passes `device=torch.cuda.current_device()`, see review item on the LOCAL_RANK pin), NVFP4 prequant weight packing + epilogue alphas, config validation, and mega-layer construction.
- New module `vllm/models/deepseek_v4/nvidia/fi_moe.py`: `DeepseekV4MegaMoEExpertsFI`, a subclass of the native `DeepseekV4MegaMoEExperts` (same weight layout + loader; overrides weight finalize and forward with the flashinfer compute path), plus the DSV4-specific helpers (NVFP4 checkpoint detection, prequant pack, routing preprocess).
- `model.py`: pick `DeepseekV4MegaMoEExpertsFI` when an fi backend is active and thread the swiglu activation clamp through; the `use_mega_moe` checks (including sequence-parallel eligibility) test membership in `MEGA_MOE_BACKENDS`.
- `config/kernel.py`: register the two new names in the `MoEBackend` literal and host the `MEGA_MOE_BACKENDS` set next to it. Required, not cosmetic — `KernelConfig` validates `moe_backend` against that literal and rejects unknown values before the model is ever constructed.
- New tests `tests/models/test_deepseek_v4_fi_moe_ep.py`: 11 unit tests (no GPU; flashinfer faked) covering backend registration, the device-pinned bootstrap, SP eligibility for every mega backend, config building, and the fp4 dequant helper.

Two backends are added, selected by `moe_backend` string:

| `moe_backend` | megakernel | notes |
|---|---|---|
| `flashinfer_moe_ep_mega_deep_gemm` | `deep_gemm_mega` | consumes an MXFP4 checkpoint verbatim (e2m1 + E8M0 per-32 scales) — the same recipe the native path uses, so this isolates the integration layer from kernel work |
| `flashinfer_moe_ep_mega_cutedsl` | `nvfp4_cutedsl` | needs NVSHMEM. The checkpoint picks the weight path, not the kernel: an NVFP4 checkpoint is consumed prequantized, MXFP4 weights are dequantized to bf16 and requantized |

Opt-in and off by default: the fi path is taken only when `moe_backend` is one of the two names above, so the native path keeps its own compute. Selection is by backend string alone.

**Sequence-parallel ready; benchmark numbers below predate SP.** Since the numbers below were taken (v0.25.1), main integrated sequence-parallel MoE, which shards the MoE batch across TP ranks — 8x fewer tokens/rank at TP8 — and moves the e2e operating point down the tokens/rank curves in the microbenchmark tables. This PR runs SP exactly like native: mega-MoE eligibility, SP included, is keyed on the shared `MEGA_MOE_BACKENDS` set, with a regression test (without this the fi backends silently ran the MoE full-batch on every rank). On the current stack `fi_dg` holds 0.997–1.008x parity with native across prefill/decode cells on 8xB200. CuTeDSL perf tuning at the sharded operating points (knob autotune at sharded token counts, quantized combine wire) is ongoing and will come as follow-ups — this PR is the correct, SP-ready plumbing.

The native `DeepseekV4MegaMoEExperts` class body is unchanged. Everything in the diff either widens the `use_mega_moe` checks from an equality test to `MEGA_MOE_BACKENDS` membership — which still matches `deep_gemm_mega_moe` — or adds the fi experts class and its config validation alongside the native one.

`flashinfer.moe_ep` is a soft dependency — imported lazily inside the fi code paths, never at module import. The backends need flashinfer >= 0.6.17 (`BootstrapConfig.device`, flashinfer-ai/flashinfer#4348), which the vLLM FlashInfer requirements pin will carry; selecting a fi backend against a build without the moe_ep runtime raises a clear ImportError at config time. The fi backends also validate an SM100 device capability up front, and reject `--enable-eplb`, since the FlashInfer experts neither apply the logical-to-physical expert map nor report per-expert load.

All numbers: **one 8-GPU B200 node (SM100)**, flashinfer `4_5_2-perf-fix` @ `1ee41bcd` (https://github.com/flashinfer-ai/flashinfer/pull/4101), **nvidia-cutlass-dsl 4.5.2** — vLLM 0.25.1's own pin. Do not unpin it: the DSL version and the flashinfer branch are a matched pair, and both harnesses assert 4.5.2 at run time. CUDA 12 and 13 both work.

Backend is selected by the `moe_backend` string — one per run, no env gating:

(fi_cutedsl additionally takes `FLASHINFER_MOE_EP_KNOB_CACHE=<repo>/vllm_e2e/results/knob_cache_ep8.json` and the NVFP4 checkpoint.) A second process benchmarks it over HTTP:

```bash

    --backend vllm --host 127.0.0.1 --port 30000 \
    --model $MODEL --tokenizer-mode deepseek_v4 \
    --dataset-name random \

The first client pass after boot is discarded as warmup and the timed passes are repeated with the median reported — the native decode baseline drifts run-over-run by more than the fi-vs-native delta, so single-pass serving numbers are quoted nowhere below.

**EP8 throughout, but the two levels reach it differently.** The microbenchmark builds the MoE layer alone with synthetic weights, so there is nothing for tensor parallelism to shard: one process per GPU, `DP8 / EP8 / TP1`, no vLLM and no checkpoint. The e2e sweeps have a whole model to place, so they run `TP8 / EP8 / DP1`. Expert parallelism is 8 in both, which is the axis under test.

One vLLM-side hazard is worth surfacing here rather than leaving in the runbook: **a cell that sets `MAX_CAPTURE` must also pin `CAPTURE_SIZES`.** With the dense default ladder, the cudagraph memory profiler reserves ~48 GiB/GPU for the flashinfer backends against a real ~6 GiB cost — the same ~6 GiB it estimates correctly for native — and the difference comes out of the KV cache. The tell is a backend that is *fast per step and slow overall*: better ITL than native, far worse throughput, because the engine is holding a fraction of the sequences requested. The other two ways to get plausible-but-wrong numbers are [§5](https://github.com/mhoqueanik/moe_ep_benchmark/tree/vllm_repro_8_gpu_v2/RUNBOOK_REPRO.md#5-things-that-will-bite-you).

### Accuracy gate — GSM8K, 200 questions, greedy, both checkpoints

| model | native | fi_dg | fi_cutedsl (NVFP4 cast) | delta |
|---|---|---|---|---|
| Flash | 0.965 | 0.965 | **0.965** | +0.000 |
| Pro | 0.880 | 0.880 | **0.890** | +0.010 |

**The delta is what gates the throughput claim.** Because fi_cutedsl runs a different checkpoint, its numbers are only comparable if its accuracy is; ±0.010 on 200 questions is two questions. Both models pass.

V4-Pro scoring 0.88 is a property of the model and this eval, not of `moe_ep` — all three backends agree exactly (176/176/178 correct), and it is not a truncation artifact: raising `--max-tokens` 512 → 1024 → 2048 moves accuracy 0.8800 → 0.8750 → 0.8750 while truncated completions only fall 15 → 14 → 13.

### Reproducibility of the numbers themselves

Ratios are stable to about ±0.02x between sessions; absolute throughput moves more with node and thermal state. +    w13_weight_scale: torch.Tensor,
