## Motivation

`_dsa_kv_cache_dtype_default` resolves `--kv-cache-dtype auto` to `fp8_e4m3` only when the device capability major is >= 10 (#11655). MI355X (gfx950) reports 9.5, so DeepSeek-V3.2 and GLM-5.x get a bf16 KV cache on ROCm by default. The HIP default DSA backend is triton (#30575), and its gfx950-tuned sparse-MLA path (`_is_gfx950_sparse_mla_fp8`) only runs with an fp8 KV cache. The GLM-5.3 MI355X cookbook already says to keep `--kv-cache-dtype fp8_e4m3` because BF16 KV slows the DSA prefill; this makes a launch without the flag do the same.

## Modifications

- `overrides.py`: `auto` also resolves to `fp8_e4m3` on HIP when `is_gfx95_supported()`, `SGLANG_USE_AITER=1`, and both DSA backends are unset, `triton` or `tilelang`. Learnable sinks, the `aiter` backends, gfx942 and `SGLANG_USE_AITER=0` keep bf16; an explicit `--kv-cache-dtype` is used as given. The aiter condition is needed because without aiter the prefix-hit MHA path reaches `dequantize_k_cache_paged_dsa`, which rejects the 576-wide fp8 row.
- `test_model_overrides.py`: gfx950 cases for the new default and each case that keeps bf16. The new case fails on main (`bfloat16 != fp8_e4m3`).
- `hisparse_guide.mdx`: the note on the `auto` default now covers MI355X and the opt-out.

A PD setup with a gfx942 prefill node and a gfx950 decode node now needs an explicit `--kv-cache-dtype`; bootstrap rejects mismatched KV dtypes.
