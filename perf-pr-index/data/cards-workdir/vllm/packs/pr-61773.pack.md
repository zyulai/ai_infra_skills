## Overview

Skip the per-layer `a1q_scale.t().contiguous()` copy between per-token-group FP8 quantization and the FlashInfer TRTLLM fp8-block MoE experts by emitting the scales in the layout the experts consume. This is pure plumbing on top of the quant kernel's existing `column_major_scales` mode — no kernel changes. ~2% TPOT improvement at concurrency 4 on Qwen3.8-Flash-Next-FP8 (TP4+EP).

## Claims

- Removes one `direct_copy_kernel` per MoE layer per decode step (24/step -> 0 on Qwen3.8-Flash-Next) from the critical path.
- ~2% TPOT p50 improvement at concurrency 4 on Qwen3.8-Flash-Next-FP8, TP4+EP on 4xGB300; parity at concurrency 1 (details below).
- Bitwise-identical expert inputs: the scale bytes are the same values, just allocated in the final physical layout, so there is no accuracy impact.
- Python-only change (+77/-14 across 5 files, mostly the test).

## Validation

### Correctness

- `pytest tests/kernels/moe/test_flashinfer.py`: 49 passed (+2 mxfp8 skips), including the new `transposed` arm of `test_trtllm_fp8_block_moe_deferred_finalize`, which builds the quant config through the production oracle + `no_dp_ep` path, asserts the prepared activation scale is column-major (`a1q_scale.t().is_contiguous()`), and asserts bitwise-equal expert output against the non-transposed baseline.
- No new test for the `column_major_scales` wrapper mode itself: it is a pre-existing feature already exercised by the CUTLASS/DeepGEMM/FlashInfer/PyTorch scaled-mm kernels on every CUDA run and by existing fusion/eplb tests.

### E2E perf

Qwen3.8-Flash-Next-FP8, TP4+EP on 4xGB300, `vllm bench serve`, 2048 input / 256 output, `--ignore-eos`. main (`f46021a7fa`) and the branch (`9f75804588`) ran sequentially on the same node, two server instances each:

TPOT p99 at concurrency 4 improves from 5.67-6.04 ms to 5.57-5.58 ms. Concurrency-1 serve numbers were noisy across instances, so c=1 was A/B'd with interleaved `vllm bench latency` (bs=1, 2048/128): 0.756/0.704 s (this PR) vs 0.756/0.800 s (main) — no regression, as expected since the eliminated copies are nearly free inside a bs=1 CUDA graph.

## Details

- Root cause: the TRTLLM fp8-block kernels consume activation scales in the physical `[K/128, M]` (scale-major) layout, while the MoE per-token-group quant emits `[M, K/128]` row-major, so every layer paid a transpose copy between the quant kernel and the experts.
- The quant kernel's existing `column_major_scales=True` mode already allocates the scale buffer as a contiguous `[G, M]` tensor viewed as `[M, G]`, so on that buffer the experts' `.t().contiguous()` is a no-op returning the same tensor. The change just threads a new `FusedMoEQuantConfig.is_scale_transposed` flag — set by the fp8 oracle only for `FLASHINFER_TRTLLM` + `[128, 128]` blocks — through `no_dp_ep` into `moe_kernel_quantize_input`. TRTLLM expert code is unchanged.
- Scope: only `no_dp_ep` forwards the flag; dispatch-based paths (deepep, naive-dp, fi-nvl) keep row-major scales since their scales cross an all2all dispatch. Other MoE backends are unaffected.
- No accuracy eval: the scale bytes handed to the experts are bitwise-identical (same values, different physical layout), so outputs cannot change; the e2e runs above exercised the modified path at c=1-4.
- Duplicate-work check: nearest open PRs inspected — #59564 (value-only amax reduction inside the quant kernel, orthogonal), #53345 (deepep ep_scatter scale-stride bugfix), #44034 (XPU quant fallback); none touch the MoE activation-scale layout.
