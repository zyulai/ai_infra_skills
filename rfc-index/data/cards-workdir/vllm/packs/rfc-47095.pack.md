# [RFC]: Extension points for backends whose physical layout isn't a permutation of the logical layout (weights, quant scales, KV-cache, MLA, EP)

> AI assistance was used to draft this RFC; a human submitter has reviewed and defends every claim. Code evidence is staged at ROCm/aiter#3885.

### Motivation.

vLLM already has three in-flight efforts that move layout handling in exactly the right direction, and we want to build on them rather than duplicate them:

- **#42082 (Standardize KV-cache Layouts)** — a standard logical KV shape `[L, B, H, N, <content>]` with physical layout selected by a `stride_order` permutation; KV-connectors become backend-agnostic.
- **#8913 (QuantizationConfig / QuantizeMethodBase Refactor)** — decouple checkpoint format from kernel, describe the computation so a dispatcher can pick a kernel that `can_implement` it.
- **#33314 (Apply #8913 to Quantized Linear Methods)** — a canonical `LinearParams` representation plus a per-kernel `process_weights_after_loading` repack/reorder hook.

We've been integrating AMD AITER kernels (CK / ASM / Triton) under vLLM and find these three already cover most of what we need for **linear weights and quant scales**, and the *permutation-expressible* part of KV layout. This RFC is **not** a competing design; it asks whether a handful of remaining extension points — needed by any backend whose physical layout is **not** a permutation/repack of the default — can be folded into those efforts.

Concretely, today the only way to run AITER under vLLM is a translation shim that reshapes/shuffles weights at load and re-`view()`/`permute()`s tensors on every forward pass. The shim is fragile, costs memory/latency, and re-implements logic vLLM owns (TP sharding, accounting, block management). AITER is just our concrete case; the gaps below are general to any backend with a genuinely different native layout.

### Proposed Change.

For each gap we note the existing RFC it extends and why that RFC, as currently scoped, doesn't yet express it.

**1. KV layouts beyond a stride permutation (extends #42082).**
#42082's `stride_order` expresses physical layout as a *permutation* of `[L, B, H, N, C]`. Some decode kernels need layouts that are not permutations of the logical dims:
- a head dim factorized into `[dim/x, x]` micro-tiles (a reshape, not a permutation);
- **K and V using different layouts** (e.g. K rank-5, V rank-4) rather than a symmetric `[2, head_dim]` content;
- **scheduler block size ≠ kernel block size** (kernel supports only a fixed set, e.g. `{256, 1024}`), requiring a virtual↔physical block-table translation.
Ask: let a backend declare a physical KV layout richer than a permutation, and let the framework own the virtual↔physical block-table mapping (so it isn't re-implemented per backend). Since #42082 / PR #42374 plan to remove `get_kv_cache_stride_order` and `get_kv_cache_shape`, it would be good to land this extension in the same redesign rather than after.

**2. MoE weight/scale repacking (extends #33314).**
#33314's canonical representation + per-kernel preprocessing hook is exactly what we want for linear weights (our 16×16 "bpreshuffle" would be a kernel preprocessing step). But it explicitly scopes out FusedMoE, and the bulk of AITER's weight/scale repacking is in MoE (pre-shuffled expert weights, two incompatible layouts depending on the kernel path). Ask: a parallel (not necessarily shared) repack hook for MoE expert weights, or confirmation of where MoE layout repacking is meant to live.

**3. Additional quant-scale axes (extends #8913 / #33314).**
The canonical scale types (per-tensor / channel / block / group) don't yet capture axes some kernels require:
- **scale orientation** (row- vs column-major, kernel-dependent);
- **scale dtype** beyond fp32, incl. UE8M0 / uint8 microscaling;
- **FP8 variant** (`e4m3fn` vs `e4m3fnuz`).
Ask: include these as declarable axes in the descriptor so they don't have to be hand-managed downstream.

**4. Alignment / padding as a declared property (new).**
Several kernels impose hard divisibility (pad hidden/intermediate, pad rows to a multiple of 16/32, MLA ≥16 heads). Today a backend pads into larger buffers and slices back, carrying pad-slack metadata, because TP sharding / KV & weight accounting assume exact model dims. Ask: let a backend declare "physical padded shape ≠ logical shape" so sharding/accounting/loading handle it without per-model glue.

**5. MLA paging extensions (extends #42082).**
#42082 can express the MLA latent as `state_content`, but not: `page_size = 1` token-linear indexing, auxiliary per-layer caches (e.g. a sparse FP8 index cache), or last-page-length metadata. Ask: support these as first-class MLA paging options.

**6. Expert-parallel dispatch contract (new; relates to MoE overhaul, project 45).**
All-to-all EP backends (e.g. MORI) use statically-sized dispatch buffers, per-local-expert token counts, and int32 top-k indices, and can't support some routing modes — differing from vLLM's more dynamic fused-MoE dispatch. Ask: generalize the dispatch contract to allow this metadata shape and a way to declare unsupported routing modes.

**Why this is materially different from the existing RFCs (per the contribution policy):**
#42082 standardizes *permutation-level* KV layout and connector code; #8913/#33314 decouple *linear* checkpoint formats from kernels. None of them currently expresses non-permutation physical layouts, MoE repacking, the extra quant axes, padding-as-shape, MLA page_size-1/aux caches, or the EP dispatch contract. This RFC is the union of those residual gaps, framed as extensions to land *within* the existing efforts where possible.
