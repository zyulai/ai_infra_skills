## PR body
```markdown
In summary, deepseek failed to warm up some kernels, which triggers JIT compilation in the inference will harm the quality. It has very **strong impact for production deepseek serving usecase**, because we don't want any JIT compile when actually serving a customer.

## Motivation

DeepSeek-V4/V4.1 JIT-compile several DeepGEMM kernels on live requests. Under DP + EP every rank waits for the compiling rank, so a few of these in one step exceed VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS (300 s). That raises RPC call to sample_tokens timed out → EngineDeadError, the symptom reported in #41530.

## Detailed purpose
This PR warms the kernels that were missed:

1. The o_proj einsum (fp8_einsum("bhr,hdr->bhd")) was never warmed. wo_a is an is_bmm linear, so DeepGemmFp8BlockScaledMMKernel deliberately does not register it as an fp8_gemm_nt warmup provider, and deep_gemm_warmup covered only fp8_gemm_nt, the grouped contiguous GEMM and Mega-MoE.
M values. relax samples every M % 16 == 1 on top of the existing boundary heuristic. M reaches DeepGEMM's config choice only through ceil_div(M, block_m) and the m <= 16/32/64 thresholds. Every block_m enumerated for a Batched einsum is a multiple of 16 (SM100's swap-A/B branch steps in 16s), so a config can only change at M % 16 == 1. The previous sampling modelled SM90's [64, 128, 256] list and missed BLOCK_M=48/112 on SM100; @adenzhou1350 reproduced the same two on B300.
V4.1 mega attention with FP8 output is a different kernel (FP8QuantizationEpilogue, use_128x4_sfd_layout=True). The warmup carries quantize_output in its data and cache key and builds that layout.
2. The mHC prenorm GEMM's DeepGEMM path (tf32_hc_prenorm_gemm) was never warmed. The JIT registry warmed only the TileLang kernel it replaces when DeepGEMM is available.
The kernel instantiates on (n, k, num_splits, ...) and M is a launch argument, so one compile per reachable split count covers every M.
It is a VllmJitKernel (HCPrenormGemmKernel, kernels/mhc/warmup.py). Each model registers it next to its own mHC warmup, with the split function its forward pass uses: V4 passes compute_mhc_num_splits (raw compute_num_split, now also what _hc_prenorm_gemm_outputs calls); V4.1 passes compute_mhc_pre_num_splits (1/4/16 rounding).
The token bound is what one rank sees: cdiv(max_num_batched_tokens, tp) under sequence parallel, since mHC runs on the sp_shard.
The broadcast weight (k = hidden_size) is registered only on layer 0 of the first PP rank.
So split selection lives in one place per model, and neither model warms a split it cannot reach.
3. Draft kernel warm up is not contained in this scope.


To better understand why the missing happens in the swap case, I put up a diagram illustrating why this would happen. It is like we want to cover missed shape for **swap** case. Following diagram illustrates how shapes are missing for the kernel.
```
The old 218-value M set has these points between 32 and 512 -- and two real holes:

M:  32   64        128  152   192        256    304 320    384         448 456    512
    |    |          |    |     |          |      |   |      |           |   |      |
----+----+----------+----+-----+----------+------+---+------+-----------+---+------+---->
         \__ hole __/            \_ hole _/
          65..127                 193..255

config staircase (steps start only at M % 16 == 1; K@x = config first seen at M=x):

    K@1   K@33  K@65   K@97  K@129 K@161 K@193  K@225 ...
    |-----|-----|------|-----|-----|-----|------|-----|---->
                   ^                        ^
                   |                        |
            BLOCK_M=48               BLOCK_M=112
            swap_ab=true             swap_ab=true
            selected only inside     selected only inside
            the hole                 the hole
                   \________________________/
                              |
                     never compiled at startup
                     ──> compiled on a live request

Root cause: the warmup models block_ms = [64, 128, 256] -- SM90's candidate list --
so it only ever emits multiples of 64 plus wave boundaries.

   what the old model assumes:   64 -------- 128 -------- 256
   what SM100 swap-A/B does:   16 32 48 64 80 96 112 128 144 ... 256
                                     ^           ^
                                   the two that were missed

Why only the swap branch is 16-granular:

   no swap:  MMA's M = block_m  ──> coarse, only 32/64/128
      swap:  D^T = B^T * A^T, so MMA's N = block_m  ──> 16-granular,
             capped at 256 by TMEM's 512 columns
             (in code: umma_n = swap_ab ? block_m : block_n)
```


## Test Plan

1. Unit tests (CPU): `tests/model_executor/test_deep_gemm_warmup.py`, `tests/model_executor/test_mhc_prenorm_gemm_warmup.py`.
2. Kernel-level, on each GPU: compile the prenorm warmup keys into an empty `DG_JIT_CACHE_DIR`, then call `tf32_hc_prenorm_gemm` for every M in 1..16384 with each model's runtime split function and count new compiles; check numerics against an fp32 reference.
3. End-to-end `vllm serve`, previous revision vs this one, one empty `DG_JIT_CACHE_DIR` per run, default config (CUDA graphs on). Snapshot committed cache entries at `/health`, then send one prefill every 32 tokens from 1 to 16384 (concurrency 1, then 16; 1,026 requests) and snapshot again. New entries are compiles that hit a live request.

Environment: the exact merge-base wheel `0.34.0rc1.dev144+g68776b023` plus this PR's files, with the md5 of every overlaid base file checked against the merge-base. Each run used a dedicated MLP pod (4 × GB200 SM100, 152 SMs, nvcc 13.1; 8 × H100 SM90, nvcc 13.0) with no foreign GPU processes before or after. Settings: `VLLM_DEEP_GEMM_WARMUP=relax`, `VLLM_BLOCKSCALE_FP8_GEMM_FLASHINFER=0`, `--max-model-len 20480`.
```
