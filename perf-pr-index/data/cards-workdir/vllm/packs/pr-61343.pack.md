## Overview

Speed up FP8 per-token-group quantization by computing the per-group scale reciprocal once and multiplying, instead of dividing per element. This covers both CUDA group-quant kernels: `per_token_group_quant_8bit` (smem and register-resident schedules) and the fused RMSNorm+group-quant kernel (`layernorm_utils.cuh`), so that all CUDA fp8 group-quant paths share the same reciprocal-multiply numerics. ~1.2-1.3x kernel speedup on GB300 across M=1..32768; ~1-2% e2e TPOT improvement on Qwen3.5-397B-A17B-FP8 (TP4).

## Claims

- 1.15-1.29x faster `per_token_group_fp8_quant` CUDA kernel on GB300 across M=1..32768 (details below).
- All CUDA fp8 group-quant paths (unfused kernel, fused RMSNorm+quant kernel, Triton fallback, UE8M0 path) now use the same reciprocal-multiply numerics; previously the fused and unfused kernels could disagree by 1 fp8 ulp on ~0.05% of elements.
- ~0.6-2.0% e2e TPOT improvement on Qwen3.5-397B-A17B-FP8, TP4, 8k input / 1k output, at concurrency 1-64.
- Accuracy-neutral: GSM8K / GPQA-Diamond deltas within noise (details below).

## Details

- Root cause: `div.rn.f32` is a multi-instruction slow sequence, and the kernel issued it once per *element* when one division per *group* suffices. The kernel's own UE8M0 path already uses reciprocal-multiply (a power-of-two scale makes the reciprocal exact); this PR applies the same transform to the fp32-scale path.
- The per-element division was inherited from the SGLang kernel this file was ported from (#21083); the register-resident path (#55330) kept it so the new schedule stayed bit-exact with the smem one. That invariant is a test convenience, not an accuracy requirement, and is preserved by changing both schedules identically.
- Numerics: this is the same rcp-mul numerics class already shipped by this kernel's UE8M0 path, vLLM's Triton fallback (`_per_token_group_quant_fp8`), and SGLang's production quant kernel.
- Scope: no Python/dispatch changes. The file is also hipified into ROCm builds; the change uses only portable float ops, so ROCm gets the same numerics (not separately benchmarked there).
- Related work: #60903 adds a separate Triton row kernel for prefill-sized inputs (large M only); this PR instead speeds up the existing CUDA kernel at all M and is complementary. No open PR duplicates this change.
- Consistency: the fused RMSNorm+group-quant kernel (`layernorm_utils.cuh`, the target of `RMSNormQuantFusionPass` for block-FP8 models, on both CUDA and ROCm via hipify) is switched to the same reciprocal-multiply. Without this, fused and unfused paths diverge by 1 fp8 ulp on ~0.05% of elements (caught by `test_fused_quant_layernorm` and `test_mamba_prefix_cache`). The fused kernel also drops 4 div.rn per vec4. Per-token fp8 keeps exact per-element division for FBGemm parity; int8 paths are unchanged.

<details>
<summary>Toolchain note: nvcc 13.0 x sm_100 mis-schedules the stock kernel</summary>

All official artifacts (release pipeline nvcc 13.0.2, Dockerfile CUDA_VERSION=13.0.3) target `... 10.0 ...` (no sm_103). nvcc 13.0 targeting sm_100 mis-schedules this kernel's div.rn slow paths: 864 instructions / 3095 static stall cycles vs 568 / 1655 under nvcc 13.1; the shipped wheel runs the stock kernel at 167.6us vs 101.2us for a 13.1 rebuild at M=32768 (sm_100 SASS loads natively on sm_103; verified with CUDA_DISABLE_PTX_JIT=1). This PR's variant is insensitive to the compiler (78.3us on nvcc 13.0 vs 78.1us on 13.1) because it removes the per-element div.rn entirely. Worth a separate build-toolchain discussion; out of scope here.
</details>
