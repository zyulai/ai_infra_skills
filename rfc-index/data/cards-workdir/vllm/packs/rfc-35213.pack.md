## 正文(PRD / 提案全文)

### Motivation.

`EngineClient` (protocol.py) is a single ABC mixing concerns that don't require an inference engine (tokenization, config, health checks) with concerns that do (inference, profiling, cache management, scheduler control, weight transfer).

Any client that only needs CPU-only features is forced to implement or stub all GPU methods. This surfaced the need for a proper protocol split, as discussed in https://github.com/vllm-project/vllm/issues/34407#issuecomment-3934345231

**OpenAIServing Already Shows the Split**

`OpenAIServing.__init__` (base for ALL serving) only extracts CPU-only fields:

```python
class OpenAIServing
    ...
    self.model_config    = engine_client.model_config
    self.renderer        = engine_client.renderer
    self.io_processor    = engine_client.io_processor
    self.input_processor = engine_client.input_processor
```

GPU methods (generate, encode) are only called from specific inference helper methods (`beam_search`, `_prepare_generators`, `_generate_with_builtin_tools`), which are only invoked by inference subclasses (`OpenAIServingChat`, `OpenAIServingCompletion`).

Serving classes that don't do inference, like `OpenAIServingTokenization`, only need the CPU-only group.

### Proposed Change.

**Approach Taken** (implemented in #36166)

Rather than a full protocol split, the implementation uses a self-contained preprocessing class:

- **`OpenAIServingRender`**: mirrors the chat/completion serving path but returns rendered inputs (chat template rendering, tokenization, tool/reasoning parsing) without any inference engine.
- **`vllm launch render`**: new CLI command that spins up a CPU-only server backed by `OpenAIServingRender`.
- **`init_render_app_state()`**: bootstraps `renderer`, `io_processor`, and `OpenAIServingRender` from a `VllmConfig` without an engine client.
- `LaunchEngineClient` (the null-object stub from #34551) was removed; the render path no longer depends on `EngineClient` at all.

The `RendererClient`/`EngineClient` protocol hierarchy is deferred.

**Original Proposal (deferred)**

```
Client(ABC)
├── is_running, is_stopped, errored, dead_error
└── check_health()

RendererClient(Client)          EngineClient(Client)
├── vllm_config                 ├── do_log_stats()
├── model_config                ├── get_supported_tasks()
├── renderer                    ├── generate()
├── io_processor                ├── encode()
├── input_processor             ├── abort()
└── is_tracing_enabled()        ├── add_lora() / remove_lora()
                                └── start_profile() / stop_profile()
```

**What This Enables**

```bash
vllm launch render --model meta-llama/Llama-3.1-8B-Instruct

curl http://localhost:8000/v1/chat/completions/render \
     -H "Content-Type: application/json" \
     -d '{"model": "meta-llama/Llama-3.1-8B-Instruct",
          "messages": [{"role": "user", "content": "Hello"}]}'
```

A future disaggregated deployment where:

- Renderer node (CPU): runs the render server, handles HTTP, tokenization, input/output processing
- Engine node (GPU): handles pure token-in/token-out inference
