## Purpose

Reduce Kimi-K3 TP8 decode latency by running the Q/K/V/G projection concurrently with the F_A/beta -> F_B branch during CUDA graph replay.

This change:

- splits the existing contiguous QKVG/F_A/beta packed weight without copying it;
- uses the shared multi-stream utility to fork and join the projection branches;
- adds TP8-specific CuTeDSL skinny-N and skinny-K GEMMs for F_A/beta and F_B, using TVM FFI tensor conversion and PDL;
- uses tuned skinny GEMMs for QKVG at M=1/2 and the autotuned FlashInfer CuTeDSL BF16 GEMM for M=3..16;
- registers all CuTeDSL compilation during model warmup;
- enables the optimization only for unquantized BF16 TP8, contiguous production shapes, CUDA graph capture, and M<=16. Other TP/DEP configurations and unsupported cases keep the existing sequential path.

### Duplicate-work check

Searched open PRs for `Kimi K3 KDA projection overlap`, `KDA skinny GEMM`, and `Kimi K3 projection multistream`, and checked this head branch.

This does not duplicate #53525. That PR optimizes C=1 intra-kernel PDL handoffs while retaining the projection structure; this PR overlaps the QKVG and F_A/F_B projection branches and covers M=1..16. It also does not duplicate #54151, which targets large-M sequence-parallel AG-GEMM.

## Model Evaluation

End-to-end accuracy on the full `moonshotai/Kimi-K3` (MXFP4) checkpoint, TP8
across two GB300 nodes (SM100), at PR head `23c02bab61`. The overlap is gated on
TP8 and `num_tokens <= KDA_PROJECTION_OVERLAP_MAX_TOKENS == 16`, so the two
configurations below sit on opposite sides of that cap:

- Low-M (`--max-num-seqs 16`, eval concurrency 8): every decode batch is at or
  below the cap, so the multistream projection produces essentially every
  generated token of both evals.
- Full TP8 (`--max-num-seqs 64`, eval concurrency 64/32): steady-state decode
  batches exceed the cap, so this exercises the sequential path as a regression
  check.

GSM8K is 5-shot over `/v1/completions` (temperature 0.6, top_p 0.95); OCRBench is
multimodal chat with thinking effort high (temperature 1.0, top_p 1.0). Reported
scores are GSM8K strict-match exact match and OCRBench Final Score Norm.

| Config | Projection path | GSM8K | OCRBench | Request errors |
| --- | --- | ---: | ---: | ---: |
| TP8, `--max-num-seqs 16` | multistream (overlap) | 96.89% (n=1319) | 88.8 (888/1000) | 0 |
| TP8, `--max-num-seqs 64` | sequential | 95.53% (n=1319) | 89.1 (891/1000) | 0 |

No accuracy regression on the overlapped path: low-M GSM8K lands 1.4 points above
the sequential run and the two OCRBench scores differ by 0.3 point, both within
run-to-run variance for these sampling settings (roughly +/-0.5 point standard
error on GSM8K at n=1319). For reference, an earlier TP8 run of the same recipe
on the same cluster, before this change, scored 95.53% GSM8K and 89.3 OCRBench.
