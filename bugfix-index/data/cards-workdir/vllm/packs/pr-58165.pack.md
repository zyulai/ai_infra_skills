## Fix FlashInfer warmup crash: `autotune(tuning_buckets=...)` must map runtime M **up**, not down

Fixes the engine crash-loop at startup for SM100/SM103 block-scaled cute-dsl linear kernels (`mm_mxfp8` / `mm_fp4`) when speculative decoding is enabled.

### The crash

`kernel_warmup` runs dummy forwards inside `fi_utils.autotune(tuning_buckets=tuning_buckets)`. With spec-decode, the DSpark draft model forward runs at M = `max_num_seqs × k` = e.g. 8 × 3 = **24** — not a bucket value. Boot dies:

```
ValueError: Invalid MXFP8 split-K tactic: ((128, 16), (1, 1), True, False, 4)
```

at `flashinfer/gemm/gemm_base.py:5327` (`CuteDSLMxfp8GemmRunner.forward`), reached from the draft model's `fused_wqa_wkv` GEMM.

Reproduced on DGX Station GB300 (SM103) with vLLM nightly + DeepSeek-V4.1-Flash + dspark k=3; standalone FlashInfer-only repro at https://github.com/flashinfer-ai/flashinfer/issues/5450.

### Root cause

`mm_mxfp8`'s own tuning config maps runtime M to buckets with `map_to_hybrid_bucket_uncapped`, which rounds **up**, and the cute-dsl split-K MMA tile is likewise chosen by rounding M up (`mma_tiler_mn_for_m`: 8/16/32). A tactic tuned at bucket b is therefore valid for every M ≤ b — tune space and apply space agree.

But inside `autotune(tuning_buckets=...)` the autotuner **replaces the op's mapper** with `make_bucket_mapper(buckets, round_map=round_up)` and `round_up` **defaults to False** (floor). So the warmup dummy run at M=24 looks up the **bucket-16** tactic — tile (128,16), split_k=4 — and `forward()` rejects it because `mma_tiler_mn_for_m(24)` is (128,32).

Outside the context (serving, CUDA-graph capture) the op's own round-up mapper is restored, so **only the warmup pass ever crashes**: the engine can never boot, while the identical weights, tactics, and cache would serve fine.

Standalone repro (no vLLM, one process, same cache — all three regimes):

```
inside autotune(tuning_buckets=..., round_up=False [default]):
  M=24 FAILED -> Invalid MXFP8 split-K tactic: ((128, 16), (1, 1), True, False, 4)
  M=12 FAILED -> Invalid MXFP8 split-K tactic: ((128,  8), (1, 1), True, False, 4)
  M=40 FAILED -> Invalid MXFP8 split-K tactic: ((128, 32), (1, 1), True, False,  2)
outside any autotune context (op mapper, rounds up):
  M=24 OK / M=12 OK / M=40 OK
inside autotune(tuning_buckets=..., round_up=True):
  M=24 OK / M=12 OK / M=40 OK
```

### The fix

One line: `round_up=True` on the warmup `autotune()` call, making tune-context mapping equal serving-time mapping. Every cached tactic at bucket b is then applied only to M ≤ b — exactly the envelope both the split-K validator and the small swap-AB base tactics guarantee.

Profiling is per bucket, so tactic choices and the cache file are unchanged; only the dummy run's execution path changes. Verified live on GB300: the crash-looping boot (identical config) boots clean with this change and serves with full CUDA graphs; warmup passes on the pre-existing cache.

### Broader hazard (why this should land even before any FlashInfer-side change)

The base (non-split-K) candidate tactics include swap-AB tiles (128, 8/16/32) whose persistent-kernel `can_implement` requires `kernel_n ≤ tile_n` (kernel_n = token count in swap-AB) — and those tactics get **no apply-time check**. Under floor mapping, a bucket-16 winner applied at M=24 runs silently outside its envelope. The same tactic generator serves `mm_fp4`, so NVFP4 + spec-decode is exposed too. The split-K `ValueError` is just the one place that notices. Filed upstream with full analysis: https://github.com/flashinfer-ai/flashinfer/issues/5450

### Notes for reviewers

- The change is one argument on one line (plus the explanatory comment); the diff is intentionally minimal.
- If maintainers prefer the fix inside FlashInfer (honor the op's mapping direction under bucket override, or size small tiles against `DynamicDim.max`), this line remains a correct, self-contained fix on the vLLM side and can be revisited later.
