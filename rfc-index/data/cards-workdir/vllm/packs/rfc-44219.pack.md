## 正文(PRD / 提案全文)

### Motivation.

This is a direct follow up to https://github.com/vllm-project/vllm/issues/42770, which proposes removing full model torch.compile from vLLM and proposes separating model definitions by hardware type in vLLM.

While the [vLLM models proposal](https://github.com/vllm-project/vllm/issues/42770) addresses a lot of the concerns related to achieving maximum performance for the most popular models on the most popular hardware (specifically measured as how many GW of power is expected to be used for inference overall for the next of couple months) it makes supporting a wide set of models and hardwares more challenging.

In this follow up, we argue that this proposal doesn’t completely serve the whole userbase. In particular:

- There is significant interest in the community for alternative hardwares. We think giving users more choice is good for the community in the long-term.
- Supporting many hardwares across many models is a challenging task; we think sharing parts of the stack between hardware is the simplest and most reliable way to do this. 

We propose to embrace this view of the world while setting appropriate boundaries to ensure this will not get in the way of the top GW users’ optimization.



### Proposed Change.

There should be a hardware-agnostic model definition for all models that is maintained by the community in the core vLLM repository. Hardware backends can choose to use this model definition or they can choose to create their own model definition (as per [the vLLM models proposal](https://github.com/vllm-project/vllm/issues/42770))

For tail models: this is keeping the existing vLLM hardware-agnostic model definitions and the CustomOp mechanism in vLLM.
For head models: this is accepting a hardware-agnostic model definition and PRs to CustomOp-ify it.

There are some options for how we can do this. The first is a hardware agnostic model definition that lives alongside the other models:

```
models/
    deepseek_v4/
        nvidia/
            model.py
        amd/
            model.py
        hw_agnostic/
            model.py
    ...
```


Another option could be just to separate it out the existing code into its own folder and spin off a new folder for the new hardware-specific code:

```
vllm/
    model_executor_hw_specific/
      # new path for best perf on specified HW - nv, amd, xpu
      layers/
      kernels/
      models/
      ...
    model_executor_hw_agnostic/
      # could rename/refactor current model_executor to model_executor_hw_agnostic
      # this folder maintained by the community
      layers/
      models/
      custom_op.py
      ...
```

## Maintenance

We're hoping that some combination of the folks who will benefit from these hardware agnostic model definitions (e.g. hardware vendors, model providers, pytorch team) will coordinate to maintain them.

## Requirements

- The model definition **should be hardware agnostic** and be testable in core vLLM. The definition of hardware agnostic is:
    - The model uses native torch ops
    - The model uses custom ops (see next point) that can be abstracted and designed for dispatch to different hardware platforms.
- **We should keep the CustomOp mechanism** and allow people to add more CustomOps. CustomOp has generally been a good way to identify “operator” boundaries that when backends provide implementations for said operators, it can result in decent performance.
    - This might evolve into vLLM IR style of CustomOp management, because vLLM IR is supposed to be an upgrade to the CustomOp system.
- The model definition should **support fullgraph capture** (with torch.compile), because many alternative backends (TPU, Intel Gaudi, IBM Spyre, CPU) benefit heavily from a fullgraph capture.
- **Isolation**: these hardware agnostic model definitions should not affect the hardware-specific (e.g. nvidia cuda) model definitions.

##  Alternatives

- Use HF Transformers backend. It is not clear if this will suffice. For example:
    - many popular models don’t work out of the box (gpt-oss-120b, qwen3.5, etc)
    - it does not have a CustomOp abstraction
    - it does not guarantee implementations are fullgraph capturable
    - we do see a perf gap from using HF transformers backend vs stock vLLM
- Maintain an out-of-tree set of model definitions. We could do this, but it seems like significantly more work (and maintenance cost) because vLLM already provides a long tail of hardware-agnostic model definitions in core.
