## 正文(PR 描述)

When in quick testing, the accept len go from `3.413 -> 3.894`

When OSL is 2048 using generate,

Before:
len = 3.459, tps = 304.65

After:
accept len = 3.842, tps = 334.12

when add the second commit of this pr,
len = 3.879, tps = 335.94 (the same basicaly)

Firstly, it's wrong to cast correction bias from fp32 to bf16 (confirmed when loading checkpoint values the accuracy of these values change), secondly, the router gemm output needs fp32 output for numerical stability, which is done by trtllm, and the compute dtype is still bf16, thus the performance loss should be mininmal.
