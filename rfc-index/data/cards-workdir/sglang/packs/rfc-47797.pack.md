## 正文(PRD / 提案全文)

## Motivation

Resume the design discussion from #30263 and draft #30264, both closed by inactivity automation. GitHub rejected reopening the original issue. Current main (`a52ee805`) still has no request-level `disable_speculative_decoding` field or consumer. Per-request speculative statistics (including #34814) do not provide an opt-out.

The original draft only transported an unenforced flag. I do not propose restoring that API as a working feature without implementing its execution semantics.

## Proposed scope and alternatives

1. Group opt-out requests into non-speculative scheduler batches, preserving ordering, streaming and KV-cache ownership across batch transitions. This makes mixed request behavior explicit but adds scheduling and execution-path complexity.
2. Use an explicit steps-zero runtime state for batches containing opt-out requests. This could reuse adaptive speculative runtime machinery, but needs a defined mixed-batch policy and correctly matched attention/CUDA-graph state. Changing only the request flag or branching inside the worker is insufficient.

`EAGLEWorkerV2` still has a `speculative_num_steps == 0` path, and `adaptive_spec_params.py` manages runtime transitions. These are investigation points, not proof that a per-request switch is safe.

## Acceptance criteria before a mergeable PR

- Opted-out requests execute no draft-model work and match the non-speculative target output for deterministic sampling.
- Default requests retain existing behavior; specify what happens when both types share a batch.
- Test eager and CUDA-graph execution, streaming/cancellation, batch transitions and KV-cache lifecycle.
- Measure latency/throughput at low and high concurrency; document the scheduling tradeoff.
- Do not accept a public parameter that is silently ignored.

I would like to resume implementation once the mixed-batch contract and preferred approach are agreed. Which of the two approaches best fits the current scheduler/runtime architecture?
