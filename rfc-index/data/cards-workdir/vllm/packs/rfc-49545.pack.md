## 正文(PRD / 提案全文)

### Motivation.

Remote KV cache loading usually completes much faster than local recomputation. However, a rare slow Mooncake `get` may keep a request waiting for up to approximately 60 seconds before returning a failure.

For these outliers, continuing to wait may be more expensive than recomputing the KV cache locally. This RFC proposes a soft-timeout fallback that reduces tail latency without changing the normal remote KV loading path.

### Proposed Change.

Introduce an optional soft timeout for remote KV cache loads, for example 5 seconds.

The proposed flow is:

1. Allocate KV blocks `A` and start loading the remote KV cache into them.
2. If the load finishes before the soft timeout, use `A` normally.
3. If the soft timeout expires:
   - Remove the load from the request's critical path.
   - Keep `A` reserved and unavailable to the block allocator.
   - Allocate a physically different set of KV blocks `B`.
   - Remap the request to `B` and recompute its KV cache locally.
4. Let the original remote load continue in the background.
5. When the original load completes, ignore its result for the request and release `A`.

If additional KV blocks cannot be allocated, vLLM should retain its existing wait or failure behavior.

The feature should initially be opt-in, with configurable limits for:

- The soft timeout.
- The maximum quarantined HBM capacity or number of fallback requests.

The normal fast path remains unchanged. Additional HBM and computation are used only when a remote load exceeds the soft timeout.

Correctness requires that `A` must not be returned to the allocator while the original transfer may still access it. A logical timeout alone must not be treated as proof that the underlying transfer has completed.

### Any Other Things.

This RFC focuses only on reducing request latency through early recomputation. RDMA cancellation and transport-level recovery are out of scope.

This proposal is not equivalent to reducing Mooncake's existing timeout from 60 seconds to 5 seconds. The old destination blocks must remain isolated until the corresponding transfer is known to have completed.

The main expected trade-off is lower tail latency at the cost of temporary HBM usage and duplicate computation for slow outliers.
