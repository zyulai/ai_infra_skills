## Overview

A duplicate `resume_generation()` can hang a data-parallel MoE engine when a request starts a new wave. An idle rank can enter the resume all-reduce while the rank that received the request skips it.

## Claims

- Unpaused ranks skip the resume collective even when they hear about a wave at different times.
- Paused ranks and newly joined Elastic EP ranks still synchronize before stepping. The engine still rejects a resume that arrives while its pause is pending.

## Validation

The regression sends a resume to an idle rank, submits a request to rank 0, then sends rank 0 its resume. For the baseline comparison, restore only `vllm/v1/engine/core.py` from the merge base. Run the test on both trees at `TP_SIZE=1` and `TP_SIZE=2`.

```sh
RAY_ADDRESS=local DP_SIZE=2 TP_SIZE=1 .venv/bin/python -m pytest -q \
  tests/v1/distributed/test_async_llm_dp.py::test_dp_duplicate_resume_while_one_rank_starts_a_wave
```

On B200 GPUs with `ibm-research/PowerMoE-3b`, reverting the production change left only rank 1 logging `setting pause state to UNPAUSED` before pytest reported `+++ Timeout +++`. With the fix, the request finished at both TP sizes. The thread timeout also allows for a cold MoE JIT cache.

For the documentation update, `mkdocs build --strict` built the full site locally and the pre-commit hooks passed on the changed files. Upstream pre-commit and the docs preview both stopped at the contributor check.

## Details

`engines_running` changes when an individual rank learns about work. `ignore_start_dp_wave` is set when the ranks agree to pause and when a new Elastic EP rank joins. Using that flag to guard the all-reduce gives every rank the same decision. [Review discussion](https://github.com/vllm-project/vllm/pull/55229#discussion_r4170893423)

The related change in #59559 moved responsibility for starting waves to the engines. I found no other open PR for the duplicate-resume guard.
