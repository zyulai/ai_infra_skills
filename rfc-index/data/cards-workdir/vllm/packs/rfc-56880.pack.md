## 正文(PRD / 提案全文)

### Motivation.

[NCP-ArchPreview](https://huggingface.co/collections/ArchSpace-Collection/ncp-archpreview) is a decoder-only language-model family that places token-level encoder and decoder towers around a chunk-level high-level model (HLM). Its public Hugging Face checkpoints use the `NCPOlmo3ForCausalLM` architecture and `ncp_olmo3` model type.

Supporting this architecture in vLLM requires more than registering a conventional decoder. The token towers can use vLLM attention and block tables, but the HLM also owns request-local state: an incomplete encoder fragment, per-layer HLM states and K/V tensors, selected concepts, and routed decoder features. That state must remain associated with request IDs across scheduler row reordering, completion, refill, chunked prefill, and recompute preemption. Prefix caching is not correct unless the corresponding HLM snapshot is cached with the token prefix.

The public Stage 2 v1 model also has a matching [NCP DFlash checkpoint](https://huggingface.co/ArchSpace-Collection/NCP_ArchPreview_dolma3_8.9B_Stage2_DFlash2_NCPFlash). Existing vLLM DFlash infrastructure is oriented around other target architectures. NCP DFlash additionally needs target-feature capture from routed decoder layers, request-owned proposal context, and transactional rollback/replay of the hierarchical target state after rejection.

I searched open vLLM issues and pull requests for NCP-OLMo, `NCPOlmo3ForCausalLM`, NCP-ArchPreview, ConceptLM, and NCP DFlash. I did not find an implementation of this model family. The related DFlash issues and PRs cover generic or other-model behavior; they do not implement NCP's hierarchical request-state contract.

Reference implementations prepared for discussion:

- [Target-model backend](https://github.com/vllm-project/vllm/compare/main...LuckySJTU:vllm:dev/ncp-archpreview)
- [DFlash extension stacked on the target backend](https://github.com/LuckySJTU/vllm/compare/dev/ncp-archpreview...dev/ncp-archpreview-dflash)

### Proposed Change.

I propose landing the work in two pull requests after RFC feedback.

#### 1. NCP-OLMo target backend

The first PR would:

- register `NCPOlmo3ForCausalLM` and document all non-DFlash checkpoints in the public NCP-ArchPreview collection;
- load standalone Hugging Face checkpoints, validating the published architecture contract and mapping split Q/K/V and gate/up tensors into vLLM's fused parameters;
- implement the token encoder, chunk-level HLM, routing/product-codebook path, and token decoder while using regular vLLM `Attention` layers for token-tower KV blocks;
- keep HLM state keyed by request ID, with explicit add/remove/reorder/refill/release and recompute-replay behavior through the V2 model-state lifecycle;
- fail closed on unsupported checkpoint variants, prefix caching, tensor or pipeline parallelism, quantized checkpoints, and CUDA graph capture in the first version; and
- add public examples, model documentation, dummy-weight registry coverage, weight-contract tests, and HF-versus-vLLM correctness tests.

The initial target scope is deliberately narrow: TP=1, PP=1, eager execution, and no prefix caching. Token-tower KV remains managed by vLLM, while dense HLM state stays request-owned outside the block manager.

#### 2. NCP DFlash extension

The stacked PR would reuse vLLM's `method="dflash"` integration while adding an NCP-specific speculator and state contract:

- validate and bind the public DFlash checkpoint to its matching Stage 2 v1 target;
- capture the configured target decoder features and load the draft during normal model initialization;
- cache proposal-side context K/V by request ID, project only newly committed suffixes, and prune state on completion or preemption;
- derive proposal width from the active decode batch after completion/refill, without mutating checkpoint configuration;
- trim variable-width proposal suffixes before target verification and reject invalid internal holes; and
- transactionally truncate or restore/replay token, HLM, routed-feature, and draft-cache state after rejection.

The correctness-first default is `sequential_exact`. `intra_chunk_exact` may widen proposals only inside the current safe HLM chunk. A cross-chunk `segmented_kv_approx` mode remains explicit and experimental because proposal-side conditioning and batched target numerics may differ even though target verification remains authoritative.

The initial implementation keeps NCP-specific behavior gated by the public DFlash checkpoint contract. Generic DFlash and non-DFlash speculators retain their existing defaults.

#### Validation completed

- Clean source builds passed for both branches.
- Target tests: 55 passed; registry dummy-weight initialization passed and was not skipped.
- NCP DFlash tests: 88 passed.
- Public Stage 1 and Stage 2 v1 checkpoints passed HF-versus-vLLM greedy-token and top-k-logprob checks and batched-versus-sequential parity.
- Stage 1 passed chunked-prefill, recompute-preemption, continuous refill, and request cleanup checks with more queued requests than `max_num_seqs`.
- The public NCP DFlash checkpoint passed target-only token parity, continuous-refill parity, same- and cross-chunk rollback tests, and a recompute-preemption test that both increased the preemption counter and preserved target tokens, text, and top-k logprobs.
- All 17 non-DFlash checkpoint configs in the public collection matched the accepted contract and exposed the same 842 weight keys.

The following is a short synthetic one-H200 snapshot with greedy decoding, seed 42, three repetitions, and medians. It is included to characterize the current trade-off, not as a universal serving-throughput claim.

| Active batch : configured width | Target-only tok/s | Exact tok/s (speedup, acceptance) | Experimental adaptive tok/s (speedup, acceptance) |
| --- | ---: | ---: | ---: |
| 1:8 | 27.05 | 29.19 (1.079x, 89.10%) | 51.68 (1.910x, 49.46%) |
| 2:8 | 47.25 | 47.95 (1.015x, 89.10%) | 70.69 (1.496x, 49.46%) |
| 4:4 | 79.45 | 75.15 (0.946x, 89.10%) | 102.21 (1.286x, 68.04%) |
| 8:2 | 120.86 | 117.31 (0.971x, 89.10%) | 135.29 (1.119x, 80.67%) |

For a continuous-refill case with 16 requests and `max_num_seqs=8`, target-only reached 68.11 tok/s; exact mode reached 66.39 tok/s (0.975x, 79.37% acceptance); and experimental adaptive mode reached 81.17 tok/s (1.192x, 68.45% acceptance). Both speculative modes produced the exact target-only token sequences in this test.

#### Alternatives considered

- **Out-of-tree plugin:** this would isolate the model code, but the required V2 request-state lifecycle, model-runner feature capture, and DFlash proposal/rollback integration are not exposed as a stable plugin surface.
- **Replay the full HLM state every step:** simpler, but it discards incremental state and substantially increases repeated work.
- **Store HLM state in the token KV block manager immediately:** attractive longer term, but it requires a separate cache payload and copy-on-write contract; treating token KV alone as sufficient would make prefix hits incorrect.
- **Ship only the widest DFlash mode:** rejected because correctness should be the default and the wider cross-chunk mode has a distinct, explicitly experimental state contract.

Questions for maintainers:

1. Is an in-tree model implementation appropriate, or should vLLM first expose additional out-of-tree hooks for request-owned model state and model-specific speculators?
2. Is the proposed two-PR split (target backend, then stacked DFlash support) the preferred review boundary?
3. Should the NCP DFlash settings remain typed fields in `SpeculativeConfig`, or move under a method-specific nested configuration?
4. Is fail-closed prefix caching acceptable for the first PR while a joint token/HLM cache contract is designed separately?
