## 正文(PRD / 提案全文)

### Motivation.

### Current state

vLLM has established support for adapting a batch-uniform speculation depth.
Dynamic SD (#32374) profiles position-level acceptance and ITL offline and
selects a per-step uniform K by goodput at runtime (currently EAGLE-1), and
#45953 extended it to work with full CUDA graphs. Separately, #36657 / #35301
proposed confidence-threshold early exit for drafting, deliberately
batch-uniform: outputs stay fixed-width `[batch_size, K]` with zero padding,
and the PR notes that "a per-request policy would be more efficient but
requires variable-length draft outputs and more complex KV-cache bookkeeping."

The interface question addressed here is orthogonal to all of the above:
representing different effective proposal lengths across requests within the
same batch.

### The gap

Acceptance behavior varies both across workloads and across requests within a
batch. With `deepseek-ai/dspark_qwen3_4b_block7` on Qwen3-4B, mean accepted
length is 6.12 on GSM8K and 3.63 on MT-Bench (block size 7, matching Table 1
of the DSpark paper, arXiv:2607.05147). More importantly for this RFC,
instrumented MT-Bench batches produce per-request confident-prefix lengths
spanning the full 0..7 range within a single step, for example
`[7, 4, 0, 7, 2, 1, 0, 0]`. Accepted-length numbers include the
target-generated bonus token, following the DSpark paper's protocol, whereas
proposal lengths here count draft tokens only.

A uniform K, however well chosen, pays for this within-batch spread either in
wasted verification (K too long for cold requests) or lost acceptance (K too
short for hot ones). The missing piece is not a policy but a contract:
per-request proposal-length metadata and its semantics across the proposer,
model runner, scheduler accounting, async scheduling, and metrics. This is
also the interface boundary left unresolved by several earlier
adaptive-speculation attempts (#28693, #26504, #44885, #43522).

Observed behavior in our prototype, based on vLLM main at `b8c7c8653`:
modifying the per-request `DraftTokenIds` lists changes effective truncation
when async scheduling is disabled, but does not change verification or
scheduler accounting on the default async path, whose draft-token feedback is
consulted for structured-output validation. This is consistent with the
fixed-shape design choice documented in #35301.

### Prototype evidence

As a concrete first consumer we wired the DSpark confidence head, which
DeepSeek ships in the released checkpoints and vLLM currently skips at load
time with the comment `confidence_head is not wired into inference yet`
(`qwen3_dspark.py`). The head is a single `Linear(hidden + markov_rank -> 1)`;
the Markov embedding it consumes is already computed inside
`DSparkSpeculator`'s sequential sampling loop, so the confidence score
requires one lightweight linear projection per draft position. The prototype
preserves fixed tensor shapes and runs under the graph mode used in our test
setup; full compatibility with the default async CUDA-graph path is part of
the proposed infrastructure work, not claimed here. Per-request confident
lengths come out as an int32 tensor copied to host outside capture. A
reference branch with the patch and measurement scripts is linked below.

Reference branch: 
https://github.com/LJX-xixi/vllm/tree/per-request-proposal-lengths-ref
(five focused changes plus unit tests; measurement scripts and raw numbers available on request.)

### Proposed Change.

### Proposed interface and semantics

We propose representing per-request proposal lengths logically, keeping
physical buffers fixed-shape.

For a decode step with maximum speculation depth `K`, the proposer may return:

* `draft_token_ids`: the fixed-shape `[R, K]` tensor, as today;
* `proposal_lengths`: an optional int32 vector `[R]` with
  `0 <= proposal_lengths[r] <= K`.

For request `r`, only the prefix `draft_token_ids[r, :proposal_lengths[r]]`
is semantically present. Positions beyond that prefix must not participate in
verification, KV-cache accounting, output-placeholder accounting, or
speculative-decoding metrics. When `proposal_lengths` is absent, the existing
uniform-K behavior is preserved bit-for-bit.

The length vector is bound to the exact in-flight batch that produced it; in
the async path it must not retroactively modify accounting for any other
batch. Whether a backend physically packs the valid prefixes or keeps padding
is an implementation choice; the interface defines only the logical lengths
and the accounting invariants. This intentionally reframes "variable-length
draft outputs" as a fixed-shape buffer plus a per-request logical length,
which is what our prototype implements.

The main design question we would like maintainer input on: should this
metadata extend Dynamic SD's existing machinery from #32374, or live as an
independent field on proposer/model-runner output consumed by scheduler
accounting? We have a working prototype of the second shape and will converge
on whichever boundary is preferred before opening the PR series:

1. `[Core][Spec Decode]` per-request proposal-length metadata, default
   behavior unchanged, sync and async paths tested, no policy attached.
2. `[Model][Spec Decode]` wire the Qwen3 DSpark confidence head as the first
   consumer, with an off-by-default minimal threshold and a small benchmark.
3. Policies as separate follow-ups.

### Non-goals

This RFC does not propose a default policy, and it makes no performance
claim. Honest measurement from the prototype: on Qwen3-4B on a single L20X up
to batch 64, confidence early stopping did not improve wall clock over fixed
full blocks at any threshold we tried; the DSpark backbone drafts the whole
block in one pass regardless of truncation, and in this regime per-step cost
is nearly flat in verified tokens while lost acceptance is paid in extra
decoding steps. These results show that per-request truncation is not
universally profitable: its value depends on the opportunity cost of
verification capacity, which may be higher for larger targets, saturated
engines, or other adaptive policies, and it is the prerequisite for any
per-request method (SpecDec++-style heads, or the per-request extension that
#35301 explicitly deferred). Accordingly, this RFC proposes an expressive
mechanism, not a performance claim or a policy recommendation; thresholds and
schedulers stay out of scope and default off.
