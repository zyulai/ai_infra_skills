## Overview

Size the KV cache from the GPU memory actually free after CUDA graph capture and warmup, instead of from a pre-capture profiling estimate. The cache's address range is reserved up front with the driver's virtual memory API, and physical memory is mapped into it only once the final size is known. Enabled by default on CUDA and ROCm with the V2 model runner.

Productization of @zhuohan123's demonstration in #47363; replaces #50779.

### Background

The KV cache has to exist before CUDA graph capture, because captured graphs bake in its addresses. So today it is sized from a profiling run that happens before capture and warmup, and everything allocated after that has to be guessed:
- **CUDA graph memory** is either ignored or estimated with a throwaway capture pass, which costs startup time.
- **Warmup and runtime transients** that profiling doesn't exercise, such as attention workspaces, sampler and logprobs buffers, and spec-decode drafts, are covered only by slack.

That slack is the `gpu_memory_utilization=0.92` default: 8% of the device, about 15 GiB of a 192 GiB GPU, left idle to absorb estimation error. When the estimate is too optimistic, the engine runs out of memory at runtime anyway.

### Extensible KV cache

The full KV cache capacity is reserved as virtual address space, with no physical memory behind it. Only the blocks that capture and warmup actually touch are backed with physical pages. After warmup, each worker measures the memory that is really free and the transient peaks it really saw. The engine then commits the final block count in one step, by mapping more physical memory into the same reserved range.

Addresses never move, so the layer views and the already-captured CUDA graphs stay valid. The cache is sized from measurement rather than from an estimate, so the default can use the whole device, keeping a measured transient reserve plus a margin.

## Claims

- **Larger KV cache by default:** 4–10% more KV cache tokens (4.9–11.3 GiB per GPU) across eight models on GB200, most of them 7–10%. The gain comes from no longer needing the 8% slack. At an explicit `gpu_memory_utilization=0.92`, the cache comes out 1–4% *smaller* than today's. It subtracts the CUDA graph and warmup memory it actually measured, which today's path leaves the slack to absorb.
- **Faster engine startup:** no throwaway CUDA graph capture pass to estimate graph memory. Engine init time, excluding weight loading, falls 21–34% (5–34 s); end-to-end startup falls 6–18%.
- **No tuning `gpu_memory_utilization` to avoid OOMs:** the cache size follows what the model, graphs and warmup actually use. The utilization setting remains a cap for sharing a GPU.
- Works with sleep mode, CUDA graphs, spec decode, hybrid models, TP/PP/DP, and the KV connectors listed under "Compatibility". Where a configuration can't use it, it falls back to today's estimate-based sizing automatically. An explicit `--enable-extensible-kv-cache` there is an error.

## Details

### Implementation

- **`ExtensibleTensor`** (`vllm/utils/extensible_tensor.py`, `vllm/utils/vmm_driver.py`):
  - A tensor over a reserved virtual address range, exposed to torch through DLPack.
  - Its segments are backed with physical memory on demand, in driver-granule chunks; newly committed blocks are zeroed.
  - Uses the CUDA (`cuMem*`) and HIP (`hipMem*`) VMM APIs through ctypes.
  - A startup probe falls back to estimate-based sizing where the driver lacks VMM support, or where a HIP runtime has the `hipMemSetAccess` defect.
- **`ExtensibleKVCache`** (`vllm/v1/worker/extensible_kv_cache.py`):
  - Plugs into `allocate_kv_cache` as an allocator hook. It reserves the capacity from the profiled budget and splits it into per-layer (or per-tensor) segments, so kernels and layer views are unchanged.
  - Before capture, only the null block is backed. Warmup commits the blocks it addresses.
- **Sizing** (`gpu_worker._measure_kv_cache_blocks`, `kv_cache_planning.finalize_extensible_kv_cache`):
  - After warmup, each worker reports how many blocks fit. That is its budget less two things:
    - the measured transient peak: the larger of the profiling peak and the warmup peak;
    - a margin of `max(1 GiB, 0.75 × transient peak)`.
  - The engine takes the minimum across workers, and across DP engines, which step in lockstep. It then shrinks the configs and issues one `extend_kv_cache` RPC.
  - Warmup gains a full-budget prefill step and a prompt-logprobs chunk, so their peaks are measured rather than estimated. For MLA models it also runs a prefill over one chunked-context workspace of cached context, which measures MLA's context up-projection for prefix cache hits.
  - With the feature on and `gpu_memory_utilization` unset, the utilization defaults to 1.0; otherwise it stays 0.92. The CUDA graph memory profiling pass is skipped.
- **Sleep mode:** sleep, and `release_kv_cache_memory()`, unmap the physical pages; wake remaps them at the same addresses.
- **Weight updates** (`reload_weights`, weight-transfer sessions): a layerwise update needs transient memory that warmup can't measure, at its peak a few times the largest layer's checkpoint-format size. Before any weight changes, the worker checks free memory against that estimate:
  - If short after a pause that cleared the KV cache (the default RL weight-update flow), it releases the cache's physical memory for the update and remaps it afterwards. Nothing is reserved in normal serving.
  - Otherwise a reload fails before loading if even the largest layer can't fit, and warns if only the estimate doesn't.
- **KV connectors:**
  - The worker-side connector is created after the final extend, so it registers the final memory.
  - Under a connector, segment boundaries are aligned to the driver granule, so RDMA registrations never span physical chunks.
- **Consistency:** every worker and every DP engine agrees on whether the feature is on and on the warmup block count, so they warm up the same steps.

### Compatibility

| Not supported | Behavior | What enabling it would need |
|---|---|---|
| Platforms other than CUDA/ROCm | Off | A `VmmDriver` per platform. XPU looks feasible: Level Zero has all the VMM primitives, but the calls need PyTorch's SYCL context (a small C++ op), and PyTorch's XPU DLPack import would need to accept the mapped pointer. |
| V1 model runner | Off | Only the V2 runner is wired up. Not planned, since V1 is deprecated. |
| `kv_cache_memory_bytes`, `num_gpu_blocks_override` | Off; error if requested | Nothing: an explicit size makes measured sizing moot. |
| HiSparse | Off | HiSparse allocates its own KV cache. It would need to allocate through the extensible allocator hook. |
| Elastic EP | Off | Scale-up launches skip warmup and reuse the profiled size. New ranks would need to adopt the running engines' committed block count. |
| `LMCacheMPConnector` | Off | It shares the cache through legacy CUDA IPC, which can't export VMM memory. Needs POSIX-fd exportable allocations, LMCache's VMM IPC wrapper (`VmmCudaIPCWrapper` / `resolve_kv_wrapper_factory`) in `wrap_kv_caches`, and handling of tensors that span segments. |
| Connectors with `custom_mem_pool` (Mooncake NVLink/BAREX) | Off | The cache must come from the connector's pool. The pool would need to supply physical allocations that can be mapped into the reserved range. |
| ROCm with NIXL, Mooncake or MoRIIO | Off | UCX and ROCr can't yet register or share HIP VMM memory. Fixed upstream in openucx/ucx#12137–#12140 and ROCm/rocm-systems#13989. Once those reach the ROCm image, drop the gate and allocate exportable (POSIX-fd) memory, which is ready in a follow-up commit. |
| HIP runtimes before TheRock 7.12 | Off (probed) | Fixed upstream by ROCm/rocm-systems#2451. Nothing needed on the vLLM side. |
| Models without a KV cache | Off | Nothing to size. |
| Weight reloads without a cache-clearing pause (e.g. `reload_weights` called directly while serving) | On; the reload needs headroom from `gpu_memory_utilization`. Without it the reload warns and may run out of memory, or fails before loading when even the largest layer can't fit | Release only the cache blocks that are free: commit in finer physical chunks, and have the scheduler set aside a range of free block ids for the reload. Chunked MoE weight processing would also shrink what a reload needs. |

+def test_measure_kv_cache_bytes():
+    gib = 1 << 30
+    # 10 GiB were free at startup; 3 GiB of non-KV memory is now resident and
+    # 1 GiB is committed to the KV cache, leaving 6 GiB free. Budget is 9 GiB.
+    common = dict(
+        init_free_memory=10 * gib,
+        free_memory=6 * gib,
+        committed_bytes=1 * gib,
+        margin_floor_bytes=0,
+        margin_fraction=0.0,
+    )
+    # Budget-bound: 9 - 3 = 6 GiB for the KV cache.
+    assert measure_kv_cache_bytes(requested_memory=9 * gib, **common) == 6 * gib
+    # Headroom-bound: at most what is free plus what is already committed.
+    assert measure_kv_cache_bytes(requested_memory=20 * gib, **common) == 7 * gib
+    # The measured transient peak is kept free in full, on either bound.
+    assert (
+        measure_kv_cache_bytes(
+            requested_memory=20 * gib, transient_peak_bytes=gib, **common
+        )
+        == 6 * gib
+    )
+    assert (
+        measure_kv_cache_bytes(
+            requested_memory=9 * gib, transient_peak_bytes=gib, **common
+        )
+        == 5 * gib
+    )
+    # The margin is a share of that peak with a floor, taken off the headroom
+    # (floor or fraction, whichever is larger), never off an explicit budget
+    # that already leaves it free.
+    assert (
+        measure_kv_cache_bytes(
+            requested_memory=20 * gib,
+            transient_peak_bytes=gib,
+            **{**common, "margin_floor_bytes": gib},
+        )
+        == 5 * gib
+    )
+    assert (
+        measure_kv_cache_bytes(
+            requested_memory=20 * gib,
+            transient_peak_bytes=2 * gib,
+            **{**common, "margin_fraction": 0.5},
+        )
+        == 4 * gib
+    )
+    assert (
+        measure_kv_cache_bytes(
+            requested_memory=9 * gib, **{**common, "margin_floor_bytes": gib}
+        )
+        == 6 * gib
+    )
+    # A small explicit budget (0.5 GiB) survives a floor larger than itself.
+    assert (
+        measure_kv_cache_bytes(
+            requested_memory=3 * gib + gib // 2, **{**common, "margin_floor_bytes": gib}
+        )
+        == gib // 2
+    )

+    assert measure_kv_cache_bytes(requested_memory=2 * gib, **common) == 0
