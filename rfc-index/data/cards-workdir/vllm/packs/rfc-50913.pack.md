### Proposed Change.

<meta charset="utf-8"><div data-page-id="IJfRdGKswoPAcoxOIMTuWwpxsne" data-lark-html-role="root" data-docx-has-block-data="true"><h1 class="heading-1 ace-line old-record-id-JiKCdYZINo2bjyxN5V9ue3uhsMb">Proposed changes</h1><div class="ace-line ace-line old-record-id-GTWGd3YluoBTq4xEBsNudIWSspH"><strong>P1 — First-token seeding.</strong> P's <code>NixlConnector.request_finished()</code> returns the sampled token in <code>kv_transfer_params.first_token_ids</code> (the router already forwards it opaquely). When D's KV pull completes, the scheduler seeds the token (<code>append_output_token_ids</code>), emits it immediately, and clamps <code>num_computed_tokens</code> so the next forward produces token#2. Removes the ~58ms recompute from TTFT (only the first ITL absorbs the forward). Flag: <code>VLLM_PD_SEED_FIRST_TOKEN</code>.</div><div class="ace-line ace-line old-record-id-F4Jld0VbDoCov6xC0ngupQ8MsTb"><strong>P2 — Fast KV side channels.</strong> Two ZMQ IPC channels between D's EngineCore and its TP workers: (a) <em>fast dispatch</em> — publish <code>reqs_to_recv</code> right after <code>schedule()</code> so a worker listener thread starts the NIXL read immediately; (b) <em>fast notify</em> — a worker poller detects completion within ~0.5ms and pushes to an EngineCore bridge thread, which aggregates TP ranks, seeds token#1 (P1), and writes the output directly to the output queue. Removes both ~28ms step-boundary waits. Flags: <code>VLLM_PD_NIXL_FAST_DISPATCH</code>, <code>VLLM_PD_NIXL_FAST_NOTIFY</code>.</div><div class="ace-line ace-line old-record-id-YrKcdKSmqoeUicxFYqcuiy0WsDc"><strong>P3 — Concurrent router dispatch + D-side prepare parking.</strong> The router dispatches P and D concurrently: D gets a <em>prepare</em> request (<code>{do_remote_prefill: true, remote_ready: false}</code>), tokenizes, enqueues, prefix-matches and allocates blocks ("arms"), then waits in <code>WAITING_FOR_REMOTE_KVS</code>. When P responds, the router POSTs P's <code>kv_transfer_params</code> to a new D endpoint <code>POST /v1/pd_kv_ready</code>; the API server pushes it straight to the P2 bridge thread, which merges the params and fast-dispatches the pull — no step boundary anywhere on the ready→pull path. Lost notifications hit a timeout (<code>VLLM_PD_PREPARE_READY_TIMEOUT_S</code>) and fall into the existing failed-KV-load path (local recompute). Flag: <code>VLLM_PD_CONCURRENT_DISPATCH</code> (router).</div><div class="ace-line ace-line old-record-id-WwShd2Qfeo42S7xvdbKurRTpsSg"><strong>P3a — Early-arm as a memory/performance trade-off.</strong> Parking without allocating ("late-alloc") gains almost nothing: the step-boundary wait just moves to the ready path (~15ms p50). Allocating at park time ("early-arm") realizes the gain but pins the request's KV blocks for the duration of the prefill (~0.7s at our load).
