## 正文(PR 描述)

## Overview

Fixes three bugs in `csrc/fused_qknorm_rope_kernel.cu`, one commit each, plus a one-line warp barrier (kernel +37/-21, tests +45/-1):

1. The 32-bit QKV offset overflows for large `num_tokens`.
2. Partial NeoX RoPE is corrupted in the multi-head-per-warp kernel (fixes #51049).
3. The NeoX partner lane is wrong when `rotary_dim / 2` is not a power-of-two number of lanes.
4. The multi-head-per-warp kernel now syncs the warp after the cp.async wait, so the cos/sin copied by other lanes is visible on the GPT-J path too. It was not observed to fail; the NeoX path already gets this ordering from the barrier in fix 2.

This supersedes the stale #43166 (bug 1). It overlaps #50903 (bug 2); see Details.

## Claims

- GLM-5.3-Flash at DP4 + EP on H200 starts with its vision encoder enabled. Main hits an illegal memory access in encoder profiling, which runs the ViT on 960,000 patches.
- `token_heads_per_warp` 2/4/8 and auto are bit-identical to the one-head kernel with partial rotary. Main differs on 33-70% of elements and returns NaN at 8.
- NeoX with a non-power-of-two pair offset (e.g. rotary_dim 48 of 128) matches the reference.
- No slowdown with full rotary.

## Details

**1. Offset overflow.** Both kernels computed `tokenIdx * num_heads * head_dim` in `int`. With 48 heads × 64 dims, the row of token 699,051 starts past INT_MAX. GLM-5.3-Flash's ViT hits this when profiling its maximum dummy video. The fix moves `qkv` to the token's row once, in 64-bit math. The per-head offsets stay row-relative `int`; promoting every offset to `int64_t` (#43166's approach) cost 4-6%. Host-side warp counts would overflow only beyond 2^31 (token, head) pairs, which is at least 256 GiB of QKV, so they are unchanged.

**2. Partial NeoX.** Only lanes `< rotary_lanes` entered the NeoX block, but it called `__syncwarp` and `__shfl_xor_sync` with the full mask. On sm_70+, `shfl.sync` waits until the other lanes in the mask execute any `shfl.sync` with the same qualifiers and mask (PTX ISA 9.7.10.6). The lanes that skipped the block met it with the next head's `warpReduceSum` shuffle, which mixed RMS sums across heads.

Now every lane enters the NeoX block, and only the rotary lanes store the result. The non-rotary lanes' cos/sin index stays below `rotary_dim / 2`, so their reads are in bounds. The existing `__syncwarp` now runs on all lanes. It also orders the cos/sin that other lanes copied with cp.async before they are read: a cp.async write is visible only to its own thread after the wait (PTX ISA 9.7.10.28.3.3).

#50903 instead moves the shuffle out of the guard and drops that `__syncwarp`, which leaves those reads unordered.

**3. Partner lane.** `laneId ^ pairOffset` equals `laneId ± pairOffset` only for power-of-two `pairOffset`. Rot 48 of 128 gives 6. The fix shuffles from the explicit lane. It keeps width 32, because the file is also built for ROCm, where the source lane must stay inside the 32-lane group on wave64.

**4. Barrier after the cp.async wait.** The GPT-J path in the multi-head kernel read cos/sin copied by other lanes with no warp barrier after `cp_async_wait_group<0>()`. A `__syncwarp()` is added there. With it, tests pass (66/66) and output is bit-identical to the previous commit at F=1/2/4/8 for GLM ViT rot 64/32 and Ling shapes, NeoX and GPT-J, N = 4,096 and 700,000.

**Tests.** The existing reference test now also runs `token_heads_per_warp=4` and rotary ratio 0.375. A compact large-N test (about 4.5 GiB; skips below 12 GiB free) covers bug 1. Both run in the H200 MIG 35GB Core Operation Kernels job. ROCm was not tested here.
