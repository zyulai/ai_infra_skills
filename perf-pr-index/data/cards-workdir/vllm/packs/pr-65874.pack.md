## Overview

This PR makes two changes to the fused GDN MTP decode kernel:

1. **K=8 support:** DSpark K=8 (9 tokens per request) fell back to the slower Triton path. The kernel now handles 9 tokens. Overlaps with #53070.
2. **Split-V:** at small batch sizes, each value head is split over a cluster of 2 or 4 thread blocks to use idle SMs (SM90+).

With Qwen3.6-35B-A3B and DSpark K=8, this PR increases output throughput over main by 18% on B300 and 13% on H100 with a single request. With 8 or more concurrent requests, the gain is 6% to 9% on B300 (measured up to 128 requests) and 2% to 6% on H100 (measured up to 32 requests).

## Claims

- DSpark K=8 decode steps now use the fused kernel. On main they silently fall back to the Triton delta-rule + gated RMSNorm path in every GDN layer, because the kernel accepts at most 8 tokens.
- The cluster split (SM90+) cuts the fused kernel time at 1 request from 22.3µs to 10.2µs on B300 and from 26.2µs to 14.3µs on H100. From 8 requests on, where it does not split, the kernel is 0.4% to 0.9% faster. It also speeds up K=7 by 8% at c1, which already used the fused kernel.
- MTP3 does not regress: output throughput rises 2% to 3% at c1 and c2, and matches main from c4 on.
- Outputs unchanged: GSM8K and acceptance length match main.

## Details

**9 tokens.** DSpark K=8 verifies 8 drafts plus the bonus token, so `state_indices` has width 9 and `_can_use_fused_gdn_mtp_decode` rejected it. Raising `kMaxMtpTokens` alone is not enough: the kernel assigned one warp per token and has 8 warps, so the 9th token was skipped. Warps now stride over tokens. Static shared memory at 9 tokens with fp32 state is ~45.6KB, under the 48KB static limit.

**Related work.**
- #53070 adds the same 9-token support as a separate width-9 template specialization next to the width-8 one. It has had no activity since Aug 31 and predates the move of the kernel to `csrc/gdn/`. This PR raises the cap in place instead (one kernel, warps stride over tokens). The cluster split does not depend on how the 9-token support lands, so it can be rebased onto #53070 if that one is preferred.
- benchislett/vllm#8 (draft) extends fused GDN verification to 12 and 16 tokens (K=11 and K=15) on SM107, with a separate wide kernel that is used when the width exceeds `kMaxMtpTokens`. It complements this PR: with both, 9 tokens would use the kernel changed here and 12 or 16 tokens the wide kernel.
- #54612 speeds up the Triton spec-decode recurrence for Qwen3-Next, which is the path that DSpark K=8 falls back to on main. This PR moves K=8 off that path to the fused CUDA kernel.

**Cluster split.** At small batch sizes the kernel launches one CTA per (request, value head), e.g. 32 CTAs on 148 SMs at batch size 1. On SM90+, each head's V rows are split over a cluster of 2 or 4 CTAs (`blockIdx.z`) while the grid still fits in one wave at 2 CTAs per SM. Each CTA loads and updates its slice of the state. The gated RMSNorm sums the partial sums of squares of the cluster through distributed shared memory, with a final cluster barrier so no CTA exits while others read its shared memory. Without a split, the kernel keeps its single-pass epilogue, so batch sizes of 8 and more are unchanged. On B300 and H100 (HV=32) the split is 4 up to 2 requests, 2 at 4 requests, 1 from 8 requests.

**Tradeoffs and limitations.**
- The split choice is a host-side heuristic from the SM count, no tuning table. It queries two device attributes on the host per launch, with no GPU sync.
- SM80 to SM89 never split. There, the split kernels compile to a trap stub to keep them out of the binary.
- Validated on B300 and H100 only. SM100 and SM120 take the same path but were not tested.
- Each kernel instantiation now has three split variants. Compiling this file for all 7 target archs (one nvcc 13.0 call with `--compress-mode=size`) takes 71s instead of 36s, and the object grows from 0.41MB to 0.90MB.
- Mixed prefill and decode batches still use the unfused path, as before. They are CUDA graphed on main.
