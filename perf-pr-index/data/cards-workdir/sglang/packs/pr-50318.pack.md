# [Perf] qwen4-exp: gather prefill PLE rows on the host for the file-backed table

## Motivation

With `--ple-offload-backend file` (#37068), Qwen3.8-Flash-Next keeps its 47.7 GiB PLE n-gram table in a file-backed mmap that the gather kernel reads directly. Since #48689, that includes discrete GPUs that read pageable memory through HMM, for example an RTX 50-series card on the open kernel modules. Together with paged experts (#42557, #48642, #49195) this serves the full model on a 16 GB card.

On such a GPU, every table row whose page the GPU has not mapped yet is a page fault the driver serves one at a time, about 0.5 ms per page. A prefill gathers 16 rows per token, mostly from different pages. For a ~1.5k-token prompt that is 17-21k distinct rows, and the gather kernel took **9-13 s** on first sight, against 0.4 s once the pages were mapped (RTX 5070 Ti). The WILLNEED hint the file backend already sends for prefill-sized gathers brings the pages into the page cache, but the GPU still faults each one into its own mapping. This was most of the time to first token.

A GPU that reads pageable memory through the host's page tables (ATS, as on GB10 / DGX Spark) does not take these faults one by one, so this PR leaves it alone.

## Modifications

- `qwen4_exp.py`, `Qwen4ExpPinnedHostEmbedding.gather`: a prefill-sized gather (at least `PLE_FILE_PREFETCH_MIN_ROWS` = 2048 ids, the threshold the prefetch hint already uses) from the file-backed table, on a GPU that faults pageable pages, reads its distinct rows on the host (`index_select` from the mmap'd table into pinned memory), copies them to the GPU in one transfer and runs the **same Triton kernel** over the staged rows with the ids remapped into them (ids outside the TP shard stay outside, so they still give zero rows). The kernel converts the staged rows exactly as it converts the table's, so the output bytes are unchanged.
- Before the host copy, `posix_fadvise(WILLNEED)` over the staged rows' pages, through a read-only descriptor of the table file opened once where the host path is on (one call per run of adjacent pages, `advise_rows_willneed` in `qwen4_exp_ple_table.py`). The server runs torch with one thread and the mapping is `MADV_RANDOM`, so without it the copy reads each cold row as its own 4 KiB read, one after another; with it the reads are in flight together.
- Unchanged, the kernel reads the table as before for:
  - decode-sized gathers;
  - gathers during CUDA graph capture;
  - the pinned backend;
  - GPUs that read through the host's page tables, or cannot be queried.
- `qwen4_exp_ple_table.py`: `device_faults_pageable_pages()` asks CUDA for `cudaDevAttrPageableMemoryAccess` (1) and `cudaDevAttrPageableMemoryAccessUsesHostPageTables` (0), sharing the attribute query with the existing `device_reads_pageable_memory()`. It is read once when the layer is built. The host path does not depend on `SGLANG_QWEN4_PLE_FILE_PREFETCH`.

## Accuracy Tests

- New GPU test (`test_qwen4_ple_offload.py`), bf16 and FP8 tables, sharded (TP 2) layer:
  - a 4096-id prefill gather through the host path is byte-identical to a gather from the source rows, covering repeated ids, both shard edges, and ids outside the shard;
  - a gather where no id falls in this rank's shard gives zero rows;
  - a decode-sized gather stays in the kernel.
- New GPU control: on a GPU that reads through the host's page tables, a prefill-sized gather stays in the kernel, with the same bytes.
- New CPU tests (`test_qwen4_exp_ple_table.py`, a fake CUDA runtime answering the attribute query): HMM faults, GB10 does not, no pageable access does not, an unqueryable runtime does not.
- New CPU tests for the WILLNEED advice: adjacent pages merge into one call, a row spanning two pages advises both, no rows means no call, a failed call stops the loop, and the kernel accepts the advice on a real table file. The GPU host-path test checks that each staged gather advised exactly its rows.

  - With the WILLNEED call and the merging of adjacent pages removed, exactly the GPU host-path test (both dtypes) and the merging test fail.
- Full model, Qwen3.8-Flash-Next-FP8 with paged experts on the RTX 5070 Ti, with this PR: GSM8K (200 questions, thinking off) **0.98**, 2 of 200 answers cut at the token limit; the disk tier without this PR scored 0.975 at the same settings. This ran before the WILLNEED hint was added; the hint only schedules reads and the staged bytes are covered by the tests above. Greedy text is not a usable check here, because the model's output already differs between two starts of the same build on this card.

+    """Queue the page-cache reads of ``rows`` of the file-backed table open as ``fd``
+    and return once they are queued: ``posix_fadvise(WILLNEED)``, one call per run
+    of adjacent pages.
+
+    The host gather copies its rows on one thread (the server runs torch with one
+    thread) from a ``MADV_RANDOM`` mapping, so without this each cold row is its own
+    4 KiB read from storage, one after another. Advised first, the reads are in flight
+    together and the copy finds the rows in the page cache. Advisory: returns the number
+    of pages advised, and stops at the first call that fails.
+    """
+    global _WILLNEED_FAILED
+    if rows.numel() == 0:
+        return 0
+    first = rows.to(torch.int64) * row_bytes
+    pages = torch.cat(
+        [first >> _PAGE_SHIFT, (first + row_bytes - 1) >> _PAGE_SHIFT]
+    ).unique(sorted=True)
+    run_starts = torch.ones_like(pages, dtype=torch.bool)
+    run_starts[1:] = pages[1:] != pages[:-1] + 1
+    starts = torch.nonzero(run_starts).flatten()
+    lengths = torch.diff(starts, append=starts.new_tensor([pages.numel()]))
+    advised = 0
