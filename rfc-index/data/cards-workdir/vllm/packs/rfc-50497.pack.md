## 正文(PRD / 提案全文)

## Motivation

MLA prefill with existing context gathers paged latent KV into a fixed workspace, up-projects it, attends, and merges the partial into the running output. The schedule is **batch-column shaped** — the workspace is divided evenly across all prefills, and every iteration processes the same context window of **every** prefill (`build_mla_chunked_context_metadata()`, `vllm/model_executor/layers/attention/[mla_attention.py](https://github.com/home/LucasWilkinson/.t3/worktrees/vllm/t3code-da61773b/vllm/model_executor/layers/attention/mla_attention.py)`):

```python
max_context_chunk = workspace_size // num_prefills_with_context   # even split
max_context_chunk = round_down(max_context_chunk, block_size)     # gather kernel requirement
assert max_context_chunk > 0
num_chunks        = cdiv(max_context_len, max_context_chunk)      # longest request drives it
```

That bought two nice properties: workspace size is bounded and predictable, and since every chunk spans the whole prefill batch, the context partial is shaped exactly like the new-token (suffix) partial, so merging is one whole-batch `merge_attn_states` with no index bookkeeping. It's now causing problems on two fronts.

**1. Poor scheduling on heterogeneous batches.** With a 64k workspace and contexts `[60k, 1k × 7]`, `mcc = 8k` and we run 8 iterations; iterations 2–8 gather only the long request's rows — ~12% workspace utilization per launch. Every iteration also runs attention over *all* prefill queries, merges over *all* prefill tokens, and pays a `mask_empty_context` Triton kernel to neutralize requests whose context is already exhausted. And `mcc = W / num_prefills` means chunks shrink as the batch grows.

**2. Workspace memory is coupled to `max_num_seqs × block_size`.** Since every prefill needs its own slice, `determine_chunked_prefill_workspace_size()` floors the workspace at `max_num_seqs * block_size`, overriding the deliberate 64k cap (documented in-code as ≈144 MB workspace + ≈3 GB transient up-projected context). This is being hit on **Kimi K3** (reported by @wzhao18): HMA raises the attention block size to cover the KDA state page size, giving `block_size = 1536` @ TP8 and ~11000 @ DEP16 — at DEP16 with `max_num_seqs=32` the floor demands ~352k rows, **5.5× the cap**, forcing users to hand-tune `max_num_seqs` down for reasons unrelated to the scheduler. 

## Proposed Change.

Replace the `[num_chunks × num_prefills]` grid with a **flat list of per-request chunks**, matching the indexer / sparse-MLA shape:

```python
@dataclass
class ContextChunk:
    req_start, req_end: int        # prefill-local request range
    token_start, token_end: int    # query tokens of those requests
    starts, seq_lens: Tensor       # per-request context offset / rows this chunk
    cu_seq_lens, token_to_seq, cu_seqlens_q: Tensor
    is_continuation: bool          # first request was already partially processed
    # + DCP: per-rank local starts / padded lens
```

**Policy:** greedily pack whole requests until the workspace is full; split a request only when it doesn't fit.

- **Phase 1** — split only when a request alone exceeds the workspace (indexer-identical). A request is then either wholly inside one chunk (single init write, no merge) or alone across N sub-chunks (init + N−1 merges over just its own tokens).
- **Phase 2** — also split the tail request to fill the workspace, giving optimal chunk count `ceil(Σ context / W)`. Chunks are emitted in request order, so only a chunk's *first* request can be a continuation: one request-slice merge plus one bulk init.

The cost is the index bookkeeping, chunks no longer align with the suffix partial so context writes/merges become per-token-slice. In exchange:

- Full workspace per launch regardless of batch composition; attention/up-projection/merge charged only to the chunk's requests. Merge work drops from `num_chunks × all_prefill_tokens` to `Σ chunk tokens`.
- `has_empty_context` / `mask_empty_context` deleted — empty spans can't occur by construction.
- **Workspace floor drops from `max_num_seqs × block_size` to one page**, making workspace memory independent of `max_num_seqs` (~5.5× less for Kimi K3 @ DEP16). Huge pages degrade gracefully: a chunk just covers fewer requests instead of asserting.
- Workspace stays independent of `max_model_len`; a long request's context is still processed in workspace-sized pieces.
