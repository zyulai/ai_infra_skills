## 正文(PRD / 提案全文)

### Motivation.

**I (@algebra-MCX) propose to add DBO support to the `deepep_v2` all2all backend on top of Model Runner V2 (MRV2), and would be glad to work on the implementation and validation if maintainers are open to it.**

`deepep_v2` is already on main, but `--enable-dbo` cannot be combined with it. The tracker [#62033](https://github.com/vllm-project/vllm/issues/62033) plans to retire `deepep_low_latency` and `deepep_high_throughput`. If that happens first, `nixl_ep` would be the only CUDA backend that supports DBO. This issue closes that gap.

There is an earlier prototype, [#52177](https://github.com/vllm-project/vllm/pull/52177), but it was written against Model Runner V1 and has had no review since August. This issue proposes to redo it on MRV2 instead of rebasing it.

#### Current vLLM behavior

At `15166efabb4d7f27eaf807ee8e1c7454fd188886`:

| Layer | Behavior |
| --- | --- |
| Config | On CUDA, the `use_ubatching` check in `vllm/config/vllm.py` allows only `deepep_low_latency`, `deepep_high_throughput` and `nixl_ep`. |
| Backend | `deepep_v2.py` already keeps one handle per microbatch (`self.handles` indexed by `dbo_current_ubatch_id()`), and forces combine to be synchronous under DBO (`combine_async = do_async and not dbo_enabled()`). |
| Backend | It has no `dbo_yield_*` / `dbo_switch_*` calls and does not override `supports_dbo()`. `modular_kernel.py` asserts `prepare_finalize.supports_dbo()` when DBO is enabled. |
| #52177 | +52/-8 in 4 files. It adds the yield/switch calls around dispatch/combine and the allow-list entry, and touches `gpu_model_runner.py` (the V1 runner). It predates [#52781](https://github.com/vllm-project/vllm/pull/52781) (v2 async finalize), so it no longer applies cleanly to the current `deepep_v2.py`. It has no description, no tests and no human review. |

### Proposed Change.

**Scope of the first slice:** single node, DP/EP, CUDA, eager DBO on MRV2. FULL CUDA Graph DBO and multi-node come after that.

1. **Execution model.** Port the yield/switch schedule from #52177 onto the current `deepep_v2.py`: capture the previous event on the compute stream, yield to the other microbatch, run dispatch/combine on the comm stream, then switch back. Keep the existing synchronous combine under DBO. Implement `supports_dbo()` and add `deepep_v2` to the CUDA allow-list only after the steps below pass.
2. **MRV2 integration.** Wire this into the MRV2 microbatching path instead of the V1 runner changes in #52177. I will check which of those V1 changes (for example the profile run with `allow_microbatching=False`) are still needed in MRV2.
3. **Buffer and event lifetime.** Make sure the buffers and events of one microbatch's dispatch/combine cannot be reused while the other microbatch still reads them. [#60735](https://github.com/vllm-project/vllm/pull/60735) fixed the same class of problem for the v1 high-throughput buffer, so I will start from that approach.
4. **CUDA Graph.** Check graph capture with two microbatches. If the first slice is not safe under capture, keep DBO eager for this backend and say so in the config check.
5. **Tests and benchmark.** Unit tests for per-microbatch handle indexing, `supports_dbo` and the allow-list. An end-to-end A/B on 1 node with DBO on/off, plus a trace.

Out of scope: DeepEP v2.5 migration (ElasticBuffer → EPBuffer, tracked under #62033), changing DeepEP kernels, SBO ([#64776](https://github.com/vllm-project/vllm/issues/64776)).

#### Completion criteria

- [ ] DBO off: code path and outputs unchanged for `deepep_v2`.
- [ ] Unit tests: per-microbatch handle indexing, `supports_dbo`, config allow-list.
- [ ] Multi-GPU, DP/EP, eager DBO on MRV2: identical outputs/logprobs with DBO on/off for one MoE model, and no hang across repeated steps with uneven microbatches.
- [ ] `vllm bench serve` throughput/TPOT with DBO on/off, plus a trace showing dispatch/combine overlapping the other microbatch's compute.
- [ ] Result of the CUDA Graph check, either supported or rejected with a clear error.
