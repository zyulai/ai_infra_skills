## Motivation

#38851 fixed QSA sparse-decode corruption with three changes:

- zero-filling the scratch tail;
- int64 pool offsets;
- dequantizing FP8 pool rows into a BF16 scratch.

The first two fix the bug. The third was a conservative choice: it makes TRTLLM-gen decode always run BF16-q + BF16-KV.

FlashInfer's `trtllm_batch_decode_with_kv_cache` supports BF16-q + FP8-E4M3-KV. With an FP8 pool, keeping the packed scratch in FP8 halves gather and attention KV traffic and removes the dequant from `fused_kv_prepare`.

## Modifications

- `_forward_trtllm_sparse` allocates the packed K/V scratch in FP8 when the KV pool is `float8_e4m3fn` and the device is SM10x. Otherwise it uses the query dtype, as before.
  - The query stays BF16.
  - The scratch cache is already keyed by dtype.
- Unchanged:
  - the zero-fill, int64 offsets and scale-free handling from #38851;
  - BF16 pools;
  - the FA2/FA4 fallback;
  - prefill;
  - SM120.
- `test_qsa_fused_kv_prepare` and `test_qsa_strided_zero_fill` now cover FP8 pool → FP8 scratch.

## Accuracy Tests

Qwen3.8-Flash-Next-NVFP4 on VR200: TP1, FP8 KV, FP8 QSA indexer, NEXTN MTP (3 steps, 4 draft tokens).

Sampling: temperature 1.0, top_p 0.95, top_k 20, `max_new_tokens` 131072. No sample reached the length limit.

- Output length is unchanged (+0.15%).
- Attention output error against an FP32 reference is the same on both paths, about 2.1e-3. It does not grow with KV length up to 64K and beyond.
