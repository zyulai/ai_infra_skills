## Motivation

Part of the MoE refactor roadmap (#8715). The roadmap entry

> [ ] `DeepEPMoE.forward_*`
>   - [ ] `flashinfer_cutedsl.py` + `modelopt_quant.py`

calls for retiring the legacy DeepEP fused-MoE forward path that bypasses the unified `MoeRunner` framework. This PR deprecates the last two pieces of that path: `DeepEPMoE.forward_flashinfer_cutedsl` and `ModelOptNvFp4FusedMoEMethod.apply_without_routing_weights`.

## Modifications

The CuteDSL v1 (DeepEP low-latency + NVFP4) path now dispatches through `MoeRunner` like every other migrated backend, mirroring the pattern from #11211 / #12054 / #16685.

- **`python/sglang/srt/layers/moe/moe_runner/flashinfer_cutedsl.py`** — single unified `CuteDslFp4MoeQuantInfo` dataclass now serves both the existing `@register_fused_func("none", "flashinfer_cutedsl")` (v2 standard, drives `CuteDslMoEWrapper.run`) and the new `@register_fused_func("deepep", "flashinfer_cutedsl")` (v1 DeepEP LL, drives `flashinfer_cutedsl_moe_masked`). `wrapper` is `Optional` and absent on the v1 path; `use_nvfp4_dispatch` / `down_gemm_overlap_args` default v2-safe. Scale fields are named `a1_scale` / `a2_scale` so the same payload reads consistently in both fused functions.
- **`python/sglang/srt/layers/quantization/modelopt_quant.py`** — `create_moe_runner` no longer bails out for v1; it always builds a `MoeRunner`. `apply` gained a `_is_cutedsl_v1_deepep` branch that constructs the unified quant_info from the layer's swizzled blockscales / alphas / scale-quants and calls `self.runner.run(...)`. `apply_without_routing_weights` is removed along with its sole `DownGemmOverlapArgs` import. The top-of-`apply` reads of `dispatch_output.{hidden_states,hidden_states_scale,topk_output}` are deferred into the branches that consume them, since `DeepEPLLDispatchOutput` has no `topk_output` attribute.
- **`python/sglang/srt/layers/moe/ep_moe/layer.py`** — `flashinfer_cutedsl + modelopt_fp4` is added to the `deprecate_flag` group so `forward_impl` / `run_moe_core` route through `super()` and the unified `quant_method.apply` path. `forward_flashinfer_cutedsl`, its branch in `run_moe_core`, and the now-dead exception in the low-latency DeepGEMM init guard are removed.
- **`python/sglang/srt/layers/moe/moe_runner/runner.py`** — drops the `assert self.fused_func is None` from `set_overlap_args` / `clear_overlap_args`. With a fused-func backend in play, overlap args are still stored on the runner and read by `apply` for inclusion in `quant_info` — that's how SBO's `down_gemm_overlap_args` reaches the masked-GEMM kernel.
- **`test/registered/moe/test_cutedsl_moe.py`** — docstring touch-up referencing the new `@register_fused_func` entry point.

The v1 vs v2 weight-layout split (v1: `[Gate, Up]` non-interleaved + swizzled scales; v2: `[Up, Gate]` interleaved + MMA scales) is preserved via the existing `_is_cutedsl_v1_deepep` / `_is_cutedsl_v2_standard` properties in `process_weights_after_loading` and `load_up_proj_weight_first`.

## Speed Tests and Profiling

`bench_one_batch` on 4×GB300, dummy weights, single MoE layer overridden to `n_routed_experts=24` (6 local @ EP=4, under the FlashInfer kernel's `num_experts<=8` cap when `dst_signals` is set), `--cuda-graph-bs 512`, `SGLANG_DEEPEP_NUM_MAX_DISPATCH_TOKENS_PER_RANK=1024`, **1024 decode steps per config** (median over 1024 samples, ~2× tighter standard error than the earlier 256-step run). Each invocation runs a leading bs=64 batch as warmup (discarded), so the first measured config doesn't absorb CUDA-graph-capture / NCCL-warmup / CuteDSL-JIT cost. `SGLANG_DEEPEP_BF16_DISPATCH=0` keeps the baseline branch on its legacy `DeepEPMoE.forward_flashinfer_cutedsl → apply_without_routing_weights` path.

Baseline used: commit `be3c42578` (parent of this branch) + one cherry-picked fix `Defer apply() top-level dispatch_output attr reads` (preexisting `DeepEPLLDispatchOutput.topk_output` crash in baseline's `apply` when `BF16_DISPATCH=1` / `deprecate_flag=True`; orthogonal to the refactor itself).

The refactor is **consistently faster across all eight configurations** (−0 to −9.5% latency, mean −5%, with no point worse than baseline). The kernel call site (`flashinfer_cutedsl_moe_masked → grouped_gemm_nt_masked`) is byte-for-byte identical between branches and replays the same GPU ops from captured CUDA graphs — the win is entirely on the Python host side, where the refactor:

1. **Short-circuits 5–10 conditional ops per decode step.** Legacy `DeepEPMoE.run_moe_core` walks `_is_npu` / `format_is_deepep_normal` / `format_is_deepep_ll` / `quant_config is None` / `use_w4afp8` / `get_moe_runner_backend().is_flashinfer_cutedsl()` / `quant_config.get_name() == "modelopt_fp4"` plus a `combine_input_wrapper` ternary + instantiation every step. Refactor collapses this to `if self.deprecate_flag: return super().run_moe_core(dispatch_output)`.
2. **Avoids `nn.Module.__setattr__` for SBO overlap args.** Baseline's `FusedMoE.set_overlap_args` writes `self.down_gemm_overlap_args` on the `DeepEPMoE` layer (`nn.Module.__setattr__` runs parameter/submodule registration checks). Refactor's write goes to `MoeRunner.down_gemm_overlap_args` on a plain Python object — a few microseconds cheaper per SBO hook fire.
3. **Cheaper dispatch indirection.** Legacy: bound-method `forward_flashinfer_cutedsl(...)` → bound-method `apply_without_routing_weights(...)` → kernel. Refactor: bound-method `apply(...)` → bound-method `runner.run(...)` → module-level function `fused_experts_deepep_to_flashinfer_cutedsl_fp4(...)` → kernel. The last hop in the refactor skips descriptor lookup / instance binding.

Each saves a few µs/step; with ~3 ms decode steps the total lands in the 0–10% band the table shows. (An earlier 256-step run sat the deltas in ±5% noise — the refactor was still ≥ baseline at every config but the magnitude was within run-to-run jitter. 1024 samples per median is enough to see the consistent direction.)

### SBO wiring verification

In each branch, SBO-on adds ~0–0.4 ms (0–10%) over SBO-off at the same batch size — that's the SBO fixed event/signal overhead exercising the `dst_signals` path. The fact that SBO-on differs from SBO-off in *both* branches by the same shape confirms `down_gemm_overlap_args` is correctly propagated through the new `quant_info` field; if the refactor were dropping the overlap args, SBO-on and SBO-off would be indistinguishable on the refactor branch.

A larger-window SBO measurement is currently blocked upstream: the FlashInfer `grouped_gemm_nt_masked` kernel asserts `num_experts<=8` whenever `dst_signals` is non-`None`. Real DSv3 with EP=4 has 64 local experts, so SBO on the full-stack production workload requires EP=32+ (out of scope for this PR).
