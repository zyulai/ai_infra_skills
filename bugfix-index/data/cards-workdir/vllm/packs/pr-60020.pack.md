## 正文(PR 描述)

## Overview

Follow-up to [#51792](https://github.com/vllm-project/vllm/pull/51792), which added this warning. `AutoWeightsLoader` emits it whenever a checkpoint weight's dtype differs from the parameter it lands in. A parameter declared wider than the checkpoint is a deliberate choice and the copy is exact, so that line reports nothing and buries the narrowing cases it was added for. Log the float widenings that cannot change a value at DEBUG instead of WARNING; every other mismatch still warns exactly as before.

## Claims

- A 48-layer Qwen3.x emits this warning 36 times at every start, once per linear-attention layer, for fp32 decay accumulators reading a bf16 `A_log` — counted from 180 occurrences over 5 starts in a serving log. All 36 are exact widenings, so the change is expected to log them at DEBUG instead; the post-change count was not measured on a model run.
- No other warning changes: the condition only subtracts from the cases that already fired.
- The conversions moved to DEBUG are exact for every finite input, not approximately: all 63,488 finite fp16 and 65,280 finite bf16 bit patterns round-trip through fp32 and fp64 unchanged, and fp32 round-trips through fp64.
- Nothing about loading changes — same values, same returned names. Only the level of the line changes; it is still logged, at DEBUG.
- Every other dtype mismatch still warns, including the fp8 pairs whose range looks wider but whose subnormals are shorter.

## Validation

On the branch point (`92044241a0`) and this PR, on CPU: load one parameter through `AutoWeightsLoader` for each stored → declared pair and record the level of the `Attempted to load weight` line.

| stored → declared | before | after |
| --- | --- | --- |
| `bfloat16 → float32`, `float16 → float32`, `float32 → float64` | WARNING | DEBUG |
| `float32 → bfloat16`, `float16 → bfloat16` | WARNING | WARNING |
| `float8_e4m3fnuz → float8_e4m3fn` | WARNING | WARNING |

`pytest tests/models/test_utils.py`: 9 passed, the same tests as the branch point.

Exhaustive check of the pairs moved to DEBUG, run outside the suite: every finite fp16 and bf16 bit pattern cast to fp32 and to fp64 and back compares bit-identical, and none of them loses a value at `tiny/4`, `±max`, `1e-30` or `0.1`. Across the 8 float dtypes checked, 56 ordered pairs, the 5 widenings moved to DEBUG lose nothing at the probed values.

No model run, no multi-GPU, no performance measurement.

## Details

**Why a whitelist and not a predicate.** Comparing what the two formats hold reads as the general answer and is not. `eps`, `max` and `min` describe the normal range, so they miss the subnormal reach: `float8_e4m3fnuz` has the same 3 mantissa bits and a smaller `max` than `float8_e4m3fn`, which makes it look strictly narrower, but its exponent bias is one higher, 8 against 7, so its smallest subnormal is 2⁻¹⁰ against 2⁻⁹ and `0.0009765625` loads as `0.0`. A predicate built on those three fields calls that cast lossless and demotes a warning that matters. `torch.finfo` exposes no subnormal bound to repair it with, and the existing `is_lossless_cast()` in `vllm/utils/torch_utils.py` compares `resolution`, `min` and `max`, and returns `True` for this very pair, so reusing it would carry the same gap. Listing the widenings that are exact by construction — fp16, bf16 or fp32 into fp32 or fp64 — is smaller and easier to verify at this scope.

**Relation to existing work.** [#51836](https://github.com/vllm-project/vllm/pull/51836) proposes config-driven changes to Qwen parameter dtypes, which is separate work on the parameters themselves; it is not landed, and it would need a config field present in each affected checkpoint. This PR changes the log level only: known-lossless widenings log at DEBUG instead of WARNING, every other dtype mismatch still warns, and no parameter or loaded value moves.
