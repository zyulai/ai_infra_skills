## Overview

Serve ModelOpt INT8_PB_WO (`quantization="modelopt_int8"`, added in #65272) on ROCm by teaching the ROCm Triton WNA16 kernel 8-bit weights. Today ROCm rejects these checkpoints at config time. This is not a duplicate of #67263, which skips the INT8_PB_WO routing test on ROCm because the method is unsupported; with this PR that test passes on ROCm instead.

## Claims

- `modelopt_int8` checkpoints load and serve on ROCm in fp16 and bf16, including group sizes 16 and 32
- The Triton WNA16 kernel (`triton_w4a16.py`) takes 8-bit `uint8b128` weights and group size 16, on ROCm only, so CUDA kernel selection is unchanged
- 8-bit GPTQ models on ROCm move from Conch to this kernel and get 9-12% more throughput with the same accuracy
- The 4-bit path is unchanged: same compiled ISA, latency ratio 1.000

## Validation

MI300X (gfx942), all on this branch against `origin/main` at 778f0fe600.

- Tests: `kernels/quantization/test_triton_w4a16.py`, `quantization/test_modelopt.py::test_modelopt_int8_pb_wo_checkpoint` and `::test_modelopt_int8_pb_wo_routes_to_its_config` passed 10/10 loops (34 tests each). The checkpoint test was skipped on ROCm and the routing test failed on main (`modelopt_int8 quantization is currently not supported in rocm`).
- No regressions against main in all of `test_modelopt.py`, `test_auto_gptq.py`, `test_gptq_dynamic.py`, the compressed-tensors WNA16 tests and `kernels/quantization -k 'gptq or exllama or conch'`.
- Accuracy, gsm8k 5-shot flexible-extract. No public INT8_PB_WO checkpoint exists, so I quantized Qwen2.5-1.5B-Instruct to INT8_PB_WO group 32 and compared it with a dense model holding the same dequantized weights:

| Model | dtype | main | this PR |
|---|---|---|---|
| Qwen2.5-1.5B INT8_PB_WO g32 (limit 500) | bf16 | rejected | 0.554 |
| same weights, dequantized and dense (limit 500) | bf16 | n/a | 0.552 |
| Qwen2.5-1.5B-Instruct-GPTQ-Int8 (full) | fp16 | 0.590 (Conch) | 0.591 (Triton) |
| Qwen2.5-1.5B-Instruct-GPTQ-Int8 (full) | bf16 | 0.583 (Conch) | 0.583 (Triton) |

- Throughput, `vllm bench throughput --model Qwen/Qwen2.5-1.5B-Instruct-GPTQ-Int8 --dtype float16 --input-len 512 --output-len 128 --num-prompts 1000`: main 107.6 / 107.7 req/s, this PR 117.6 / 120.9 req/s. Forcing Conch in this branch with `VLLM_DISABLED_KERNELS=TritonW4A16LinearKernel` gives 104.8 / 101.0 / 106.7 against 119.3 / 120.1 / 119.5 with Triton.
- Kernel microbenchmark (HIP graphs, cold weights), 8-bit group 128: faster than Conch at every Llama-3-8B and Qwen2.5-1.5B linear shape from M=1 to 8192 (1.1x at M=1 up to 6-10x at large M), and faster than Exllama in fp16.

## Details

The Triton kernel only assumed 4 bits in its packing constants (8 values per int32, `0xF` mask, three interleaves), so it now takes the bit width as a constexpr and the 4-bit code compiles to the same instructions. Allowing `modelopt_int8` alone would not have been enough: Exllama takes 8-bit weights but only fp16 activations, and Conch only groups -1 and 128, so a bf16 checkpoint with group 16 or 32 found no ROCm kernel. On CUDA, Humming already serves these configs, so the new paths are gated to ROCm.

Not covered here: gfx950 hardware, and AMD CI for `test_modelopt.py`. The kernel tests run on MI355 in the AMD kernels job, but the AMD Quantization job that runs `test_modelopt.py` is disabled on main until #66672 lands.
