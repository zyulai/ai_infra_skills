## Overview

Qwen3.8-Flash-Next decode ITL **-9.5% at concurrency 1 on a single DGX Spark (SM121, TP=1)** by adding SM121 skinny-GEMM plans for the TP=1 BF16 shapes, which today fall back to cuBLAS. The LM head `(248320, 2560)` gives most of it (-8.3% alone); the remaining rows add -1.3% on `local-inference-lab/Qwen3.8-Flash-Next-NVFP4`, where the router, HC projections and shared-expert gate are BF16 and the other dense projections are MXFP8. On `nvidia/Qwen3.8-Flash-Next-NVFP4` attention, GDN and shared experts are BF16 as well and use the same rows; that checkpoint does not fit a single Spark, so it is not measured end to end.

Complements #59632 (SM121 plans for TP=2 shapes, from #59605): this PR only adds TP=1 keys to the same mechanism. Happy to fold this into #59632 or rebase on it, whichever lands first.

## Claims

- In a c1 decode step (MTP k=3) the LM head runs 4 times: 3 draft steps at M=1 (cuBLAS gemv, 6.8 ms each) and the target verify at M=4 (5.3 ms), 25.7 ms or about 33% of the 77.6 ms step (torch profiler, `local-inference-lab/Qwen3.8-Flash-Next-NVFP4`). Almost all of the end-to-end gain comes from the three M=1 calls (about 2.2 ms saved each).
- cuBLAS reaches about 175 GB/s at M=1 on this shape; the skinny GEMM reaches 253 GB/s: **1.45x at M=1**, 1.04x to 1.08x at M=2 to 16.
- End to end: ITL 25.30 to 22.91 ms (-9.5%), output tokens/s +9.9% at concurrency 1 (mean of two interleaved runs per arm; LM-head rows alone: 23.20 ms, -8.3%); parity at concurrency 8 (its M=32 verify step is outside the skinny GEMM range and stays on cuBLAS).
- GSM8K within run-to-run noise: base 249 / 247, LM-head rows only 245 / 247, full table 246 / 246 of 256 (two runs each; two identical base runs differ by 2).

A bake-off on the LM-head shape (FlashInfer `mm_bf16` cudnn / cublaslt / tinygemm, b12x `bf16_vocab_projection` default config) found nothing faster than the skinny GEMM at M=2 to 16; at M=1 b12x was 4% faster than the skinny config but would need a new dependency.

**End to end**, same node (p4242-0074), `local-inference-lab/Qwen3.8-Flash-Next-NVFP4`, TP=1, MTP k=3 with forced acceptance length 3, FP8 KV, `--max-num-batched-tokens 4096`, SPEED-Bench 2K in / 1K out, two interleaved runs per arm, mean:

**Accuracy**: GSM8K, first 256 test questions, greedy, thinking off, speculative decoding off, 8 concurrent requests, two runs each: base 249 and 247, LM-head rows only 245 and 247, full table 246 and 246 (of 256). Batch composition varies between runs, so identical configs differ by a few questions.

Disclaimers:
- End to end ran on vLLM `af7f9488c` (the image used for Flash-Next serving) with this PR's table overlaid on `low_latency_gemm.py`.
- Small request counts per cell (8 and 16); baseline repeats on one node agreed within 1.5%.
- `(13312, 2560)` is the unfused QSA QKV/gate shape; after #59533 lands, the fused `(13952, 2560)` key needs a row (sweep data available).
- SM120 (RTX PRO 6000) is not covered: on the 600 W Server Edition the LM head gains only 1.07x to 1.09x, since cuBLAS is already close to that card's bandwidth.
