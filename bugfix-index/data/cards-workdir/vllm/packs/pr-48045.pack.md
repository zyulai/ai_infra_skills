## 正文(PR 描述)

## Summary

Fixes #47935

## Root cause

FlashMLA's `get_mla_decoding_metadata_dense_fp8` computes

```
int num_sm_parts = sm_count / num_heads_k / cutlass::ceil_div(num_heads_per_head_k, block_size_m);
```

This can be 0 when `ceil_div(num_q_tokens_per_head_k, block_size_m) > sm_count` (with `num_heads_k == 1`). The bf16/fp16 version clamps the minimum to 1: https://github.com/vllm-project/FlashMLA/blob/a6ec2ba7bd0a7dff98b3f4d3e6b52b159c48d78b/csrc/api/dense_decode.h#L79

In vLLM, `num_q_tokens_per_head_k = max_query_len * num_q_heads` (`FlashMLAMetadataBuilder._build_decode`), and short prompts (query length ≤ `reorder_batch_threshold == 128`) are routed to the decode pathway. So **DeepSeek-R1 (128 heads) crashes on any 67–128 token prompt** on a 132-SM GPU (H100/H200).

## Fix

**vllm-project/FlashMLA#14** clamps `num_sm_parts` to `>= 1` like the bf16/fp16 version

## Testing

On an H200 (132 SMs), with the patched FlashMLA build:

- Direct `get_mla_decoding_metadata_dense_fp8` call at `num_q_tokens_per_head_k` = 8449 and 16384 (both previously `num_sm_parts → 0`, assert): returns valid metadata, no crash.
- End-to-end vLLM `generate` on a dummy DeepSeek-V3 (128 heads, 1 dense layer, `--kv-cache-dtype fp8`, FlashMLA): 100- and 128-token prompts complete normally (previously crashed with the assertion above).
- Control (66-token prompt, `num_sm_parts = 1`): unaffected.

AI assistance (Claude Code) was used to investigate, build the repro, and prepare this change.
