## 正文(PRD / 提案全文)

**TL;DR.** On platforms where the driver advertises GPU P2P but the fabric silently drops peer writes (ACS + translated IOMMU, misconfigured BIOS, some VMs), vLLM either hangs forever at engine startup (TP=2). vLLM already owns the right tool — the write-and-verify check `gpu_p2p_access_check` — but today only one of its three (soon four) P2P consumers consults it, it is skipped by default, and it runs *after* the point where NCCL hangs. This RFC proposes to settle the **contract** for functional P2P checking across consumers: (1) make that check the single canonical verdict with **veto-only** semantics, and (2) wire **all** P2P consumers to it, including NCCL via env.

---

## Motivation

### The failure class

`cudaDeviceCanAccessPeer` (and the cuMem capability queries NCCL uses) is a capability lookup — GPU SKU allowlist, chipset allowlist, topology shape — not a data-path test. Whether a peer write actually *arrives* additionally depends on runtime platform state the driver does not model:

- **PCIe ACS** on root ports redirects peer transactions up to the IOMMU;
- an **IOMMU in translated mode** (the default DMA domain on current kernels) has no mapping for peer BAR addresses, so the redirected write faults;
- a PCIe peer write is a **posted** transaction — no acknowledgment exists in the protocol. The dropped write is logged only in the *host* kernel log (`AMD-Vi: IO_PAGE_FAULT` / `DMAR: ... fault`); the GPU and the CUDA stack see nothing. The receiving kernel spin-polls a flag that never arrives.

The result is either an infinite hang (dropped flag writes) or **silent output corruption** (dropped data writes with surviving synchronization).

This is a long-standing, recurring failure class:
- #17676 — "vLLM hangs forever on waiting engine process to start" (open, 42 comments): the umbrella symptom.
- #2728 — the original issue that motivated `can_actually_p2p` ("the driver might be broken, and `can_device_access_peer` returns True even if P2P access is not actually possible").

### Case study — full causal chain, reproduced end to end

Hardware: bare-metal 2-socket AMD EPYC server, 8× PCIe GPUs (no NVLink), one GPU per host bridge/NBIO, Ubuntu kernel 6.17, driver 580.x / CUDA 13.0 / NCCL 2.28.9, workloads in Docker. BIOS ships ACS enabled (each GPU sits alone in its own IOMMU group), kernel default `iommu: Default domain type: Translated`.

1. **The driver blesses every pair.** `nvidia-smi topo -p2p w` reports `OK` for all 64 pairs; `cudaDeviceGetP2PAttribute(AccessSupported, 0, 1) == 1`.

2. **`vllm serve -tp 2` hangs forever** at `Waiting for 1 local, 0 remote core engine proc(s) to start.` with both GPUs pinned at 100%. The stuck frame is the pynccl warmup all-reduce (`vllm/distributed/device_communicators/pynccl.py:142-145`):

   ```python
   stream = current_stream()
   # A small all_reduce for warmup.
   data = torch.zeros(1, device=device)
   self.all_reduce(data)
   stream.synchronize()   # <- never returns; no timeout exists
   ```

3. **The host IOMMU testifies.** Every start attempt logs a burst of faults, stamped with the GPU's BDF, at the moment the warmup spins:

   ```
   nvidia 0000:21:00.0: AMD-Vi: Event logged [IO_PAGE_FAULT domain=0x002e address=0x11b400826200 flags=0x0030]
   nvidia 0000:21:00.0: AMD-Vi: Event logged [IO_PAGE_FAULT domain=0x002e address=0x11b800000000 flags=0x0030]
   ```

   (flags bit 5 = write; the address is the peer GPU's BAR window. The write was redirected by ACS to the IOMMU, which had no translation and dropped it.)

4. **Model-independent minimal repro** (no vLLM involved):

   ```python
   # t.py — hangs on the affected platform at nproc-per-node=2
   import torch, torch.distributed as dist
   dist.init_process_group("nccl")
   r = dist.get_rank(); torch.cuda.set_device(r)
   x = torch.ones(1, device="cuda")
   dist.all_reduce(x); torch.cuda.synchronize()
   print(f"rank {r}: OK sum={x.item()}")
   ```

5. **Why exactly TP=2 (and why most users' "TP=4 works" misleads triage).** NCCL's `ncclTopoCheckP2p` (`src/graph/paths.cc`) defaults to `p2pLevel = PATH_PXB` — *"don't use P2P across CPU Host Bridges"* — which on a switchless topology forbids P2P for every pair. But it carries an AMD-specific carve-out:

   ```c
   if ((arch == NCCL_TOPO_CPU_ARCH_X86 && vendor == NCCL_TOPO_CPU_VENDOR_AMD)
       && system->nodes[DEV].count <= 2)
     p2pLevel = PATH_SYS;
   ```

   Verified empirically on the same pair of GPUs:

   ```
   nranks=2: isAllDirectP2p 1 ... 0[0] -> 1[1] via P2P/CUMEM   -> hangs (timeout kill)
   nranks=4: isAllDirectP2p 0 ... 0[0] -> 1[1] via SHM/direct  -> OK sum=4.0
   nranks=8: isAllDirectP2p 0 ... all hops via SHM/direct      -> OK sum=8.0
   ```

   So NCCL's *distrust* of host-bridge P2P accidentally shields TP≥3, while its AMD ≤2-GPU *trust* carve-out selects exactly the 2-GPU population for the hang. Note this shield covers only NCCL: vLLM's own P2P kernels (below) stay armed at any TP, and host-side `IO_PAGE_FAULT`s were observed during a TP=4 vLLM startup on the same box.

6. **Platform fix exists** (`iommu=pt` or BIOS ACS off — verified: the hang and the faults disappear, P2P works at full speed). But vLLM cannot assume every user can reboot into a fixed platform; its job is to not hang or silently corrupt for the next user who lands on one of these machines.

The complete diagnosis above required host `dmesg` access, `NCCL_DEBUG=INFO`, `py-spy`, and roughly a day — for a failure vLLM already contains the machinery to detect in seconds.

### vLLM today: N consumers, N trust decisions, N kill switches

| P2P consumer | Trust basis today | Functional gate | Kill switch |
|---|---|---|---|
| NCCL / pynccl | NCCL's own topology policy (driver capability + path type) | none | `NCCL_P2P_DISABLE=1` (user must know to set it) |
| `CustomAllreduce` | driver report (`can_device_access_peer`) since #21904 | `gpu_p2p_access_check`, **opt-in** via `VLLM_SKIP_P2P_CHECK=0` | `--disable-custom-all-reduce` |
| `SymmMemCommunicator` | driver report | none | `VLLM_ALLREDUCE_USE_SYMM_MEM=0` |
| MiniMax fused AR (#47544, in flight) | adding its own ad-hoc functional check | own | own |

History: the write-and-verify check ran **by default** until #21904 (`e91d3c9cda`, July 2025) flipped `VLLM_SKIP_P2P_CHECK` to default-skip for startup-cost reasons ("We assume drivers can report p2p status correctly"). Even at its most vigilant setting, today the check protects only custom allreduce — and it executes *after* `PyNcclCommunicator` is constructed (`cuda_communicator.py`), i.e. after the point where the NCCL warmup has already hung. A user who discovers `VLLM_SKIP_P2P_CHECK=0` gains nothing against the hang, and a user who sets `NCCL_P2P_DISABLE=1` un-hangs NCCL only to hand the same broken fabric to custom allreduce and symm-mem (observed: startup proceeds past NCCL, then spins at 100% in the first profiling forward).

Each consumer independently rediscovering this failure mode and growing its own ad-hoc check (#47544 being the latest) is the pattern this RFC wants to end.

## Proposed change

### 1. The contract: one canonical verdict, veto-only

Promote `gpu_p2p_access_check(src, tgt)` (subprocess write-and-verify, JSON cache — already implemented in `vllm/distributed/device_communicators/all_reduce_utils.py`) to the single source of truth for "is P2P *functional* between these GPUs".

**Semantics are veto-only:**
- `False` ⇒ P2P is disabled for **every** consumer. A fabric that drops legacy cudaIpc peer writes (ACS/IOMMU/root-complex level) drops cuMem writes too — the veto transfers.
- `True` ⇒ forces nothing. The check exercises legacy cudaIpc mappings, while NCCL 2.28 and torch symmetric memory use cuMem — a pass does not certify those paths, so consumers keep their existing enablement logic.

### 2. Wire all consumers to the verdict

When the check runs (see §3 for when) and returns `False` for any pair in the comm:

- **`CustomAllreduce`** — already wired; unchanged.
- **`SymmMemCommunicator`** — add the same gate before enabling.
- **MiniMax fused AR** — #47544 consumes the shared verdict instead of a private check.
- **NCCL** — vLLM cannot patch libnccl's transport choice, but it owns the worker bootstrap: set `NCCL_P2P_DISABLE=1` in the worker's environment *before the first communicator is created*, unless the user already set any `NCCL_P2P_*` variable themselves (never override explicit user config), and log prominently: `P2P verified non-functional between GPUs 0<->1 (driver reports OK); disabling P2P for NCCL, custom allreduce, and symmetric memory. See <docs link> — likely platform cause: PCIe ACS + IOMMU in translated mode; fix with BIOS ACS off or iommu=pt.`

### 3. Cost story — no new default overhead

- Default behavior is unchanged: check skipped, trusting the driver (per #21904). Healthy platforms pay nothing new.
- With `VLLM_SKIP_P2P_CHECK=0`, the verdict now protects everything, not just custom allreduce — and #39249's async precompute hides its startup latency.
- Follow-up (separate PR, opt-in → maybe default later): auto-enable the check only on risk-class topology — multi-GPU, PCIe-only, no NVLink — and especially the population NCCL's AMD ≤2-GPU carve-out uniquely exposes. NVLink boxes never pay anything.
