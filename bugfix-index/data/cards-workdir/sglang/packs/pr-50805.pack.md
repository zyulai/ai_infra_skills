## 正文(PR 描述)

## Motivation

Series: #50803 (1/4, srt runtime core), #50804 (2/4, srt models and layers), #50805 (3/4, kernels), #50806 (4/4, diffusion).

Part 3 of a four-part cleanup split by package (1/4 srt runtime core, entrypoints, managers, tools; 2/4 srt models and layers; **3/4 kernels**; 4/4 multimodal_gen diffusion). It follows #44690, #48366, #48399 and #49189 and uses the code-cleanup skill (#49163). This part covers `python/sglang/kernels/**`: the AOT C++/CUDA sources and the `sgl_kernel` Python package, the JIT kernels, and `kernels/ops/**` (attention, MoE, quantization, diffusion, communication), with their tests. What drifted: checks that never checked anything (a `TORCH_CHECK` whose condition was a size, a test helper that compared a tensor with itself, a verify flag that always printed a mismatch), a package export that could hand back a module instead of a function, architecture gates written on the raw capability major, and kernel entry points that kept unreachable branches, unread parameters and docstrings naming files and variables that do not exist.

**77 files, +390 / -986.** About 200 of the added lines are tests. The four PRs touch disjoint files and can merge in any order.

Source paths below are relative to `python/sglang/kernels/` unless they start with `srt/`, `test/` or `python/`.

## Kept on purpose

- The `nvlink_comm` files are recent and their multi-GPU NVLink path could not be exercised on the single-GPU machines used here, so they were left untouched.
- The public API of the `sgl_kernel` wheel is unchanged: no exported op, wrapper or `__init__` name is removed. The only C++ edits in the AOT tree are the two `csrc/cpu/moe.cpp` fixes and the duplicate declaration in `sgl_kernel_ops.h`.
- `sampling/softmax.cuh` keeps its private `fence_mbarrier_init_cluster`, the same instruction as `ptx::fence_barrier_init`: the file is recent (added in November). Other private PTX wrapper copies sit in files that are recent or SM100-only and could not be built for their target here.
- `swa_verify_splitkv.py::_swa_verify_reduce` and the single-layer `commit_kda_replayssm_spec` stay (see "For the owners").
- Numeric kernels that share statements but are not identical code stay separate, for example the two `select01` diffusion kernels and `_vv2_reduce`.
- `kU64Mask` and `kReqPoolIdxPadding` in `kv_canary/consts.cuh`: `test_const_sync.py::test_int_consts_sync` requires the C++ and Python constant sets to be equal.

- One-line comments that are stale but not wrong.

## For the owners (not changed here)

Fixes that were prepared and left out because they change numerics or a public name and could not be validated on the target hardware or with real weights:

- **xAI temperature differs between the deterministic prefill kernel and the others.** `ops/attention/extend_attention.py::_fwd_kernel_unified` scales the logits by `1 if p < L else L / (p + 1)` (`L = xai_temperature_len`, `p` the absolute query position). `_fwd_kernel` in the same file and both decode kernels (`_fwd_kernel_stage1`, `_fwd_grouped_kernel_stage1` in `decode_attention.py`) use `log2(p) / log2(L) if p > L else 1`. Only `srt/models/grok.py` sets the length, from `attn_temperature_len`. `TritonAttnBackend.forward_extend` takes the unified kernel for every prefill under `--enable-deterministic-inference`, so such a checkpoint prefills with the first formula and decodes with the second. Measured on H200 (prefix 48, extend 80, `L = 16`): the unified kernel differs from a torch reference of the log2 form by up to 1.725 in the output. The fix would switch the unified kernel to the log2 form. It changes logits on a path that runs today, and which form the checkpoint was trained with is the model owner's call; it needs a deterministic vs non-deterministic greedy comparison on real weights.
- **`fuse_scale_shift_kernel` reads a non-blocking copy before it lands** (`ops/diffusion/modulate/scale_shift_triton.py`). When scale and shift are one-element tensors it decides "both zero" with `scale_blc.any().to("cpu", non_blocking=True) or shift_blc.any().to("cpu", non_blocking=True)` and then returns a copy of `x`. The host value can be read before the copy has landed. Measured on H200 on main with one-element non-zero scale (0.5) and shift (0.25), bf16 `x` of shape 1 x 32760 x 5120, calls issued back to back with no synchronization in between: `x` came back unmodified in 115 of 300 calls. With smaller tensors (up to 2 x 4096 x 1536) it did not happen in 2000 calls. We found no caller in the tree that passes non-zero one-element operands, so nothing returns a wrong value today. The Wan-family blocks (`wanvideo.py`, `causal_wanvideo.py`, `lingbot_world.py`, `longlive2.py`) pass one-element zeros with `scale_constant=1` through `forward_native`; there the copy path and the Triton kernel are both correct and differ only in the sign of zero, so which one runs is timing-dependent. Deleting the fast path, or making the read blocking, fixes it. It was left out because it changes what the `forward_native` route executes (ROCm without FlyDSL, XPU, the CUDA fallback) without a model run on those routes.
- **`infllm_v2` stage 1 serves fp16 and other head sizes with the bf16 / 128 kernel** (`aot/csrc/infllm_v2/flash_attn`). `FP16_SWITCH` always picks `cutlass::bfloat16_t`, `HEADDIM_SWITCH` picks 128 for everything that is not 64, and only the bf16 hdim 64 / 128 kernels are built, but `mha_varlen_fwd_stage1` (`flash_api.cpp`) accepts `kFloat16` and any head size that is a multiple of 8 up to 256. Measured on H200: fp16 q / k give scores that differ from the same values in bf16 by 77% (head dim 64) and 92% (head dim 128) of the largest score; head dim 32 returns a finite tensor. No error in either case. Reachable from the MiniCPM sparse backend (`compressed_attention`) when the model dtype is float16 and `minicpm_fuse_topk` is off. A check that rejects both was left out: a MiniCPM server started with `--dtype float16` runs today and would raise on its first request. The owner has to choose between raising, casting to bf16 at the call site, or building the fp16 kernels.
- **`segment_packbits` is an unregistered op with importable wrappers.** `sgl_kernel/speculative.py::segment_packbits` calls `torch.ops.sgl_kernel.segment_packbits`, which no extension defines, so calling it raises `AttributeError`. `csrc/speculative/packbit.cu` is compiled only by `setup_musa.py` and never registered.
