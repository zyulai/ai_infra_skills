## Overview

Two changes to the Triton MiniMax-M3 indexer (`vllm/models/minimax_m3/common/ops/index_topk.py`):

1. **Decode launch-grid retune.** `TARGET_GRID` goes from 512 to 4096 (decode index score) and `TOPK_TARGET_GRID` from 64 to 512 (decode top-k). This applies to every CUDA GPU on the Triton MiniMax-M3 indexer, not only SM120. ROCm uses its own `amd/ops/index_topk.py` and is not touched. Folded in from #49229 with its author's agreement; original commit by Zijing Liu, co-authored by Kyle Liang.
2. **SM12.0 prefill split-K.** On SM12.0 only, the prefill index score (`_index_block_score_kernel`) splits its K loop across CTAs when the launch grid is small, as it is for short chunked-prefill extends. Other GPUs keep the unsplit launch.

This PR was closed after the concurrency-12 point showed no gain, then reopened and narrowed:
- FP8 index-cache support and the operand casts are in #59081 (supersedes #47665).
- The fused decode top-k and the router change are dropped.

## Claims

Faster decode at higher batch sizes on the Triton indexer (grid retune), and faster short-extend prefill on RTX PRO 6000 (SM120, split-K).

## Validation

- **E2E:** MiniMax-M3-NVFP4 + EAGLE3 on 8x RTX PRO 6000, InferenceMAX recipe at c10 TP8.
  - Grid retune: removing it costs 4.6% throughput (tput 0.954x). Decode step p50 at 10 requests is 49.2 ms without it and 39.6 ms with it, matching the reference stack's 39.6 ms. #49229 separately reported +44% at B300 TP4 c24.
  - Split-K: short cached extends take 263 ms per iteration without it and 200 ms with it (reference stack 192 ms). This comes from a leave-one-out of the earlier fused-top-k + split-K version; split-K is the only part of that version on this path.
  - This PR as a whole: the split-K-only confirmation run already included the grid retune, so it measures exactly these contents. It reaches 0.985 tput / 1.004 interactivity vs the InferenceMAX reference stack, and per-request TPOT 0.997 [0.975, 1.008] vs the earlier fused+split-K version (n=1).
- **SM120 tests:** `pytest tests/kernels/attention/test_minimax_m3.py` gives 95 passed, 0 failed, 58 skipped. Main gives 92 / 0 / 58; the only difference is the 3 new prefill cases, and outcomes on the shared IDs are identical. `test_decode_index_topk_correctness` passes all 6 cases with the new decode grids (256 score chunks; up to 16 top-k chunks). All 4 prefill cases take `USE_SPLIT_K=True`.
- **CI:** `test_prefill_index_topk_correctness` forces the split path on any CUDA GPU (incl. an uneven split), so L4 runs it.
- **Lint:** `pre-commit`, including mypy-3.12, passed.

## Details

- Decode chunk counts stay shape-constant, so the launch is still CUDA-graph safe. At 2 or fewer decode requests the score grid is unchanged, because both values hit the 256-chunk cap.
- The split count is `split_k = min(max_block, 48 // (n_q_tiles * batch * heads))`, on SM12.0 only.
- Each CTA writes a disjoint range of per-block maxima, so no reduction is needed.
- Splits past a query tile's causal window exit early.
