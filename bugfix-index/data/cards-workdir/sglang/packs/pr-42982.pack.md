## 正文(PR 描述)

## Motivation

`jit-kernel-unit-test-amd` has been red on `main` since #40785 merged. Every run that has executed the job since has failed identically — #40785's own run, two on #34537, and one on an unrelated branch, all reporting `30732 / 65536` mismatched elements at the same index. The job only runs when a PR touches `python/sglang/kernels/`, so most PRs skip it and it went unnoticed.

Full evidence in #42981.

## Modifications

torch's `float8_e4m3fn` cast saturates to its max finite value. `float8_e4m3fnuz` has no infinity, so `fp8e4m3fnuz_from_fp32_value` returns NaN (`0x80`) for every magnitude at or above 256.0. Triton's cast saturates on both types, so the fused commit kernel from #40785 matches eager on CUDA and diverges on gfx94x.

This is not only a test problem. `set_kv_buffer_prefix_valid` has a fused path and an eager fallback, and on ROCm they now write different bytes for the same input — the fallback writes NaN into a committed KV slot, which poisons attention for that slot on every later read.

Rather than have the test chase whichever cast runs, this makes saturation the defined contract and clamps before the FP8 cast in all three places:

- `cache_move.py` — the kernel clamps, with the limit passed as a `tl.constexpr`; NaN falls through both `tl.where` arms. Two vector ops added to a memory-bound kernel.
- `memory_pool.py` — the eager fallback clamps identically, so the two production paths agree.
- `test/kernels/prefix_valid.py` — the shared oracle clamps identically.

The limit is `torch.finfo(fp8).max`, not the conservative `fp8_max` constant (224.0 on fnuz): clamping at 224.0 would pull values that eager rounds to 240.0 down a step.

All three are no-ops on CUDA, where the eager cast already saturates to 448.

## Test plan

`jit-kernel-unit-test-amd` on MI300 / ROCm 10: **42/42 files passed** ([job](https://github.com/sgl-project/sglang/actions/runs/37648241557/job/113082433719)), including `test_prefix_valid_fp8.py` and `test_prefix_valid_fp8_pool.py`. For reference, the same job on current `main` fails at 6/42 with 30732/65536 mismatched elements.

An earlier revision of this branch clamped in FP32, which turned the `bf16/fp16 -> fp8` cast into `fp32 -> fp8`; those lower to different conversions and left 2/65536 elements off by one FP8 subnormal step at fp16 with a host scalar scale. Clamping in the source dtype restores the original lowering, and that is the version here.

Still red on this PR, all reproducing on #40785 or unrelated to this path:

- `stage-b-test-1-gpu-small-amd (7)` — MiniMax sparse decode kernel requests 128 KiB LDS against a 64 KiB limit (`OutOfResources`), same partition red on #40785.
- `stage-b-test-1-gpu-small-amd-mi35x (1)` — red on #40785.
- `extra-a-test-1-gpu-small-amd` — `test_e2e_spec_eagle.py`; the server stops responding mid-stream (`RemoteDisconnected`), with no CUDA/HIP fault, scheduler exception or OOM in the log. That test runs `kv_cache_dtype=auto`, so `self.dtype` is not FP8 and neither the fused branch nor the eager clamp in this PR is reached — the non-FP8 commit path goes through `set_kv_buffer_prefix_valid_tiled`, which is untouched here. The same job is also red on #40785, on a different test.
- NPU jobs — `set_kv_buffer_prefix_valid` returns early for non-CUDA/non-HIP before reaching any line this PR touches.

If you would rather the kernel reproduce eager's `e4m3fnuz` NaN-on-overflow instead of saturating, I can invert the patch — but that writes NaN into the KV cache on AMD and diverges from the CUDA path, so saturation looks like the better contract.
