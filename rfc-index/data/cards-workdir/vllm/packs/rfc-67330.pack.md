## Motivation

We propose an optional interface allowing a quantized linear kernel to combine its base computation with the LoRA update. The initial implementation targets compressed-tensors W4A16 dense linear layers on AMD gfx1151.

Today, these layers use separate logical operations for the quantized base GEMM, LoRA shrink, and LoRA expand. For small activation batches, the separate expand operation adds launch overhead and reads and writes the base output again.

Our prototype retains the standard Punica shrink operation and incorporates expand into the W4A16 GEMM epilogue. This reduces output memory traffic and removes the standalone expand operation for supported calls.

For token `t` using adapter `i`, the intended computation remains:

```text
y_t = x_t @ dequant(W).T + s_i * (x_t @ A_i.T) @ B_i.T + b

Stock: 3 launches per LoRA linear                  Fused: 2 launches per LoRA linear

x ─► lora_shrink ─► z = x·Aᵀ (fp32)                 x ─► lora_shrink ─► z = x·Aᵀ (fp32)        same kernel
x ─► W4A16 GEMM ─► y = round(x·Wᵀ)   store y        x ─► W4A16 GEMM, per output tile:
     y = round(y + bias)                                 acc = x·Wᵀ                  (fp32)
y ─► lora_expand: load y                                 acc += z[m]·B'[slot(m)]ᵀ    (fp32, epilogue)
     y = round(y + round(z·B'ᵀ))     store y             y = round(acc)              store y once
                                                    y = round(y + bias)
```

Tokens without an adapter receive only the base result. Existing adapter formats, loading, scaling, and per-token selection are preserved. Fusion changes intermediate rounding and addition order, so numerical equivalence requires explicit validation.

We would like feedback on the shared interface and integration approach before submitting the implementation PR.

## Proposed Change

### 1. Add a small, optional kernel interface

The prototype introduces three hooks:

```python
# LinearMethodBase
get_fused_lora_kernel(layer) -> MPLinearKernel | None

# MPLinearKernel
can_apply_weights_with_lora(layer, x) -> bool
apply_weights_with_lora(layer, x, bias, lora_a, lora_b,
                        output_slices, meta_args) -> torch.Tensor
```

The defaults retain the existing execution path.

A quantization method exposes a kernel only when calling that kernel preserves all behavior of its normal `apply()` method. Methods performing additional transforms or preprocessing must retain their existing path unless explicitly supported.

The LoRA layer invokes the optional path when eligible. The kernel owns its hardware, shape, rank, and layout restrictions.

The initial implementation opts in only compressed-tensors WNA16 layers using `RDNAHybridW4A16LinearKernel`.

### 2. Use a registered PyTorch custom op

The prototype follows the existing base GEMM's registration pattern:

```text
LoRA layer
  -> quantization-method opt-in
  -> kernel eligibility check
  -> torch.ops.vllm.rdna_hybrid_w4a16_lora_apply
      |-- no active adapter: base GEMM
      |-- supported call: shrink + GEMM with expand epilogue
      `-- declined call: shrink + base GEMM + expand
```

The operation returns a fresh output, declares no input mutations, and provides a fake implementation.

Shape-dependent fusion decisions remain inside the opaque operation so that compiled execution can handle calls spanning fused and fallback shapes without tracing those decisions into Python control flow.

We propose retaining `direct_register_custom_op`, consistent with the existing `rdna_hybrid_w4a16_apply`.

### 3. Keep the initial scope narrow

| Area | Initial scope |
| --- | --- |
| Hardware | AMD gfx1151 |
| Quantization frontend | Compressed-tensors WNA16, 4-bit weights |
| Activation/adapter dtype | FP16 or BF16, with compatible layouts |
| Quantization | Symmetric/asymmetric; group sizes 32, 64, 128 |
| Activation rows per call | Generally 6-64, with additional shape restrictions |
| Adapter capacity | At most eight allocated slots |
| Packed projections | At most three output slices, with aligned boundaries |
| Parallelism | TP=1; fully sharded LoRA disabled |

Rank restrictions depend on serving buffer capacity and GEMM tile shape. The current maximum is 64, with tighter limits for larger activation batches and tiles. Large tall projections also have exclusions.

Calls outside the supported envelope retain standard LoRA execution. Dual-stream and batch-invariant modes retain their existing paths. Other hardware and quantization methods retain their defaults.

### 4. Make the optimization opt-in initially

The prototype adds:

```python
KernelConfig.enable_rdna_hybrid_w4a16_fused_lora = False
```

Example:

```bash
vllm serve <model> \
  --enable-lora \
  --kernel-config '{"enable_rdna_hybrid_w4a16_fused_lora": true}'
```

The field participates in the configuration hash to distinguish compiled artifacts for enabled and disabled execution.

We welcome feedback on the configuration location and naming. This direct PyTorch operator is separate from vLLM's `CustomOp` class registry; its selection does not currently depend on `compilation_config.custom_ops`.

### 5. Validate numerical behavior and execution modes

The prototype includes coverage for:

- Stock Punica comparisons and an independent dequantized reference.
- Hand-checkable cases that detect missing, doubled, or incorrectly routed adapter corrections.
- Scaling through the real adapter loader, including per-projection rank/alpha patterns.
- Packed projections, partial adapters, slot reuse, mixed adapter/base batches, and inactive-row contamination.
- Fusion eligibility boundaries and valid fallback configurations.
- Custom-op schema, FakeTensor, mutation/aliasing, and dynamic AOT checks.
- Eager execution, `torch.compile`, graph replay, and concurrent streams.
- Real model and server execution.

Numerical tolerances must account for dequantization, shrink accumulation, casts, and the changed order of bias and LoRA addition. Bitwise identity is not assumed for the fused path.

Before the implementation PR, we will complete the numerical-bound review and use the fusion flag as the primary A/B control, keeping other execution settings constant.

### Preliminary results

The following are author-reported measurements from one native Linux gfx1151 system using a Ryzen AI MAX+ 395 / Radeon 8060S. They require the accompanying reproducibility package and final review.

| Measurement                       | Preliminary result                                                                                                                              |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Representative fused kernel cases | Approximately 1.06-1.16x stock geometric-mean speed                                                                                             |
| Kernel, M=1-5 and M>=65           | 1.00x stock (outside the envelope; stock path)                                                                                                  |
| Kernel, M=6-32                    | Approximately 1.08x (FP16) and 1.14x (BF16) stock geometric-mean speed                                                                          |
| Kernel, M=33-64                   | Approximately 1.13x (FP16) and 1.16-1.17x (BF16) stock geometric-mean speed for fused rank-16 cases; ranks 32/64 decline at approximately 1.00x |
| Serving, concurrency 1            | Approximately 1.00x stock output throughput                                                                                                     |
| Serving, concurrency 8-32         | Approximately 1.06-1.07x stock output throughput                                                                                                |
| Feature disabled                  | Default behaviour, unchanged                                                                                                                    |
| Kernel/layer suite                | 499 passed, zero failures or skips, as reported                                                                                                 |

The serving workload uses Qwen3-4B W4A16 with a GSM8K adapter, random input/output lengths of 128/256 tokens, and concurrency 1/8/16/32.

The per-batch-size kernel rows use the qkv, o, gate_up, and down projections of Qwen3-4B, Llama-3.1-8B, and Qwen2.5-7B at M (activation rows) of 1, 5, 6, 8, 16, 32, 33, 64, and 65, with ranks 16/32/64, round-robin and mixed adapter mappings, and the median of three repetitions per case.

Some enabled FP16 kernel cases are slower, with measured speed ratios around 0.90-0.97x stock. The implementation is therefore proposed as opt-in while eligibility and performance criteria are reviewed.

A full GSM8K evaluation produced 84.00% with fusion, compared with stock runs of 84.46% and 83.70%. These observations alone do not establish accuracy equivalence.

### Alternatives considered

- **Retain separate operations:** preserves the existing implementation and compiler freedom, but retains standalone expand overhead.
- **Compiler-pattern fusion:** could avoid explicit LoRA-layer dispatch hooks, but would need to recognize the relevant opaque operations and metadata. Eager execution would still need consideration.
- **A vLLM** `CustomOp` **wrapper:** could provide standardized backend/configuration dispatch. We would appreciate feedback on whether that adds value alongside the existing quantization-kernel selection.
- **A backend-specific special case:** could reduce the generic interface change, but would place hardware-specific behavior in shared LoRA code.

### Questions for maintainers

1. Is an optional kernel-owned LoRA interface appropriate, or would another integration point be preferable?
2. Is a sibling registered PyTorch operation consistent with the existing base GEMM the preferred compilation boundary?
3. Is a default-off `KernelConfig` field appropriate for initial deployment?
4. What numerical and performance acceptance criteria should apply?
5. What validation arrangement is acceptable given the current lack of gfx1151 upstream CI coverage?
6. Should this proceed directly as an upstream PR, or first through `ROCm/vllm:gfx11` staging?
