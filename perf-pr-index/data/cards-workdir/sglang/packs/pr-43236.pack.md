## Motivation

On Blackwell the JIT activation kernels are built without fast-math. For SiLU, `x / (1 + expf(-x))` then compiles to an IEEE division. In the SASS (sm_103a, default 16-element vector), every element gets its own `BSSY`/`BSYNC` region: `MUFU.EX2` → `MUFU.RCP` → Newton `FFMA`s → `FCHK` → conditional `CALL` to the division slow path. That is 16 `FCHK`s and 16 `CALL`s per thread, so the elements run back to back instead of interleaving (~46 ns per element on B300). At decode sizes there are too few warps to hide this, and SiLU-and-mul costs 1.7–1.8 µs/layer even for a single token.

The precise-math choice was not specific to activation. The AOT sgl-kernel stopped using `-use_fast_math` for SM100 builds when Blackwell FP8 blockwise GEMM landed (#4278, #4376), and #10701 later split AOT `common_ops` into an SM90 fast-math build and an SM100+ precise build. The JIT activation (#22094) mirrored that policy. Hopper has always run these kernels with fast-math.

## Modifications

`get_activation_cuda_cflags()` now returns `["--use_fast_math"]` whenever `is_cuda()`, and `[]` otherwise. That drops the SM100+ exception. Fast-math turns the IEEE division into a branch-free approximate one, uses the approximate `expf`, and flushes subnormals to zero.

**Affected kernels:** everything built with these flags.
- The gated activations (`silu_and_mul`, `gelu_and_mul`, `gelu_tanh_and_mul`).
- `relu2` when called with its default `fast_math=True`. Callers that need BF16 subnormals already pass `fast_math=False` (e.g. Cosmos3).
- `situ_and_mul`.

The rounding variants (`*_with_activation_rounding`) still build the precise `rounded_activation` module. HIP still gets no fast-math. MUSA previously received `--use_fast_math`; it now follows whatever `is_cuda()` returns under `torchada`, which I have not tested.

## Accuracy Tests

**Kernel numerics.** Outputs on Blackwell are **not** bitwise identical to main. The difference is almost entirely flush-to-zero of BF16 subnormal results: BF16 shares fp32's exponent range, so BF16 subnormals are fp32 subnormals.

Exhaustive check of SiLU-and-mul on B300 over all 65,536 gate bit patterns, fast-math against precise, with 7 `up` cases (±1, 0.5, 3, randn ×2, randn×100):

| dtype | outputs that differ | what they are |
| --- | --- | --- |
| BF16 | 0.78–1.22% | Precise gives a subnormal and fast-math gives 0, at \|g\| < 1e-36 or g < −80. Over the 47,819 gates in −80 ≤ g, \|g\| ≥ 1e-36 there are 0 differences at `up=1` and one 1-ulp rounding flip with random `up`. |
| FP16 | 1–3 values | 1-ulp rounding flips (FP16 subnormals are normal in fp32, so there is no FTZ effect) |

Against an fp64 reference rounded to BF16 (`up=1`), precise is correctly rounded on 65,263 / 65,280 finite outputs and fast-math on 64,752. The gap is the flushed subnormals. GELU, GELU-tanh, ReLU² and SiTU were covered by the unit tests below, not by an exhaustive sweep.

**End-to-end.** `test_inkling_small_nvfp4.py` (Inkling-Small-NVFP4, TP4, DSpark speculative decoding, `--enable-deterministic-inference`) asserts bitwise prefill/decode logprob consistency. In this server the JIT SiLU runs in the DSpark draft model. On 4× B300, with #43447 applied:

## Speed Tests and Profiling
