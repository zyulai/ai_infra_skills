# RFD: Unified `sglang` Command-Line Interface

## Status

Draft

## Summary

SGLang’s current invocation pattern requires users to run Python modules directly, for example:

```bash
python -m sglang.launch_server
python -m sglang.bench_latency
```

This is workable but brittle: it is easy to mistype, hard to discover, and forces users to memorize internal module names that we may want to refactor. This RFD proposes a first-class `sglang` CLI with a small set of well-named commands, and an internal structure that can scale without turning into a bespoke CLI framework.

This document leans heavily on a close study of vLLM’s CLI, because vLLM is a good preview of what happens when an inference engine accumulates years of flags, modes, and “just one more option” requests. The goal here is not to imitate vLLM; it’s to learn from its successes and avoid inheriting its pain.

## Context and motivation

We repeatedly see users struggle with “what exact incantation do I need?” and “which module path is correct?” because SGLang exposes multiple operations as separate Python module entrypoints with no unified discovery mechanism. The net effect is that the interface leaks implementation details: users are coupled to our package structure.

A unified CLI should make common workflows obvious and stable. It should also give us a place to enforce consistent validation and error messages, rather than distributing that responsibility across multiple `__main__` blocks and scripts.

## Proposed interface

The entry point is `sglang`. The initial command surface is:

```text
sglang launch
sglang chat
sglang complete
sglang batch
sglang bench <subcommand>
```

Benchmarks are intentionally grouped as a subtree so they remain discoverable without polluting unrelated command help:

```text
sglang bench latency
sglang bench serving
sglang bench throughput
```

Whether the canonical verb is `launch` or `serve` is open; if we pick one, we should almost certainly provide the other as an alias for familiarity across ecosystems.

## Design principles

This CLI should be discoverable via `--help`, stable under internal refactors, and responsive for trivial operations like `--version` and `--help`. It should fail fast on invalid combinations of flags before expensive initialization. It should also be maintainable: the CLI will grow over time, and we should be wary of designs that force us into thousands of lines of plumbing or a proliferation of one-off parsing hacks.

The vLLM study is relevant here because vLLM demonstrates both ends of the spectrum: they have real rigor in validation and reuse, and they also show how a CLI can accumulate framework-wrestling code once it reaches a certain scale.

## Architecture

This proposal separates the CLI into three layers: a command framework, a command registry, and a configuration layer. The layers are small, but the separation matters, because it determines whether the CLI remains a thin interface or becomes a second system.

### Command framework (parsing, help, completion)

The command framework is responsible for parsing options, rendering help, and dispatching to the correct subcommand. The recommendation is Typer (built on Click), rather than argparse.

This recommendation is directly informed by vLLM. vLLM uses argparse and has clearly invested substantial engineering to keep it usable at scale. That investment is instructive. Their CLI lives under `vllm/entrypoints/cli/`, and their OpenAI-server-facing CLI args are built in `vllm/entrypoints/openai/cli_args.py`. The net result is functional, but it is also an example of “argparse at scale” creating its own engineering surface area: custom action classes, help filtering utilities, parallel parser construction for docs, and explicit command wiring.

In vLLM, the amount of code dedicated to “making argparse behave like a modern CLI” is not incidental; it is the dominant cost once the CLI becomes featureful. This RFD’s bias toward Click/Typer is essentially a decision to not re-implement that layer ourselves.

There is also a responsiveness concern. vLLM’s `vllm/entrypoints/cli/main.py` has explicit lazy import structure to keep `--version` and `--help` fast. The fact that they had to do that is not a criticism; it’s an honest signal about what happens if CLI parsing is tightly coupled to importing the world. We should treat “help must be fast” as a design constraint from the start, regardless of framework.

### Command registry (structure, dispatch, lazy imports)

The registry organizes subcommands and dispatches execution. The important design point is that dispatch should support lazy imports so that running `sglang --help` does not import or initialize GPU/model-related code.

vLLM provides two notable patterns here. First, they use a top-level list of command modules (`CMD_MODULES`) and import them only when needed in `vllm/entrypoints/cli/main.py`. This keeps the CLI responsive, but it also creates a manual wiring point: every new command requires editing a central list. That is easy to forget, and it is an example of “mechanical friction” that tends to show up as user-visible incompleteness (“why doesn’t my command appear?”) rather than a clean failure.

Second, vLLM uses a base class shape for subcommands (`CLISubcommand` in `vllm/entrypoints/cli/types.py`) and an argparse pattern where a callback is injected into the parsed namespace via `set_defaults()`, then executed after parsing. This works, but it ties command dispatch to argparse’s data model, and it subtly encourages the command’s “definition” and “execution” to be scattered (parser building in one place, validation elsewhere, execution somewhere else).

For SGLang, the intent is to keep the registry explicit but low-friction. If we use Typer/Click, subcommand registration is naturally structural (functions grouped under commands), and help is scoped by default without filtering hacks. We still need to be disciplined about imports: the handler for `launch` should import the server implementation only when invoked, not at module import time.

### Configuration layer (mapping flags to validated config)

The configuration layer maps CLI options into typed configuration objects that are used by the engine/server. This is where we get reuse (CLI and programmatic entrypoints share the same config) and where we can place validation in one coherent location.

vLLM does something genuinely good here. They centralize a large portion of CLI option definition and reuse through `FrontendArgs` and related configuration constructs, and they reuse parser construction between the CLI and the API server entrypoint rather than duplicating flags by hand. The compositional pattern in `make_arg_parser()` (in `vllm/entrypoints/openai/cli_args.py`) is a strong signal that “one configuration definition reused across entrypoints” is the right direction.

However, vLLM also demonstrates the cost of marrying that configuration layer to argparse. Where options require structured parsing, they end up with bespoke argparse Action classes such as `LoRAParserAction` to support multiple input formats, and various workarounds for JSON-like values. None of this is conceptually difficult, but it forces parsing logic into framework-specific corners, which makes it harder to test, harder to read, and easier to accidentally break.

This RFD therefore proposes that SGLang’s configuration layer should be framework-agnostic. The CLI can adapt options into a typed configuration object; validation then happens on that object before we do expensive initialization. The CLI framework should not be the place where we encode half of our configuration semantics.

## vLLM study: what we should explicitly learn from

vLLM’s strongest pattern is fail-fast validation before expensive work. Their serve command validates parsed args (for example, ensuring option combinations are coherent) before model loading. This is exactly the user experience we want: if the configuration is invalid, the user should learn that immediately, not after waiting for GPU initialization and model load.

Their second strong pattern is import discipline. The explicit lazy import scaffolding in their CLI entrypoint is a sign that performance and reliability matter even for mundane CLI operations. A CLI that occasionally triggers heavyweight imports during `--help` will feel “broken” even if it’s technically correct.

Their third strong pattern is composition of argument sources: serving options, frontend options, engine options are assembled together, which reduces duplication.

Where vLLM appears to struggle is in all the code that exists purely to compensate for argparse ergonomics at scale. Help filtering is an especially telling example: once commands have 100+ flags, you either accept overwhelming help output or you build your own filtering layer. vLLM builds a filtering layer. That’s a rational outcome, but it’s also an outcome we can avoid by choosing a framework that naturally scopes help to the relevant command and supports grouping without custom introspection.

Similarly, documentation generation pressure shows up as parallel parser construction (`create_parser_for_docs()`), which is a classic drift risk. This is not a vLLM-specific mistake; it is a common failure mode when “the runtime definition” and “the documentation definition” are not the same artifact. We should design SGLang’s CLI so that docs can be generated from the actual commands without reconstructing them.

Finally, manual dispatch wiring (the need to register commands in a central list) is not catastrophic, but it is the kind of tax that accumulates as the command set grows. It is also the kind of tax that disproportionately affects contributors, because the “happy path” is to implement the command logic, not to remember to edit a registry file. Our design should bias toward structures where commands appear by construction, not by ceremony.

## Implementation details

Command handlers should be thin adapters. Each handler should construct a configuration object from the CLI options, validate it, and then call an internal API to do the real work.

The key non-negotiable is that configuration validation happens before expensive initialization. That includes validating cross-flag constraints, file existence, template compatibility, and any “mode implies constraint” rules. vLLM’s validation pattern is a good example to follow here; we just want it expressed in our configuration layer rather than scattered across parsing glue.

Benchmarks should be implemented as nested subcommands with a discovery mechanism that does not require heavyweight imports for top-level help. vLLM’s benchmark subtree uses subclass-based discovery, which is clever and keeps wiring minimal, but it relies on imports that may or may not be cheap depending on module structure. For SGLang, the requirement is simpler: entering `sglang bench --help` can afford to import benchmark command definitions; `sglang --help` should not.

## Backward compatibility

Existing module-based invocations should remain supported for at least one deprecation window, but should warn and point users to the new CLI. Internally, the module entrypoints should become thin wrappers around the same functions used by the new CLI, so we do not maintain two logic paths.

## Alternatives considered

Argparse is the obvious alternative, and vLLM proves it can be made to work. The reason to not choose it is that the long-term steady-state appears to require a non-trivial amount of framework-specific plumbing: custom parsing actions, help filtering, doc parser duplication, and manual dispatch scaffolding. Choosing Click/Typer is a decision to avoid re-learning those lessons.

Keeping module-based invocation avoids work in the short term but keeps the user experience coupled to internal code structure and does not address discoverability.

## Risks and tradeoffs

A unified CLI is a user-facing contract. Once users adopt `sglang launch ...`, we need to treat option names and semantics as stable and versioned. That argues for being deliberate now, especially about naming, defaults, and grouping.

Lazy imports improve responsiveness but require discipline in module boundaries. vLLM’s explicit lazy import work is a reminder that this is not optional if we want a CLI that feels reliable.

Unifying configuration will require some refactoring. The payoff is that validation, reuse, and documentation become tractable rather than duplicated.

## Open questions

We should decide whether the canonical verb is `launch` or `serve`, and whether we want aliases.

We should decide whether a config-file format is in scope for the first iteration. Even if we defer it, we should ensure the configuration layer makes it easy to add later.

We should decide how much extensibility we want for benchmarks: internal-only is simplest; plugin-style is powerful but adds surface area.

## Determination

We should build a unified `sglang` CLI. The design should incorporate vLLM’s clear successes—fail-fast validation, argument composition, and import discipline—while avoiding the long-term argparse complexity that vLLM’s codebase demonstrates in practice. The CLI should be a thin layer over typed configuration and internal APIs, not a second implementation of SGLang’s behavior.
