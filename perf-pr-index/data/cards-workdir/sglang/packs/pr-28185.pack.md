## PR body
```markdown
## Motivation

Linear-attention models (KDA, GDN / Gated DeltaNet) keep one compact recurrent **state** per sequence instead of a growing KV cache. SGLang already caches these states in the radix tree (`MambaRadixCache`) so a shared prefix's state can be restored on a hit instead of recomputed.

The problem is **capacity**. The active mamba state pool stores one **bf16** state per cached prefix, and that pool is sized to the running set, not to the cache. Measured on a linear-attn model: the token-KV pool holds millions of tokens, but the mamba pool saturates at a small number of checkpoints and is **length-independent** (one full state per cached *sequence*). As the number of **distinct** cached prefixes grows past the pool size, prefix reuse collapses — the KV tokens are still resident, but the states get evicted and recomputed. This is the dominant cost for workloads with **many distinct short/medium prefixes** (multi-doc RAG, many short sessions, agentic fan-out).

## Modifications
This PR introduces an optional, dedicated **int8 checkpoint pool** for the radix-cached linear-attn states, behind `--enable-int8-mamba-checkpoint` (off by default).

- The radix-cached temporal (SSM) state is stored as **int8** with a per-`(head, k-channel)` symmetric scale (`Int8CheckpointStore`, already in tree). The conv1d window stays bf16 (tiny).
- Each cached state takes ~1 byte/element instead of 2, so at roughly the same memory the pool holds **~2× more distinct prefixes**, moving the reuse-collapse knee out by 2×.

### Why int8, and why a separate pool

- **Quality-safe by construction.** A state is quantized **once on store** and dequantized **once on a hit** — it never re-enters the recurrence, so there is no error accumulation.
- **int8 beats fp8** for this data: the linear-attn recurrent state is ~uniformly distributed (an accumulated sum of rank-1 updates), so fp8-e4m3 wastes bits on an exponent it doesn't need; int8-per-channel spends all 8 bits on mantissa precision (≈0.5% vs ≈0.7% decode error at 1 byte).
- **Separate pool** because the recurrence kernels need bf16 working memory — running requests cannot read int8 slots directly. So we keep an *active* bf16 pool (kernel-facing, sized to the running set) and an *int8 checkpoint* pool (radix-cached states). A donate quantizes active → int8; a cache hit copy-on-writes dequantize int8 → active.

### Strategy-agnostic donate hook (spec-KDA-ready)

Both scheduler strategies converge on the same point — "an active slot becomes the cached `mamba_value`": `no_buffer` via a copy, `extra_buffer` via the ping-pong track buffer (the spec path). The quantize hook lives at that common convergence point, so a single implementation covers both, including the future spec path.

## Design

<img width="3106" height="1410" alt="image" src="https://github.com/user-attachments/assets/0b9c0abc-3217-4686-be92-e8ac1105223d" />


Today (baseline) the radix-cached linear-attn states live in the **same** bf16 `MambaPool` as the running requests: a cached node's `mamba_value` is just a slot in that one pool, and on a hit it is `copy_from`'d bf16→bf16 into a fresh slot. So the cache and the working set compete for one pool, and every cached prefix costs a **full bf16 state** — the pool saturates at a small number of checkpoints and prefix reuse collapses. This PR splits them: a **small bf16 working pool** (running set, kernel-facing) + a **separate, compact int8 checkpoint pool** (the cache). The expensive, growing part — the cache — is the one that gets compressed.

| | baseline (shared bf16 pool) | this PR (bf16 working + int8 cache) |
|---|---|---|
| pools | one bf16 pool (running + cache) | small bf16 working pool + separate int8 cache pool |
| where cached states live | in the bf16 pool (`mamba_value` = bf16 slot) | in the int8 pool (`mamba_value` = int8 slot) |
| bytes per cached prefix | a full bf16 state | int8 (≈ half) |
| cache capacity | `pool_size − running_set`, bf16-expensive → small | independent int8 pool → ~2× at the same bytes |
| cache hit | `copy_from` bf16→bf16 (no quant) | dequantize int8→bf16 (COW, forward stream) |
| working-pool size | grows with the cache (coupled) | stays small (sized to concurrency) |

**Advantages of the int8 design:**

- **~2× more distinct prefixes cached at the same memory** — directly lifts the reuse-collapse knee (256 → 512 in the A/B below), so high-distinct-prefix workloads (multi-doc RAG, many concurrent sessions, agentic fan-out) keep hitting the cache instead of recomputing the state.
- **Cache size is decoupled from the working set.** The baseline forces one pool to hold both, so a bigger cache means a bigger bf16 pool — which also drags the KV-cache budget down. Here the bf16 pool stays small (sized to concurrency) while the int8 cache grows independently, giving a big cache **and** a high KV budget (see the memory table) — something the single-pool design cannot do.
- **Spend the 2× either way** — as more cached prefixes, or as the same cache at ~half the mamba HBM (freeing HBM for KV → longer context / higher concurrency).
- **Quality-safe and isolated** — quantize-once-on-store / dequantize-once-on-hit (the state never re-enters the recurrence; within the serving stack's own noise on GSM8K), off by default, and the baseline bf16 path is byte-for-byte unchanged when disabled.

## Flags

- `--enable-int8-mamba-checkpoint` (bool, default off): store radix-cached linear-attn states as int8.
- `--int8-mamba-ckpt-size` (int, optional): number of int8 checkpoint slots; defaults to `2 × max-mamba-cache-size`.

## Validation

Validated on **Qwen3.5-35B-A3B** (GDN-hybrid) on 4×H20-3e. The int8 mem-cache path is GDN/KDA-agnostic (both flow through the same `MambaPool` + `MambaRadixCache` + `chunk_gated_delta_rule` path), so this validates the integration model-independently.

### Capacity + latency/throughput — A/B

Via the committed benchmark `benchmark/bench_linear_attention/bench_int8_checkpoint_reuse.py` (Qwen3.5-35B-A3B, `extra_buffer`, `--max-mamba-cache-size 256` → active 256 / int8 512, prefix ~1000 tokens, parallel 8), run against the server with vs. without `--enable-int8-mamba-checkpoint`:

| K (distinct prefixes) | reuse_frac (bf16 → int8) | probe p50 ms (bf16 → int8) | probe throughput rps (bf16 → int8) |
|---|---|---|---|
| 128 (both fit) | 0.940 → 0.940 | 149.9 → 152.4 | 46.9 → 50.6 |
| **384 (bf16 collapsed)** | **0.020 → 0.940** | **204.1 → 150.5** | **36.9 → 49.0** |
| 640 (both exceed pool) | 0.000 → 0.048 | 204.1 → 207.5 | 37.7 → 36.7 |

The reuse-collapse knee moves **256 → 512 (≈2×)**. In the band 256 < K ≤ 512 — where the baseline has collapsed but int8 still serves prefixes from cache — int8 delivers **~47× more prefix reuse, ~26% lower probe-prefill latency, and ~33% higher throughput** (K=384), because the probe is a cheap cache hit instead of a full prefix recompute. Below the bf16 pool size (K=128) int8 is on par (no overhead); above the int8 pool size (K=640) both collapse, as expected. 0 errors / crashes / leaks in both runs.

### Memory efficiency — same cache, less mamba HBM, KV decoupled

The other way to spend the 2× density: cache the same number of distinct prefixes using far less mamba HBM, and keep the KV budget high. int8 decouples the cache from the active pool, so a small active pool drives the KV budget while a large int8 pool holds the cache (Qwen3.5-35B-A3B, per card):

| config | cache cap | mamba HBM | max_total_num_tokens |
|---|---|---|---|
| bf16 single pool 1280 | ~1280 | ssm 18.76 + conv 0.44 = **19.2 GB** | 8.32M |
| **int8** (256 active + 1024 ckpt) | ~1024 | 3.85 (active) + **4.16** (int8) = **8.0 GB** | 9.93M |

bf16 forces a trade-off — a big cache needs a big pool, which drops the KV budget (8.32M). int8 gives a big cache *and* the high KV budget of a small pool (9.93M), caching ~1024 prefixes at ~4 MB each vs bf16's ~15 MB. **Caveat (follow-up):** the int8 pool's HBM is not yet subtracted from the KV-budget computation (int8's max_total equals the 256-pool value; the pool currently rides on GPU headroom). It should be accounted; even when accounted the mamba footprint (8 vs 19.2 GB) wins.

### Quality / precision — does int8 degrade output?

Three levels of evidence, each isolating the int8 effect from the serving stack's noise. **Headline: no systematic task-accuracy degradation; the perturbation is small, bounded, and does not compound with cache depth.**

**1. Mechanism (why it's bounded).** The state is quantized once on store and dequantized once on a hit — it never re-enters the recurrence as a quant→dequant loop. On chained cache extensions the dequantized state *does* continue the recurrence, but the gated-delta rule is contractive (per-channel decay α<1 plus a negative-semidefinite delta-rule Jacobian), so an injected quantization error is attenuated geometrically. Measured on a faithful fp32 gated-delta recurrence driven through the real codec: the accumulated state error **saturates** (does not grow with depth) — ~6.6e-3 at 1 checkpoint → ~1.3e-2 by 32 chained checkpoints → flat through 128 (seq 2048). The per-(head,k-channel) scale matches the per-k-channel decay, so the dominant large state entries keep ~bf16 precision and the error concentrates on small entries that barely affect the readout `o = Sᵀq`.

**2. Logit-level isolation (real model, deterministic).** On prefix-extension cache hits where int8 dequant actually fires (Qwen3.5-35B-A3B, TP1 greedy → run-to-run deterministic, so the noise floor is exactly 0), the next-token distribution shifts by **KL ≈ 6e-3** (max ~0.5 nats on a tail token), with **greedy top-1 unchanged** in every probe. For reference, loading a *bf16* cached state instead of recomputing is itself not bit-exact (KL ≈ 5e-4); int8 is ~10× that already-accepted baseline and, crucially, never diverges from the bf16 path.

**3. Task accuracy (GSM8K, int8 dequant confirmed firing).** Qwen3.5-35B-A3B, 200 questions, 5-shot, greedy, `extra_buffer`, with the int8 dequant path instrumented and **confirmed firing 599×** (≈ every question × 3 runs). WARM = cache reused from the int8 pool; COLD = `flush_cache` per question = full bf16 recompute (deterministic baseline); a bf16-reuse server is the control.

| config | COLD (bf16, deterministic) | WARM accuracy band (3 runs) | WARM run-to-run agreement |
|---|---|---|---|
| **int8** (dequant ×599) | 0.805 | **0.832 [0.830–0.835]** | 0.86 |
| bf16 (control) | 0.805 | 0.842 [0.815–0.855] | 0.89 |

int8's WARM band sits **inside** bf16's; the ~1pp mean gap is well within the reuse path's run-to-run churn. Both WARM means exceed the COLD baseline (0.805), which confirms the warm-vs-cold spread is trajectory-shuffling noise, not a quality change — quantization cannot *raise* accuracy. **The cache-reuse path is itself non-deterministic** under overlap scheduling (even bf16 warm-vs-warm agrees on only ~89% of answers, and the reused-token count varies run-to-run), which is why accuracy is reported as a band over a deterministic cold baseline rather than a single number.

**Methodology note (important for reproducing).** int8 is only exercised when the cached prefix is genuinely reused from the int8 pool, which requires `--mamba-scheduler-strategy extra_buffer`: `no_buffer` only snapshots state at the full-sequence leaf, so a fixed-prefix / divergent-question workload (few-shot GSM8K, or the divergent-suffix benchmark) reuses ~0 mamba state and int8 dequant **almost never fires** (measured: 2 dequant calls in a 50-question `no_buffer` run vs 599 with `extra_buffer`). Any int8 quality claim must instrument the dequant count to confirm the path is actually live — a naive GSM8K run under the default `no_buffer` measures bf16, not int8.

### Correctness — both scheduler strategies

- `extra_buffer`: store / match / int8-dequant-COW correct; reuse stable across repeated probes.
- `no_buffer`: int8 store/match/COW also correct (an appended-suffix probe hits cleanly, cached 663/666). NOTE: `no_buffer` shows low prefix reuse on a divergent-suffix workload **by strategy design** (it only snapshots state at the full-sequence leaf, so a divergent suffix lands on a `_split_node` with `mamba_value=None`) — this is unchanged from baseline `no_buffer`, not specific to int8. Mid-sequence prefix reuse requires `extra_buffer`'s track-buffer.
```

```diff
+MambaCheckpointPool — the radix prefix cache's int8-compressed store for cached
+linear-attention (KDA / GDN / Mamba2 gated-delta-rule) recurrent states.
+
+It decouples the *cached* states (radix-owned, idle, compressed) from the *active*
+``MambaPool`` (running requests, full precision, kernel-facing). The radix stores
+one cached state per node HERE; on a prefix-cache hit it is dequantized back into
+a fresh active slot (copy-on-write).
+
+Per cached slot it holds:
+  * the SSM temporal state in **int8** (per-(head,k-channel) symmetric), via the
+    embedded ``Int8CheckpointStore`` — ~2x more cached states than bf16,
+    quality-safe (quantized once on store, dequantized once on a hit; never
+    re-enters the recurrence as a quant->dequant loop).
+  * the conv1d window state at its native dtype (tiny, W-1 tokens; not worth
+    quantizing).
+
+Why int8 (not fp8): a cached checkpoint is loaded ONCE on a cache hit, then
+decoding continues at full precision, so the only error is a single rounding of
+S. The temporal state is roughly uniformly distributed, so int8-per-(head,
+k-channel) beats fp8-e4m3 at the same 1 byte (fp8 wastes bits on the exponent).
+The scale axis (reduces over d_v) matches the per-k-channel decay diag(alpha), so
+the large state entries keep ~bf16 precision and the error concentrates on small
+entries that barely affect the readout. Storing cached states int8 gives ~2x the
+cached-prefix capacity at fixed memory, and composes with host-offload
+(HiMambaRadixCache) which it also halves.
+
+This is strategy-agnostic: whether the active slot to be cached was produced by
+the ``no_buffer`` donate (copy_from) or the ``extra_buffer`` ping-pong track
+buffer (spec path), both converge on "an active slot becomes the cached
+``mamba_value``" — which is exactly the (store_from_active) hook here. Slot
+lifecycle is owned by the caller via the embedded ``MambaSlotAllocator``.

+class Int8CheckpointStore:
+    """int8 store for cached multi-layer linear-attn states.
+
+    Tensors (slot index handed out by the caller's allocator):
+        qdata : [L, num_slots, H, d_v, d_k]  int8        (the quantized state)
+        scale : [L, num_slots, H, 1,   d_k]  scale_dtype  (per layer,slot,head,k-chan)
+
+    A "state" spans all L mamba layers for one cached point (matching how the
+    radix caches one full state per node). The reduction axis for the scale is
+    d_v (dim=-2), so each (head, k-channel) gets its own scale — aligned with the
+    per-k-channel decay diag(alpha).
+
+    ``scale_dtype`` should match the source state's dtype (bf16 / fp16 / fp32) so
+    that quantize and dequantize use the identical scale — it is NOT required to
+    be bf16.
+    """
+
+    QMAX = 127
+
+    def __init__(
+        self,
+        *,
+        num_layers: int,
+        num_slots: int,
+        num_heads: int,
+        head_v_dim: int,
+        head_k_dim: int,
+        device: str,
+        scale_dtype: torch.dtype = torch.bfloat16,
+    ):
+        self.num_layers = num_layers
+        self.num_slots = num_slots
+        self.H = num_heads
+        self.d_v = head_v_dim
+        self.d_k = head_k_dim
+        self.device = device
+        self.qdata = torch.empty(
+            num_layers,
+            num_slots,
+            num_heads,
+            head_v_dim,
+            head_k_dim,
+            dtype=torch.int8,
+            device=device,
+        )
+        self.scale = torch.empty(
+            num_layers,
+            num_slots,
+            num_heads,
+            1,
+            head_k_dim,
+            dtype=scale_dtype,
+            device=device,
+        )
+
+    # ---- (de)quant math (also usable standalone for probes/tests) ----
+
+    @classmethod
+    def quantize(cls, state: torch.Tensor):
+        """state [..., H, d_v, d_k] -> (qint8, scale[..., H, 1, d_k]).
+
+        amax / scale / round are computed in float32 so quantizing a low-precision
+        state doesn't lose precision in the intermediate (symmetric with
+        ``dequantize``, which is already float32). The scale is rounded to the
+        state dtype (its storage precision) BEFORE the division, so quantize and
+        dequantize use the identical scale."""
+        state_fp32 = state.to(torch.float32)
+        amax = state_fp32.abs().amax(dim=-2, keepdim=True).clamp(min=1e-8)
+        scale = (amax / cls.QMAX).to(state.dtype)
+        q = (
+            torch.round(state_fp32 / scale.to(torch.float32))
+            .clamp(-cls.QMAX, cls.QMAX)
+            .to(torch.int8)
+        )
+        return q, scale
+
+    @staticmethod
+    def dequantize(q: torch.Tensor, scale: torch.Tensor, out_dtype: torch.dtype):
+        return (q.to(torch.float32) * scale.to(torch.float32)).to(out_dtype)
+
+    # ---- store / load (caller supplies slot indices) ----
+
+    def store(self, slots: torch.Tensor, state: torch.Tensor) -> None:
+        """Quantize and write states. state: [L, N, H, d_v, d_k] for the N slots
+        (or [L, H, d_v, d_k] when slots is a scalar/len-1)."""
+        if state.dim() == 4:
+            state = state.unsqueeze(1)
+        q, scale = self.quantize(state)
+        self.qdata[:, slots] = q
+        self.scale[:, slots] = scale.to(self.scale.dtype)
+
+    def load(self, slots: torch.Tensor, out_dtype: torch.dtype) -> torch.Tensor:
+        """Dequantize states at slots -> [L, N, H, d_v, d_k] in out_dtype."""
+        return self.dequantize(self.qdata[:, slots], self.scale[:, slots], out_dtype)
+
+    def copy_to_pool(
+        self,
+        dst_temporal: torch.Tensor,
+        src_slots: torch.Tensor,
+        dst_slots: torch.Tensor,
+    ) -> None:
+        """Dequantize checkpoints at ``src_slots`` directly into the active pool
+        tensor ``dst_temporal`` [L, pool_slots, H, d_v, d_k] at ``dst_slots`` (the
+        copy-on-write on a cache hit). Output dtype follows ``dst_temporal``."""
+        dst_temporal[:, dst_slots] = self.load(src_slots, dst_temporal.dtype)
+
+    def store_from_pool(
+        self,
+        src_temporal: torch.Tensor,
+        src_slots: torch.Tensor,
+        dst_slots: torch.Tensor,
+    ) -> None:
+        """Quantize states from an active pool tensor into checkpoint slots (cache
+        store / donate)."""
+        self.store(dst_slots, src_temporal[:, src_slots])
+
+    def mem_usage_bytes(self) -> int:
+        return (
+            self.qdata.numel() * self.qdata.element_size()
+            + self.scale.numel() * self.scale.element_size()
+        )
+
+    def bytes_per_slot(self) -> int:
+        return self.mem_usage_bytes() // max(1, self.num_slots)

+

+
+    def free(self, slots: torch.Tensor):
+        self.allocator.free(slots)
+
+    def available_size(self) -> int:
+        return self.allocator.available_size()
+
+    def clear(self) -> None:
+        """Release every checkpoint slot (radix flush/reset). The int8 qdata is
+        left as-is; slots are reused/overwritten on the next store."""
+        self.allocator.clear()
+
+    # ---- state transfer between the active MambaPool and this store ----
+
+    def store_from_active(self, active_mamba_pool, active_slots, ckpt_slots) -> None:
+        """Quantize temporal + copy conv from the active pool into checkpoint slots
+        (the radix donate / cache-store)."""
+        cache = active_mamba_pool.mamba_cache
+        self.temporal.store_from_pool(cache.temporal, active_slots, ckpt_slots)
+        for i, c in enumerate(self.conv):
+            c[:, ckpt_slots] = cache.conv[i][:, active_slots]
+
+    def load_to_active(self, active_mamba_pool, ckpt_slots, active_slots) -> None:
+        """Dequantize temporal + copy conv from checkpoint slots into the active pool
+        (the cache-hit copy-on-write)."""
+        cache = active_mamba_pool.mamba_cache
+        self.temporal.copy_to_pool(cache.temporal, ckpt_slots, active_slots)
+        for i, c in enumerate(self.conv):
+            cache.conv[i][:, active_slots] = c[:, ckpt_slots].to(cache.conv[i].dtype)
+
+    @staticmethod
+    def estimate_mem_usage_bytes(
+        *,
+        num_layers: int,
+        num_slots: int,
+        num_heads: int,
+        head_v_dim: int,
+        head_k_dim: int,
+        conv_shapes: List[tuple],
+        conv_dtype: torch.dtype,
+        temporal_dtype: torch.dtype,
+    ) -> dict:
+        """Estimate the pool's HBM footprint (bytes) WITHOUT allocating, so a
+        caller can check it against free memory before construction. Mirrors the
+        real layout: int8 qdata + per-(head,k) scale + bf16 conv windows, including
+        the reserved slot 0."""
+        slots = num_slots + 1  # slot 0 reserved (matches MambaSlotAllocator)
+        scale_isz = torch.empty((), dtype=temporal_dtype).element_size()
+        conv_isz = torch.empty((), dtype=conv_dtype).element_size()
+        qdata = num_layers * slots * num_heads * head_v_dim * head_k_dim  # int8 = 1B
+        scale = num_layers * slots * num_heads * head_k_dim * scale_isz
+        conv = 0
+        for shape in conv_shapes:
+            n = 1
+            for s in shape:
+                n *= int(s)
+            conv += num_layers * slots * n * conv_isz
+        return {
+            "qdata": qdata,
+            "scale": scale,
+            "conv": conv,
+            "total": qdata + scale + conv,
+        }
+
+    def mem_usage_bytes(self) -> int:
+        conv_bytes = sum(c.numel() * c.element_size() for c in self.conv)
+        return self.temporal.mem_usage_bytes() + conv_bytes
```
