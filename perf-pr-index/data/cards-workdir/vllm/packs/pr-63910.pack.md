## Overview

GLM-5.3-Flash on ROCm: the kpool sparse indexer (`vllm/models/glm5next/amd/sparse_indexer.py`) launches int32↔int64 casts, a `+1`, a `-1` fill and a buffer copy around `expand_pools_and_append_tail` in every sparse-attention layer. This PR lets the expand kernel read int32 pool ids and int64 positions as they are (the `+1` moves into the kernel) and write straight into `topk_indices_buffer`, removing 6 launches per sparse-attention layer, 66 per decode step.

## Claims

- 1.7–4.4% lower median TPOT at 1–32 concurrent requests on 1k/1k, 8k/1k, 64k/1k and 128k/1k (MI355X, TP4, `amd/GLM-5.3-Flash-Quark-MXFP4`) against the same ROCm nightly without this PR, and 0.9–1.8% at 64; flat at 64k c16 (−0.2%), where each step carries other requests' long prefill. Two runs per arm on swapped GPU halves; every point except 128k c8 moves the same way in both runs. 128k c8 is +2.1%, inside its run-to-run spread (the arm's two runs differ by 5.7%, see below); the change only removes launches.
- With MTP (multi-token decode rows, padded layout): median TPOT −1.6% geomean with MTP3 (acceptance identical in both arms) and −1.5% with MTP5 (median of three runs per arm).
- A decode step issues 66 fewer kernels (1,295 → 1,229) and 308 µs less kernel time under the profiler.
- Accuracy unchanged: GSM8K 0.920 vs 0.921, GPQA-Diamond 0.904 and 0.909 vs 0.914 and 0.894. RULER NIAH (`niah_single_2`, 64k) scores 1.0 with this PR at TP2, TP4 and TP8, with MTP off, 3 and 5.
- gfx942 (MI325X, `zai-org/GLM-5.3-Flash` FP8, TP4): total throughput +1.9% geomean, every one of 15 points faster (+0.5% to +3.5%); accuracy unchanged.
- Unchanged: the NVIDIA kpool indexer and every other model.

## Details

- `expand_pools_and_append_tail(..., seq_len_offset=1, out=topk_indices_buffer[rows])`: reads `positions` directly (int64) and computes `seq_len = pos + 1` in-kernel; writes the full buffer row, `-1` past `topk + pool_size - 1`, so the caller's `-1` fill only covers rows after the decode rows on the uniform layout. Each decode return taken under that skip is marked in the code as having to write full width.
- `_kpool_decode_update_batched_kernel` takes int64 positions (no narrowing copy).
- Pool ids stay int32 (< 65k pools), so `pid * pool_size` fits.
- Prefill chunks get the same direct write.
