## 正文(PRD / 提案全文)

### Motivation.

Currently, when using sleep mode and wake_up() for RLHF, like in [verl](https://github.com/volcengine/verl/tree/main), we can run into issues like [here](https://github.com/volcengine/verl/issues/302), where we run into OOMs when waking up the vllm engine due to additional copies of the model living on the same GPU.

The issue in verl specifically lives in the [fsdp_vllm sharding manager](https://github.com/volcengine/verl/blob/main/verl/workers/sharding_manager/fsdp_vllm.py#L94), where when we want to update weights for the woken up vllm engine, we have memory allocated for the old discarded weights, discarded kv cache, as well as the new copy of the weights all on the same gpu. A simplified version of this code is shown below, as well as a diagram demonstrating how OOM happens.

```python
params = self.fsdp_module.state_dict() # new weights on GPU
self.inference_engine.wake_up() # old weights + kv_cache memory allocated -> this can cause OOM for big models!
self.inference_engine.llm_engine.model_executor.driver_worker.worker.model_runner.model.load_weights([(name, param) for name, param in params.items())])
```


<img width="492" alt="Image" src="https://github.com/user-attachments/assets/9b9f47da-27ca-421b-9d6f-1a9bfe022885" />

One thing here to note is that technically these issues can be avoided by offloading our new model weights to CPU, and then loading weights into the woken up VLLM engine from CPU, however since most RLHF libraries want to optimize weight transfer by using NCCL to keep weights on GPU, we typically want to avoid offloading to CPU whenever possible.

### Proposed Change.

To fix this issue, I propose both a temporary improvement as well as a later milestone
1. (Temporary Improvement) Add support for separately calling `wake_up(tags=(”weights”,))`, and `wake_up(tags=(“kv_cache”)`. Example shown below:
```python
model = "Qwen/Qwen2.5-32B"
train_model = AutoModelForCausalLM.from_pretrained(model).to("cuda")
llm = LLM(model, enable_sleep_mode=True)
llm.sleep(level=2)
new_weights = train(train_model).state_dict() # train does some gradient update on the model 
llm.wake_up(tags=("weights")) # reallocate just the weights in memory
llm.inplace_update_weights(new_weights) # update from other gpu located model
del new_weights # clear memory 
torch.cuda.empty_cache()
llm.wake_up(tags=("kv_cache")) # now allocate kv cache memory
```

<img width="635" alt="Image" src="https://github.com/user-attachments/assets/37033bed-67a6-4578-9355-7111aaf719ec" />

   - This could help avoid OOMs when updating larger models (i.e. 32B on an A100-80G) and allow for higher gpu memory utilization to be set in RLHF libraries like verl
   - In the V1 engine, this would also require adding a collective_rpc call like `llm.inplace_update_weights(new_weights)` to update the weights in place given a new set of weights (in v0 you could directly access model.load_weights) 

2. (Later milestone) Add support for fully fine grained in place weight updating via an api like `llm.wake_up_with_weights(new_weights)`
- This would mean adding some endpoint in the `CumemAllocator` to do `wake_up_with_weights(new_weights)`, where we interleave memory remapping, copying the new weights over, and freeing the new weights memory once they are copied into the vllm engine memory.
 - This would result in the lowest possible gpu memory allocation at peak time, but might require modifying model code to handle getting per layer weight loaders
