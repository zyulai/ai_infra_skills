### Motivation

## TL;DR
I am implementing a new speculative decoding method **PRISM**. PRISM routes each draft step to different transformer layers (modules), aiming to improve acceptance length and scalability while keeping draft latency low. I would like maintainer guidance on the best integration path in SGLang.

## Motivation
As mentioned in this [LMSYS blog](https://lmsys.org/blog/2025-12-23-spec-bundle-phase-1/) and [META tech report](https://arxiv.org/abs/2508.08192), large training corpora and multi-layer draft models provide better e2e performance compared to the original EAGLE-3 because of better accuracy of speculation. However, these changes may increase draft model inference overhead and the training cost.

PRISM targets a better tradeoff: increase draft model accuracy and acceptance length without increasing computational cost per draft step.

## PRISM architecture and performance
I provide some architecture details and performance results of PRISM on my SGLang prototype implementation in this SpecForge [issue](https://github.com/sgl-project/SpecForge/issues/444). More results will be shown in the coming preprint.

## Proposed integration path
- Add a new flag to SGLang to enable PRISM.
- Extend existing EAGLE worker to support PRISM.
- Add a new PRISM model in `python/sglang/srt/models`.
- Add a new key-value pair in model's `config.json` to specify the draft step to module mapping in PRISM.
- Modify the `eagle_draft_cuda_graph_runner.py` and `eagle_draft_extend_cuda_graph_runner.py`.

## Questions
- I am implementing PRISM on V1 version of the EAGLE worker. Should I implement PRISM on V2 version?
- I am using the scripts in `benchmark/mtbench` to benchmark PRISM on different benchmark datasets. Should I keep using these scripts, or switch to `python3 -m sglang.bench_serving` as mentioned in the documentation?
- Do you have any suggestions on the proposed integration path or other recommendations?
