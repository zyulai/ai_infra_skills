## Purpose

`_forward_core_rocm` currently gates the AITER GDN decode fast path on `self.gqa_interleaved_layout`, so only Qwen3-Next takes it and flat-layout models (e.g. Qwen3.5, Qwen3.8) fall through to the generic path. #42880 added that guard because the fused reshape+conv kernel only understood Qwen3-Next's packing and read the wrong columns from a flat tensor.

ROCm/aiter#3251 added a `qkvz_layout` parameter handling both. It selects the source index mapping only — outputs stay in canonical order, so the downstream `fused_rearrange_sigmoid_gated_delta_rule` is unchanged — and `"interleaved"` stays the default, so Qwen3-Next is bit-identical. This PR passes the layout through and drops the layout guard. Older AITER builds would raise `TypeError`, so `gdn_fused_conv_supports_qkvz_layout()` probes the signature once (mirroring
`fused_moe_supports_gate_mode()`) and flat layouts keep the guard there.

The fast path returns before the entire generic block, so four kernel launches per GDN layer per step become two: `core_attn_out.zero_()` and `z_out[:] = z` are pure removals, since the AITER kernel writes both buffers including the padding rows above `num_actual_tokens`.

Also adds `vllm/model_executor/layers/mamba/gdn` to the Kernels Mamba `source_file_dependencies`, which did not list it.

## Test Plan

```bash
pytest tests/kernels/mamba/test_gdn_rocm_layout_dispatch.py -q
```

New host-side tests (CPU, no GPU or AITER needed) covering flat dispatch with and without kernel support, Qwen3-Next non-regression on both, batch shapes that must stay generic, and the capability probe. Accuracy uses the `lm_eval` invocation from #42880; performance uses decode traces of `amd/Qwen3.8-2.4T-A95B-Quark-MXFP4` on 8x MI355X.
