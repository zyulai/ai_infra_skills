## 正文(PR 描述)

## Purpose

`resolve_chat_template_content_format` returns an explicitly specified
`--chat-template-content-format` without ever comparing it against the format
detected from the template. The warning that was written to catch exactly that
mismatch has been unreachable since #19735.

## Root cause

#19735 added an early return so that a specified format skips the Jinja AST
parse:

```diff
+    if given_format != "auto":
+        return given_format
...
-    return detected_format if given_format == "auto" else given_format
+    return detected_format
```

Detection also fed `_log_chat_template_content_format`, which has exactly one
caller — below that early return. So the forced path exits before the logger,
and the logger is only ever reached when `given_format == "auto"`. The guard

```python
if given_format != "auto" and given_format != detected_format:
```

is false on every reachable path. `git log -S` puts this at #19735 (June 2025).

## Impact

Forcing a format the template cannot consume fails in one of two ways. Running
vLLM's own detection helpers over the 35 templates in `examples/` (33 usable):

| forced format | outcome |
| --- | --- |
| `auto` | correct on every template |
| `string` | correct on every template |
| `openai` | 17 raise `TypeError`, 8 silently corrupt, 8 fine |

The 17 concatenate with `+` and raise `can only concatenate str (not "list") to
str`, surfacing as HTTP 500. The other 8 interpolate with `{{ message.content }}`,
so Jinja calls `str()` on the list and renders the Python repr into the prompt:

```
### Instruction:
[{'type': 'text', 'text': 'Reply with exactly OK.'}]
```

HTTP 200, no exception, nothing in the logs. For those 8 templates
(`alpaca`, `inkbot`, `teleflm`, `llama3.2_pythonic`, `phi4_mini`, `toolace`,
`xlam_llama`, `xlam_qwen`) this warning is the only signal in the system.

## Changes

- Restore detection before the return and select with a ternary, as the code did
  prior to #19735. The override still wins; only the comparison is added back.
- Gate the info line on `auto`, so users who already passed the flag are not told
  they can pass it to override.
- Cache the resolved content format, so restoring detection does not add
  per-request work (see below).
- Inline the logging and use `info_once` / `warning_once`, removing
  `_log_chat_template_content_format`.

## Test

Verified against `examples/template_chatml.jinja` (detected `string`) and
`tool_chat_template_llama3.1_json.jinja` (detected `openai`):

| template | given | returned | logged |
| --- | --- | --- | --- |
| chatml | `openai` | `openai` | warning |
| chatml | `string` | `string` | — |
| llama3.1 | `openai` | `openai` | — |
| chatml | `auto` | `string` | info |

The override is honoured in every case and only the genuine mismatch warns.

`pytest tests/renderers/test_hf.py` gives 28 passed with the existing
content-format tests unaffected. The 3 failures (`ultravox`,
`Llama-Guard-3-1B`, `paligemma-3b-mix-224`) are `403 Cannot access gated repo`
and reproduce identically on a clean tree. Built and run from source on Apple
Silicon (CPU backend, Python 3.12); `pre-commit run` passes.

## Notes for reviewers

- **This does not close #54486.** That issue asks for the combination to be
  rejected before request handling; this only restores the diagnostic. Filing it
  as the symptom that surfaced the regression.
- **Performance.** Detection now runs even when a format is given, so per
  review it is cached. `lru_cache` was not usable — `tools` is a list and
  `ModelConfig` sets `__eq__` without `__hash__` — so this follows the existing
  `_PROCESSOR_CHAT_TEMPLATES` idiom and keys a bounded dict on the fields that
  select the template. Only the presence of `tools` is in the key: it decides
  whether the processor template is tried, and its contents never reach the AST.
  The bound matters because a request can carry its own `chat_template`.

  Measured on Qwen2-VL-2B, explicit chat template: **~16 us -> 0.109 us** per
  call once warm. With `chat_template=None` it was already ~0.2 us, since
  `_try_get_processor_chat_template` and `_detect_content_format` are memoized;
  the cost sat in `tokenizer.get_chat_template()` on the explicit path. Detected
  format is unchanged against an uncached resolve for all 35 templates in
  `examples/`.

- **Eight advisory warnings.** Forcing `string` on a template that also supports
  `openai` renders correctly but still warns, since the formats differ. That
  seems right — you have silently given up multimodal capability — and the
  warning's own text is advisory. Happy to narrow it to the
  `detected == "string"` direction if preferred.
- **Overlap with #53824.** That PR touches the same two files but a different
  function (`_iter_nodes_assign_content_item`, improving detection accuracy).
  Complementary rather than duplicate — it makes detection more correct, this
  makes a wrong override visible — but there may be a textual conflict in the
  test file depending on merge order.
