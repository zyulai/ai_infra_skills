## 正文(PR 描述)

This PR proposes partially reverting behavior introduced in https://github.com/vllm-project/vllm/pull/37416 while prompting the user to up `max-num-seqs` when current memory isn't enough.
```
(Worker_TP1 pid=509811) ERROR 03-26 18:27:04 [multiproc_executor.py:949] ValueError: max_num_seqs (1024) exceeds available Mamba cache blocks (512). Each decode sequence requires one Mamba cache block, so CUDA graph capture cannot proceed. Please lower max_num_seqs to at most 512 or increase gpu_memory_utilization.
```

A `_is_profiling` flag is piped through `_check_and_update_cudagraph_mode` to skip this check during the "dummy" kv cache creation for profiling.

## Problem

`adjust_cudagraph_sizes_for_mamba_cache` **silently** modifies the shared cudagraph_capture_sizes list, which restricts both PIECEWISE (prefill) and FULL (decode) cudagraph captures. But the Mamba constraint only applies to FULL decode graphs. The PIECEWISE path runs Mamba ops eagerly and is unaffected.

Meanwhile, the FULL decode dispatcher in [cudagraph_dispatcher.py:217-220](vllm/v1/cudagraph_dispatcher.py) already filters decode capture sizes to `<= max_num_seqs * uniform_decode_query_len`, so the real safety check is simply `max_num_seqs <= num_blocks`.

Current implementation can lead to severe issue in performance as initially highlighted in https://github.com/vllm-project/vllm/pull/37416, when the prefill is silently run in eager mode.
