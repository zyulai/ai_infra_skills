## 正文(PR 描述)

## Motivation

DSpark verify reuses `DFlashVerifyInput`, so `_is_dflash_verify()` routes it into the `seq_lens_cpu` branch of the SWA mask update in the NPU attention backend. Unlike DFlash (whose target verify graph runs through the NPU graph runner with on-device `seq_lens`), DSpark's verify graph goes through `decode_cuda_graph_runner`, which passes a CPU tensor (`forward_batch.seq_lens.cpu()` during capture, `buffers.seq_lens_cpu` on replay). Comparing it against the on-device `swa_indices` buffer raised:

```
RuntimeError: Expected all tensors to be on the same device. Expected NPU tensor, please check whether the input tensor device is correct.
```

This crashes the target model at graph capture time, so DSpark cannot run on Ascend NPU with hybrid SWA layers.

## Modifications

One-line fix in `ascend_backend.py` (`_apply_cuda_graph_metadata`): move `seq_lens_int` to the backend device before the SWA mask comparison:

```python
seq_lens_int = seq_lens_cpu[:bs].int().to(self.device)
```

- No-op for the DFlash path (its `seq_lens_cpu` is already on-device).
- Side benefit: DSpark now also gets the correct SWA mask window (`seq_lens_cpu` = prefix + block_size), so draft KV positions stay unmasked instead of being masked out by the prefix-only `seq_lens`.
- The copy runs in replay prep (outside the captured graph) and moves `bs × 4` bytes, so the performance impact is negligible.

## Accuracy Tests

No impact — this change only fixes a crash at graph capture time (device placement of metadata tensors); it does not alter any compute logic. On devices where capture previously succeeded (DFlash path), `.to(self.device)` is a no-op.

## Speed Tests and Profiling

No impact — the added transfer is a host-side `bs × 4` byte copy executed outside the captured graph (~µs level), and it is a no-op when the tensor is already on-device.
