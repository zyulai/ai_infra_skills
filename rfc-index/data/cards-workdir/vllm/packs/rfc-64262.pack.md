## 正文(PRD / 提案全文)

Builds on #47456 and #49349 (JIT warmup v1).

## Summary

Today, a Triton kernel joins JIT warmup by being wrapped, together with its warmup inputs, in a `triton_kernel_dispatcher_with_warmup` dispatcher. That works, but it has two costs:

1. there's a lot of boilerplate to register and warm a kernel;
2. the grid logic moves away from the call site.
3. as a result, models are still not fully de-JITified, causing `--jit-monitor-mode error` to fail.

This RFC proposes warmup v2: a Triton-specific contract that removes both. 
* The kernel signature says what to warm.
* (1) Annotations give pointer dtypes, (2) defaults give constants, and (3) the caller passes deployment values to `register_warmup`.
* A small decorator (`@triton_warmup`) covers whatever the signature can't express.

Triton's own engine then turns those values into compile keys, exactly as it does at launch. vLLM's existing `_triton_key_deriver` runs each case through the kernel's Triton binder. 

Launches stay plain `kernel[grid](...)` calls, and the back end is unchanged. Nothing wraps the kernel: `@triton_warmup` returns the same `JITFunction`, and every call goes straight to Triton.

The workflow:

1. **Declare** next to the kernel: annotations, `constexpr` defaults, and `@triton_warmup(...)` only if needed. A pure host launcher can take `@triton_warmup_launcher(...)` instead, and then its kernels need nothing.
2. **Register** where the deployment values live. Registrations made outside an active registry are deferred to the next warmup.
3. **Expand**: at startup, each registration becomes a set of candidate launch arguments (one representative per Triton integer class).
4. **Derive keys**: Triton's binder and `compute_cache_key` map each candidate to a cache key, and duplicates are dropped.
5. **Compile** each key with `kernel.warmup(...)`, in parallel. _No kernel runs_.

Conceptually, a `@triton.jit` kernel is a template that Triton instantiates implicitly on first launch. The new warmup declarations (`Ptr` annotations, decorator entries, `register_warmup` values) act as explicit instantiation: they list the instantiations to compile at startup, and `@triton_warmup` states the constraints between parameters.

As a showcase, we migrate the 17 kernels of #56323 and its partial revert #56654 in https://github.com/vllm-project/vllm/issues/64262 (kernel side: +367/−876 lines). To keep the review focused on the API that kernel authors see, the PR contains only these kernel-side changes. The supporting code and its tests follow once the API is agreed.

## Motivation: Existing Triton contract

Here is `expand_kernel` under the current contract in MAIN:

```python
@triton.jit(do_not_specialize=["replace_from", "replace_to"])
def expand_kernel(
    output_ptr,  # [num_tokens]
    input_ptr,   # [batch_size]
    cu_num_tokens_ptr,  # [batch_size]
    replace_from,
    replace_to,
    MAX_NUM_TOKENS: tl.constexpr,
): ...


def _expand_warmup_inputs() -> dict[str, object]:
    dtype = WarmupChoices(torch.float32, torch.int32, torch.int64)
    data = TritonWarmupTensor(dtype)
    return dict(
        output=data,
        input=data,
        cu_num_tokens=TritonWarmupTensor(torch.int32),
        replace_from=0,
        replace_to=0,
    )


@triton_kernel_dispatcher_with_warmup(
    kernel=expand_kernel, warmup_inputs=_expand_warmup_inputs
)
def _expand(output, input, cu_num_tokens, replace_from, replace_to) -> DispatchSpec:
    return (input.shape[0],), dict(MAX_NUM_TOKENS=MAX_SPEC_LEN)


_expand(expanded_x, x, cu_num_tokens, replace_from, replace_to)  # call site
_expand.register_warmup()  # registration
```

Problems: 
* **Boilerplate.** Every kernel needs a warmup-inputs function, a dispatcher, a registration and a rewritten call site. The argument list is written three times (kernel, warmup inputs, dispatcher), and every derived flag twice (once as a dispatcher expression, once as a warmup choice that must match it). MRV2 also needs `@capture` and `activate()` in its model runner, because speculators are built outside an active registry.

* **Grid away from the call site.** The grid and the `constexprs` live in the dispatcher, so the call site no longer shows how the kernel launches. And the warmup inputs have to be kept in sync with the dispatcher by hand. They drift: the reverted MRV2 warmup #56654 declared `idx_mapping` and `sample_idx_mapping` as `int32`, but both are `int64` at runtime.

One constraint holds throughout: **compile keys must be static**, coming only from declarations and config. Relying on dummy runs would defeat the purpose of de-JIT.

## Scope

This only applies to Triton; CuTeDSL and TileLang keep the existing contract for now. Triton is special because its cache key is a function of the call: pointer dtypes and 16-byte alignment, integer classes, `constexpr` values and launch options. A signature can therefore describe most of its own keys.

The new contract is only a front end. Key derivation (`_triton_key_deriver`), compile-only `kernel.warmup`, parallel `compile_many` and `JitWarmupRegistry` are shared and unchanged from warmup v1. The old dispatcher keeps working, so kernels can migrate one at a time.

Adoption is opt-in per kernel: a kernel that never calls `register_warmup` behaves exactly as today. Nothing here runs on the launch path either. The proposal has two mechanisms beyond plain declarations, and both act only during startup warmup:
- a `register_warmup` method added to Triton's `JITFunction`;
- in the launcher form, a temporary swap of the launcher module's kernel globals.

## Proposed contract

### Kernel form

Here is `expand_kernel` under the new contract:

```python
@triton.jit(do_not_specialize=["replace_from", "replace_to"])
def expand_kernel(
    output_ptr: Ptr[tl.float32, tl.int32], # [num_tokens]
    input_ptr: Ptr[tl.float32, tl.int32],  # [batch_size]
    cu_num_tokens_ptr: Ptr[tl.int32],      # [batch_size]
    replace_from,
    replace_to,
    MAX_NUM_TOKENS: tl.constexpr = MAX_SPEC_LEN,
): ...  # body unchanged


expand_kernel[(batch_size,)](expanded_x, x, cu_num_tokens, replace_from, replace_to)
expand_kernel.register_warmup()
```

There's no warmup function, no dispatcher and no decorator. A decorator is only needed when the signature can't express something, as with `copy_and_expand_dflash_inputs_kernel`:

```python
@triton_warmup(
    num_query_per_req=lambda num_speculative_tokens: 1 + num_speculative_tokens,
    BLOCK_SIZE=WarmupIntRange(1, 257, advance=lambda value: value * 2),
    HAS_NUM_REJECTED=(False, True),
    num_rejected_tokens_ptr=lambda HAS_NUM_REJECTED: (
        Ptr[tl.int32] if HAS_NUM_REJECTED else 0
    ),
)
@triton.jit
def copy_and_expand_dflash_inputs_kernel(
    next_token_ids_ptr: Ptr[tl.int32],       # [num_reqs]
    target_positions_ptr: Ptr[tl.int64],     # [num_context]
    ...,  # output, block-table and metadata pointers: annotated the same way
    block_table_stride,
    num_rejected_tokens_ptr: Ptr[tl.int32],  # [num_reqs] or null (0) when not padded
    parallel_drafting_token_id,
    block_size,
    num_query_per_req,
    num_speculative_tokens,
    total_input_tokens,
    BLOCK_SIZE: tl.constexpr,
    HAS_NUM_REJECTED: tl.constexpr = False,
): ...  # body and launch unchanged


# DFlashProposer.__init__
copy_and_expand_dflash_inputs_kernel.register_warmup(
    block_table_stride=(self.max_model_len + self.block_size - 1) // self.block_size,
    parallel_drafting_token_id=self.parallel_drafting_token_id,
    block_size=self.block_size,
    num_speculative_tokens=self.num_speculative_tokens,
)
```

Here the pointer dtypes come from annotations. The four registered values bind to the parameters with the same names. `total_input_tokens` has no value, so it warms all three integer classes. The decorator only says what the signature can't:
- `num_query_per_req` is derived from a registered value;
- `BLOCK_SIZE` varies at runtime;
- `num_rejected_tokens_ptr` follows the `HAS_NUM_REJECTED` flag.

### Registration

Importing the helper adds `register_warmup` to every `JITFunction`. Registrations stay one line, in the code that owns the deployment values, with the same arguments as today.

*Registration doesn't need an active registry.** Today, `JitWarmupRegistry.register` only records a registration while a registry is active. That means inside `with registry.activate():`, or inside a method decorated with `@JitWarmupRegistry.capture`. Anywhere else, the registration is silently dropped. That's why #56323 had to add `@capture` and `activate()` to MRV2's model runner: its speculators are built in `__init__`, outside any active registry.

Triton registrations go through a new `JitWarmupRegistry.register_or_defer` instead. It looks up the active registry the same way, through the `ContextVar` that `activate()` sets:
- inside an active registry, it registers directly, exactly like `register`;
- outside, it appends to a process-wide queue instead of dropping.

`JitWarmupRegistry.warmup()` first adopts everything in that queue, then expands and compiles as usual. A deferred registration is therefore indistinguishable from a direct one. It goes through the same key expansion and parallel compile.

Existing owners (CuTeDSL, TileLang, DeepGEMM, …) keep calling `register` and keep their `activate()` blocks and `@capture`. This proposal doesn't remove any of those for now.

On CPU, `KernelOverride` gets a no-op `register_warmup`, so `cpu_triton_utils.py` is untouched.

### MRV2 example

Here is the MTP speculator's embedding shift as it was in #56323:

```python
def _shift_input_embeds_warmup_inputs(*, speculator):
    hidden = TritonWarmupTensor(
        speculator.dtype,
        shape=(1, speculator.hidden_size),
        strides=(speculator.hidden_size, 1),
    )
    return dict(
        input_embeds=hidden,
        draft_embeds=hidden,
        idx_mapping=TritonWarmupTensor(torch.int32),  # int64 at runtime
        query_start_loc=TritonWarmupTensor(torch.int32),
        last_token_indices=TritonWarmupTensor(torch.int64),
        num_reqs=1,
    )


@triton_kernel_dispatcher_with_warmup(
    kernel=_shift_input_embeds_kernel,
    warmup_inputs=_shift_input_embeds_warmup_inputs,
)
def _shift_input_embeds(
    input_embeds, draft_embeds, idx_mapping, query_start_loc, last_token_indices, num_reqs
) -> DispatchSpec:
    hidden_size = input_embeds.shape[-1]
    return (num_reqs, triton.cdiv(hidden_size, 256)), dict(
        hidden_size=hidden_size, BLOCK_SIZE_Q=16, BLOCK_SIZE_H=256
    )


_shift_input_embeds(input_embeds, draft_embeds, idx_mapping, query_start_loc,
                    last_token_indices, num_reqs=num_reqs)  # call site
_shift_input_embeds.register_warmup(speculator=self)  # + @capture/activate() in the model runner
```

And with this proposal https://github.com/vllm-project/vllm/issues/64262:

```python
@triton.jit
def _shift_input_embeds_kernel(
    input_embeds_ptr: Ptr[tl.float16, tl.bfloat16, tl.float32],
    draft_embeds_ptr: Ptr[tl.float16, tl.bfloat16, tl.float32],
    idx_mapping_ptr: Ptr[tl.int64],
    query_start_loc_ptr: Ptr[tl.int32],
    last_token_indices_ptr: Ptr[tl.int64],
    hidden_size,
    BLOCK_SIZE_Q: tl.constexpr = 16,
    BLOCK_SIZE_H: tl.constexpr = 256,
): ...  # body unchanged


_shift_input_embeds_kernel[(num_reqs, triton.cdiv(hidden_size, hidden_block_size))](
    input_embeds, draft_embeds, idx_mapping, input_buffers.query_start_loc,
    last_token_indices, hidden_size, BLOCK_SIZE_H=hidden_block_size,
)  # call site: the launch from before #56323
_shift_input_embeds_kernel.register_warmup(hidden_size=self.hidden_size)  # load_model
```

The kernel is called directly, and the model runner is untouched. The warmup function, the dispatcher and the `@capture`/`activate()` changes are all gone. `_shift_input_ids_kernel` needs only its annotations and a bare `register_warmup()`.

### Launcher form

Some kernels sit behind a thin host function that derives every kernel argument from its inputs. Shapes become sizes and strides, the device picks tiles, optional inputs set flags. Declaring all of that on each kernel would duplicate the launcher, so we warm the launcher instead:

```python
@triton_warmup_launcher(
    # Only per-row shape matters; src rows may differ in dtype from the state.
    lambda state_shape, state_dtype, src_dtype: dict(
        state=WarmupTensor((1, *state_shape), state_dtype),
        src=WarmupTensor((1, *state_shape), src_dtype),
        indices=WarmupTensor((1,), torch.int32),
    )
)
def scatter_states(state, src, indices) -> None:
    ...  # upstream body, unchanged


# GLM-5-Next KDA layer
scatter_states.register_warmup(
    state_shape=recurrent_state_shape,
    state_dtype=recurrent_state_dtype,
    # The chunk kernels return an fp32 final state; FlashKDA's matches the cache.
    src_dtype=(
        recurrent_state_dtype if self.kda_prefill_backend == "flashkda" else torch.float32
    ),
)
```

The split is the same as in the kernel form. The decorator describes the launcher's inputs: which arguments are tensors, and how their shapes relate. Its function takes the `register_warmup` arguments by name. The caller passes plain deployment values and never builds tensors.

`apply_top_k_top_p_triton` uses this to cover all four top-k/top-p kernels from one declaration (See https://github.com/vllm-project/vllm/pull/62015): the batch sizes where the compiled code changes, with and without `k`/`p`. That one inputs function, 24 lines, replaces four warmup-inputs functions and four dispatchers (210 lines) in #56323, `vllm/v1/sample/ops/topk_topp_triton.py`. With the launches moved back to their call sites, `topk_topp_triton.py` and `topk_topp_sampler.py` shrink by 168 lines net (+94/−262).

## Design notes

- **No dummy runs.**
- **No pointer ties.** Pointers that always share a dtype are annotated independently. That might cost a few unreachable compiles at startup, done in parallel, in exchange for one less concept.
- **Why not just `do_not_specialize` everything?** It would compile each kernel once, but it isn't free. An integer that multiplies a row index (vocab size, row stride, hidden size) is divisible by 16 at runtime, and specialization lets Triton prove that and emit 128-bit loads. Unspecialized, those accesses become scalar. Measured on B300, through the real launchers, with `do_not_specialize` on every runtime integer:

  | Kernel | Unspecialized | Slowdown |
  |---|---|---|
  | `sample_recovered_tokens_kernel` (every spec-decode step) | `vocab_size` | 1.6–2.6× |
  | `apply_top_k_top_p_triton`, top-k | row stride, batch size | 1.4–1.7× |
  | `apply_top_k_top_p_triton`, top-k + top-p | row stride, batch size | 1.2–1.3× |
  | MTP `_shift_input_embeds_kernel` | `hidden_size` | up to 2.4× |
  | `scatter_states` | batch strides | none (bandwidth-bound copy) |

  It also does nothing for `constexpr` variants, pointer dtypes or launch options, which make up most of what warmup compiles. So unspecializing stays a per-kernel call, made after a PTX diff and a benchmark.

## Risks and limitations

- **It relies on three Triton internals:** the `__triton_builtin__` marker, Triton ignoring unknown annotation names (pinned by a unit test), and adding `register_warmup` to `JITFunction`.
- **Attribute binding is by name only.** If an attribute on the registered object is renamed, a `constexpr` that relied on it fails at warmup. An integer falls back to its three integer classes without a message. That's still correct, but costs up to two extra compiles.
- **Launcher replay swaps module globals.** It only sees kernels in the launcher's own module, and it must not run concurrently with that launcher.
- **Builds without Triton** get plain functions from the placeholder `triton.jit`, with no `register_warmup`. CPU is fine thanks to `KernelOverride`.
- **Not covered yet:** autotuned and heuristics kernels are rejected explicitly for now.
