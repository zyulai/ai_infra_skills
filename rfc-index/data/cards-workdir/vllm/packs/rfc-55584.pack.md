## 正文(PRD / 提案全文)

### Motivation.

Reinforcement learning (RL) rollouts with mixture-of-experts (MoE) models need a record of which experts actually ran for each token. Training can replay those routing choices. vLLM already captures and returns these R3 records. It can also reuse them with a local prefix cache.

Prefill/decode disaggregation adds a missing step. Prefill (P) and decode (D) run in separate instances. D loads key/value (KV) cache data from P and does not run every prompt token again. D therefore cannot produce all prompt routes from its own capture alone.

This RFC proposes native NIXL transfer of R3 records from P to D. It would build on the R3 storage code that the project accepts from [PR #45635](https://github.com/vllm-project/vllm/pull/45635), or a successor. Workers would transfer the route data directly and keep it alive together with the matching KV. The proxy would not carry or merge route arrays. This is a PD extension of the work discussed in [RFC #45221](https://github.com/vllm-project/vllm/issues/45221), not a second R3 store or a new design for a general Artifact Connector.

The key rule is that routes must match the KV that D actually uses, not just the same prompt text. Consider a 48-token prompt. D already has KV for the first 32 tokens and recomputes the last prompt token:

| Token range, start inclusive and end exclusive | KV source | Required R3 source |
|---|---|---|
| `[0, 32)` | D's existing local cache | The old routes that match this cached KV |
| `[32, 47)` | KV loaded from P for this request | P's routes that match the loaded KV |
| `[47, 48)` | Computed by D for this request | D's new capture |

Replacing all prefix routes with P's current trace would not preserve this link. The same prefix hash does not prove that two executions chose exactly the same routes. Block reuse, async output, partial blocks, and transfer failures also affect when records are valid and when their memory can be freed.

As of September 6, 2026, PR #45635 at `df09778c1f` replaces the old scheduler-side slot store with records that workers own and look up by block key. It still rejects R3 when a KV connector is enabled. This RFC would extend that storage design for PD instead of bringing back the old slot manager. See the [R3 worker code](https://github.com/xhx1022/vllm/blob/df09778c1f5ad65706fccf5bc9c0c82d2b650736/vllm/distributed/artifact_connector/worker.py#L65) and its [current configuration checks](https://github.com/xhx1022/vllm/blob/df09778c1f5ad65706fccf5bc9c0c82d2b650736/vllm/config/vllm.py#L1012).

Related work:

- [PR #39289](https://github.com/vllm-project/vllm/pull/39289) addresses the same R3+PD use case. It carries route arrays in `kv_transfer_params` and merges them on D. This proposal instead uses NIXL for the route data and selects records based on the KV source.
- [PR #45419](https://github.com/vllm-project/vllm/pull/45419) relaxes the configuration check and relies on proxy-side merging. It has companion work in [vLLM Router #184](https://github.com/vllm-project/router/pull/184) and [llm-d Router #1627](https://github.com/llm-d/llm-d-router/pull/1627). This proposal keeps the proxy's normal PD handoff role. The engine and connector would check that the KV and routes match and are complete.
- [PR #52902](https://github.com/vllm-project/vllm/pull/52902) reorganizes the R3 capture/replay tests. PD tests would extend that test setup and stay aligned with output-range work such as [PR #37094](https://github.com/vllm-project/vllm/pull/37094).

This RFC asks for agreement on the native NIXL path and how it should fit with these efforts. It does not assume that it replaces an existing PR. The implementation would use the storage interfaces accepted by the project. Before that storage work merges, this RFC can define the smallest additions needed for PD.


### Proposed Change.


### 1. Goals and initial scope

The proposed first version would:

1. Transfer P's routes for the external KV that D actually reuses. Combine them with D's cached routes and new local capture to form the complete result.
2. Keep prefix caching, chunked prefill, CUDA graphs, and async output enabled. Correctness must not depend on turning these features off.
3. Require both KV and matching R3 to be ready before completing a load or exposing a cache hit. Keep transfer memory alive until no transfer can still access it.
4. Be disabled by default. When disabled, preserve the base version's NIXL compatibility checks, R3 output rules, and other serving behavior.

The first version would support:

- Model Runner V2, text-only MoE models, non-streaming completions, and `n=1`.
- One data-parallel replica per side (`DP=1`).
- Matching tensor-parallel (`TP`) layouts on P and D, plus compatible expert-parallel (`EP`) layouts that pass their own tests.
- Dedicated producer and consumer roles, NIXL pull, one full-attention KV cache group, and matching logical-block layouts, hash-block layouts, and R3 data formats.

The first version would not support MTP/speculative decoding, DBO/microbatching, LoRA, multimodal inputs, resumable requests, different TP layouts on P and D, multiple DP output workers, pipeline parallelism (PP), decode/prefill context parallelism (DCP/PCP), reverse transfer, or CPU KV offload. Passing tests with another EP backend does not prove DeepEP support. Unsupported combinations would be rejected at startup or during request preprocessing. These new limits apply only when this extension is enabled.

Weights would remain fixed while requests or transfers are active. To change weights, the deployment must first finish or safely stop those requests and transfers, then bring both sides to a consistent state. This RFC does not implement replay in the trainer or guarantee bit-exact training/inference logprobs.

### 2. Configuration and API behavior

Both sides would keep using `--enable-return-routed-experts`. They would also set the proposed `enable_routed_experts_transfer` field in `KVTransferConfig` to `true`. This new field would default to `false`. The P configuration would be:

```json
{
  "kv_connector": "NixlConnector",
  "kv_role": "kv_producer",
  "enable_routed_experts_transfer": true,
  "kv_load_failure_policy": "fail"
}
```

D would use `kv_consumer` with the same R3 transfer settings. The handshake would include an optional R3 transfer capability and data-format version. A transfer must fail if only one side enables the feature, or if versions or layouts do not match. It must not fall back to a warning or return an incomplete trace. With the extension disabled, the existing compatibility factors stay unchanged. This does not bypass vLLM's version checks or add a guarantee for mixed-version deployments.

The public R3 response format and token-range rules would stay the same. Normal requests to P would still return R3 as before. P requests used only for an internal PD handoff would not serialize a second copy of the full route array. D would return the complete route result. The last sampled token has no route row until it has run through a forward pass.

The proxy would keep forwarding the normal PD handoff. At most, it would pass along a small export ID. Workers would exchange the full route data, per-block transfer metadata, and memory descriptors directly. These would not travel as JSON arrays in `kv_transfer_params`.

### 3. Storage ownership and public interfaces

The base R3 code would still capture routes, store completed blocks, and build R3 output. It would also keep each request's unfinished block and decide when cached records can be removed. The unfinished part of a hash block is called a tail. Published records are immutable: their contents cannot be changed in place. NIXL would manage transfer snapshots, memory registration, transfer handles, and notifications.

The new PD control path would send small readiness and completion messages to the Scheduler through public interfaces. It would not add a second source-of-truth route cache or route-data transfer code to the Scheduler. It would not access the store's private memory or eviction tables, or NIXL's private handles. The base R3 output path through EngineCore and the API server would stay unchanged.

The first version would use CPU transfer snapshots with a fixed memory budget. It would copy the matching records from the R3 store into a stable export buffer. D would receive them into a separate staging buffer, validate them, and then commit them through the store's public API. Each snapshot belongs to one transfer. It is not used for prefix lookup and is not a second R3 cache. The first version would not borrow raw addresses from the store's private memory buffer or claim end-to-end zero-copy transfer.

A transfer lease keeps its data alive while a transfer may still access it. A manifest is the metadata that describes the transfer's source, format, and valid rows. The R3 worker layer would provide these public operations. Final method names can follow the accepted storage API, but the ownership and completion rules are part of this proposal:

| Operation | Input and result | Required behavior |
|---|---|---|
| Reserve a usable cached prefix | Candidate KV range and its R3 references → usable prefix and reservation | Check that the records exist and match the KV. Keep them alive so they cannot be evicted before use. |
| Prepare an export | Request, KV/R3 links, and token range → export lease and manifest | Include the needed full blocks and tails. Allow remote reads only after the snapshot is ready. |
| Prepare a receive | Manifest and target request → private staging buffer | Check size, format, ranges, and request identity. Reserve budget before allocating memory. |
| Commit received rows | Completed and validated staging data → local R3 references or tails | Commit through the store's API. Do not write private slots or change an existing immutable record. |
| Release export or receive data | Lease or staging reservation | Free it only after NIXL confirms that no transfer can still access the memory. |

With matching TP layouts, each rank would transfer its KV shards through the existing NIXL path. R3 uses logical token positions, layer IDs, and expert IDs. Only the output rank that holds the full route record would export it; other TP ranks would not send duplicate copies. Completion must cover all required KV ranks, not just the output rank.

### 4. Link KV to the exact route record

Each KV cache range used by an R3 request would carry a reference to its matching route record. The R3 store owns this reference. Callers pass it back to the store rather than build it themselves. A prefix hash finds a possible cache hit; the record reference identifies the routes that belong to that specific KV. NIXL must not select an arbitrary stored record based only on the prefix hash.

If KV moves to a new address without being recomputed, this link stays the same. If a new forward pass produces new KV, it must link to the matching new route record. An old record with the same prefix hash is not an automatic substitute. The R3 storage code would create and resolve record references and any needed version information. PD would not maintain a separate key-generation scheme.

The export manifest would bind:

- The source instance identity, a unique `transfer_id`, and the source cache epoch for this export.
- The deployed model/weight identity and R3 format: layer count, experts per token (top-k), expert-ID encoding, and numeric type (dtype).
- The matching KV/R3 record references, valid token ranges, and byte counts.
- The request and transfer identity that the receiver can check.

The deployment configuration or a coordinator supplies the model/weight identity. A local cache generation counter is not a weight version. The handshake checks that both sides declare compatible identities; it does not prove that checkpoint files contain the claimed weights. Instance identity after a restart, local cache epoch, and shared weight identity must remain separate. Equal generation counters do not prove equal weights. Different counters do not by themselves prove a mismatch.

A completion event must match the active request, `transfer_id`, and receive generation. An old notification cannot complete a new request. Data from an old epoch cannot be committed as valid data for a new epoch.

### 5. Normal transfer flow

1. **P keeps the records alive.** Before its handoff request ends, P retains the needed R3 records and tails for export. Request cleanup must not free them before the snapshot is ready.
2. **P prepares the export.** Once the async readout and snapshot are complete, NIXL gets stable export descriptors. A background `put()` that is only queued is not enough.
3. **D finds its usable prefix.** D reserves the longest local prefix with both valid KV and matching R3. It handles the rest as a normal cache miss: fetch both from P or recompute both.
4. **D receives the external range.** KV and R3 transfers may make progress separately. Until they are ready, other requests and prefix lookups cannot see the receive buffers.
5. **D resumes execution.** D leaves the load-wait state only after the external KV it will reuse and the matching R3 rows have arrived and passed validation. This does not wait for routes of tokens that D has not run yet.
6. **D commits the final records.** D runs the remaining tokens. It combines cached routes, received routes, and new capture based on their actual sources, then completes the final block and output through the R3 storage API.
7. **P releases the export lease.** Once all required KV/R3 reads have ended, NIXL notifies P to release its export snapshot. P does not wait for D to finish the whole generation. D manages its own staging and cache references through the local lifecycle.

If D needs no external range, it issues no R3 READ. It uses the existing notify-only path to release P's lease. Checking a cached prefix and retaining its records must form one reservation operation. There must be no gap where a record passes the check and is then evicted before use.

The first version would resume D only when both the reused external KV and its matching routes are ready. This keeps the normal output path from having to handle executed KV whose required routes are still in flight. Running D as soon as KV arrives while delaying route output is a possible later optimization, not part of this first version.

### 6. Tails and the final block

P's partial block would be copied into an immutable transfer snapshot with an explicit valid token range. Its export lease would keep it alive after the normal request tail is released. Transfers may use whole blocks, but D must use only the rows declared valid in the manifest.

If D recomputes the last prompt token, it must not use P's route row for that token in the final record. D first waits for the external range it will reuse, then runs its local tokens. The final immutable block, including D's new rows, is published after that forward pass. D must not publish P's full final block and modify it in place later. It must also not wait for its own new routes before allowing the forward pass that creates them.

### 7. Failures, cancellation, and limits

**Missing records before scheduling:** If KV has a cache hit but its R3 is missing, not ready, or from the wrong source, treat that range as a cache miss for this R3 request. Shorten the usable local prefix and fetch or recompute both KV and R3 for the missing range. The first version would not refill R3 alone, attach P's current routes to D's old KV, or disable prefix caching globally.

**Errors after a transfer starts:** Follow `kv_load_failure_policy="fail"`. End the affected request with an error. Do not retry without a bound or return a partly valid R3 result. If any required KV or R3 transfer fails, cancel or drain the others. Free receive buffers and source leases only after confirming that DMA can no longer access those addresses.

**Timeouts and unconfirmed cancellation:** A timeout does not prove that DMA has stopped. Memory must remain reserved and count against the in-flight budget until NIXL confirms that all access has ended, through completion or safe cancellation. It cannot be given to another request. If the connector cannot recover, use its failure or instance-isolation path rather than reuse memory that may still be accessed.

**Resource limits:** Each output worker would track export and receive snapshots separately from the R3 store. The first version's total snapshot-byte limit would equal that worker's effective R3 store capacity. The number of in-flight transfer windows would be limited to `2 * max_num_seqs`; a window is one tracked export or receive operation. A manifest could not contain more records than the full blocks and tails needed for the request's valid token range. This budget would not reduce or change the store's existing capacity. The deployment must account for snapshot memory as an extra cost. When the budget is full, reject new transfers with a request-level resource error, but keep completing and releasing transfers already in flight. Memory reports must separate the R3 store, snapshots, tail/capture buffers, and descriptors.

**Error handling:** Reject unsupported configurations at startup and invalid requests during preprocessing. Handle recoverable missing-data and transfer errors at request scope. Keep assertions for broken internal invariants. Do not hide code bugs with a broad exception catch. This follows the existing [review on error handling](https://github.com/vllm-project/vllm/pull/45635#discussion_r3908999090).

### 8. CUDA graphs, async scheduling, and pause

Route export would reuse the base R3 implementation's async GPU-to-CPU copy. It must not add CPU/GPU synchronization inside MoE layers or on each decode step. It must keep the device-buffer addresses used by CUDA graphs stable. Snapshot work, memory registration, and network work stay in the worker/connector lifecycle. See the [review on CPU/GPU overlap](https://github.com/vllm-project/vllm/pull/45635#discussion_r3909040668).

The Scheduler would receive public events for KV/R3 readiness and transfer completion. If the engine needs to track work that is only waiting on I/O, the KV connector would expose a small public progress interface. The implementation must not read NIXL's private state or add route-array handling to the Scheduler's main loop. See the [review on these module boundaries](https://github.com/vllm-project/vllm/pull/45635#pullrequestreview-4840148178).

Pause may stop model scheduling, but required transfers, heartbeats, cancellation, and cleanup must keep making progress. Before sleep or a change to registered KV memory, related transfers must finish or be cancelled safely. Waiting for a CUDA stream is not a substitute for draining NIXL DMA. Until these combinations pass validation, the extension must reject unsafe operations. It must not silently free memory or change the existing meaning of pause.

### 9. Implementation order and merge criteria

After the base storage changes merge and their public interfaces are settled, the PD feature would be submitted as one complete PR. It would include the small R3 transfer interface, NIXL support, shared KV/R3 lifecycle rules, and tests. Any new interface would ship with its actual caller, not as an unused general abstraction. Independent base-layer bug fixes can be submitted separately after checking for duplicate work.
