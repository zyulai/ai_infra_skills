## Motivation

The current `trtllm_mla` backend has several minor inefficiencies and confusing parts:

1. Element-wise operations on `seq_lens` are repeatedly executed inside CUDA Graph replay, instead of being done once during metadata initialization.  
2. A redundant `torch.cat` operation (`k` + `k_rope`) exists in `draft_extend`, `draft`, and `verify` paths. This operation has been moved so it only happens during prefill.  
3. Some logic around sequence length metadata is confusing:
   - `metadata.max_seq_len_q = num_tokens_per_bs + 1` appears unnecessary.  
   - The handling of `spec_info.accept_length_cpu` likely needs a `+1` adjustment. (And why `accept_length=accept_length_cpu+1`?)

In earlier debugging, I encountered multiple `trtllm_mla`-related issues — such as low output performance with odd batch sizes and low output performance when `draft_extend` using cuda graph.  
This cleanup aims to improve both stability and runtime efficiency.

Preliminary benchmarks show a **~2% latency improvement** in decoding, and in faster speculative decoding scenarios, up to **4–5%** gain.

---

## Modifications

- Added `seq_lens_k` field to `TRTLLMMLADecodeMetadata` and initialize it properly.  
- Moved `seq_lens` arithmetic from CUDA graph replay into metadata initialization.  
- Refactored and unified logic in `init_forward_metadata_capture_cuda_graph`, `init_forward_metadata_replay_cuda_graph` and `init_forward_metadata`.  
- Removed redundant `metadata.max_seq_len_q = num_tokens_per_bs + 1`.  
- Clarified `spec_info.accept_length_cpu` handling and ensured consistent `+1` logic.  
- Deferred `k` / `k_rope` concatenation to prefill only.  
- Simplified `seq_lens` update expressions for clarity and efficiency.
