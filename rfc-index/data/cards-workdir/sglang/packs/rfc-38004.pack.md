## 正文(PRD / 提案全文)

## Summary

Quantization methods in SGLang are currently written in two different shapes.

Five of them follow a package layout with an explicit scheme split:

- `layers/quantization/awq/`, `compressed_tensors/`, `gptq/`, `modelslim/`, `quark/`

The rest are single files that hold config parsing, weight creation, post-load processing, and backend kernel dispatch together:

- `fp8.py` (2765 lines), `modelopt_quant.py` (3050), `mxfp4.py` (2060), and 14 smaller ones. 17 top-level files define a `QuantizationConfig` subclass today.

This RFC suggests finishing the migration so that every method follows the layout our own contribution guide already prescribes:

```text
layers/quantization/<method>/
    <method>.py          # Config: parse, validate, select a scheme
    schemes/
        <method>_linear.py   # Scheme: weight create, load, post-process
        <method>_moe.py
```

with backend kernels under `hardware_backend/<plat>/quantization/<method>_kernels.py`, and scheme selection done explicitly through `get_linear_scheme` / `get_moe_scheme`.

Nothing here is a new architecture. `docs/docs/developer_guide/quantization_contribution_guide.mdx` specifies this already, and #21126 (AWQ) and #26402 (GPTQ) are worked examples. This is a plan to take the rest of the directory there.

The intent is incremental. Every existing import path keeps working through re-export shims, each PR is small enough to review in one sitting, and the directory is busy enough that nothing should depend on a long-lived branch: it took 46, 48, 49, 56, 70 and 84 commits in the last six months, 217 in the last 90 days.

Related roadmap: #15194.

## Why

The current layout makes sense historically. Methods were added one at a time, each in the shape that was convenient then, and the scheme split arrived later. It is getting harder to maintain.

Some practical problems that come out of it:

- it is hard to tell where a given behavior lives, because config parsing, weight loading and kernel dispatch sit in the same 2000-line file;
- the same helper gets reimplemented per method, and the copies diverge silently. There are 11 variants of "is this layer excluded from quantization" today, and a fix applied to one copy has already failed to reach another;
- adding a method means editing an eager import block, a base dict and up to four imperative platform-override blocks, plus a separate CLI choices list. Those lists drift: until #37552 landed, `--quantization marlin` passed argparse and then failed at startup, because the choices list named a config class that was never registered;
- lists of class names maintained by hand go stale. `WEIGHT_LOADER_V2_SUPPORTED` has 20 entries, 9 of which name no class that exists;
- importing the package to ask which methods exist imports all 24 config modules, and with them every third-party quantization dependency;
- there are two separate KV-cache quantization systems (`kv_cache.py`, 83 lines, and `fp4_kv_cache_quant_method.py`, 895), and a parallel quantization stack in `multimodal_gen` (28 files, 6,620 lines) that reimplements the srt fp8, modelopt, mxfp4 and modelslim bodies while reaching into srt internals from 30 import sites;
- the four largest files are where the churn is, so unrelated changes collide in them.

For scale: 101 files, 39,262 lines.

The desired end state is simple: when someone adds or changes a quantization method, there should be one obvious file for the config, one directory for the schemes, and one line to register it.

## Proposed Shape

### Method packages

Any method with more than one scheme or backend path becomes a package, as above. Single-scheme methods can stay single files; the split is not worth it for them.

The four monoliths are the substance of the work:

| File | Lines | Becomes |
|---|---|---|
| `modelopt_quant.py` | 3050 | `modelopt/`, splitting 5 config classes from 7 method classes |
| `fp8.py` | 2765 | `fp8/` with config plus linear and MoE schemes |
| `fp8_utils.py` | 2169 | dispatch-once `Fp8LinearOp`, shared post-load helpers extracted |
| `mxfp4.py` | 2060 | `mxfp4/` with per-backend schemes |

### Registry

One declarative listing of methods, as strings, so the tables can be read without importing any config implementation:

```python
QUANTIZATION_METHOD_SPECS = {
    "fp8": "sglang.srt.layers.quantization.fp8:Fp8Config",
    ...
}
```

with the platform overrides as a declarative table rather than imperative `if is_npu(): BASE.update({...})` blocks, and config classes resolved on first lookup. This is what #37602 proposes; it is open, not merged, so everything described above is the state of `main` today.

### Compatibility model

The series should be conservative about anything importable:

- `sglang.srt.layers.quantization.base_config` keeps its symbols. There are 256 import statements across 251 files, plus user-facing docs teaching that path;
- the package root keeps re-exporting `QuantizationConfig`, `get_quantization_config`, `QUANTIZATION_METHODS`, and every `*Config` it exports today;
- shims are explicit re-import stubs rather than `__getattr__` indirection, so `isinstance` identity is preserved by construction and the shims stay greppable;
- shims are only removed in a final gated phase, after a release has shipped with deprecation warnings.

Some things this RFC deliberately does not propose:

- no changes to `FusedMoEMethodBase.apply` signatures or MoeRunner wiring. That migration is already in progress and marked in the code: `TODO(cwan): refactor other backends` appears in `fp8.py`, `mxfp4.py`, `quark_int4fp8_moe.py` and two MoE schemes, and `mxfp4.py:1418` notes a path that still `routes through apply without a MoeRunner`;
- no bulk relocation of kernel wrappers into `hardware_backend/`, ahead of the separate kernels-namespace work;
- no semantic merge of the two KV-cache quantization systems. They get co-located; unifying them reaches into mem_cache and the attention backends and deserves its own RFC.

### Delivery

Small PRs, titled `[N/N] Quantization Refactor: <what>`, with two rules that keep them reviewable:

- mechanical moves and behavioral changes never share a PR. Each high-churn file gets exactly one mechanical move PR, landed quickly, with behavioral follow-ups afterwards in the freshly split files;
- each PR states its equivalence evidence. For registry-shaped changes that means the resolved method table compared before and after, keys, values and order. For file splits it means the prepare/move/postpare flow from the mechanical-refactor-verify skill.

## Migration Plan

### Phase 0: cleanup and registry

Land first, in any order, because none of it depends on the rest.

Remove code with no callers, so that later mechanical moves do not have to carry it (#37552, merged). Drive the method registry from a declarative spec table, and resolve config classes lazily (#37602, open).

Then add `test/registered/unit/layers/quantization/test_import_shims.py`, asserting that every legacy import path still resolves and that the key `isinstance` identities hold. Later PRs append their own shim paths to it. This is the safety net for everything in Phase 2, so it should land before the splits start.

### Phase 1: shared foundations

These land before the splits that consume them.

- **Unify the scheme ABCs** in `base_scheme.py`. Each of the five migrated families declares its own Linear and MoE scheme base, ten classes in total, all subclassing the two ABCs in `base_scheme.py` and mostly restating what those already declare. The contract moves to the two roots and the ten become empty-bodied subclasses. They stay distinct classes rather than plain aliases, because the family return annotations in `compressed_tensors.py`, `quark.py` and `modelslim.py` only mean something if the names are not all one object. `get_min_capability`, `create_moe_runner` and the MoE `apply_weights` move up declared-and-raising rather than abstract: ModelSlim's MoE method owns the `MoeRunner`, so its six MoE schemes implement neither of the last two, and making either abstract makes all six unconstructible.
- **Add `quantization/fp8_postload.py`** for the FP8 post-load sequence that is currently repeated per method. `requantize_with_max_scale` alone has five call sites, in `modelopt_quant.py`, `fp8.py`, `quark/schemes/quark_w8a8_fp8.py` and two compressed-tensors schemes, each wrapped in slightly different surrounding logic. Migrate the two lowest-risk callers as proof, then the rest, including the per-expert MoE loops. This is the highest numeric risk in the phase, since the aiter/ROCm and SM120 paths have no CPU coverage.
- **Split `utils.py`**: layer targeting, GPTQ dynamic-override glue, test-only bit packing, and NVFP4 MoE layout helpers each move out, and `utils.py` becomes a re-export shim.
- **Collapse the 11 `is_layer_skipped` variants** onto one parameterized function. Each variant's matching semantics, prefix or fnmatch or regex, should be enumerated in the PR body, because a wrong merge silently changes which layers get quantized.
- **Replace `WEIGHT_LOADER_V2_SUPPORTED`** with a `supports_weight_loader_v2` class attribute, set on the classes that actually support it.
- **Slim `base_config.py`**: move the modelopt-specific override glue into the modelopt package. Also retire `get_scaled_act_names`. It is not dead, but no implementation can ever make it fire: of its 24 definitions, 18 return `[]` and the other 6 raise `NotImplementedError`. Its single caller, `get_act_fn` in `activation.py:481`, therefore either tests `act_fn_name in []`, which is always false, or raises. `ScaledActivation` is consequently unreachable.

### Phase 2: monolith splits

One fast mechanical PR per file, landed within days, then behavioral follow-ups in the split files.

1. `fp8.py` becomes a package.
2. `modelopt_quant.py` becomes a package.
3. `mxfp4.py` and its four delegate modules become a package.
4. mxfp4 backend selection resolves once into an enum, instead of the six flags `Mxfp4MoEMethod.__init__` sets (`use_triton_kernels`, `use_marlin`, `use_flashinfer`, `use_deep_gemm`, `use_mega_moe`, `_use_sm90_humming`) and re-reads throughout.
5. mxfp4 per-backend scheme extraction, one backend family per PR: triton and aiter, then marlin and humming, then the flashinfer pair. This is the highest behavioral risk in the series, which is why it is three independently revertable PRs rather than one.
6. `fp8_utils.apply_fp8_linear`, currently 266 lines with 11 parameters and 28 branches, moves onto the resolve-once idiom the same file already uses elsewhere, as an `Fp8LinearOp` resolved at scheme init. The current entry point stays as a thin wrapper.
7. Shared `w8a8/` package for the `w8a8_fp8` and `w8a8_int8` overlap, gptq scheme dedup, then proportional treatment for `humming.py`, `gguf.py`, `unquant.py`, `nvfp4_online.py`, `bitsandbytes.py`, `auto_round.py`, `moe_wna16.py` and `w4afp8.py`.

### Phase 3: cross-cutting

Co-locate the two KV-cache quantization systems into `quantization/kv_cache/`, with a declarative dtype-factory table. Consumers stay untouched and the semantics stay separate.

Then a selection-flow tidy: documented deterministic registry-order iteration in `ModelConfig._verify_quantization`, and the per-method escape hatches currently hand-written into `weight_utils.get_quant_config` and `model_loader/loader.py` move behind config-owned hooks.

### Phase 4: adjacent stacks

`multimodal_gen` keeps its own registry, but its duplicated fp8, modelopt, mxfp4 and modelslim bodies get rewritten as thin adapters over the srt scheme classes, one family per PR. Diffusion-native methods (`nunchaku_linear.py`, the `quanto_*`, `kitchen_*` and `comfy_*` files) are untouched. The 30 deep imports of srt quantization internals collapse into a committed adapter surface.

`srt/models/inkling_common/quantization/` gets the same treatment last, once the adapter shape has proven itself.

### Phase 5: shim removal

Gated and last. One PR per shim cluster, only after grep shows zero in-repo consumers and at least one release has shipped with deprecation-warning shims. The `base_config` symbols, the package-root re-exports and `fp8_utils.bmm_fp8` are API rather than shims, and stay.

## Testing

- Add import and registry tests that run without a GPU. Both are cheap and catch the failure mode this series is most likely to introduce, which is a moved symbol that nothing imports any more.
- For each PR, compare the failure set of the quantization unit suites against the merge base, rather than asserting a clean run, since some cases need a GPU or a vendor package.
- Numeric-risk PRs add a one-model generate plus accuracy sanity for the touched family, and the AMD or NPU suites where the touched path is ROCm or Ascend only.
- Keep the registry tables machine-checked: every spec resolves to its named class, including the tables the running platform does not activate.

## Review Rule

If we agree on this direction, quantization PRs should follow one rule:

A quantization method's config parsing, its weight handling, and its backend kernel calls should live in three different places: `<method>/<method>.py`, `<method>/schemes/`, and `hardware_backend/<plat>/quantization/`.

Reviewers should ask for a `schemes/` split when a PR adds a method with more than one backend path, ask for a one-line registry entry rather than a new import block, and avoid growing the files this RFC is trying to split.

## Open Questions

- Should the FP8 post-load migration land as one PR or split into linear and MoE halves? The MoE half touches four per-expert loops with no CPU coverage.
- For mxfp4, the delegate classes and the `Mxfp4MoEMethod` flag monolith currently coexist. This RFC assumes the delegates win, since they are already the live dispatch path and map onto the guide's scheme split, but that is worth confirming with the people who own that code.
- Where exactly should the boundary sit against the in-flight MoeRunner migration? Phase 2's behavioral follow-ups avoid that surface, but it would be better to agree it explicitly than to discover it in review.
- Anything else, please tell me. Happy to reorder or drop phases.
