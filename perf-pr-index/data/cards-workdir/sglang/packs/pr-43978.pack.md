## Motivation

HiCache host pools are allocated by `alloc_mmap` as one `MAP_SHARED | MAP_ANONYMOUS` mapping prefaulted with `MAP_POPULATE` from a single thread, then pinned with `cudaHostRegister`. An anonymous shared mapping is shmem: every page fault takes the backing shmem file's locks, so the prefault runs at ~1.5–2 GB/s single-threaded and plateaus at ~2–4.5 GB/s with 32–64 threads (ablation below), and shmem THP is disabled by default (`shmem_enabled=never`), so every page is 4 KB.

With large host pools this becomes a significant part of engine startup. On a single node with 4x B300 and a ~306 GB host pool per rank, allocating and pinning the host pools takes ~185 s of every start.

## Modifications

Opt-in via `SGLANG_HICACHE_HOST_PARALLEL_ALLOC_THREADS=<n>` (default `0` = off; with it unset the code path is unchanged):

- `mmap_allocator.py`: new `_mmap_private_parallel_prefaulted(alloc_bytes, num_threads)`:
  - maps the pool `MAP_PRIVATE | MAP_ANONYMOUS` (regular anonymous memory, no shmem lock contention);
  - `madvise(MADV_HUGEPAGE)` so it is backed by 2 MB transparent huge pages under the common `enabled=madvise` policy (best effort; still correct on 4 KB pages);
  - `madvise(MADV_DONTFORK)`: this is what makes `MAP_PRIVATE` safe to pin. The reason the existing path uses `MAP_SHARED` is that a private page goes copy-on-write in a forked child and a parent write after `fork()` would move the parent off the page `cudaHostRegister` pinned. With `MADV_DONTFORK` the mapping is not inherited at all, so there is no COW to race with — the same treatment the CUDA driver gives `cudaHostAlloc` memory. Consequence: a `fork()`ed (not spawned) child cannot see this buffer;
  - prefaults the whole range before returning (as `cudaHostRegister` requires) with a THP-aligned chunked `memset` from `n` threads (32 in the runs below). ctypes releases the GIL around the libc call, so the threads fault in parallel. (`MADV_POPULATE_WRITE` per chunk was measured to be noticeably slower than `memset` with the same thread count.)
- `alloc_mmap`: when `n > 0`, the plain (non-hugetlb) path uses the function above; any `OSError` logs and falls back to the existing shared prefaulted mapping. The explicit hugetlb path (`SGLANG_HUGEPAGE_SIZE`) is untouched.
- `environ.py`: `SGLANG_HICACHE_HOST_PARALLEL_ALLOC_THREADS` (`EnvInt(0)`), documented in `docs/references/environment_variables.mdx`.
- Tests (`test/registered/unit/mem_cache/test_mmap_allocator.py`, CPU CI):
  - the mapping is fully resident and zero-filled for 1 / 4 / 64 threads with a ragged, non-THP-aligned size;
  - a forked child touching the buffer gets `SIGSEGV` (i.e. `MADV_DONTFORK` is in effect; mutation-checked — removing the `madvise` makes this test fail);
  - with the flag on, `alloc_mmap` does not take the shared path, and an `OSError` on the new path falls back to it;
  - with the flag unset (default), the new path is never taken.

Note: `alloc_mmap` is also used by `utils/weight_checker.py` for its snapshot arena, which therefore follows the same flag.

## Accuracy Tests

N/A — host memory allocation only; the pool contents are zero-filled exactly as before and no model-output code is touched.

## Speed Tests and Profiling

End to end, one B300 node, 4 ranks allocating concurrently, 306 GB host pool per rank, real `alloc_mmap` + `_cuda_host_register` path, two runs (per rank):

| | allocation + prefault | `cudaHostRegister` | total (slowest rank) |
|---|---|---|---|
| default (`MAP_SHARED`, single-thread `MAP_POPULATE`) | 115–172 s | 13–47 s | 185–189 s |
| `SGLANG_HICACHE_HOST_PARALLEL_ALLOC_THREADS=32` | 4–27 s | 12–29 s | 46 s |

~4x faster overall (~140 s saved per start); with 4 concurrent ranks, allocation is bound by memory bandwidth / page allocator rather than threads.

Ablation, 64 GB prefault, one B300 node (256 cores, kernel 6.8, THP `enabled=madvise`, `shmem_enabled=never`), chunked `memset`, two runs:

| mapping | 1 thread | 8 threads | 32 threads | 64 threads |
|---|---|---|---|---|
| default: shared + `MAP_POPULATE` | 1.4–1.8 GB/s | – | – | – |
| shared (4 KB; `MADV_HUGEPAGE` has no effect on shmem here) | 1.1–1.4 | 1.7–3.8 | 1.7–4.5 | 1.9–4.6 |
| private, 4 KB (`MADV_NOHUGEPAGE`) | 1.2 | 4.1–5.4 | 7.6–8.9 | 8.4–14.4 |
| private + THP (100% 2 MB pages) | 2.2–2.3 | 10.2–10.4 | 30–43 | 47–48 |

So multithreading alone on the shared mapping gives at most ~2x and is noisy; going private gives most of the scaling, and THP another ~4x on top.

+    after fork() moving the parent off the pinned page; so a fork()ed child
+    cannot see this buffer.
+    Pages are prefaulted before return, as cudaHostRegister requires.
+    """
+    if _libc is None:
+        raise OSError("libc unavailable")
+    mm = mmap.mmap(

+    )
+    base = ctypes.addressof(ctypes.c_char.from_buffer(mm))
+    if _libc.madvise(base, alloc_bytes, _MADV_DONTFORK) != 0:
+        errno = ctypes.get_errno()
+        mm.close()

+    # Best effort: still correct on 4 KB pages if THP is disabled.
+    _libc.madvise(base, alloc_bytes, _MADV_HUGEPAGE)

+    chunk = -(-chunk // _THP_SIZE) * _THP_SIZE
