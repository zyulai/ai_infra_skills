## 正文(PR 描述)

## Overview

Implements solution 2 as outlined in issue #62865.
In more detail: fixes #62865 by reverting #42129 and, under torch < 2.13, keeps its intended hang protection by not formatting the slow log message for vLLM ops.
Currently using compile mode 1/2, or mode 3 with `splitting_ops: []` on Transformers-backend models corrupts the KV cache because Inductor passes tensors in a different layout than the kernels assume. As discussed with maintainers and @okorzh-amd (author of #42129) in Slack, this is the revert-based alternative to #62924.

## Claims

- Fixes degenerate output for Transformers-backend models (e.g. Qwen3, Kolibri-1, likely others) under compile mode 1/2, or mode 3 with `splitting_ops: []`.
- It does so by restoring PyTorch's default handling for all `vllm::` and `vllm_aiter::` custom ops.
- Keeps the compile-hang protection from #42129 through: (1) from torch 2.13 the slow log message is only built with INFO logging; (2) below 2.13 (currently only the gfx1250 preview image) the message is never built for `vllm::` and `vllm_aiter::` ops, the same ops #42129 covered.

## Validation

Environment: 2x RTX PRO 6000 Blackwell, torch 2.13.0+cu130, precompiled kernels. All runs with vLLM and Inductor compile caches disabled.

**3. Bounded log message for vLLM ops under torch < 2.13**

I could not test on gfx1250 itself.

### Compile time
On CUDA, cold-cache compile time is unchanged within noise (`main` vs this PR): Kolibri-1 mode 3 28.3 vs 28.1 s, Kolibri-1 TP=2 61.1 vs 62.1 s, Qwen3-4B mode 3 19.4 vs 19.5 s.

On ROCm, @djramic reported on Slack that without the #42129 allow-list the Kimi-K2 arch (dummy weights, torch 2.13) compiles about as fast as before. I had no ROCm access to verify this myself.

## Details

**Root cause:** #42129 added every `vllm::*` and `vllm_aiter::*` op to Inductor's `FALLBACK_ALLOW_LIST`. Inductor creates fallbacks for allow-listed ops without PyTorch's default layout constraint for custom ops. Without it, Inductor passes `vllm::unified_kv_cache_update` a head-major key, strides `(128, 128*S, 1)` instead of eager's `(1024, 128, 1)`. `reshape_and_cache_flash` only reads `key.stride(0)` and assumes packed heads, so every cached key is scrambled and the output is garbage. Default mode 3 is unaffected because it splits the graph at the attention and KV-cache ops.

**Why revert:** The allow-list only existed to skip an implicit-fallback INFO message that torch <= 2.12 builds eagerly, which hung compilation on deep MoE/TP graphs. pytorch/pytorch#185951 makes it lazy from torch 2.13, and CUDA, CPU, XPU and the default ROCm images are on >= 2.13. Reverting restores PyTorch's behavior for all vLLM ops. #62924's own control row (allow-list disabled) already gives token-identical output to its patched run. The allow-list cannot stay for torch < 2.13 either, because the layout bug is in that code path on every torch version; those versions only need the hang protection, which skipping the message for vLLM ops provides.

**Limitations and follow-ups**
- The torch < 2.13 patch can be removed once every platform pins torch >= 2.13. Until then, Inductor messages for vLLM ops (including lowering errors) show only the op name on those versions, as with #42129.
- On torch >= 2.13 with Inductor's graph logger at INFO, the full message is still built and can be slow on very deep graphs (`IRNode.__str__` has no depth limit, as #43111 found). This is opt-in debug logging.
- Overlaps with #57310, whose allow-list change should become unnecessary.
- A follow-up PR could make the KV-cache writers (reshape_and_cache, reshape_and_cache_flash and their Triton versions) reject keys whose heads are not packed, so a future layout change raises an error instead of silently corrupting the cache.
