## 正文(PRD / 提案全文)

## Summary

Post-capture KV sizing currently requires the prefill CUDA graph to have captured every reachable prefill shape. This RFC proposes relaxing that to the treatment the decode side already uses: allow the prefill bucket list to top out below `chunked_prefill_size`, and reserve activation headroom for the eager prefill instead of disabling the feature.

## Current behavior

`post_capture_kv_sizing_planned()` in `python/sglang/srt/server_args.py` bails out entirely when the largest reachable prefill forward batch is not already captured:

```python
if (
    prefill_cfg.backend == Backend.DISABLED
    or self.chunked_prefill_size <= 0
    or self.max_prefill_buffer_tokens() > max(prefill_cfg.bs or (0,))
):
    return False
```

`max_prefill_buffer_tokens()` is `chunked_prefill_size` outside PP dynamic chunking, and `prefill.max_bs` defaults to `chunked_prefill_size`, so the condition holds under default settings. It stops holding as soon as anyone passes `--cuda-graph-max-bs-prefill` below `chunked_prefill_size`, at which point the feature turns off with no log saying why.

## Why the constraint is stronger than the requirement

**The two values are independent knobs.** `chunked_prefill_size` is a scheduling ceiling; prefill `max_bs` is capture coverage. Requiring the latter to be >= the former makes "capture covers every reachable prefill shape" a precondition of post-capture sizing. That is an implementation convenience, not something the mechanism needs.

**What the mechanism needs is a bound on eager activation, not the absence of eager forwards.** The benefit of post-capture sizing is that graph memory is *measured* rather than *estimated*. That benefit is orthogonal to whether some forwards run eager. The decode side already operates on exactly this reading: `compute_post_capture_kv_resize()` in `python/sglang/srt/model_executor/model_runner_components/kv_pool_runtime.py` accepts a captured decode `max_bs` below `max_running_requests` and raises the reserve instead of bailing out.

```python
eager_decode_gap = (... and decode_max_bs < running_requests)
if eager_decode_gap or mambaish_config(...) is not None:
    headroom_gb = max(headroom_gb, ...pre_capture_activation_reserve_mb(...) / 1024)
```

**The current gate makes two legitimate goals mutually exclusive.** Lowering prefill `max_bs` is a reasonable thing to want: the bucket list runs to `chunked_prefill_size` and its largest buckets cost seconds each to capture. Today you can have a shorter capture or post-capture sizing, never both.

The one defensible argument for the status quo is that the eager prefill activation peak is hard to estimate, and under-reserving means OOM. But decode carries the same uncertainty and chose to reserve. That argues for a more conservative formula, not for a hard gate.

## Proposal

Move the prefill condition out of the gate and onto the headroom path that `eager_decode_gap` already uses:

- keep `backend == DISABLED` and `chunked_prefill_size <= 0` as hard gates, since those are genuinely inapplicable
- when `max_prefill_buffer_tokens() > max(prefill_cfg.bs)`, warn and raise `headroom_gb` to cover the eager prefill activation peak

No new estimate is needed: `pre_capture_activation_reserve_mb()` already has a prefill branch keyed on `chunked_prefill_size`. Its 10GB floor on large-memory GPUs makes the relaxed path less profitable than the fully-captured one, but still better than the current fallback, which on top of the same activation reserve also *estimates* graph memory via `reserve_for_graph_mb()`.

A tighter variant would reserve only the delta between the eager prefill peak and the largest captured bucket's peak, since the latter is already reflected in the measured free memory. That needs a model of how activation scales with token count, so it seems worth doing only if the simple version proves too conservative in practice.

## A smaller item that can land independently

Whichever way the above goes, the gate should not be silent. Passing `--cuda-graph-max-bs-prefill` below `chunked_prefill_size` today disables post-capture KV sizing with no diagnostic at all. A single `logger.warning` naming the two values would have saved the debugging in #33847 and costs nothing.

## Context

This surfaced in #33847, where a CI-wide `--cuda-graph-max-bs-prefill 1024` default silently gated the feature off on H100-class GPUs, on which `chunked_prefill_size` defaults to 8192.
