## 正文(PRD / 提案全文)

**Software-dequant fp8 KV cache for MLA on Ampere (sm80/sm86): the pieces exist, here is a consolidated path, a concrete field case, and a standing validation offer**

Three threads on this have stalled independently. This issue asks for a maintainer decision on a merge path and volunteers a production validation site.

**Problem**
MLA models (DeepSeek V4.x, Kimi-K3, GLM-5.3) on Ampere are bf16-KV-only today:

- `TritonMLAImpl` raises for any `--kv-cache-dtype fp8*` below SM89 ("native FP8 (fp8e4nv) requires SM89+") — even though the `fp8_ds_mla` layout is *storage-only*: queries stay bf16 and pages are dequantized on load, so no native fp8 arithmetic is required;
- `TRITON_MLA_SPARSE` lists only auto/fp16/bf16 (`triton_mla_sparse.py`);
- the fp8-capable sparse kernels (FlashMLA-sparse, FlashInfer-MLA-sparse) are sm90+ only.

Cost: **1152 B/token/layer instead of 656 B** (the fp8_ds_mla layout) — 1.76× KV capacity left on the table for every Ampere MLA deployment.

**The pieces already exist (all open, none merged)**
- #47629 — TRITON_MLA_SPARSE for sm80 (stated prerequisite in #48374's discussion)
- #48374 — sparse-path fp8 KV RFC; author verified end-to-end on sm_86, including an engine-level boot on a GLM MoE-DSA model (teacher-forced cosine 0.999996 vs bf16, 1.76× pool) and describes the implementation as working
- #52202 — dense TritonMLA decode RFC (~220-line software-dequant kernel sketch, storage-only fp8_ds_mla)
- #55173 — portable Triton fp8e4nv conversions (SM75 bitcode), A100-validated
- #55184 / #55177 — DSV4 pre-sm90 software-fp8 sparse-MLA omnibus, A100-validated (currently conflicted/unreviewed)

**Field case (why this matters beyond 24 GB cards)**
We run GLM-5.3-Flash (hybrid KDA + sparse-MLA indexer, AWQ W4A16) in production on 4× A800 (sm80) at max-model-len 1M — stock vLLM cannot serve this model on sm80 (no sparse-MLA backend), so a fork is required (wtdcode/vllm-backport v0.13.1). Baseline, verified this week on the bf16 path: 930K-context needle recall 5/5, decode 70 tok/s at 930K context, KV/token 11.6 KiB.

- KV budget 24.7 GiB/card → 2.25M tokens → max **2** concurrent full-length 1M requests (2.15×);
- with fp8 KV the same budget yields **~3.7×**, and 4× full-length becomes reachable within the existing headroom.

Ampere A800 remains the most widely deployed 80 GB datacenter GPU in China (per #57144); "more concurrent full-length contexts" is a measurable, recurring demand there.

**Proposed path (please advise or pick)**
1. Land #55173 (portable conversions) as the shared foundation.
2. Once #47629 lands, accept the sparse-path fp8 KV as a PR based on #48374's verified work.
3. For dense TritonMLA, evaluate #52202's sketch. Everything gated behind explicit `--kv-cache-dtype fp8_e4m3`/`fp8_ds_mla`; bf16 stays default; warmup/autotune must key on the cache dtype (the dtype-blind autotune behavior is documented in #48374).

**Standing offer**
We can validate candidate branches on our A800 sm80 fleet with a production-shape harness: teacher-forced parity vs bf16, needle-recall at 930K–1M contexts, throughput/concurrency sweeps, and a cross-session state-pollution canary (this hybrid model class is sensitive to cache interactions; our canary keeps the comparison isolated from speculation). We will report numbers publicly either way.

**Questions**
1) Is software-dequant fp8 KV for Ampere acceptable in principle?
2) Preferred sequencing among the pieces above?
3) For the dense TritonMLA decode kernel, is the #52202 sketch the shape you would accept?
