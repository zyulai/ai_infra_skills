## Overview



On ROCm, give the K/V cache views used by `TRITON_ATTN` a Triton `ptr_range()` bounded by their layer's region. This lets Triton's AMD backend keep 32-bit buffer addressing for them, fixing a ~16% throughput regression on RDNA3 introduced by #51718, which moved the KV cache into one backing allocation.

## Claims



- `TRITON_ATTN` throughput on Radeon Pro W7900 (gfx1100):
  - **+18%** for Whisper-large-v3: 5.34 → 6.31 req/s, back to the pre-#51718 level of 6.40.
  - **+18%** for Qwen2.5-7B-Instruct: 2.70 → 3.19 req/s.
- No accuracy change:
  - Whisper transcripts are token-identical on all 2,703 LibriSpeech validation-clean clips.
  - lm-eval GSM8K is within run-to-run noise.
- No change to KV-cache allocation, layouts, KV connectors/offloading or non-ROCm platforms, and no new configuration.

## Details



**Root cause.**
- Triton's AMD backend marks a pointer argument `tt.pointer_range = 32`, which enables buffer loads with 32-bit offsets, only if `arg.ptr_range()` or else `arg.untyped_storage().size()` is ≤ 2 GiB (`is_within_2gb`).
- Since #51718, each layer's KV cache is a view into one allocation (~36.6 GiB here), so the storage check fails.
- `kernel_unified_attention` therefore uses 64-bit addressing: 205 → 256 VGPRs, and occupancy on gfx1100 drops from 7 to 5 waves/SIMD.
- Bisected with only vLLM changing: #51718 measures 5.40 req/s, its parent 6.40.

**Change.**
- `set_triton_ptr_range(region, *views)` sets each view's `ptr_range()` to the bytes from its `data_ptr()` to the end of `region`, computed from shape and strides.
- `TritonAttentionImpl` calls it on ROCm for the K/V views in `forward` and in `do_kv_cache_update`.

**Safety.**
- The bound is the view's real extent, and Triton still checks it against 2 GiB at every launch. Layers above 2 GiB, or block-outermost layouts, keep 64-bit addressing.
- Both kernels only address within the view: through block-table indices or slot mappings, with padding slots skipped. This is the assumption Triton already made before #51718.
- Views are rebuilt every forward, and only host-side metadata is read, so there is no GPU synchronization.

**Duplicates.** I searched open and closed PRs and issues for `ptr_range`, `pointer_range`, buffer ops/addressing, 2 GiB, and #51718 regressions; none overlap.

+def set_triton_ptr_range(region: torch.Tensor, *views: torch.Tensor) -> None:
+    """Bound the bytes Triton kernels may access through ``views``.
+
+    Triton's AMD backend uses 32-bit buffer addressing only for pointer
+    arguments within 2 GiB. It checks ``ptr_range()`` first and otherwise the
+    size of the whole storage, so views into one large allocation (such as a
+    layer of the KV cache) lose it. Each view gets the distance from its
+    ``data_ptr()`` to the end of ``region``; kernels must not access past it.
+    """
+    if region.numel() == 0:
+        return
+    last = sum((n - 1) * stride for n, stride in zip(region.shape, region.stride()))
+    region_end = region.data_ptr() + (last + 1) * region.element_size()
+    for view in views:
+        view.ptr_range = functools.partial(int, region_end - view.data_ptr())
