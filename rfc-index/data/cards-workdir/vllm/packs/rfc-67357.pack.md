## 正文(PRD / 提案全文)

### Motivation.

Multi-turn agentic workloads often combine long, growing conversation histories with relatively short outputs. In Prefill/Decode (P/D) disaggregated serving, these workloads can concentrate pressure on Prefiller instances, especially during request bursts.

The Decoder that served the previous turn may still hold a substantial reusable prefix in its local KV cache, including tokens generated during that turn. Sending the next request through the Prefiller can introduce queueing, additional prefill computation, and KV transfer, even when the Decoder could reuse its local prefix and compute the remaining suffix.

We propose **Decoder Append-Prefill**: an opt-in path that allows a follow-up request to reuse KV on its previous Decoder and perform the remaining prefill locally. When the required local cache is unavailable, the request falls back to ordinary P/D.

The target is a workload where Prefiller pressure is high, Decoder capacity is available, and the uncached suffix is relatively short. The design must account for the effect of additional prefill work on ongoing decode requests.

### Proposed Change.

**1. Request flow**

1. The first turn follows the ordinary P/D path.
2. The router records the Decoder endpoint and data-parallel rank that served the session.
3. For an eligible follow-up turn, the router sends the complete request directly to that Decoder and rank, requesting local-cache admission.
4. The Scheduler checks the actual reusable local KV prefix. If admitted, the Decoder computes the uncached suffix and generates the response.
5. If the admission condition is not satisfied, the Decoder rejects the attempt before executing prefill or generating output. The router retries the original request through ordinary P/D.

Clients continue to provide the complete conversation history. The reusable range is determined by the actual token-prefix match. Session affinity identifies a likely cache owner; it does not reserve KV blocks or guarantee residency.

**2. Request-level admission policy**

Introduce a request-level option expressing that local prefill is conditional on a usable local KV prefix.

The reference implementation uses `require_decoder_cache_hit` and admits a new local attempt when the usable local prefix is nonzero. The upstream field name and API placement are open for discussion.

A nonzero hit alone does not bound the remaining prefill work. We would welcome feedback on whether the initial interface should also support a minimum hit threshold or maximum uncached-suffix budget. The external router can additionally decide whether to attempt local execution based on its routing and load policy.

The feature should be disabled by default.

**3. Structured rejection and Scheduler integration**

The engine needs a machine-readable result that distinguishes an admission rejection from successful generation and other failures.

For streaming requests, a zero-token rejection must reliably reach the router. The router should consume the rejected attempt internally and preserve the original request and generation budget for P/D fallback. Protocol metadata emitted before admission completes must not make the rejected attempt appear to be a successful response.

We propose integrating admission into the existing Scheduler cache-lookup path, allowing it to reject an individual waiting request and continue scheduling other requests. The implementation should preserve KV block lifetimes, request cleanup, and synchronous/asynchronous output ordering.

The reference implementation currently copies the upstream scheduling body to insert this check. An upstream admission point would reduce that maintenance burden. We would like feedback on whether this should be a direct Scheduler policy or a small extension interface.

**4. Preemption and KV recovery**

Admission of a new follow-up request and restoration of an existing preempted request require separate handling.

An existing request with valid offload recovery state should be allowed to restore its own KV through the connector lifecycle. A CPU-offloaded copy for an earlier request does not, by itself, satisfy local-cache admission for a new turn.

A zero-output rejection can fall back through ordinary P/D. Recovery failure after output has been generated requires an explicit terminal result unless an accurate continuation protocol is available.

Transparent continuation through Prefiller reconstruction after output is separate work. It requires preserving the original input tokens, generated tokens, remaining generation budget, and streaming semantics. This RFC does not assume that replaying generated text into chat messages provides that guarantee.

**5. Performance and validation**

Evaluation should cover both the intended benefit and Decoder interference:

- End-to-end latency, TTFT, throughput, and Prefiller queueing.
- TPOT and tail latency for concurrent decode requests.
- Actual local-cache admission rates and cache-miss fallback costs.
- Correctness with complete multi-role conversation histories.
- Cache eviction, DP routing, cancellation, and synchronous/asynchronous scheduling.
- Same-request offload restoration where supported.

Workloads should vary conversation length, uncached-suffix length, arrival rate, Decoder pressure, and cache residency.

**6. Questions for the community**

- Is request-level local-cache admission the appropriate upstream abstraction?
- How should admission rejection be represented through engine outputs and serving APIs?
- Should the initial policy require only a usable prefix, or also bound uncached-suffix work?
- What is the smallest maintainable Scheduler integration?
- Which connector and hardware configurations should form the initial validation scope?

### Any Other Things.

A reference implementation and deployment-specific evaluation are available in [[vLLM-Ascend PR #19884](https://github.com/vllm-project/vllm-ascend/pull/19884)](https://github.com/vllm-project/vllm-ascend/pull/19884). The PR documents the MRV2 benchmark methodology, local admissions and P/D fallbacks, the TPOT trade-off, and a separate same-request offload-restoration validation. These results provide evidence for the tested Ascend deployment; validation on other backends remains necessary.

Related discussions:

- [[RFC #24256: Cache-hit-based admission control](https://github.com/vllm-project/vllm/issues/24256)](https://github.com/vllm-project/vllm/issues/24256). Decoder Append-Prefill is a local-cache-focused use case of this direction. The earlier RFC also considers external/offloaded cache and preemption handling. We would like to build on that discussion when defining the admission interface.
- [[RFC #32733: Bidirectional P/D KV transfers](https://github.com/vllm-project/vllm/issues/32733)](https://github.com/vllm-project/vllm/issues/32733). This proposes transferring reusable Decoder KV to the Prefiller and explicitly discusses incremental prefill on the Decoder as an alternative. Decoder Append-Prefill explores the trade-off of using Decoder compute to bypass the Prefiller for suitable follow-up requests. Its usefulness depends on workload and available Decoder capacity.
