## 正文(PR 描述)

## Overview

Fixes one item from #67307. #67071 dropped `gpu_memory_utilization: 0.90` from the Kimi-K3-pruned75 DSpark TP4 eval config. Since then, the server dies at startup with a CUDA OOM in `run_kv_cache_sizing_warmup`. This PR releases the KV cache blocks that `warmup_kernels` committed before the sizing warmup runs. It uses the same call that already releases warmup's blocks before CUDA graph capture (#66523).

## Claims

- The Kimi-K3-pruned75 DSpark TP4 eval config now starts on 4 x B200 with `gpu_memory_utilization` unset, and it answers a chat request. Before this PR, every run failed with a CUDA OOM in `run_kv_cache_sizing_warmup`.
- The config does not need the `gpu_memory_utilization: 0.90` stopgap to start (the CUDA counterpart of #67244). With the default, rank 0 ends with a KV cache of 629 blocks (25.92 GiB). With 0.90 it gets 402 blocks (16.59 GiB).
- The way the final KV cache size is measured does not change.
- A new regression test fails without the fix and passes with it.

## Details

**Root cause.** These numbers are from rank 0, taken with temporary debug logging that is not part of this PR.

1. At KV cache init, `warmup_committable_blocks` is set from free memory, minus the profiled activation peak and a margin. Here 51.76 GiB was free. Warmup may commit 967 blocks of 42.2 MiB, which keeps 6.51 GiB (peak) + 4.88 GiB (margin) free.
2. `warmup_kernels` runs up to `max_num_seqs` small requests. Kimi-K3 has 3 KDA (Mamba-like) groups, and each holds 1 + 8 speculative blocks per request. A block is 3200 tokens. So 33 requests commit 958 blocks (39.47 GiB), which is nearly all that warmup may commit.
3. Commits are grow-only. The only release is the one before CUDA graph capture, and capture comes after the sizing warmup. The JIT warmup also grew torch's reserved memory by about 6 GiB. So the full-budget sizing step (16384 tokens, `prompt_logprobs=20`) starts with 6.34 GiB free, beside 958 committed blocks, but it addresses only 83 of them. The FlashInfer TRT-LLM MXFP4 MoE kernel then asks for a 2.04 GiB workspace and fails.
4. With 0.90, the KV cache capacity is 30.04 GiB, and `committable_blocks()` is capped by it. So `warmup_kernels` commits about 12 GiB less, and the step fits. This is why the stopgap works. But `docs/configuration/optimization.md` says that with the extensible KV cache, `gpu_memory_utilization` defaults to 1.0 and "doesn't need tuning to avoid out-of-memory errors".

**Fix.** In `Worker._compile_or_warm_up_model`, call `kv_cache.commit(kv_cache.min_committed_blocks, shrink=True)` just before `run_kv_cache_sizing_warmup`. The `kv_cache = ...` lookup and its `assert` move up for this call. The released blocks only hold data from finished warmup requests. Each sizing step then commits only the blocks it addresses (`ensure_kv_cache_blocks`). In a debug run with the fix, the full-budget step started with 42.34 GiB free. Its measured transient (peak − current) was 6.27 GiB, which is below the profiled 6.51 GiB. So the reserve was big enough. The memory the step needed was being held by leftover blocks. The sizing reads torch's allocated peak, and the final size uses free plus committed memory. Neither depends on how many blocks warmup held.

**Related PRs.** #67296 keeps more headroom for allocator fragmentation. This PR does not change the headroom. Once the blocks were released, the measured transient fit in the existing reserve, so headroom was not what ran out here. I did not test #67296 on this config. #67244 is the ROCm config stopgap. This PR fixes the code path instead, and keeps `gpu_memory_utilization` unset.

**Options not taken.**

- Make `ensure_kv_cache_blocks` shrink as well as grow. This remaps about 39 GiB twice inside `warmup_kernels` and changes all three callers.
- Lower `warmup_committable_blocks`. This is tuning, and it shrinks the kernel warmup batch everywhere.
- Run the sizing warmup before `warmup_kernels`. The sizing steps would then JIT compile inside the measured peak window.
- Restore 0.90 in the config. This is a stopgap that turns off the documented default.

**Scope and limitations.**

- `run_kv_cache_sizing_warmup` has one caller (`gpu_worker.py`). The CPU and XPU workers have no extensible KV cache.
- Validated only on 4 x B200. The CI job's GSM8K eval was not run. Validation covers startup and one chat request.
- `warmup_committable_blocks` is still fixed at KV cache init, before the JIT warmup grows torch's memory (about 6 GiB here). `warmup_kernels` still ends with about 6.3 GiB free. This did not fail here, because its steps are small. It is a different mechanism and is left out of this PR.
