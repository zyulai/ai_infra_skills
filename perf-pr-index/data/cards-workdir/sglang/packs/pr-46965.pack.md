## Motivation

Since #44399, `--attention-backend fa3` runs Gemma-4's 10 full-attention layers (head_dim 512) on FA4. FA4 has no FP8 KV path on SM90, so `--kv-cache-dtype fp8_e4m3` is rejected at init, although FA3 already reads FP8 KV on the 50 sliding-window layers (head_dim 256). The sliding-window layers also run on FA4 whenever a batch carries image tokens, including the VLM startup warm-up, so FA4 needs FP8 KV at both head dims.

This PR lets FA4's SM90 forward read an FP8 e4m3 KV cache at head_dim 256 and 512. Gemma-4 can then serve with `--kv-cache-dtype fp8_e4m3` on H100/H200, which doubles both KV pools.

## Modifications

- **Kernel** (`flash_fwd_sm90.py`, `named_barrier.py`, `utils.py`): K/V tiles are loaded as fp8 into a staging buffer and cast to fp16 in shared memory by the MMA warpgroups. The K/V descales fold into the softmax scale and the output scale. At head_dim 512 each warpgroup casts its half of V; at head_dim 256 all MMA threads cast the whole of V behind one barrier. One pipeline stage when FP8 KV is on.
- **Interface** (`interface.py`): bf16/fp16 Q with fp8 e4m3 K/V on SM90 selects this path, and the Q/K/V dtypes join the compile key. Unsupported cases raise `NotImplementedError`: e5m2, head_dim other than 256 or 512, non-paged KV, `qv`, `rel_bias`, block sparsity, `mma_pv_is_rs=False`. bf16 Q is narrowed to fp16 in-kernel, so |q| above 65504 overflows; Gemma-4's QK-norm keeps Q far below that.
- **Backend** (`flashattention_backend.py`): the `fa3` backend accepts an `fp8_e4m3` cache when it upgrades layers to FA4. FA4 layers keep Q unquantized and receive the k/v descales; FA3 layers quantize Q as before. On SM90 the `fa4` backend rejects an `fp8_e4m3` cache at init for MHA models with head_dim other than 256 or 512; MLA keeps its existing path.

Follow-up: a native FP8 MMA path on SM90 (WGMMA e4m3 for QK^T and PV) would drop the in-kernel cast to fp16. It is left for a separate PR to keep this change small.

Usage:

```bash
python -m sglang.launch_server --model-path RedHatAI/gemma-4-31B-it-FP8-block \
  --attention-backend fa3 --kv-cache-dtype fp8_e4m3
```

## Speed Tests and Profiling

Measured using `sglang.benchmark.serving` on `RedHatAI/gemma-4-31B-it-FP8-block`, 1×H200, TP1, both arms from the same build; the FP8 arm adds `--kv-cache-dtype fp8_e4m3`. The cases target the memory-limited regime: in-flight KV (concurrency × (input + output)) exceeds the BF16 pools and fits in FP8's.

Common serving settings:

    --tp-size 1
    --attention-backend fa3
    --page-size 64
    --context-length 65536
    --chunked-prefill-size 8192
    --max-running-requests 128
    --mem-fraction-static 0.9
    --swa-full-tokens-ratio 0.2

Benchmark settings:

- Random dataset with tokenized prompts and fixed input/output lengths.
- Requests per cell: 2–4 × concurrency.
- Request rate: unlimited.
- Random-length ratio: 1; one seed per cell, so no cell reuses another's prompts.

Summary:

- FP8 KV holds more requests in flight: the mean decode batch grows up to 2× (for example 43.6 → 64.0 at 4k/c64), and retractions fall from 16 → 0 at 1k/c64 and 11 → 0 at 4k/c64.
- Output throughput rises 10–25 % at 1k–4k input and 4–6 % at 8k–16k. Median TTFT falls up to 61 %, since fewer requests wait for KV space.
