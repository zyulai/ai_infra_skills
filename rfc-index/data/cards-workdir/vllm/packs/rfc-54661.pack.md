## 正文(PRD / 提案全文)

### Motivation.

**Summary.** On hybrid models that carry an EAGLE-style sliding-window draft group (DFlash/DSpark-shaped drafters), that group hashes `cdiv(sliding_window - 1, block_size) + 1` block ids at *every* prefix-cache boundary and frees them *cached* onto the protected tail of the one LRU that all groups share, while — once it is exempted from the hit `min` — contributing nothing to the reconciled hit length. On a GLM-5.3-Flash deployment this one group spends 87% of the prefix cache and caps coexisting conversations at ~50K tokens each. A per-group retention interval, combined with exempting such hit-inert groups from the hit `min`, restored ~4× the coexisting-conversation capacity with the fine hit grid kept for the target model's groups, and a third party reproduced 99.95% cached across alternating 120K conversations. All numbers below are **deployment evidence from a vLLM fork**, not upstream verification; the code reading is against upstream `main` @ `22df3a3`. This RFC asks for agreement on the policy before any code is posted as a PR.

**Where the cost comes from (upstream `main` @ `22df3a3`, verified).**

- `--prefix-cache-retention-interval` (`vllm/config/cache.py:156-158`, `vllm/engine/arg_utils.py:530`) reaches the coordinator as one scalar, `KVCacheCoordinator.retention_interval` (`vllm/v1/core/kv_cache_coordinator.py:158`), and is handed unchanged to every manager at both `cache_blocks` sites (`:306-326` base, `:740-768` hybrid).
- Everything below the coordinator is already per group: `SingleTypeKVCacheManager.cache_blocks(..., retention_interval=None)` (`vllm/v1/core/single_type_kv_cache_manager.py:432-436`), and each `reachable_block_mask` interprets it against its own block size and window (`:485-`, `:1010-`, `:1472-`).
- A sliding-window group needs `need = _contiguous_blocks_for_hit(window, block_size, use_eagle)` contiguous blocks at every retained boundary (`:898-908`, `:1028`); a full-attention group needs one block per boundary. Those SWA blocks are freed by `remove_skipped_blocks` -> `_remove_blocks_in_range` -> `BlockPool.free_blocks` (`:632`, `:605`), and because they are hashed they go to `blocks_to_evict_last` / `append_n`, the LRU *tail* (`vllm/v1/core/block_pool.py:723-747`). Full-attention blocks stay allocated until request end; Mamba align-mode state blocks may also be freed mid-request (`single_type_kv_cache_manager.py:1529-1557`), but a 3584-token Mamba group frees one id per segment where the draft group frees 33. The group with the least reusable state gets the most eviction protection.
- `HybridKVCacheCoordinator.find_longest_cache_hit` folds every attention group, EAGLE draft group included, into the reconciled hit (`kv_cache_coordinator.py:770-903`, `curr_hit_length = _new_hit_length` at `:871`). So giving the draft group a sparser retention on `main` today would shorten everyone's hit — which is why the fork below carries a `min` exemption first.

**Measured (deployment evidence: GLM-5.3-Flash, 2× DGX Spark, TP=2, DFlash2 draft k=7; vLLM fork `0.1.dev20051+g487ecf187`; GLM-5.3-Flash support upstream is #53906).** Groups: MLA block 3584, four Mamba "align" groups at 3584, one EAGLE sliding-window draft group with window 2048 / block 64, scheduler block 3584; one `BlockPool` of 643 block ids (642 usable; derived from the logged `max_concurrency`, see *Any Other Things*).

| group | block ids per cached 3584-token segment (dense retention) |
|---|---:|
| full attention (MLA) | 1 |
| Mamba × 4 | 4 |
| **draft sliding window** | **33** (`cdiv(2047, 64) + 1`) |
| total | 38 |

Two conversations of `S` segments coexist only while `642 >= 43·S` (each of B's segments pops 38 ids while A's cached draft tail contributes 33 back), i.e. `S <= 14.9`. Measured on a clean server: 14 segments OK / 17 evicting; pair ladders at 45K / 56K / 66K tokens hit 99% / 0% / 0%.

Raising the single global `--prefix-cache-retention-interval` to 14336 restored the ladder to 99 / 98 / 97 / 96% at 45K / 56K / 66K / 80K — but it bought that capacity by coarsening *everyone's* retention grid: a diverging sub-agent prefix then hit only 45% of a ~29K prompt instead of landing on the 3584 grid.

With per-group retention — retention `0` (reachable-boundary tails only) on the draft group, dense for MLA/Mamba — and the draft group exempted from the hit `min`, the per-segment cost drops to 5 ids (+33 per turn boundary), projected `S <= 54` (~195K tokens per conversation) with the 3584 hit grid kept. Independent reproduction by a third-party tester on a different 2× DGX Spark deployment (`max_model_len=524288`, `max_num_seqs=4`), two distinct 120K-token conversations alternated A -> B -> A -> B:

```
A cold             cached      0 / 119,995   TTFT 174.522s
A warm             cached 119,936 / 119,995   TTFT   0.581s
B cold             cached      0 / 119,995   TTFT 174.392s
B warm             cached 119,936 / 119,995   TTFT   0.590s
A return after B   cached 119,936 / 119,995   TTFT   0.567s
B return after A   cached 119,936 / 119,995   TTFT   0.567s
```

99.95% cached on every return, where the same shape previously evicted the parked conversation. Sources: https://github.com/MiaAI-Lab/GLM-5.3-Flash-EXL3-2x-DGX-Sparks/pull/83 (per-group retention; the tester's receipt above is in its comments) and https://github.com/MiaAI-Lab/GLM-5.3-Flash-EXL3-2x-DGX-Sparks/pull/84 (fine-grained hits, tested together). Those are recipe overlays on a fork; nothing there applies to `main` as-is.

### Proposed Change.

Three parts, in this order. The ask is agreement on 1 and 3 before any of the code is posted as a PR.

1. **Exempt hit-inert sliding-window groups from the reconciled hit `min`, with an explicit per-group lookup/consumption contract.** A sliding-window group is *hit-inert* when (a) it is EAGLE-annotated (`KVCacheGroupSpec.is_eagle_group`), so its hit length is not needed to bound the target's; (b) its window is shorter than `_cache_hit_alignment_tokens`, so its cached tail is only ever consultable at an alignment boundary; and (c) sparse retention is actually reachable for it: `need < alignment_tokens // block_size` (otherwise `reachable_block_mask` returns dense anyway, `single_type_kv_cache_manager.py:1027-1053`), `block_size` divides the alignment, and `extra_retained_tokens == 0` (it separately affects admission/retention sizing, `vllm/v1/kv_cache_interface.py:694-730` / `single_type_kv_cache_manager.py:888-895`; nonzero values require separate handling or exclusion).

   The group is still looked up. If its own hit reaches the candidate boundary, its blocks are consumed as today — that is how the retained boundary tail keeps a conversation's own follow-up turn warm. If its hit is *shorter*, it must neither shorten `curr_hit_length` nor inflate `longest_hit_length`, and its per-group result must be an explicit "no reusable blocks; allocate a fresh window", not the empty list the current lookup would return: today `find_longest_cache_hit` initialises empty per-group results (`kv_cache_coordinator.py:795-800`), fills them only for `attention_groups` (`:815-874`), and `KVCacheManager.get_computed_blocks` passes them straight to allocation (`vllm/v1/core/kv_cache_manager.py:228-294`), so an empty draft result cannot reuse a retained tail. This is the same per-group-boundary concern #53786 raises for SWA fine-grained hits, and it is the part that needs design agreement.

   **Unproven risk, stated plainly:** final outputs are protected by target verification, but the drafter's *acceptance* depends on the window's KV being valid. Whether a newly allocated window block is zeroed depends on `needs_kv_cache_zeroing` (`single_type_kv_cache_manager.py:88-94`); the design must guarantee the window is recomputed during prefill of the uncached remainder rather than read stale, and the acceptance dip while it refills has only been measured on the fork (decode-rate control within noise), not upstream. It is free whenever the remainder is at least one window — the diverging-prefix / new-turn case. #50457 (all-sliding DFlash drafter with prefix caching, PR) is in this area and may be the right home.

2. **Resolve the retention interval per KV cache group.** `KVCacheCoordinator` gains `retention_interval_by_group: tuple[int | None, ...]`, resolved once in `__init__` and indexed at both `cache_blocks` sites. The manager API is untouched (already per call). With the identity resolution behaviour is byte-identical, which the accompanying tests pin. The seam patch is ready and rebased on `22df3a3` — `vllm/v1/core/kv_cache_coordinator.py` +37/−4, tests +72: https://github.com/nood-co1/vllm/tree/feat/per-group-prefix-cache-retention (commit https://github.com/nood-co1/vllm/commit/b9f82ae0f946039be1e96084ef15399e8cf2e07c). It is deliberately *not* opened as a PR: on its own it is plumbing with no user-visible effect, and it is only safe to use once part 1 exists.

3. **Policy:** resolve `retention_interval = 0` for groups that satisfy part 1's predicate, i.e. cache only the reachable-boundary tails (`SlidingWindowManager.reachable_block_mask`, `retention_interval == 0` branch), and the configured value for every other group. A genuine SWA target model (window spanning the alignment, or a group still inside the `min`) is unchanged. A user override can come later if wanted; the default should not need one.

Offered as a follow-up PR (parts 1–3 together, or 2 first if maintainers prefer the decomposition) once the policy is agreed.

**Caveats.** All measurements are deployment evidence from a fork on GLM-5.3-Flash, which is not yet in `main` (#53906); the block-id arithmetic uses code paths that exist unchanged on `main` (`SlidingWindowManager.reachable_block_mask`, `BlockPool.free_blocks`).
