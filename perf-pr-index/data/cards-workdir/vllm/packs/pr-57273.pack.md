## Purpose

Retune one kernel's launch parameters for sm_90 (H100/H200/H20): `_qsa_sparse_paged_gqa_splitk_kernel`, the Triton split-K kernel that runs the sparse attention of Qwen3.8-Flash-Next's QSA layers over the 2048 selected tokens per query. Its tile width, split count and warps per CTA come from `_select_config()` in `vllm/models/qwen4_exp/nvidia/ops/qsa.py`, a table tuned on GB300 (#55557 added an sm_120 table beside it). Measured on H20, the GB300 entries are the wrong geometry in most decode regions, so this PR adds `_select_sm90_config()` in the same shape as the sm_120 helper. Besides that nothing else changes. Regions where the default entry is already fastest return `None` and keep it.

Each row below is one region of `_select_config`'s key, `base_programs = query rows × kv_heads per rank` (at TP8 with MTP3 that is 4 × concurrency, so the second column shows which serving points land in the region). "GB300 entry" is what runs today, "sm_90 entry" what this PR selects on H100/H200/H20; a tuple is (BLOCK_N, target_splits, num_warps). "Latency" is the change in this kernel's time per call when switching from the GB300 entry to the sm_90 entry, measured on one H20 (attention + split-K merge + fused output gate, CUDA-graph replay, median of 3 interleaved orders × 9 replays, hot and L2-evicted), at the three head geometries group 3 / 6 / 12 = query heads per kv head at TP8 / TP4 / TP1-2. Negative is faster.

bf16 K/V cache:

| `base_programs` | TP8 + MTP3 | GB300 entry | sm_90 entry | latency, group 3 / 6 / 12 |
|---|---|---|---|---|
| ≤ 24 | C1 – C6 | (32, 64, 4) | (64, 64, 2) | −11 % / −12 % / −14 % at 4 rows, −12 % / −19 % / −21 % at 16 rows |
| 25 … 32 | C7 – C8 | (32, 16, 1) | (64, 64, 2) | −7 % / −7 % / ±0 |
| 33 … 64 | C9 – C16 | (32, 8, 1) | (32, 16, 1) | −8 % / −6 % / −4 % |
| 65 … 128 | C17 – C32 | (32, 4, 1) | (32, 8, 1) | −14 % / −13 % / −9 % |

| 257 … 512 | C65 – C128 | (64, 4, 2) | (32, 4, 1) | −13 % / −12 % / −4 % |

|---|---|---|---|---|
| ≤ 24 | C1 – C6 | (32, 64, 4) | (64, 64, 2) | −8 % / −8 % / −20 % at 4 rows, −15 % / −18 % / −22 % at 16 rows |

| > 2048 | prefill | same as bf16 | unchanged | not measured |

Why: at small `base_programs` the kernel hands tiles to split programs stride-wise, so (32, 64, 4) leaves one program with a two-tile tail (65 tiles over 64 splits) that the launch waits for, whereas a 64-wide tile gives 33 tiles over 33 splits, one per program. From a few hundred programs up the kernel is gather-bound and wants resident CTAs: BLOCK_N 64 needs 68–76 KB of shared memory per CTA (3 CTAs/SM) against 35–41 KB for BLOCK_N 32 with one warp (6 CTAs/SM). With fp8 the in-kernel dequant adds per-tile work, which is why the 64-wide entries lose almost half the time there.

No region regresses beyond run-to-run noise on any geometry; every candidate passed the FP32 reference at `rtol=atol=2e-2`. This kernel is 3–9 % of a decode step on this model, so end-to-end throughput moves by well under 1 % with bf16 caches; with fp8 caches the change is about 6 % of a C128 decode step. All measurements are H20; H100/H200 were not available. `benchmarks/kernels/benchmark_qsa_select_config.py` (added here) re-measures one shape in about 10 s, so a maintainer can check the direction there:

```bash
python benchmarks/kernels/benchmark_qsa_select_config.py --requests 128 --query-len 4 --group 3 --kv-heads 1 [--kv-dtype fp8]
```
