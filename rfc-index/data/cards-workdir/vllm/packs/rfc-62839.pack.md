## 正文(PRD / 提案全文)

### Motivation.

https://github.com/vllm-project/vllm/pull/62840 contains an initial implementation of the proposal described in this RFC.

## Bottom line

One new TileLang kernel, ~113 lines, fuses DSpark's confidence head (`cat + cast + GEMV + sigmoid`) into **one CUDA launch, one CUDA-graph node, zero fp32 temporary** per decode step. Median kernel-latency speedup vs `torch.compile`: **1.92× on RTX 5090 (SM120)** and **1.90× on H200 (SM90)**; real-checkpoint A/B under greedy decode produces **0/30 divergent outputs** on both GPUs. TPOT-level gain is < 0.05 % — the value is on the mechanism (launch count, graph nodes, activation-memory traffic), not end-to-end. DeepInfer (DeepSeek's own engine) already ships an equivalent fused kernel via `AcceptRatePredictor` and the same PDL trick; this is a port-with-FP32-weight.

## Summary

Adaptive speculative decoding in vLLM (the DSpark drafter, gated by `--speculative-config '{"method":"dspark","enable_adaptive_verification":true,...}'`) runs a small **confidence head** once per drafted block to decide how many tokens to submit to the verifier:

```
p_accept = sigmoid( ( [ hidden_state ; markov_embed ] @ W ) / temperature )
   hidden_state     (n, H)        bf16
   markov_embed     (n, r)        bf16
   W                (H + r, 1)    fp32   # ReplicatedLinear(params_dtype=fp32)
   p_accept         (n,)          fp32
```

Per draft step, this is **four CUDA launches** — `torch.cat`, `.float()` cast, cuBLAS GEMV, `.sigmoid()` — plus one `(n, H + r)` fp32 temporary that bypasses CUDA-graph memory reuse on the decode fast path. The GEMV itself is tiny (`H + r ≈ 7 200`); on an RTX 5090 the four launches cost ~117 µs of CPU-side scheduling and ~14–45 MB of activation traffic per call, for a useful answer that's about 2 µs long.

DeepInfer — DeepSeek's own inference engine — ships an equivalent fused kernel in its open-source DSpark drafter. The kernel is 60 lines of TileLang ([`dflash.py:12-72`](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/model_executor/layers/tilelang_ops/cuda/dflash.py#L12-L72)) wired into their `AcceptRatePredictor` ([`heads.py:37`](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/model_executor/models/v4_modules/heads.py#L37)), and uses PDL (`T.pdl_sync()`) to overlap with the preceding GEMV. The same file contains another small `dflash_input_store_tl` fusion, which suggests DeepInfer's motivation is systematically flattening small ops on the DSpark path — confidence-head fusion is one piece of a larger pattern, and the open-source repo does not quote a per-kernel TPOT delta. They cast the confidence weight to bf16 for tensor-core FMA. vLLM keeps the same weight in FP32 (`params_dtype=torch.float32` in `qwen3_dspark.py:124-131`), so a drop-in port would silently change which draft tokens get accepted.

This RFC proposes **porting the DeepInfer fusion to vLLM while preserving FP32 weight semantics**. We also expect this kernel to be the first of several small DSpark fusion ports (e.g. `dflash_input_store_tl`, `dspark_draft_embed_store_tl`) so the mechanism-level benefit compounds.

## Numbers

Measured on **two GPUs**, one card each (no TP, no DP):

- RTX 5090, SM120 (Blackwell), 32 GB, CUDA 13.0, driver 575 — dev pod.
- NVIDIA H200, SM90, 143 GB HBM3e, CUDA 13.1, driver 590.44.01 — single-card.

vLLM 0.32.0, PyTorch 2.13.0+cu130, TileLang 0.1.12. Target / drafter for the E2E / A/B runs: `Qwen/Qwen3-4B-FP8` + `deepseek-ai/dspark_qwen3_4b_block7` (~10 GB total HBM).

### Dispatch gate (when does the fused path actually run)

The kernel is **only** dispatched when **all** of the following hold. Otherwise the call site returns `None` and falls back to the existing PyTorch path (no behavioral change).

| Condition | Required value | Why it matters |
|---|---|---|
| Platform | NVIDIA Hopper (SM90) or later, including consumer Blackwell (SM120) | TileLang's PDL (programmatic dependent launch) is SM90+. |
| `hidden.dtype` | `torch.bfloat16`, CUDA tensor | DSpark contract; the kernel assumes bf16 inputs. |
| `markov.dtype` | `torch.bfloat16`, CUDA tensor | Same. |
| `weight.dtype` | `torch.float32`, CUDA tensor | vLLM keeps fp32 here for determinism — this is the deliberate divergence from DeepInfer's bf16 variant. |
| `(n_embed, markov_rank)` shape | `(7168, 32)` only (DeepSeek-V4-Flash) | Only this shape shows end-to-end benefit on datacenter GPUs in our measurements. Smaller DSpark variants (e.g. Qwen3-4B-DSpark at H=2560, r=256) see parity on consumer GPUs and a regression on H200. |
| `hidden.stride(-1)` | `1` (last-dim contiguous) | Kernel assumes row-major, last-dim unit stride. |
| `markov.stride(-1)` | `1` when `r > 0` | Same. |
| Batch size `n` | `32 ≤ n ≤ 2048` | See "Batch gate rationale" below. |
| `markov_embed.shape[-1]` | `≥ r` (rank parameter) | Compile-time kernel template expects this. |

The dispatch conditions live in `vllm/model_executor/kernels/dspark/__init__.py:43-83` and are checked at every call. When any one of them fails, the wrapper returns `None` and the caller's PyTorch fallback runs — that fallback is already correct and tested.

### Batch + shape gate rationale

The gate has two pieces: a **V4-Flash-only shape floor** and a **batch size window**.

**Shape floor.** Only `(n_embed = 7168, markov_rank = 32)` is admitted to the fused path. This is the DeepSeek-V4-Flash DSpark production shape — the configuration DeepInfer designed and validated the fusion for on datacenter GPUs. Smaller DSpark variants currently in-tree (e.g. Qwen3-4B-DSpark at H=2560, r=256):

- See **parity** fused vs PyTorch on consumer (RTX 5090 / SM120) at every batch we tested (sequential: 5.01 s vs 5.02 s; batched at B ∈ {32, 128, 256}: ratios 0.97×–0.99× — see "Batch sweep" below).
- See a **~42–58 % wall-clock regression** on H200 SM90 in the sequential setting (see "Systematic wall-clock puzzle" below), driven by ~93 µs per-call TileLang dispatch overhead on Hopper.
- Contribute ≤ 0.1 % of decode kernel time even when fused, so the kernel is structurally too small to recover its dispatch overhead at these shapes.

For those variants the right thing is the existing PyTorch fallback (which is free under `FULL_AND_PIECEWISE` cudagraph capture), not a fused custom op. Rather than ask reviewers to audit a kernel they'll never exercise, we hard-limit the dispatch to the V4-Flash shape and revisit when / if smaller variants become production-relevant.

**Batch floor and ceiling.** `n < 32` is declined because the per-call TileLang dispatch overhead (~93 µs on Hopper; less on Blackwell) dominates the kernel's savings at tiny batch. `n > 2048` is declined as a sanity bound; the benchmark sweep covers up to `n = 8192` and the kernel is correct across the entire range, but matching realistic DSpark block-size × concurrency stays well below 1024.

### Batch sweep evidence on RTX 5090

Sequential `llm.generate()` per-prompt on the 4B drafter previously showed parity fused vs baseline (5.01 s vs 5.02 s). To test whether **larger batches** break the tie (since fused kernel savings should grow with `n` while TileLang Python dispatch overhead is fixed), we ran an end-to-end sweep against `Qwen/Qwen3-4B-FP8` + `deepseek-ai/dspark_qwen3_4b_block7` with `num_speculative_tokens=7`, greedy sampling, on one RTX 5090:

| Concurrent requests B | fused (s) | baseline (s) | fused / baseline | per-req fused (ms) | per-req baseline (ms) |
|---:|---:|---:|---:|---:|---:|
| 32  | 0.414 | 0.422 | **0.98×** | 12.9 | 13.2 |
| 128 | 0.817 | 0.839 | **0.97×** |  6.4 |  6.6 |
| 256 | 1.445 | 1.467 | **0.99×** |  5.6 |  5.7 |

(The B=8 row is excluded as a warmup artifact — fused runs first and pays JIT + first-replay costs that baseline then misses. B=32/128/256 are steady-state.)

Interpretation: at every production-realistic batch the two paths are within noise on the 4B shape. Combined with the H200 regression at the same shape and the observation above that the kernel contributes ≤ 0.1 % of decode time here, the fused path **cannot pay for itself** at the 4B shape on current hardware. That is the empirical basis for the shape floor.

### Micro-benchmark, vs `torch.compile` baseline

Per-implementation latency, `n × H=7168, r=32` (dominant DSpark decode shape), 200 iters each. Reproduce: `python benchmarks/kernels/dspark/bench_confidence.py` on the PR branch. The fused dispatch gate applies only up to `n = 2048`; numbers beyond are kernel-capability visibility.

| GPU | Shapes | Median latency speedup | Min / max | Production shape band (n ≤ 2048) | Median err_ratio vs `compiled` |
|---|---:|---:|---:|---:|---:|
| RTX 5090 (SM120) | 36 | **1.92×** | 0.72× / 3.56× | 1.72× – 2.77× | **0.610** |
| NVIDIA H200 (SM90) | 20 | **1.90×** | 0.39× / 5.15× | 0.39× – 2.97× | **0.695** |

H200's wider range: small-shape launch overhead is more costly on Hopper; above `n=128` H200 pulls ahead of 5090, reaching 5.15× at `n=8192, H=7168, r=32` where HBM3e bandwidth favors the fused kernel.

### What changes per decode step

| Quantity | main (PyTorch) | fused (this PR) | Delta |
|---|---:|---:|---:|
| CUDA launches along the path | 4 | 1 | **−3** |
| CUDA-graph nodes along the path | 4 | 1 | **−3** |
| fp32 temporary per call | 14 – 45 MB (n ≤ 2048) | **0 B** | 100 % |

### Engine-level dispatch smoke (`--load-format dummy`)

**Takeaway: the kernel dispatches into the real engine path, launches exactly once per drafted step, is captured inside CUDA graphs on both GPUs, and contributes well under 0.1 % of total kernel time.**

Real `vllm.LLM(...)` runs against target `Qwen/Qwen3-4B-FP8` + draft `deepseek-ai/dspark_qwen3_4b_block7`, adaptive verification enabled, on both GPUs. Traced with vLLM's worker-side profiler (`llm.start_profile()`/`stop_profile()`; see [docs](https://docs.vllm.ai/en/latest/contributing/profiling.html)):

| Metric | RTX 5090 (SM120) | NVIDIA H200 (SM90) |
|---|---:|---:|
| `confidence_head_fused_tilelang_kernel` launches in a 64-token decode | **64** | **64** |
| Launches with CUDA graph id set | **64 / 64** | **64 / 64** |
| Median per-call kernel time | 1.70 µs | 1.79 µs |

### Production-scale TPOT

Production DSpark shapes (DeepSeek-V4.1-Flash ≈ 300 GB packed; V4-Pro ≈ 880 GB) require multi-GPU H200/H20 per-replica, so they're not covered here. DeepInfer does not publish a per-kernel TPOT delta either. If multi-H200 capacity becomes available we will land TPOT numbers as a follow-up comment.

### Proposed Change.

Port the DeepInfer fusion pattern into vLLM, with the FP32-weight delta and standard vLLM wrapping contracts.

**Code** (in [PR #62840](https://github.com/vllm-project/vllm/pull/62840)):

- New TileLang kernel in `vllm/model_executor/kernels/dspark/tilelang_kernels.py` — one launch, fp32 accumulator, in-kernel sigmoid. 113 lines.
- Wrap in `VllmJitKernel` (`vllm/model_executor/kernels/dspark/tilelang.py`) mirroring `kernels/mhc/` — precompiles at engine JIT warmup so shape-specialized builds are ready before first request.
- Register as `torch.ops.vllm.dspark_confidence_tilelang` via `direct_register_custom_op` so CUDA-graph capture sees one opaque node.
- Call-site dispatch in two `compute_confidence()` methods: `vllm/model_executor/models/qwen3_dspark.py` and `vllm/models/deepseek_v4/nvidia/dspark.py`. Caller falls through to the existing PyTorch path on any gate condition failure — no user-visible behavior change.
- **Fallback observability**: the dispatch wrapper logs a one-line `logger.debug` per unique decline reason on first occurrence; disabled by default. A metric counter is not added in this PR to keep scope aligned with existing kernel integrations.

**Behavioral consistency check (real DSpark checkpoint, fused on vs off)**

The kernel is not bitwise-identical to the PyTorch path — fused uses an fp32 accumulator + in-kernel sigmoid while the fallback goes through bf16 intermediates. So we checked what matters for behavior: **does flipping the kernel on change which draft tokens are accepted, and does that change the generated text?**

Setup: real `Qwen/Qwen3-4B-FP8` target + real `deepseek-ai/dspark_qwen3_4b_block7` drafter, `enable_adaptive_verification=True`, greedy sampling (temperature=0, seed=42), `max_tokens=64`. 30 diverse prompts (reasoning / code / writing / math / knowledge), repeated on both GPUs (SM120 and SM90).

| GPU | Branch | Wall-clock (30 prompts × 64 tok) | Identical outputs to fallback? |
|---|---|---:|---:|
| RTX 5090 (SM120) | fused | 5.01 s | — |
| RTX 5090 (SM120) | baseline | 5.02 s | — |
| NVIDIA H200 (SM90) | fused | 4.55 s | — |
| NVIDIA H200 (SM90) | baseline | 3.20 s | — |
| — | **divergent prompts** | — | **0 / 30 on both GPUs** |

All 30 prompts' output text **and** output-token counts are **bitwise identical** between fused and baseline on both GPUs. Per-call fused kernel time is ~1.7 µs (5090) / 1.79 µs (H200) — the kernel itself is ~µs-and-change per decode step.

**Systematic wall-clock puzzle on H200** (flagged for review / future repro): 30 sequential single-prompt `llm.generate()` calls, each 64 tokens, measured twice on the H200:

| Branch | Run 1 | Run 2 | Mean |
|---|---:|---:|---:|
| fused | 4.55 s | 5.35 s | **4.95 s** |
| baseline | 3.20 s | 3.38 s | **3.29 s** |

Fused is consistently ~50 % slower on H200 in this shape. On RTX 5090 the same script/branch policy yields fused 5.01 s vs baseline 5.02 s (within noise). Causes we've ruled out:
- The kernel itself: ~0.1 ms per prompt of 64 confidence-head launches.
- cuLaunchKernel count: identical (1024 in both branches per trace — PyTorch fallback is also captured into the same CUDA graph).

Possible cause, not verified: per-call TileLang custom-op dispatch overhead is higher on Hopper than Blackwell (different CUDA driver / cudaGraph launch path). **Consequence of the new gate**: this regression is no longer reachable — the H200-4B shape is now rejected by the dispatcher (`(2560, 256) != (7168, 32)`) and falls back to PyTorch. The regression could in principle still bite at the V4-Flash shape if H200 dispatch overhead is worse than we think, but at that shape the kernel's savings scale with `n` and the production batch floor of 32 gives headroom. We have not yet isolated whether Hopper-specific dispatch cost at the V4-Flash shape + batch >= 32 stays within budget; landing a multi-H200 TPOT reproduction remains a follow-up.

## Risks

- **Behavioral consistency at the accept gate** (fp32 accumulator + in-kernel sigmoid vs bf16 intermediates). Addressed by the real-checkpoint experiment above: 0/30 divergent on both SM120 and SM90.
- **TileLang coverage.** v0.1.12 emits `T.exp` via libdevice; some shapes produce ptxas warnings on older drivers. Mitigation: the PyTorch fallback stays in-tree.
- **Small-batch slow case — now gated out.** At `n = 1` the fused kernel is 0.72× cuBLAS (launch-bound); the new gate declines dispatch at `n < 32` so this regime is unreachable in production. H200 sequential-mode regression is also no longer reachable on the 4B shape because that shape is rejected by the shape floor (see "Batch + shape gate rationale").

## Open question for reviewers

**Is 30-prompt greedy behavioral identity enough to gate the numerics risk?** We have: (a) 29-shape synthetic tolerance tests, (b) 36-shape (5090) + 20-shape (H200) sweeps vs `torch.compile`, (c) 30 real-checkpoint greedy prompts producing identical strings on two GPU architectures. Happy to land the script that produced the 30/30 result in-tree (under `tests/` or `benchmarks/`).

### Benefits

1. **−3 CUDA-graph nodes per decode step.** Faster capture and replay; matters more as DSpark `block_size` and `num_speculative_tokens` scale.
2. **Zero fp32 activation memory traffic on the decode path.** Removes the per-step temporary that CUDA-graph memory must recycle.
3. **Matches numerics DeepSeek vetted in production.** Same fused math, same `AcceptRatePredictor` shape contract — not a guess.
