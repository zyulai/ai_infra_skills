# RFC: Layerwise KV Pooling and P/D Disaggregation for High-Hit-Rate Agent Workloads

## Summary

This RFC proposes a coordinated layerwise design for KV-cache pooling and Prefill/Decode (P/D) disaggregation in Agent workloads with KV-cache hit rates above 90%. Pool reuse, P/D handoff, consumption acknowledgement, and block reclamation must follow matching layerwise lifecycle boundaries. This allows KV blocks to be reclaimed layer by layer while loading a later KV group is overlapped with computation on the current group.

The core design is to reuse grouped KV blocks within a layerwise lifecycle and pipeline cache loading with model computation, with the goal of hiding as much loading time as possible. Supporting work includes reducing per-layer preparation overhead, avoiding redundant lookups, and addressing resource contention between H2D copies and AlltoAllV.

## Motivation

In a test with 140K input tokens and a 95% cache hit rate, performance with 24 concurrent requests was reported to be about 50% worse than with a single request in token throughput. The result nevertheless indicates that cache hits do not automatically translate into better performance at higher concurrency.

There are two related goals:

1. **Improve HBM utilization.** If cached blocks remain logically held after they are no longer needed, they cannot be reused for new requests, reducing effective concurrency.
2. **Hide cache-loading latency.** Pool loading should overlap with model computation. Any uncovered loading time remains on the critical path and can reduce throughput or increase latency.

At high hit rates, Prefill is primarily constrained by HBM capacity: the more KV cache that remains resident, the fewer requests can run concurrently, making it harder to keep compute resources busy. Layerwise pooling can reclaim KV blocks as soon as their consumption at a layer is complete, reducing per-request HBM usage and increasing the number of runnable requests.

Asynchronous scheduling can make block retention worse in non-layerwise execution. Because resources cannot be returned at each layer boundary, more blocks may remain held by requests while asynchronous loads and request execution progress. This reduces reusable HBM and limits concurrency. To realize layerwise reclamation, P/D handoff, consumption acknowledgement, and pool reclamation must use matching layerwise boundaries. Changing only pooling or only P/D disaggregation to layerwise is insufficient: without matching handoff granularity, Decode cannot confirm that a layer has finished consuming its data and release the corresponding block. **This RFC therefore proposes layerwise KV pooling and layerwise P/D disaggregation as a coordinated design, with later-group loading pipelined against current-group computation.**

## Goals and Non-Goals

### Goals

- Improve effective HBM utilization and runnable-request capacity in high-hit-rate, long-context workloads.
- Define matching layerwise data handoff, consumption acknowledgement, and block-reclamation lifecycles for pooling and P/D disaggregation.
- Reduce exposed KV-loading time through grouped block reuse and loading-computation overlap.
- Evaluate the end-to-end effects of hit rate, concurrency, and the coordinated layerwise design with reproducible metrics.

### Non-Goals

- Change the KV-cache content format or model-computation semantics. The proposal does define lifecycle agreements needed for layerwise handoff, consumption acknowledgement, and block reclamation.
- Treat performance results from one workload as guarantees for all models or hardware.

## Problem Analysis

The current issues span two related areas: **the pooled-block lifecycle** and **the layerwise P/D data path**. The available analysis identifies the following problems:

1. Non-layerwise asynchronous scheduling can delay block reclamation, leaving more blocks held by requests and preventing timely HBM reuse.
2. Although layerwise execution provides the basis for per-layer processing, grouped KV reuse and HBM-block reclamation are still insufficient or delayed.
3. CPU-side preparation and redundant lookups add overhead to the per-layer path.
4. H2D operations may contend with AlltoAllV and reduce communication performance.

#### Layerwise Pooling Module 

- Organizes and manages grouped KV blocks at layerwise granularity.
- Returns a group to the pool after consumption completes and makes its blocks available for subsequent groups.
- Tracks group availability and lifecycle so a block is not reused while a transfer or computation still depends on it.
- **To be specified:** group granularity, pool metadata, allocation and reclamation interfaces, concurrent access, and state synchronization.

#### Layerwise P/D Disaggregation Module  https://github.com/vllm-project/vllm/pull/62504

- Coordinates the provision of KV groups by Prefill and their receipt and consumption by Decode at layerwise granularity.
- Provides per-layer readiness and consumption-completion boundaries so the pooling module can safely reclaim the corresponding blocks.
- Supports pipelined loading of later groups alongside computation on the current group, including waiting or backpressure when data is not ready.
- **To be specified:** P/D handoff interface, ready/consumed signals, data-ownership boundaries, cancellation and error handling, and cross-process synchronization.

#### Module Interaction

1. The P/D module requests or receives a KV group and advances the corresponding layer computation when the data is ready.
2. After Decode finishes consuming the group, the P/D module notifies the pooling module that the group has reached its reclamation boundary.
3. The pooling module reclaims and reuses the blocks. The P/D module can then continue with subsequent groups, forming a loading-computation pipeline.

These steps describe the logical architecture and do not prescribe a specific transport backend, API, or synchronization primitive. Those details can be added during interface design.

### Design Principles

1. **Use a consistent layerwise granularity.** The pooling unit, P/D transfer unit, consumption acknowledgement, and reclamation unit must align.
2. **Define block ownership and lifecycle.** Specify when Prefill publishes a layer's KV, when Decode receives it, when consumption completes, and when the underlying block may be reused.
3. **Reuse grouped KV blocks.** Manage KV in groups suited to transfer, computation, and reclamation. Return consumed blocks promptly for reuse by later groups. The group size should balance management overhead, transfer efficiency, and reclamation opportunities.
4. **Pipeline loading and computation.** Prepare or load a later group while the current group is being computed. Use explicit ready/consumed dependencies to control visibility and reuse, keeping loading waits off the critical path where possible.
5. **Optimize for end-to-end results.** Group reuse, layerwise handoff, and synchronization can add scheduling or control overhead. Evaluate these costs together with HBM savings, loading coverage, and concurrency.

### Optimization Areas

1. **Grouped block reuse and timely reclamation:** Divide KV cache into independently managed groups. Reclaim a group's blocks after consumption and reuse them for later groups, lowering per-request HBM usage and increasing concurrency.
2. **Loading-computation overlap:** Pipeline prefetch/loading of KV groups with computation on the current group. When loading is not hidden, identify whether the cause is transfer bandwidth, CPU preparation, scheduling gaps, or resource contention.
3. **Reduce per-layer preparation time:** Find serial work and repeated operations in the layerwise preparation path and shorten CPU-side critical-path time.
4. **Avoid redundant lookups:** Reduce repeated cache-key lookups and overlap necessary lookup work with other stages where possible.
5. **Address H2D and AlltoAllV interference:** Measure contention and adjust execution timing or concurrency so H2D loading does not unnecessarily delay AlltoAllV.

## Reported Results

For Agent workloads with cache hit rates above 90%, the final layerwise coordinated design was reported to outperform the non-layerwise design:

| Metric | Workload and baseline | Reported improvement |
|---|---|---:|
| TTFT | Agent, >90% hit rate; layerwise coordinated design vs. non-layerwise | About 40% better |
| Aggregate throughput | Agent, >90% hit rate; layerwise coordinated design vs. non-layerwise | About 20% higher |

Earlier material also reported about a 3% performance regression for a layerwise workload at a 95% hit rate, with some optimizations not yet integrated. This is an intermediate result from a different stage; its metric and baseline were not specified, so it should not be compared directly with the final results above. Reproducing the reported gains requires the model, hardware, hit-rate definition, request set, concurrency, measurement methodology, and run count.

## Evaluation Plan

Compare the coordinated design with the baseline using the same model, hardware, input lengths, and request-arrival pattern. Cover:

- **Hit rates:** include low-hit, 90%, and 95% operating points.
- **Concurrency:** single-request and 24-request cases, plus intermediate levels to identify saturation.
- **Input length:** include the 140K-token case and record the actual token-length distribution.
- **Metrics:** throughput, request-latency percentiles, TTFT, TPOT, peak and average HBM usage, runnable-request count, KV-loading time, the fraction of loading covered by computation, and pipeline gaps between groups.
- **Resource contention:** record H2D and AlltoAllV timings and distinguish CPU preparation, P/D handoff, device copies, and model computation.
- **Ablations:** compare no layerwise pooling, pooling only, layerwise P/D handoff only, the coordinated design, and per-layer preparation optimizations to isolate each contribution.

Record software versions, model, hardware, parallel configuration, cache capacity, request set, warmup, run count, and metric definitions for each experiment.

## Risks and Trade-Offs

- Synchronous reclamation can improve HBM reuse, but reclamation must wait until device-side asynchronous users have completed.
- Grouped reuse can reduce cache capacity requirements, but may add management complexity and data movement; measure the end-to-end effect.
- H2D/AlltoAllV scheduling may depend on hardware and communication topology and should be validated across target configurations.

## Open Questions

1. In the 140K-token, 95%-hit, 24-request result, does the reported ~50% performance drop refer to throughput or latency? How is the single-request baseline defined?
2. Does “about 40% TTFT improvement” mean TTFT latency is reduced by 40%?
3. What is the P/D handoff unit (a layer, layer group, or another unit), and where are the ready/consumed signals and block-ownership transition points?
4. After Decode consumes a layer, which resource is reclaimed: the local HBM block, a shared pooled resource, or both? Which asynchronous operations must complete first?
5. How should KV groups be formed (by layer, layer group, token/block count, or transfer batch), and what prefetch/buffering policy should be used?
6. Which profiler evidence shows H2D-induced AlltoAllV degradation, and which hardware configurations are in scope?
7. What metric, baseline, and set of changes correspond to the earlier ~3% regression result?
