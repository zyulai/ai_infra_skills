## 正文(PRD / 提案全文)

### Motivation.

We have seen asks from multiple groups to offer a token-in / token-out API for vLLM, including:
- disaggregated tokenization/MM input processing use cases (e.g. llm-d, Dynamo, etc)
- custom frontends around vLLM (for users doing custom tool calling, MM input processing)
- RL use cases



### Proposed Change.

#### Existing MM Refactor Effort

There is an existing effort in vLLM to refactor MM input processing (#22880 by @WoosukKwon and @ywang96) to convert the `Processor` class to a `Renderer` class which :
- Has much less layers of abstraction
- Does not necessarily need to use the HF Processor class (allow custom implementation for model providers)
- Sits outside the AsyncLLM (at the API server level)

Goal is to introduce a new class called a “Renderer”, which:
- Converts OpenAI Spec → Tokens, MM Features, etc
- Sits “Outside” the AsyncLLM (so moved to the API Server level)
- AsyncLLM becomes tokens in >> tokens out

#### Enabling Token-In | Token-Out API Server

As the AsyncLLM interface becomes token-in/tokens-out, we can wrap this in an API. Create a clear class, document, make it an external API
- Note: `GenerateRequest` roughly maps to `EngineCoreRequest`
- Note: `GenerateResponse` roughly maps to `EngineCoreOutput`
- `/generate` that maps to the new `AsyncLLM.generate()`, which is now tokens-in/tokens-out after the update for the Renderer
- We can make `Detokenization` step optional in the `AsyncLLM` (note: this 

```python
class GenerateRequest:
    request_id: str
    token_ids: list[int]
    features: union[list[torch.tensor], dict[str,torch.tensor]]
    placeholder_range: list[tuple[int,int]
    mm_identifier: list[string] # i.e. hashes
    sampling_params: SamplingParams
    kv_transfer_params: Optional[dict[Any,Any]]

class GenerateResponse:
    request_id: str
    token_ids: list[int] # raw tokens
    logprobs
    prompt_logprobs
    finish_reason
    stop_reason
    kv_transfer_params: Optional[dict[Any,Any]]

class GenerateResponseStreaming:
    request_id: str
    token_ids: list[int] # raw tokens
    logprobs
    prompt_logprobs
    finish_reason
    stop_reason

# microservice for tokens in / tokens out
vllm serve-tokens $MODEL

/generate
    input: GenerateRequest
    output: GenerateResponse

/generate_streaming
    input: GenerateRequest
    output: GenerateResponseStreaming
```

#### Disaggregated Tokenization

With a tokens-in / tokens-out API, we can build a disaggregated tokenization architecture for large scale serving

```bash
# microservice for renderer
vllm renderer $MODEL

/v1/chat/completions/render
    input: ChatCompletionRequest
    output: GenerateRequest

/v1/completions/render

# microservice for coordinator
vllm coordinate $MODEL

/v1/chat/completions/coordinate
    # send to vLLM, GenerateResponse -> ChatCompletionResponse
    # detokenization, tools, etc
    input: GenerateRequest
    output: ChatCompletionResponse

/v1/completions/coordinate
```
