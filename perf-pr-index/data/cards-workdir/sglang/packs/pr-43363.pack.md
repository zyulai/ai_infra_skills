## Summary

**TL;DR: This PR enables sglang's startup autotune to tune FlashInfer's CUTLASS MoE kernel for prefill sizes too, not only for decode sizes.** sglang already autotunes this kernel (`cutlass_fused_moe`, FlashInfer's MoE kernel, not its attention backend) at startup, but each call tells FlashInfer to tune only up to its own token count. The startup run is one decode-sized batch, so only decode sizes get a tuned kernel configuration (tactic), and prefill chunks above that size run FlashInfer's untuned fallback tactic (its default kernel configuration). This PR gives FlashInfer one tuning range per server instead: the largest prefill batch the MoE layer sees (chunk size × attention data-parallel size, capped at 8192, FlashInfer's own default range for this call), so the same startup autotune also covers prefill. No new flag, kernel or extra pass. It applies on every GPU this kernel runs on (SM90, SM100, SM110, SM120), where it is the default MoE kernel of DeepSeek-V4.1/V4, Ling-3.0, Nemotron-H, gpt-oss and ModelOpt NVFP4 MoE models (which GPU for which model: Design notes), and to any other MoE model that runs on it. Other MoE kernels and the decode servers of prefill-decode (PD) disaggregation are unchanged. Measured on H200 (SM90).

- **Performance** (H200): faster prefill on all seven MoE models measured (DeepSeek-V4.1-Flash, Nemotron-3.5, Ling-3.0, gpt-oss-20b, GLM-5.3-Flash, MiniMax-M3, Gemma-4): TTFT (time to first token) for 8k-token prompts **30.3–57.8% lower** (DeepSeek-V4.1-Flash: 573.9 → 400.0 ms, **30.3%**), for 32k-token prompts **23.0–52.8% lower**, prefill throughput **43.4–143.4% higher**; decode ITL (inter-token latency) unchanged on the three models measured for it. It complements open PR #42736 (an extra startup tuning pass): with both, 8k-token TTFT on DeepSeek-V4.1-Flash is **24.7% lower** than with #42736 alone.
- **Accuracy:** unchanged by design (only the tile configuration, or tactic, of the same GEMM changes); GSM8K on all seven models and the DeepSeek-V4-Flash CI GSM8K test stays within the 95% noise range (−0.83 to +0.15 points on the seven models).
- **Cost:** a longer startup autotune when no saved results exist: 41–42 → 176–177 s on DeepSeek-V4.1-Flash 8×H200 (server ready 153–154 → 288–289 s), 116 → 604 s on Ling-3.0-flash, and 4–26 s more on the other five models. Saved results are reused on one GPU, but multi-GPU servers currently re-tune at every start; `--disable-flashinfer-autotune` turns the startup autotune off. Each GPU has 0.4–1.2 GiB (0.3–0.9% of an H200) less free memory while the server runs, mostly the buffer FlashInfer keeps for timing tactics at startup, now sized for the prefill chunk instead of the decode batch; the KV cache size is unchanged. PD decode servers pay nothing.

## Motivation

sglang runs FlashInfer's autotune at startup (#12306, on by default since #14357). For `cutlass_fused_moe`, FlashInfer keeps one tactic per token-count bucket (powers of two up to 256, then larger steps up to 8192: 21 buckets) and tunes every bucket up to the caller's `tune_max_num_tokens`; the same value also decides which bucket a call uses. Both sglang call sites (the `flashinfer_cutlass` runner, used for BF16, FP8 and NVFP4 experts, and the CUTLASS path of `flashinfer_mxfp4`, used for MXFP4 experts) pass `next_power_of_2(x.shape[0])`, which dates from #7327, before the startup autotune existed. This has two effects:

1. **Prefill runs an untuned tactic.** The startup batch is decode-sized, one token per request up to the request limit (256 tokens on DeepSeek-V4.1-Flash, 138 on Nemotron-3.5-Lightning, 4096 on gpt-oss-20b), so nothing above that size is tuned: an 8k-token chunk maps to bucket 8192 and gets FlashInfer's fallback tactic. The server log shows nothing, because sglang sets FlashInfer's logger to ERROR.
2. **The tactic depends on earlier requests.** Every `cutlass_fused_moe` call that runs Python code (the startup autotune, CUDA graph capture, and every serving forward that is not a CUDA graph replay) first calls `MoERunner.refine_tuning_config(tune_max_num_tokens)`. That method is wrapped in `functools.lru_cache` and rebuilds FlashInfer's class-wide bucket list only the first time it sees a value, so a call with a value seen before keeps the list built for the latest new value. On DeepSeek-V4.1-Flash with `--cuda-graph-max-bs-decode 64`, the first decode batch of 65–128 requests while serving runs without a CUDA graph and rebuilds the list for 128 tokens (a short prompt of a new size likewise rebuilds it, for its own size); later prefill chunks of an already-seen size, such as every 8k-token chunk after the first, then run the 128-token bucket's tactic, because a list built for 128 tokens ends at bucket 128 and every larger call falls into that last bucket.

flashinfer-ai/flashinfer#5625 was filed by an sglang user who hit both effects serving DeepSeek-V4-Flash on 4×H100 with `flashinfer_mxfp4`. One value for the whole server, computed from its configuration and used by every call, as large as the largest prefill batch (up to 8192 tokens), removes both.

## Modifications

- **`python/sglang/srt/layers/moe/moe_runner/flashinfer_cutlass.py`** -- the new `_cutlass_moe_tune_max_num_tokens(num_tokens)` gives both `cutlass_fused_moe` calls their `tune_max_num_tokens`: `min(prefill chunk size × attention DP size, 8192)`, with the chunk size (`--chunked-prefill-size`, or `--max-prefill-tokens` when chunked prefill is off) read the way `flashinfer_autotune.py` already does (`max_prefill_buffer_tokens() or get_schedule().max_prefill_tokens`). PD decode servers keep `next_power_of_2(num_tokens)`.
- **`test/registered/unit/layers/moe/test_flashinfer_cutlass_swiglu_params.py`** (CPU suite) -- new `TestCutlassMoeTuneMaxNumTokens`. With the kernel stubbed, it checks at both calls that token counts 1, 257, 777, 2048, 4097, 8192 and 16384 map to a bucket the startup autotune tunes, in five server configurations, and that PD decode servers keep the per-call value. 60 of its 80 sub-cases fail on main.
- **`test/registered/unit/layers/quantization/test_mxfp4_sm{90,120}_cutlass.py`, `test/registered/unit/layers/moe/test_moe_runner_config_placement.py`** -- their fused-MoE calls now run inside `get_context().override_server_args()`, because the helper reads the server configuration.

Design notes:

- Where this kernel is the default MoE path: on SM90 and SM120, DeepSeek-V4.1/V4 and Ling-3.0 (MXFP4 experts, through `flashinfer_mxfp4`) and BF16/FP8 Nemotron-H (`flashinfer_cutlass`); on SM120 also gpt-oss and ModelOpt NVFP4 MoE models, the latter on SM110 too since #41765. On SM100 no model uses it by default (`flashinfer_mxfp4` runs a TRT-LLM kernel there). Any other MoE model reaches it with `--moe-runner-backend flashinfer_cutlass` (BF16, ModelOpt FP8/NVFP4) or `flashinfer_mxfp4` (MXFP4).
- DP attention: sglang splits `--chunked-prefill-size` across the DP ranks, and the MoE layer runs on the tokens gathered from all of them, so the largest batch the MoE layer sees is each rank's chunk × the DP size, which is the `--chunked-prefill-size` the user set.
- The 8192 cap is a choice, not a limit on chunk size: it is FlashInfer's own default range for this call, and chunks larger than 8192 tokens still run, using bucket 8192's tactic, which in a one-layer test with DeepSeek-V4.1-Flash's MoE shape is as fast as a tactic tuned for each larger size (One MoE call, under Experimental Results); tuning beyond 8192 would only lengthen startup. Omitting the argument would also give one value, but PD decode servers and servers with smaller chunks would then tune sizes they never use.
- Servers whose startup decode batch is above 8192 tokens (for example attention DP 8 with the default request limit) tune fewer buckets than main and start faster, at no MoE run-time cost: main cannot use those larger buckets at run time either (item 2), and in a one-layer test bucket 8192's tactic is about as fast as each size's own tactic at 12288–32768 tokens (One MoE call, under Experimental Results).
