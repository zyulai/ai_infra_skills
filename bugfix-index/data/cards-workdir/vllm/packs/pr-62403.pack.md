## 正文(PR 描述)

## Purpose

On `ROCM_ATTN`, the QK-norm + RoPE + KV-cache fusion (`fuse_qk_norm_rope_kvcache`) stores V in an interleaved layout, and the layer's attention kernels must read it that way. Two places break that contract, so the fusion produces wrong output on `main`:

1. **Qwen3 models decode garbage** (Qwen3-8B GSM8K 0.87 → 0.005). `QkNormRopeKvCacheFusionPass` calls `set_interleaved_v_cache()` on each eligible layer, but with `layer_name` hoisted (`_USE_LAYERNAME`, torch >= 2.11) one layer's patterns cover the model, so the loop `break`s after the first eligible layer and skips the call for every other one. Those layers keep `_use_interleaved_v_cache=False`: the fused kernel then writes the NHD layout into a cache their kernels read as the paged layout. Prefill looks right because it attends over the fused kernel's `k_out`; every decode step after it reads the cache. The existing fusion tests use a single attention layer, so they never reached the second layer.
2. **With `fuse_rope_kvcache` also on, models without QK-norm get a corrupted V cache** (Llama-3.1-8B GSM8K 0.766 → 0.71). The pass switches layers to the interleaved V cache before any pattern matches. On a layer the QK-norm pattern does not match, the RoPE + KV-cache fusion writes the KV cache instead, through `RocmAttentionImpl.do_rope_and_kv_cache_update`, whose Triton writer (`rocm_aiter_ops.triton_rope_and_cache`) only stores the regular V layout. A per-layer check at pattern registration cannot keep such layers out, because with `layer_name` hoisted one pattern serves every layer and graphs loaded from the compile cache skip the passes.

Fixing the first alone makes the second hit every layer instead of one (Llama-3.1-8B GSM8K 0.012), so both are fixed here, one commit each:

1. `QkNormRopeKvCacheFusionPass` switches every eligible layer and only skips the duplicate pattern registration.
2. `do_rope_and_kv_cache_update` applies RoPE in place (`ops.rotary_embedding`) and takes the unfused `do_kv_cache_update`, which already writes the interleaved layout, on layers that use the interleaved V cache. Layers with the regular V cache keep the fused Triton writer.

Only `ROCM_ATTN` is affected; `fuse_qk_norm_rope_kvcache` is off by default.

## Test Result

**Unit tests:** 1497 and 50 passed (24 skipped). Two new cases fail on `main` and pass here:

- `test_qk_norm_rope_kvcache_fusion_interleaves_every_layer` builds three `ROCM_ATTN` layers and checks that all of them switch.
- `test_rope_kvcache_fusion` gains an `interleaved_v` case that compares the fused and unfused caches of an interleaved-V `ROCM_ATTN` layer; its bf16 variants fail on `main`. (With an fp8 cache and `block_size=16` the two V layouts coincide, so those pass either way.)

**Root cause of the first bug, confirmed at runtime** on Qwen3-0.6B (28 layers): on `main`, `set_interleaved_v_cache()` ran for one layer; that layer's fused writes used `use_shuffle_layout=True` and the other 27 layers' used `False`. The fused writer and the unfused interleaved writer produce byte-identical caches, and the decode and prefill kernels read the interleaved layout correctly, so only the flag was missing.

On the fusion arm `splitting_ops` is limited to the attention ops and the `rotary_embedding` CustomOp is dispatched, which keeps the request from being dropped without turning on Inductor graph partition; the RoPE + KV-cache fusion is also on there but does not match Qwen3.
