## 正文(PRD / 提案全文)

## Motivation

A draft model's acceptance rate is **workload-dependent**: a drafter trained/aligned on one distribution accepts well on some requests and poorly on others. When a single deployment serves mixed workloads, some requests get little or negative benefit from speculation.

Speculative decoding is also not free under load: verification cost scales with `batch_size × draft_length`, so SD helps at low batch size but can reduce goodput at high batch size — which is exactly why `--speculative-adaptive` exists (it lowers `speculative_num_steps`, down to 0, as batch size grows).

Today SD is **all-or-nothing per server** — fixed at startup via `--speculative-*`. There is no way to say "this particular request should skip speculation," even though operators often do know, by route / task / SLO, which requests will not benefit. SGLang already surfaces per-request speculation stats in `meta_info` (e.g. `spec_verify_ct`, `spec_accept_rate`, `spec_accept_length`), so operators can *measure* per-request acceptance — but there is no knob to *act* on it per request.

This proposal is the operator-declared complement to the accept-length-driven per-request/mixed-workload policy direction on the Adaptive Speculative Decoding roadmap (#23705): the roadmap's switch policies *infer* when speculation is worth it from runtime signals; this flag lets the client *declare* it when the operator already knows. The demand has also recurred elsewhere: vLLM was asked for runtime API control over SD (#7569) and per-sequence SD control (#17984), both closed as not-planned, and SGLang's own #9319 (dynamic SD, including disable-under-load) was closed by the stale bot. This RFC scopes the problem down to the smallest concrete piece: a per-request opt-out flag, plus a design discussion on how to enforce it correctly.

## Proposal

Add a boolean sampling parameter, default `False`:

```python
# sampling_params.py::SamplingParams
disable_speculative_decoding: bool = False
```

- Exposed on `CompletionRequest` / `ChatCompletionRequest` and passable via the native `/generate` `sampling_params`.
- Semantics: when `True`, the request's output is produced by the target model alone — output-equivalent to plain decoding, with no draft tokens verified for it.
- No-op when the server has no speculative decoding configured.
- On servers **without** this feature, the OpenAI endpoints ignore the unknown field; the native `/generate` endpoint fails on unknown sampling params (currently an unhandled `TypeError` surfacing as HTTP 500 rather than a clean 400), so `/generate` clients should gate on server version.

```python
client.completions.create(
    model=..., prompt=...,
    extra_body={"disable_speculative_decoding": True},
)
```

The draft PR (#30264) implements the **API plumbing end-to-end** (SamplingParams → OpenAI/`/generate` → msgpack IPC → `Req`), with CPU unit tests and docs. It deliberately does **not** wire worker-side enforcement — enforcement turned out to be the actual design problem, analyzed below. The PR stays in GitHub Draft and is not meant to merge until at least the naming/shape question (open question 1) is settled; the field, docs row, and tests get renamed or reshaped per that outcome.

## Why enforcement is non-trivial (the design question)

My first instinct was: "an all-opted-out batch can just reuse the existing `speculative_num_steps == 0` trivial-verify path in `EAGLEWorkerV2` — zero kernel changes." That is wrong:

The `num_steps == 0` path is only consistent when the **steps-0 runtime state is active**. Adaptive SD reaches it exclusively through the runtime-state swap the `AdaptiveController` drives via the worker's `apply_runtime_state()` (`EAGLEWorkerV2.apply_runtime_state`), which atomically swaps (a) the target CUDA-graph runner (re-captured at `num_tokens_per_bs = 1`), (b) the matching attention backend, and (c) `speculative_num_steps` / `speculative_num_draft_tokens`. Taking the trivial-verify branch while a static `K > 0` state is live breaks the `num_tokens_per_req == draft_token_num` invariant downstream:

- **CUDA-graph path (default)**: `load_batch` computes `raw_num_token = bs × num_draft_tokens` from the static state and copies a `bs`-token input into a `bs × D` buffer slice → shape-mismatch crash.
- **Eager path**: TARGET_VERIFY attention metadata diverges — FA3's `cu_seqlens_q` / `max_seq_len_q` come from the backend's static `num_draft_tokens`, DP-attention batch-size recovery uses the `num_tokens_per_req = K + 1` that `verify()` stamps, while flashinfer's `qo_indptr` follows the input's `draft_token_num = 1` — a miscomputed, mutually inconsistent query layout rather than a clean fallback.

So per-request opt-out **requires a runtime-state switch, not just an input-shape change**. The realistic options:

- **(A) Runtime-state swap for fully-opted-out batches.** Pre-build a steps-0 `SpecRuntimeState` at startup (the worker's `build_adaptive_runtime_state(0, 1)` constructs exactly this) and apply it when every request in the batch has opted out, restoring the previous state after. Batch-granular: mixed batches still speculate for everyone. Two caveats worth stating up front. First, this machinery is currently validated only inside adaptive SD's support matrix — `eagle_topk == 1`, EAGLE/EAGLE3, and none of DP-attention / two-batch-overlap / pdmux (`adaptive_unsupported_reason` in `adaptive_spec_params.py`); notably, the auto-chosen EAGLE config for Llama-family targets uses `topk = 4`, so the most common non-adaptive config sits outside that envelope, and the DP-attention exclusion reason (tier decisions not synchronized across ranks) applies equally to a batch-content-driven swap. (A) would initially gate on the same conditions. Second, pre-building the steps-0 state costs extra CUDA-graph capture time and GPU memory at startup for servers that never use the flag.
- **(B) Homogeneous-batch scheduling.** The scheduler groups opted-out requests into their own non-spec batches, making the per-request guarantee hold under arbitrary mixing. This is the "right" long-term answer but a much larger scheduler change (and interacts with continuous batching: under load, a decode batch contains all running requests, so opt-out traffic rarely forms a pure batch on its own).
- **(C) Scheduler-level treatment as a distinct request class** (e.g. route to a non-spec worker in PD/disagg setups). Out of scope here, noted for completeness.

My inclination: **(A) first**, gated to the same support matrix as adaptive SD, with (B) as the follow-up that makes the flag a hard guarantee. Input from whoever owns the adaptive runtime-state machinery (#23705) would be especially valuable.

## Scope and limitations

- Enforcement (once landed) would initially target the `EAGLEWorkerV2` verify path, i.e. EAGLE / EAGLE3 / NEXTN. STANDALONE and frozen-KV MTP subclass `EAGLEWorkerV2` but do not wire the adaptive runtime-state machinery; NGRAM, DFLASH, and multi-layer EAGLE implement their own worker paths — all of these would silently ignore the flag until given their own hooks.
- Even for an opted-out request, the draft model's **prefill/extend still runs** in designs (A)/(B) to keep draft KV warm — the flag removes draft/verify compute during decode, not the drafter's memory footprint or prefill cost.
- Batch-granular (A) means mixed batches ignore the flag; whether that is surfaced to the client is open question 3.

## Open questions

1. **Naming/shape.** `disable_speculative_decoding: bool` vs. a per-request `speculative_num_steps: Optional[int]` override (generalizes to "use K steps for this request", and maps naturally onto the runtime-state tiers adaptive SD already builds). Preference?
2. **Enforcement.** (A) runtime-state swap now, (B) scheduler grouping later — reasonable sequencing? Or should (B) land first so the semantics are a hard guarantee from day one?
3. **Observability.** Should the response `meta_info` report whether opt-out was actually honored for the request (vs. ignored in a mixed batch), and/or should there be an aggregate counter?
4. **Adaptive interaction.** Should fully-opted-out batches be excluded from the adaptive EMA (their accept-length ~0 would otherwise drag the tier down for other traffic), and does per-request opt-out need any special handling under PD-disaggregation or the overlap scheduler?
