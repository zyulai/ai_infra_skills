## 正文(PRD / 提案全文)

### Motivation.

We propose adding a native, additive **Disaggregated Pull-Based Queue Worker interface** (`vllm.entrypoints.pull_worker.worker`).

This feature enables workers to initiate gRPC streaming connections **outward** to a central queue server, explicitly pulling tasks via credit grants (`TaskGrantRequest`) only when GPU execution slots and KV cache blocks are available. This replaces traditional push-based HTTP proxies that push requests to vLLM workers.

1. **Multi-Hardware / Heterogeneous GPU Support**: Clusters increasingly contain a mix of GPU types with varying VRAM capacities (e.g., 80GB A100s alongside 24GB RTX 4090s) and specific LoRA adapters. Push routers struggle to route large context prompts safely, risking OOMs on smaller GPUs. In a pull-based model, workers naturally filter and pull only tasks that fit their specific hardware capacity and capabilities, seamlessly enabling efficient heterogeneous cluster utilization.
1. **Multi-Zone, Multi-Region and Multi-Cloud Topology Awareness:** In enterprise Kubernetes deployments, worker nodes span availability zones and regions. Traditional push routers lack topology awareness, pushing requests across cloud regions and incurring cross-zone data egress costs and latency spikes. Pull workers can automatically report node topology labels (e.g., `topology.kubernetes.io/zone`) via `WorkerStatus`. The central heuristic router steers tasks to same-zone workers, eliminating cross-zone egress costs and optimizing inter-region routing.
2. **Natural Backpressure (Zero OOMs):** Push routers estimate load via active HTTP connections, often overwhelming worker KV block allocation during bursty traffic and causing OOM crashes. Pull workers grant work strictly when KV cache memory is available.
3. **Zero-Drift Prefix Cache Locality:** Workers report active radix tree block hashes (`active_prefix_hashes`). Central heuristics match system prompt prefixes to warm workers before granting tasks, eliminating prompt prefill overhead.
4. **No Ingress Load Balancer Needed:** Pull workers pull directly from the central queue server, eliminating the need for NGINX/Envoy load balancers in front of GPU worker nodes (Those are still needed in front of the Queue Workers but can also be replaced by the cloud providers or north-south loadbalancers directly).

### Proposed Change.

We propose adding a native, additive Disaggregated Pull-Based Queue Worker interface (`vllm.entrypoints.pull_worker.worker`) and an official example reference implementation (`examples/heuristic_pull_router/`)

This change is purely additive. **It does not modify any core vLLM engine files or existing HTTP push endpoints**, ensuring zero instability for existing push-based deployments.

Extensibility is achieved via a gRPC interface (`queue.proto`). Users can write custom queue implementations in any language simply by implementing the proto interface.

Telemetry is pluggable. Workers report a `WorkerStatus` message split into two categories:

* **Core Metrics:** Essential safety data (e.g., num_running_reqs, free_gpu_kv_blocks).

* **Extended Metrics:** Opt-in data containing custom telemetry. Users can inject custom hardware or software state (e.g., Kubernetes zone labels, active LoRA adapters) into the custom_metrics maps via a custom StatLoggerBase plugin, allowing the central router to execute complex business logic without altering the vLLM core.

#### Code Organization

**Reference:** https://github.com/aojea/vllm/tree/vllm_pull

* `vllm/entrypoints/pull_worker/`: The native pull-worker executable and stat-logger.
* `vllm/entrypoints/pull_worker/proto/`: The queue.proto interface contract.
* `examples/heuristic_pull_router/`: The reference implementation (stateless gRPC server, Redis backend, and pluggable BasePolicy heuristic interface).
* `tests/entrypoints/pull_worker/`: Comprehensive unit and end-to-end integration tests.
