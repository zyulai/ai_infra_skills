## Motivation

When a gfx1250 accelerator is split into two partitions, the partitions share its links to the other accelerators, while the link between the two partitions is a separate one. On an 8-GPU node (bf16, CUDA graph, 256 MB), two TP2 rings across accelerators run at once (GPUs 0/2 and 1/3) take 634-777 us against 448 us alone, while two rings within accelerators (GPUs 0/1 and 2/3) both stay at 319 us.

`ring_simple` (#49955) already keeps each accelerator's partitions next to each other in the ring, but each accelerator still sends 2 * (2m - 1) / 2m of the tensor to the others (m accelerators, 1.75x the tensor at TP8). This PR adds `hier_ring_simple`, which splits every chunk across the two partitions so each accelerator sends 2 * (m - 1) / m (1.5x at TP8), and passes the pair's share over the separate partition-to-partition link inside the same kernel.

## Modifications

- **`hier_ring_simple` kernel** (`csrc/distributed/ring_simple.cuh`): one launch, one channel per CU the device reports. Half h of every chunk runs a ring over partition h of every accelerator, for 2m - 1 steps per loop. At step s the rank, its pair peer and every rank of both rings work on the same chunk index, so each step waits only on earlier steps and on the peer's same step.
  - Three FIFOs per channel, behind 64-bit ready/drained counters like `ring_simple`'s: cross (the ring), pair-in (the input chunk the peer reduces next) and pair-out (each reduced chunk, for the peer's output).
  - During step s, 3 of the block's 8 warps move the peer's pair-in chunk for step s + 1 and its pair-out chunk from step s - 1, while the other 5 run the cross step. Run in sequence by every warp, the pair copies cost TP8 a fifth of its time at 256 MB.
  - 16 packs per thread per source: the reducing steps load three sources, so `ring_simple`'s 32 spill registers.
  - Shares are whole hunks per chunk, as in `ring_simple`.
- **`HierRingPlane`** (FFI object) and **`HierRingSimpleAllReduce`** (`ring_simple_all_reduce.py`): the plan, an uncached symmetric buffer of its own (3 FIFOs x 2 x 512 KB slices per channel) and the all-reduce.
- **Dispatch**: `Heuristic.hier_ring_simple` is tried right after `hier_2shot_push`, and `CustomAllReduceV2` marks the choice with `use_hier` and `use_ring` together. Planning keeps it only for groups made of partition pairs on at least two accelerators. There, 2shot_push keeps only the sizes below it and `ring_simple` none it covers, so the flat ring plane is not allocated. Other groups get the table unchanged.
- **Table**: only the `HIP_FORCE_DEV_KERNARG=1` rows take it so far: TP4 from 8 MB + 16 and TP8 from 16 MB + 16, where it starts to beat 2shot_push. TP2 is one accelerator, and TP16 is not measured.
- **Tests**: hier ring cases in `test_custom_all_reduce.py` (512 KB and 2 KB slices, eager and CUDA graph). The ring tests now build their own plane, so they run whatever the table picks. Capability tests cover the `=1` table rows and planning with and without partition pairs.

+/// steps load three sources, so the flat ring's 32 do not fit in registers:
+/// 16 runs 5-15% faster than 32 or 8 from 64 MB at TP4 and TP8.

+/// Warps of a hier ring block that run the cross step; the rest run the pair
+/// copies of the neighbouring steps at the same time. Run in sequence by every
+/// warp, the pair copies cost TP8 a fifth of its time at 256 MB; 5 of 8 warps
+/// beat 4 and 6 by up to 4% from 64 MB.
+inline constexpr uint32_t kHierCrossWarps = 5;
+static_assert(0 < kHierCrossWarps && kHierCrossWarps < kRingSimpleThreads / device::kWarpThreads);

+/// One hier ring's state on one rank, padded to a cache line. Each counter has
+/// one writer: the cross-ring neighbour named, the pair peer, or this rank.
+struct alignas(128) HierRingSemaphore {
+  uint64_t x_drained;    // cross packets the cross successor drained from this rank
+  uint64_t x_ready;      // cross packets the cross predecessor published here
+  uint64_t in_drained;   // pair-in packets the peer drained from this rank
+  uint64_t in_ready;     // pair-in packets the peer published here
+  uint64_t out_drained;  // pair-out packets the peer drained from this rank
+  uint64_t out_ready;    // pair-out packets the peer published here
+  uint64_t x_packet;     // cross packets this rank's ring has sent (and received); rank-local
+  uint64_t in_packet;    // pair-in packets exchanged with the peer, each way; rank-local
+  uint64_t out_packet;   // pair-out packets exchanged with the peer, each way; rank-local

+  uint8_t* peer;    // the pair peer's rows
+  HierRingSemaphore* credits;
+  HierRingSemaphore* x_prev_credits;
+  HierRingSemaphore* x_next_credits;

+  static constexpr bool kStoreOut = kStoreOut_, kSendX = kSendX_, kSendP = kSendP_;

+/// split every chunk in halves, and half h runs a ring over partition h of
+/// every accelerator, so each accelerator sends 2 * (m - 1) / m of the tensor
+/// to the others (m accelerators) instead of 2 * (2m - 1) / 2m. The pair exchange rides in the same steps: while the
+/// ring reduces, each rank pushes the peer the input chunk the peer reduces next (pair-in FIFO), and every reduced
+/// chunk also goes to the peer (pair-out FIFO). One loop is 2m - 1 steps; at step s the rank, its peer and every rank
+/// of both rings work on the same chunk index, so each step waits only on steps before it and on the peer's same step.
+template <typename T, uint32_t kCrossSize, bool kUsePDL>
+__global__ __launch_bounds__(kRingSimpleThreads, 1) __attribute__((
+    amdgpu_waves_per_eu(1, 2))) void all_reduce_hier_ring_kernel(const __grid_constant__ HierParams params) {

+  static_assert(kCrossSize >= 2, "a hier ring needs at least two accelerators");
+  constexpr uint32_t kVecSize = 16 / (sizeof(T) * 2);
+  constexpr uint32_t kNumCross = 2 * (kCrossSize - 1);  // cross packets per loop
+  constexpr uint32_t kNumSteps = kNumCross + 1;

+  const auto slot_vecs = ws.slot_bytes / 16;
+  const auto fifo_bytes = ws.num_slots * ws.slot_bytes;
+  const auto row = ch * kNumHierFifos * fifo_bytes;

+  // over it in 2 * kCrossSize chunks of at most one slot: chunks [0, m) are

+    };

+          chunk_len(h ^ 1, c),
+          w,
+          count);

+          HierHop<false, true, false, true, false, false>{},

+          slot_of(ws.own, kPairOutFifo, p),
+          nullptr,
+          nullptr,
+          0,
+          chunk_start(h ^ 1, c),
+          chunk_len(h ^ 1, c),
+          w,
+          count);
+    };

+    // peer's pair-out packet from step s - 1, so each step publishes once and
+    // waits only on packets sent a step earlier, or this step by the cross ring.
