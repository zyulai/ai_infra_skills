## 正文(PR 描述)

## Overview

Fixes #48590. On SM90, single-slice `lora_expand` with fp32 inputs (the real `add_lora_linear` path) returns garbage or NaN for rank ≥ 64. This PR forces `num_stages=1` for that path on SM90, which works around triton-lang/triton#9433. It also adds the missing fp32-input regression test. This is an alternative to #48638.

## Claims

- Correct output for fp32-input `lora_expand` on SM90 at every rank and batch size we tested. End to end, Qwen3-8B with an r=64 LoRA goes from 2047/2047 NaN prompt logprobs to 0.
- Expand kernel cost on single-slice layers is at most +8% (`add_inputs=False`) or +21% (`add_inputs=True`) on the worst shape (R=128, T=8192). Multi-slice layers are unchanged. For comparison, #48638 costs +106% on the same shape.
- The workaround is applied after config selection, so it also covers configs from `VLLM_TUNED_CONFIG_FOLDER`.
- New test `test_lora_expand_fp32_inputs` covers the `CAST_TYPE` path, which no existing test exercises.

## Validation

## Details

**Root cause.** The fp32 → bf16 cast in-kernel (`CAST_TYPE`) makes the wgmma read its A operand from registers. With `num_stages=2`, Triton leaves the second wgmma of each iteration in flight across the loop back-edge. ptxas older than 13.3 then reuses that wgmma's A registers for the next iteration's shared-memory loads (triton-lang/triton#9433). Triton 3.5.0–3.8.0 all assemble SM90 kernels with an affected ptxas. To confirm, the unfixed kernel passes the new test when `TRITON_PTXAS_PATH` points at the ptxas 13.3 bundled with triton 3.8.0 (`ptxas-blackwell`).

**Why `num_stages=1`.** With one stage, Triton waits for every wgmma within its own iteration, so no register-A wgmma stays in flight across iterations. That removes the hazard structurally, whatever the tile shape. `block_n=32` (#48638) only hides the hazard because ptxas happens to serialize the wgmmas for that shape. `block_n=64` with the same stages and warps still fails at R=128.

**Scope.** The workaround applies only to CUDA SM90 with `CAST_TYPE`. Other GPUs (including ROCm, where `is_cuda()` is false) and bf16/fp16-input callers are unchanged. It covers all slice counts. The multi-slice default measured correct, but it runs the same pipelined register-A loop, and `num_stages=1` costs nothing there.

**Removal.** This can be dropped once vLLM's Triton assembles SM90 kernels with ptxas ≥ 13.3. Triton main does that via triton-lang/triton#12035, expected in 3.9.0.

**Not covered here.** `fused_moe_lora_op.py` does `tl.dot(a.to(tl.bfloat16), ...)` with `num_stages=3`. For fp16 MoE models, that cast is a real conversion and could hit the same bug. We haven't verified it, so it is left for a follow-up.
