## 正文(PRD / 提案全文)

### Motivation.

The speculative decoding (spec decode) module in vLLM faces significant maintainability and extensibility challenges that hinder both upstream development and hardware plugin integrations.

## Current Problems

#### 1. Inconsistent Proposer Interfaces

Different speculative decoding algorithms implement vastly different interfaces, making it difficult for the model runner to interact with them uniformly:

- **NgramProposer**: `propose(sampled_token_ids, num_tokens_no_spec, token_ids_cpu, slot_mappings=None)`
- **SuffixDecodingProposer**: `propose(input_batch, sampled_token_ids, slot_mappings=None)`
- **MedusaProposer**: `propose(target_hidden_states, sampling_metadata, slot_mappings=None)`
- **EagleProposer**: Inherits from `SpecDecodeBaseProposer`
- **DraftModelProposer**: Similar to EagleProposer but with different initialization

Only Eagle and DraftModel proposers share a common base class (`SpecDecodeBaseProposer`), while others follow completely independent implementations.

#### 2. Model Runner Coupling

The `gpu_model_runner.py` contains extensive `if-else` branching to handle different speculation methods:

```python
if spec_config.method == "ngram":
    draft_token_ids = self.drafter.propose(...)
elif spec_config.method == "suffix":
    draft_token_ids = self.drafter.propose(...)
elif spec_config.method == "medusa":
    # Different logic to compute hidden_states
    draft_token_ids = self.drafter.propose(...)
elif spec_config.use_eagle() or spec_config.uses_draft_model():
    # Completely different code path with multiple sub-branches
    ...
```

This tight coupling means:
- Adding a new algorithm requires modifying the model runner
- Testing individual algorithms in isolation is difficult
- The model runner code becomes increasingly complex with each new method

### Proposed Change.
#### 1. class inheritance
```python
# Base class defines the interface
class BaseProposer(ABC):
    @abstractmethod
    def propose(self, proposer_input: ProposerInput) -> ProposerOutput:
        pass

# Hardware-specific implementations inherit and override
class EagleProposer(BaseProposer):
    """Shared implementation for CUDA/ROCm"""
    pass

class AscendEagleProposer(EagleProposer):
    """Ascend-specific overrides only where needed"""
    
    def prepare_inputs(self, ...):
        # Ascend-specific input preparation
        pass
```
---

#### 2. ProposerInput
```python
# After refactor
proposer_input = self.drafter.prepare_inputs(...)
proposer_output = self.drafter.propose(proposer_input)
```

The standardized `ProposerInput` dataclasses are essential for this decoupling.

---

#### 3. ProposerRegistry

### Module-level mapping

```python
# In vllm/v1/spec_decode/registry.py
PROPOSER_CLASSES: dict[str, type[BaseProposer]] = {
    "ngram": NgramProposer,
    "medusa": MedusaProposer,
    "eagle": EagleProposer,
    # ...
}

def create_proposer(method: str, vllm_config: VllmConfig, device: torch.device):
    if method not in PROPOSER_CLASSES:
        raise ValueError(f"Unknown method: {method}")
    return PROPOSER_CLASSES[method](vllm_config, device)
```

```python
# In gpu_model_runner.py
proposer = create_proposer(spec_config.method, self.vllm_config, self.device)
```

For vllm-ascend to override proposer implementations:

```python
# In vllm/v1/spec_decode/registry.py
def register_proposer(method: str):
    """Decorator to register a proposer class."""
    def decorator(cls: type[BaseProposer]) -> type[BaseProposer]:
        PROPOSER_CLASSES[method] = cls
        return cls
    return decorator
```

```python
# In vllm-ascend/vllm_ascend/spec_decode.py
from vllm.v1.spec_decode.registry import register_proposer
from vllm.v1.spec_decode import EagleProposer

@register_proposer("eagle")  # Overrides vllm's default when vllm-ascend is imported
class AscendEagleProposer(EagleProposer):
    """Ascend-specific EAGLE proposer."""

    def prepare_inputs(self, ...):
        # Ascend-specific implementation
        pass
```
