## 正文(PRD / 提案全文)

### Motivation.

At temperature 0, enabling speculative decoding can change the generated sequence relative to plain decoding. This is already reported for ngram spec decode in #41758, and #52522 proposes batch-invariant support for speculative decoding — but scoped to the sampling layer (RNG streams, request ordering, preemption recovery).

We ran a multi-day forensic campaign driving a 125B hybrid linear-attention/MoE model with a native MTP head (TP4, FP16) toward bitwise verify↔decode parity. Our finding: on our stack the dominant cause is **forward-pass arithmetic**, not sampling. The target model's verification pass computes rows with `M = k+1`, plain decode computes the same rows with `M = 1`, and **nothing in the current stack guarantees those two produce identical bits**. Real text contains decision points whose top-2 logit margin sits at ULP scale; one 1-ULP difference in one operator flips such a token, and greedy decoding turns that flip into a permanently divergent trajectory. Visible symptom on one of our workloads, purely from this effect: draft acceptance ~100% → 72%, decode ~110 → 89 tok/s.

**The invariant being violated:** given the same checkpoint, the same input and the same runtime/load configuration, the target model's verify pass over rows `[t..t+k]` must reproduce, bit for bit, what plain `M=1` decode would produce at each of those positions.

We are filing this because the mechanisms below are hardware- and method-generic, and because our experience says model-level point-mitigation does not converge. We deliberately do **not** propose a design.

#### Taxonomy of sources (each observed and isolated with bitwise evidence)

**Class A — kernel-level M-dependent reductions.** The same kernel produces different bits for the same logical row depending on how many rows were launched.
- Split-K GEMMs: partial-sum combination order follows launch geometry, which includes M.
- Explicit M-conditioned reduction configuration: we found a norm implementation selecting a 1024-wide reduction for M=1 and 512-wide for M>1 — a literal per-M topology branch.
- Hand-written F16 GEMM, M=5 vs 5×(M=1), random weights: ~92–114 of 20480 elements differ by 1–2 ULP.

**Class B — compiler/fusion topology.** `torch.compile`/Inductor generates reduction schedules **per shape specialization**.
- The native decomposition of an op (a gated RMSNorm, in our case) is fused differently inside an M=1 graph than inside an M=k+1 graph, producing sparse 1-ULP output differences from bitwise-identical inputs.
- **Opaque custom ops act as fusion barriers.** Registering an extra, numerically no-op custom op into only one engine's graph changed *neighbouring* arithmetic by 1 ULP; making both engines' graphs structurally identical restored bitwise equality. Graph structure — not just op semantics — is part of the numerical contract.
- Instrumentation participates in this: adding dump/trace ops changes fusion topology, so naive tracing perturbs the very difference under measurement.

**Class C — execution-form asymmetry between engines.** Spec-enabled engines route parts of the model through different execution forms than non-spec engines.
- An auto-gate keyed on "speculative config is present" moved a whole attention-block family to an opaque/eager path on the spec engine while the non-spec engine kept the compiled path → divergence at **prefill layer 0**, before any speculative token exists.
- The reverse leak also occurred: an opaque wrapper unconditionally instantiated in the non-spec engine moved the *non-spec* baseline trajectory. Which modules run compiled vs eager has to be treated as part of each engine's frozen contract.

**Class D — configuration-activated members.** Which of the above actually express depends on deployment configuration, so a fix validated in one configuration silently loses coverage in another.
- Quantization admission (a path accepted vs rejected) swaps whole kernel families in and out.
- **Load strategy is numerically non-neutral:** switching checkpoint loading between prefetch and mmap/lazy changed the greedy trajectory from token 0 with identical checkpoint bytes — not by corrupting data, but by shifting mapped addresses, allocation order and compile/capture timing, which re-rolls every Class A–C die.

#### Why model-level point-mitigation does not converge (empirical)

We closed a long series of individual members with pre/post bitwise evidence (top-k tie-break determinism, per-row replays of specific projections, norm dispatch admission, symmetric op placement, fixed-topology reduction reimplementations). Observed dynamics:

1. **The divergence point migrates instead of closing.** Across successive true fixes, the index of the first divergent token moved 14 → 2 → 14 → 10. Every real fix exposes the next member earlier or later, and each spec depth k, plus boundary prompt lengths (4/5/6 tokens), exercises *distinct* compile specializations with distinct expressing members.
2. **Gates lie in both directions when fed synthetic data.** Random-weight kernel probes over-predicted expression (kernel red, engine mute). Mild synthetic samples under-predicted it (operator gate green, real checkpoint red). Only per-instance gates on real checkpoint weights were trustworthy — and two layer instances sharing one kernel and one shape can still disagree, because expression is value-dependent.
3. **Replicating compiled arithmetic is a treadmill.** Matching Inductor's generated reduction means cloning exact codegen parameters (XBLOCK / R-block / warps / output tiling) per shape, it breaks on multi-output subgraphs with alias/buffer contracts, and any compiler upgrade invalidates it.

After closing every member that expressed at production shapes, we reached 16/16 greedy-token parity at 1K/4K contexts with acceptance restored to 81% and the expected spec speedup back — but residual 1-ULP members remained reachable at boundary shapes, each costing several full-model runs to localize. We stopped and documented those as known differences. That end state is operationally usable; it is a workaround, not a solution.

#### Gap relative to existing work

- #41758 is the symptom class, on a completely different model/method/hardware combination (Qwen3-0.6B, ngram, A100) — which is what convinced us this is systemic rather than a property of our stack.
- #52522's scope (sampling, RNG streams, preemption recovery) is necessary but not sufficient: none of Classes A–D live in the sampling layer.
- The `VLLM_BATCH_INVARIANT` kernel work is the right neighbourhood, but its axis is batch composition across requests. Speculative decoding adds the `M=1 ↔ M=k+1` axis for the *same* logical row, which is the axis we found unguarded.

### Proposed Change.

What we are asking for is a **scope decision, not an implementation** — we have no design to offer here, and we think ours would be the wrong one: every mitigation we built lives at the model/site level, and the campaign above is our evidence that this level cannot hold the invariant durably.

The change we would like considered: treat **forward-pass batch invariance across M for a fixed logical row** as a first-class contract at the kernel and compilation layer, in the same way `VLLM_BATCH_INVARIANT` treats batch composition today, and extend the batch-invariant spec-decode effort (#52522) to cover it rather than stopping at the sampling boundary.

Questions we think are worth settling before anyone writes code:

1. Is forward-pass M-invariance considered in scope for #52522, or is it a separate workstream?
2. Should verify↔decode bitwise parity be an explicitly documented guarantee under a batch-invariant mode (with the cost that implies), or an explicit non-guarantee — so that users stop treating greedy-output changes under spec decode as a bug in their own configuration?
3. If it becomes a guarantee, does it cover the compilation layer as well as kernels? Class B and Class C say that guaranteeing only kernels is not enough: fusion topology and per-engine execution form change results on their own.

We are happy to contribute evidence, reproduction methodology and measurements to whatever direction maintainers choose. Details in the appendices below.

### Any Other Things.

Everything below is offered as raw material for anyone continuing this investigation on their own stack. Each item exists because the naive version misled us first.

#### Appendix A — attribution methodology that survived

1. **Route-hit proof before interpretation.** Before trusting any A/B, prove the code under test actually executed (one-shot entry probes checked in logs). Note that logging inside compiled regions can be silenced by `torch.compiler.is_compiling()` guards — probe at admission time or outside the graph. Several of our early "fixes" were no-ops because the gate meant to admit them evaluated false on the spec engine; two others passed reduced gates and then regressed the full model. Arms without route-hit proof must be marked INVALID, never "no effect".
2. **Per-instance operator gates on real checkpoint weights.** Extract each layer instance's actual weights from the loaded engine and compare `op(k rows stacked)` against `k × op(1 row)` bitwise, per instance, for M = 1..8, plus padded-M variants. Per (1) above, do not substitute random weights. Our final inventory ran ~1,500 such comparisons across two operator families to certify zero expression at production shapes.
3. **Observation neutrality.** Under full CUDA graphs, naively saving intermediates returns capture-aliased garbage, and inserting dump ops changes fusion topology. The only neutral mechanism we found was copying from persistent, pre-registered graph buffers present identically in both arms, snapshotted after the step. Validate neutrality by checking that the instrumented run still reproduces the uninstrumented token sequence.
4. **Anchor gates.** Before comparing anything across arms: assert `input_ids` bitwise-identical, and pin both arms by full commit tuple. Every code snapshot silently spawns a new numerical baseline (Class B), so "matches the previously recorded golden output" is only meaningful when you name the build that produced that golden.
5. **Execution-form bisection.** Forcing both engines into the same form (both eager, or both compiled) is a cheap diagnostic: it collapses Class C entirely and leaves A/B isolated. In our case, unifying a single op's implementation across forms made all 48 layers' block outputs bitwise-equal over a 1024-token prefill — one op's fusion boundary accounted for the entire asymmetry.
6. **Fragile tokens are detectors, not evidence.** A token position with a ULP-scale top-2 margin is a sensitive tripwire, but different perturbations flip it to *different* tokens, so token-level observation cannot attribute cause. Attribution has to happen at the first divergent tensor, walked layer by layer.

#### Appendix B — measured signatures per class

- **Class A:** hand-written F16 GEMM, M=5 vs 5×(M=1), random weights: ~92–114 of 20480 elements at 1–2 ULP. The same kernel, gated per-instance on real checkpoint weights across 140+ instances × M=2..8: **zero** expression — fully latent on that checkpoint. This contrast is exactly why synthetic probes mislead.
- **Class B (fusion):** gated-RMSNorm decomposition under Inductor, M=1 vs M=2, bitwise-identical inputs: 1 FP16 element of 10240 differs, |Δ| = 7.63e-6, deterministic across reruns (a topology property, not a race). Generated reduction for the M=1 specialization: XBLOCK=1, R0_BLOCK=2048, 16 warps over a 128-element row — parameters that change per shape specialization.
- **Class B (barrier asymmetry):** one numerically no-op custom op registered into a single engine's graph → downstream layer outputs differ at 1 ULP across ~2.3M elements; symmetric registration → bitwise equal.
- **Class C:** spec-engine-only eager routing of an attention-block family → divergence present from prefill layer 0, before any speculative token exists.
- **Class D:** load-strategy flip (prefetch ↔ mmap/lazy) alone changed the greedy trajectory from token 0, with identical checkpoint bytes.
- **End-to-end:** first divergent token index migrated 14 → 2 → 14 → 10 across successive true fixes; acceptance ~100% → 72% and decode ~110 → 89 tok/s while members were expressing; after closing all members expressed at production shapes, 16/16 greedy-token parity at 1K and 4K with 81% acceptance and the expected speedup restored.

#### Appendix C — minimal reproduction recipe (any model, mainline vLLM)

1. **Symptom:** temperature 0, fixed prompt, spec decode on vs off, compare full token sequences (this is #41758's setup; any spec method works).
2. **First split:** compare the two configurations' **prefill** logits for the same prompt, bitwise. If they already differ, you have Class C/D — engine construction, execution form or configuration asymmetry — before speculation is even involved.
3. **Core check:** for an accepted prefix, compare the target model's verify-pass logits at position t (computed with M=k+1 rows) against plain decode logits at the same position (M=1). Any bit difference is Class A/B expressing. Walk layers to the first divergent tensor using pre-registered buffers (Appendix A.3).
4. **Shape axes that expose members:** tiny prompts (4/5/6 tokens — compile-specialization boundaries), prompts straddling block/graph-capture boundaries, and each spec depth k separately (each k is its own specialization).
5. **Configuration axes:** load format, quantization on/off, CUDA graph mode, `custom_ops` selection (native decomposition vs custom kernel), TP size. Each combination re-rolls which members express.

#### Environment

Observed on SM70/V100 ×4 (TP4), FP16 activations, a 125B hybrid linear-attention/MoE model with a native MTP head, full+piecewise CUDA graphs, `torch.compile`/Inductor. The SM70 software stack made expression *frequent*, but every mechanism above — split-K reductions, per-shape Inductor codegen, fusion barriers, spec-keyed execution-form gates, load-order sensitivity — exists on current hardware and mainline code paths.

Searched existing issues before filing; the closest are #41758 (symptom) and #52522 (adjacent scope), both linked above.
