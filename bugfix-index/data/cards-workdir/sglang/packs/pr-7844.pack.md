## 正文(PR 描述)

## Motivation

The current implementation of the dynamic LoRA update has several major limitations, most notably:

- Issue 1 [Known limitation] (#7463 ). User must provide at least one initial `--lora-paths`, and 
- Issue 2 [Bug]  (#7808 ). the initial adapter shapes (target modules, lora_rank) must be either the same or "larger" than ALL subsequent dynamically loaded adapters, otherwise, the process might fail, or even worse, produce incorrect result (when CUDA graph is enabled).

This PR is focusing on addressing the Issue 2 in a **backward-compatible** way, such that:
1. User can explicitly customize lora weight info via the newly introduced server args (similar to vLLM) to avoid having to find a "large enough" initial adapter.

2. Existing programs / commands would work equivalently in both result and performance.

```
python3 -m sglang.launch_server --max-loras-per-batch 1 --model-path meta-llama/Llama-3.1-8B-Instruct  --disable-radix-cache --lora-paths lora=algoprog/fact-generation-llama-3.1-8b-instruct-lora
python3 -m sglang.bench_serving --backend sglang  --num-prompt 480 --request-rate 8 --lora-name lora
```

3. User can get explicit and comprehensible error response when dynamically loaded adapters are incompatible with the current setup. No crashing server or implicit wrong result.

## Modifications

1. Refactor LoRAManager and LoRAMemoryPool to correct handle weight shape updates.
2. Add validation logic to ensure unsupported behaviors are denied in a user-friendly and predictable way without crashing server or producing unexpected behavior.
3. Add tests to cover both positive and negative cases.
