## 正文(PRD / 提案全文)

## Summary

Several vLLM MTP implementations perform checkpoint completeness validation inside
`model.load_weights()`. This assumes that one invocation receives a complete MTP
checkpoint. RL weight transfer does not have that property: IPC/NCCL may split one
logical update into multiple transport buckets and invoke `load_weights()` once per
bucket.

The result is a false missing-layer or missing-parameter error on the first partial
bucket, even when the complete update contains every required weight.

This RFC separates two concerns:

1. immediate validation of each received item (name, shape, shard mapping,
   divisibility, dtype/quantization metadata), which should remain in
   `load_weights()`;
2. completeness validation of a logical checkpoint/update, which must run once at
   the transaction boundary after all buckets have been accounted for.

## Affected MTP loaders

The current checks use three different notions of completeness:

- **MTP layer coverage:** DeepSeek, DeepSeek V3.2/GLM-5.2, DeepSeek V4,
  MiniMax M3, and Bailing infer loaded MTP layer IDs from successfully loaded
  parameters and require every configured MTP layer to appear.
- **Exact parameter coverage:** Step3.5 compares the required parameter set (minus
  explicitly optional scales) with the set returned by the loader.
- **Required parameter subset:** Inkling checks a model-specific required subset.

These differences reflect checkpoint mappings, not a need for three validation
lifecycle implementations. The validation boundary and set-difference algorithm can
be unified once each model provides canonical expected weight IDs.

## Current behavior

### Initial model loading

The default loader calls `model.load_weights(...)` for the startup checkpoint and,
when supported, compares the returned loaded parameter set with the model parameters
expected on the local rank.

This generic startup check is intentionally relaxed for quantized and online-
quantized models because checkpoint keys do not always have a one-to-one relationship
with runtime parameters. Examples include fused parameters, TP/PP/EP shards,
shared/tied parameters, optional scales, and parameters created or replaced by
quantization.

MTP loaders additionally run their model-specific completeness checks during startup.
Because startup normally supplies the complete checkpoint stream to one logical load,
those checks are valid at that boundary.

### RL IPC/NCCL updates

The checkpoint-format RL update flow is:

```text
start_weight_update()
  -> update_weights(bucket 0)
  -> update_weights(bucket 1)
  -> ...
  -> finish_weight_update()
```

Each bucket is passed to `model.load_weights()` independently. The transfer engines
currently discard the returned loaded set and do not aggregate it into an
expected-vs-loaded check for the complete update. Main-model parameters therefore
retain their immediate per-item loader checks, but do not currently receive a generic
aggregate completeness check at the end of an RL update.

The MTP checks are different only because they currently try to enforce complete
checkpoint coverage inside every individual `load_weights()` call. That causes the
false failures described by this issue.

## Short-term fix

The minimal fix is tracked in
[#49175](https://github.com/vllm-project/vllm/pull/49175) (development PR:
[aoshen02/vllm#4](https://github.com/aoshen02/vllm/pull/4)).

IPC and NCCL wrap only their incremental `model.load_weights()` calls in a scoped MTP
completeness-suppression context. The scope is automatically restored on success or
exception. It does not mutate every model submodule, and `start_weight_update()` /
`finish_weight_update()` do not manage a persistent flag.

This preserves:

- normal startup MTP completeness validation;
- parameter name, shape, shard mapping, divisibility, dtype, and quantization checks;
- layerwise reload initialization/finalization.

It intentionally does **not** claim that RL updates now have aggregate completeness
validation. It only removes the incorrect per-bucket assertion until the transaction-
level solution lands.

## Target architecture

After the `WeightLoadSession` lifecycle refactor in
[#48908](https://github.com/vllm-project/vllm/pull/48908) lands, both startup loading
and checkpoint-format RL reloads should use the same logical transaction:

```text
session.prepare()
  -> load one complete startup stream, or load multiple RL buckets
  -> record canonical IDs for successfully mapped local weights
session.finish()
  -> finalize model-specific loading
  -> validate expected_ids - loaded_ids
```

The session should provide generic accounting and validation APIs conceptually like:

```python
session.record_loaded_items(owner=self, loaded_items=canonical_ids)
session.register_validator(owner=self, validator=self.validate_completeness)
```

For an RL update, `record_loaded_items()` unions IDs across all IPC/NCCL buckets.
For startup, the same mechanism usually records one complete stream. In both cases,
the validator runs exactly once from `finish()`.

### Canonical weight manifest

The unified check should operate at canonical weight/parameter-ID granularity, not
only at MTP-layer granularity and not directly on raw checkpoint names. A manifest
must account for:

- fused parameters and individual fused shards;
- TP/PP/EP local ownership;
- shared/tied parameters;
- optional and format-specific scales;
- quantization mappings and generated/replaced parameters;
- checkpoint aliases such as shared MTP head/embedding weights;
- model/platform-specific post-load finalization.

Therefore `set(model.named_parameters())` is not a sufficient universal expected
manifest. Models/loaders define the manifest and canonicalization rules; the session
owns the lifecycle, aggregation, and common `expected_ids - loaded_ids` algorithm.

Example canonical IDs may distinguish whole parameters and fused shards:

```text
("parameter", "model.layers.61.mtp_block.fc.weight")
("parameter_shard", "model.layers.61.qkv_proj", "q")
("shared_parameter", "embed_tokens.weight")
```

## Follow-up PR plan

1. **Stop per-bucket MTP completeness failures.** Keep the short-term scoped
   suppression small and restricted to incremental IPC/NCCL `load_weights()` calls.
2. **Land the shared load lifecycle.** Complete #48908 so startup and RL reloads have
   a common `prepare() -> load -> finish()` transaction boundary. This PR should not
   attempt to define every model's required-weight manifest.
3. **Add generic session accounting.** Record canonical loaded IDs across one or many
   load calls, register validators, define cleanup/error semantics, and validate once
   at `finish()`.
4. **Migrate MTP loaders.** Replace layer-level, exact-parameter, and required-subset
   lifecycle code with model manifests plus the generic validator. Remove the
   temporary suppression context after all affected MTP loaders are migrated.
5. **Extend aggregate validation to main-model RL updates.** Reuse the same session
   accounting and model manifests so startup and RL have equivalent transaction-level
   completeness guarantees where the checkpoint format supports them. Preserve
   explicit relaxations for quantized/online-quantized and non-one-to-one formats.
6. **Harden checkpoint canonicalization.** Treat silently skipped or mis-normalized
   keys as a separate loader correctness class. For example, #43456 is not fixed by
   moving the validation boundary: missing DeepSeek V4 top-level head/embed aliases
   require key normalization and parameter-level accounting.

## Required tests

- complete single-stream startup loading succeeds and validates once;
- incomplete startup loading fails at `finish()`;
- complete multi-bucket RL loading succeeds after aggregation;
- a genuinely missing aggregate MTP or main-model weight fails at `finish()`;
- per-item name/shape/mapping errors still fail immediately;
- duplicate canonical IDs and fused-shard accounting behave deterministically;
- optional/shared/quantized parameters follow the model manifest;
- failed or cancelled updates clean up the session and cannot leak suppression state;
- IPC packed/non-packed and NCCL packed/non-packed paths use identical semantics.

## Non-goals of the short-term fix

- It does not solve silently ignored or incorrectly normalized checkpoint keys.
- It does not make layer-level coverage equivalent to parameter-level completeness.
- It does not add aggregate main-model validation to current RL updates.
- It does not make #48908 itself a completeness checker; accounting and manifests are
  explicit follow-up work.
