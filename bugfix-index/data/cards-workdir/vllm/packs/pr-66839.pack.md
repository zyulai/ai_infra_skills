## Overview

On CUDA, `convert_to_uint32_v2` now keys every NaN above +inf, as the FP16 coarse bins already do. On main, rows with sign-set NaN scores make the DSA top-k kernels select the wrong indices, write past the output row (`sampled_topk`) or fault (`cooperative_topk`). I found this while validating #66840.

## Claims

- Fixes three failures on main: the wrong top-k from fp32 `persistent_topk` (radix, FilteredTopK, sampled), at least 64 KiB written past the output by `sampled_topk`, and an illegal memory access in `cooperative_topk`'s recovery path, with enough sign-set NaNs in a row (cases below).
- The comparison replaces the sign test. On the B200, no config is more than 0.8 % slower than main.

## Validation

B200 builds of `csrc/{topk,cooperative_topk,sampler}.cu` from main `4e3463c874` and from this PR, with identical flags.

- `test_topk_nan_ordering_matches_torch` now also runs with sign-set NaNs, except on ROCm. A first version of the test set them in fp32 only. With it, main failed the 12 fp32 `persistent_topk` cases at 16, 48 and 128 rows because it leaves those NaNs out, and this PR passed all 72 cases. The current version also sets the bits after the bf16 cast; I have not run it, but the H100 CI job does.
- Rows of 100000 columns with sign-set NaNs, fp32 and bf16, `top_k` 2048:
  - 80 rows, 8000 NaNs in the last row: main's `sampled_topk` overwrites all 64 KiB of sentinels after the output.
  - 1 row, 4096 NaNs: main's `cooperative_topk` fails with an illegal memory access.
  - With this PR, neither writes past the output.
- main's `test_top_k_per_row.py` on this PR's build: 885 passed, 45 skipped, as on main.
- `benchmarks/kernels/benchmark_persistent_topk.py`, 4 rounds alternating the order of main and this PR: geomean 0.999 with `--backend persistent` and 1.000 with the default backend. No config is more than 0.8 % slower.

## Details

- Root cause: `cvt.rn.f16.f32` drops a NaN's sign. On the B200, 0xFFC00000 converts to 0x7FFF, and the bf16 path's packed conversion does the same, since the bf16 `cooperative_topk` case also faults on main. So the FP16 coarse bins put every NaN on top, while `convert_to_uint32_v2` keys a sign-set NaN below -inf.
- Paths that bin with FP16 and select with FP32 keys then disagree:
  - `sampled_topk`'s exact fallback picks a cutoff below every finite key and keeps nearly the whole row.
  - `cooperative_topk`'s single-key recovery counts every finite score as above the pivot.
- The fix replaces the sign test with `int32(bits) > int32(0xFF800000)`. Non-NaN keys are unchanged, and every NaN of either sign lands above the +inf key, the order `torch.topk` uses. On sm_100 and sm_120 some key sites need one more instruction.
- ROCm keeps the old key, and the new test cases are skipped there: I have not verified what its FP16 conversion does with a NaN's sign.
