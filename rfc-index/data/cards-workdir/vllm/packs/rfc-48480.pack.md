## 正文(PRD / 提案全文)

## Motivation

vLLM ships a large and growing set of Triton kernels (MoE, Mamba/SSD, GDN/FLA, KDA, linear/flash attention, INT8/FP8 quantization, normalization). Triton is portable by design and these kernels already run on non-NVIDIA backends for example  Intel GPU (XPU) builds compile and execute them through the same Triton path. However, the unit tests for these kernels do not reflect that portability and a large fraction of the kernels has no isolated unit test at all. Two concrete gaps:

- Tests are pinned to CUDA even when the kernel is not:
  Many kernel tests hardcode device="cuda", torch.set_default_device("cuda"), or call CUDA-only host APIs (torch.cuda.get_device_capability(), torch.cuda.is_current_stream_capturing()). The result is that a pure-Triton kernel which runs correctly on ROCm/XPU is still untested there: the test either error with a CUDA-only call or are simply skipped

- Many kernels are only tested indirectly, or not at all:
  A number of kernels are tested through a high-level pipeline test (e.g. the Mamba-2 SSD chunk kernels are reachable only via mamba_chunk_scan_combined_varlen; several DeepGEMM EP-scatter/gather and GDN/FLA helper kernels have no dedicated test). When kernel like that has a regression, the failure surfaces far from its cause and is hard to localize.

We reviewed the Triton kernel surface and selected the kernels we consider most important: the ones on the hot paths of widely-used model families (MoE, Mamba/SSD, GDN/FLA, KDA, attention, INT8/FP8 quant, normalization). This RFC proposes a uniform, upstream-friendly way to close both gaps for those kernels and explains why new or modified tests belong in upstream rather than living separately, somewhere in a vendor fork.

## Proposed Change

Every PR targets one kernel (or one tightly coupled kernel family) and states, in its description, which kernel it covers and the rationale for the change. Two PR shapes:

### "Adjusted" — make an existing CUDA-pinned test hardware-agnostic

For tests that already exist but are CUDA-bound:

- Replace device="cuda" / torch.set_default_device("cuda") literals with current_platform.device_type.
- Replace a module-level CUDA skip with
  pytest.mark.skipif(not (current_platform.is_cuda_alike() or current_platform.is_xpu()), reason=...).
- Scope genuinely CUDA-only assertions (device capability, stream capture, CUDA-only C++ ops) behind current_platform.is_cuda() /  is_cuda_alike() so CUDA behavior is unchanged and other backends take the path they already support.

### "New" — add an isolated test where coverage is missing

For kernels with no dedicated test (or only indirect coverage):

- Add a standalone test that launches the kernel directly (the same way its production wrapper does) and validates it
- Parametrize over the shapes/dtypes/flags the kernel sees in production so the test exercises each compiled variant
- Make it device-agnostic from the start (current_platform.device_type, no CUDA-only guards) so it runs on CUDA, XPU, ROCm and any other HW or plugin out of the box, possibly other HW.

### Guarantees that keep this upstream-safe

- No source-behavior change on CUDA/ROCm:
  The handful of touched source files only guard CUDA-specific host calls behind a platform check; the CUDA branch is the original code path
- Pure-Triton, no kernel rewrites. No .cu/SYCL kernel is added or modified
- Same numeric. References are standard PyTorch; tolerances follow existing upstream precedent (e.g. ROCm already doubles bf16 atol for selective_state_update - we extend the same thing to XPU)
- The pattern is already upstream-accepted. It matches what was merged in tests/kernels/test_mhc_kernels.py and tests/kernels/ir/test_layernorm.py and two PRs in this effort (#42736, #43307) are already merged upstream.
- Why these tests belong upstream and not in a fork:
    - The kernels are upstream and hardware-agnostic, so their tests must be too
    - Indirect coverage is not regression-localizing coverage
    - It strengthens upstream CI for everyone
    - One kernel per PR, each with an explicit rationale

### Scope

This scope covers the most important kernels: the ones used in key paths for widely used model families. They are grouped by function below, with representative PRs listed for each group (open unless noted):

This approach has already been proven upstream: #42736 (Mamba kernels on two hardware backends) and #43307 (lightning_attn + AWQ Triton) have both been merged, with no CUDA regressions.

###

No compatibility impact is expected. CUDA and ROCm code paths and test results remain unchanged: the source edits only guard CUDA-only host calls behind a platform check, and each new test is either device-agnostic or XPU-only. There are no changes to public APIs, kernels, or numeric.

### Test plan

Each PR is validated on GPU and  Intel XPU (Battlemage). CUDA/ROCm continue to be covered by upstream CI, which the gated, additive tests do not alter.
