## PR body
```markdown
## Motivation

Sleep level 2 releases KV cache memory, but it also discards model weights. This
is unnecessarily expensive when a framework only needs temporary GPU headroom
while keeping the same model instance resident.

One concrete use case is model weight update in RL training. The workaround in
[verl#7373](https://github.com/verl-project/verl/pull/7373) uses
`sleep(level=2)` followed by `wake_up(tags=["weights"])` before updating the
standalone model. Releasing only the KV cache reduces peak GPU memory and can
avoid OOM during the update, without discarding and remapping weights.

## Summary

This PR adds `release_kv_cache_memory()` as a dedicated KV-only partial-sleep
operation. It discards KV cache allocations, keeps model weights resident, and
pauses scheduling until the released memory is restored with the existing
`wake_up()` API.

## Implementation

### Call flow

The offline and server entry points converge on the same engine path:

```text
LLM.release_kv_cache_memory() -> LLMEngine ---------\
                                                       -> EngineCore
POST /release_kv_cache_memory -> EngineClient ------/       |
                                                             v
                                      Executor.discard(("kv_cache",))
                                                             |
                                                             v
                                               Worker -> SleepModeBackend
                                                             |
                                                             v
                                           CuMem/XPU allocator.discard(tags)
```

`EngineCore` first pauses the scheduler and clears the prefix cache. Depending
on the selected pause mode, it either handles existing requests immediately or
waits for in-flight requests to finish before asking all workers to discard KV
cache allocations. The scheduler remains paused after release; a discard
failure also fails closed instead of resuming scheduling with potentially
partially unmapped memory.

At allocator level, only mapped allocations tagged `kv_cache` are unmapped and
released, without a CPU backup. Per-allocation mapping state prevents duplicate
unmap or map operations when release, sleep, and wake-up calls are mixed.

### Interaction with sleep levels

`release_kv_cache_memory()` is treated as a KV-only partial sleep. A later
`sleep(1)` or `sleep(2)` can upgrade that state to a full sleep:

| Current state | Operation | Result |
| --- | --- | --- |
| Fully awake | `release_kv_cache_memory()` | KV cache discarded, weights resident, scheduler paused |
| KV-only sleeping | `sleep(1)` | Weights offloaded, KV cache remains discarded |
| KV-only sleeping | `sleep(2)` | Weights discarded, KV cache remains discarded |
| KV-only sleeping | `wake_up(["kv_cache"])` | KV cache remapped and scheduling resumed |
| Full sleep | `wake_up(["kv_cache"])` | Only KV cache remapped; weights remain sleeping and scheduling stays paused |
| Full sleep | `wake_up()` | All allocations restored and scheduling resumed |

The executor tracks the exact internal state with `sleeping_tags`. Scheduling
is resumed only after no sleeping tags remain.

### Logging and observability

This PR reuses the existing sleep-state logger instead of adding a dedicated
`kv_cache_released` Prometheus state. After KV release, the existing metrics
report `awake=0`, `weights_offloaded=0`, and `discard_all=0`: the engine is not
available for scheduling, but it is not in sleep level 1 or 2. The precise
resource state remains available internally through `sleeping_tags`.

There is currently no requirement to monitor KV-only release separately. If
that becomes useful, a dedicated Prometheus state and its transition logic can
be added in a follow-up change.

## Scope

The public API intentionally supports only KV cache release. Existing sleep
levels already cover the other current cases:

- `sleep(1)` offloads weights and discards KV cache memory.
- `sleep(2)` discards all managed GPU memory.

A generic public tag API would also need to define whether each tag is discarded
or offloaded, increasing the API surface and overlapping with existing sleep
semantics. More fine-grained public memory management can be discussed when a
concrete additional use case appears; the internal `discard(tags)` path remains
extensible.

## Related work

- [vLLM#42658](https://github.com/vllm-project/vllm/pull/42658) explores generic
  tag-level sleep management. This PR instead provides a smaller, explicit
  end-to-end API for the known KV-only use case.
- [vLLM#46438](https://github.com/vllm-project/vllm/pull/46438) contains related
  allocator-level selective-discard work.
- [verl#7373](https://github.com/verl-project/verl/pull/7373) demonstrates the
  downstream model-update use case and its current sleep/wake workaround.

This PR does not duplicate the generic public API proposed in #42658; its scope
and semantics are intentionally narrower.
