## 正文(PRD / 提案全文)

# Motivation

Text watermarking for LLMs is a process by which we perturb the output of a model in such a way that is detectable after generation. This process allows us to test whether a sequence of text is consistent with a watermarked generation process after the fact.

Watermarking is a necessary functionality in vLLM, because:
- It has become an important part of responsible LLM deployment
- It has become required by regulation by certain entities, to support provenance and transparency requirements (see [EU AI Act, Article 50(2)](https://artificialintelligenceact.eu/article/50/) and [California SB 942](https://leginfo.legislature.ca.gov/faces/billNavClient.xhtml?bill_id=202320240SB942))
- It is a modification of the sampling process, which cannot be modified by downstream consumers

Watermarking cannot be left as an out-of-tree functionality (such as `CustomLogitsProcessor`) because:
- Not all watermarking schemes are simple "logit biasers": some (such as gumbel-max) require adjust the sampling process itself
- Some schemes require access to the final output distribution of the model (after top-p, temperature...) and this is not currently possible with a `CustomLogitsProcessor`
- Production-ready implementations of watermarking will require support for speculative-decoding, which will potentially require adjustments to rejection sampling and other core behaviours of vLLM
- Watermarking will only become more ingrained with the generation process as techniques evolve and complexify

# Proposed Change

We propose the implementation of native vLLM watermarking during sampling, using techniques such as Gumbel-max or SynthID-Text. This change is drafted in https://github.com/vllm-project/vllm/pull/54053, and we recommend you treat it as a technical support to this RFC.

## Desiderata

1. Non-distortion - the watermark should not alter the expected output distribution of a model over keyed generations, nor rely on metadata attached to an output.
2. Detectable - the watermark should be reliably detectable using inexpensive techniques, to allow for large-scale scoring.

## Proposed Algorithm

We propose an initial implementation using the [Gumbel-max algorithm (Aaronson and Kirchner, 2023)](https://simons.berkeley.edu/sites/default/files/2024-10/LLM24-2%20Slides%20-%20Scott%20Aaronson.pdf) which has multiple desirable qualities:
- Single-token non-distortion (can be adjusted for single-sequence non-distortion using repeated-context deduplication) of the model's output distribution, see G.3 of [SynthID-Text Appendix](https://media.springernature.com/original/springer-static/esm/art%3A10.1038%2Fs41586-024-08025-4/MediaObjects/41586_2024_8025_MOESM1_ESM.pdf)
- Fast, relative to other schemes
- Unintrusive to implement, as it does not require access to significant parts of the model or request state
- Good detectability, using inexpensive methods
- May be updated to support speculative sampling

This algorithm uses a pseudo-random function (PRF) to create a deterministic keyed vector of uniform-random values `r_k ~ U(0, 1)`. At each position, we them sample `argmax_x r_k(x) ^ 1/p(x)`. The Gumbel-max identity allows us to structure our sampling by a key `k` without changing the expected distribution `p` over `k`.

Given a sequence of text of unknown provenance, we can then recalculate `r_k` for each token, and `score = sum_t -log(1 - r_t)` over our sequence. Under the null, `score` follows `Gamma(n, 1)`, so we have a length-adjusted p-value: this can be used with a threshold to classify a sequence as watermarked.

## Implementation

The implementation is divided into two independent components: generation and reference detection primitives.

### Watermarked generation

The initial implementation will support Model Runner V2 and Gumbel-max watermarking. Speculative decoding is out of scope initially, but may be supported with dual-key approaches: see [He et al. (2026)](https://arxiv.org/pdf/2605.12456) and [Sander et al. (2026)](https://arxiv.org/pdf/2602.01428)

Watermarking is configured at engine startup:

```python
@dataclass
class WatermarkConfig:
    algorithm: Literal["gumbel"]
    key: int
    context_width: int = 4
```

as well as a `SamplingParams` change that allows requests to control whether watermarking is applied:

```python
@dataclass
class SamplingParams:
    watermarking: bool | None = None
```

This allows for us to deploy an engine with watermarking configured, but to disable it on a per-request basis when unnecessary, such as internal or none-human-facing use.

The sampling pipeline remains unchanged until final token selection:

```text
model logits
    |
existing penalties and constraints
    |
temperature, min-p, top-k and top-p
    |
final token selection
    |
watermark disabled → existing random sampler
watermark enabled  → configured Watermarker
```

A shared `Watermarker` interface will define the algorithm-specific final selection. The initial `GumbelWatermarker` replaces the ordinary random draw with the keyed Gumbel-max draw. Greedy requests remain ordinary greedy sampling, as they cannot be watermarked.

This isolates watermarking from the model runner and allows us to extend support to additional algorithms, such as SynthID-Text and more advanced forms of Gumbel-max sampling (dual-key generation for example).

### Detection primitives

Basic detection does not require model weights or inference (although more advanced techniques that do this may be considered). vLLM will expose reusable detector primitives that expect token IDs:

```python
detector = GumbelWatermarkDetector(
    key=key,
    context_width=context_width,
)

result = detector.detect(token_ids)
```

The result contains the aggregate score, p-value, number of scored tokens, and threshold-based classification.

Shared detector logic handles context construction, repeated-context deduplication (necessary for p-value calibration), score aggregation, and thresholding. Concrete implementations will provide the token-level scoring and the corresponding p-value if available, if not then an aggregate score.

These implementations will serve as references for downstream implementations of detection services. A full detection endpoint would need to handle multiple tokenizers, multiple keys, additional algorithmic optimizations to the detection algorithms (entropy-weighting, early-fusion), and hinted search. These all fall outside the scope of vLLM and thus are not being proposed here.

We would suggest having a small, minimal example of a detection server in `examples/` to serve as documentation, and to further expose the detection primitives to downstream users.

### Implementation plan

While the code required to implement this proposal is minimal, it is critical that we thoroughly verify its behaviour. We must ensure that:
- Watermarked sampling is not significantly slower than normal sampling: this can be evaluated using E2E latency and throughput benchmarks, as well as micro-benchmarking of the samplers. This is heavily dependent on the chosen algorithm (both the watermarking scheme, and the PRF), we expect throughput degradation of O(0.3% for 1B models, 0.1% for 30B+ models) for Gumbel-max sampling and O(1% - 0.5%) for SynthID-Text (see Table 4 of [TextSeal](https://arxiv.org/pdf/2605.12456))
- Watermarked sampling does not significantly distort the quality of an expected output of a model: this is mathematically proven theoretically but remains dependent on certain aspects of key generation and context handling, it will be empirically validated with evaluations
- Watermarked generations are reliably detectable: we will provide TPR@FPR and detection power across lengths and generation entropies to accompany the baseline detection algorithm, but we expect downstream consumers to optimize their own algorithms as there is a large cost-quality tradeoff to explore that will differ by provider (as well as false-positive calibration)

### Note on diversity
Note that while watermarked generation may induce a loss in diversity over a sequence (single-token non-distortion) or multiple sequences (single-sequence non-distortion), most methods that would be considered for production watermarking do not produce a _catastrophic_ loss of diversity (determinism, given a fixed key and input). The proposed Gumbel-max algorithm, given its simplicity, does exhibit this behaviour.

If this RFC is accepted, we expect to add multiple other watermarking schemes. These schemes may employ techniques that restore diversity:
- Repeated-context deduplication
- Tournament sampling with randomly sampled candidates
- Random-tape methods
- Dual or multi-key methods
- Gated watermarking (random, or conditional on entropy, or conditional on context)
- Speculative decoding 

See Results section below for results.

### Additional points of discussion

#### Choice of PRF

Many watermarking schemes rely on a keyed PRF to guide generation, making the choice of such a function important to the behaviour of the algorithm. There are certain qualities we desire in our PRF:

1. Stability over time: a torch/triton update should not break a `(k, WM_k(output))` pair (see [Philox](https://dl.acm.org/doi/10.1145/2063384.2063405), which otherwise would be an excellent candidate)
2. Fast on GPU: many PRFs are only available in CPU form (see [SipHash](https://www.aumasson.jp/siphash/siphash.pdf)), which would require us to maintain an internal GPU/triton implementation
3. Good statistical properties: the PRF must have good uniformity in its output, independence across inputs and no structure; most PRFs have this as a principal objective already
4. [optional] Cryptographically secure: it may be desirable for the `(context, key) -> pseudorandom value` mapping to be indistinguishable from a fresh random function, as it protect from attackers predicting keys from context, predicting values from unseen contexts, or generating strongly watermarked text without the key. We can also suppose that some deployments may require FIPS compliancy

As we cannot ensure that every PRF is suitable to every use, we propose a modular PRF system to allow easy extension to new PRFs. This will allow us to implement a PRF that aligns with points 1, 2 and 3 while downstream consumers may extend the system to use PRFs with other qualities (such as FIPS compliance).

Here are some candidates for a suitable PRF:

| Candidate | 1. Stable | 2. Fast on GPU | 3. Statistical quality |
|---|---:|---:|---:|
| HMAC-SHA-256 | Yes | No | Yes |
| Philox (PyTorch) | No, due to API | Yes | Yes |
| SipHash-2-4 | Yes | No existing impl. | Yes |
| TextSeal integer hash | Yes* | Yes* | Yes** |

_* Assuming we maintain a frozen internal implementation_
_** Its statistical properties have no public analysis compared to the alternatives_

For an initial implementation, we propose an internal version of the Philox algorithm, that can be maintained as stable. It is high-performance and well-established for PRFs (supported by NumPy and used by PyTorch for CUDA RNG). [HMAC](https://csrc.nist.gov/pubs/sp/800/224/ipd) is a potential contender, as it is also well-established, cryptographically secure and can be FIPS compliant (unlike Philox), but even an optimized GPU implementation may not be fast enough as the algorithm itself is much heavier.

