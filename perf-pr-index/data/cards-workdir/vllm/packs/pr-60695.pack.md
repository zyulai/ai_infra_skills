## Details

**Root cause.** Take P = 7,449 tokens, prefix-match unit U = 128 and EAGLE block drop on, so the Mamba checkpoint is H = 7,296.

1. The first request computes the prompt. On the GPU, the Mamba state is registered at 7,296 and the attention tail at 7,424, which is H + U.
2. Normal Mooncake saves store attention only up to the last scheduler-block boundary, 7,168. Mamba state is never stored by normal saves.
3. The partial-tail save stores the Mamba state at 7,296. But it clipped attention to the same position (key `hash@7296`), so the proof at `hash@7424` was never stored.
4. After a GPU reset, the Mooncake lookup works like this:
   - Attention matches 7,296, and the EAGLE drop brings it to 7,168.
   - Mamba has no state at or below 7,168.
   - The hit is 0.

**Fix.**
- **Boundary puts.** `ReqMeta.boundary_puts` lists every block the job stores under an explicit prefix hash, as `BoundaryPut(group_id, block_id, num_tokens)`. The scheduler resolves and pins all of them; the worker writes each block under `block_hashes[num_tokens // U - 1]` (`_boundary_puts`). Two kinds of entries:
  - **Mamba state.** Each core hand-off, whether a block-aligned snapshot or the sub-block tail at H, becomes one put of the handed-off block. Under DCP, Mamba blocks are smaller than the LCM, and only the boundary block is stored.
  - **Non-Mamba tail.** `_partial_tail_non_mamba_puts` (scheduler, once per store job) covers each non-Mamba group from the last scheduler-block boundary to H plus that group's `eagle_proof_margin`, once that much has been computed. Each block is keyed at its end, clipped to that point; null and missing blocks are skipped.
- **Publishing.** The tail is published on the save that first covers the whole prompt (`ReqMeta.publish_partial_tail`, which mirrors the tracker's `partial_tail_sent`), or when a Mamba hand-off arrives. The boundary is derived from the prompt length, so a job without a Mamba hand-off can still publish the attention proof. Later saves carry no tail.
- **Pinning.** A store job pins exactly its boundary puts' blocks (plus every non-Mamba block for a normal save). Before, a finish-time tail pinned only the Mamba block while the worker read attention blocks from the freed table.
- **Prompt length vs. prefill end.** `ReqMeta` separates `num_prompt_tokens` (used for the checkpoint) from `prefill_end_tokens` (includes output tokens replayed after preemption, used for store masks), and adds `completed_token_len`.
- **External lookup.** It scans past the hit limit for EAGLE groups, as the core lookup does since #60533. The shared helpers `eagle_proof_margin` and `partial_hash_hits_enabled` replace the local copies.
- **Partial hits follow core.** Mooncake used to decide `enable_partial_hash_hits` itself, from the Mamba specs of the groups it transfers. Core also requires every group's manager to support fine-grained lookups (a sliding-window group needs block-aligned ones) and counts groups the store does not transfer, so the two could disagree. Mooncake's scheduler and worker now read core's resolved `kv_cache_config.cache_hit_alignment_tokens`. One core line makes that possible: `engine/core.py` sets the field (and `hash_block_size`) on the scheduler's `KVCacheConfig` as well as the workers'; the scheduler's copy is deep-copied before they are resolved, and core itself does not read them there.

**Known limitations and follow-ups:**
- The prompt-completion tail is sent once. If that save is skipped under store pressure or its put fails, it is not retried; before, every later save rebuilt it (and `batch_is_exist` dropped it once stored). The Mamba state already worked this way, because its CoW block is pinned only for its own job.

**Duplicate check.** #59826 contains these changes. Splitting it into core (#60533) and Mooncake parts was requested at review, so this PR is that Mooncake part, not a duplicate.
