## 正文(PR 描述)

Resolves [#21308](https://github.com/vllm-project/vllm/issues/21308#issuecomment-3192203896)


### **Purpose**
This PR resolves a RuntimeError that occurs on the ROCm platform when using speculative decoding (eagle3 method) with FP8 quantization.

The root cause was a data type mismatch in the attention backend. The drafter model was not inheriting the kv_cache_dtype from the target model, causing its KV cache to default to uint8 while the target model used fp8, leading to a crash in the Triton kernel.

This fix ensures the drafter model inherits the global CacheConfig from the vLLM engine, guaranteeing type consistency.

The core fix is the logic to retrieve and pass down the configurations. The other changes are mainly to support this parameter passing through the class constructors.

Core Logic of vllm/model_executor/models/llama_eagle3.py (Lines 12, 36, 41, 121, 132)

### **Other potential points**

**1：In the case of auto, we check as follows: if the target model is fp8, process it. If it is float16, keep it as it is.**

Modification Location: "The core code for this fix is ​​located in the vllm/model_executor/models/llama_eagle3.py file, specifically in the init method of the LlamaModel class."

Implementation: "By importing and calling the get_current_vllm_config() function, the global, parsed configuration of the current vllm engine, is obtained."

Logic Explanation: "Then, the cache_config objects obtained from the main model configuration are directly passed to the LlamaDecoderLayer in the draft model for initialization."

If the main model's kv_cache_dtype is fp8, then the cache_config.cache_dtype obtained by the draft model will naturally be fp8, resolving the issue.

If the main model's kv_cache_dtype is auto or float16, then the configuration obtained by the draft model will also be auto or float16. float16, completely unchanged, without any side effects.

This avoids hard-coding code like "if 'fp8' in ...," making the fix more general and robust.


**2：We have reproduced and fixed the issue with rocm. We need to mention the issue with cuda.**

In the GPU environment, the combination of the V1 engine, mandatory Triton backend, and egale3 instructions in the def is_kv_cache_dtype_supported function in vllm/vllm/platforms/cuda.py does not meet the scenario requirements and returns false. As a result, the def _is_v1_supported_oracle function in vllm/vllm/engine/arg_utils.py enters the if self.kv_cache_dtype != "auto": logic, ultimately throwing an assertion error unless you use a graphics card model supported by the code.

**3：Why isn't the kvcache for speculative decoding VLLM separated? Will adding the kvcache dtype config for speculative decoding to the top-level configuration take effect?**

The architecture was originally designed for a single master model, with global configurations such as CacheConfig and QuantizationConfig.

Modular Implementation: Speculative decoding was added later and is implemented by loading a separate "scratch model." vLLM creates a separate model configuration (ModelConfig) for this scratch model.

Bug Root: This is the problem. We originally added code to vllm/vllm/engine/arg_utils.py to retrieve the target model's configuration from the draft model. Then, in the next layer, vllm/vllm/config/__init__.py, 
in the `def __post_init__(self):` method, 
`if self.model is not None:`, 
      `self.draft_model_config = ModelConfig(...)`, 
we added the `kv_cache_dtype` parameter to `ModelConfig`, but this did not take effect. This is because this ModelConfig lacks a default `kv_cache_dtype` attribute, causing the loading process to fall back to a default, simpler configuration path. In this path, `kv_cache_dtype` in auto mode ultimately resolves to `uint8` (a basic quantization type), rather than querying the main model's configuration.

Conclusion: The root cause of the bug is the lack of a reliable configuration inheritance and synchronization mechanism between the two independent configuration domains of the main model and the draft model. Our final fix (directly retrieving the global configuration in `llama_eagle3.py`) aims to establish this direct and reliable connection.
