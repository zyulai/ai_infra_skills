## PR body
```markdown

When HiSparse uses its **shared host pool**, all local TP ranks share one `/dev/shm` mmap per DP rank. Even so, every TP rank registers the whole pool with NIXL, and every TP rank READs the same host-pool KV into the same pages. With UCX this means `ibv_reg_mr` of the full pool on every NIC, twice per NIC when relaxed ordering is on. At TP8 with 8 NICs, the pool is registered **128 times per node**, and each request's host-pool KV is pulled **8 times** into identical memory.

This PR adds an opt-in flag, `VLLM_NIXL_HISPARSE_DRAM_RANK0_ONLY=1`, which makes TP rank 0 the only rank that registers the shared pool and pulls into it. The other ranks:

- keep the DRAM regions in their metadata, so the prefill handshake still sees identical region lists;
- skip the DRAM `register_memory`;
- skip the DRAM transfer dlist;
- skip the DRAM part of each READ.

The GPU-resident part (the indexer cache) is still read by every rank, and every rank still notifies the producer.

Completion and ordering need nothing new:

- A request finishes only when all TP ranks report it done.
- HiSparse restores from the shared pool on the next step.
- The `cudaHostRegister` pin of the pool on every rank is unchanged, because each rank's GPU still reads from it.

### Changes

- `vllm/envs.py`: adds `VLLM_NIXL_HISPARSE_DRAM_RANK0_ONLY` (default off).
- `nixl/base_worker.py`:
  - `_leaves_dram_xfer_to_rank0()` decides whether a rank skips. That requires the flag, mixed DRAM/VRAM regions, `tp_rank != 0`, and `use_shared_hisparse_host_pool()`. Private (non-shared) pools are never affected.
  - Skipping ranks:
    - do not register DRAM ranges;
    - store `None` instead of preparing DRAM dlists, in both the local path and the split path;
    - leave zeroing of clipped shared-pool pages to rank 0.
  - Shutdown ignores the `None` handles.
- `nixl/pull_worker.py`: `_read_blocks_mixed()` drops the DRAM descriptors on skipping ranks and keeps the device part. It registers the request even when nothing is left to read, so it still completes and notifies.
- `NixlPushConnector` already rejects mixed-memory KV caches, so it is unchanged.
- Tests (`tests/v1/kv_connector/unit/test_nixl_connector.py`):
  - **The rank decision:** flag on/off × rank 0 vs non-zero × shared vs private pool.
  - **No DRAM dlist on skipping ranks:** descriptor positions still cover the DRAM regions, so ids stay aligned with the remote side.
  - **A READ that keeps only the device part** still notifies.
  - **A READ left with no descriptors** still completes and notifies.
  - Existing `object.__new__` fixtures initialise the new attribute.

### Why: VM freezes on cloud RoCE VFs

On Cloud VPC instances (QEMU/KVM guests with ConnectX-7 SR-IOV VFs over RoCE, UCX 1.21 via NIXL 1.3.2), a GLM-5.3 HiSparse decode froze **both VMs** during NIXL registration with a 384 GiB pool. There was no guest panic, no guest log and no watchdog output; the nodes had to be reprovisioned. The same configuration passes on bare-metal H200 with InfiniBand.

Guest-side sampling explains the scale of the problem:

- **Pins per page:** `nr_foll_pin_acquired − released` measured exactly **8 + ranks × NICs × 2** (relaxed ordering) per page of pool.
- **Registration metadata:** the VFs' `fw_pages_total` stayed flat at 4 per VF throughout, so the registration metadata is not taken from guest memory.
- **Freeze point:** the freeze appeared between 36.9 TiB (passed) and 49.2 TiB (froze) of NIC-registered memory per VM.

### Results (llmd-roce cluster, GLM-5.3, DeepEP LL decode, 8 NICs, relaxed ordering on unless noted)

**Registration footprint per VM**, from a 2-node decode (DP2 × TP8). These numbers are measured with a startup patch equivalent to this PR on vLLM `87ecf7dbb`.

Startup is not faster per node: rank 0 does the same per-rank work as before. What drops 8x is the number of registrations, the pinned memory and the NIC metadata.

**P/D correctness**, using a separate prefill and greedy decoding:

- **Results:** P/D output matched the prefill-only reference for 18-, 28.7k- and 250k-token prompts, at pool sizes 100, 288 and 384 GiB. The short prompt shows the usual small numerical divergence between prefill and decode kernels; the 28.7k answer is identical; the 250k answer is the same sentence, differing in one word ("at" vs "in").
- **Transfer count:** each request takes **9** NIXL transfers (rank 0 host + 8 device) instead of 16.
- **Failures:** 0 failed transfers.

**End-to-end benchmark**, 4P/4D, 64 H100:

- **Prefill:** DP4 × PCP8/DCP8.
- **Decode:** DP4 × TP8 with a 288 GiB shared pool.
- **Load:** cc_traces 256k, constant load, 900 s per level.
- **Fairness:** both arms ran on the same 8 nodes, and both roles were re-created between arms.
```
