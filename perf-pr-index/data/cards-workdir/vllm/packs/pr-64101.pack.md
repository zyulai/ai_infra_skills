## PR body
```markdown
## Purpose

Mono decode (`--monokernel`) for DeepSeek-V4.1-Flash runs only at TP2 and TP4. `MonoDecodeLayer._create` refuses any other tensor-parallel size. At conc 1 a TP8 server can still use mono decode: each rank streams half the weights, while the persistent K1/K2 chain stays the same length. This PR makes the existing FlyDSL kernels correct at TP8 on gfx950. That means 8 attention heads per rank, and a 288-wide routed/shared expert intermediate (routed is padded to 384 by the loader).

At TP8 the only kernel changes are the head-tile rounding and one GEMV tail. The cross-rank reduction, MoE, router, K1 front, combine and draft runner already loop over `tp` and need no changes.

## Changes

- `mono/attention/plan.py`, `Dims`: `head_tiles` now rounds up (`cdiv(heads, 16)`), and a new `heads_pad` gives whole tiles. Before this, `head_tiles` was `8 // 16 = 0` at TP8, so the split-attention loops (`back.py`) emitted no MFMAs and would silently produce wrong output once the gate opens.
  - At M=7, ratio 2, the CPU compile for gfx950 shows 0 bf16 MFMAs before the fix and 32 after, the same count as TP4.
  - A rank must have at least one tile; this is asserted.
- `mono/attention/back.py`: the split stage's q/p/st LDS and the stat offset are sized by `heads_pad`. The padded head columns are computed but never stored. That is correct by column independence:
  - each head has its own score max and its own PV column;
  - the stat stores and the combine read only `h < heads`.
- `mono/stages/gemv.py`: the row-major FP8 step load accepts `K % 64 == 32`, which is the shared expert's down projection at K = 288. The last step's upper lanes are clamped into the row, and `_fp8_step_mfma` already zeroes them on both sides.
- `mono_decode.py`: the gate admits TP8. gfx942 stays TP4 only (`:410`).
- Tests: TP8 cases are added to `test_dsv41_mono_numerics.py` (`tp in [2, 4, 8]`) and `test_dsv41_mono_layers.py` (`(8, 8)` and `(8, 28)` on cdna4).

## Test Plan

1. CPU-only FlyDSL compile for gfx950 (AITER 0.1.26, FlyDSL 0.4.0), on this branch and on unmodified main:
   - TP8 builds: K1, K2 and FFN at M = 7 and 28; ratios 0, 1 and 2; the index-source and fold variants; and the DSpark draft K1/K2.
   - TP2 and TP4 builds: compared byte for byte against main.
2. GPU, 8x MI355X: a TP8 server with `--monokernel` running the MLPerf conc-1 recipe:
   - DSpark k=6;
   - adaptive verification off;
   - decoder SWA bounded replay;
   - MXFP4 sparse-logits indexer.

   Measurements:
   - `vllm bench serve`, random 32k in / 1k out, `--ignore-eos`, synthetic acceptance length 3.87, so the step time is isolated from acceptance;
   - GSM8K-1319, 8-shot greedy, block rejection with real acceptance, on the same server.
3. To run on this branch with 8 GPUs:
   ```
   pytest tests/models/test_dsv41_mono_numerics.py -k "8"
   pytest tests/models/test_dsv41_mono_layers.py -k "8-8 or 8-28"
   ```

- Status of the GSM8K gap: investigated, but not explained yet. The layer tests below pass, and an earlier TP4 on/off pair went the other way (mono 0.929 vs 0.919).

**Follow-ups (not in this PR):**
- With the launch-count reductions in #63885, #63888, #63890 and #63891 and the tuned K1 of #63893 (on #63027) and X8R of #63892 widened from TP4 to TP8, conc 1 reaches **4.53 ms** (GSM8K 0.919, AL 3.570). That is -14% vs TP4 + mono on the same image. The TP8 widening of #63892/#63893 is a follow-up. It also needs #63027's tuned seam (`attn_words`) to poll its 16 per-rank ATTN units in one batch: `POLL_MAX` is 12, so a split batch costs two serial round trips.
- **Not for conc ≥ 4.** At conc 4, one TP8 server is 26% lower in throughput than 2 x TP4 replicas: 1262 vs ~1706 tok/s, TPOT 2.35 vs ~1.71 ms. TP8 mono is a conc-1 configuration.
- The mono kernels' cross-rank spin-waits are unbounded, at TP4 as well. A hang on one rank stalls every rank of the server, which matters more at 8 ranks. A bounded wait with a host fail-stop, as the Kimi-K3 mono has, is planned as a separate PR.
```
