## 正文(PRD / 提案全文)

### Motivation.

There are three main motivations:
- vLLM should support integrating with all MCP servers
  - TODO: Test with enterprise ones like Github
- Clean up gpt-oss tool specific code paths in vLLM
  - Tools and models change, but MCP is a protocol meant to support all models
  - Sets the stage for full MCP integration for all tool calling models
- Avoid losing information due to lossy OpenAI types for output
  - An example below

```
# What you can return to the user on the ResponsesAPI for this tool call with the OpenAI types.
class ActionOpenPage(TypedDict, total=False):
    type: Required[Literal["open_page"]]
    url: Required[str]
# The interface for the actual tool call the model does
open_link(ctx: Context,
    id: Union[int, str] = -1,
    cursor: int = -1,
    loc: int = -1,
    num_lines: int = -1,
    view_source: bool = False,
    source: Optional[str] = None)
```

This feature is similar to the concept of “connectors” because we still don’t support users specifying arbitrary MCP servers by URL yet, the list is static and owned by the server, which is more similar to the concept of [OpenAI MCP Connectors](https://platform.openai.com/docs/guides/tools-connectors-mcp#quickstart).

### Proposed Change.

### Tool Namespaces
- For gpt-oss, a namespace represents a group of tools. For OpenAI Harmony, some namespaces get treated in unique ways 
- A MCP server has a collection of tools. The MCP server can be identified by its **serverInfo.name** 
- For the ResponsesAPI, the MCP Tool type has a **server_label** field to identify the MCP server.

In the codebase these were three different concepts, but by using it as a foreign key we simplify the codebase and still provide needed functionality. MCP servers and the Responses API are generic and able to support all models, you should be able to use the same MCP server for Deepseek and gpt-oss. 

As RL for tools gets more popular, more models will have special case behavior for tools. Different fine tunes of the same model may have different special case behavior for tools. So this special case handling has been moved from hard coded paths to be based on **namespaces**. 

These are defined by the server/model and I’ll refer to namespaces that need special case handling as **elevated**. (Needs a new name)

There is currently special case code in vLLM to treat the container namespace as elevated. Other use cases may not want the same thing. So now, one deployment can elevate the namespace with an env variable, and the other deployment doesn’t need to. 

### Standardize around MCP 
While still supporting backwards compatibility with OpenAI built-in tool types like CodeInterpreter, we now map all tool types to MCP tools. vLLM itself should not be responsible for executing the tools themselves outside of demos, so all tools will be executed on MCP servers anyway! 

Then, by using the MCP tool type everywhere:
- The user can have an expectation about which server_label are treated as elevated
- The code no longer needs special cases for different OpenAI tool types

As a next step, we should standardize all tool calls and outputs use the McpCall type as well, as it will continue to simplify the logic and allow us to use server_label to handle elevated tool calls/output in the input to ResponsesAPI. 

Note: Now, if we assume reasoning messages for tool calls have the same channel as the call that comes right afterwards (OpenAI makes this assumption in their Responses API implementation), we have a path to using ResponsesAPI losslessly for gpt-oss only using Responses types (no Harmony metadata needed). 

### Usage Example:
Run the provided simple Memory MCP server using:
```
python tests/entrypoints/openai/memory_mcp_server.py 
# 8765 is the default port
```
Then register it with your vLLM responses API server with:
```
CUDA_VISIBLE_DEVICES=6 vllm serve openai/gpt-oss-20b --tool-server=localhost:8765
```
And then try it out with something like:
```
curl http://localhost:8000/v1/responses \
  -H "Content-Type: application/json" -N \
  -d '{
        "model": "openai/gpt-oss-20b",
        "input": "Show me that the memory tool works.",
        "tools": [
          {
            "type": "mcp",
            "server_label": "memory", 
            "server_url": "ignored"
          }
        ],
        "enable_response_messages": true
      }'
```
