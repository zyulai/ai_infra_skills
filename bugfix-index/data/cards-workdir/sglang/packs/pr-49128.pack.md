## 正文(PR 描述)

## Why the test broke

`test/registered/debug_utils/test_nightly_precision_regression.py` failed in the Nov 7 nightly (attempt 1) with `zai-org/GLM-5.2-FP8: FAILED - tensor=...model.layers.56.self_attn.inputs.hidden_states rel_diff=0.00117`, and passed on the rerun on the same commit.

- **The failure itself is a runner, not code.** On healthy hardware the dumped tensors are bit-reproducible: 16 fresh launches on one commit on a separate 8x H200 machine were bit-identical to each other and to the stored baseline, and passing CI runs report `max_rel_diff=0.0`. The failing attempt ran on one specific `8-gpu-h200` runner whose deviation (starting at layer 48, prefill tokens 11-16, largest on TP rank 1, growing to ~1.4e-2 by layer 77) is bit-identical across a month of nightlies on different commits; every comparison from that runner against a baseline from another runner has failed. That runner needs to be drained and checked; no threshold can separate it, since its deviation is as large as a real numerics change.
- **The rerun then poisoned the baseline store.** `push_run` skips the tensor upload when the same model + date + sha path is already in the manifest. Attempt 1 pushed its tensors with `pass_label="failed"`; attempt 2 passed and only refreshed meta and appended a `passed` manifest row, so that row now serves attempt 1's deviating tensors as the next baseline (`fetch` takes the newest non-failed row). The next nightly on a healthy runner will compare against them. The same reuse turned an earlier deviation into the baseline in October.

## Changes

- `push_run` skips the tensor upload only for a `failed` push. A passed push at an existing path uploads its own tensors, so a `passed` row always points at tensors from a passing run; a failed push still leaves the earlier tensors in place.
- The CI context records `RUNNER_NAME` as `ci_runner`, promoted to the manifest, so a deviation that follows one machine is visible from the manifest.

The baseline the store holds right now still needs one refresh from a healthy runner (`SGLANG_PRECISION_FORCE_UPDATE=1`); this PR does not write to the store.

## Verification

- Checked locally against a fake `HfApi`: a passed push after a failed one at the same path uploads its own tensors here and skips them on main; a failed push still skips them.
- The nightly test itself is not rerun from this PR: it writes to the shared baseline store.
