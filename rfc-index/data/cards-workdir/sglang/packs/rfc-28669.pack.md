## 正文(PRD / 提案全文)

### Motivation

Before a model runs, the serving system often needs to know what the request will look like to the model:

- A router places and sizes work before a request reaches a GPU: how long the request is, whether its prefix is already cached, and whether its media is already processed.
- A disaggregated pipeline prepares a request once and hands the model the tokens, instead of re-tokenizing at each hop.

For both cases, the prepared request has to match what the model actually runs. When it does not, cache lookups can miss and token counts can be wrong (#26555, #27386, [llm-d-router#1072](https://github.com/llm-d/llm-d-router/issues/1072)).

This proposal exposes that request view before execution, so routing and model servers do not rely on approximations.

### Proposal

The goal is to expose the same preprocessing path used by SGLang inference as a lightweight standalone service that returns the prepared generate request without running the model.

In particular, this should:

- Run as a CPU-light preprocessing-only server.
- Share the exact preprocessing logic used by normal SGLang inference endpoints.
- Return a generate request, not just raw token IDs, with the metadata needed for tokens-in/tokens-out.
- Include multimodal hashes and related metadata in the tokenize/preprocess output, so encoder-disaggregated setups can route and reuse MM encoder work consistently.

**Before and after:**

Today, chat and completions requests can be tokenized through one dedicated `/tokenize` endpoint:

```
chat / completions
   |
   v
/tokenize
   |
   v
token ids + count
   - no mm features (no hashes, no positions)
   - no /responses or /messages support
```

Proposed, the same request becomes the full input the model runs:

```
request  (chat / completion / messages / ...)
   |
   v
preprocessing   (same logic used by serving entry points)
   - chat template, tools, reasoning
   - tokenization
   - media identity and token positions
   |
   v
generate request
   - token ids
   - request metadata
   - multimodal fields needed by the generate path
   |
   v
model    (token ids in  ->  token ids out)
```

The model accepts this generate request directly, so preprocessing and execution can run in one process or on separate machines. The rest of the request, such as the sampling settings and any cache key, rides along unchanged for the model to run.

### Usage

The standalone mode could be exposed either as:
```bash
sglang serve renderer
```
or as a dedicated command:
```bash
sglang renderer
```

For HTTP APIs, the clearest option is to expose preprocess-specific endpoints that mirror the serving APIs, for example:
```
/v1/chat/completions/render
/v1/completions/render
/v1/responses/render
/v1/messages/render
```
These endpoints would accept the same request format as the corresponding serving endpoint, but return the prepared generate request instead of running the model.

### Phasing

1. **Shared preprocessing path.** Factor preprocessing into one shared path used by the existing serving entry points. This should not change behavior, and is useful on its own.
2. **Standalone preprocessing service.** Expose the same path as an opt-in service that can run without starting the full serving engine or loading the model (following #27606 in spirit).

### QA

**Why not just use the current `/tokenize` endpoint?**
`/tokenize` is useful, but it only returns token ids and a count. That is enough for simple text cases, but not for precise routing or token-in/token-out execution.
For multimodal requests, we also need media identity and positions in the token sequence. `/tokenize` is also not a lightweight standalone service today: it still requires starting the serving engine, loading the model, and it does not cover all request APIs such as `/responses` or `/messages`.

**What is a generate request?**
A generate request is the prepared input the model runs on: the token ids, the multimodal inputs if any, and the execution settings that should stay attached to the request.
It is not part of the standard OpenAI-compatible API. Each backend defines its own version, so vLLM and SGLang may represent it differently.

**How is multimodal handled?**
For multimodal requests, preprocessing exposes the information needed before execution: the tokenized request, the media identity, and where each media item appears in the token sequence.
Whether heavier processed media data is produced in the standalone service or later in the SGLang server is left as an implementation choice. The important part for this RFC is that routing and model execution use the same media view as full inference.

**Why does SGLang need this, instead of one shared preprocessing server for all backends?**
The output has to match SGLang's internal model input. Tokenization, chat templates, special tokens, multimodal placeholder handling, and the internal generate-request format can vary by backend and model, so a generic preprocessor would only approximate the result.
A shared layer can still normalize user requests before they reach SGLang, but it cannot replace the SGLang-specific preprocessing that produces the model input.

**Is this only useful for routing?**
No. Similar needs have come up for custom frontends and reinforcement learning. SGLang has related requests for server-mode token IDs and token-ids input (#5653, #12145).
