## Purpose

Fix a CUDA illegal memory access (IMA) crash in the MLA indexer's decode flattening path when using data parallelism + speculative decoding (MTP).

### What changed

`arange_buffer` in `DeepseekV32IndexerMetadataBuilder` was allocated with size `max_num_seqs * next_n`, while the other flattening buffers (`expanded_seq_lens_buffer`, `expanded_block_table_buffer`) correctly use `max_num_batched_tokens`. During CUDAGraph dummy runs on idle DP groups, stale `query_start_loc` entries for padded requests inflate `actual_expanded` beyond `max_num_seqs * next_n`, causing a silent out-of-bounds GPU write.

### Why

1. `execute_dummy_batch` creates a 1-request dummy batch but `_build_attention_metadata` uses `num_reqs_padded` (CUDAGraph bucket size).
2. `query_start_loc` is only populated for the 1 real request; padded indices retain stale values from previous real batches.
3. `split_decodes_and_prefills` classifies all padded requests as decodes (since `max_query_len <= decode_threshold` with spec decode).
4. The flattening path computes `actual_expanded = sum(decode_lens)` over all padded requests, yielding values far exceeding the buffer size.
5. `self.arange_buffer[:actual_expanded]` writes out-of-bounds → CUDA IMA surfacing asynchronously at the next sync point.

## Test Plan

Tested with GLM-5-FP8 on 8× H200:
```bash
vllm serve /path/to/GLM-5-FP8 \
  --data-parallel-size 4 --tensor-parallel-size 2 \
  --speculative-config.method mtp \
  --speculative-config.num_speculative_tokens 3 \
  --kv-cache-dtype fp8 --gpu-memory-utilization 0.85
```

## Test Result

- **Before fix**: Server crashes with CUDA IMA soon under load (1000 requests, avg 10K prompt tokens)
- **After fix**: Server ran 85+ minutes stable under the same benchmark load with zero errors
