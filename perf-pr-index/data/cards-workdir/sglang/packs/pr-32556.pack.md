## Problem

The warmup flashinfer autotune runs a **decode-shaped** dummy forward (`BaseRunner.warmup` → `_autotune_buffers()`, 1 token/req), so tuned buckets only cover token counts up to the decode batch size. Larger prefill/extend batches fall outside the tuned buckets at serving time and run flashinfer's slow default heuristic:

```
[AutoTuner]: No tuned config covers flashinfer::trtllm_fp4_block_scale_moe input_shapes=(torch.Size([16384, 7168]), ...);
falling back to runner=MoERunner tactic=-1. This shape is outside the tuning bucket range ...
```

With flashinfer **0.6.15.post1**, the default heuristic for `trtllm_fp4_block_scale_routed_moe` is **~30% slower than the tuned tactic at >=8192 tokens** on sm100 (GB300) — flashinfer-ai/flashinfer#4190. Microbench at Kimi-K2-architecture shapes (384 experts, top-8, hidden 7168, intermediate 512/rank at tp4), same GPU, µs/call:

| tokens | 0.6.13 heuristic | 0.6.15.post1 heuristic | 0.6.13 autotuned | 0.6.15.post1 autotuned |
|---|---|---|---|---|
| 1024 | 567 | **443 (−22%)** | 550 | **402 (−27%)** |
| 4096 | 607 | 593 | 554 | 545 |
| 8192 | 840 | **1074 (+28%)** | 839 | 825 |
| 16384 | 1319 | **1713 (+30%)** | 1313 | 1304 |

End-to-end: **−7…−9% extend throughput** on TP-only NVFP4 MoE serving at >=8k-token extend batches (dp-attention configs stay under the bucket per rank and are unaffected).

## Fix

One **EXTEND-shaped** autotune dummy forward at warmup:

- **Sized to `max_prefill_tokens`** (÷ `dp_size` under dp-attention) — the scheduler's per-forward-batch extend-token budget, i.e. the largest shape the kernels see; tuning there covers every smaller bucket. `chunked_prefill_size` would under-cover (it caps per-request chunks; chunks batch together up to `max_prefill_tokens`). Deliberately unbounded, no new knob: serving must survive a real forward at that exact shape, buffers are freed after the pass, and large-context configs are the ones whose workload lives in the big buckets. Disable via `--disable_flashinfer_autotune`.
- **Packed within the req pool**: the dummy batch is at most `req_to_token_pool.size` seqs × N tokens (e.g. 1024×16) via `_dummy_run(extend_num_tokens_per_req=...)` — per-seq attention metadata (e.g. triton `kv_indptr`) is sized to the req pool, so num_tokens 1-token seqs would crash configs with `max_prefill_tokens > max_num_seqs`. Also matches real chunked-prefill shapes. Autotune buckets key on num_tokens, so tuning results are unchanged.
- The dummy buffer set skips the `(num_tokens, vocab)` fp32 logits buffer (>10 GB at 16k tokens) since autotune runs with `skip_logits`.
- Speculative-decoding runners are skipped for now (`_dummy_run` forces TARGET_VERIFY shapes there); spec configs are a follow-up.

## Verification (GB300, Kimi-K2-arch NVFP4 MoE, tp4, flashinfer 0.6.15.post1, `batch_full` bench)

prefill extend tok/s (bs=1, n=3, IQR≈0):

| input_len | 0.6.13 | 0.6.15.post1 unfixed | 0.6.15.post1 + this PR |
|---|---|---|---|
| 4096 | 47,270 | 47,357 | 48,473 |
| 8192 | **53,155** | **48,957 (−7.9%)** | **53,401 (+0.7% vs 0.6.13)** |
| 16384 | **51,946** | **47,877 (−7.8%)** | **51,349 (+0.4%)** |

decode_long@8192 +9.6%, saturated-throughput +9.3% (ttft −17%) vs unfixed; numerics unchanged (wikitext / long-decode ppl identical to 4 digits across versions). The packed dummy (1024×16) validated end-to-end on a config with `max_num_seqs=1024, max_prefill_tokens=16384` that crashed with the unpacked shape.
