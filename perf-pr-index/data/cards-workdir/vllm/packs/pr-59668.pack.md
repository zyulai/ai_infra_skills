## Overview

On ROCm, the DeepSeek V4.1 decode candidate mask goes from four kernels per consumer indexer layer to one. The flags kernel is folded into `_mask_candidates_strided_kernel` (added in [#56628](https://github.com/vllm-project/vllm/pull/56628)), and the int64 cast and `zeros_like` before it are dropped. No existing PR does this; [#57859](https://github.com/vllm-project/vllm/pull/57859) touches the same code, see Details.

## Claims

- The decode candidate mask is 1.06× to 2.50× faster on MI355X (not counting the two removed elementwise kernels, about 9.6 µs more per call).
- Mean TPOT -0.48% and throughput +0.44% end to end on MI355X, over 12 sweep points.
- Masking within `[0, end)` is unchanged, and GSM8K accuracy is unchanged within error.

## Details

Each consumer layer (4 per decode step) masked its decode logits with four kernels:


| kernel                            | source                                                               | µs per call |
| --------------------------------- | -------------------------------------------------------------------- | ----------- |
| `direct_copy`                     | `visible.to(torch.int64)`                                            | 4.4         |
| `FillFunctor<long>`               | `torch.zeros_like(visible)`                                          | 5.2         |
| `_candidate_flags_kernel`         | clears all `nblocks + 1` flags per row, then scatters the candidates | 8.7         |
| `_mask_candidates_strided_kernel` | masks `[0, end)` from the flags                                      | 4.1         |


The flags kernel clears the whole row, however short the live context. The two elementwise kernels only build an all-zero starts tensor and an int64 copy of `seq_lens`, and the Triton kernels need neither.

`_mask_candidates_strided_kernel` now builds its own flags. Each row's tiles are handed out round-robin to its programs, and each program clears the flags of its own live tiles, scatters the candidates that land in them, and masks. Nothing past the live context is cleared. On AMD, `tl.debug_barrier()` only waits for LDS traffic, so a store wait goes before each barrier and the flags are read with `.cv`. The wait is `s_waitcnt vmcnt(0)` on gfx9, `s_waitcnt_vscnt` on gfx11 and `s_wait_storecnt` on gfx12, since gfx10+ count stores separately. The tile is 2048 columns below 64 rows and 4096 from 64 rows up. It depends only on the row count, so the grid stays fixed under FULL CUDA graphs. Stores now stop at `end` instead of the next 1024-column boundary.

At the decode call site, the int64 cast, `zeros_like` and `repeat_interleave` are replaced by `None` starts, the int32 `seq_lens` and `row_repeat`, as on the CUDA path. This applies to both the mask and the select paths.

**Limitations.** The tile sizes were tuned on gfx950 only. gfx942 runs in CI but was not benchmarked. The gfx11 and gfx12 store waits were checked in the compiled ISA only, since no RDNA hardware was available.

## Existing PRs and interaction with #57859

I searched vllm-project/vllm PRs (open and closed) for the kernel names, "candidate flags / mask / fuse", `zeros_like` and `row_repeat` with ROCm. No PR fuses the flags and mask kernels or removes these two elementwise kernels. [#56628](https://github.com/vllm-project/vllm/pull/56628) (merged) added the strided decode mask that this PR builds on and kept the separate flags kernel. [#57859](https://github.com/vllm-project/vllm/pull/57859) (open) adds a candidate-only paged MQA scorer for gfx950 decode and edits the same code.

- **Its fast path skips the mask.** On gfx950, consumer layers with `compress_ratio == 1`, `next_n == 1`, no `requires_padding` and a page size that is a multiple of the candidate block size score only the candidate columns. Top-k then runs on the compact buffer, so no mask kernel runs. In that case, which probably covers the four V4.1 consumer layers in decode without speculative decoding, this PR's fused kernel doesn't run.
- **Its dense fallback still has what this PR changes.** The fallback keeps `repeat_interleave`, `.to(torch.int64)`, `zeros_like`, then select or mask. It is used by:
  - the candidate source layer, which always takes this path because the fast path requires `candidate_write` to be false, so removing the cast and zero-fill still saves two kernels per step there;
  - gfx942, `next_n > 1`, padded decode and `compress_ratio != 1`;
  - `rocm_paged_mxfp4_indexer.py`, which calls the strided mask directly.
- **As posted, #57859 reverts code on** `main`**.** Its diff deletes `_mask_candidates_strided_kernel` and `_apply_candidate_mask_strided` (from #56628), so its fallback goes back to the shared full-width `_apply_candidate_mask`. It also deletes the C4A Triton paged-MQA decode path, the native top-512 gate in `_get_aiter_top_k_kernel` and `FP8_DTYPE`. `rocm_paged_mxfp4_indexer.py` still imports `_apply_candidate_mask_strided`, so merging as-is would break that import. This is most likely a stale branch (last updated 2026-09-23) and needs a rebase.
- **Merge order.**
  - If this PR lands first, #57859's rebase should keep `_apply_candidate_mask_strided` in its fallback and adopt the `None` starts and `row_repeat` call. The conflict is in the same `if candidate_blocks is not None:` block.
  - If #57859 lands first, this change moves into its `else:` branch.
