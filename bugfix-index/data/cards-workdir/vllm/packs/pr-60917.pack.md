## 正文(PR 描述)

Fix https://github.com/vllm-project/vllm/issues/58599, https://github.com/pytorch/test-infra/issues/8931

### What's wrong

The MiniMax fused allreduce+RMSNorm kernel needs each GPU to read the other GPUs' memory directly. To set that up, every GPU allocates a buffer, gets a small 64-byte "IPC handle" for it, and sends that handle to the other GPUs. They then use it to open the buffer.

vLLM converted the handle to bytes and back through its .reserved field. In cuda-bindings 13.4 (part of cuda-python), NVIDIA removed that field from cudaIpcMemHandle_t, so the code now fails with:
AttributeError: 'cuda.bindings.runtime.cudaIpcMemHandle_t' object has no attribute 'reserved'


When that happens, vLLM falls back to the slower non-fused path, and test_minimax_reduce_rms_qk fails. It shows up in the torch-nightly CI lane because that environment installs cuda-bindings 13.4.x.

### The fix

Copy the 64 handle bytes through handle.getPtr(), the handle's memory address, using ctypes. Every cuda-bindings version supports it, so no version check is needed.

_ipc_handle_to_bytes(handle) reads the 64 bytes out of a handle.
_ipc_handle_from_bytes(raw) creates a new handle and copies the 64 bytes into it.
The fix is limited to vllm/model_executor/layers/minimax_rms_norm/lamport_workspace.py.


### Test plan
pytest tests/kernels/core/test_minimax_reduce_rms.py::test_minimax_reduce_rms_qk -k "2-"
Before: fails with the AttributeError above and logs "Falling back to the eager allreduce".
After: 6 passed, 12 skipped (the 4- and 8-GPU cases, since there are only 2 GPUs). The fallback message is gone, so the fused path runs.
