## Purpose

On ROCm, Kimi-K3 MLA decode runs the per-layer query preparation and the KV-cache
write as separate launches:

1. `vllm::concat_and_cache_mla_kernel` — the fp8 KV-cache write
2. `triton_poi_fused__to_copy_cat_clamp_mul_reciprocal_view_0` — the
   `[ql_nope | q_pe]` concat and that query's static fp8 quant

This collapses both into a single AITER `fused_qk_rope_concat_and_cache_mla`
launch: **288 → 144 kernel launches and 1351.8 → 682.8 µs (1.98×) per rank over
6 decode steps**, i.e. **9.39 → 4.74 µs per MLA layer per decode step** on
MI355X at TP=8.

Kimi-K3 MLA is NoPE (`mla_use_nope`), while that kernel always applies RoPE and
takes the cos/sin caches as required arguments. It is fed an **identity rotation**
(`cos = 1, sin = 0`) so the rotation degenerates to a no-op — the same approach
ROCm/ATOM uses to route K3 through this kernel.

The identity cache is a **single row**. AITER's per-head and `_opt` decode kernels
clamp `pos` into `[0, cos_cache.size(0))` before indexing, so real positions pass
straight through; a full-length constant cache would otherwise cost ~268 MB at
K3's `max_position_embeddings` of 1 048 576 to express a provable no-op. AITER's
*general* decode kernel does **not** clamp, so the layer refuses
the head counts that would select it (`kv_lora_rank * num_heads < 2048`, i.e.
≤3 heads/rank, reachable at TP=32).

## Scope, and why this is small

This is a **kernel-count / device-time optimization on the MLA decode path**. The
two replaced kernels are a sub-1% slice of a decode step, on 24 MLA layers in a
model that is roughly 1:3 MLA:KDA. End-to-end serving throughput improvement is below 1%

## Relationship to #47757 and #57452

**This supersedes #57452**, which I opened for the same optimization and will
close in favor of this one. That PR stacked on #47757: it carried #47757's six
commits so CI could run, and extended its hook in the shared
`MLAAttention.forward_impl`, also touching
`vllm/model_executor/layers/mla.py`. Two problems with that shape:

- it could not merge until #47757 did, and it is still under review
- it modified shared MLA code, so every MLA model and backend was in the blast
  radius of a Kimi-K3-only optimization

This PR drops both. It touches **no shared code at all** — only
`vllm/models/kimi_k3/amd/` — mirroring the vendor-local q/kv RMSNorm fusion that
the same wrapper already owns (#52494, merged). Consequences:

- no dependency on #47757, so CI runs standalone and this can merge in any order
- zero blast radius: no other model, backend or platform can be affected
- it is a **single file** — the AITER call lives directly in the K3 wrapper

#47757 remains complementary: it fuses the **sparse** MLA path (deepseek_v32)
through the shared hook, while this fuses the **dense** Kimi-K3 path inside the
vendor wrapper. Different call sites, no conflict in either merge order.

**Updated after review** (thanks @Rohan138) — the fused call is no longer a
registered custom op, the `torch.compiler.is_compiling()` guard is gone, and the
branch now lives directly in `forward()` instead of a helper returning `None`.
That folded the separate ops module away, so this is now one file. All numbers
below were re-measured on the refactored code.

On `is_compiling()`: the baseline's `triton_poi_fused…` kernel comes from
`mla_decode_concat_quant_fp8` compiling its own `forward_native` (class docstring
at `mla_attention.py:1541`), not from the model being compiled — Kimi-K3 is not
`@support_torch_compile`. The guard was dead code.

### Why not a duplicate

- **#47757** — same kernel, sparse MLA on deepseek_v32; this is the dense K3 path

- **#55230** — same kernel family, DeepSeek-R1, edits shared `layers/mla.py`.

- **#52494** (merged) — the sibling q/kv RMSNorm fusion in this same wrapper.

## Implementation

One file, `vllm/models/kimi_k3/amd/mla.py`, on the existing K3 wrapper:

- **`_fused_qk_prep_supported()`** resolves everything fixed at load time —
  platform, KV-cache dtype, shapes, DCP/PCP/HiSparse, head padding, and which
  `W_UK` variant is live. Evaluated once in `__init__`.
- **`_fused_decode()`** mirrors `MLAAttention.forward_impl`'s `W_UK` dispatch
  *including its precedence* (fp4 before fp8; both flags can be set at once) so
  `ql_nope` is bit-identical to what the unfused path feeds its concat+quant,
  then issues the fused call and continues through `impl.forward_mqa` and
  `_v_up_proj`.

With the static gating hoisted into `__init__`, the only per-batch condition left
in `forward()` is that the batch is **decode-only**. Everything else takes the
stock `MLAAttention` path, unchanged:

- any batch that is not purely decode (the fused call covers only the MQA slice,
  so a mixed batch's prefill rows would never reach the KV cache)
- **DCP** (the kernel skips `slot < 0` rows, which would then be garbage after the
  query all-gather), **PCP** and **HiSparse** (both rewrite the KV inputs/slots
  before the standalone write, which this path bypasses)
- the fp8-bmm and AMX `W_UK` variants, and any `q_pad_num_heads` head padding
- profile/dummy runs, an unallocated KV cache, or a missing slot mapping
- non-ROCm, non-fp8 KV cache, or head counts that would select AITER's
  non-clamping general decode kernel

## Results

### 1. Decode kernel census — two kernels become one

Rank-0 torch profile, 6 engine steps, 24 MLA layers, `144 = 24 × 6`:

| kernel | baseline | fused |
|---|---:|---:|
| `vllm::concat_and_cache_mla_kernel` | 144 (668.0 µs) | **0** |
| `triton_poi_fused__to_copy_cat_clamp_mul_reciprocal_view_0` | 144 (683.8 µs) | **0** |
| `aiter::fuse_qk_rope_concat_and_cache_mla_kernel` | 0 | **144** (682.8 µs) |

**288 → 144 launches, 1351.8 → 682.8 µs = 1.98×.**
Per MLA layer per decode step: **9.39 → 4.74 µs**.

Dispatch lands on AITER's `_opt` decode kernel rather than `per_head` —
`per_head` requires `kv_cache.size(1) == 1` and vLLM derives 1536 here. The `_opt`
gate is `kv_lora_rank × num_heads ≥ 2048`; at TP=8 that is 512 × 12 = 6144.
`_opt` is also the position-clamping kernel the single-row identity cache needs.

### 2. GSM8K — no accuracy regression

Full 1319 questions, 5-shot, `temperature=0, top_p=1`, `max_tokens=4096`,
chat template applied:

| arm | strict-match | flexible-extract | stderr |
|---|---:|---:|---:|
| fused | **0.9545** | 0.9553 | 0.0057 |

### 3. E2E serving — unchanged within noise

ISL 1024 / OSL 8192 C=1|8|32 one repeat showed TPOT p50 (ms), ITL p50 (ms), ITL p90 (ms), out tok/s for Conc 1 and 8 are flat to within 0.2%. Conc 32 moves ~0.7% in the baseline's favor, having moved ~1% the other way before the refactor — same essential code, opposite sign, so nothing is claimed in either direction.

This is the expected outcome. The fusion removes a sub-1% slice of a decode
step's device time; for scale, `cross_device_reduce_2stage` alone is ~46% of
rank-0 decode device time in the same trace.
