## 正文(PRD / 提案全文)

## Summary

Profiling **Step-3.7-Flash** (`Step3p5` MTP drafter, `num_speculative_tokens=2`) on H100 shows the GPU **idling on the host during the MTP draft phase** — `Self CPU time ≈ Self CUDA time`, and ~25% of the decode timeline is GPU-idle-waiting-for-kernel-launch (nsys `GAP_PERCENTAGE`/`LONG_GPU_WAITING_FOR_KERNEL_LAUNCH`). A torch profile attributes it to a swarm of tiny host-driven ops per step (`aten::copy_` ×12.7k, decomposed RMSNorm, MoE dispatch) around the draft loop.

**Root cause:** the draft *forwards* are already CUDA-graphed (`set_forward_context(cudagraph_runtime_mode=…)`), but inside the multi-step draft loop (`llm_base_proposer.py` ~L657–712, `step3p5.py` L385–440) **each speculative step reconstructs attention metadata on the host** via `build_per_group_and_layer_attn_metadata → metadata_builder.build_for_drafting(...)`, plus per-step position/slot-mapping recompute. That host-side construction serializes CPU↔GPU *between* the graphed forwards and starves the GPU.

## Why the existing fast path doesn't apply

`constant_draft_positions=True` (Gemma4, `gemma4.py:47`) skips the per-step rebuild, but its docstring states it assumes *all draft steps predict from the same position*. **MTP is sequential** — `step3p5._update_positions_dependent_metadata` advances `positions + 1` and recomputes slot_mappings each step — so the rebuild is currently **required for correctness**. The fast path is not applicable to sequential MTP/EAGLE drafting.

## Proposal — persistent, in-place drafting attention metadata

Make the whole draft loop GPU-side and full-cudagraph-capturable *even under dynamism* by reusing the pattern main-decode already uses (persistent metadata buffers updated in place):

1. **Pre-allocate** the drafting attention-metadata object + its tensors once at max padded shape (persistent input/hidden/position/slot_mapping buffers already exist).
2. Per draft step, **update the metadata tensors in place on GPU** (`positions += 1`, recompute `slot_mapping` via the existing kernel, adjust `seq_lens`) instead of constructing a new metadata object on the host.
3. **Absorb dynamism** (rejected tokens, variable seq_lens) via pad-to-max + `PADDING_SLOT_ID` masking (already partially present).
4. **Capture the draft loop under full cudagraph** so the graphed forwards fire back-to-back with no host stall between them.

New backend hook, alongside `build_for_drafting`:
```python
def update_for_drafting_inplace(self, md, common_attn_metadata, draft_index) -> None: ...
```
implemented first for **FlashAttention-3** (the backend Step-3.7 uses), then extendable to other backends.

## Expected impact

Removes the per-step host metadata rebuild + copies from the critical path → the GPU stops waiting during MTP. (The separate ~32% TP all-reduce cost seen on H100-**NVL** is a *topology* issue — custom all-reduce is correctly disabled on bridged-pair GPUs; it disappears on NVSwitch H100 — and is out of scope here.)

## Scope & correctness

Cross-backend (start with FA3). **Correctness-critical** — spec-decode failures are silent, so validation must confirm **mean acceptance length is unchanged** (~2.28 for this config) and output parity vs. the current path, before this leaves draft.
