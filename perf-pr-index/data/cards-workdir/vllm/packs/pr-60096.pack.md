## Overview

DeepSeek-V4 MegaMoE (also used by Kimi-K3) loads the routed experts into loader-side parameters, then `finalize_weights` asks the `DeepGemmMegaMoEBackend` (#58053) to transform them into DeepGEMM's layout and drops the loaded parameters, so any later `load_weights` has nowhere to write. The fused shared expert is built the same way, from a shared MLP whose weights the fusion then takes over.

This PR moves the layout into load time. The backend is selected when the experts are constructed, registers the kernel-layout tensors as the parameters (`create_weights`), and writes each checkpoint shard straight into them (`load_weight`). Whether the shared expert is fused is also decided at construction. Loading, reloading and updating weights then write into the tensors the kernel reads, and there is no MegaMoE post-load step left: `finalize_weights`, `finalize_mega_moe_weights` and the post-load hooks that only called them are removed (DeepSeek-V4 keeps its mHC hook).

## Claims

- `reload_weights` works with MegaMoE. DeepSeek-V4-Flash GSM8K after a reload: `main` 0.948 → 0.008, this PR 0.951 → 0.948.
- DeepSeek-V4.1 (MXFP8 shared expert) keeps its fused shared expert across a reload: `main` 0.898 → 0.010, this PR 0.904 → 0.901.
- An identity reload changes no parameter and moves no storage (0 of 1588 per-rank checksums, DeepSeek-V4-Flash TP2).
- The shared expert has no second copy: its four kernel tensors are the parameters (DeepSeek-V4-Flash TP2: 76.6 GiB, same as `main`).
- Kimi-K3 drops its `finalize_weights` override and the `_mega_l*` buffers.

## Details

**Backend interface.** #58053's `transform_weights` / `transform_shared_expert_weights` / `supports_shared_experts(deep_gemm)` become:
- `create_weights(layer, ...)`: register the routed (and fused shared) parameters in the kernel layout, indexed by local expert on dim 0 (EPLB moves experts along it);
- `load_weight(dst, src, shard_id, is_scale)`: write one checkpoint shard into one expert slice or a shared parameter;
- `supports_shared_experts(shared_experts)`: decide fusion at construction.

A post-load transform cannot coexist with in-place weight updates, because it replaces the storage the loaders write into. A backend with a different layout (e.g. an SM90 plugin) expresses it in `create_weights` and `load_weight`. Out-of-tree backends written against #58053 need this migration.

**SM100 layout.** DeepGEMM's `transform_weights_for_mega_moe` interleaves gate/up rows in groups of 8 and permutes scale rows for UTCCP; the L2 weight is unchanged. Each row of each shard lands at a fixed position, so `load_weight` copies a shard into a strided view of its final location:
- L1 gate row `r` → `(r // 8) * 16 + r % 8`, up row `r` → `(r // 8) * 16 + 8 + r % 8`.
- Scales are the UE8M0 bytes expanded to one per 1x32 block, packed four along K per int32, stored MN-major, with the UTCCP row map `128b + 32j + i → 128b + 4i + j`.

Routed FP4 parameters are int8 (the kernel's dtype) instead of uint8; loads reinterpret the bytes.

**Shared expert.** Fusion requires FP8 shared weights with UE8M0 scales that tile to 1x32 (checked on the shared MLP's parameters, which its quant method creates at init) and a DeepGEMM with the shared-expert API. Otherwise it warns once and keeps the separate shared MLP, as on `main`, but at construction instead of after loading, so the layout never changes after load. When fused, `DeepseekV4MoE.shared_experts` is `None` and `load_weights` routes `shared_experts.*` tensors to the experts' four kernel-layout parameters.

**Backend selection.** The backend is selected for the device the model is built on, or for the worker's current GPU when that is `meta` (`--load-format ipc_cache`).

**Scope.** EPLB with a reload after a rebalance is broken on `main` and is not addressed. XPU keeps its own implementation.

**Not a duplicate.** #59003 (draft, stacked on #53509) also targets MegaMoE reload, but by staging new checkpoint sources and re-packing into buffers through a reload lifecycle. This PR removes the packed copy: the parameters are the kernel tensors, so there is nothing to stage or rebuild.
