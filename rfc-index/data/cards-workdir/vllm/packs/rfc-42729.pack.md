## 正文(PRD / 提案全文)

### Motivation.

The `/render` endpoints (`POST /v1/chat/completions/render` and `POST /v1/completions/render`) landed in PR #36166 as the preprocessing leg of disaggregated serving. They accept a standard OpenAI request and return a`GenerateRequest` that the GPU inference tier can consume directly without a tokenizer.
unif
After generation, the inference server (`/inference/v1/generate`) returns a `GenerateResponse` containing raw output token IDs, along with logprob entries encoded as `"token_id:N"` placeholder strings because the generate server has no tokenizer. To turn that into a client-facing OpenAI response, we need to:

1. Detokenize the output token IDs back into text
2. Resolve `"token_id:N"` logprob placeholders into real token strings
3. Populate the `bytes` field in logprob entries (required by the OpenAI spec, cannot be filled by the tokenizer-free generate server)
4. Format the result as a `ChatCompletionResponse` or `CompletionResponse`

Currently this postprocessing is coupled to `OpenAIServingChat` /`OpenAIServingCompletion` inside the GPU server. Operators running llm-d, Dynamo or any other disaggregated setup are forced to either run the full vLLM stack on the CPU tier or implement postprocessing themselves.

This RFC proposes exposing the detokenization as `/derender` endpoints on the existing render server which is the direct inverse of `/render`. 

Detokenization is defined as a post processing step of `GPU-less deployment of frontend` in RFC #34407:

> "Allow preprocessing (tokenization, MM input processing) and **postprocessing (detokenization, tool call parsing, reasoning parsing)** to
> run without GPU."

This RFC in addition adopts that full definition as its goal: `/derender` is the inverse of `/render`. A true inverse must emit `reasoning_content` and `tool_calls`, not just `content` (ref: https://github.com/vllm-project/vllm/issues/42729#issuecomment-4592871058 and https://github.com/vllm-project/vllm/issues/42729#issuecomment-4621521435). Reasoning and tool call parsing are therefore **in-scope goals of this RFC** built on ~the unified `Parser` from RFC #32713 (its `extract_response_outputs(model_output, model_output_token_ids, request, ...)`~ (`Parser.parse()` for batch and `Parser.parse_delta()` for streaming, the same calls `/v1/chat/completion`s makes, so derender and chat serving parse the same way) is the single source of truth for decode side parsing). This functionality is for disaggregated / RL consumers who need `derender(tokens) -> content` today.

The work is phased as follows:
- **Detokenization** endpoint lands first. The protocol is made parsing ready now so the follow up requires no breaking API change. (#43606)
- **Reasoning/tool call parsing** (non-streaming), built on the unified `Parser`. ~#45045~ Superseded by and landed in **#45919**.
- **Streaming derender + streaming parsing** is specified in the companion RFC #47161. Detokenization landed in #47301 and reasoning/tool parsing in #50550.

Partial #34407 and #22817.

#### New Endpoints

| Method | Path | Input | Output |
|--------|------|-------|--------|
| `POST` | `/v1/chat/completions/derender` | `DerenderChatRequest` | `ChatCompletionResponse` |
| `POST` | `/v1/completions/derender` | `DerenderCompletionRequest` | `CompletionResponse` |

Both endpoints:
- Run on the existing render server (`vllm launch render` PR #36166). No new process or server binary is needed
- Are GPU-free, only the `Renderer` (tokenizer) is required
- Are synchronous, stateless and idempotent. The caller already holds the complete `GenerateResponse` and therefore nothing to stream

#### Protocol Additions

Two new request types in `vllm/entrypoints/scale_out/token_in_token_out/protocol.py`:

```python
class DerenderChatRequest(BaseModel):
  stream: Literal[False] = False
  model: str | None = None
  generate_response: GenerateResponse  # output_mode="tokens" only (#58588)
  prompt_tokens: int | None = None
  prompt_token_ids: list[int] | None = None
  # GenerateRequest.token_ids from /render (a suffix is enough). Seeds
  # decoding so the first output token keeps its leading space (#59046).
  chat_request: ChatCompletionRequest | None = None
  # The request the client sent to /render, before adjust_request ran.
  # Carries the fields the chat parsers read (tools, tool_choice,
  # include_reasoning, chat_template_kwargs and model-specific fields).
  # Required when a reasoning or tool parser is configured (400 otherwise).
```

```python
class DerenderCompletionRequest(BaseModel):
    stream: Literal[False] = False
    model: str | None = None
    generate_responses: list[GenerateResponse]
    prompt_tokens: list[int] | None = None
    prompt_token_ids: list[list[int] | None] | None = None
     # GenerateRequest.token_ids from /render (a suffix is enough). Seeds
    # decoding so the first output token keeps its leading space (#59046).
    completion_request: CompletionRequest | None = None
    # Original request context. Used for skip_special_tokens. Completions
    # don't run reasoning/tool parsing.
```

`prompt_tokens` is caller-supplied because `GenerateResponse` does not carry the prompt token count (only output tokens per choice are stored). The caller already holds `GenerateRequest.token_ids` from the render step, so passing `len(token_ids)` costs nothing. This avoids a protocol change to `GenerateResponse`.

For completions, `generate_responses` is a list parallel to the `list[GenerateRequest]` returned by `/v1/completions/render`. If `prompt_tokens` is provided its length must equal `len(generate_responses)`. A mismatch will return `400 Bad Request`.

`chat_request` / `completion_request` are optional on the wire and the caller already holds them from the `/render` step, so passing them is free and requires no change to `GenerateResponse`. On a server with a reasoning or tool parser configured, chat derender returns `400` without `chat_request` rather than falling back to plain detokenization which would leak parser markup into `content` (#50550). `model` is optional (#51463). `chat_request` is the request as sent to `/render`. `/render` only returns the `GenerateRequest`, so derender never sees what `adjust_request` changed (see the `adjust_request` row below).

#### Implementation Details

##### Chat: `ServingDerender.derender_chat_response` → `OnlineDerenderer.derender_chat`

1. Validate model via `_check_model` and resource bounds (#47260)
2. If a reasoning or tool parser is configured and `chat_request` is missing, return `400`
3. For each choice: reject empty `token_ids` and resolve logprob placeholders
4. Decode incrementally, seeded from the prompt tail (`prompt_token_ids`), the same way the engine primes its detokenizer (#59046)
5. With a parser: decode with `skip_special_tokens=False`, build the parser with `chat_request.tools`, the resolved `chat_template_kwargs` and `model_config`, then run `Parser.parse()` over the text and `token_ids` to get `reasoning`, `content` and `tool_calls`. Without a parser: honour `chat_request.skip_special_tokens` and `spaces_between_special_tokens`
6. Build `ChatCompletionResponse` with `usage` from `prompt_tokens` and the output token counts. Pass `prompt_logprobs` and `kv_transfer_params` through unchanged

CPU work (detokenization, logprob resolution, parsing) runs on the renderer's executor (`renderer_num_workers`), off the event loop (#49396).

> [!NOTE]
> In a disaggregated setup the render tier must be launched with the same `--reasoning-parser` / `--tool-call-parser` / `--enable-auto-tool-choice` and chat template config as the would be chat tier or parity breaks regardless of protocol. This is a deployment/docs requirement and not a code one.

##### Completions: `ServingDerender.derender_completion_response` → `OnlineDerenderer.derender_completion`

Same pattern, iterating over `(generate_response, prompt_token_count)` pairs and emitting `CompletionResponseChoice` objects with an increasing `index` across all responses. Plain detokenization only.
