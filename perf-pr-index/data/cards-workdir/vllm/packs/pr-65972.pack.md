## 1. Why this change

Under data parallelism (DP), every DP rank pads its batch to the largest batch on any rank. The FlashInfer TRT-LLM **monolithic** MoE kernels are the default on Blackwell for block-FP8 and MXFP8 checkpoints. They route from the router logits themselves, so padded rows pick experts like real tokens, and the kernel loads and computes those experts.

`VLLM_MOE_SKIP_PADDING` (on by default) cannot help here. It works by having vLLM's routers write expert id -1 for padded rows, and the monolithic kernels never call vLLM's routers.

Padding under DP is large:
- In decode steps with up to 32 rows per rank, 34-65% of rows are padding.
- In mixed (prefill + decode) steps, 37-84% of rows are padding, because every rank pads to the rank running prefill.

## 2. What this PR changes

Under DP, the runner routes with vLLM's top-k, where padded rows get -1, and then calls the kernel's precomputed-routing op (`trtllm_fp8_block_scale_routed_moe`), which skips those rows. There is no new option: the existing `VLLM_MOE_SKIP_PADDING=0` turns it off (its doc comment now says so).

- `FusedMoEExpertsMonolithic.apply_precomputed_routing` and `supports_precomputed_routing`, implemented for TRT-LLM block FP8 and MXFP8 (`TrtLlmFp8ExpertsMonolithic`). The kwargs shared with the logits call move to one helper.
- `prepare_routed` for the NaiveDPEP monolithic prepare/finalize: it all-gathers top-k ids and weights instead of logits.
- `MoERunner` takes the routed path under DP.
  - Routers that do not mask padding themselves (`masks_padding` False, e.g. grouped top-k outside DeepEP v2) get the mask applied after top-k in the runner.
  - Routed-expert capture receives the gathered top-k ids, in the same layout as the monolithic kernel's `routing_replay_out`.
  - `routed_scaling_factor` is applied exactly once, as on the modular path: either by the router on the weights or by the runner on the output. The routed kernel call gets `None`.
- FlashInfer autotune tunes the op that runs. Under DP, the autotune cache key now records that the routed op is used, so a cache saved before this PR (which has only the logits op) does not hit and skip tuning. Only models with a MoE layer that can take the routed path get the new key; every other deployment keeps its key and its saved cache.

## 3. When the new path runs

Every MoE forward of the target model where all of these hold:
- Blackwell (SM100) with block-FP8 or MXFP8 MoE weights;
- DP > 1, either with EP and the default `allgather_reducescatter` all2all backend (DeepEP and other all2all backends use modular kernels and are unaffected), or without EP (the MoE layer is then TP-sharded across the DP ranks and always uses the naive DP all-gather, whatever the all2all backend);
- no EPLB and no sequence parallel;
- a routing method the TRT-LLM monolithic FP8 kernel supports;
- `VLLM_MOE_SKIP_PADDING` on (the default);
- the routing simulator (`VLLM_MOE_ROUTING_SIMULATION_STRATEGY`) off. The simulator works by feeding the kernel synthetic logits, so it keeps the logits op.

The decision depends only on DP size, so every DP rank takes the same path. This matters because the two paths dispatch different tensors in the all-gather.

| router | models | validation |
|---|---|---|
| softmax top-k (`FusedTopKRouter`) | Qwen3 MoE, Qwen3-Next / 3.5 / 3.8 FP8 | unit tests + serving (Qwen3.8-Flash-Next-FP8) |
| sigmoid + bias (`FusedTopKBiasRouter`, MiniMax2) | MiniMax-M2 / M3 | unit tests + serving (MiniMax-M3-MXFP8) |
| grouped top-k (`GroupedTopKRouter`, DeepSeekV3 routing) | DeepSeek-V3/R1, Kimi-K2, GLM-4.5+ FP8 | unit test vs the kernel's own grouped routing + serving (GLM-5.3-FP8, DP8 + EP) |

**No size threshold.** The top-k launch is a fixed cost per MoE layer. A threshold on batch size would leave out mixed steps, which are the most padded, and would need tuning per model. The cost of having none is on small-expert models at high concurrency (Qwen3.8-Flash-Next, section 4.2): some large decode steps are slower, while throughput stays within noise. A FlashInfer-side padding mask would remove the top-k launch: flashinfer-ai/flashinfer#9000. The runner could then pass the mask instead.

### 3.1 Why only under DP + EP, not TP

**In short:** TP pads almost nothing, so the top-k launch has nothing to save. Forcing the path on under TP4 gives no throughput gain (table below), so it runs only with DP. All DP measurements in this PR are DP + EP; DP without EP also takes the path but is not measured here.

How much of the MoE input is padding. For each step: padded rows / all rows the MoE layers process, summed over DP ranks (TP has one), i.e. 1 - real tokens / (DP ranks x padded batch per rank). Averaged over the steps of Baseline serving runs. Steps are grouped by kind and by the padded batch per rank:

| step kind | DP4 / DP8 (Qwen, M3, GLM) | TP4 (Qwen, M3) |
|---|---|---|
| decode, <=32 rows | 34-65% | 0-0.4% |
| decode, 33-512 rows | 11-22% | 2-5% |
| mixed (prefill + decode) | 37-84% | 4-16% |

In the kernel table (section 4.3), the top-k path loses at 0% padding and only breaks even around 20%.

To check, I forced the same path on under TP4 (a local patch, not in this PR) with MiniMax-M3-MXFP8, which has the largest experts of the three models and so is the best case for this path. Each side was launched twice. Measured on an earlier base (871147447b); the TP path is unchanged since.

## 4. Measured results

Summary:
- **Higher serving throughput for large-expert models under DP + EP:** GLM-5.3-FP8 (DP8) +9% / +26% / +27% at concurrency 8 / 16 / 64; MiniMax-M3-MXFP8 (DP4) +13% / +4% / +5% at concurrency 4 / 16 / 64. Both runs better at every concurrency for both models.

Those buckets are 18% and 16% of step time.
- **Accuracy unchanged** on all three router types (softmax top-k, sigmoid + bias, grouped top-k).
- **No gain without DP:** forcing the path on under TP4 does not change throughput beyond noise (section 3.1), so it runs only under DP.
- **Opt-out:** `VLLM_MOE_SKIP_PADDING=0` restores main's behavior on this path. It also turns off padding skip on the modular MoE paths, as it already does on main.

Terms:
- **Baseline** = upstream main at this PR's base commit; **After PR** = this change.

- **Rows per rank** = the padded batch size per DP rank.
- Each side was launched twice. **(both runs better)** / **(both runs worse)**: both After PR launches beat (or lost to) both Baseline launches. **(within noise)**: the two sides' values interleave.

**Why small experts gain less.** The new path adds vLLM's top-k, a fixed 5-15 us per MoE layer. It saves the padded rows' work:
- at small batches, the experts that only padded rows select;
- at large batches, the padded rows' GEMM rows.

Mixed steps under DP are mostly padding (37-84% of rows across the three models), because every rank pads to the rank running prefill.
- GLM-5.3 (38M-parameter experts) and MiniMax-M3 (57M) save far more than the top-k costs.
- Qwen3.8-Flash-Next (4.9M parameters, 512 experts) saves little per row. Its large decode steps are only 11-22% padding, so there the top-k launch costs more than it saves.

Frontier models deployed with DP + EP have experts of 25-66M parameters (DeepSeek-V3/V4, Kimi-K2/K3, GLM-5, MiniMax-M3, Qwen3.8-2.4T), i.e. the GLM / M3 side.

### 4.4 Autotune cache key

Qwen3.8-Flash-Next-FP8 DP4 with autotune on: main and this PR write different cache directories (`153f2d40…` vs `a4700ae6…`). This PR's cache holds entries for the routed op (top-k id/weight inputs) as well as the logits op, which the draft model's MoE layer still uses (below); main's holds only the logits op. After upgrading, a DP deployment of a block-FP8 / MXFP8 TRT-LLM MoE model retunes once at its first start; other deployments keep their key.

## 5. Limitations

- Only block-FP8 / MXFP8 TRT-LLM monolithic experts. NVFP4 monolithic is not selected under DP + EP; the NVFP4 modular kernel is, and the modular path already uses vLLM's routing and masks padding. FP8 per-tensor, BF16 and MXFP4 keep the kernel's routing.
- DP without EP takes the same path (same padding, same all-gather, TP-sharded experts) but is not measured in this PR.
- Small-expert models: large decode steps are slower (Qwen3.8-Flash-Next +6% to +13% at concurrency 64 / 256), with throughput within noise. `VLLM_MOE_SKIP_PADDING=0` turns the path off, together with padding skip on the modular paths.
- Draft-model forward passes do not mark padding (the forward context has `is_padding` only under PCP), so MoE layers in MTP drafters keep the kernel's own routing, as on main.
- GLM-5.3-FP8 runs with FlashInfer autotune off on both sides: with autotune on, main crashed at startup on this config in earlier tests (illegal memory access in the TRT-LLM routing kernel during the autotune dummy runs); this is pre-existing and tracked separately.

## 6. Not a duplicate

I searched open PRs for padding / monolithic / routed MoE / precomputed routing.
- #50759 (draft) masks padding in vLLM's routers, i.e. the modular path; it does not reach the monolithic kernels. The only overlap is masking padding after top-k for routers that cannot fuse it; this PR does that inline in the runner's routed path.
- #54109 (DeepEP v2 padded format) and #57946 (b12x padding sentinel) are other paths.
