## Motivation
The fused bf16→fp8 KV cache write kernel (launch_reshape_and_cache_flash) was only enabled on the unified-attention path (use_triton_unified_attention). On the standard aiter path (read via paged_attention_ragged), FP8 KV writes fell back to set_kv_buffer, which performs a separate divide + cast + store_kvcache — i.e. extra elementwise kernels and intermediate DRAM traffic per K/V per attention layer.

The KV write only produces the fp8 cache and is independent of the attention read path, so the fused kernel can be reused for the standard path as well. This PR broadens the fused write to the standard aiter prefill/decode FP8 path and fixes a latent scale-correctness gap.

## Modifications
python/sglang/srt/layers/attention/aiter_backend.py:

Decode (forward_decode): relax the fused-write gating from use_triton_unified_attention and kv_cache_dtype == fp8 to kv_cache_dtype == fp8 and not use_mla, so the standard (non-unified) aiter path also uses launch_reshape_and_cache_flash instead of set_kv_buffer.
Prefill (forward_extend): add the same fused write for the non-SWA, non-MLA FP8 case (previously this path used the naive set_kv_buffer).
Correctness: pass k_scale/v_scale to launch_reshape_and_cache_flash. The existing decode FP8 branch (#23620) omitted them, which is only correct when the KV descale is 1.0; passing them keeps non-unit descales correct.
MLA is explicitly excluded (not use_mla) and keeps its own KV write path.

## Accuracy Tests

### Kernel-level (fused write vs naive set_kv_buffer)
Compared the reused fused write against the naive set_kv_buffer path (per-tensor descale = amax/fp8_max), checking both the written cache slots and fp8 contents:

| Case                   | fused vs fp32-divide ref | fused vs naive-bf16 mismatch | mean abs err vs fp32 ref (fused / naive) |
| ---------------------- | ------------------------ | ---------------------------- | ---------------------------------------- |
| decode  [32, 1, 256]   | 0.0000% (bit-identical)  | ~1.7%                        | fused ≤ naive                            |
| prefill [8000, 1, 256] | 0.0000% (bit-identical)  | ~2.5%                        | fused ≤ naive (fused slightly closer)    |

### End-to-end (before vs after, standard aiter FP8 path)
To isolate "FP8 KV quantization itself" from "this change", I compared the pre-change naive `set_kv_buffer` write against the fused write on the same standard aiter path. The pre-change naive FP8 write is not directly runnable on ROCm (`set_kv_buffer` → `store_cache` raises `BufferError: float8 types are not supported by dlpack`), so for the baseline I bypassed `store_cache` to use the naive scatter write — identical numerics, only a different store mechanism.

GSM8K, Qwen3.5-397B-A17B, TP8, full 1319 questions, 5-shot, greedy:

KV / FP8 write | gsm8k (1319) | invalid
-- | -- | --
naive set_kv_buffer FP8 (before) | 93.1% | 3.4%
fused FP8 write (this PR)         | 92.9% | 3.7%
bf16 KV (full-precision ref)      | 94.2% | 2.1%

naive vs fused differ by 0.2pp, and fp8 vs full-precision bf16 by ~1.3pp
(decode is bit-identical at the kernel level). So the small gap comes from FP8 KV
quantization itself, not from this change.

+def _naive_bf16_write(k, v, k_cache, v_cache, loc, k_scale, v_scale, fp8_dtype):
+    """Naive reference: bf16 in-place divide -> fp8 cast -> scatter."""
+    ck = k.clone()
+    cv = v.clone()
+    ck.div_(k_scale)
+    cv.div_(v_scale)
+    k_cache[loc, 0] = ck.to(fp8_dtype)
+    v_cache[loc, 0] = cv.to(fp8_dtype)

+def _fp32_divide_write(k, v, k_cache, v_cache, loc, k_scale, v_scale, fp8_dtype):
+    """Fused-kernel reference: fp32 divide -> fp8 cast -> scatter."""
+    k_cache[loc, 0] = (k.float() / k_scale.float()).to(fp8_dtype)
+    v_cache[loc, 0] = (v.float() / v_scale.float()).to(fp8_dtype)
