## 正文(PR 描述)

## Summary

Two related bugs prevent `--tp N --ep M --enable-lora --lora-backend triton --moe-runner-backend triton` from running on any MoE model with per-expert LoRA adapters; both reliably crash in the first forward pass with `CUDA error: an illegal memory access was encountered`. This PR fixes both and adds unit coverage.

### Bug 1 — `LoRAMemoryPool` sizes per-expert buffers for the global expert count

`FusedMoEWithLoRA` allocates LoRA A/B buffers via `LoRAMemoryPool`, whose per-expert shape was `[num_loras, num_global_experts, ...]`. Under EP, however, `StandardDispatcher` remaps `topk_ids` from global → local IDs *before* the MoE kernel (see `python/sglang/srt/layers/moe/token_dispatcher/standard.py`), so both the base MoE weights and the LoRA delta kernels are indexed with IDs in `[0, num_local_experts)` plus a `-1` sentinel. A LoRA buffer sized `[..., 128, ...]` being indexed with local IDs `[0, 32)` therefore reads the wrong expert's weights (or, combined with bug #2, triggers the illegal access).

### Bug 2 — `moe_lora_align_block_size` doesn't filter the `-1` sentinel in one branch

`_count_and_sort_expert_tokens` only rejected `expert_id >= num_experts`:

```cpp
for (size_t i = tid; i < numel; i += stride) {
  int32_t expert_id = topk_ids[i];
  if (expert_id >= num_experts) { continue; }      // <-- no `< 0`
  ...
  int32_t rank_post_pad = atomicAdd(
    &cumsum_buffer[(model_offset * (num_experts + 1)) + expert_id], 1);
  sorted_token_ids[max_num_tokens_padded * model_offset + rank_post_pad] = i;
}
```

`-1` passes that guard and produces:
- `atomicAdd(&cumsum_buffer[model_offset * (num_experts+1) + (-1)], 1)` — OOB write (negative stride), and
- `sorted_token_ids[offset + rank_post_pad]` with a garbage `rank_post_pad`.

Both sibling call sites in the same file already guard `expert_id < 0 || expert_id >= num_experts`. This PR makes the third call site consistent.

## Changes

- **`python/sglang/srt/lora/mem_pool.py`**
  - Capture `(moe_ep_size, moe_ep_rank)` and `moe_use_local_expert_ids` at pool init. The latter is `True` iff `moe_ep_size > 1` **and** the active runner remaps to local IDs (Triton/DeepGEMM/Marlin) — the check is skipped for runners that keep global IDs (FlashInfer CUTLASS / CuteDSL / TRTLLM-routed), so their buffers stay globally-keyed.
  - Size per-expert LoRA buffers by `num_local_experts` (`get_lora_A_shape` / `get_lora_B_shape`).
  - Route all four per-expert load paths in `load_lora_weight_to_buffer` through a new `_iter_local_expert_weights(weights)` helper that filters and remaps global → local expert IDs for both `dict` and 3D-tensor inputs, then zeros unowned/unloaded slots.
  - No-op for pure TP and for runners that keep global IDs — verified by the TP-only LoRA unit tests, which still pass unchanged.

- **`python/sglang/jit_kernel/csrc/lora/moe_lora_align_kernel.cu`**
  - Add `expert_id < 0` to the guard in `_count_and_sort_expert_tokens`, matching the two other call sites; adds a comment explaining the sentinel contract with `StandardDispatcher`.

- **`test/registered/unit/lora/test_mem_pool_ep_unit.py`** (new, 22 cases, hermetic CPU-only)
  - `_get_num_experts` covering `num_experts`, `num_local_experts`, `n_routed_experts`, and fallbacks.
  - `_get_num_local_experts` under no-EP / EP=1 / EP=4 and uneven splits.
  - `_global_to_local_expert_id` ownership filter.
  - `_iter_local_expert_weights` for dict and 3D-tensor inputs, with correct remapping under EP.
  - `LoRAMemoryPool.__init__` EP-context capture for no-EP, Triton+EP, and FlashInfer+EP.

## Compatibility

- **Pure TP (any `--tp`, no `--ep`)**: `moe_ep_size == 1` → `moe_use_local_expert_ids == False` → buffers and iteration are identical to pre-fix behavior. Verified end-to-end with `--tp 2` + LoRA.
- **Pure EP**: per-rank buffers and remapping via `_iter_local_expert_weights`.
- **Mixed TP + EP**: same as pure EP — TP slicing already happened when the base model loaded; the LoRA fix only affects the expert dimension.
- **FlashInfer CUTLASS / CuteDSL / TRTLLM-routed**: `_moe_runner_keeps_global_expert_ids()` returns `True`, `moe_use_local_expert_ids` stays `False` → buffers stay globally-keyed, matching what those runners expect.
- **Non-LoRA paths**: untouched.
