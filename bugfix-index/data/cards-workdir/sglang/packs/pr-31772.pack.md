## 正文(PR 描述)

## Motivation

Loading LLaDA2 on NPU with the FRACTAL_NZ weight cast enabled roughly doubles MoE weight memory, and on a 64 GB 910B3 the server fails to start at all.

`LLaDA2MoeModelLM.load_weights` ended by building `self.routed_experts_weights_of_layer` from `LLaDA2MoeSparseMoeBlock.get_moe_weights()`, which snapshots `x.data` — a separate Tensor object sharing the Parameter's storage — for every expert weight. That snapshot is taken *before* `process_weights_after_loading` runs, so when the NZ cast rebinds `weight.data` to the newly allocated NZ tensor, the map still holds a handle on the ND storage and its refcount never reaches zero. Every MoE weight then stays resident in both layouts.

Verified by walking the referrer graph during a real model load: immediately after the cast, exactly one live tensor still shares the pre-cast storage — same shape, not a Parameter, reachable from the dict key `routed_experts_weights_of_layer`.

For LLaDA2.0-mini (19 MoE layers, w13 1 GiB + w2 0.5 GiB each) that pins an extra 28.5 GiB. Measured on TP1 / 910B3 with the CI test's config (`--mem-fraction-static 0.9`, NZ cast on):

| | weights | load time | result |
|---|---|---|---|
| before | 59.03 GB | 73.9 s | `ValueError: loaded weights leave no GPU memory for the KV cache` |
| after | 30.45 GB | 38.4 s | KV cache 628736 tokens, server starts, GSM8K 0.93 |

The LLaDA2-mini CI test has been masking the symptom with `SGLANG_NPU_DISABLE_ACL_FORMAT_WEIGHT=1`, which also gives up the NZ kernel's speedup.

## Modifications

**1. Build the map lazily (`models/llada2.py`)**

Wrapped `routed_experts_weights_of_layer` in `LazyValue`, deferring it until EPLB actually asks for it — which is after weight processing. This matches the existing pattern in `qwen3_moe.py` and `sdar_moe.py` (and `deepseek_v2.py`, which exposes it through a property). The dict comprehension and its filters are unchanged; only the evaluation point moves.

This also fixes a latent correctness bug that is not NPU-specific: with the eager build, any backend whose `process_weights_after_loading` rebinds `weight.data` left the map pointing at storage the model no longer uses, so EPLB expert relocation would have written into dead tensors. Built lazily, the map aliases the live post-processing weights.

**2. Drop the kill switch from the CI test (`test/registered/ascend/basic_function/dllm/test_npu_llada2_mini.py`)**

With the OOM fixed, `SGLANG_NPU_DISABLE_ACL_FORMAT_WEIGHT=1` is unnecessary and the NZ cast is re-enabled. An aligned single-denoise-iteration profile on LLaDA2.1-mini (decode trajectories verified identical, 556 device kernels and 38 GroupedMatmul calls per side, identical input shapes) shows the cast is also a small win at the kernel level:

| | ND | NZ | |
|---|---|---|---|
| MoE GroupedMatmul | 8305.9 us | 7697.8 us | 1.08x (38/38 calls faster) |
| whole-step kernels | 13308.2 us | 12736.0 us | 1.045x |

NZ dispatches to `aclnnGroupedMatmulWeightNz` instead of `aclnnGroupedMatmulV5`, and no `TransData` appears, so there is no runtime format-conversion penalty.

The whole `env` override is removed rather than just the one key: it replaced `GSM8KAscendMixin.env` wholesale, so the test was also running without the mixin defaults (`PYTORCH_NPU_ALLOC_CONF`, `HCCL_BUFFSIZE`, and the rest). That was *not* the cause of the OOM — both runs in the table above had `PYTORCH_NPU_ALLOC_CONF` unset — just an unrelated papercut fixed in passing.

## Note

`bailing_moe.py` and `sarvam_moe.py` still build this map eagerly and have the same latent issue. They are left alone here since I have no way to validate a change to them.
