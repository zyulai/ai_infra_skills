## PR body
```markdown
## Summary

- encode ordinary video outputs with H.264/AAC in one FFmpeg pass instead of writing a silent video and remuxing it
- use pinned CPU memory for the existing materialization path
- on supported Linux/CUDA MP4 paths, copy directly into a CUDA-registered memfd that FFmpeg consumes, avoiding an intermediate pageable CPU tensor
- reuse one shape-aware registered buffer (capped at 1 GiB), select a bounded x264 thread count, and retain the existing imageio implementation as the compatibility fallback

## Scope and compatibility

The direct path is used only for CUDA tensors on Linux when the request:

- writes MP4
- does not request frame interpolation or upscaling
- does not need decoded frames returned to the caller

Unsupported configurations and runtime failures fall back to the existing materialized/imageio path. Audio remains AAC-encoded and requests without audio retain the existing behavior.

## Performance

For a representative 124-frame 1344x768 H.264/AAC output:

- previous path: 1.591 s median
- registered-memfd path: 0.621 s median
- speedup: 2.56x

The resulting H.264/AAC output was validated by complete decode.

- `19 passed` in the output-saving and output-materialization unit suites
- pre-commit passed for both changed files
- public diff is limited to the output helper and its unit tests
```
