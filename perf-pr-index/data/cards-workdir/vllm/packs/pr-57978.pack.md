## Purpose

`_expand_page_indices_kernel` in the AITER MLA backend is launched with a grid
of one program per request, and each program walks that request's tokens in a
serial loop:

```python
_expand_page_indices_kernel[(num_reqs,)](...)

    req_idx = tl.program_id(0)
    for i in tl.range(0, num_tokens, BLOCK_SIZE):
```

The parallelism is therefore entirely over the batch. That is fine at high
concurrency and degenerates at low concurrency: with `num_reqs == 1` a **single
workgroup** expands the whole sequence while the rest of the GPU idles. The
bug is invisible in the regime it was presumably tuned for.

On a long-context decode workload (MI355X, TP8, ~97k-token context, conc=1)
this measured **61.6 µs per call and 7 calls per model step — 0.431 ms, or
1.23% of a 34.9 ms step**. For scale, 97k int32 stores is ~388 KB, well under
a microsecond of HBM bandwidth. The kernel is not bandwidth-bound; it is
serialised.

This affects **any MLA model on ROCm at low concurrency**, not one model in
particular.

## The change

Add a second grid dimension over token chunks and drop the loop, so each
program handles exactly one `BLOCK_SIZE` chunk:

```python
num_chunks = max(1, cdiv(block_table.shape[1] * kernel_block_size, 1024))
_expand_page_indices_kernel[(num_reqs, num_chunks)](...)
```

The arithmetic, the masks and the stores are unchanged — only the iteration
space is mapped onto the GPU instead of onto one workgroup. The chunk count is
derived host-side from the block table width, an upper bound on tokens per
request, so **no device synchronisation is introduced**; over-launched
programs mask out entirely and cost nothing.

## Test plan

**Bit-exactness against the existing serial kernel.** Both versions built from
source and compared on device — this is an index computation, so a wrong value
does not crash, it silently reads the wrong KV:

```
conc=1 long context, kbs=1    97000 indices identical
conc=1 long context, kbs=16   97000 indices identical
exact multiple of 1024         4096 indices identical
1024+1                         1025 indices identical
1024-1                         1023 indices identical
ragged 4 reqs                 38011 indices identical
kbs=16 ragged tail             4212 indices identical
single token                      1 indices identical
```

Cases cover chunk boundaries, ragged multi-request batches, and
`kernel_block_size > 1`.

**6.8× faster.** Identical call counts on both sides, so this is the same work

### Concurrency sweep — does the extra grid dimension cost anything?

Requested during review: the win above is at conc=1, where one workgroup walked
the whole context. At higher concurrency `num_reqs` already supplies
parallelism, so the question is whether the second grid dimension costs
anything there.

The kernel grid-strides rather than partitioning, so a grid width of 1
reproduces the pre-PR launch exactly. "Before" below is therefore the same
kernel launched the old way, not a reimplementation. Width is this PR's
launch-site formula, `num_chunks = max(1, cdiv(block_table.shape[1] * kernel_block_size, 1024))`
(an upper bound on tokens per request read from the block-table width, so
it needs no device sync; at `kernel_block_size=1` this gives 375 / 64 / 8 / 1
for the contexts below). MI355X, 256
CUs, `kernel_block_size=1`, `BLOCK_SIZE=1024`, median of 7 reps x 100
iterations on an idle node. Output compared byte-for-byte at every width and
shape; all agree.

| 1 024 | 256 | 1 | 10.59 | 10.76 | 0.98x |
| 8 192 | 64 | 8 | 10.73 | 10.74 | 1.00x |
| 8 192 | 256 | 8 | 10.78 | 10.74 | 1.00x |
| 65 536 | 1 | 64 | 16.59 | 10.75 | 1.54x |

**No shape regresses.** The lowest ratio anywhere is 0.98x, on shapes sitting
at a ~10.7 µs floor where run-to-run spread is around ±2%. At 1k context the
width is 1, so the launch is bit-identical to before and those rows measure
noise rather than a change.

Ragged batches are the case worth checking explicitly, since
`num_token_blocks` comes from `max_seq_len` over the whole batch — one long
request widens the grid for every short request too, launching programs that
find nothing to do:

| batch | width | before µs | after µs | ratio |
|---|---:|---:|---:|---:|
| 1x384k + 7x1k | 375 | 115.60 | 10.86 | 10.64x |
| 1x384k + 63x1k | 375 | 115.67 | 13.80 | 8.38x |
| 1x65k + 127x512 | 64 | 16.62 | 10.74 | 1.55x |
| 8x65k + 56x1k | 64 | 17.01 | 10.80 | 1.58x |

The widened grid costs nothing measurable: 63 short requests at width 375 still
come out 8.4x ahead, because the programs with no work exit immediately.

Ratios converging to 1.00x at the high end (65k/256) are the expected
behaviour rather than a cost — the "before" side has enough requests to fill
the machine on its own. These remain kernel microbenchmarks; at high
concurrency this kernel is a small share of the step, so the table is here to
show the change does not cost anything there, not to claim a win.

### End-to-end context

The kernel runs 3 times per step on current main, so the 0.057 ms it saves is
about **0.24%** of a 23.40 ms step. That is below what a 1200 s conc=1 arm can
resolve, and it is the honest ceiling for this change on this configuration.

Earlier end-to-end arms are included for completeness, but should **not** be
read as the effect size:

| build | | interactivity p90 | tpot p90 | step time |
|---|---|---:|---:|---:|
| A | baseline | 110.28 | 0.00907 | 34.01 ms |
| A | this PR | 112.06 (+1.61%) | 0.00892 | 33.45 ms |
| B | baseline | 140.97 | 0.00709 | 26.59 ms |
| B | this PR | 142.75 (+1.27%) | 0.00701 | 26.29 ms |

Both figures exceed what the kernel can physically save, so they are
noise-dominated at this effect size — a 1200 s conc=1 arm carries roughly 1%
run-to-run spread, against a ceiling here well under that. A third arm on
current main measured −0.35%, which is the same noise in the other direction.
The kernel measurement above is the reliable signal; these rows are not.

Worth noting why the end-to-end impact shrank across builds: the per-call cost
is essentially unchanged (23.3 µs then, 22.4 µs now), but upstream reduced the
call count from 6 per step to 3. The serialisation this PR removes is the same;
there is simply less of it to remove than there was.

**Accuracy** is unaffected by construction — the page indices are bit-
identical, so the model reads exactly the same KV. Confirmed anyway with
GSM8k over the full 1319 questions: 0.9659, unchanged.
