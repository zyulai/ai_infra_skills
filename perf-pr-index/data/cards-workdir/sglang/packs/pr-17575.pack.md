## Motivation

The `HashRing::new` method in `src/core/worker_registry.rs` previously performed $N \times 150$ heap allocations using the `format!` macro to generate virtual node keys. For a cluster with 1,000 workers, this resulted in **150,000 temporary string allocations** during a single registry update, leading to significant allocator pressure and non-deterministic latency spikes.

## Modifications

* Updated `HashRing::new` in `src/core/worker_registry.rs` to use the incremental `blake3::Hasher::update` API.
* Replaced `format!("{}#{}", url, vnode)` with direct byte updates to the hasher:
* `hasher.update(url_bytes)`
* `hasher.update(b"#")`
* `hasher.update(&(vnode as u64).to_le_bytes())`


* This approach eliminates all temporary heap allocations within the virtual node loops.
