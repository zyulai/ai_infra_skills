## Summary

`dequantize_and_gather_k_cache_cutedsl` launched `grid = (num_reqs, 1024)`. The SWA call gathers 128 rows per request and the compressed call ~1k rows, so most of the 32k CTAs did no work; measured effective bandwidth was 0.35–2.4 TB/s on GB200 (8 TB/s HBM). `grid.y` is now picked per call from the launch shape.

## Where this kernel is hot: batch-invariant (deterministic) serving

The kernel came in with vllm-project/vllm#42236, which profiled **prefill** — one request, thousands to 262k rows per launch. At that shape a fixed `grid.y = 1024` is close to optimal, and this PR changes nothing there (table below). The shape that is badly served by a fixed grid is **many requests × few rows each**, and that is exactly what batch-invariant DSv4 decode produces on every step. Four things in `DeepseekV4FlashMLAAttention` combine to put this kernel on the BI decode critical path:

1. **BI decode has to use the sparse kernel, and only the sparse path gathers.** `_forward_decode` dispatches on `VLLM_DS4_DECODE_KERNEL`. The `paged` path calls `flash_mla_with_kvcache` straight on the paged cache and never touches this kernel; its KV split comes from the in-kernel planner (`tile_scheduler_metadata` / `num_splits`), which plans over the whole batch, so the reduction order moves with batch composition. The `sparse` path instead materializes compressed KV and SWA KV into a dense workspace with two `dequantize_and_gather_k_cache` calls per layer and feeds `flash_mla_sparse_fwd`. So with `VLLM_BATCH_INVARIANT=1` + `VLLM_DS4_DECODE_KERNEL=sparse` this kernel runs **84 times per decode step**, where the non-BI (`paged`) configuration runs it zero times per decode step. The cost measured below is a cost that only the BI arm pays.

2. **BI decode is one token per request.** The BI branch requires `query_len == 1` for every request and pins `max_gather` to `window_size` (128). A decode step is therefore 32 requests × 128 rows — 4096 rows spread over 32×1024 = 32768 CTAs with the old grid. Measured 18.9 µs for work that takes 3.0 µs.

3. **BI replaces the batch maximum with model capacity, so the caller's row bound stops being informative.** Outside BI, `max_compressed` is the batch max of `seq_len / compress_ratio`. Under BI it must be `ceil(max_model_len / compress_ratio)`, otherwise the flattened KV stride and every request's base index depend on its neighbours' lengths and a request would not land at the same addresses alone and in a packed batch. For the compressed gather that makes `out.shape[1] - offset` = 262272 while the real work is ~1k rows per request. This is why `ceil(max_rows / 4)` alone cannot pick the grid in this configuration and the total-CTA cap is the term that actually binds.

4. **BI prefill runs one request per chunk.** The grouped prefill chunk plan picks workspace dimensions and offsets from all requests in a chunk, so BI mode puts each request in its own chunk to keep N, M, gathers, indices and launch geometry dependent on that request alone. Prefill launches therefore arrive as many `num_reqs = 1` calls rather than a few batched ones.

Net effect on the configuration we run (DSv4-Flash-Base, GB200 DP8/EP8, `VLLM_BATCH_INVARIANT=1`, sparse decode): **1.66 ms → 0.51 ms of gather per decode step**. This is one of three kernel-side changes (#18, this, #20) that together take BI=1 from −10.8 % to +1.3 % output throughput against the best BI=0 run at 256 concurrency.

`grid.y` is now a runtime `Int32` kernel argument, computed per call in the wrapper:

```
grid.y = max(1, min(ceil(max_rows / 4), ceil(8192 / num_reqs)))
```

Two terms, both measured rather than assumed:

| term | what it does | dropping it costs |
|---|---|---|
| `ceil(max_rows / 4)` | one row per warp is all the parallelism a request can use; a CTA has 4 warps | 32-request SWA decode 3.1 → 18.7 µs (**6.1×**), because grid.y would stay 1024 |
| `ceil(8192 / num_reqs)` | hold the whole grid near 8192 CTAs, where measured throughput plateaus at every request count | 1-request 262144-row gather 67.7 → 276.1 µs (**4.1×**) if the first term is capped low enough to serve decode; 32-request decode 10.8 → 21.9 µs (**2.0×**) if it is not |

`max_rows` is the caller's upper bound on rows per request (`out.shape[1] - offset`). The public signature is unchanged — the grid is no longer a compile-time property of the kernel, so one compiled variant serves every launch shape.

The 8192-CTA plateau was found by sweeping grid.y per shape with the same interleaved harness as the tables below: single-request gathers keep improving up to 8192 CTAs (262144 rows: 71.0 µs at 1024, 69.9 at 4096, 67.9 at 8192), 4-request prefill peaks at 2048 per request (11.4 → 9.7 µs), and 32-request decode peaks at 256 per request — all three are the same total.

This supersedes the first version of this PR (compile-time `grid.y = clamp(ceil(max_rows/4), 1, 128)`), which made single-request gathers of 16k–262k rows — the prefill / full-context shapes exercised by vllm-project/vllm#42236 — up to 3.9× slower than the original grid (262144 rows: 275 vs 70 µs).

## Numerics

Each CTA does exactly the same per-row work as before; only the row→CTA assignment changes. Every case in the shape sweep is `torch.equal` to the old kernel and to the Triton reference for every `grid.y`.

E2E gate (DSv4-Flash-Base, GB200 DP8/EP8, `VLLM_BATCH_INVARIANT=1`, cudagraph `FULL_DECODE_ONLY`, together with #18): **512/512 bitwise vs the previous kernel** (g0 vs baseline), run-to-run r1/r2/r3 pairwise 512/512, batch-invariance and prefill/decode rescore gates bitwise.
