## 正文(PR 描述)

## Purpose

Since #59645, `cooperative_topk` crashes with `cudaErrorIllegalAddress` when a row of 64K columns or more contains more NaNs than `top_k` (e.g. 1% of a 256K row, or a fully-NaN row). NaN scores can reach decode top-k during warmup and CUDA-graph capture, where the indexer reads uninitialized KV blocks (see the note in `candidate_blocks.py`). Before #59645 such rows produced garbage indices; now they take down the process.

**Root cause.** nvcc compiles the integer expression `bits | 0x80000000u` in `convert_to_uint32_v2` as the FP operation `-|x|`:

```
ISETP.GE.AND P0, PT, R2, RZ        // bits >= 0 ?
FADD R10, -|R2|, -RZ               // "bits | 0x80000000u" emitted as -|x|
@P0 IMAD.MOV.U32 R9, RZ, RZ, R10
```

That is bit-exact for finite values and ±inf, but FADD canonicalizes NaN to `0x7FFFFFFF`, which is the ordered key of -0.0. The FP16 coarse bins put NaN above +inf (bin 1023), so the two orderings disagree. When NaNs overflow the threshold bin, the exact recovery takes the single-key path with a -0.0 pivot. Every positive score then counts as "above" it, and the unchecked append in `collect_exact_candidates` writes past `s_topk` (compute-sanitizer: invalid `__shared__` write in `unbounded_round0_single_key`).

**Fix.** Read the bits through an opaque `mov.b32`, so the key stays bit-exact and NaN orders above +inf in both the coarse and exact keys, matching `torch.topk`.
