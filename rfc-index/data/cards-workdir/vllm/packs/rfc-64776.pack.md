## 正文(PRD / 提案全文)

### Motivation.

**I (@algebra-MCX) propose to integrate Single Batch Overlap (SBO) for the DeepEP low-latency path, once the required kernel arguments exist upstream, and to lead the vLLM-side implementation and validation, subject to maintainer feedback.** This revisits [#34963](https://github.com/vllm-project/vllm/issues/34963) (closed as stale) and the prototype [#29211](https://github.com/vllm-project/vllm/pull/29211) (closed as abandoned because it depended on two unmerged forks). This issue records what has changed, what is still blocking, and a vLLM-side plan that does not pin a fork.

SBO targets decode batches that are too small for DBO to pay off (the crossover studied in [#64100](https://github.com/vllm-project/vllm/issues/64100)). With one batch there is no second microbatch to hide the all-to-all. SBO instead lets the DeepEP LL combine start sending each expert's rows as soon as the down GEMM has finished them, coordinated through a shared signal tensor.

#### Current vLLM behavior

At `dc4dd5a2217bc757232e9fa4d8a8b59e207ca068`, without DBO, on an async prepare/finalize (DeepEP LL, NIXL EP):

| Phase | Current behavior | Overlap |
| --- | --- | --- |
| Dispatch | [`_prepare`](https://github.com/vllm-project/vllm/blob/dc4dd5a2217bc757232e9fa4d8a8b59e207ca068/vllm/model_executor/layers/fused_moe/modular_kernel.py#L1276-L1306) calls the receive hook immediately | none |
| Expert down GEMM | [`fp8_m_grouped_gemm_nt_masked`](https://github.com/vllm-project/vllm/blob/dc4dd5a2217bc757232e9fa4d8a8b59e207ca068/vllm/model_executor/layers/fused_moe/experts/batched_deep_gemm_moe.py#L471) finishes completely before combine starts | none |
| Combine | [`_finalize`](https://github.com/vllm-project/vllm/blob/dc4dd5a2217bc757232e9fa4d8a8b59e207ca068/vllm/model_executor/layers/fused_moe/modular_kernel.py#L1457-L1488) sends, runs shared experts (`MK_INTERNAL_OVERLAPPED`), then receives | shared experts |

So the shared-expert half of SBO already exists. The missing part is down GEMM ↔ combine send.

#### Upstream kernel status (checked 2026-10-30)

| Component | Status |
| --- | --- |
| DeepEP `main` (`f6aa38fe06`, 2026-10-21) | no `src_signals` / signal-aware combine |
| DeepEP [#249](https://github.com/deepseek-ai/DeepEP/pull/249), [#388](https://github.com/deepseek-ai/DeepEP/pull/388) (computation/communication overlap) | open, conflicting |
| DeepGEMM `main` (`5081f8513a`, 2026-10-20) | masked GEMM has no signal output |
| DeepGEMM [#183](https://github.com/deepseek-ai/DeepGEMM/pull/183) (SBO: down GEMM with combine send) | open, conflicting |
| SGLang | ships its own packaged forks (`sgl-deep-ep`, `sgl-deep-gemm`) whose `low_latency_combine` takes `overlap`, `src_signals`, `src_signal_expect_value` |

vLLM's DeepEP LL integration does not depend on these forks, and #29211 showed that pinning forks is not a mergeable path.

### Proposed Change.

**Phase 0 – kernels (prerequisite, outside vLLM).** Help land a signal-aware LL combine and a signal-producing masked FP8 grouped GEMM upstream (DeepEP #249/#388, DeepGEMM #183 or successors). vLLM work does not start merging until a released upstream version exposes them.

**Phase 1 – vLLM, opt-in, Hopper, DeepEP LL + DeepGEMM masked FP8.**

1. Capability check, no fork pin: enable SBO only when the installed DeepEP/DeepGEMM expose the signal arguments; otherwise keep today's path unchanged. Opt-in flag, default off.
2. Per layer step, allocate a zeroed `int32` signal tensor of `num_local_experts × ceil(max_tokens_per_rank / block_m)` from existing workspace (graph-capturable, no per-step `torch.zeros`).
3. Down GEMM runs with `num_sms - comm_sms` SMs and increments the signal per finished block; combine is launched on the existing aux stream with `overlap=True`, waits on a start event, and sends rows whose signal reached the expected value.
4. Shared experts move to the dispatch window (between dispatch send and receive hook), because the combine window is now taken by the down GEMM.
5. DBO interaction: a step uses either DBO or SBO, never both. The first version disables SBO whenever the step is microbatched.

Out of scope for phase 1: NIXL EP (`nixl_ep` 1.5 has no signal argument), FlashInfer CuteDSL / Blackwell (the #34963 path), DeepEP HT/v2, BF16 masked GEMM.

#### Completion criteria

- [ ] Upstream DeepEP and DeepGEMM releases expose the signal interfaces; vLLM requires no fork.
- [ ] With SBO off or unsupported, the code path and outputs are unchanged.
- [ ] Unit tests: capability detection, signal sizing, SM split, shared-expert placement, DBO exclusion.
- [ ] DeepSeek-V3/R1 FP8, DP/EP decode on H200: identical outputs/logprobs with SBO on and off; FULL CUDA graph capture and replay.
- [ ] `vllm bench serve` TPOT/throughput, plus a trace showing combine sends overlapping the down GEMM, across batch sizes below and around the DBO crossover.
