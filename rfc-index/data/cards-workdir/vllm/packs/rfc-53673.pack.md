## 正文(PRD / 提案全文)

## Motivation

vLLM supports context parallelism for the target model (PCP, #25749, and DCP), but speculative decoding currently assumes the drafter uses the same parallel mapping as the target. Two in-flight PRs take different approaches to PCP + MTP:

- #53427 (@pisceskkk) keeps the target PCP-sharded but runs a fully replicated drafter on every PCP rank over the global batch. This is simple and works for any drafter with no PCP awareness, at the cost of repeating long-prefill draft compute and KV writes on every rank.
- #53653 (@GirasoleY) keeps the MTP draft prefill PCP-sharded, restoring global order only at sampling boundaries. This performs better on long prefills and supports the GLM-5.2 sparse-MLA path, but each speculative method needs its own PCP adaptation.

We probably want both eventually:

1. A drafter that hasn't implemented PCP/DCP (ngram, DSpark, EAGLE, suffix decoding, new methods) should still work when the target uses context parallelism, by consuming the global batch.
2. A drafter that has a sharded implementation (MTP today) should run sharded and skip the redundant compute.

The same question comes up for DCP: e.g. Kimi K3 (MLA, so DCP makes sense for the target) paired with a GQA draft model. There it probably makes sense to disable DCP for the draft model, since GQA already shards KV heads across TP and DCP would just add latency.

We already let the draft model diverge from the target config in some places: `draft_tensor_parallel_size` (draft TP=1 under target TP=N), and the per-draft `moe_backend` / `attention_backend` overrides in `SpeculativeConfig`. This RFC proposes generalizing that into a separate drafter parallel config so we don't accumulate ad-hoc per-method special cases in the model runner.

## Proposed Change

Give the draft model its own parallel config instead of implicitly inheriting the target's: `SpeculativeConfig` grows a `draft_parallel_config` (subsuming the existing `draft_tensor_parallel_size` field), where each parallelism size is initially restricted to 1 or the target's value. Defaults are per-method (e.g. MTP inherits the target's PCP size; methods without a sharded implementation default to 1) and can be overridden via `--speculative-config`. A drafter validates the config it is handed at startup and fails with a clear error if it can't execute it.

Note this does not mean different process groups or rank placement. The drafter still runs on the same ranks as the target; a draft size of 1 just means that group is treated as replication for the drafter, the same way draft TP=1 under target TP=N works today. No new distributed groups are needed.

## Alternatives considered

- Replicated-only (#53427 alone): simplest and works for every method, but gives up long-prefill draft perf and scales draft KV memory with CP size.
- Sharded-only (#53653 alone): best perf where implemented, but every drafter has to be individually adapted to PCP before it works at all, so new and niche speculative methods would silently lose CP support.
- Arbitrary drafter parallelism (any TP/CP/EP per draft model with its own process groups and rank placement): much bigger change to distributed init and scheduling, and nothing on the table needs it. The proposed config keeps the drafter on the target's ranks and restricts each size to 1 or the target's value, and we can relax this later if a use case shows up.

## Open questions

1. CUDA graph support: #53427 validates PIECEWISE (with #53515); #53653 currently requires eager. What do we commit to for each path, and should supported graph modes depend on the drafter parallel config?
2. Should the global-vs-sharded choice ever be dynamic (e.g. global for short-prefill batches, sharded for long), or is a static per-run choice enough?
3. Sparse-MLA indexer: #53653 distinguishes PCP-expanded target slot mappings from replicated-draft mappings. Does that distinction belong in the attention backend interface or the PCP manager?
4. Does the scheduler need to know the drafter's effective CP degree for token budgeting, or can this stay contained in the runner?
