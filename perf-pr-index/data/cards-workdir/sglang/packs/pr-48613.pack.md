## PR body
```markdown
With `--mamba-ssm-dtype bfloat16`, run the fused CuTe-DSL KDA target-verify kernel instead of falling back to Triton.
The default (`--mamba-ssm-dtype float32`) is unchanged: on an FP32 state the patched kernel is bitwise identical to the
current one.

## Motivation

With `--mamba-ssm-dtype bfloat16`, Kimi-K3.1 DFLASH decode loses the fused CuTe-DSL KDA target-verify kernel
(`fused_kda_decode_mtp_dspark`, the `nv_cutedsl` verify backend):

- `KDAAttnBackend._can_run_dspark_cutedsl_mtp` returns False for any state that is not FP32, and the wrapper raises on
  one. The kernel `cp.async`'s the state with an FP32 128-bit copy atom into FP32 shared memory and stores the
  `intermediate_ssm` snapshots as FP32.
- The next candidate, `_can_run_fused_chain_verify` (`SGLANG_OPT_FUSED_KDA_VERIFY`, off by default), is FP32-only too.
- So every KDA layer of every verify step falls back to `causal_conv1d_update` (Triton) +
  `fused_sigmoid_gating_delta_rule_update_kernel` (Triton) + a separate gated RMSNorm, because the output norm is
  fused only into the CuTe kernel.

Under DFLASH the target model only runs TARGET_VERIFY, so this is the KDA path of every decode step.
Measured cost before this PR (details below):

- **Kernel:** per layer, the fallback takes 1.5–2.3× as long as the fused kernel on the same BF16 state. Over
  Kimi-K3.1's 69 KDA layers that is 0.7–2.9 ms more per decode step at 8–128 requests per rank.
- **Serving (1P2D, conc 72):** KDA kernel time per decode step is 3.31 ms on the fallback vs 0.84 ms fused (FP32
  state: 0.77 ms); throughput -0.9% (fallback) vs +0.4% (fused) relative to the FP32 state. See the A/B tables.

## Modifications

Two runtime files:

- `kernels/ops/attention/kda_decode_mtp.py` (the kernel):
  - The shared-memory state stage takes the state's dtype (`h0.element_type`).
  - The 128-bit `cp.async` copy atom moves 4 FP32 or 8 BF16 elements.
  - The shared-memory byte count scales with the dtype.
  - The recurrence is unchanged: it runs in FP32 registers, and BF16 values are widened on the smem-to-register load.
  - Only the `intermediate_ssm` snapshot store narrows to BF16 (compile-time branch; the FP32 store is unchanged).
  - The wrapper accepts FP32 or BF16 state with 16-byte-aligned slots (stride and offset in multiples of 4 FP32 / 8
    BF16 elements), and requires `intermediate_ssm` to have the state's dtype.
  - For an FP32 state the copy atom, layouts, shared-memory size and stores are the same as before.
- `srt/layers/attention/linear/kda_backend.py`: `_can_run_dspark_cutedsl_mtp` admits a BF16 state (8-element
  alignment) as well as FP32 (4-element alignment), and requires the snapshot cache to have the state's dtype.

There is no new flag or env var. With `--mamba-ssm-dtype bfloat16` the fused kernel is used under the same conditions
as for an FP32 state (CuTe-DSL verify backend, SM100/SM103, the DSpARK shape contract).

Tests (see **Tests**): new cases in `test/registered/kernels/ops/attention/test_kda_decode_mtp.py` (GPU) and
`test/registered/unit/layers/attention/test_mamba_track_state_dtype.py` (CPU).

Not changed:

- The ReplaySSM commit fold `kda_replayssm_exact_fold_kernel` (`commit_kda_replayssm_spec`) is already
  dtype-generic: it loads in FP32 and stores in the state dtype.
- Prefill, the conv state (already BF16) and the default FP32 path.

### Why it is faster

1. **One kernel instead of three per layer.** The fused kernel does the conv update, the gated delta-rule recurrence
   for all draft tokens, and the output gated RMSNorm. The fallback launches two Triton kernels plus the norm.
2. **Half the state bytes.** The verify reads each request's 12 × 128 × 128 state once. In BF16 that is 384 KB instead
   of 768 KB per request per layer, so the fused BF16 kernel is also 7–11% faster than the fused FP32 kernel at 32–128
   requests per rank (0–4% at 8).

### Memory

BF16 halves the bytes of a KDA state, and the state budget is set in bytes (`--mamba-full-memory-ratio`), so BF16
roughly doubles the number of state slots. Measured on the prefill worker (TP8/DCP8, `--mamba-full-memory-ratio 1.2`,
per GPU):

| | FP32 state | BF16 state |
|---|---:|---:|
| Device state slots (`max_mamba_cache_size`) | 440 | 852 |
| SSM state memory | 22.29 GB | 21.55 GB |
| Host (HiCache) state slots at `--hicache-size 100` | 971 (54.54 GB) | 1877 (54.51 GB) |

- On a decode worker (TP8/DCP8, `--max-running-requests 64`) the slot count is fixed by the running-request cap
  (80). BF16 frees 2.0 GB of SSM state per GPU, and the KV pool grows from 2.45M to 2.55M tokens (+4.2%).
- Host memory: a BF16 run with prefill `--hicache-size 120` failed at startup on one node. That node had
  55.3 GB free against a 65.4 GB host state-pool request per rank. FP32 runs requested the same 65.4 GB, because the
  HiCache size is split between KV and state by device-pool bytes; BF16 only doubles the slots within it. So this was
  a low-memory node, not BF16. All runs here use `--hicache-size 100`.
- This PR does not change any memory sizing.

## Limitations

- **Only the DSpARK/DFLASH target-verify path** (2–8 tokens per request, `_can_run_dspark_cutedsl_mtp`). Other KDA
  paths keep their current dtype support:
  - The single-token fused decode `kda_fused_decode` (JIT CUDA, `covered()` requires an FP32 state) stays FP32-only.
    It is not on the DFLASH decode path: the target model never runs DECODE mode there, and under
    `--enable-linear-replayssm-spec` it is disabled anyway.
  - `_can_run_fused_chain_verify` (`SGLANG_OPT_FUSED_KDA_VERIFY`, off by default) stays FP32-only.
- **SM100/SM103 only**, as before: the gate requires compute capability 10.x and the CuTe-DSL kernel.
- **The fused output norm** is still compiled for 12 heads per rank only (`_k3_fused_decode_args`), independent of the
  state dtype. With other head counts the fused kernel runs without it and the model applies the norm.
- **Shared-memory padding** is kept in elements (`TILE_K + p2_lanes`), so a BF16 row's padding is half as many bytes as
  an FP32 row's. The BF16 kernel is still faster than the FP32 kernel at every measured size, but bank conflicts of
  the BF16 smem-to-register load were not profiled.
- **Accuracy is GSM8K only.** Long-context (where state rounding accumulates over more tokens) is not measured beyond
  the 128-round kernel test.
