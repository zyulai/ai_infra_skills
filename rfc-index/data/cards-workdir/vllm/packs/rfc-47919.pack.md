## 正文(PRD / 提案全文)

## Summary

This RFC is intended to supersede the broad topology-aware KV cache compression framing in #38725 with a narrower, falsifiable vLLM integration target: a disabled-by-default topology policy for sparse MLA logical-token index selection.

The goal is not to introduce a new KV cache compression stack. The goal is to test whether topology-aware replacement of a bounded tail of an existing learned sparse-MLA `topk_indices_buffer` can improve sparse attention quality under the same budget, while preserving vLLM's current sparse MLA coordinate contracts and fail-closed behavior.

## Why this is materially different from #38725

#38725 proposes a broad topology-aware KV cache compression framework with lifecycle compression, directional pruning, NPU-oriented matrix operations, and expected memory/FLOPs gains.

This RFC narrows the surface to sparse MLA index policy only:

- topology object: sparse MLA logical request-local token indices, shape `[num_tokens, topk]`
- invariant: learned-token retention plus segment/witness coverage, optional barrier and diversity terms
- implementation rule: preserve a learned prefix and replace only a bounded tail with topology witnesses
- baseline: existing sparse MLA learned/top-k indices unchanged
- null models: same-budget random, locality, and learned-tail selectors
- fallback: disabled or unsupported paths return the original learned indices unchanged
- hot path: no Python loops or CPU sync in CUDA runtime paths without a separate benchmark gate

## Proposed contract

A topology index policy should satisfy these constraints before runtime wiring:

- disabled by default
- exact `torch.int32` 2D coordinate contract
- logical request-local token offsets, not physical cache slots
- `-1` sentinel padding preserved
- no duplicate selected logical tokens in the produced candidate set
- bounded structural replacement, never unbounded learned-token eviction
- dense or unmodified fallback on dtype, shape, device, budget, coordinate, or guard mismatch
- schedule construction time benchmarked separately from sparse attention execution
- quality guard based on relative L2, cosine similarity, KL, top-1 agreement, and next-token agreement

## Local screening evidence

These are screening-only local results, not a vLLM runtime speedup claim.

The seq64 run selected nonzero topology barrier/diversity and improved mean L2/KL versus the null models, but the prototype schedule cost erased speedup. The guard correctly rejected all sparse policies on relative L2/cosine, and for the topology policy also on speed/schedule overhead.

## Falsification gates before PR-ready runtime wiring

1. Unit tests for disabled passthrough, dtype/shape/device fallback, bounded replacement, learned retention, duplicate removal, padding layout, and coordinate bounds.
2. A CPU reference policy that produces the same 2D logical-token coordinate contract as sparse MLA.
3. A vectorized or kernel-side schedule path before any CUDA hot-path use.
4. `vllm bench` or sparse MLA backend benchmark comparing current sparse MLA, same-budget random, locality, learned-tail, and topology-index policy.
5. Quality gates: relative L2, cosine, KL, top1 agreement, next-token agreement, and task-level eval where applicable.
6. Observable counters: learned tokens retained, structural tokens inserted, fallback reason, and schedule-build time.

## Suggested first PR scope

A first PR should not wire this into runtime serving. It should add only:

- an isolated sparse MLA topology-index helper
- disabled-by-default config object
- explicit result/fallback object
- unit tests for the coordinate and fallback contract
- benchmark notes showing that current evidence is screening-only

That gives maintainers a small reviewable base before any kernel/runtime integration is proposed.
