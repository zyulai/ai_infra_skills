## Purpose

DeepSeek V4.1 selects attention tokens in two levels: one indexer layer publishes the top candidate blocks of the context, and the indexer layers after it pick their top-k inside those blocks. Today the consumer layers still score the **whole** context with dense MQA logits and then mask everything outside the candidates. DeepGEMM 2.8 ships sparse MQA-logits kernels (deepseek-ai/DeepGEMM#432) that score only a given list of blocks, so this PR lets the consumer layers score just the candidate blocks. Their logits work goes from O(context) to O(candidate blocks), a fixed 16K positions for V4.1-Flash, and their top-k runs in that compressed space and is mapped back to context positions.

Design:

- **A separate indexer, not a branch in the dense one.** The consumer layers use a new `SparseMQAIndexer` layer with its own backend and attention metadata (`DeepseekV41SparseIndexerBackend`, `DeepseekV41SparseIndexerMetadata`). It is a plain module rather than a custom op: V4.1 does not go through `torch.compile`, and the attention layer already runs the indexer inside its breakable-CUDA-graph eager segment. The dense `SparseAttnIndexer` op is untouched. The candidate-source layer and the indexers before it stay dense.
- **Every requirement is checked once, at engine start.** The metadata builder validates the model, the MXFP4 indexer cache, the GPU generation, the DeepGEMM version, the DeepSelect extension and the logits/top-k layout it needs, and raises a clear error instead of silently falling back per step. There is no PyTorch fallback anywhere on the path: the candidate expansion and the index remap are Triton kernels, the top-k is DeepSelect.
- **Nothing is allocated or recomputed on the hot path.** The builder owns the per-row scratch; the candidate-block expansion and the DeepGEMM schedule depend only on the candidates, which are identical for all consumer layers of a step, so the first consumer computes them and the others reuse them through the shared metadata.
- **No dtype casts on the hot path.** The sparse kernels take bf16 weights and emit bf16 logits. The fused Q RoPE-quant kernel that produces the per-head weights writes them in bf16 for this indexer (fp32 for the dense one), and DeepSelect (#56464) runs the top-k on the bf16 logits directly.
- **Opt-in** via `--attention-config '{"indexer_kv_dtype": "mxfp4", "indexer_sparse_logits": true}'`. Below ~16K tokens the candidates cover the whole context and the dense path is cheaper, so the default stays off; the feature is for long-context serving.
- **One KV-layout requirement.** DeepGEMM's paged kernels address pages as `base + page * stride` and need that stride 512B-aligned. In V4.1's block-major layout the stride is the whole block (all layers' pages), which is not 512-aligned. `MLAAttentionSpec` gains `block_stride_alignment`, and the block size is rounded up to it in the same place HiSparse already rounds it (`_get_kv_cache_bytes_per_block`). With the flag on this costs 0.8% of KV memory; with it off nothing changes.

## Requirements and limitations

- SM100-class GPUs, DeepGEMM >= 2.8 (the repo pin is older; the flag fails at startup with a clear message on older builds), the DeepSelect extension (`vllm._deepselect_C`, built with vllm) and the MXFP4 indexer cache (the kernels take UE8M0 scales). `--sparse-indexer-topk-backend` must be `auto` or `deep_select`. Not supported with DCP/PCP.
- The sparse kernels score in bf16 with bf16 weights (no fp32 option), so the flag changes the indexer's score precision; greedy outputs are not token-identical to the dense path (see the NLL table).

+def _build_fp4_paged_cache(req_lens: torch.Tensor, page_kv: int, head_dim: int):
+    """MXFP4 paged cache in DeepGEMM's fused layout: per page, all tokens'
+    fp4 data first, then their packed UE8M0 scales."""
+    device = req_lens.device
+    pages_per = (req_lens + page_kv - 1) // page_kv
+    num_pages, max_pages = int(pages_per.sum()), int(pages_per.max())
+    kv_cache = torch.zeros(
+        num_pages, page_kv, 1, head_dim // 2 + 4, dtype=torch.uint8, device=device
+    )
+    block_table = torch.zeros(
+        len(req_lens), max_pages, dtype=torch.int32, device=device
+    )
+    page_pool = torch.randperm(num_pages, device=device)
+    offset = 0
+    for b in range(len(req_lens)):
+        n = int(pages_per[b])
+        block_table[b, :n] = page_pool[offset : offset + n].to(torch.int32)
+        offset += n
+        k_fp, k_sf = _quant_fp4(
+            torch.randn(int(req_lens[b]), head_dim, device=device, dtype=torch.bfloat16)
+        )
+        rows68 = torch.zeros(n * page_kv, 68, dtype=torch.uint8, device=device)
+        rows68[: int(req_lens[b]), : head_dim // 2] = k_fp.view(torch.uint8)
+        rows68[: int(req_lens[b]), head_dim // 2 :] = k_sf.view(torch.uint8).view(-1, 4)
+        by_page = rows68.view(n, page_kv, 68)
+        split = torch.cat(
+            [by_page[..., :64].reshape(n, -1), by_page[..., 64:].reshape(n, -1)], dim=1
+        ).view(n, page_kv, 1, head_dim // 2 + 4)
+        kv_cache[block_table[b, :n].long()] = split
+    return kv_cache, block_table

+def check_deep_select_layout(num_sparse_cols: int, topk_tokens: int) -> None:
+    """Raise unless DeepSelect accepts the sparse logits layout.

+_INT32_BIG = tl.constexpr(2**31 - 1)

+@triton.jit
+def _expand_candidates_kernel(
+    cand_ptr,
+    cand_stride,
+    ks_ptr,
+    ks_stride,
+    ke_ptr,
+    ke_stride,
+    si_ptr,
+    si_stride,
+    end_ptr,
+    end_stride,
+    K: tl.constexpr,
+    S: tl.constexpr,
+    RATIO: tl.constexpr,
+    SBK: tl.constexpr,
+):
+    """One program per row: expand + filter + sort candidate blocks.
+
+    Each row's valid sparse blocks come out sorted ascending (no dedup pass:
+    production candidates are unique, and the kernel tolerates repeats),
+    padded by repeating the last valid block — DeepGEMM's padding convention.
+    ``end`` counts valid sparse-token columns; valid columns form a prefix
+    because block ids are sorted.
+    """
+    row = tl.program_id(0)
+    ks = tl.load(ks_ptr + row * ks_stride)
+    ke = tl.load(ke_ptr + row * ke_stride)
+    cols = tl.arange(0, K)
+    cand = tl.load(cand_ptr + row * cand_stride + cols)  # K is pow2, no mask
+    if RATIO == 2:
+        cand = tl.interleave(cand * RATIO, cand * RATIO + 1)
+
+    # Keep only blocks inside the row's KV range [0, ke - ks); the lower
+    # bound is free since candidates are non-negative.
+    kv_len = tl.maximum(ke - ks, 0)
+    max_block = (kv_len + SBK - 1) // SBK
+    valid = (cand >= 0) & (cand < max_block)
+    vals = tl.where(valid, cand, _INT32_BIG)
+    vals = tl.sort(vals)
+
+    # Anchor at the row's ks rounded down to a sparse-block boundary
+    # (identity for the paged path, where ks == 0).
+    base = ks // SBK
+    si = tl.where(vals != _INT32_BIG, vals, 0) + base
+    n_valid = tl.sum(valid.to(tl.int32))
+    last_rel = tl.max(tl.where(valid, cand, -1))
+    pad_val = tl.where(n_valid > 0, last_rel + base, base)
+    tl.store(
+        si_ptr + row * si_stride + tl.arange(0, S),
+        tl.where(tl.arange(0, S) < n_valid, si, pad_val),
+    )
+
+    # Valid sparse-token column count; only the last block can be partial.
+    # Absolute start of the last block: (base + last_rel) * SBK + ks % SBK,
+    # which is exactly last_rel * SBK + ks.
+    last_start = last_rel * SBK + ks
+    fill = tl.minimum(tl.maximum(ke - last_start, 1), SBK)
+    end = tl.where(n_valid > 0, (n_valid - 1) * SBK + fill, 0)
+    tl.store(end_ptr + row * end_stride, end)
