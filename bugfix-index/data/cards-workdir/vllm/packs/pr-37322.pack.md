## Summary

PR #37136 introduced an EP weight filter that skips non-local expert tensors before reading them from disk, drastically reducing storage I/O for MoE models under EP. However, it has two bugs:

**1. Breaks EPLB (catastrophic accuracy loss — gsm8k drops from ~0.95 to ~0.08)**

When EPLB is enabled, redundant physical expert slots (e.g., 256 logical + 32 redundant = 288 physical for DeepSeek-R1) can map to *any* logical expert. The EP weight filter partitions based on `model_config.get_num_experts()` (256 logical experts) and skips non-local ones. But the weight loader via `make_expert_params_mapping` needs ALL 256 logical experts to populate the redundant physical slots. The filter starves the weight loader, leaving redundant slots uninitialized.

**Fix:** Skip the EP weight filter entirely when `enable_eplb` is set.

**2. Corrupts NVFP4 activation scales (~2% accuracy regression without EPLB)**

FlashInfer NVFP4 backends compute a global activation scale via `a13_scale.max()` across ALL expert slots. The EP weight filter skips non-local experts' `input_scale` checkpoint tensors, leaving those slots at their `torch.empty()` initialization (random garbage). The `max()` then picks up garbage values, producing an incorrect global activation scale.

**Fix:** Only filter tensors ending in `.weight` (the heavy ones). Scale and metadata tensors (`input_scale`, `weight_scale`, `weight_scale_2`) are negligibly small and always loaded.

## Test plan
- [ ] Verified EPLB accuracy restored on DeepSeek-R1-0528-FP4-v2 (GB200 NVL72, EP16, 32 redundant experts)
- [ ] Verified non-EPLB EP accuracy restored (lm_eval gsm8k 0.93 → 0.95)
- [ ] EP weight filter still active for `.weight` tensors (I/O savings preserved)
