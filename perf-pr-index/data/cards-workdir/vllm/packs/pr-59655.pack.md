## PR body
```markdown
# [Bugfix][Spec Decode] DeepSeek V4/V4.1 NVFP4: keep ignored MTP/DSpark experts on MXFP4

## Purpose

With `nvidia/DeepSeek-V4.1-Flash-NVFP4`, DSpark speculative decoding accepts no draft tokens. Acceptance length is
1.00 (0 of 604,200 draft tokens on GSM8K), against 3.57 for the same speculative config on
`deepseek-ai/DeepSeek-V4.1-Flash`. Speculation then only adds overhead. With this fix NVFP4 + DSpark is 2.3x faster at
concurrency 1 and 2.0x at concurrency 8 on MT-Bench, close to the native checkpoint.

No error is raised and accuracy is unaffected, since every draft token is rejected. The only hints are a warning right
after the draft loads (log from v0.30.0):

```
WARNING [modelopt.py] w1_weight_scale_2 must match w3_weight_scale_2. Accuracy may be affected.
```

and that the draft never logs `Using 'FLASHINFER_TRTLLM_MXFP4_MXFP8' Mxfp4 MoE backend`.

**Root cause.** ModelOpt NVFP4 exports of DeepSeek V4/V4.1 quantize the target's routed experts and keep the modules in
`quantization_config["ignore"]` in their native format:

```json
"moe_quant_algo": "NVFP4",
"ignore": ["*.attn.*", "*.ffn.shared_experts.*", "head", "mtp.*"]
```

So the bundled MTP/DSpark layers (`mtp.*`) of `nvidia/DeepSeek-V4.1-Flash-NVFP4` stay MXFP4. Its
`model.safetensors.index.json` stores them as `weight`/`scale`, the same as the native checkpoint, not with NVFP4's
`weight_scale_2`/`input_scale`.

`DeepseekV4FP8Config.get_quant_method` nevertheless returned `ModelOptNvFp4FusedMoE` for every `RoutedExperts` layer
whenever `moe_quant_algo == "NVFP4"`. That includes the draft layers, built as `layers.{num_hidden_layers + k}` in
`vllm/models/deepseek_v41/nvidia/dspark.py`. Loading then goes wrong without an error:

- The packed 4-bit weights have the same shape as NVFP4's, so they load.
- NVFP4's block-scale parameters are larger, and the MoE weight loader narrows them to the checkpoint shape, so half of
  each is never written.
- The NVFP4-only per-tensor scales (`w13/w2_weight_scale_2`, `w13/w2_input_scale`) have no counterpart in the MXFP4
  checkpoint, so they keep their uninitialized `torch.empty` values. The warning comes from comparing the two halves of
  the uninitialized `w13_weight_scale_2`.

The draft MoE then computes garbage, and every draft token is rejected.

## Fix

`DeepseekV4FP8Config.from_config` now records the checkpoint's `ignore` list. A routed-expert layer whose checkpoint name
matches it (`fnmatch`) keeps `Mxfp4MoEMethod`. Draft/MTP layers, built as `layers.{num_hidden_layers + k}`, are matched
under their checkpoint name `mtp.{k}`. Everything else keeps the previous behaviour: target experts, draft layers that are
not ignored, checkpoints without an `ignore` list, and non-NVFP4 checkpoints.

On CUDA/ROCm, DeepSeek-V4 checkpoints use this same config class. For the published NVIDIA NVFP4 checkpoints (formats
taken from each `model.safetensors.index.json`):

| checkpoint | MTP/draft experts on disk | `mtp.*` in `ignore` | main | this PR |
|---|---|---|---|---|
| `nvidia/DeepSeek-V4.1-Flash-NVFP4` | MXFP4 | yes | NVFP4 (wrong) | MXFP4 |
| `nvidia/DeepSeek-V4-Flash-NVFP4`, `nvidia/DeepSeek-V4-Pro-NVFP4` | MXFP4 | yes | NVFP4 (wrong) | MXFP4 |
| `nvidia/DeepSeek-V4-{Flash,Pro,Pro-0813}-nvfp4-DSpark` | NVFP4 | no | NVFP4 | NVFP4 |

Only the first row was run end to end. The DeepSeek-V4 rows are covered by the unit test.

`quantized_layers` is not used. The `*-nvfp4-DSpark` exports list only `mtp.0` there while shipping `mtp.0`-`mtp.2` as
NVFP4, so it is not a complete listing.

Not changed:
- `moe_quant_algo` is still read from the current (target) `hf_config`, so a separately shipped draft whose expert
  format differs from the target's (the #49133 setup) behaves as before.
- The FlashInfer `moe_ep` mega-MoE backends decide NVFP4 globally in `deepseek_v4/nvidia/fi_moe.py`.

Tests:
- A CPU unit test in `tests/quantization/test_fp8.py`. `deepseek_v41/quant_config.py` is added to the Quantization
  step's source dependencies.
- A GSM8K config, `DeepSeek-V4.1-Flash-NVFP4-DSpark-TP4.yaml`, with `min_acceptance_length: 2.5`. A broken draft keeps
  accuracy, so only the acceptance gate catches this. It is added to `models-spec-decode.txt` (B200 "LM Eval Spec
  Decode"), with `vllm/models/deepseek_v41/` as a source dependency of that step.

## Not a duplicate

- **#49133** (closed, unmerged) had the same symptom on DeepSeek-V4 with a separately shipped DSpark drafter. It was
  closed as low priority ("we have nvfp4 drafter for dsv4-nvfp4 now"). This PR does not change that separate-drafter
  case.
- **#56054** does the same `mtp.{i}` -> `layers.{num_hidden_layers + i}` re-keying, but for Quark's `layer_quant_config`
  in `vllm/models/deepseek_v4/`. This PR applies it to the ModelOpt `ignore` list in `DeepseekV4FP8Config`, which Quark
  checkpoints never reach.
- **#55498** extends `ModelOptMixedPrecisionConfig`. These checkpoints resolve to `deepseek_v4_fp8`.
- **#49900** fixes quant-target matching for the generic `draft_model` method (compressed-tensors).
- **#43319** skips the quant config for BF16 DeepSeek-V4 MTP weights. Here the draft is MXFP4 and needs
  `Mxfp4MoEMethod`, not an unquantized layer.

## Test Result

All runs used vLLM v0.30.0 on GB300 (TP4), with this PR's `quant_config.py` mounted over the installed one. On main the
file differs from v0.30.0 only in the Quark handling of `override_quantization_method`, which these checkpoints do not
reach. Below, "v0.30.0" means unmodified and "PR" means v0.30.0 with this change.

**Unit test:** 7 cases. Against the unmodified v0.30.0 file, 2 fail: `ignored-mtp0` and `ignored-mtp2`, the V4.1
draft. With this PR all 7 pass.

**Lint:** `ruff check` and `ruff format --check` are clean. mypy 1.20.2 with the repo config reports no issues (the
same as for the unmodified file). The full `pre-commit` suite was not run.
