## Motivation

LFM2.5-8B-A1B uses two BF16 Triton MoE GEMMs on B300 (`SM103`):

- gate/up projection: `E=32, N=3584, K=2048, topk=4`
- down projection: `E=32, N=2048, K=1792, topk=1`

The generic Triton path previously fell back to heuristic schedules for this
model/device pair. A shape-specific KDA kernel improved over that fallback, but a
separately tuned generic Triton baseline was faster for medium/large token counts
and high-concurrency serving. Therefore this PR has been converted to a
**config-only** change, following the same conclusion as #37159.

## Changes

Add B300 (`NVIDIA_B300_SXM6_AC`) Triton 3.7.1 configs for LFM2.5:

- gate/up config with 8 tuned M buckets
- down config with 8 tuned M buckets
- TMA enabled in every selected config

There is no custom kernel, dispatch branch, or model-specific runtime code in the
final diff.

## Tuning setup

Hardware: NVIDIA B300 SXM6 AC (`SM103`). Software: CUDA 13.0, PyTorch
2.13.0+cu130, Triton 3.7.1.

The tuner ran on PR base `771e613d96de0ee89631bc308a2525aaeae9f13e`, where
the former KDA dispatch did not exist:

- 100 deterministic `E=32, topk=4` routing samples
- M grid: `1, 8, 32, 256, 1024, 2048, 4096, 16384`
- 240 focused configs per M
- `BLOCK_M`: 16/32/64/128/256
- schedules covering `BLOCK_N` 32/64/128/256, `BLOCK_K` 64/128,
  4/8 warps, 3/4/6 stages, and group sizes 1/8/16/32
- both gate/up and down TMA variants tested

The runtime uses nearest-M selection between the tuned buckets. Gate/up and down
configs use the same `BLOCK_SIZE_M` at each bucket, as required by the shared
expert-row alignment.

## LFM2.5-8B-A1B serving results

Two TP1 servers were benchmarked concurrently. GPU assignments were then swapped
and the full matrix repeated. Each assignment used seeds 1001/1002/1003. Results
pair the same physical GPU and use the geometric mean of GPU0/GPU1 ratios to
remove multiplicative card-to-card bias.

- concurrency: `1, 4, 16, 32, 64`
- decode: input 1, output 256, `max(16, 4 * concurrency)` prompts
- mixed: input 1024, output 256, `max(8, 2 * concurrency)` prompts
- fixed lengths with `--random-range-ratio 1.0`
- cache flushed before each trial

Positive throughput means tuned Triton is faster. Positive ITL means KDA has
higher (worse) ITL.

| Workload | Concurrency | Tuned throughput advantage | KDA ITL penalty |
|---|---:|---:|---:|
| decode 1/256 | 1 | +0.38% | +0.44% |
| decode 1/256 | 4 | -0.78% | -0.36% |
| decode 1/256 | 16 | +0.67% | +0.73% |
| decode 1/256 | 32 | -0.56% | -0.38% |
| decode 1/256 | 64 | **+6.36%** | **+6.29%** |
| mixed 1024/256 | 1 | +1.06% | +1.20% |
| mixed 1024/256 | 4 | +1.94% | +1.45% |
| mixed 1024/256 | 16 | +1.86% | +1.07% |
| mixed 1024/256 | 32 | +1.31% | -0.14% |
| mixed 1024/256 | 64 | **+10.20%** | **+8.56%** |

Decode through concurrency 32 is effectively tied (all throughput differences
within 0.8%). The tuned configs win clearly at concurrency 64 and win every mixed
throughput point after GPU crossover correction.

## Correctness and validation

- Tuned generic Triton and the former KDA candidate matched exactly (`rtol=0`,
  `atol=0`) for both projections at M =
  `2, 4, 8, 16, 64, 128, 256, 512, 1024, 4096, 16384` (22 cases).
- Completed 60 paired serving runs plus two additional concurrency-16 sanity
  runs, including the GPU0/GPU1 crossover.
- Both JSON files parse successfully, contain the expected 8 M buckets, enable
  TMA in every bucket, and keep gate/up and down `BLOCK_SIZE_M` aligned.
- `git diff --check` passes; the final PR diff contains only the two config files.

## Conclusion

The initial KDA work identified a real missing-config problem, but the custom
kernel is not the best fix after tuning the existing Triton path. The final PR
keeps the useful artifact—the tuned generic Triton configs—and removes 951 lines
of custom kernel, dispatch, and test code.
