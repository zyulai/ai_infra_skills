## 正文(PRD / 提案全文)

### Motivation.

PrefixLM models like Gemma3 multimodal require mixed attention patterns: bidirectional attention for image tokens (prefix) combined with causal attention for text tokens. Currently, vLLM handles this pattern using TritonAttention (or FlexAttention as fallback), which is slower than FlashAttention-2.

The core issue is that FlashAttention-2 only supports pure causal or pure non-causal attention—it cannot represent the hybrid mask pattern:

```
Image Tokens [0, N):      Bidirectional (attend to all image tokens)
Text Tokens [N, seq_len): Causal + attend to prefix
```

This forces PrefixLM models to use slower backends, creating a significant performance penalty for multimodal inference.

From benchmarks on A100-80GB:

| Backend | gemma3-4b seq=512 | gemma3-27b seq=512 | Notes |
|---------|-------------------|---------------------|-------|
| **FlashAttention-2** | 0.072 ms | 0.082 ms | Text-only baseline |
| **TritonAttention** | 0.18 ms | 0.16 ms | Current PrefixLM path |
| **FlexAttention** | 0.29 ms | 0.33 ms | Fallback |
| **Ratio** | 2.5x slower | 2x slower | Overhead vs FlashAttn |

The 2-4x overhead applies to every attention layer, accumulating to significant end-to-end latency.

Models with `is_mm_prefix_lm=True` that would benefit:
- Gemma3 (4B/12B/27B) - Multimodal with bidirectional image prefix
- Future multimodal models - Any model requiring partial bidirectional attention
- PrefixLM architectures - T5-style prefix attention patterns

Strategic value:

1. Significant performance improvement for multimodal: Closing the gap with FlashAttention
2. O(N) memory for attention masks vs O(N²): critical for long context
3. Unified backend: Single backend for text and multimodal (simpler codebase)
4. Future-proof: Extensible to other complex mask patterns

### Proposed Change.

FlashMask (ICLR 2025 Accepted, Wang et al.) extends FlashAttention-2 with column-wise sparse mask representation, enabling arbitrary attention patterns with O(N) memory complexity.

Paper: "FlashMask: Efficient and Rich Mask Extension of FlashAttention"
Status: ICLR 2025 Poster
Authors: Guoxia Wang, Jinle Zeng, Xiyuan Xiao, Siming Wu, Jiabin Yang, et al.

Column-Wise Sparse Mask Representation

Instead of storing a dense O(N²) mask, FlashMask represents attention patterns as column indices per row:

```
# For each query row i, store the start/end columns that can be attended to
mask_representation = {
    "col_left": [left_bound_0, left_bound_1, ...],   # [seq_len]
    "col_right": [right_bound_0, right_bound_1, ...]  # [seq_len]
}

# Attention allowed: col_left[i] <= j <= col_right[i]
```

For Gemma3 PrefixLM pattern with 256 image tokens:

```
# Image tokens (rows 0-255): attend to all image tokens
col_left[0:256] = 0
col_right[0:256] = 255

# Text tokens (rows 256+): causal + attend to all prefix
col_left[256:] = 0      # Can attend back to token 0 (prefix)
col_right[i] = i         # Causal: attend up to current position
```

This representation is O(seq_len) instead of O(seq_len²).

The FlashMask kernel extends FlashAttention-2's tiling algorithm:

```cpp
// FlashAttention-2 base (simplified)
for (int k_block = 0; k_block < num_k_blocks; k_block++) {
    // Load Q, K, V tiles
    // Compute attention scores
    for (int j = 0; j < BLOCK_N; j++) {
        // Causal mask: if (col > row) mask = -inf
        bool valid = (k_block * BLOCK_N + j) <= query_row;
        scores[j] = valid ? qk_dot[j] : -INFINITY;
    }
    // Online softmax, accumulate output
}

// FlashMask extension
for (int k_block = 0; k_block < num_k_blocks; k_block++) {
    int col_start = k_block * BLOCK_N;
    
    // Load column bounds for current query rows
    int left = col_left[query_row];
    int right = col_right[query_row];
    
    // Column-wise sparse mask
    for (int j = 0; j < BLOCK_N; j++) {
        int col = col_start + j;
        // Check against column bounds (replaces causal check)
        bool valid = (col >= left) && (col <= right);
        scores[j] = valid ? qk_dot[j] : -INFINITY;
    }
    // Rest unchanged: online softmax, accumulate output
}
```

The mask check remains O(1) per element—only the comparison changes.

2.3 Mask construction

```
# vllm/v1/worker/gpu_model_runner.py

def _build_flashmask_metadata(
    self,
    seq_lens: List[int],
    mm_prefix_ranges: List[Optional[Tuple[int, int]]],
    sliding_window: Optional[int],
) -> Tuple[torch.Tensor, torch.Tensor]:
    """Build FlashMask column bounds from mm_prefix_range.
    
    For each sequence with prefix range [start, end):
    - Rows in [start, end): col_left=start, col_right=end-1 (bidirectional)
    - Rows >= end: col_left=0, col_right=current_row (causal + prefix)
    """
    col_left_list = []
    col_right_list = []
    
    for seq_len, mm_range in zip(seq_lens, mm_prefix_ranges):
        if mm_range is None:
            # Pure causal (no prefix)
            col_left_list.append(torch.zeros(seq_len, dtype=torch.int32))
            col_right_list.append(torch.arange(seq_len, dtype=torch.int32))
        else:
            prefix_start, prefix_end = mm_range
            col_left = torch.zeros(seq_len, dtype=torch.int32)
            col_right = torch.arange(seq_len, dtype=torch.int32)
            
            # Bidirectional within prefix region
            col_right[:prefix_end] = prefix_end - 1
            
            col_left_list.append(col_left)
            col_right_list.append(col_right)
    
    return torch.cat(col_left_list), torch.cat(col_right_list)
```

Alternatives considered

1. Continue using TritonAttention

Status: Current solution
Pros: Already implemented, correct behavior
Cons: 2-4x slower than FlashAttention, not optimal for production

2. FlexAttention

Status: Available as fallback
Pros: Supports arbitrary masks
Cons: slower than FlashAttention, high compile overhead

3. Fused QKNormRoPE optimization

Status: Investigated, not viable for Gemma3
Reason: GemmaRMSNorm uses `x*(1+w)` formula, incompatible with existing fused kernel
Impact: Would only provide small performance gains even if implemented

4. Hybrid backend runtime switching

Status: Not possible in current vLLM architecture
Reason: vLLM selects attention backend once at model initialization
Would require: major architectural changes to support per-request backend selection
