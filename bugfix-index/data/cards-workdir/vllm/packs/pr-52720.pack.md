## 正文(PR 描述)

## Purpose

Structured output fails for Mistral models whose tokenizer transformers loads as a `MistralCommonBackend`.

Transformers picks that class when `mistral-common` is installed and `TOKENIZER_MAPPING_NAMES` maps the model's `model_type` to it — `mistral`, `ministral`, `ministral3`, `mistral3`, `mixtral`, `pixtral`, `voxtral`, `voxtral_realtime`. vLLM reaches it whenever `resolve_tokenizer_args` does not select `tokenizer_mode="mistral"`.

That class subclasses `PreTrainedTokenizerBase` rather than `PreTrainedTokenizerFast`, and the two grammar backends fail on it differently:

**xgrammar — HTTP 500.** `is_mistral_tokenizer()` is `False`, so the working Mistral path is skipped and `xgr.TokenizerInfo.from_huggingface()` raises `ValueError: Unsupported tokenizer type`. The backend is built lazily on the first structured-output request, so the server starts fine and plain completions keep working.

**outlines — silently wrong.** No crash: `get_cached_tokenizer` returns a `CachedTokenizer` subclass whose `convert_tokens_to_string` falls back to `"".join(tokens)`. The vocabulary it builds is wrong instead. On `mistralai/Mistral-Nemo-Instruct-2407` via `get_tokenizer(tokenizer_mode="hf")`, 409 of 129044 reduced-vocabulary entries map to the wrong token ids, collapsing onto 3 shared ids, so the grammar is compiled over a corrupted vocabulary.

## Fix

`MistralCommonBackend` already carries what the Mistral path needs, and vLLM already has a wrapper that consumes it (`MistralTokenizer.__init__(tokenizer: MistralCommonBackend)`). The wrap happens once in `StructuredOutputManager`, where the tokenizer is acquired, so it covers every backend and keeps a single `MistralTokenizer` instance — the vocabulary caches keyed on the tokenizer object (outlines' `_outlines_vocabulary`, lm-format-enforcer's `lru_cache`) are not discarded.

`backend_xgrammar.py` and `backend_outlines.py` are untouched.

## Test

`tests/v1/structured_output/test_mistral_common_tokenizer.py`, built through `get_tokenizer`:

- the reduced vocabulary is correct after wrapping and mismapped before it
- both backends accept a valid document token by token, and reject an invalid token
- the xgrammar bitmask width matches the vocabulary
- xgrammar still raises `ValueError` without the wrapper
- a non-Mistral tokenizer passes through untouched

9 tests, ~15s.

## Notes

`guidance` already handled `MistralCommonBackend` and is unaffected. It rejects SentencePiece-backed instances with `TypeError: Guidance only supports Tekken tokenizers`, raised by mistral_common's own `from_mistral_tokenizer`; that is unchanged by this PR and reproduces identically without it.
