## 正文(PR 描述)

FIX #47724

## Purpose

`LoRAModelManager.set_adapter_mapping` memoizes on `self._last_mapping` (the
per-token LoRA ID mapping of the running batch) and skips the punica metadata
refresh when it is unchanged. The memo is never invalidated when a GPU slot is
reassigned: an out-of-band `add_lora()` on a live engine eagerly activates the
new adapter (`LRUCacheWorkerLoRAManager.add_adapter` -> `activate_adapter`),
which can LRU-evict a slot held by an adapter that is currently decoding and
rotate `lora_index_to_id`. Because the in-flight request set is unchanged, the
`LoRAMapping` is identical, the memo hits, and `punica_wrapper.update_metadata`
is skipped — `token_lora_indices` still encodes the old slot layout, and
in-flight requests silently decode with another adapter's weights. See
#47724 for the full analysis and a self-contained reproduction.

This PR keys the memo on the slot layout as well as the mapping: the refresh
now also runs whenever `tuple(self.lora_index_to_id)` has changed since the
last call. Per-step no-op calls (the common case) still hit the memo, so the
optimization is preserved.

Not a duplicate: searched open PRs and issues for `set_adapter_mapping`,
punica staleness, and `add_lora` eviction — no existing report or fix
(closest are unrelated: #36187 LoRA shrink kernel contiguity, #39935
sleep/wake with LoRA).

## Test Plan

1. New regression test
   `tests/lora/test_lora_manager.py::test_set_adapter_mapping_refreshes_after_slot_reassignment`:
   drives the exact production sequence at the manager level — two adapters
   decoding in both slots, an out-of-band activation LRU-evicts and the
   re-activation lands the batch's adapters in swapped slots, then
   `set_adapter_mapping` is called with an identical mapping. Asserts
   `punica_wrapper.token_lora_indices` follows the new slot layout. Fails on
   `main` without the fix (metadata stays `[0, 1]`), passes with it.
2. End-to-end reproduction script from #47724 (1x H100): reference
   phase, repeated reference phase (determinism control), then a test phase
   with `add_lora()` churn against two greedy in-flight decodes.

```
pytest tests/lora/test_lora_manager.py::test_set_adapter_mapping_refreshes_after_slot_reassignment -v
VLLM_WORKER_MULTIPROC_METHOD=spawn python3 lora_memo_bug_min_repro.py
```

## Test Result

All validation on 1x H100, vLLM `main` @ `ba2215209` via the per-commit
precompiled wheel, plus released 0.22.1 / 0.24.0.

Unit test (main @ `ba2215209`):

- without the fix: FAILED at the final assertion (`assert [0, 1] == [1, 0]` —
  `token_lora_indices` still encodes the pre-eviction slot layout)
- with the fix: PASSED
- (both runs show one teardown error specific to the validation pod's
  environment; unmodified neighboring tests, e.g.
  `test_lora_lru_cache_model_manager`, show the identical teardown error there)

End-to-end repro script from the issue (three phases: reference, repeated
reference as per-stream determinism control, then `add_lora()` churn; greedy,
prefix caching disabled):

| build | slot-map changes | punica refresh skipped | A1 stream (control bitwise-clean) |
|---|---|---|---|
| stock 0.22.1 | 62 | 59 | diverges under churn @ token 509 |
| stock 0.24.0 | 64 | 58 | diverges under churn @ token 510 |
| stock main @ ba2215209 | 63 | 58 | diverges under churn @ token 515 |
| fixed 0.24.0 | 64 | 0 | bitwise identical under churn |
| fixed 0.24.0 (repeat) | 63 | 0 | bitwise identical under churn |
| fixed main @ ba2215209 | 53 | 0 | bitwise identical under churn |

The fixed rows double as the determinism control for the divergence claim:
the identical churn workload with only the fix applied produces zero skipped
refreshes and byte-identical outputs, so the stock-build divergence is caused
by the stale routing, not by add/decode timing.
