## Purpose

This PR set split_k to 1 for triton_kernels:
* It's reported that triton has worse performance than marlin for small batch size, see https://github.com/vllm-project/vllm/issues/28894. This is because the computed split_k become greater than 1 for small batch size, then triton_kernels will use torch.float32 dtype, see [here](https://github.com/triton-lang/triton/blob/v3.5.1/python/triton_kernels/triton_kernels/matmul_ogs.py#L169)
  * split_k computation: `split_k = max(n_sms // grid_size, 1)`, see [here](https://github.com/triton-lang/triton/blob/v3.5.1/python/triton_kernels/triton_kernels/matmul_ogs_details/opt_flags_details/opt_flags_nvidia.py#L45-L54)
  * split_k become smaller when grid_size become bigger (For example, n_sms =132 for H200, if grid_size is > 66, split_k start to become 1). grid_size become bigger when m become bigger. This explains for higher batch size (m is big), split_k become 1, dtype is bf16 precision.
  * We found split_k start to become greater than 1 when m become smaller than 32 (roughly).
* So this PR set split_k to 1 for Hopper (sm90). Because for big batch size, split_k is already 1. For small batch size, split_k  > 1 leads to worse performance, because it will use fp32 precision as explained above, as well as split_k doesn't make sense for small matmul.
* Blackwell (sm100) is already setting split_k to 1, because Blackwell set is_persistent to true, this will make split_k to 1, see [here](https://github.com/triton-lang/triton/blob/v3.5.1/python/triton_kernels/triton_kernels/matmul_ogs_details/opt_flags.py#L189-L190)
* For batch size 16, e2e output token throughput improves about 38%.
