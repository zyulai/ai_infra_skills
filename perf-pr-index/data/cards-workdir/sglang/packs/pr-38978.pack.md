## PR body
```markdown
## Problem

Optimistic prefill reduces decode bootstrap latency by overlapping decode-side allocation with prefill. Under `write_through` HiCache, however, speculative KV follows the normal publication path before the bootstrap result is known, making ownership unsafe across retries and aborts.

## Changed

- Keep pending-bootstrap KV request-owned and out of the shared radix cache.
- Advance multi-chunk requests without publishing speculative KV.
- Release retry, bootstrap failure, and abort paths without inserting unfinished KV or releasing it twice.
```
before:
Request
  → Decode bootstrap and KV preallocation
  → Wait for decode readiness
  → Prefill computation
  → Publish KV to radix cache and async write-through L2
  → Transfer KV to decode
  → First token

after:
Request
  ├─ Decode bootstrap and KV preallocation
  └─ Prefill computation
       → Keep KV request-owned and unpublished while bootstrap is pending
       → Bootstrap succeeds: publish once and async write-through L2 and transfer to decode
       → Bootstrap fails/retries/aborts: release unpublished KV and requeue
```
## Validated


DeepSeek-V4-Pro was tested twice on MI355X with 1P1D TP8/DP8, concurrency 256.
```
