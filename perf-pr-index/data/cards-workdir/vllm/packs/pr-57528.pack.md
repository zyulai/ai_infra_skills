## Purpose

Fixes #57350.

The plain streaming chat and completion derender paths currently `call _detokenize_delta()` synchronously from the FastAPI event-loop thread. Under concurrent streaming workloads, this can serialize derender processing and delay unrelated asynchronous work.

This PR:

- Creates an asynchronous wrapper around `_detokenize_delta()` using the renderer's existing shared executor.
- Awaits that wrapper from both `derender_chat_stream()` and derender_completion_stream().
- `Keeps _detokenize_delta()` synchronous for code already executing within the renderer executor.
- Adds regression coverage verifying that both streaming paths execute detokenization on the configured renderer executor rather than the event-loop thread.
- Streaming derender suite after rebasing onto current `upstream/main`: `60 passed, 1 xfailed` (an upstream test marked as an expected failure)

I searched open PRs by issue number and behavior keywords. #50550 modifies the streaming reasoning/tool-parser path, while this PR targets the plain incremental-detokenization path. The distinction and proposed executor boundary were confirmed in #57350 before implementation.

This changes execution placement only. It does not change tokenization semantics, stream-state handling, output ordering, model execution, or the public API.

**AI disclosure:** This PR includes code developed with assistance from OpenAI Codex during implementation, test design, and review. I reviewed and understood every changed line and ran all tests listed below.

The focused regression test was also run before and after the production change. It exercises both public streaming methods and compares the detokenization thread with the event-loop thread and the configured executor worker.

The performance workload used 20 concurrent streams with 2,048 one-token chunks per stream, for 40,960 derender requests per run. Tokenization probes using a 1,537-token prompt were issued every 250 ms while derender was under load. Each configuration was run three times, and the table reports the median of the per-run measurements.

The benchmark compared `upstream/main` at `6dc34b6334` with this PR at `a1de8533fe`, using `--renderer-num-workers` values of 1 and 4.

## Test Result

- Streaming derender suite: `61 passed, 1 xfailed`
- The expected failure is an existing parser-path case tracked by #55195.
- Ruff formatting and linting: passed.
- Mypy and all other applicable pre-commit hooks: passed.
- Focused regression before the fix: both chat and completion cases failed because detokenization ran on the event-loop thread.
- Focused regression after the fix: both cases passed and ran on the configured renderer executor.

With one renderer worker, throughput was effectively unchanged (`-0.2%`), median derender latency improved slightly, and in-load tokenization did not regress. With four workers, throughput improved by `1.2%`, median derender latency improved by `1.6%`, and derender and cadence p99 remained effectively unchanged.

The four-worker in-load tokenization p99 median was higher for this PR, although the individual-run ranges overlapped substantially (`93.87–129.97 ms` upstream and `105.89–134.84 ms` for this PR). This may indicate renderer-pool contention or normal tail-latency variance; the benchmark does not distinguish between them. The results show no material derender throughput or cadence regression from the additional executor hop.

No model evaluation was run because this change does not affect model execution, sampling, token selection, or generated output.
