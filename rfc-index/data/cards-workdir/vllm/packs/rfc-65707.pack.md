## 正文(PRD / 提案全文)

# Fused MoE Static and Runtime Quantization Configs

**Status:** Proposal / RFC

**Date:** 2026-11-03

## Summary

Split `FusedMoEQuantConfig` into two objects with different lifetimes:

* `FusedMoEQuantSchema` is an immutable, tensor-free description of the
  quantization scheme owned by a quantization method. It contains
  [`QuantKey`](vllm/model_executor/layers/quantization/utils/quant_utils.py)
  values for both activation GEMMs and both expert weight GEMMs, plus only the
  role metadata and GEMM1 activation parameters that are not derivable from
  those keys, as well as the backend-selected scale-layout and MX-alignment
  fields.
* `FusedMoEQuantConfig` remains the runtime object. It contains the loaded
  weights, scales, zero points, biases, and other tensor-valued parameters.
  During the compatibility stages it also holds temporary references to static
  metadata; those references are removed once they are no longer needed.

The existing external interface is preserved through properties. Callers keep
using the current names such as `quant_dtype`, `block_shape`, `a1_scale`, and
`w1_bias`; they do not read dataclass fields, `_a1`/`_w1` descriptors, or the
new static reference directly.

`FusedMoEQuantSchema` is the only static quantization type. Selection consumes
only the schema's role keys; after choosing the backend, the quantization method
finalizes the backend ABI fields (`is_scale_swizzled`, `is_scale_transposed`, and
`mx_alignment`) by constructing a new immutable schema value for kernel
construction.

Schema construction, backend selection, ABI finalization, and modular kernel
construction happen in each quantization method's `__init__`, before weights are
loaded. This proposal does not add a setup hook or change the
`RoutedExperts.__init__` sequence. `process_weights_after_loading` transforms
tensors, constructs the runtime `FusedMoEQuantConfig`, and retains it on the
quantization method for execution. The runtime config is passed explicitly to
the already-built kernel on each invocation; the kernel and experts do not own
or cache it. Post-load processing no longer selects a backend, constructs a
kernel, or mutates the quantization schema.

The split gives the system one explicit ordering:

```text
quant method __init__: static schema keys -> select backend
                     -> construct kernel (kernel finalizes schema ABI)
weight loading       -> transform weights -> build runtime config
                     -> pass at execution
```

## Motivation

### Current state

`FusedMoEQuantConfig` currently combines two kinds of information:

* Static information: quantized dtypes, group shapes, symmetry, scale layout,
  activation constants, and derived predicates such as `is_block_quantized` or
  `use_fp8_w8a8`.
* Runtime information: weight scales, activation scales, global scales,
  zero points, biases, Triton `PrecisionConfig`s, and now, in some paths, the
  weights themselves.

This conflation affects the whole setup flow:

1. A quantization method selects a backend from `QuantKey`s during
   construction.
2. Weights and scales are loaded.
3. `process_weights_after_loading` transforms tensors and builds
   `FusedMoEQuantConfig` from the loaded parameters.
4. Only then can the modular kernel be constructed.
5. Some expert implementations run their own `process_weights_after_loading`
   after the kernel has been constructed.
6. Wrappers such as `FusedMoEModularMethod` may replace the kernel's
   implementation during post-load processing.

The kernel is therefore built at the end of a long, implementation-specific
post-load sequence even though all inputs needed to choose and construct it are
available at model setup. At the same time, backend selection often happens in
the quantization-method constructor, before dimension rounding. One decision is
therefore split across the two extreme ends of model setup, which makes both
orderings accidental.

### Problems

#### Kernel construction depends on loaded tensors

Many expert constructors read `quant_config` tensor fields. Examples include
scale-derived buffers in FlashInfer CuteDSL, scale-processing setup in TRT-LLM,
and the emulation experts that rewrite the quant config. Consequently the
kernel cannot be constructed until after loading.

#### Post-load ordering is implicit and fragile

The required order differs by quantization method and expert. Some experts need
the kernel to exist before their post-load hook runs. Others must transform
scales before the quant config is built. Others cause the kernel to be rebuilt
or swapped. This creates ordering dependencies between unrelated objects and
makes adding a backend or an expert easy to get wrong.

#### The quant config is mutable shared state

Several experts modify the config after construction, for example by clearing
scales or changing the effective weight dtype. This means the object does not
describe a stable contract: the same config can mean different things before and
after a hook runs. It also complicates weight reloads, CUDA graph capture, and
reasoning about which tensors a captured kernel will read.

#### Backend execution policy can differ implicitly

An emulation backend may be selected from the checkpoint scheme
(`kInt4Static32`, for example) but execute a different effective scheme
(unquantized weights). Today that difference is represented by mutating the
config. It should instead be an explicit execution policy of the selected
backend or expert, with the schema left unchanged.

#### Oracles and quant methods duplicate derivation logic

Oracles consume selection keys, quantization methods build a second config with
the same dtype and shape information, and kernel classes derive predicates from
that config again. Keeping one canonical static description removes this
duplication.

#### Kernel construction is split across model setup and weight loading

Some quantization methods select a backend in `__init__`, while others select
one during `process_weights_after_loading`. Stage 4 centralizes schema
creation, backend selection, and modular kernel construction in each
quantization method's `__init__`; the kernel constructor owns ABI finalization.
It deliberately leaves the
`RoutedExperts.__init__` sequence and dimension-rounding behavior unchanged.

## Goals

* Provide one immutable static quantization contract for modular MoE kernels.
* Use the schema for selection through its key roles, then have the kernel
  constructor finalize its backend-specific ABI fields without introducing a
  second configuration type.
* Make `QuantKey` the canonical representation of quantization type, scale
  semantics, and symmetry inside that contract.
* Construct prepare/finalize and expert kernels in each quantization method's
  `__init__`, before weights are loaded, without changing
  `RoutedExperts.__init__`.
* Keep all loaded tensors in one runtime config. A reference to the static
  contract may exist during migration, but it is not part of the final runtime
  payload contract.
* Define a deterministic post-load sequence that produces a validated runtime
  config for execution.
* Eliminate post-construction mutation of quantization scheme fields.
* Preserve the existing external `FusedMoEQuantConfig` API with properties and
  methods rather than exposing new fields.
* Make oracle selection and kernel construction testable without allocating
  real quantized weights.
* Land the work in independently reviewable stages: first introduce the static
  config behind the existing API, then migrate internal consumers incrementally.

## Proposed Design

### API compatibility rules

The split is an internal representation change first. External code should
continue to interact with `FusedMoEQuantConfig` through the current properties
and helper methods.

* Dataclass fields are private. Cross-module access uses `@property` methods or
  explicit methods, never `_schema`, `_a1`, `_w1`, or role-descriptor members.
* Existing property names and semantics are preserved. Runtime properties
  delegate static questions to `FusedMoEQuantSchema`; they do not ask
  callers to learn a new vocabulary.
* Static-only consumers eventually take `FusedMoEQuantSchema` directly. They do
  not reach through a runtime config to obtain it.
* The compatibility guarantee for schema-derived runtime properties lasts only
  while `_schema` is present. It is removed after all callers use the schema
  directly.
* New properties and methods are additive in Stage 1. Constructor and factory
  signature changes are deferred to Stages 2a-3.
* Any unavoidable exception is implemented as a compatibility property or
  helper with a documented removal plan, not as direct member access.

### Static quantization description

The static side adds one immutable schema and one role descriptor. The
quantization method creates the schema in `__init__`, before weight loading;
selection consumes its role keys, after which the schema's backend ABI fields
are finalized by constructing a new immutable value. Its dataclass fields are
internal to `config.py`; external consumers use the properties described below:

```python
@dataclass(frozen=True)
class FusedMoEStaticQuantDesc:
    """Static description of one activation or weight role."""

    # The complete quantization description. Do not duplicate fields from it.
    key: QuantKey | None = None

    # Supplemental layout metadata only when key is absent or key's scale group
    # shape cannot represent the required alignment, e.g. GPTQ activation
    # alignment. This must be None when key already supplies the same shape.
    alignment_shape: GroupShape | None = None

    # Presence flags are part of the kernel ABI and are not 100% derivable from
    # the key: symmetry does not, by itself, guarantee a zero point is present.
    has_bias: bool = False
    has_zero_point: bool = False

    def __post_init__(self) -> None:
        assert self.alignment_shape is None or self.key is None or (
            self.alignment_shape != self.key.scale.group_shape
        ), "alignment_shape must not duplicate key.scale.group_shape"


@dataclass(frozen=True)
class FusedMoEQuantSchema:
    """Static quantization and kernel-ABI description for one MoE layer."""

    a1: FusedMoEStaticQuantDesc
    a2: FusedMoEStaticQuantDesc
    w1: FusedMoEStaticQuantDesc
    w2: FusedMoEStaticQuantDesc

    is_scale_swizzled: bool = True
    is_scale_transposed: bool = False
    mx_alignment: int = 0

    gemm1_alpha: float | None = None
    gemm1_beta: float | None = None
    gemm1_clamp_limit: float | None = None
```

The schema has separate `a1`/`a2` and `w1`/`w2` roles so it can represent
different quantization for each GEMM. `w1` denotes the fused gate/up weight
(`w13`); `w2` denotes the down projection. Most current kernels require
`a1 == a2` and `w1 == w2`. Initial builders preserve that restriction by using
one activation key for both activation roles and one weight key for both weight
roles. A backend that later supports mixed schemes can consume the distinct
roles without changing the schema type.

#### Oracle selection inputs

Oracles receive `FusedMoEQuantSchema` and select using only its role keys.
Selection-specific policy such as `allow_vllm_cutlass`, user backend overrides,
and platform checks remain explicit arguments to, or internal policy of, the
concrete oracle; they are not schema fields.

The initial single-key oracle adapters use the schema's common `activation_key`
and `weight_key` properties. Those properties raise when `a1 != a2` or
`w1 != w2`, so a single-key adapter cannot silently choose one role. An oracle
is widened to the role-specific keys when it actually supports mixed schemes.

#### Backend ABI fields

`is_scale_swizzled`, `is_scale_transposed`, and `mx_alignment` are not derivable
from `QuantKey` and depend on the selected backend. The initial schema supplies
defaults for selection; after the backend is chosen, the kernel constructor
finalizes these fields in a new immutable schema value and stores it as the
kernel's canonical schema. Selection must not inspect these fields.
Prepare/finalize, experts, and the kernel's `quant_schema` use that finalized
value.

### Runtime quantization description

Keep the existing name, but make the object a tensor payload. During Stages 2a-3
it retains a transitional reference to the static schema so that existing
properties can keep delegating to static information. The layout below shows
that intermediate shape:

```python
@dataclass
class FusedMoEQuantTensors:
    """Tensor-valued parameters for one activation or weight role."""

    scale: torch.Tensor | PrecisionConfig | None = None
    alpha_or_gscale: torch.Tensor | None = None
    zp: torch.Tensor | None = None
    bias: torch.Tensor | None = None


@dataclass
class FusedMoEQuantConfig:
    """Runtime quantization state for one MoE layer."""

    # Transitional compatibility reference; removed when static questions no
    # longer need to be answered through the runtime config.
    _schema: FusedMoEQuantSchema

    # Weights are part of the runtime state in the target design.
    _w1_weight: torch.Tensor
    _w2_weight: torch.Tensor

    _a1_tensors: FusedMoEQuantTensors = field(default_factory=FusedMoEQuantTensors)
    _a2_tensors: FusedMoEQuantTensors = field(default_factory=FusedMoEQuantTensors)
    _w1_tensors: FusedMoEQuantTensors = field(default_factory=FusedMoEQuantTensors)
    _w2_tensors: FusedMoEQuantTensors = field(default_factory=FusedMoEQuantTensors)

    @property
    def quant_schema(self) -> FusedMoEQuantSchema: ...

    @property
    def w1(self) -> torch.Tensor: ...

    @property
    def w2(self) -> torch.Tensor: ...

    @property
    def a1_scale(self) -> torch.Tensor | None: ...

    @property
    def w1_scale(self) -> torch.Tensor | None: ...

    @property
    def g1_alphas(self) -> torch.Tensor | None: ...

    @property
    def w1_bias(self) -> torch.Tensor | None: ...
```

The `_schema` member and `FusedMoEQuantConfig.quant_schema` accessor are bootstrap
compatibility mechanisms, not part of the final runtime contract. Remove them
once no call site needs the runtime config to answer static questions. After that
cleanup, static-only consumers read `FusedMoEQuantSchema` directly and the
runtime config contains only loaded tensor state.

The property list above is illustrative, not exhaustive. The existing
accessors such as `quant_dtype`, `weight_quant_dtype`, `is_quantized`,
`is_per_act_token`, `per_act_token_quant`, `per_out_ch_quant`, `block_shape`,
`is_block_quantized`, `is_per_tensor`, `is_scale_swizzled`,
`is_scale_transposed`, `mx_alignment`, `a1_scale`, `a2_scale`, `w1_scale`,
`w2_scale`, `a1_gscale`, `a2_gscale`, `w1_zp`, `w2_zp`, `w1_bias`, `w2_bias`,
`w1_precision`, `g1_alphas`, `g2_alphas`, `gemm1_alpha`, `gemm1_beta`,
`gemm1_clamp_limit`, the `use_*` predicates, `ocp_mx_scheme`, `config_name`,
`scale_shape`, and `batched_scale_shape` retain their names and meaning.

Static predicates are implemented once on `FusedMoEQuantSchema`; while the
compatibility reference exists, the runtime config delegates to them through its
existing properties. No caller outside `config.py` reads `_schema`,
`_a1_tensors`, `_w1_tensors`, or the role descriptors. New internal code must
use properties or explicit methods. Existing private accesses such as
`quant_config._w1.scale = ...` are migration debt and are removed when the
corresponding expert moves to the static API.

The runtime config is constructed only after all weight and scale
transformations are complete. Its construction validates that tensor presence,
dtype, and shape agree with the static contract. The quantization method retains
the runtime config for its layer and passes it explicitly to kernel execution. A
runtime config without weights is not a valid input to a modular kernel. Unit
tests or benchmarks that only need static quantization information must use
`FusedMoEQuantSchema`, not a partially populated runtime object.

Shape validation must be backend-aware. Swizzled or transposed scales use a
physical layout that may differ from the logical `QuantKey` shape. The shared
validator checks logical dtype and presence; the backend's construction helper
checks the kernel's canonical schema ABI fields before the runtime config is
used.

Once built, the runtime object is treated as immutable even though its fields
contain mutable tensors. Reload and weight-replacement paths construct a new
runtime object; they do not patch fields in place. Kernels and experts receive
the runtime object per invocation and must not retain it across calls.

During migration, the legacy `make()` helpers may continue to return a runtime
config with absent weights so existing monolithic and test call sites keep
working. That compatibility form is incomplete and is not a valid input to
modular-kernel execution.

### Backend selection and execution policy

Selection sees the schema's role keys and must not inspect its backend ABI
fields. After choosing the backend, the quantization method creates the finalized
schema used for kernel construction. The original selection input is not
mutated. Selection may additionally depend on `FusedMoEConfig`, platform
capabilities, a user backend override, or oracle-specific policy such as
`allow_vllm_cutlass`.

An emulation backend may dequantize those parameters at load time or on the fly.
That is an execution policy of the selected expert, not a second quantization
scheme. For example, the int4 emulation path retains the int4 weight keys in the
schema so selection and construction know what storage the quant method owns;
the selected emulation expert dequantizes the runtime tensors and applies an
unquantized compute path. During migration, such an expert may expose an
internal execution view for the shared unquantized base class, but it must not
clear fields on the schema or mutate a shared runtime config during
construction.

If an online quantization method changes the stored format before kernel
execution, it builds the schema for that final stored format before selection.
The source checkpoint method remains a separate object.

### Quantization-method construction API

`FusedMoEMethodBase` keeps its existing constructor lifecycle. The explicit API
adds the schema and repurposes the runtime builder:

```python
class FusedMoEMethodBase:
    def fused_moe_quant_schema(self) -> FusedMoEQuantSchema:
        ...

    def get_fused_moe_quant_config(
        self, layer: "RoutedExperts"
    ) -> FusedMoEQuantConfig | None:
        """Collect final weights and transformed scales after loading."""
```

Each concrete quantization method constructs a transient `quant_schema` in
`__init__`, selects the backend and experts class, and constructs
prepare/finalize plus the expert kernel through its oracle. The oracle's kernel
constructor finalizes the schema's ABI fields internally and stores the
canonical schema on the kernel. All of this completes before the constructor
returns and before weight loading starts. No new model-setup hook is added, and
`RoutedExperts.__init__` remains unchanged. Backend selection therefore uses the
`FusedMoEConfig` available at quantization-method construction; a post-rounding
revalidation phase is outside this proposal.

The existing `get_fused_moe_quant_config` is repurposed as the runtime builder.
Its existing name, signature, and optional return remain unchanged for
compatibility; a non-`None` result must now contain the complete final tensor
payload. It is the only method allowed to collect that payload.
