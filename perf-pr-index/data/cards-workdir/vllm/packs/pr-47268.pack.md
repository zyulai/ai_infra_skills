## What does this PR do?

Fixes non-coalesced HBM access in `marlin_int4_fp8_preprocess_kernel_awq` (AWQ int4-fp8 weight preprocessing kernel, model-load cold path).

### Problem
Original thread mapping used `threadIdx.x` for the row dimension:
```cpp
qweight[(blockIdx.x * 32 + threadIdx.x) * size_n / 8 + blockIdx.y]
```
Adjacent threads (tidx 0..31) read elements strided by `size_n/8` int32 words — non-coalesced, ~12.5% sector utilization on large matrices.

### Fix
Remap `threadIdx.x` to the column dimension (stride 1, fully coalesced):
```cpp
int col = blockIdx.y * 32 + threadIdx.x;
if (col >= size_n / 8) return;
int32_t val = qweight[blockIdx.x * (size_n / 8) + col];
```
- Grid: `dim3 blocks(size_k, (size_n / 8 + 31) / 32)`, `blockIdx.x` indexes rows directly
- Alignment relaxed from implicit `size_n % 256` to explicit `size_n % 8` + tail boundary check

### Coverage equivalence
Old: `(row=bx*32+tidx, col=by)`; New: `(row=bx, col=by*32+tidx)` — same `[0,size_k) × [0,size_n/8)` element space, each processed exactly once, logically equivalent.

## Why is this not duplicating an existing PR?
Searched open PRs/issues for "marlin preprocess" and coalesced-access fixes on this kernel; found only general marlin performance discussions, no PR addressing the non-coalesced thread mapping in `marlin_int4_fp8_preprocess_kernel_awq`.

### Performance
```bash
python -c "
import torch
from vllm import _custom_ops as ops
k,n,g = 16384,16384,128
qw = torch.randint(0,2**31,(k,n//8),dtype=torch.int32,device='cuda')
qz = torch.randint(0,16,(k//g,n//8),dtype=torch.int32,device='cuda')
for _ in range(5): ops.marlin_int4_fp8_preprocess(qw,qz)
torch.cuda.synchronize()
s,e = torch.cuda.Event(enable_timing=True),torch.cuda.Event(enable_timing=True)
s.record()
for _ in range(50): ops.marlin_int4_fp8_preprocess(qw,qz)
e.record(); torch.cuda.synchronize()
print(f'{s.elapsed_time(e)/50*1e3:.1f} us/iter')
"
```
- Before: 1291.1 us/iter
- After: 581.9 us/iter
- Speedup: **2.22x**

Control: the unchanged `without_zp` kernel path shows no regression (557.7 → 557.4 us/iter, within noise), confirming measurement stability.
