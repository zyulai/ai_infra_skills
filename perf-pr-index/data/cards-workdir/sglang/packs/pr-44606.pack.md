## PR body
```markdown
## Motivation

A diffusion scheduler process imports about ten thousand modules before it builds its pipeline. Imports create long-lived modules, classes and functions and very little garbage, yet CPython runs a full collection every time the surviving heap has grown by a quarter, and each one traces every tracked object again. A scheduler process runs 12 of them during startup, which together take about 1.6 seconds of CPU, with or without compiled bytecode.

Where those collections fall also depends on the import order rather than on the work done. Moving an import, for example to load a module on first use, can add or remove a whole-heap collection inside a given span of startup, which makes import time changes hard to judge.

## Modifications

- `runtime/utils/process.py` gains `defer_full_gc_for_imports()`, a context manager that raises the third GC threshold so that no automatic full collection runs inside the block. Young collections keep running, so short-lived cyclic garbage is freed as usual. Restoring the original thresholds lets automatic full collections resume after the block. On CPython 3.14.0–3.14.4, which uses incremental GC and ignores the third threshold, the context manager is a no-op.
- On exit it restores the thresholds it found, also when the block raises. Nested and concurrent blocks restore them when the last one exits, a child forked inside a block restores them at fork, and the collector's enabled state is never changed, so a process that disabled the collector keeps it disabled.
- It is used where diffusion processes import their runtime in bulk, in the activation phase of `bootstrap_scheduler_process` (platform initialization through the `gpu_worker` import), the activation phase of `bootstrap_http_server_process`, and pipeline and config discovery in the registry. Pipeline discovery enters the block only on its first run, so the registry lookups that return early touch nothing.
- No new option, and nothing changes for srt.

Two simpler forms were measured first and not used. `gc.disable()` over the same blocks saved the same CPU, but it also stops young collections, so about 7 MB of short-lived cyclic garbage (frames of caught exceptions, closures, package metadata structures) stayed alive until the block ended, which showed up as 8 MiB more anonymous memory in the HTTP server child. `gc.freeze()` after the imports would keep import-time objects out of every later collection, but frozen objects are never collected again, so it changes steady-state serving memory, and freezing after warmup is the existing pattern for that.

## Accuracy Tests

No output path changes. Only the timing of garbage collections during startup imports changes.

`test_process.py` checks that full collection is deferred where the collector supports threshold2, that incremental GC is left unchanged on CPython 3.14.0–3.14.4, and that nesting, exception exits with GC disabled, and forked children restore the correct state. The file passes on CPython 3.11.16, 3.12.15, 3.13.15, 3.14.0, 3.14.4, and 3.14.5; only the threshold2-specific collection assertion is skipped on 3.14.0–3.14.4. The earlier CPU diffusion-unit comparison had the same per-test outcomes as the base, apart from the added GC coverage.

## Speed Tests and Profiling

Measured on a CPU-only host with scripts that start each process the way it starts in a server, without touching a device. After each run, the same process allocates 100,000 objects so that any collection this change postpones is paid inside the measurement. Each process ran once with compiled bytecode present, as in an installed package, and once with every module compiled from source.

In every process measured, including the launcher, anonymous memory (`Pss_Anon`), peak RSS (`VmHWM`), minor page faults and the number of full collections read no worse than without this change.
