## PR body
```markdown
## Purpose

Add Proton CUDA graph replay attribution for the default model runner. With `proton_graph_attribution=true`, replayed kernels retain their capture context, including Triton launch metadata when the hook is enabled. Proton profiling now requires attribution whenever decoder or encoder CUDA graphs are enabled; otherwise replay kernels would be silently omitted.

In short, this PR extends #48789 with proton cudagraph attribution capability.

## Design

One Proton session observes capture and replay. Capture activity is discarded through the phase API; each profiling interval then flushes, exports and clears its own phase while retaining graph metadata. The worker enters the default-no-op `WorkerProfiler.capture_cuda_graphs()` hook before actual decoder or encoder capture. Backend session and phase management remain in `ProtonProfilerWrapper`.

Configuration validation runs after graph defaults, platform normalization and runner selection. Attribution requires TreeData and Triton >=3.7; explicitly selected or fallback MRV1 is unsupported. Ordinary eager profiling retains Triton 3.6 compatibility. PC sampling and Chrome traces require graphs disabled.

`periodic_flushing` is rejected with graph attribution, including mixed-case mode names. Its backend independently exports and clears phases, conflicting with the wrapper's phase ownership: after the wrapper clears capture phase 0, periodic flushing may still try to export it and abort. A future periodic-profiling backend can use the existing lifecycle hooks, but phase export and cleanup must have one owner. Full compatibility is deferred: Triton 3.7.1 exposes no Python API to synchronize the periodic flush watermark or explicitly export the final completed phase, and periodic output uses session-owned part files. Supporting it requires a separate lifecycle/export design rather than removing the clear calls.

The encoder-only fix adds the actual encoder capture predicate to the existing hook condition; it needs no encoder implementation changes. Duplicate starts, repeated intervals, delayed/limited profiling and cleanup after export errors remain covered.

## Usage

```bash
vllm serve facebook/opt-125m \
  --profiler-config '{
    "profiler": "proton",
    "proton_profiler_dir": "./proton_profile",
    "proton_output_format": "hatchet",
    "proton_hook": "triton",
    "proton_graph_attribution": true
  }'
```

Use `/start_profile` and `/stop_profile`. Each interval writes a separate rank-qualified profile. For ordinary Proton profiling or Chrome traces, use `--enforce-eager`.
