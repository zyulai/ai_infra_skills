## Summary

based on https://github.com/sgl-project/sglang/pull/24246

I add the jit but also keep the original in case our hardware can fall back to torch if fail on jit.

  ### Hidden side-benefit: ~68% drop in `AllReduce` kernel time on prefill-heavy LoRA workloads

  While cross-checking optimize-2 against pre-opt-2 traces (Qwen3-30B-A3B + LoRA, TP=4, GB300,
  input=65536 / output=32, 10 prompts, `--max-concurrency 4`), I noticed a much larger drop in
  `ncclDevKernel_AllReduce_Sum_bf16` than the PR's micro-benchmark numbers would suggest:

  | metric | pre-opt-2 (merged 4-TP) | post-opt-2 (TP-0 × 4 estimate) | Δ |
  |---|---:|---:|---:|
  | `AllReduce` kernel total | 6,778 ms | ~2,192 ms | **−4,586 ms (−68%)** |

  #### Mechanism

  NCCL collectives are CUDA kernels that **spin-wait inside the kernel** until all ranks
  arrive. Pre-opt-2 had a recurring per-layer CPU stall on each TP rank coming from the PyTorch
   align fallback:

  | pre-opt-2 CPU stall source | time (ms) | removed by |
  |---|---:|---|
  | `Torch-Compiled Region: 4/0` (`_align_block_size_torch` + `torch.compile`) | 3,851 | **this
   PR** |
  | `aten::sort` (`torch.argsort` in the fallback) | 790 | **this PR** |
  | `aten::item` / `_local_scalar_dense` (`.any().item()` ×4,728 in `_add_lora_gate_up_delta`)
  | ~2,000 | #24246 |

  Whichever rank is currently stalled forces the other three ranks' AllReduce kernels to keep
  spinning until it catches up. After this PR (combined with #24246) no rank stalls, all four
  ranks reach AllReduce together, and the kernel duration collapses to roughly just the actual
  data transfer.

  #### Attribution to this PR

  The two stall sources that this PR removes (`Torch-Compiled Region` + `aten::sort`) sum to
  **~4,640 ms**, which closely matches the observed −4,586 ms AllReduce drop. #24246
  contributes another ~2 sec on a separate path (likely partially overlapping in the same
  stream).

  Long stalls hurt NCCL more than frequent short ones: the `.any().item()` calls in #24246 are
  4,728 × ~291 µs (often amortizable), whereas one `Torch-Compiled Region` call is hundreds of
  µs continuous, which the other ranks cannot work around.

  #### Caveats

  - No incremental traces were taken — only `pre-opt-2` vs `post-opt-2`. The per-PR attribution
   above is by stall-source matching, not direct per-PR measurement.
  - The post side uses **TP-0 × 4** as a rough proxy for merged 4-TP; a full merged 4-TP
  post-opt-2 trace would tighten the number.
  - The `4,640 + 2,000 = 6,640 ms` total estimated stall removal exceeds the observed `−4,586
  ms` AllReduce drop, which is consistent with overlap (the two PRs' stalls partially share the
   same GPU-stream window).

  **TL;DR:** the headline 8× speedup of `_align_block_size` is real, but on prefill-heavy
  multi-TP workloads the bigger end-to-end win is **NCCL un-stalling**, which only shows up
  when you diff `AllReduce` kernel time across pre-vs-post traces.

+    """

+    num_total_tokens = flat_topk_ids.numel()

+    # JIT kernel uses +1 offset convention: -1 -> bucket 0 (sentinel),
+    # expert i -> bucket i+1. So pass num_experts + 1 as the bucket count.
+    jit_num_experts = num_experts + 1
+
+    if num_total_tokens < jit_num_experts:
+        max_num_tokens_padded = num_total_tokens * block_size
+    else:

+    # kernel fills sorted_token_ids with vectorized int4 writes whose last
+    # store can spill up to 3 int32s past the logical end. With a fused
+    # allocation the spill would corrupt the adjacent sub-buffer.
+    _A4 = lambda n: (n + 3) & ~3  # noqa: E731
