## 正文(PR 描述)

## Summary

Gemma4's `Gemma4MoE` passes `activation="gelu"` (exact GELU via `torch.ops._C.gelu_and_mul`) to `FusedMoE`, but the published model config (`hidden_activation="gelu_pytorch_tanh"`) and the HuggingFace reference implementation both use the tanh-approximated variant. The dense `Gemma4MLP` in the same file already correctly enforces `gelu_pytorch_tanh` with a `raise ValueError` guard.

The root cause is that `MoEActivation` had no `GELU_TANH` variant when `Gemma4MoE` was written, so `"gelu"` was used as the closest available string.

## Changes

FusedMoE activation enum:
- add `GELU_TANH` and `GELU_TANH_NO_MUL` enum members
- add `"gelu_pytorch_tanh"` to `"gelu_tanh"` alias in `from_str()`
- wire gated dispatch to `torch.ops._C.gelu_tanh_and_mul` and non-gated to `F.gelu(approximate="tanh")`
- register in `_CUSTOM_OP_NAMES` and `_WITHOUT_MUL` lookup tables

Backend allowlists:
- add `GELU_TANH` + `GELU_TANH_NO_MUL` to `_supports_activation` in `TritonExperts`, `BatchedTritonExperts`, `MarlinExpertsBase`, and `HummingExpertsBase`

Model fix:
- Change `Gemma4MoE.__init__` activation from `"gelu"` to `"gelu_tanh"`

## Source of truth

- [`config.json`](https://huggingface.co/google/gemma-4-27B-it/blob/main/config.json): `"hidden_activation": "gelu_pytorch_tanh"`
- HuggingFace reference: `self.act_fn = ACT2FN[config.hidden_activation]` resolves to `nn.GELU(approximate="tanh")`
- Dense MLP in same file: `GeluAndMul(approximate="tanh")` with `raise ValueError` if config doesn't match

## Impact

- the numerical difference between exact and tanh-approximated GELU is ~2e-4 per element in float32, well within bf16 noise for standard generation
- this is primarily a correctness fix: the implementation now matches the published model specification
- zero performance cost — `gelu_tanh_and_mul` runs at the same speed as `gelu_and_mul`

### Smoke test

- `MoEActivation.from_str("gelu_tanh")` and `from_str("gelu_pytorch_tanh")` both resolve to `GELU_TANH`
- `apply_moe_activation(GELU_TANH, ...)` produces output matching `F.gelu(x, approximate="tanh")` within fp32 tolerance
- `GELU_TANH` output diverges from `GELU` output as expected (confirming the activation actually changed)
