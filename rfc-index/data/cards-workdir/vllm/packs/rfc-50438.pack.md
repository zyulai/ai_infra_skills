## 正文(PRD / 提案全文)

### Motivation.

vLLM groups speculative methods that consume target-model hidden states under `SpeculativeConfig.use_eagle()`. For prefix-cache lookup, all of these EAGLE-style draft methods conservatively drop the last matched unit and recompute it.

This behavior is necessary with the current cache key. The reusable draft cache at a boundary depends on the finalized target token immediately following that boundary. The dependency is easiest to see in the autoregressive EAGLE/MTP input shift. For target tokens

```text
x0 x1 x2 x3 | x4
```

the draft inputs corresponding to target positions `0..3` contain the shifted token IDs

```text
x1 x2 x3 x4
```

as well as target-derived hidden states at positions `0..3`. A normal prefix-cache key for the first four-token block only proves equality of `x0..x3`. It does not prove equality of `x4`, even though `x4` is part of the draft input that produces the final cache entry at that boundary.

For example, both of these requests have the same current block hash:

```text
request A: a b c d | e
request B: a b c d | f
```

However, their draft input at the boundary is different (`e` versus `f`). Therefore, reusing the final matched draft block based only on the current block tokens would be unsafe. The current last-block drop makes the reuse safe by recomputing the boundary.

The cost is significant for hybrid full-attention + Mamba/GDN models. Their aligned cache unit can contain hundreds or thousands of tokens, so a one-unit drop can erase a large part of the prefix-cache benefit. This behavior is reported in:

- <https://github.com/vllm-project/vllm/issues/38182>
- <https://github.com/vllm-project/vllm/issues/44858>

One Qwen3.6 report on vLLM 0.20.1 measured the hit rate dropping from 87.3% to 69.9%, with 1,056 fewer hit tokens per request—approximately one 1,072-token aligned block: <https://github.com/vllm-project/vllm/issues/38182#issuecomment-4498973050>. This is historical evidence from vLLM 0.20.1. Current `main` includes partial prefix-hit changes, so the remaining recomputation cost—including the Mamba align-mode backoff—must be measured again.

This RFC proposes making the boundary dependency part of the cache key. If the cache key proves that the token immediately following a block is also equal, then the target-derived state and boundary-token inputs used by the EAGLE-style drafter are equal. The final matched block can then be reused without the conservative drop.

The lookahead token in this proposal is the finalized prompt/target token immediately following a hash boundary. It is not one of the `K` unverified draft tokens. vLLM currently applies the same final-match drop policy to every `use_eagle()` method. This RFC proposes one finalized boundary token as the shared hash dependency, independently of `num_speculative_tokens`. The one-token contract must be validated for each current implementation—`eagle`, `eagle3`, `mtp`, `dflash`, and `dspark`—before its pop is disabled.

#### Goals

- Safely retain the final matched prefix-cache unit when its EAGLE-style draft boundary input is proven to match.
- Avoid the EAGLE-style last-block drop for colocated serving.
- Avoid the corresponding one-block Mamba align-mode backoff.
- Preserve the current conservative behavior when the next token is unknown or different.
- Build on the prefix-match and hybrid-cache behavior already present on current `main`.

#### Non-goals

- P/D disaggregated serving or any external KV connector.
- KV-cache event consumers.
- Speculative decoding methods for which `use_eagle()` is false.
- Resumable/streaming-input requests whose finalized tail can be replaced.
- Changing Mamba state checkpointing or retention policy.
- Fixing every correctness issue tracked in <https://github.com/vllm-project/vllm/issues/43559>. This proposal is an efficiency optimization with an explicit cache-key safety condition.

### Proposed Change.

#### 1. Include one following token in each EAGLE-style block hash

Let the prefix-match unit be `B`, and let block `i` cover the half-open token range `[s, e)`, where:

```text
s = i * B
e = (i + 1) * B
```

The current chained block hash is conceptually:

```text
H_i = hash(
    H_(i-1),
    token_ids[s:e],
    extra_keys[s:e],
)
```

For colocated EAGLE-style draft models, compute:

```text
H_i_eagle = hash(
    H_(i-1)_eagle,
    token_ids[s:e+1],
    extra_keys[s:e+1],
)
```

`token_ids[e]` is the lookahead token. The overlap is intentional:

- it is the lookahead token of block `i`;
- it is also the first regular token of block `i + 1`.

Existing cache salt, LoRA identity, and multimodal extra-key semantics remain part of the hash chain. If a multimodal placeholder starts at the lookahead position, its identity is included in both the preceding block's lookahead proof and the following block's regular content.

#### 2. Delay publishing a block until its lookahead token is known

A full block is not hash-ready until `B + 1` relevant tokens are available. Therefore:

- if a request ends exactly on a hash boundary, its final block remains pending;
- after the target model produces and finalizes the next token, the pending hash can be computed;
- the block becomes publishable only after the draft-cache entry at position `e - 1` has been materialized or overwritten from target-derived states together with the finalized `token_ids[e]`;
- cache managers must never publish a full or partial cache entry beyond the number of available request block hashes.

Observing `token_ids[e]` in the request is necessary but not sufficient. The scheduler/model-runner ordering must guarantee that the corresponding draft-cache write has completed before the cache manager registers the block.

This does not make the no-lookahead case worse. Today the final block may match and then be dropped. With the proposed key, that block is not considered a hit until its boundary dependency is known.

#### 3. Use a successful lookahead-aware match as proof that no pop is needed

For the new mode, a hit on `H_i_eagle` proves:

1. the target token prefix through the block is the same;
2. the target-derived hidden, auxiliary, or context states used by the drafter for the block are therefore the same;
3. the finalized boundary token used by the drafter is also the same, because `token_ids[e]` is part of the hash;
4. the cached boundary entry was published only after the corresponding draft-cache write completed.

The scheduler and KV-cache coordinator can consequently skip the EAGLE-style last-block drop for these hashes.

The expected behavior is:

| Incoming request state | Final lookahead hash | Behavior |
| --- | --- | --- |
| The following token is not known | Not available | Do not reuse the final block |
| The following token is known and equal | Matches | Reuse the final block without a pop |
| The following token is known and different | Does not match | Fall back to the longest earlier cache hit |

For dense/full-attention cache groups, a next-token mismatch naturally loses the final match unit. For hybrid sparse-retention groups, the reconciled result is the longest earlier prefix jointly available across all cache groups; this proposal does not guarantee that every Mamba retention policy has an earlier checkpoint exactly one unit back.

#### 4. Remove the corresponding Mamba align-mode backoff

The current Mamba align scheduler backs `last_cache_position` off by one aligned block when EAGLE-style prefix lookup drops the final full-attention block. In lookahead-aware EAGLE mode, the full-attention drop is disabled, so the matching Mamba backoff should also be disabled.

This does not change how Mamba states are materialized or retained. It only removes the scheduler backoff that existed to stay consistent with the speculative-decoding cache pop.

#### 5. Enable the mode for every colocated EAGLE-style drafter

The first version should be selected only when all of the following are true:

```text
prefix caching is enabled
AND speculative_config.use_eagle() is true
AND no kv_transfer_config is present
AND KV-cache events are disabled
```

At the time of writing, `use_eagle()` covers `eagle`, `eagle3`, `mtp`, `dflash`, and `dspark`. The implementation should use the capability predicate rather than duplicate this method list. All five methods are in the target scope, but the no-pop path should be enabled for each implementation only after its one-token dependency and cache-publication ordering have been validated.

The speculative configuration is immutable for an EngineCore, so every request using a local prefix cache follows one consistent hash mode. No user-facing flag is required for the initial implementation, although an explicit cache-key mode is listed as an open design question below.

The absence of `kv_transfer_config` is intentionally a conservative gate. It excludes both P/D disaggregation and other external KV connector/offload cases until their transfer contracts are considered.

Resumable/streaming-input requests should remain on the current behavior for the first version. Their tail token may be replaced, so safely enabling this mode would require hash invalidation or delayed publication rules for mutable tails.

### Why P/D Disaggregation Is Out of Scope

P/D introduces more than a configuration check:

- P and D may learn or consume the boundary token at different times.
- Both sides must agree on the cache-key mode.
- Transferred block metadata must identify whether a hash includes a lookahead dependency.
- Remote block trimming must distinguish a cached prefix at the front from an extra lookahead allocation at the back.
- Cache events and external stores may need a versioned key/payload contract.

Issue <https://github.com/vllm-project/vllm/issues/43996> demonstrates a concrete failure caused by P and D having different lookahead/block-allocation behavior. For that reason, this RFC proposes a colocated-only first phase. P/D support should be a follow-up design after role negotiation, transfer ranges, and key semantics are explicit.

### Compatibility and Safety

#### Cache-key isolation

Local block hashes are process-lifetime data. A colocated EngineCore does not mix normal and lookahead-aware EAGLE hashes. External connectors and KV events are excluded, so the first version does not require a cross-process migration or compatibility protocol.

#### Hash collisions

The proposal keeps the configured hash function and its existing collision assumptions. It only adds one token and the corresponding existing extra keys to the hashed payload.

#### Hashing overhead

The additional input is one overlapping token per hash unit. The expected CPU hashing overhead is approximately proportional to `1 / B` of token payload processing and should be negligible compared with avoiding model recomputation. This still needs to be measured.

#### Correctness invariant

A cache block may be reused without the speculative-decoding pop only if the hash key proves equality of every target-derived and boundary-token input needed to construct the reusable draft-model cache entries in that block, and the corresponding draft-cache write is known to have completed before the block is published.

If this invariant cannot be established for a model or speculative method, the existing pop remains the fallback.

### Implementation Outline

A prototype on current `main` uses the following structure:

1. Extend the request block hasher with a configurable lookahead-token count.
2. Select one lookahead token for every local `use_eagle()` prefix-cache path.
3. Compute hashes only for blocks whose lookahead token is available.
4. Ensure the target-derived boundary draft-cache write completes before its hash-ready block is published.
5. Cap cache publication at hash-ready boundaries.
6. Disable speculative last-block popping in the coordinator for this mode.
7. Keep EAGLE-style scheduling behavior, lookahead-slot allocation, and draft input handling unchanged.
8. Disable the Mamba align-mode one-block backoff for this mode.
9. Keep the old behavior for non-EAGLE speculative methods, KV connectors, KV events, and resumable requests.

The prototype does not add a new public CLI option.

### Test and Evaluation Plan

#### Unit tests

- Text block hashing includes exactly one following token.
- The final exact-boundary block stays pending until the following token is appended.
- A matching following token reuses the final block without a pop.
- A different following token falls back to an earlier hash boundary.
- Multimodal extra keys include a lookahead placeholder correctly.
- Cache publication waits for the target-derived boundary draft-cache write.
- Hybrid full-attention + Mamba align mode reuses the same exact prefix length across groups.
- Configuration tests verify that `eagle`, `eagle3`, `mtp`, `dflash`, and `dspark` enable the mode, while P/D, other KV connectors, KV events, non-EAGLE speculative methods, non-speculative serving, and resumable requests do not.

The current local prototype passes the relevant CPU prefix-cache, partial-hit, hashing, and streaming scheduler tests.

#### End-to-end correctness

Before opening the implementation PR, run deterministic output comparisons with prefix caching enabled/disabled and with the optimization enabled/disabled:

- Qwen3.5 or Qwen3.6 hybrid full-attention + GDN/Mamba, `mamba_cache_mode=align`;
- EAGLE/EAGLE3 and MTP, with `num_speculative_tokens` equal to 1 and greater than 1;
- DFlash and DSpark on supported models/configurations;
- identical continuation, changed boundary token, and no-known-lookahead cases;
- A -> B -> A cache perturbation;
- multi-turn tool-use and long-context recall workloads;
- chunked prefill and supported async-scheduling configurations.

Prefix caching must remain behavior-preserving. Any deterministic output divergence is a release blocker.

#### Performance

Measure:

- cached-token count at each request;
- number of tokens recomputed after a cache hit;
- TTFT and prefill latency;
- end-to-end throughput;
- draft acceptance length/rate;
- CPU block-hashing time.

The expected result is to recover one speculative drop unit when the boundary token matches, with no hit-rate regression when it does not. On hybrid models, avoiding one drop may also avoid a much larger aligned Mamba recomputation.

GPU/model evaluation results will be added before the implementation PR is submitted.

### Alternatives Considered

#### Keep the current unconditional drop

This is conservative and simple, but it permanently sacrifices one match unit. The cost is especially visible when hybrid alignment makes that unit large.

#### Skip the drop based on prefill/decode phase

<https://github.com/vllm-project/vllm/pull/44986> proposes skipping the drop during prefill because draft tokens are generated during decode. That is a smaller change and addresses the same performance symptom.

This RFC uses a different safety condition: it makes the cache key prove equality of the EAGLE-style boundary input. The decision to retain the block is content-based rather than phase-based. This distinction is useful when a cache entry was produced by an earlier request and is later consumed during a new request's prefill.

The RFC requests maintainer feedback on whether the phase-based rule is sufficient for every EAGLE-style cache lifecycle, or whether the stronger key invariant is preferable.

#### Drop or rewind a Mamba state correctly

The following work focuses on correctness when hybrid cache groups disagree or when Mamba must honor the speculative boundary:

- <https://github.com/vllm-project/vllm/pull/43650>
- <https://github.com/vllm-project/vllm/pull/45614>
- <https://github.com/vllm-project/vllm/pull/46281>
- <https://github.com/vllm-project/vllm/pull/48375>

Those approaches preserve or repair the backoff. This proposal is materially different: it strengthens the cache key so the backoff can be skipped when the boundary input actually matches. The approaches can remain complementary as a safe fallback.

#### Do not cache the speculative boundary block

Avoiding publication of the boundary block is safe, but it gives up the same reuse opportunity. Delaying publication until the finalized lookahead token is known retains safety while allowing later continuations to reuse it.

#### Cache additional target hidden states

Persisting the target hidden states required by the drafter could avoid recomputation, but it adds a separate cache payload and lifecycle. Encoding the shifted-token dependency in the existing key is smaller and keeps the current KV/state storage model.

The open work above establishes both the correctness problem and the cost of the conservative drop. The proposed contribution is not another unconditional “skip pop” patch and not another Mamba rewind patch. Its distinct contribution is a cache-key contract that includes the finalized boundary token, allowing the cache hit itself to prove that the final EAGLE-style draft block is reusable. Although several motivating reports use MTP models, the cache contract and proposed scope cover every method represented by `use_eagle()`.

### Open Questions

1. Should this be an internal `use_eagle()` policy, or should vLLM introduce an explicit cache-key/hash mode?
2. Should a discriminator such as `eagle_lookahead_v1` be included in the initial hash payload even though the first version is process-local?
3. Should the `use_eagle()` contract explicitly guarantee one finalized-token boundary dependency, or should each drafter report its required cache-key lookahead count?
4. What method-specific validation should accompany the shared invariant for EAGLE3 auxiliary hidden states and DFlash/DSpark parallel drafting?
5. What metadata and versioning would be required before enabling KV events or external KV connectors?
6. For future P/D support, should P compute/publish the lookahead-aware hash, should D do so after transfer, or should the hash mode be negotiated and carried in transfer metadata?
