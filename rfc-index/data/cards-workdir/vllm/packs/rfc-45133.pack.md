## 正文(PRD / 提案全文)

### Motivation.


### Background

vLLM uses Triton kernels in many places, including sampling, attention, normalization, mamba/copy, and speculative decoding. These kernels are designed and optimized specifically for GPU. Some other hardwares can not run these kernels directly. Here I take Ascend NPU as an example to explain the compatibility problem.

#### Functional limitations

1. **Grid mapping limitations**: GPU uses logical grid dimensions decoupled from physical cores, while NPU uses physical core-bound mapping. Grid size must not exceed AI Core count, and 2D grids must match the hardware topology. Large or multi-dimensional grids commonly used in vLLM kernels cause functional errors on NPU.

2. **Data type limitations**: NPU vector units do not support certain data types (e.g., int64 for Vector ADD, int64/int32 for Vector CMP). Kernels using these types produce incorrect results or fall back to scalar operations.

3. **Memory access alignment**: NPU requires 32-byte alignment for vector operations and 512-byte alignment for cube-vector fused operations. GPU kernels often use different alignment assumptions.

4. **TL.dot constraints**: NPU has specific requirements for M/N/K tile sizes, accumulation dtype, and output dtype in tl.dot operations that differ from GPU Tensor Core constraints.

5. **Missing GPU-specific APIs**: CUDA thread, stream, event, and kernel synchronization APIs are unavailable on NPU.

#### Performance problem

Even when kernels can functionally run on NPU, they suffer severe performance degradation:

1. **Excessive grid parallelism**: GPU kernels often launch grids with far more logical programs than NPU physical cores, causing multi-round dispatch overhead and excessive launch latency.

2. **Lack of NPU-optimized tiling**: GPU kernels lack the inner-loop tiling (XBLOCK/XBLOCK_SUB) pattern that NPU needs for efficient on-chip memory utilization (192KB UB capacity on Atlas 800T/I A2). Without proper tiling, kernels either overflow UB or fail to enable multi-buffer instruction parallelism.

3. **Missing NPU-specific compiler optimizations**: triton-ascend supports AscendNPU IR optimizations like multibuffer, unit_flag, tile_mix_vector_loop, etc. that are not configurable in GPU-oriented kernels.

4. **Synchronization overhead**: tl.load with partial mask filling (default other=0 behavior) causes unnecessary Vector-MTE synchronization on NPU, reducing instruction parallelism.

### Proposed Change.


### Current Status

vllm-ascend now has rewritten over **55 Triton kernels** with NPU-specific implementations. However, the current approach uses **monkey-patching** to replace upstream vLLM kernels at runtime:

```
# vllm_ascend/patch/worker/patch_triton.py
import vllm.model_executor.layers.mamba.ops.causal_conv1d
vllm.model_executor.layers.mamba.ops.causal_conv1d.causal_conv1d_update = causal_conv1d_update_npu
vllm.model_executor.layers.mamba.ops.causal_conv1d.causal_conv1d_fn = causal_conv1d_fn

# vllm_ascend/patch/worker/patch_mamba_utils.py
mamba_utils.batch_memcpy_kernel = batch_memcpy_kernel
mamba_utils.batch_memcpy = batch_memcpy
```
There is no need to explain the problem of monkey-patching again here. In short, it makes the codebase more complex and harder to maintain. Even worse, it can lead to subtle bugs and performance issues.

### Target

I propose adding a **Triton Kernel Dispatcher** module (vllm/model_executor/triton_dispatcher.py) that provides two decorators:

- @pluggable_kernel: Applied to the default (CUDA) Triton kernel in vLLM core code, making it replaceable.
- @register_kernel(name): Applied to a platform-specific override in a hardware plugin, registering it under a unique name.

The dispatcher preserves the standard Triton invocation syntax kernel[grid](...), so existing call sites require zero changes.

1. Marking a kernel as pluggable (in vLLM core):
```
from vllm.model_executor.triton_dispatcher import pluggable_kernel
from vllm.triton_utils import tl, triton

@pluggable_kernel
@triton.jit
def expand_kernel(output_ptr, replace_from, replace_to, ...):
    ...
```

2. Registering a platform-specific override (in a hardware plugin):
```
from vllm.model_executor.triton_dispatcher import register_kernel

@register_kernel("vllm.v1.sample.rejection_sampler.expand_kernel")
def npu_expand_kernel(*args, grid=None, **kwargs):
    # NPU-specific implementation
    ...
```

Or equivalently as a function call:
```
register_kernel("vllm.v1.sample.rejection_sampler.expand_kernel")(npu_expand_kernel)
```

3. Dispatch behavior:

When `kernel[grid](args)` is called:
- If a registered override exists: the dispatcher calls override(args, grid=grid, **kwargs)
- If no override exists: the dispatcher falls back to the default Triton kernel with native kernel[grid](args) syntax

This means:
- On CUDA: no override registered, so default kernel runs with zero overhead
- On NPU: the Ascend plugin registers overrides at startup, and NPU implementations are dispatched
- On Other Platforms: just registers its implementations similarly


4. KernelDispatcher class

The KernelDispatcher wraps a default Triton kernel and provides:

- __call__(*args, **kwargs): Dispatches to override (if registered) or default
- __getitem__(grid): Returns a _KernelLauncher for overrides (passing grid as keyword arg), or delegates to default_kernel[grid] for native Triton behavior
