## 正文(PRD / 提案全文)

### Motivation.

HiSparse already offloads large sparse-MLA (DSA) main KV to CPU memory, keeps lightweight indexer KV on GPU, and resolves decode KV on demand from top-k indices. However, as noted in the [HiSparse design doc](https://github.com/vllm-project/vllm/blob/55aa0cab78dedbb018ad4f4ea649f2d3d5e1c2a8/docs/design/hisparse.md#L219-L220), *"prefill and mixed prefill/decode batches retain per-layer staging."* This proposal builds on HiSparse's CPU offload framework to complete prefill data loading and buffering. Long-context prefill requests typically fall into two patterns. **Short-append requests** (common in multi-turn agent and coding workloads) hit long CPU-cached prefixes with only a few new tokens; per-layer compute is brief, so H2D history loading dominates latency. **Large-chunk requests** (such as later chunks in chunked prefill or long appends after a CPU prefix hit) have longer per-layer compute windows, while concurrency and long sequences put heavy pressure on GPU memory capacity. In practice, the scheduler frequently batches both request types together.

For short-append requests, indexer KV stays on GPU and produces top-k indices before main KV is loaded, yet [HiSparse's current prefill path](https://github.com/vllm-project/vllm/blob/55aa0cab78dedbb018ad4f4ea649f2d3d5e1c2a8/vllm/v1/hisparse/runtime.py#L785) builds a full-history staging layout and reads every non-resident history row from CPU. Under tensor parallelism (where MLA main KV is replicated across ranks), every TP rank independently reads the full history from the shared host pool, multiplying host memory read-bandwidth pressure by `TP`. On `GLM-5.2` (`K = 2048`) across real agent trajectories and repository code (see [Supplementary](#supplementary)), appending `128` tokens to a `512K` history selects a per-layer top-k union covering only **1.2%–2.4%** of history on average (about `1%` extrapolated to `1M`). Over 97% of full-staging host reads go unused. **Stage 1 (PR1)** filters host gather by the top-k row union, cutting host reads in colocated deployments with minimal changes.

Stage 1 eliminates wasted reads for short appends, but as new query tokens grow (e.g., `Q ≥ 1024` or larger chunks), the top-k union widens rapidly—reaching 25%–50%+ on moderate histories or individual layers. Scattered row gather then saves far less data, achieves lower H2D bandwidth than contiguous page copies, and stalls serially behind each layer's top-k step. Meanwhile, large-chunk requests have long enough per-layer compute windows to hide contiguous transfers via **layerwise full-page prefetch overlapped with compute**. On the memory side, disaggregated prefill (P) nodes can cache long prefixes in a large CPU host pool with LRU reuse; once KV is handed off, they no longer need per-layer GPU-resident main KV or local decode hot buffers. After a small prerequisite PR adds generic NIXL mixed-memory export to unblock P-nodes, **Stage 2 (PR2)** alternates all main-KV layers across two physical GPU slots on P-nodes—hiding next-layer full-page loads behind current-layer compute while shrinking P-node GPU KV footprint.

When short-append and large-chunk requests share a batch, running full-page prefetch for all requests triggers large H2D transfers for short appends that their brief compute cannot hide, creating wait bubbles. Conversely, running on-demand gather for all requests stalls large chunks after top-k and forfeits cross-layer overlap. **Stage 3 (PR3)** lets both request types share the same two slots within one batch, splitting loading paths per request before executing sparse attention together.

### Proposed Change.

Building on HiSparse's CPU source pages and host gather, we evolve the prefill path in three stages—on-demand gather, layerwise two-slot reuse (following [#33398](https://github.com/vllm-project/vllm/issues/33398) and [#48203](https://github.com/vllm-project/vllm/issues/48203)), and mixed-batch loading—while keeping existing scheduling, block allocation (`schedule` / `allocate_slots`), and the downstream sparse-attention call contract unchanged:

| Stage & Target Workload | GPU Main-KV Buffer | Host→GPU Loading & Timing | Target Deployment |
| --- | --- | --- | --- |
| **Baseline**: Current HiSparse prefill | Existing resident pool + single-layer temp staging | Synchronously gathers all host-miss rows per layer (no cross-layer overlap) | Colocated (and disaggregated D-node import) |
| **PR1**: Low-compute short appends with prefix hits | Same as baseline (full staging layout unchanged) | Gathers only host-miss rows in the top-k union (after current-layer top-k) | Colocated initially (extends to P/D after NIXL PR) |
| **PR2**: Large chunks & high concurrency | Two `num_blocks`-sized physical slots shared by even/odd layers | Contiguous full-page (`FULL`) prefetch overlapped with previous-layer compute | Disaggregated P-node (requires NIXL mixed-memory PR) |
| **PR3**: Mixed short appends & large chunks | Shares PR2's two slots | Cross-layer `FULL` prefetch for large chunks + on-demand row gather (`DEMAND`) for short appends | Disaggregated P-node |

### Stage 1: Top-K-Filtered On-Demand Gather (PR1)

Using the current batch's staging block table, PR1 remaps logical prefill top-k indices to destination staging rows. During remapping, it records the union of rows selected across all prefill queries in a GPU mask without host synchronization, intersects that mask with the existing host-miss mask, and gathers only the selected missing rows from pinned host memory (GPU-resident rows are likewise copied only when selected). Downstream sparse attention consumes the remapped row indices directly.

This preserves the existing KV cache layout and sparse-attention interface: staging keeps its full layout, and newly generated KV is written at the same offsets as before. PR1 initially targets colocated deployments with changes self-contained inside HiSparse. The only added overhead is building the union mask on GPU, and the filtered host gather runs right after current-layer top-k.

### Stage 2: Layerwise Two-Slot Reuse and Prefetch Overlap (PR2)

For large-chunk requests with many new queries and wide top-k unions, scattered row gather offers lower bandwidth efficiency and longer post-top-k stalls, while per-layer compute is long enough to hide contiguous transfers. PR2 pairs asynchronous full-page prefetch with two-slot layerwise reuse. Full main-KV history stays per layer in the CPU host pool; on GPU, `num_blocks` is sized from `(all-layer indexer + 2 main-KV slots)`, and `KVCacheTensor` aliases even and odd layers onto two `num_blocks`-sized physical slots (`Slot 0` and `Slot 1`). This reuses `schedule`, `allocate_slots`, and native `block_table` / `slot_mapping` directly without custom admission checks or page-table remapping. While layer `L` computes on its active slot and writes newly generated KV back to CPU asynchronously, a background prefetch stream loads layer `L+1`'s historical blocks into the other slot; a slot is overwritten only after both prior reads and CPU writeback complete. PR2 initially targets disaggregated P-nodes.

This builds on the layerwise reuse design in [#48203](https://github.com/vllm-project/vllm/issues/48203) (which proposes 2–4 buffers). Because current-layer CPU writeback runs concurrently with compute, two slots are enough for a single H2D prefetch stream whenever writeback finishes in time and next-layer H2D fits inside the compute window. If single-layer H2D exceeds compute, adding more slots on the same H2D channel cannot reduce steady-state per-layer latency. We plan to collaborate with [@zhangsicheng5](https://github.com/zhangsicheng5) and the #48203 team to bring layerwise reuse to GPU and align on cache allocation and layerwise loading interfaces.

*Consecutive layers alternate between Slot 0 and Slot 1, prefetching next-layer historical KV concurrently with current-layer compute and async CPU writeback.*

### Stage 3: Mixing Full-Page and On-Demand Loading in One Batch (PR3)

Building on PR2, PR3 keeps the same two-slot block locations from the native `block_table` and splits requests by loading mode during worker batch preparation. Compute-heavy or wide-union requests take the full-page path (`FULL`), prefetching whole history blocks into their assigned slot blocks ahead of time. Long-history, short-append requests take the on-demand path (`DEMAND`): history-only blocks skip full-page prefetch, and after current-layer top-k, a GPU kernel gathers only the selected missing rows into their corresponding intra-block offsets (all other blocks use `FULL` directly without reallocation).

To prevent background bulk transfers from slowing down latency-critical on-demand gather on the current layer, layer `L+1`'s `FULL` prefetch starts after layer `L`'s on-demand H2D completes, overlapping with layer `L`'s sparse attention / FFN and layer `L+1`'s QKV / indexer top-k. Once both paths have populated layer `L`'s historical KV, the entire batch runs in a single sparse-attention call.

![FULL and DEMAND share two slots for joint batch compute, converging before Sparse Attention after split loading](https://github.com/user-attachments/assets/c7326566-1920-466d-aaf6-e51536b2ba4f)

*Layer L FULL finishes its prior-layer prefetch during QKV/Top-K while DEMAND gathers selected rows after Top-K. Both converge before Sparse Attention, and Layer L+1 FULL prefetch starts after Layer L on-demand H2D to overlap through Layer L+1 Top-K.*

Capacity sizing and P/D handoff details are summarized in [Supplementary](#supplementary).

**PR Breakdown**

- **PR1**: Add top-k-union-filtered on-demand gather to HiSparse prefill while keeping the full staging layout and backend contract unchanged, initially supporting colocated deployments.
- **Prerequisite PR (NIXL)**: Extend existing [NIXL CPU KV support](https://github.com/vllm-project/vllm/blob/55aa0cab78dedbb018ad4f4ea649f2d3d5e1c2a8/vllm/distributed/kv_transfer/kv_connector/v1/nixl/base_worker.py#L1716) with generic [producer-side mixed-memory (DRAM + VRAM) export](https://github.com/vllm-project/vllm/blob/55aa0cab78dedbb018ad4f4ea649f2d3d5e1c2a8/vllm/distributed/kv_transfer/kv_connector/v1/nixl/base_worker.py#L2759-L2762) to support HiSparse (including PR1) on disaggregated P-nodes and unblock P/D delivery for PR2/PR3.
- **PR2**: Implement P-node two-slot reuse in HiSparse via cross-layer tensor aliasing, overlapping next-layer full-page KV prefetch with current-layer compute.
- **PR3**: Over the same two slots, split `FULL` prefetch and `DEMAND` on-demand gather per request on the worker side and execute joint attention within one batch.

We have not yet completed end-to-end GPU benchmarks for this design. Upcoming validation will cover each stage: PR1 will measure GPU top-k union ratios across history lengths and query counts, verifying output equivalence and comparing host bytes read and gather bandwidth against full staging. PR2 will inspect GPU timelines to verify cross-layer transfer/compute overlap (including host-bandwidth limits under multi-GPU TP concurrent prefetch), measure max concurrency under a fixed HBM budget, compare TTFT and throughput at matched concurrency, and verify complete KV handoff over P/D. PR3 will evaluate mixed batches on the same two slots against all-`FULL` and all-eligible-`DEMAND` baselines.

We propose landing two-slot layerwise reuse first as a P-node prefill residency mode within HiSparse, implementing slot synchronization and lifecycle management on the existing [KVConnector layerwise load/save hooks](https://github.com/vllm-project/vllm/blob/55aa0cab78dedbb018ad4f4ea649f2d3d5e1c2a8/vllm/distributed/kv_transfer/kv_connector/v1/hisparse/connector.py#L358-L371). We can then review with the #48203 authors and maintainers which abstractions should be promoted to generic `KVConnector` interfaces.

## Supplementary

### How Many History Rows Does On-Demand Gather Read?

With `H` historical rows, `Q` new queries in the current step, and at most `K` rows selected per query, the worst-case union size (with zero overlap across queries) is `min(H, Q × K)`, and only non-GPU-resident rows in the union are read from CPU. We measured exact row-level top-k unions `|union|` on `GLM-5.2` (`K = 2048`) across two real-world corpora:

1. **Multi-turn coding-agent trajectories** (OpenHands / Terminus2 trajectories from Tracebench): At `Q = 128`, the per-layer, per-request union size plateaus around `6.6K–8.7K` rows as `H` grows—covering **12.6% / 6.6% / 2.9% / 1.25%** of history at `H = 64K / 128K / 256K / 512K` (about `3.2×–4.2× K`). At `Q = 1024`, union coverage rises to **32%–45%** at `H = 64K` (10-layer to 42-layer averages) and **4.0%–5.7%** at `H = 512K` (about `21K–30K` rows).
2. **Long-context repository code** (194 concatenated source files with broader cross-file attention; 10-layer mean union rows and share of `H`):

| History `H` \ New Queries `Q` | `Q = 128` | `Q = 256` | `Q = 512` | `Q = 1024` |
| --- | --- | --- | --- | --- |
| **`64K`** | 8,838 (**13.5%**) | 12,046 (**18.4%**) | 16,854 (**25.7%**) | 23,922 (**36.5%**) |
| **`128K`** | 11,058 (**8.4%**) | 15,760 (**12.0%**) | 22,536 (**17.2%**) | 32,771 (**25.0%**) |
| **`256K`** | 11,932 (**4.6%**) | 17,144 (**6.5%**) | 25,547 (**9.8%**) | 38,794 (**14.8%**) |
| **`512K`** | 12,743 (**2.4%**) | 18,598 (**3.6%**) | 28,526 (**5.4%**) | 45,218 (**8.6%**) |

At `256K + Q=64`, the mean union is `8,378` rows (**3.2%**). Per-request union sizes stay stable under multi-request concurrency, while union coverage varies by roughly `4×` from layer to layer (reaching **40.4%** on individual layers at `128K + 1024` and **53.3%** at `64K + 1024`). This aligns with the strong query-to-query overlap (84%–90% shared positions) reported on DeepSeek-V3.2 (128K RULER-QA) in [PIVOT Preliminary (O1–O2) and Appendix C](https://arxiv.org/html/2607.24593). Together, these numbers show a clear trade-off: at small `Q`, union row counts grow very slowly with `H` (strongly favoring on-demand gather on long histories), whereas large `Q` or moderate `H` widens the union quickly (favoring contiguous full-page prefetch)—motivating request routing based on both `H` and `Q`. End-to-end GPU host-read volumes at `1M` history on DeepSeek-V3.2 and GLM-5.x will be measured in PR1.

### HiSparse Integration and Capacity

Full per-layer main KV lives in the CPU host pool (`HiSparseSourceManager`), sized independently from the host memory budget for cross-request LRU prefix reuse, while all-layer indexer KV stays on GPU. P-nodes omit per-layer GPU-resident main KV and local decode hot-cache groups. Instead, available GPU KV memory is divided across `(all-layer indexer + 2 main-KV slots)` to yield a unified GPU `num_blocks`, with even and odd layers aliased onto the two physical slots via `KVCacheTensor`. For example, on `GLM-5.3` with FP8 KV (78 main-KV layers and 21 shared indexers), two-slot reuse shrinks the physical main-KV footprint to 2/78 of a standard all-layer GPU P-node—saving about **92.4%** of total GPU KV memory (indexer included) and expanding allocatable `num_blocks` by about **13.2×** within the same HBM budget (alongside zero decode hot-cache overhead). [HiSparse cache layout](https://github.com/vllm-project/vllm/blob/55aa0cab78dedbb018ad4f4ea649f2d3d5e1c2a8/vllm/v1/hisparse/layout.py#L414) · [KVCacheTensor aliasing](https://github.com/vllm-project/vllm/blob/55aa0cab78dedbb018ad4f4ea649f2d3d5e1c2a8/vllm/v1/worker/utils.py#L597-L599)

For P/D handoff, once newly generated KV across layers has been written back and synchronized to CPU, NIXL exports the complete CPU main KV alongside GPU indexer KV (supported by extending existing [NIXL CPU KV support](https://github.com/vllm-project/vllm/blob/55aa0cab78dedbb018ad4f4ea649f2d3d5e1c2a8/vllm/distributed/kv_transfer/kv_connector/v1/nixl/base_worker.py#L1716) with the prerequisite [producer-side mixed-memory export](https://github.com/vllm-project/vllm/blob/55aa0cab78dedbb018ad4f4ea649f2d3d5e1c2a8/vllm/distributed/kv_transfer/kv_connector/v1/nixl/base_worker.py#L2759-L2762) PR), retaining source blocks until transfer completes.

Source baseline: [`55aa0cab`](https://github.com/vllm-project/vllm/commit/55aa0cab78dedbb018ad4f4ea649f2d3d5e1c2a8).
