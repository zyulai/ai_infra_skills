## Purpose

Fixes #56363.
Fixes #58406.

vLLM accepts `mm_processor_kwargs` from both engine configuration and per-request overrides, and supports both legacy flat kwargs and Hugging Face modality-scoped kwargs such as `images_kwargs` and `videos_kwargs`.

This PR defines consistent semantics across those two dimensions:

* **Generic vLLM handling** defines precedence across engine/request and flat/modality-scoped kwargs, discovers the supported HF processor kwargs per scope, and routes flat kwargs to the HF modality scopes that support them.
* **Model-specific handling** provides processor semantics that cannot be inferred generically.
  * For Qwen2-VL/Qwen3-VL, for example, `min_pixels` / `max_pixels` correspond to `size.shortest_edge` / `size.longest_edge`.


```text
                           Qwen semantic preparation
                               alias completion
                                      |
                                      ▼
                                 generic vLLM
                                      |
          ┌───────────────────────────┼───────────────────────────┐
          │                           │                           │
 source/scope precedence       supported schema            flat → HF scopes
     MultiModalConfig         BaseProcessingInfo        InputProcessingContext
          │                           │                           │
          └───────────────────────────┼───────────────────────────┘
                                      |
                               resolved kwargs
                                      |
                              Qwen/HF adaptation
                                      |
                               Transformers / HF
```

### Generic `mm_processor_kwargs` handling

`MultiModalConfig.merge_mm_processor_kwargs()` now applies source and modality specificity together. For an effective setting within a modality, the precedence is:

```text
engine flat
< engine scoped
< request flat
< request scoped
```

- When both values are mappings, they are merged recursively so a higher-priority partial override does not discard unrelated lower-priority entries.
- For other value combinations, the higher-priority value replaces the lower-priority one.
   - At the modality-scope level, a missing scope, a `None`-valued scope (e.g., ` {"images_kwargs": None}`), and an empty mapping are treated as absent and therefore do not participate in replacement. This applies only to the scope itself; an explicit `None` inside a non-empty scope remains a value.

This is deliberately more specific than a recursive merge of engine and request dictionaries: source precedence alone is not sufficient when the same effective setting can also be represented flat or inside a modality scope.

`BaseProcessingInfo` derives the supported processor kwargs for each HF scope from the processor contract and the modalities supported by the model. This keeps schema discovery generic for HF-compatible processors instead of requiring each model family to reimplement it.

`InputProcessingContext` then resolves flat kwargs using that per-modality processor schema:

```text
0 supported scopes → keep flat
1 supported scope  → route to that scope
N supported scopes → fan out to every supported scope
```

For example, if `size` is supported by both image and video:

```python
{"size": X}
```

is resolved as:

```python
{
    "images_kwargs": {"size": X},
    "videos_kwargs": {"size": X},
}
```

while a video-specific override remains isolated to video:

```python
{
    "size": X,
    "videos_kwargs": {"size": Y},
}
```

becomes:

```python
{
    "images_kwargs": {"size": X},
    "videos_kwargs": {"size": Y},
}
```

When flat and scoped values are both mappings, they are composed recursively with the scoped value taking precedence.

Unknown kwargs are preserved. Without a supported-key schema, vLLM does not guess destinations or create scopes; it only removes redundant flat copies already represented inside recognized HF scopes. This keeps existing callers conservative while preventing lower-priority flat values from being reintroduced alongside an already-resolved scoped representation.

### Qwen-specific handling

The generic layer intentionally does not know that different processor kwargs can represent the same model setting. Qwen therefore prepares its semantic aliases before the generic merge:

```text
size.shortest_edge ↔ min_pixels
size.longest_edge  ↔ max_pixels
```

This is alias completion rather than canonicalization. It makes request precedence visible even when engine configuration and request express the same Qwen setting through different aliases, while preserving explicitly supplied values.

Qwen uses the generic per-scope schema discovery from `BaseProcessingInfo`. Qwen3-VL only extends that schema where vLLM intentionally supports compatibility input that is not part of the native HF video processor contract: `min_pixels` / `max_pixels` are added as video routing targets even though `Qwen3VLVideoProcessor` accepts the equivalent setting through `size`.

Qwen sizing consumers now read the resolved `images_kwargs` / `videos_kwargs` scopes directly rather than requesting a temporary flat view for one modality. Effective vision size remains Qwen-specific:

```text
processor defaults
< size
< non-None min_pixels / max_pixels
```

Qwen3-VL also applies those effective-size semantics at the HF boundary. If an image or video scope contains a `size`, `min_pixels`, or `max_pixels` override, the effective `size` is completed from the corresponding processor defaults before calling HF. This keeps runtime preprocessing consistent with the size used by vLLM's own sizing logic and allows partial scoped `images_kwargs.size` and `videos_kwargs.size` overrides to work correctly.

The final HF representation differs slightly between image and video:

```text
images_kwargs
    processor defaults
        + size
        + min_pixels / max_pixels
            │
            ▼
      complete size
            │
            ▼
     HF image processor
     (min/max remain valid)


videos_kwargs
    processor defaults
        + size
        + min_pixels / max_pixels
            │
            ▼
      complete size
            │
      remove min/max
            │
            ▼
     HF video processor
```

For images, `min_pixels` / `max_pixels` are valid HF kwargs and remain present.

For video, vLLM has historically accepted flat `min_pixels` / `max_pixels`, while `Qwen3VLVideoProcessor` expects the equivalent setting as `size`. Qwen3-VL therefore folds those compatibility aliases into `videos_kwargs.size` and removes the unsupported aliases before any HF call, including text/image-only calls.

For multi-video requests, list-valued `fps` / `num_frames` are converted to the corresponding scalar for each video using independent copies of the resolved kwargs. This preserves the shared merged state and the existing sampling/timestamp behavior.

### Compatibility and related work

- Legacy flat kwargs and HF-style scoped kwargs remain supported.
- Shared flat values continue to apply to every modality whose HF processor schema advertises support for them, while scoped values specialize only their own modality.
- Partial Qwen3-VL image and video size overrides are resolved against the corresponding processor defaults before reaching HF.
- Qwen3-VL keeps its historical flat `min_pixels` / `max_pixels` video compatibility while presenting HF with the native `size` representation.
- Unknown kwargs are retained, and the generic resolver does not attempt to become a universal HF processor validator or model-specific canonicalizer.

This work is broader than #58408: that PR recursively merges nested mappings within the same dictionary path, but explicitly leaves flat/scoped precedence and modality resolution for follow-up. This PR covers that full contract together with the Qwen-specific semantics needed to resolve #56363.

No documentation update is included because this is a bugfix to the existing `mm_processor_kwargs` behavior rather than a new user-facing option.

## 🛠️ Changes since the first review

The first review surfaced three issues in the `mm_processor_kwargs` merge/resolution path. The current implementation was adjusted as follows:

- **Normalize empty modality scopes:** `MultiModalConfig.merge_mm_processor_kwargs()` now treats a missing scope, a `None`-valued scope, and an empty mapping as absent, so none of them creates a scoped entry.
  - This applies only to the scope itself: an explicit `None` inside a non-empty scope remains a value, while other non-mapping scope values remain explicit and follow normal source precedence.
  - Keeping this normalization in the generic merge avoids duplicating empty-scope handling in model-specific code.

- **Move schema-aware merge/resolution to `BaseProcessingInfo`:** `_merge_and_resolve_mm_processor_kwargs()` now lives in `BaseProcessingInfo`, providing the common path for merging configured/request kwargs and resolving flat keys using `supported_mm_processor_kwargs`.
  - Qwen still prepares its `size` / `min_pixels` / `max_pixels` aliases first, then delegates to the base implementation.
  - Mistral3 now uses the same path and reads the resolved `images_kwargs.size` for its internal sizing, keeping vLLM's placeholder/token calculations aligned with the effective size used by Pixtral/HF, including configured-flat / request-scoped precedence.

- **Cache supported processor kwargs per `ProcessingInfo`:** `supported_mm_processor_kwargs` is now a `cached_property`, so the supported kwargs discovered from the HF processor are computed once per processing-info instance.
  - `get_supported_mm_processor_kwargs()` remains overridable, so model-specific additions such as Qwen3-VL's video `min_pixels` / `max_pixels` compatibility support are included in the cached result.
  - Only this processor-derived metadata is cached; request-specific merge/resolution remains dynamic, avoiding repeated processor introspection in sizing/profiling paths.
