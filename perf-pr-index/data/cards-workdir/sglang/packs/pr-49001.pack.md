## PR body

## Motivation

#47964 runs `CustomAllReduceV2` (carv2) on ROCm, with a workspace shared by POSIX fd and a launch table tuned on MI350X, and leaves ROCm dispatch on AITER. On MI450 (gfx1250) that table makes carv2 lose to RCCL in serving: DeepSeek-V4-Flash TP8 at C64 was 21% behind (1,628 vs 2,051-2,105 tok/s).

In SGLang decode the ranks reach each all-reduce at different times. A C64 trace with the MI350X table showed `1shot_push` on a 96-block grid (one block per CU) spending most of each call waiting for peers (p50 86 us vs p10 18 us per 512 KB call) and the compute kernels around it running 15-20% slower.

This PR shares the workspace by FABRIC handle on devices that support it, lets ROCm opt in to carv2, and gives MI450 its own thresholds, push grid and `2shot_push` block size. With it, carv2 beats RCCL in DeepSeek-V4-Flash serving on 8x MI450 by 11.1% at C64 and 5.5% at C256.

## Modifications

**FABRIC handles** (`srt/utils/hip_vmm_utils.py`)
- `HipSymmetricBuffer` can export each rank's VMM allocation as a 64-byte `hipMemFabricHandle_t` and exchange the handles with `all_gather_object`, instead of POSIX fds over `SCM_RIGHTS`.
- `SGLANG_HIP_VMM_HANDLE_TYPE` (new, `srt/environ.py`): `auto` (default; FABRIC when `hipDeviceAttributeHandleTypeFabricSupported` is set, else POSIX fd), `fabric`, or `posix_fd`.
- Ranks agree on the handle type in the existing allocation agreement, so a mismatch raises on every rank instead of leaving peers blocked in the exchange. Rank 0 logs the buffer size and handle type.

**ROCm dispatch** (`device_communicators/custom_all_reduce.py`)
- `dispatch_custom_allreduce` selects `CustomAllReduceV2` on ROCm only when `SGLANG_OPT_USE_CUSTOM_ALL_REDUCE_V2=1` is set explicitly. The default stays AITER; CUDA is unchanged.

**gfx1250 table** (`configs/custom_all_reduce_v2.py`, `jit/csrc/distributed/custom_all_reduce.cuh`; selected by `gcnArchName`, MI350X keeps its table)
- `1shot_push` up to 64 KB, `2shot_push` up to 8 MB, no pull algorithms; larger all-reduces fall back to RCCL.
- Push grid of 64 blocks instead of one per CU (96).
- `2shot_push` launches 256 threads per block up to 4 MB, where the default rule picks 512-1024 from 512 KB.

**How the table was chosen.** TP8 sweeps over 4 KB-16 MB in three modes: back to back, with one rank arriving late, and with one rank late plus a GEMM before each all-reduce (the decode pattern). First grid (8-96) x threads (auto/128/256/512/1024), two runs per point; then grid 32/64/96 at a fixed 256 threads, four runs per point. Against the MI350X table (geomean over sizes) the result is about 0.92x back to back, 0.5x with a late rank, and 0.4x with GEMM + late rank.
- At 256 threads, grid 64 is within ~4% of the best of 32/64/96 in every mode (96 is 4% faster back to back but 14% slower with GEMM + late rank; 32 is 22% slower back to back).
- The pull algorithms lose to `2shot_push` or RCCL at every size, and a 64-block `2shot_push` is slower than RCCL at 16 MB, hence the RCCL fallback above 8 MB.
- Back to back, `1shot_push` is faster than `2shot_push` at 128-256 KB (7.6 vs 12.0 and 10.2 vs 13.1 us); the 64 KB cutoff is for the skewed case, where `1shot_push` loses 30-60% there.
- Push grids above the CU count are not safe: 128 push blocks hung the GPUs at 1 MB.
- The thresholds are tuned at TP8 only.
