## Motivation

`--startup-weight-load-mode=overlap` overlaps checkpoint prefetch with decode CUDA-graph capture to shorten model startup, but it was gated as CUDA-only: the options resolved `is_cuda_platform` and `device == "cuda"`, so NPU was rejected. This enables the overlap path on NPU, where the decode graph is still captured and the prefill graph (`TC_PIECEWISE` by default) is disabled — `tc_piecewise` prefill bakes weights during `torch.compile` and is unsafe for commit-after-capture.

## Modifications

- Add `is_npu` to `StartupWeightLoadOptions` and populate it from `current_platform.is_npu()`.
- Relax the overlap startup validation rule from CUDA-only to CUDA-or-NPU (`is_cuda_platform or is_npu`; `device in ("cuda", "npu")`), updating the message to `"CUDA or NPU only"`.
- Replace the hard-coded `torch.cuda.synchronize()` with the device-agnostic `current_platform.synchronize()`.
- CUDA behavior is unchanged.

## Accuracy Tests

Validated on NPU by the e2e case `test_npu_startup_weight_load_mode.py` (companion test branch `test/npu-startup-weight-load-mode`): launching Qwen3-32B with `tp=2` and the prefill graph disabled, in both `serial` and `overlap` modes, and asserting the generated text contains "Paris". This proves the sentinel weights baked during capture are replaced by real weights after commit — a baked-sentinel graph would output gibberish. The unit test `test_startup_weight_load.py` is updated with the new `is_npu` option, asserts `StartupWeightLoadManager` is selected for `device="npu"`, and expects the updated `"CUDA or NPU only"` rejection message.

## Speed Tests and Profiling

The e2e test measures startup wall-clock (process start → first `/health_generate` 200) for `serial` vs `overlap` on Qwen3-32B / `tp=2`, prints the speedup, and guards against overlap being more than 2x slower than serial (CI timing noise). This change only enables the overlap startup path on NPU (reduces startup latency); per-token throughput is unaffected, and the CUDA path is untouched.
