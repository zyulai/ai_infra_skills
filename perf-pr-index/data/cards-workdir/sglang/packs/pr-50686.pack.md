```markdown
## Motivation

The row-major split-K path of `kernels/ops/gemm/bf16_tiled_small_m_gemm.py` (`rowmajor_gemm` / `rowmajor_gemm_partials`) runs the BF16 small-M GEMMs of the Muse Spark decode / verify step on MI355X. In every TP8 step it runs the attention O projection `[8192, 1024]` and the MoE unpooler `[8192, 4096]`, about 1.4 ms per step. The same path also serves the pooler, the BF16 joint router/pooler, the DFlash draft model and the generic unquantized linear on ROCm.

The kernel is memory bound. At 64 rows the unpooler streams 67 MB in about 18 us (~3.6 TB/s), while the larger draft shape `[14336, 8192]` reaches ~5.1 TB/s on the same kernel.

## Modifications

The kernel change is confined to `bf16_tiled_small_m_gemm.py`, and a second commit adds the unit test `test/registered/amd/test_bf16_rowmajor_small_m_gemm_gfx950.py`:

- **`ROW_MAJOR_ROT`, a per-bucket K-start rotation.** For the long-K buckets, each N block starts its K loop at tile `(pn * ROT) % KT_PER`, so concurrent workgroups stream different K tiles of the weight instead of the same one. The `ROW_MAJOR` table itself is unchanged, and buckets without an entry keep the in-order loop.
- **`_sum_partials` as a flat reduction.** All SK partial loads are in flight at once. `rowmajor_gemm` launches it with a block size chosen by element count (`_sum_block`). The tiled path keeps its existing `_sum_partials` launch; the signature is unchanged.

These changes came from a [Hyperloom](https://github.com/AMD-AGI/Hyperloom) kernelforge campaign. Two other changes that campaign proposed are left out:

- a single-launch split-K with a shared arrival counter, which two concurrent streams could race on and which no Muse decode call uses;
- a warps change for `(8192, 1024, 64)`, which showed no gain (median 1.000x).

## Accuracy Tests

- **Coverage.** `rowmajor_gemm_applies` serves exactly the same (N, K, M) set as before.
- **Every row count of every `ROW_MAJOR` bucket** (17..128 or 1..128 per bucket, 9 shapes):
  - Inputs: real Muse Spark weights (layers 5 / 55: TP8 and TP4 O-projection shards, `post_expert_proj`, `pre_expert_proj`, packed joint router/pooler) for the Muse shapes, random weights for the draft shapes.
  - Both APIs are checked (`rowmajor_gemm`, and the partials with the `rowmajor_gemm_partials_split` SK contract).
  - SNR vs FP32 is 55.4 dB, the same as the current kernel (BF16 output). The maximum relative difference vs the current kernel is 4.9e-3, from the changed FP32 summation order before BF16 rounding.
- **Tiled path** (`tiled_gemm`, which shares `_sum_partials`): relative error 1.7e-3 on every `LAUNCH` bucket.
- **GSM8K, compared question by question.** lm-eval, 5-shot, 1319 questions; Muse Spark TP8 / EP8, DFlash2 with real acceptance, 64 concurrent requests. The baseline was run twice on one server to measure run-to-run variation; with real-acceptance speculative decoding, batch composition alone changes long generations.

## Platforms

- Every caller reaches this path only on gfx95 GPUs:
  - `unquant.py` and `dflash.py` import it under `is_gfx95_supported()`, and the unquantized linear also needs `register_gfx950_unquantized_gemm_shapes`;
  - the Muse Spark routing front and O projection run on MI355X.
- The K-start rotation only changes the order of the K loop, and `_sum_partials` is a plain element-wise reduction. Neither changes the LDS or register footprint of any `ROW_MAJOR` launch, and correctness does not depend on the GPU.
- `ROW_MAJOR_ROT` sits next to `ROW_MAJOR`, which is already MI355X-tuned. Performance was measured only on MI355X.
- No new environment variables.

**End to end.** InferenceX AgentX trace replay, Muse Spark Open MXFP4, TP8 / EP8, concurrency 28, 3600 s, `lmsysorg/sglang-rocm:muse-spark-open-mi355-1106` with the InferenceX recipe, simulated acceptance length 4.05, fresh server:

Decode is about 1.5% faster, which matches the kernel numbers: these GEMMs are about 1.4 ms of a ~15.8 ms verify step. The change in e2e normalized interactivity is within the run-to-run spread of this workload (about ±2%), so this PR claims the kernel-level gain and the decode-speed change, not a measurable e2e gain on its own.

All measurements ran on 8x MI355X with `lmsysorg/sglang-rocm:muse-spark-open-mi355-1106`. The changed kernel file was byte-identical to `main` at the time, and this branch is rebased onto current `main` (552e16968) with no change to the measured code.
