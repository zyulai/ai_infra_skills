## Purpose

The `(MI300) LM Eval TurboQuant KV Cache` group, added by [#50519](https://github.com/vllm-project/vllm/pull/50519), fails all four of its tests in [AMD CI build 12548](https://buildkite.com/vllm/amd-ci/builds/12548/list?sid=01a0609c-72b4-4312-b09a-ec5852db1fc7&tab=output). Each server exits during startup with:

```
ValueError: No KV cache layout satisfies every supported set: [['LHBNC', 'LBHNC'], ['LBNHC']].
```

A `turboquant_*` KV cache never covers the whole model. `TurboQuantConfig.get_boundary_skip_layers` keeps the first and last two attention layers of a dense model at the native dtype, so those layers select an attention backend of their own while every other layer selects `TURBOQUANT`. On ROCm they land on `ROCM_ATTN`, first in the platform's priority list, which reads `LHBNC` or `LBHNC` and keeps the K and V groups in separate planes. `TURBOQUANT` reads only `LBNHC`, because it packs K and V into one slot per token and head. One layout has to serve the whole worker, so the intersection is empty and `get_supported_kv_cache_layouts` raises.

This treats an empty intersection as a reason the backend is invalid for the layer. The boundary layers then get `TRITON_ATTN`, which is stride-aware and declares no layout preference, and the run resolves to `LBNHC`. The same filter applies to an explicit `--attention-backend`, a path that already tolerates a mismatch on a `turboquant_*` run because no single backend can serve every layer. Runs whose KV cache dtype is not `turboquant_*` are unaffected.
