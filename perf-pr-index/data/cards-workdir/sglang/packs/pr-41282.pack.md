## Motivation

On HIP (ROCm), the `cos_sin_cache` is converted from fp32 to bf16 through three independent code paths, silently disabling the fused QSA indexer JIT kernel (`qsa_indexer.cuh`) which requires `const float*` inputs. This causes a fallback to **42 eager PyTorch kernels per QSA layer** (190µs each), wasting ~2.28ms per decode step (~20% of the decode cycle) on hybrid GDN+QSA models like Qwen3.8-Flash-Next.

On CUDA, `cos_sin_cache` is already kept as fp32 via the init guard (`_is_cuda`). This PR extends the same fp32 behavior to HIP.

## Root Cause

Three code paths convert `cos_sin_cache` dtype on HIP:

| Path | File | Effect |
|---|---|---|
| Init guard | `base.py:114` | `cache.to(dtype)` converts fp32→bf16 at creation |
| `_match_cos_sin_cache_dtype` | `base.py:156`, `mrope.py:173` | Converts to `query.dtype` (bf16) on first forward |
| `fallback_rotary_embedding` | `base.py:439` | Converts to `query.dtype` before fallback kernel |

The `_use_fused_prep()` check in `qsa_indexer.py` correctly requires `cos_sin_cache.dtype == torch.float32`, which always fails on HIP after any of these conversions.

## Modifications

- Add `_is_hip` to the fp32 init guard in `base.py` (matching CUDA behavior)
- Split `_match_cos_sin_cache_dtype` into device-match (always) and dtype-match (non-HIP only) in both `base.py` and `mrope.py`
- Keep fp32 in `fallback_rotary_embedding` path on HIP

All changes are **scoped to HIP only** — CUDA behavior is 100% unchanged.

## Why this is safe

`cos_sin_cache` is a read-only lookup table. Both the QSA fused JIT kernel (`qsa_indexer.cuh`) and `apply_rope_with_cos_sin_cache_inplace` document it as fp32. Downstream consumers (e.g., `cos_sin_cache[positions]` → mul with bf16 q/k) handle fp32→bf16 auto-casting implicitly on tiny indexed tensors. Memory overhead is negligible (~64MB at 256K context = 0.01% of GPU memory).
