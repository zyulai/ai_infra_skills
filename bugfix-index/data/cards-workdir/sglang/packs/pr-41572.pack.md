## 正文(PR 描述)

## Motivation

Validating `--linear-attn-prefill-backend ptx_kda` end to end on B200 turned up two problems in the PTX prefill path. Neither depends on the arch: both exist on SM103, where ptx_kda runs today.

1. **Models without a gate lower bound get NaN.** On Kimi-Linear-48B-A3B-Instruct, ptx_kda scored GSM8K 0.000 against 0.902 for Triton, every prompt logprob of a 6K-token prefill was NaN, and nothing was logged. The kernel only handles the safe gate (`lower_bound` set, as in Kimi-K3 and GLM-5.3-Flash).
2. **The workspace cache grows with every batch shape until the process runs out of memory.** A GLM-5.3-Flash TP4 server on ptx_kda hit CUDA OOM about 20 s into GSM8K, while Triton on the same args ran the full eval.

## Modifications

- `srt/layers/attention/linear/kernels/kda_ptx.py`: batches from a model without a gate lower bound take the wrapper's existing Triton fallback, the same path as spec draft-extend, track-state snapshots and unsupported shapes. It logs one warning.
- `kernels/jit/csrc/attention/kda_prefill.cu`: `get_workspace` clears its cache once it holds 4 entries. The device code is unchanged.
- `test/registered/kernels/ops/attention/test_kda_prefill.py`, one regression case per fix. Like the existing ptx cases they run on SM103 (GB300 CI).
  - `test_ptx_without_lower_bound_matches_triton`: with no lower bound and `exp(A_log)` near 200, the output must be finite and match Triton.
  - `test_ptx_workspace_memory_is_bounded`: 16 new batch shapes must not keep one workspace each.

## Accuracy Tests

Unit tests on B200, with the companion PR's SM100 enablement applied so the ptx cases run there (on this branch alone they run on SM103 only):

```

```

Both new cases fail on the code before this change: the output has NaN, and 16 shapes keep 107.6 MB against a 37.9 MB bound.

End-to-end on B200, same setup:

| | before | after |
|---|---|---|
| Kimi-Linear-48B, TP2, ptx_kda: GSM8K | 0.000 (Triton 0.902; 500 questions, 5-shot) | 0.93 (200 questions, 5-shot) |
| GLM-5.3-Flash, TP4, ptx_kda: GSM8K, 500 questions, 20-shot | CUDA OOM during the eval | 0.932 (Triton 0.924) |

- Kimi-Linear now runs its prefill on Triton, and the server logs the fallback once per rank.
- GLM-5.3-Flash uses the cookbook Blackwell recipe plus `--disable-radix-cache`, which keeps its tracked batches off the Triton fallback. Its prompt logprobs on a 2040-token prefill are bit-identical with and without the cache bound.

## Benchmarking and Profiling

The bound can make a cache hit into a miss, so this measures what a miss costs: the latency of the first call of a batch shape against a repeat of it. B200, 16 heads, safe gate, 16K tokens, CUDA events:

| batch | new shape (miss) | repeated shape (hit) |
|---|---|---|
| 1 sequence (fused route) | 895–939 µs | 764–798 µs |
| 2–9 sequences (builder + chain) | 573 µs | 532 µs |
