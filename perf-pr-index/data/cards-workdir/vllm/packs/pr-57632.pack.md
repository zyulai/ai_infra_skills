## Purpose

Even when the query forward replays a FULL CUDA graph, the DFlash/DSpark draft step still runs the context K/V precompute (`precompute_and_store_context_kv`) eagerly outside the graph, because the number of context tokens varies from step to step.

This PR captures the context K/V precompute ahead of the query forward in the draft's FULL decode graph. Each graph stores one full verify of context rows per request; rows past the batch are padded with `PAD_SLOT_ID` so they write no K/V, and any prefill context beyond the graph's rows is stored eagerly before replay. The precompute has no host syncs, so every DFlash drafter captures it. The draft attention metadata build stays eager, as before.


## Validation

Capturing the context K/V precompute must not change the speculator's proposals. The checks below therefore compare acceptance and accuracy between this branch's parent commit (`c723a831a8`) and `d8de1d3a2f`, and serving performance against current main, with everything else held fixed.

### Setup

- **Hardware / software:** 4× GB200, FlashInfer 0.6.18.post1, `VLLM_USE_V2_MODEL_RUNNER=1`.
- **Model:** DeepSeek-V4.1-Flash (`dba1be0a40aa45a94ad051997016db3960a90277`).
- **Speculative decoding:** DSpark with 5 speculative tokens and full decode CUDA graphs.
- **Topologies:**
  - **DEP4:** MegaMoE backend with adaptive verification.
  - **TP4:** auto MoE backend with fixed verification.

### Acceptance and GSM8K accuracy

Each pair runs the full GSM8K test set (1,319 identical 5-shot completion prompts) with greedy decoding, concurrency 32, a 1,024-token output cap, and strict answer extraction.

Acceptance length is read from the engine's `vllm:spec_decode_*` counters over the whole run for DEP4. For TP4, it is aggregated from the engine's periodic SpecDecoding log windows over the steady state; the same method is used on both sides of each pair.

| Configuration | Acceptance length, incl. bonus (parent → PR) | GSM8K (parent → PR) |
| --- | ---: | ---: |
| DEP4 | 3.411 → **3.434** | 1234 → 1228 / 1319 (93.56% → 93.10%) |
| TP4 | 3.471 → **3.463** | 1227 → 1219 / 1319 (93.03% → 92.42%) |

- The acceptance deltas are within ±1% and have opposite signs across the two topologies, and the per-position acceptance curves coincide. The captured precompute therefore does not change what the drafter proposes.
- The GSM8K deltas are run-to-run noise: two repeats of the same DEP4 parent configuration scored 0.9219 and 0.9356 (an 18/1319 spread), which is wider than any delta in the table.
- These results establish parity with the parent; they do not claim an accuracy improvement.

### Serving benchmark

TP4, DSpark (5 speculative tokens, synthetic acceptance length 5.5), random dataset with 128 input / 1,024 output tokens. **Base** is main and **PR** is `d8de1d3a2f`. CPU/step is the host time per engine step, measured with an injected per-step probe.

| Concurrency | CPU/step | TPOT | ITL |
| ---: | ---: | ---: | ---: |
| 1 | 6.77 → 5.03 ms | 1.27 → 1.08 ms (−15.2%) | 6.95 → 5.88 ms (−15.3%) |
| 8 | 6.64 → 5.24 ms | 1.87 → 1.84 ms (−1.6%) | 9.96 → 9.90 ms (−0.6%) |
| 64 | 6.82 → 5.43 ms | 3.90 → 3.87 ms (−0.7%) | 19.97 → 20.01 ms (+0.2%) |

The PR cuts host time per step by 1.4–1.7 ms. At concurrency 1 the step is host-bound, so this carries through to a ~15% lower TPOT and ITL; at higher concurrency the GPU dominates and latency is roughly unchanged.
