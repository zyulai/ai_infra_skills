## 正文(PRD / 提案全文)

# Summary

SGLang has kernel code in several places today:

- `python/sglang/jit_kernel`
- `sgl-kernel/python/sgl_kernel`
- `python/sglang/srt/**/triton_ops`
- model- or subsystem-specific kernel paths

This RFC suggests making `sglang.kernels.ops.*` the public import surface used by SGLang runtime code and tests:

```python
from sglang.kernels.ops.<group> import <kernel>
```

For example:

```python
from sglang.kernels.ops.layernorm import rmsnorm
from sglang.kernels.ops.activation import silu_and_mul
from sglang.kernels.ops.kvcache import reshape_and_cache
```

The intent is incremental. `jit_kernel` and `sgl_kernel` can remain implementation layers, but new SGLang-side call sites should have one obvious place to import callable kernels from.

# Status — migration complete ✅ (2026-07)

All phases have landed. **`sglang.kernels` is now the single home for SGLang kernels, and `python/sglang/jit_kernel/` has been removed entirely** (#32072).

Final layout:

- `sglang.kernels.ops.<group>.<kernel>` — the public operator API this RFC proposed.
- `sglang.kernels.jit/` — shared JIT CUDA build + runtime infrastructure (`utils/`, `csrc/`, `include/`, `__main__`, in-package `benchmark/` + `tests/`); `KERNEL_PATH` resolves here. JIT-backed operators live in their group as `sglang.kernels.ops.<group>._jit_<op>` and call this infra directly.
- `sgl_kernel` — unchanged AOT wheel boundary.
- `sglang.jit_kernel` — **removed**. This supersedes the conservative "keep `sglang.jit_kernel` as a transition layer" language in the phase descriptions below, which is preserved as the original proposal.

| Phase | What shipped | PR(s) |
|---|---|---|
| 2 | `sglang.kernels` namespace + `srt/**/triton_ops` migrated | #30044 |
| 2.5 | Swept ~280 scattered Triton / CuTe DSL / TileLang kernels into `kernels.ops.*` | #30784–#30795 (7 PRs) |
| metadata | `KernelSpec` / `KernelBackend` / device-based `CapabilityRequirement` + HIP/NPU backends | #31292, #31307 |
| 3 + 4 (batch-1) | Shared JIT infra → `sglang.kernels.jit.utils`; first operator groups | #31666 |

| finale | Move build infra into `kernels/jit/`, refactor `KERNEL_PATH`, drop the last 8 shims, delete `sglang.jit_kernel` | #32072 |

# Why

The current layout makes sense historically, but it is getting harder to maintain. Triton kernels alone are spread across attention, LoRA, memory cache, speculative decoding, constrained decoding, model executor, and model-specific directories.

<img width="744" height="607" alt="Image" src="https://github.com/user-attachments/assets/7852e678-785e-4468-af27-90e9de95efbd" />

That creates a few practical problems:

- it is hard to tell whether a logical operator already has a kernel;
- alternative implementations for the same operator are not easy to compare;
- correctness tests for related kernels do not always live or import in the same way;
- backend coverage across JIT CUDA, AOT CUDA/C++, Triton, CuTe DSL, FlashInfer, DeepGEMM, and torch fallback paths is harder to inspect;
- new kernel PRs do not have a clear public API target;
- future agent-oriented kernel work would benefit from a stable kernel namespace and consistent tests.

The desired end state is simple: when runtime code or tests need to call a kernel, they should usually import it from `sglang.kernels.ops.<group>`.

# Proposed Shape

## Public namespace

Introduce a package layout along these lines:

```text
python/sglang/kernels/
  __init__.py
  spec.py
  registry.py
  selector.py
  ops/
    __init__.py
    activation/
    attention/
    communication/
    diffusion/
    gemm/
    grammar/
    kvcache/
    layernorm/
    mamba/
    memory/
    moe/
    quantization/
    sampling/
    spatial/
    speculative/
```

The operator groups are not meant to be perfect on day one. They just give us a stable place to put public kernel APIs and make future cleanup mechanical.

## Compatibility model

The first version should be conservative:

- keep the `sgl_kernel` wheel public API stable;
- keep `sglang.jit_kernel` usable as the JIT CUDA development layer during the transition;
- expose existing `jit_kernel` and `sgl_kernel` functions through thin `sglang.kernels.ops.*` wrappers;
- move scattered Python/Triton kernels into `sglang.kernels.ops.<group>` when the move is low-risk;
- for sensitive paths, add wrappers first and move the implementation later.

This lets us migrate imports and tests before doing large file moves.

## Metadata and selection

The first version can add lightweight metadata for inventory and simple dispatch:

- `KernelSpec`
- `KernelBackend`
- `FormatSignature`
- `CapabilityRequirement`
- `PlatformInfo`

Selection should start with a heuristic policy only. A simple selector can rank by explicit backend request, platform capability, operator properties, priority, and backend preference. Autotuning can wait until the namespace and tests are stable.

## Exit path for `jit_kernel` forwarding

The initial forwarding path is a migration tool, not the final shape.

A JIT-backed operator may start as:

```text
sglang.kernels.ops.layernorm.rmsnorm
  -> sglang.jit_kernel.norm.rmsnorm
```

The target shape should be:

```text
sglang.kernels.ops.layernorm.rmsnorm
  -> op-local JIT wrapper under sglang.kernels.ops.layernorm
  -> shared JIT infrastructure
```

So the final split should be:

- public operator APIs live under `sglang.kernels.ops.<group>`;
- shared JIT CUDA build/runtime code lives in an internal JIT infrastructure package;
- individual JIT-backed operators live in their logical operator groups and call the shared JIT infrastructure directly.

After that migration, `sglang.jit_kernel` should not be the main public operator API surface. It should either contain shared JIT infrastructure, keep only compatibility glue that maintainers still want, or be folded into an internal package under `sglang.kernels`.

# Migration Plan

## Phase 1: strengthen tests first

Before moving implementation code, add or improve correctness coverage for important existing kernels.

This should be a small test-focused PR. It should:

- add a few representative fixed shape cases for important kernels;
- keep CI runtime under control;
- trim overly broad random or Cartesian shape coverage where appropriate;
- avoid benchmark-style tests in normal unit CI;
- link back to this RFC as the safety baseline for the namespace migration.

Once that PR is opened, we can link it from this issue.

## Phase 2: add `sglang.kernels` and migrate the easy surface

Add the public namespace:

```text
sglang.kernels.ops.<group>.<kernel>
```

In the same phase:

- expose existing `jit_kernel` and `sgl_kernel` functions through thin `sglang.kernels.ops.*` wrappers;
- update tests and straightforward runtime call sites to import from `sglang.kernels.ops.*`;
- move scattered Python/Triton kernels under paths such as `python/sglang/srt/**/triton_ops` into the matching `sglang.kernels.ops.<group>` directory when the move is safe;
- keep wrappers for risky paths and move those implementations later.

This phase should not require changing how JIT CUDA kernels are developed or how the `sgl_kernel` wheel is built. Old direct imports from `sglang.jit_kernel` and `sgl_kernel` can keep working during the transition, but new SGLang-side code should use the unified namespace. Developer docs, local skills, and review guidance should say the same thing.

## Phase 2.5: sweep the remaining scattered kernels (7 PRs)

Phase 2 (#30044) migrated the `srt/**/triton_ops` directories, but a full-tree audit found roughly 280 more Triton kernels (~105 files), plus CuTe DSL / TileLang kernels and one standalone `.cu`, still living outside `sglang.kernels` / `sglang.jit_kernel` / `sgl_kernel`. Phase 2.5 moves all of them into `sglang.kernels.ops.*`, split into 7 review-friendly PRs. Every PR follows the Phase 2 recipe: byte-identical file moves, `KernelSpec` registry entries, in-tree import rewrites only.

1. **quantization** — `layers/quantization/fp8_kernel.py` (12 kernels), `int8_kernel.py`, `awq/awq_triton.py`, `mxfp8_amd_gfx95.py`, `mxfp4_flashinfer_trtllm_moe.py`, plus the CuTe DSL `nvfp4_gemm_swiglu_nvfp4_quant.py`.
2. **moe** — `layers/moe/ep_moe/kernels.py` (22 kernels), `moe_runner/triton_utils/fused_moe_triton_kernels.py` (10), `topk.py`, `router.py`, `deepep_waterfill.py`, `rocm_moe_utils.py`, `moe_runner/triton_utils/mxfp8_moe_amd_gfx95.py`.
3. **top-level `srt/layers` strays** — `elementwise.py`, `gemma4_fused_ops.py`, `deepseek_v4_rope.py` (incl. TileLang), `multimodal.py`, `fused_qk_norm_rope_store.py`, `mhc_head.py`, `fused_qk_rmsnorm_rope_gate.py`, `fused_qk_norm.py`, `dp_attention.py`, plus `rotary_embedding/{triton_kernels,mrope}.py` and `layers/utils/hash.py`.
4. **generic attention** — `attention/utils.py` (8 kernels), `flash_mla_sm120.py` + `flash_mla_sm120_triton.py`, the kernel embedded in `flashattention_backend.py`, `nsa/triton_decode/`, plus `layers/dcp/`.
5. **dsa + dsv4** — all Triton files under `attention/dsa/` and `attention/dsv4/` (incl. `unified_kv_kernels/`), plus both `tilelang_kernel.py` files.
6. **linear-attention family + diffusion** — `attention/linear/{seg_la,lightning_attn}.py`, the CuTe DSL `linear/kernels/{gdn_blackwell,kda_blackwell}/`, `attention/minimax_sparse_ops/`, and `multimodal_gen`'s `sparse_linear_attn.py` + `csrc/render/hunyuan3d_rasterizer/rasterizer_gpu.cu` (the only `.cu` outside the canonical trees).
7. **vendored subtrees** — `attention/fla/` (34 kernels, 18 files) and `attention/mamba/` (16 kernels, 8 files incl. vendored `ops/`), moved as pure directory relocations in one PR so the large-but-trivial diff stays isolated.

Deliberately excluded from Phase 2.5: platform-private kernels under `hardware_backend/{musa,xpu}`, the `_triton_stub`, `batch_invariant_ops`, communication kernels in `distributed/`, and the `cpp_extension` inline modules (`mem_cache/cpp_radix_tree`, `native_hash`, `kv_vmm_backing`, `hf3fs_usrbio_client`, `pynccl_allocator`) — the latter will move together with the Phase 3 shared-infrastructure work.

## Phase 3: move shared JIT infrastructure

Move the shared `jit_kernel` infrastructure into an internal location under `sglang.kernels`, for example:

```text
python/sglang/kernels/ops/jit_kernel
```

or another maintainer-approved location.

This phase should move common JIT CUDA build/runtime infrastructure, not dump every JIT operator into one new public package. Behavior should stay unchanged.

## Phase 4: remove JIT operator forwarding group by group

After the shared JIT infrastructure has a stable home, remove `jit_kernel` operator forwarding one operator group at a time.

For each group:

1. Inventory the `sglang.jit_kernel.*` functions exposed through `sglang.kernels.ops.<group>`.
2. Create op-local modules under `sglang.kernels.ops.<group>` for those JIT-backed operators.
3. Move the public Python wrapper for the operator into the op-local module.
4. Keep shared JIT build/runtime utilities in the internal JIT infrastructure package.
5. Update tests to import from `sglang.kernels.ops.<group>`.
6. Update in-tree runtime call sites to import from `sglang.kernels.ops.<group>`.
7. Remove the `sglang.kernels.ops.<group> -> sglang.jit_kernel.*` forwarding path for that migrated operator.
8. Keep a temporary compatibility import in `sglang.jit_kernel` only if maintainers want to preserve the old import path for external users.

Example:

```text
Before:
  sglang.kernels.ops.layernorm.rmsnorm
    -> sglang.jit_kernel.norm.rmsnorm

After:
  sglang.kernels.ops.layernorm.rmsnorm
    -> sglang.kernels.ops.layernorm._jit.rmsnorm
    -> shared JIT infrastructure
```

This can be repeated for groups such as `layernorm`, `activation`, `quantization`, `moe`, `kvcache`, `attention`, and `diffusion`.

## Phase 5: keep only the compatibility surface we actually need

The final state should have most SGLang kernel calls go directly through `sglang.kernels.ops.*`.

Only a small number of `sgl_kernel` APIs should continue to be forwarded where they represent the stable external wheel boundary.

# Testing

- Add import/registry tests that run without GPU.
- Keep existing correctness tests for migrated kernels, but import through `sglang.kernels.ops.*`.
- Add a small number of fixed representative shape cases for important kernels.
- Reduce broad random or Cartesian coverage where needed to keep CI time stable.
- Put hardware-specific cases in the matching hardware-specific CI lane.
- Keep benchmark-style coverage out of normal unit CI.

# Review Rule

If we agree on this direction, new kernel-related PRs should follow one rule:

SGLang runtime code and tests should import callable kernels from `sglang.kernels.ops.*`.

Implementation work can still happen in `jit_kernel` or `sgl_kernel` when appropriate, but the public in-tree call path should go through the unified namespace. Reviewers should ask for a `sglang.kernels.ops.*` entry point when a PR adds a new callable kernel, and should avoid growing `jit_kernel` as a long-term public operator namespace.
