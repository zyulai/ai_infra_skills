## 正文(PRD / 提案全文)

### Motivation.

A **Specialized Decode** implementation is one where most/all operations in a model’s forward pass are manually implemented in a way that optimizes for the model’s specific shapes and execution patterns on certain hardware. Typically, these include heavy kernel fusions and overlap for low-latency execution, and custom kernels that tune exact grid sizes for certain batch sizes. These implementations can reach tens of thousands of lines of code, and present a major challenge in managing their complexity. This RFC proposes a standard way to modularize and integrate these runtimes into vLLM under `vllm/models/<model>/<vendor>/`.

#### Why Specialized Decodes like MonoKernels?

At low concurrency, decode is bound by launch overhead and weight reads, and a MonoKernel removes most of both. On 8× MI350X a graph-mode GLM-5.2 decode step issues ~2,459 kernels in vLLM. With the MonoKernel it issues ~210: 75 MonoKernel launches plus ~135 for dense layers 0–2, input prep and the head.
 
| GLM-5.2-MXFP4 (#60889), TP8, MI350X, ~3k-token context | vLLM | MonoKernel | Speedup |
| --- | --- | --- | --- |
| Time per token, batch 1 / 8, defaults (BF16 attention) | 13.70 / 17.33 ms | 5.92 / 11.44 ms | 2.31× / 1.51× |
| Time per token, batch 1, FP8 attention opt-in | 13.70 ms | 4.80 ms | 2.85× |
| MoE layer w/o indexer (57 of 75), batch 4 / 8, FP8 | 178.8 / 189.6 µs | 69.1 / 100.6 µs | 2.59× / 1.88× |
| MoE layer with indexer (18 of 75), batch 4 / 8, FP8 | 214.9 / 227.6 µs | 88.5 / 123.4 µs | 2.43× / 1.84× |
| AgentX time between tokens, 1 / 8 users (3,600 s/point), FP8 | 15.0 / 20.4 ms | 6.5 / 12.7 ms | 2.28× / 1.68× |
| GSM8K strict, 1,319 questions, graphs, BF16 | 1228, 1234, 1235 (3 runs) | 1240 | parity: paired McNemar p = 0.22–0.63 |

Layer times are profiler-corrected, from one run. The gain shrinks with batch size, so the target is latency-bound serving: agents, chat and small-batch decode.

### Proposed Change.

#### Goals

1. **Opt-in:** off by default, enabled with one switch (`additional_config={"decode_backend": "latency_specialized"}` today).
2. **Refuse at startup:** an unsupported deployment fails with one error listing every reason, never a silent fallback.
3. **The model owns it:** code lives under `vllm/models/<model>/<vendor>/specialized_decode/`, with no core changes.
4. **One `plan()` per step:** it picks the specialized kernels or vLLM's stock forward; prefill and mixed batches always run stock.
5. **One `step()` or `run()` per pass**  If specialized_decode exists, run the `step()` or `run()` function, else call stock
6. **Fixed batch sizes:** the decode kernel declares the batch sizes it serves; larger batches run stock.
7. **Avoid duplicating weights** where prudent, reading vLLM's loaded weights and caches in place.

#### Layout
Layout (shown for a monokernel; Kimi-K3 uses `nvidia/` and `cutedsl/`):

```
vllm/models/<model>/<vendor>/
    model.py                 # calls specialized_decode_config() in __init__, plan() in forward
    model_state.py           # MRV2 ModelState: builds the decode after load, binds KV caches
    specialized_decode/
        README.md            # supported checkpoints, refusals, options
        runtime/
            __init__.py      # DecodeConfig, batch sizes, specialized_decode_config(), unsupported()
            decode.py        # SpecializedDecode: plan(), run() or Step.layer()
            ...              # weight views, guards, model-specific helpers
        mono/                # the kernels, when the decode uses monokernels
tests/models/<model>/        # proposed: CPU tests for refusals and plan() routing
```

Instantiation of specialized decode happens at startup
```
self.specialized_decode_config = specialized_decode_config(vllm_config)
self.specialized_decode = SpecializedDecode(
            self.model, self.specialized_decode_config
        )
```
Two methods to Available. 

Replace the whole forward function with the specialized decode (and let it decide when to call the stock version)
```python
# Kimi-K3 (step mode, #61867): the whole step runs in the specialized decode
decode = self.specialized_decode
step = decode.plan(positions, intermediate_tensors)
if step is not None:
    return decode.run(step, input_ids, inputs_embeds)
return self.model(input_ids, positions, intermediate_tensors, inputs_embeds)
```

Replace the Decode Layer within the forward function with the specific kernel to run, and let the forward function decide.
```python
# GLM-5.2 (layer mode, #60889): a kernel per layer, or vLLM's layer
step = None if decode is None else decode.plan(positions, intermediate_tensors)
...
kernel = step.layer(idx) if step is not None else None
hidden_states, residual = (kernel or layer)(positions, hidden_states, residual)
```

**Not in Scope**

- Prefill and mixed steps. These always run vLLM's layers.
- Models compiled with `@support_torch_compile`.
- Launches that span more than two layer (some fusions may fuse end of one layer with beginning of another)
- No Runtime fallback. If a megakernel fails the engine should stop.

##### Enabling and refusal

- **Switch:** `--monokernel` (with `--no-monokernel`), the same for every model and off by default, like `--async-scheduling`. It sets `KernelConfig.monokernel`, so it also works from a config file or the Python API.
   - Additionally we can use `--additional_config={"decode_backend": "latency_specialized"}` As this will be used in the more generic case. 
  - It applies to the loaded model's spec. A model has at most one spec per vendor, so there is no name to pick.
  - There are no other user knobs. Tuning lives in the spec's `options`.
- **Refusal** happens in three stages: config (before load), model (after load) and caches (at every bind). Each stage reports every reason, not only the first. If the switch is on and the config is refused, startup raises.
- **Default-deny:** any feature in use that `supports` doesn't list is refused, then the spec's own checks run. The features are: PP, DP, EP, EPLB, DCP, PCP, LoRA, KV connectors, routed-expert capture, speculative decoding, sleep mode, CPU weight offload, weight updates, partitioned GPUs, and EAGLE3 aux layers among the kernel layers.
- MonoKernels run only under Model Runner V2.
