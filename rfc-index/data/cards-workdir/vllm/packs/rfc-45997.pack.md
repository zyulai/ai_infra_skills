## 正文(PRD / 提案全文)

## Motivation

#27743 added "cross-layer KV blocks" so a KV connector can stage/transfer a block's KV for
all layers at once, by allocating all layers in one tensor (`use_uniform_kv_cache` /
`allocate_uniform_kv_caches`).

For MLA backends the only supported physical layout was **block-major**
`(num_blocks, num_layers, ...)`. That makes each per-layer view a *strided* (non-contiguous)
slice, and MLA kernels require contiguous per-layer views — so #37090 **disabled cross-layer
KV for all MLA backends** (`get_kv_cache_stride_order(include_num_layers_dimension=True)`
returns the identity permutation to signal "unsupported").

The result: the cross-layer connector optimization is off for exactly the models that dominate
disaggregated prefill/decode and KV offloading today — DeepSeek V3/V3.2, GLM, Kimi, all MLA.
With it disabled, vLLM falls back to **one independent `torch.zeros` per layer**, so a connector
sees `L` allocations at unrelated base addresses. Two concrete costs:

1. The GPU↔staging layer↔page transpose needs `L` separate copies per block — there is no
   constant stride across layers to exploit.
2. RDMA connectors must register `L` memory regions (one per layer) instead of one.

## Proposed Change

Add a **second uniform layout: layer-major contiguous slices**. Allocate one buffer for all
same-spec layers and hand each layer a **contiguous slice** at a constant stride
`S = num_blocks * page_size_bytes`. The per-layer view stays contiguous and bit-identical to a
standalone tensor, so **attention kernels (including MLA) are unaffected** — no
`get_kv_cache_stride_order` support is required. This is kernel-agnostic, unlike the existing
block-major path.

```
Today — one independent torch.zeros per layer (cross-layer disabled for MLA, #37090):

  layer 0   : [ blk0 blk1 ... blkN ]   @ ptr0
  layer 1   : [ blk0 blk1 ... blkN ]   @ ptr1     (ptr1 - ptr0 : arbitrary)
   ...
  layer L-1 : [ blk0 blk1 ... blkN ]   @ ptr(L-1) (no constant stride)

  => L memory regions; gathering block b across layers = L copies at L unrelated addresses


Proposed — one buffer, per-layer CONTIGUOUS slices, constant stride S = num_blocks * page_size_bytes:

  base -> +--------- layer 0 ---------+--------- layer 1 ---------+ ... +-------- layer L-1 -------+
          | blk0 blk1 ...      blkN   | blk0 blk1 ...      blkN   |     | blk0 blk1 ...      blkN  |
          +--------------------------+--------------------------+     +-------------------------+
          ^                          ^                          ^
          base + 0*S                 base + 1*S                 base + (L-1)*S

  per-layer view  = base + l*S            (contiguous slice, identical to standalone -> kernel safe)
  block b, layers = base + l*S + b*blk    for l in [0, L)   => CONSTANT inter-layer stride S
```

Two concrete wins for connectors, both from the constant stride / single allocation:

**1. `cudaMemcpy2D` transpose (zero SM).** Gather a block across all layers into a contiguous
page in one copy-engine 2D op, instead of `L` separate copies:

```
cudaMemcpy2D(dst    = page_b,                 // contiguous staging page, L * blk bytes
             dpitch = blk,
             src    = base + b*blk,           // block b of layer 0
             spitch = S,                      // constant inter-layer stride
             width  = blk,
             height = L)
// runs on the copy engine (0 SM), one launch per block; today: L memcpys per block
```

**2. Single memory registration.** One allocation → connectors register **one** RDMA memory
region (one rkey) / one CUDA IPC handle for all layers, instead of `L`.

Implementation sketch:
- `_allocate_kv_cache_tensors`: one `torch.zeros(total)` sliced per page-size bucket, instead of
  N independent `torch.zeros`. Downstream `_reshape_kv_cache_tensors` is unchanged — contiguous
  int8 slices support `.view(dtype)` / `as_strided`, and `storage_offset` is carried (vLLM core
  already tolerates non-zero kv-cache `storage_offset`: Mamba state tensors and Triton fp8 scales
  use `as_strided` with offsets today).
- Gate behind a new connector preference, weaker than `prefer_cross_layer_blocks` (which signals
  the block-major layout): a connector opts in when it only needs a constant inter-layer stride,
  not per-block contiguity.

Open API questions for discussion:
- How to advertise/select this layout — a new connector preference, or a backend-level capability
  flag distinct from the existing block-major `stride_order[0] != 0` signal?
- How to communicate the inter-layer stride to the connector — explicit (registration field /
  callback) vs. the connector detecting that per-layer `data_ptr`s are arithmetic.

This is purely additive and opt-in; default allocation is unchanged.

## Any Other Things

We maintain [PegaFlow](https://github.com/novitalabs/pegaflow), a disaggregated KV connector
(RDMA across nodes + tiered host/SSD storage). We are moving its CPU-side KV from layer-first to
**page-first** (a block's all-layer KV contiguous on the host) to cut per-block metadata by a
factor of `num_layers` — one RDMA descriptor / one SSD iovec / one storage slot per block instead
of one per (layer). The transpose from vLLM's per-layer GPU layout into that page is the operation
this RFC makes cheap: with a constant inter-layer stride it is one `cudaMemcpy2D` per block on the
copy engine. We are happy to contribute the vLLM-side allocation change and a unit test mirroring
`tests/v1/kv_connector/unit/test_kv_cache_layout.py`.
