## PR body
```markdown
## Motivation

The LTX-2 video VAE **decode** stage is `conv3d`-bound. On Hopper, `Conv3d` runs **~2.7–3.7× faster** in `channels_last_3d` (NDHWC) memory format, and the VAE loader already converts `Conv3d` weights to `channels_last_3d` for Wan/QwenImage (`_convert_conv3d_weights_to_channels_last_3d`). LTX-2 never got this speedup for two reasons:

1. **`LTX2VideoCausalConv3d` is layout-hostile.** Its temporal causal padding used `repeat()` + `concatenate()`, which produces a **contiguous (NCDHW)** tensor. That breaks `channels_last_3d` and forces an expensive layout reconversion before every conv, negating the win.
2. **The loader `auto` policy excluded LTX-2** — it enabled `channels_last_3d` only for QwenImage and single-GPU Wan.

## Changes

- **Layout-preserving causal pad.** When the conv weight is `channels_last_3d`, the padded tensor is allocated directly in `channels_last_3d` and filled via `copy_` — one allocate-and-copy that does *both* the replication pad and the layout fix. **Self-gated on the weight layout**, so when `channels_last_3d` is off the original `repeat()`+`concatenate()` path runs **byte-for-byte unchanged** (zero risk to the default path).
  - The `copy_` pad is bandwidth-bound (~0.5 ms at the largest decode shape, ≈ hardware limit). A custom Triton pad kernel was prototyped and measured to **not** beat it, so none is added.
- **Loader `auto` policy** now enables `channels_last_3d` for **single-GPU LTX-2** (same convention as Wan). Multi-GPU still requires the explicit `SGLANG_DIFFUSION_VAE_CHANNELS_LAST_3D=1` override.

This is complementary to #26878 (which optimizes the decode *stage* orchestration: untiled-decode policy + GPU-side postprocess). That PR does not change the conv memory format; this one does. They stack — `channels_last_3d` speeds up each conv in both the tiled and untiled paths.

## Correctness

The pad is numerically identical to the previous path (replicate-edge == repeat-edge frame; asserted bit-exact in tests). Only the cuDNN NDHWC conv kernel's float accumulation order differs — the same tradeoff already shipped for Wan/QwenImage. Verified: module-level fp32 decode diff `~1e-4`.

Notes:
- The end-to-end decode-stage speedup (1.41×) is smaller than the isolated-conv microbench (~3.67×) because the default decode path is **tiled** and the stage also includes non-conv work (norms, upsample reshapes, audio VAE, postprocess, CPU-offload transfers). - **Peak memory drops ~9.7 GiB**: the layout-preserving pad avoids the `repeat`+`concat` + NCDHW→NDHWC transpose intermediates. This also makes higher-resolution untiled decode more feasible.
- Output videos are visually equivalent (same seed/denoise; decode differs only by bf16 conv accumulation order).
