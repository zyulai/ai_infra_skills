## Overview

At the start of a direct weight reload (`VLLM_RELOAD_MODE=direct`, #64336), zero MoE expert padding, so that post-load processing reruns over the same bytes as a cold start. Part of the direct weight reload work (#54477).

MoE expert parameters are often larger than the checkpoint tensors loaded into them: DeepEP rounds the hidden size up, MXFP4 / TRT-LLM / AITER backends round the intermediate size, and block-aligned FP8 TP pads shards. Loaders copy only the checkpoint part. On a direct reload the padding then holds the previous post-processed bytes, which post-load processing processes again. After a `load_format=dummy` cold start (the usual RL setup) it holds random values.

## Claims

- **gpt-oss-20b (TP2, MXFP4), direct reload through IPC weight transfer:** every tensor is bit-identical to a fresh start, both after 3 same-weight syncs and after a dummy start plus one sync. On main, 168 expert tensors differ after every sync and drift from one sync to the next. After a dummy start, 288 differ and GSM8K drops about 2 points.
- Cold start and layerwise reload are unchanged.
- No loader changes: whether to fill is decided from `moe_config` when the checkpoint layout is recorded at cold start, so it also covers dummy and other cold starts that skip loaders, and the load plan (#64418) that bypasses them.

## Details

**Design.**
- `RoutedExperts.padding_fill_params()` applies when `moe_config` shows the hidden size or the per-partition intermediate size rounded up past its unpadded value, or block-aligned TP sharding.
- It returns the layer's parameters minus per-expert scalars: a parameter is filled if it has more than two values per expert. So per-tensor and static input scales, which may be absent from the checkpoint, are kept.
- `record_checkpoint_layout` stores `(module, name)` at cold start, before post-load processing. Some post-load processing pads only the runtime copy and writes the padded size back into `moe_config`, so the decision must not be made later.
- `begin_direct_reload` looks up each name after the view-back, skips parameters post-load processing has dropped, and zero-fills the rest whole. Loaders then overwrite every checkpoint region.

**Requirement.** The fill erases the checkpoint region too, so every checkpoint tensor loaded into these parameters must be resent on every update. The direct delivery contract in `direct.py` says so; the completeness check (F2 in #54477) will enforce it.

**Padding value.** Everything is filled with 0. A padding-only scale block only multiplies weights the same fill zeroes, so its value doesn't change the output. MXFP4 (DeepSeek-V4.1, gpt-oss) and NVFP4 scales are created as zeros or empty, so 0 also matches a cold start. Block-aligned TP padding is rewritten by its loader after the fill, with scales at 1. Weights created with `torch.empty` had uninitialised padding at cold start; they get 0 here.

**`moe_config` is the source today, not the only possible one.** A layer padded some other way implements `padding_fill_params()` and reuses the same fill.

**Not changed.** Layerwise reload, the block-aligned TP loader fill, and `_zero_intermediate_padding` (cold start still needs it, since those weights are `torch.empty`).

**History.** This replaces this PR's earlier design, where loaders recorded the padding regions on every load and `fill_padding` wrote them before post-load processing. That design worked with layerwise reload and partial updates. Under the decision to require full updates and to drop layerwise reload (#54477), the fill at begin is much smaller and needs no loader changes. The streamed gpt-oss MXFP4 TP split moved to #65353, and Inkling AMD's padding (#64690) is covered by this fill.
