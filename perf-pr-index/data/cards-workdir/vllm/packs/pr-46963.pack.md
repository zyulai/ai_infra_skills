## PR body
```markdown
## Purpose

`--kv-cache-dtype nvfp4` has a paged KV write path only on SM100, where trtllm-gen provides the native store, so the dtype cannot be used on SM8x or SM12x at all.

On SM8x and SM12x this writes the cache with FlashInfer's `nvfp4_quantize_append_paged_kv_cache_with_slot_mapping` and reads it back with the native fa2 prefill and decode wrappers, so no kernel change is needed. On SM12x, NVFP4 groups use the native decode wrapper instead of XQA and capture only single-token decode graphs, as on SM8x. One helper carves each page into its K and V halves for NHD and HND and leaves the data/scale split to the existing `nvfp4_split_data_scale`; SM100 builds its views through the same helper and keeps its trtllm-gen kernels. The query and output stay in model dtype on the fa2 path, so q_scale is not applied and no FP8 staging buffer is allocated. Both FlashInfer entry points are in the pinned 0.7.0, so no version bump is needed. On the sm_80 host used for validation, KV cache capacity went from 1,446,932 to 4,805,405 tokens (3.32x).

On these GPUs two combinations are refused in `supports_combination`, so the server stops at backend selection before the weights load: head_size 64, where fa2 prefill misreads NVFP4 by 10 to 15 percent once it picks the 128-row query tile (flashinfer-ai/flashinfer#5965, reproduced on sm_80 too), and attention sinks, since the sink prefill wrapper cannot read the block scales (flashinfer-ai/flashinfer#5966). flashinfer-ai/flashinfer#6024 and flashinfer-ai/flashinfer#6021 fix these but are not merged yet, so both refusals stay until the fixes ship in a FlashInfer release and the pin moves. DCP is refused in the metadata builder, because `supports_combination` does not see it. Scale-search variants such as `nvfp4_4over6` stay SM100-only because the slot-mapping writer has no scale search yet; once FlashInfer's writer supports it, enabling them here is a two- or three-line change.

`#46329`, `#54772` and `#56550` also target SM12x; this path needs no CUDA kernel or XQA change. RFC `#47684` tracks the wider work.

I used Codex and Claude while implementing and preparing this PR. I reviewed the final diff and ran the tests below.
```

```
## Test Result

The GPU test writes through `do_kv_cache_update()` on all four block-compact layouts, dequantizes what the slot-mapping writer stored through the same views, and checks it against the input and that the neighbouring layer stays untouched. The read path is covered by the evals below. pre-commit passes.

mgoin ran this on SM121 with the stock `flashinfer-python==0.7.0.post1` wheel; the results are in the comments. On sm_80 with the same stock wheel at `9adf229fb5`, the four nvfp4 tests pass, `openai/gpt-oss-20b` with an NVFP4 cache stops in 45 s with the head_size 64 reason, and GSM8K with the FLASHINFER backend for both dtypes gives:

| Model | Questions | bf16 KV | nvfp4 KV |
| --- | --- | ---: | ---: |
| Qwen/Qwen3-0.6B | 100, two runs | 0.350, 0.350 | 0.170, 0.130 |
| Qwen/Qwen3-0.6B | all 1319 | 0.384 | 0.174 |
| Qwen/Qwen3-4B (32 query / 8 KV heads) | 100, two runs | 0.920, 0.910 | 0.880, 0.880 |

MRCR on Qwen3.5-4B, 30 samples across needles 2/4/8 with prompts of 16,626 to 33,231 tokens, measured on an earlier, larger revision of this PR:

| KV dtype | Match ratio | Prefix hit rate | n2 | n4 | n8 |
| --- | ---: | ---: | ---: | ---: | ---: |
| auto | 0.8523 | 1.0000 | 0.9949 | 0.7987 | 0.7633 |
| nvfp4 | 0.8452 | 0.9667 | 0.8951 | 0.8773 | 0.7633 |

SM100 now builds its views through the shared helper. For LBHNC and BLHNC, the two layouts SM100 accepts, they match the previous views on CPU whenever the cache has more than one block; SM100 itself was not run. SM86, SM89, SM120 and performance are untested.
```
