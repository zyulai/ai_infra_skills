## Purpose

ModelOpt FP8 checkpoints are currently rejected on NVIDIA A100 GPUs before vLLM can select its existing weight-only FP8 execution path:

```text
ValueError: The quantization method modelopt is not supported for the current GPU. Minimum capability: 89. Current capability: 80.
```

This PR lowers `ModelOptFp8Config`'s minimum CUDA capability from SM89 to SM80. On GPUs with capability SM80 through SM88, it also emits one model-level warning explaining that FP8 is not executed natively, that vLLM will use emulation for the model, and that some models may run more slowly. SM89 and newer GPUs retain their existing behavior and do not receive the warning.

This enables a serialized ModelOpt `quant_algo=FP8` checkpoint to load on A100 without a backend override. The exercised model was `nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-FP8`. While it may appear counter-intuitive, the emulated FP8 actually shows better performance than the unquantized BF16 model due to the bandwidth reduction achieved for bandwidth-limited GEMMs. (Added a warning because for dense/compute-limited GEMM models, FP8 emulation may lag native bf16 execution due to the dequantization overhead.)

## Test Plan

The before/after reproduction uses one NVIDIA A100 80GB GPU, tensor parallelism 1, vLLM 0.26.0, BF16 activations, and an FP8 KV cache. The tested FP8 checkpoint revision was `f8dc1c0afee92f44417695b4f5ddca9afc95ea58`.

Run this command with stock vLLM 0.26.0, then run the same command after applying this PR:

```bash
vllm serve nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-FP8 \
  --revision f8dc1c0afee92f44417695b4f5ddca9afc95ea58 \
  --served-model-name nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-FP8 \
  --tensor-parallel-size 1 \
  --max-num-seqs 512 \
  --trust-remote-code \
  --max-model-len 25088 \
  --kv-cache-dtype fp8 \
  --gpu-memory-utilization 0.9 \
  --block-size 128 \
  --no-enable-prefix-caching \
  --host 0.0.0.0 \
  --port 8000
```

Stock vLLM 0.26.0 exits at the capability check shown above. With this PR applied to the same vLLM version, the checkpoint loads, the server becomes ready, and the existing automatic FP8 fallback is selected for both dense and MoE layers. No backend-selection environment variable or command-line override is used.

For the matched BF16 control, start a second run on the same A100 with:

```bash
vllm serve nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16 \
  --revision 2d59de1cbd51c0adf384eb906b766d1aee0e0517 \
  --served-model-name nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16 \
  --tensor-parallel-size 1 \
  --max-num-seqs 512 \
  --trust-remote-code \
  --max-model-len 27136 \
  --kv-cache-dtype fp8 \
  --gpu-memory-utilization 0.9 \
  --block-size 128 \
  --no-enable-prefix-caching \
  --host 0.0.0.0 \
  --port 8000
```

The two servers use the same GPU, vLLM version, TP size, KV-cache dtype, maximum sequence count, memory utilization, block size, and prefix-cache setting. Their `max-model-len` values differ because each was set to the exercised capacity for that weight format; the GSM8K prompts and generation settings are identical.

The GSM8K evaluator used for the reported results is public at `NVIDIA/srt-slurm`, commit `cb651682117df129162cd276cf567ec70dc57b36`. Clone that revision:

```bash
git clone https://github.com/NVIDIA/srt-slurm.git
```

## Test Result

The stock FP8 run failed before model loading with the SM89 minimum-capability error. Applying this PR changed the same command to a successful load and healthy server. The full FP8 GSM8K run and the BF16 control both completed all 1,319 questions with no request failures.

| Metric | BF16 weights | ModelOpt FP8 weights | FP8 delta |
|---|---:|---:|---:|
| Completed questions | 1,319 / 1,319 | 1,319 / 1,319 | — |
| Accuracy | 61.1069% | 58.3776% | -2.7293 pp |
| Invalid responses | 0% | 0% | — |
| Evaluation wall time | 539.667 s | 435.493 s | -19.30% |
| Questions/s | 2.4441 | 3.0288 | +23.92% |
| Total output tokens | 588,906 | 611,214 | +22,308 |
| Output tokens/s | 1,091.24 | 1,403.50 | +28.62% |
| Full job wall time | 13:31 | 11:56 | -11.71% |
| Process exit status | 0 | 0 | — |

The FP8 run was approximately 1.24x faster by evaluation time and 1.29x faster by output-token throughput, with a 2.73 percentage-point accuracy reduction in this single full-dataset run. Because the FP8 run generated more output tokens than the BF16 control, output tokens per second is the more useful normalized throughput comparison than total job wall time. These results establish the measured performance/accuracy tradeoff rather than claiming that every model or workload will speed up.
