## PR body
```markdown
## Motivation

`--fp8-gemm-backend flashinfer_deepgemm` routes every dense block-FP8 linear through
`flashinfer.gemm.fp8_blockscale_gemm_sm90`. That is one Python entry point over **two
different kernels** — profiling kernel names on H200 shows the dispatch flip at M = 32:

| M | kernel actually launched |
| --- | --- |
| M < 32 | `deep_gemm::fp8_gemm_kernel_swapAB` |
| M >= 32 | `deep_gemm::fp8_gemm_kernel` |

Only the swapAB half is worth taking. This PR keeps the backend on `1 <= M < 32` and
hands everything else to DeepGEMM (or triton when DeepGEMM is unavailable), mirroring
vLLM's `FlashInferFp8DeepGEMMDynamicBlockScaledKernel`, which gates the same kernel on
`input.shape[0] < 32`.

The file already carries a guard of this shape: `aiter_w8a8_block_fp8_linear` keeps a
per-shape M bound because `ck_gemm_a8w8_blockscale` returns NaN above it.

## Why M >= 32 should not go there

**Performance — the primary reason, and it holds unconditionally.** Microbenchmark on
H200, per-shape, versus DeepGEMM:

| M | flashinfer vs DeepGEMM |
| --- | --- |
| 16 (decode) | **1.05x faster** |
| 32–64 | **1.42x slower** — flashinfer's worst region, right above the threshold |
| 850 (prefill) | 1.10x slower |

So the split is not a trade-off: below 32 flashinfer wins, above 32 it loses, and the
loss is largest immediately above the boundary.

**Accuracy — a real but checkpoint-dependent second reason.** On Qwen3.6-27B-FP8,
`sglang.run_eval --eval-name gsm8k` drops **3.8 points** with the unguarded backend.
That is not noise: two same-config repeats put the noise floor at 0.15 points. It is
localized to prefill (switching only the prefill backend reproduces it; switching only
decode has zero effect), and the failure mode is specific — extra immediate-EOS empty
generations, all `ntok=1`, while the score on the answered subset is unchanged
(0.8307 -> 0.8307). vLLM reports the same class of regression on DeepSeek-V3.1
(GSM8K 88% vs 95%) as their reason for the same split.

**But this must be stated plainly: the accuracy regression does not reproduce on every
checkpoint.** Running the existing `test_fp8_blockwise_gemm.py` (Qwen3-4B-Instruct-2507-FP8,
GSM8K 1319 examples, 8-shot) on an H200:

| backend | score |
| --- | --- |
| `deep_gemm` | 0.9016 |
| `flashinfer_deepgemm`, this PR | 0.8955 |
| `flashinfer_deepgemm`, current main (no guard) | 0.8940 |

At n = 1319 the binomial standard error is ~0.83 points, so all three agree within
noise. The defect is checkpoint- and shape-dependent, and **the existing accuracy test
does not catch it** — please read the accuracy argument as a secondary benefit on some
models, not as a universal bug fix. The performance argument is the load-bearing one.

## Why M == 0 must not go there

`fp8_blockscale_gemm_sm90` hard-fails on an empty input. Measured on H200
(N=2560, K=2048, block `[128, 128]`):

| backend | M = 0 |
| --- | --- |
| `deep_gemm` | ok, `(0, 2560)` |
| `triton` | ok, `(0, 2560)` |
| `flashinfer_deepgemm` | `RuntimeError: Check failed: (input_ptr != nullptr) is false: input is null` |

An empty batch is not an edge case here — with DP attention an idle rank runs a
zero-token forward so the collectives stay in sync
(`ScheduleBatch.prepare_for_idle`), so M = 0 is a normal steady-state input.

## What the guard does

Resulting routing, verified on H200 for M in {0, 1, 8, 31, 32, 64} x {DeepGEMM on, off}:

| M | DeepGEMM available | DeepGEMM unavailable |
| --- | --- | --- |
| 0 | `deep_gemm` | `triton` |
| 1 – 31 | **`flashinfer`** | **`flashinfer`** |
| >= 32 | `deep_gemm` | `triton` |

M = 0 and M >= 32 never reach flashinfer in either column. The M check folds into the
existing shape/dtype fallback so there is a single triton exit that keeps the UE8M0
scale unpacking, and DeepGEMM — which has its own triton fallback for shapes it cannot
serve — takes both ends when available.

## Tests

Both suites run on H200 (SM90), which is the only hardware where this code path is
reachable.

- `test/registered/quant/test_fp8_blockwise_gemm.py` — `TestFP8BlockwiseGemmDeepGemm`
  0.9016, `TestFP8BlockwiseGemmFlashinferDeepGemm` 0.8955. `Ran 2 tests, OK`.
- `test/registered/ep/test_deepep_small.py` — `Ran 6 tests, OK (skipped=1)` over the six
  non-MTP classes (scores 0.61–0.665 against a 0.60 threshold). The three MTP classes
  need `lmsys/sglang-ci-dsv3-test-NextN`, which is not publicly accessible, so they were
  not run.
- Routing verified per the table above.
- Condition isolation for the DeepEP interaction described below: nine server-launch arms
  on H200 varying MoE all-to-all backend, DP attention, TP size and GEMM backend.

Worth flagging for reviewers: **CI does not exercise this backend.** The only test that
selects it, `TestFP8BlockwiseGemmFlashinferDeepGemm`, is registered on a `4-gpu-b200`
runner while its own `skipIf(get_device_sm() != 90)` makes it a no-op there. That is why
the M >= 32 behaviour went unnoticed, and it means this path needs manual verification on
Hopper.

## What this PR does not do

**1. Auto mode is untouched; the backend stays opt-in.** An earlier revision of this PR
also made the hybrid the auto-mode default on Hopper. That commit is reverted here — see
point 2.

**2. This backend trips a pre-existing problem in the DeepEP path, and that is not fixed
here.** With `SGLANG_ENABLE_ASYNC_ASSERT=true` (enabled in CI outside `base-a`) the
server fails to start. Isolating the condition on H200, model `lmsys/sglang-ci-dsv3-test`:

| config | fp8 backend | runs | server start |
| --- | --- | --- | --- |
| tp4, `--moe-a2a-backend deepep` | `flashinfer_deepgemm` | 3/3 | **fails** — `NaN detected! sampler: next_token_logits` |
| tp4, `--moe-a2a-backend deepep`, `--enable-dp-attention --dp 2` | `flashinfer_deepgemm` | 1/1 | **fails** — same assertion |
| tp4, `--moe-a2a-backend deepep` | `triton` | 1/1 | ok |
| tp4, `--moe-a2a-backend deepep` | `deep_gemm` | 1/1 | ok (this is today's auto default) |
| tp4, `--moe-a2a-backend none` | `flashinfer_deepgemm` | 1/1 | ok |
| tp1, `--moe-a2a-backend none` | `flashinfer_deepgemm` | 1/1 | ok |
| Qwen3-4B-Instruct-2507-FP8, tp1 | `flashinfer_deepgemm` | 1/1 | ok (GSM8K 0.8955, above) |

Rows 1 and 5 are a single-variable comparison — same model, same TP, DP attention off in
both — so the trigger is `--moe-a2a-backend deepep`, **not** DP attention and not TP size.
Rows 1, 3 and 4 hold the config fixed and vary only the GEMM backend, so on this config
`flashinfer_deepgemm` is the only one of the three that fails.

The mechanism, as far as I could trace it: some rows entering the block-FP8 linears hold
uninitialized memory. At `forward_mha.py::forward_normal_core -> o_proj` one such row
measured `6.70e16`, `5.09e35`, `1.69e38`, `2.30e38` and `3.10e38` on different calls while
rows 0–6 of the same input stayed in `[0.09, 1.1]` — a different value every call at the
same call site. Whether that becomes NaN depends on the magnitude. Injecting a single
row of a known magnitude into that exact shape (N=2560, K=1024, block `[128, 128]`):

| row magnitude | `deep_gemm` | `triton` | `flashinfer_deepgemm` |
| --- | --- | --- | --- |
| <= 1e35 | clean | clean | clean |
| 1e36 – 3.2e37 | clean | **NaN + Inf** | clean |
| >= 1e38 | clean | clean | **NaN** |

So the uninitialized row is a live hazard for two of the three backends, in different
magnitude windows, and DeepGEMM — the current auto default — is the one that saturates to
a finite value at every magnitude tested. That is why nothing has caught this so far.
`triton` survives the table above in practice only because the magnitudes that actually
occur in this model skip its window.

With the assertion off, the hybrid's `output_ids` are byte-identical to pure DeepGEMM, so
real tokens are unaffected. These rows sit at M < 32, so this guard does not — and
cannot — protect against them.

I could not identify the buffer that produces them. Zeroing the two `dp_attention.py` DP
buffers (at allocation, and with an explicit `buffer.zero_()` outside the
symmetric-memory context) does not fix it, and neither does sanitizing the `o_proj` input.
One further data point I cannot fully attribute: with both CUDA-graph backends disabled
the same config passes, and the garbage magnitudes observed there topped out at `5.09e35`
— below the flashinfer threshold. That run also carried an instrumentation probe, so I
cannot separate "graphs off" from "probe present". The fix belongs upstream of this
backend — initialize the region, or restrict the assertion to valid rows — and is
deliberately not attempted here. I will file it separately.

Consequence for users: **do not combine `--fp8-gemm-backend flashinfer_deepgemm` with
`--moe-a2a-backend deepep` while the async NaN assertion is on.**

**3. One observation I could not explain, recorded rather than omitted.** At the same
call site (M=8, K=2048, N=2560), one run produced NaN in the flashinfer output while all
eight input rows were finite and bounded (`0.097`–`0.473`). An isolated repro of that
shape with clean input produces no NaN, and an isolated repro with one `1.69e38` row
produces NaN only in that row (DeepGEMM and triton stay finite). I have no mechanism for
the clean-input case.
```
