## PR body
```markdown
Fixes #51094.

## Summary

- Treat `mamba_cache_mode="all"` like `"align"` when constraining OffloadingConnector hit windows.
- Recompute the last token at an exact offload-chunk boundary instead of restoring a Mamba point state that already includes it.
- Extend the existing Mamba CPU-offload boundary test to cover both cache modes.

## Root cause

`resolve_mamba_align_size()` only enabled boundary alignment for `mamba_cache_mode="align"`. In `"all"` mode, an exact chunk-boundary lookup could return the full boundary while restoring the point state at that boundary. Mamba then resumed from a state that had already consumed the last prompt token, silently changing generated output.

## Testing

- All pre-commit hooks applicable to the changed files pass (ruff, format, mypy, SPDX, forbidden imports, and repository validation hooks).
- Pytest collection confirms the existing GPU test now expands to separate `align` and `all` cases.
- Direct helper validation: `none -> None`, `align -> 32`, `all -> 32`.
- H100 model test on current `main` (`43c4bdca`) with Nemotron-Nano-9B-v2, OffloadingConnector, `mamba_cache_mode=all`, and a 2816-token exact boundary: cold run and CPU-refetch run produced the same 32 token IDs; connector debug showed the refetch constrained to 1408 tokens.
- The issue reproduction on v0.25.1 documents the negative control: without this change, the exact-boundary refetch changes output.

## Duplicate check

I searched open issues and PRs for `mamba_cache_mode=all`, `resolve_mamba_align_size`, and exact OffloadingConnector boundaries. #50409 concerns align-mode local replay-boundary caching and does not cover all-mode CPU-offload hit-window alignment. No PR currently fixes #51094.
```
