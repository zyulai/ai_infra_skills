## 正文(PR 描述)

## Purpose

Extend the fault tolerance (FT) framework (#44428) to prefill/decode (P/D) disaggregated deployments. When KV transfer is enabled, a worker failure currently causes two problems:

1. **KV transfer progress loss.** When `_model_forward` raises, the exception path discards the `kv_connector_output`, so `finished_sending` / `finished_recving` / `invalid_block_ids` for in-flight transfers are lost. After `retry` recovery, the scheduler's KV transfer bookkeeping no longer matches the actual connector state, and requests can hang or leak KV blocks.

2. **Response queue residue.** In the executor's `get_response`, the first `FAILURE` response raises immediately, without dequeuing the remaining workers' responses. The stale responses left in the MQs are then consumed by the *next* RPC call, corrupting subsequent steps.

Key design:

- **Preserve KV state on failure**: a failed worker's `kv_connector_output` is extracted before the exception is shipped, carried via a new `ExceptionWithKVConnectorOutput` / `ResponseStatus.FAILURE_WITH_KV_OUTPUT` status, and deferred into the executor's `KVOutputAggregator`
- **Drain-then-raise**: `get_response` always dequeues **all** workers' responses before raising (this covers all collective RPCs, not just `execute_model`), so no residue is left in the response queues
- **Defer-and-replay**: `KVOutputAggregator.ft_defer_kv_connector_outputs` stashes salvaged outputs; they are replayed through the normal `aggregate()` loop at the next successful step, so pending transfers are correctly reported without any special-case merging logic. Salvaged `kv_cache_events` are dropped (see Details)
- **Consume, don't drop**: on recovery, `EngineCoreSentinel` drains the batch queue and consumes each future's `kv_connector_output` (worker-side connectors use get-and-clear semantics) instead of clearing the queue wholesale
- **No new control flow**: everything rides the existing response MQ, batch queue, and `KVOutputAggregator` mechanisms

### Details

1. **Async output extraction.** `get_kv_connector_output()` is added to `AsyncModelRunnerOutput` and its implementations (v1 GPU runner, v2 `AsyncOutput` / `AsyncPoolingOutput`). In `WorkerProc.enqueue_output`, when `get_output()` raises, the pending `kv_connector_output` is extracted and shipped to the executor as `FAILURE_WITH_KV_OUTPUT`.

2. **Drain-then-raise in the executor.** In `get_response`, a `FAILURE` / `FAILURE_WITH_KV_OUTPUT` no longer raises immediately. All workers' responses are dequeued; KV connector outputs (explicit or embedded in successful responses) are stashed via `KVOutputAggregator.ft_defer_kv_connector_outputs`, and only then is the error raised. Stale exception responses from other ranks are dropped. When FT is disabled or the executor has already failed, the original raise-immediately behavior is preserved.

3. **Defer-and-replay in the aggregator.** Salvaged outputs are stashed by `ft_defer_kv_connector_outputs` and replayed through the normal aggregation loop at the next successful `aggregate()` call, so `finished_sending` / `finished_recving` / `failed_recving` / `invalid_block_ids` and worker metadata are preserved exactly as if they had arrived late. Salvaged `kv_cache_events` are dropped at stash time: a dropped event only costs a cache miss until its blocks are stored again, while replaying them could perturb the surviving workers' event quorum (e.g. overshooting LMCache's `count == num_workers` exact-match threshold). `aggregate()` itself is unchanged.

4. **Batch queue drain on recovery.** `EngineCoreSentinel` now drains the batch queue instead of `clear()`ing it: each pending future's `kv_connector_output` is consumed and applied via `scheduler.update_from_output(SchedulerOutput.make_empty(), ModelRunnerOutput.with_kv_conn_output_only(...))` (KV transfer state only -- the rest of the model output is not applied to avoid corrupting scheduler state mid-recovery).
