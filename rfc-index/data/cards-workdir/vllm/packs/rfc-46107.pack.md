# [RFC]: Heterogeneous TP↔DP parallelism across the P/D disaggregation boundary (MoRIIO)

## Motivation

Disaggregated prefill/decode lets the two phases run with **different** optimal parallelism, but MoRIIO today assumes the prefill and decode engines share the same parallelism layout (DP8EP↔DP8EP, or TP8↔TP8).

The two phases can benefit from different parallelism configurations. For example, on an 8K-in/1K-out DeepSeek-R1 workload (run on MI300X / gfx942):

- **Prefill** is latency-bound → **TP** wins TTFT (TP8 ≈ 1s vs DP8EP ≈ 10s).
- **Decode** is throughput-bound at higher concurrency → **DP/EP** scales (DP8EP keeps scaling ≥ c256).

So at high concurrencies, the best deployment option could be **heterogeneous**. With prefill nodes configured in TP8 mode and decode nodes configured in DP8EP mode, we can achieve low TTFT from the TP8 prefill, and scalable throughput at high request loads (e.g. 512 concurrent request load).

The performance results below show the benefit of the heterogeneous setup. Various concurrency levels were tested, which control the maximum number of requests that are allowed to being served at once in the P/D setup. For each concurrency level, 10 * C total requests were sent, where C is the concurrency. Warmups were also done to prevent cold start from affecting the reported performance.

At the highest concurrency tested (512 concurrency requests), the mixed parallelism 2P_TP8:1D_DP8EP setup achieves the highest throughput and lowest TTFT of the three configurations.

One target topologies has been enabled and validated by the PRs in this RFC:
- **Forward**: `P_DP8EP → D_TP8` (DP/EP prefill, TP decode). This is the configuration described above.

- **Mirror** : `P_TP8  → D_DP8EP` (TP prefill, DP/EP decode). The mirror of the configuration described above.

## Proposed Change

The P/D KV transfer must route reads across engines whose `(dp_size, tp_size)` differ. Design (describing behaviour, not the diff):

1. **Source-rank resolution lives in the connector, not the proxy.**
The proxy only does coarse instance + DP-rank request distribution; the *KV source rank* is a connector decision because only the connector knows the KV layout (MLA-replicated vs partitioned).

2. **Per-`(dp, tp)` session keying.**
Sessions/handshake state are keyed by `(engine, dp_rank, tp_rank)` (`get_engine_name_with_dp_tp`) so each remote prefill rank gets its own session + memory-region metadata, instead of a single DP-only key.

3. **Flexible prefill-TP read (this RFC's headline mechanism).**
For a TP-replicated prefill (prefill TP + MLA) feeding a TP1 decode, the latent KV is replicated across all prefill TP ranks, so *any* rank is a valid source. Previously, heterogeneous parallelism PD setups would only read from a single TP rank (TP0), rather than distributing READ load across multiple ranks. The connector picks a prefill TP rank per read via deterministic round-robin to spread reads and prefill NIC load across TP0...N-1. Gated on: `world_size==1` (decode TP1 → no local TP collective to keep in lockstep over the choice), `use_mla` (KV replicated), and `remote_dp_size==1 && remote_tp_size>1` (a pure-TP prefill with >1 rank). Outside the gate the source rank stays fixed by the local-rank mapping. This is byte-identical to current behaviour.
**Future work:**
The gate currently requires a *pure-TP* prefill (`remote_dp_size == 1`). An intra-node DP×TP prefill (e.g. `DP4TP2`) falls back to the fixed-rank read; extending the random spread to "a random TP rank *within* the request's DP partition" is a localized follow-up (the `(dp, tp)` threading is already in place).

4. **Consistent rank threading.** The chosen rank flows through the session key, the build-on-demand handshake, the peer-host resolution and the read-completion notify port, so a read and its completion notify always address the same prefill rank (a drift leaks the prefill buffer → MR overflow).

### Implementation PRs
The implementation is split into focused, **independent** PRs, all standalone on
`main` (no cross-dependencies):
- **#46116** `[Core][KV-transfer]`: heterogeneous TP<->DP read routing: DP-rank read routing, per-`(dp, tp)` session keying, the flexible prefill-TP read (§3), and an eager pre-forward handshake so mixed configs don't deadlock.
