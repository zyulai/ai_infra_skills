## Motivation

Block-wise FP8 checkpoints loaded through the compressed-tensors path (`CompressedTensorsW8A8Fp8`, `BLOCK` strategy) produce NaN / empty output on Blackwell (SM100), making such models unusable on Blackwell with the default GEMM backend (e.g. `poolside/Laguna-M.1-FP8`: GSM8K 0.00%, all generations empty).

On Blackwell the block-FP8 linear dispatches to DeepGEMM, which quantizes activations to UE8M0 scales and expects the weight scales to be UE8M0-packed as well. `Fp8LinearMethod` already requantizes the weight scales to UE8M0 (via `requant_weight_ue8m0_inplace`) when DeepGEMM is the active runner, but the `BLOCK` branch of `CompressedTensorsW8A8Fp8.process_weights_after_loading` never did — it kept the raw float32 block scales. DeepGEMM then combined UE8M0 activation scales with float32 weight scales and emitted NaN logits.

(NVFP4 is unaffected — CUTLASS path; the compressed-tensors FP8 MoE experts are unaffected — they do not dispatch DeepGEMM.)

## Modifications

- **compressed-tensors block FP8 fix.** In the `BLOCK` branch of `CompressedTensorsW8A8Fp8.process_weights_after_loading`, requantize the weight scales to UE8M0 when DeepGEMM is the active runner, so DeepGEMM no longer pairs UE8M0 activation scales with float32 weight scales. Non-Blackwell hardware and the `triton` / `cutlass` backends keep float32 scales unchanged.
- **Shared requant helper.** Extract the UE8M0 weight-scale requant decision into a single helper `maybe_requant_block_scale_ue8m0()` in `fp8_utils.py`, and route all three call sites through it — `Fp8LinearMethod`, `Fp8MoEMethod`, and the compressed-tensors scheme — so the gate (DeepGEMM runner selected + 128×128 block + bf16/aligned shape + not-already-UE8M0) lives in one place instead of being duplicated. This is a behavior-preserving refactor of the existing `Fp8LinearMethod` / `Fp8MoEMethod` paths.
- **Tests.** Add a registered CPU unit test `test/registered/unit/layers/quantization/test_deepgemm_ue8m0_requant.py` (mockable; checks the requant decision fires once for a supported DeepGEMM / bf16 / 128×128 layer and skips for non-bf16 output, DeepGEMM-unsupported shape, a non-DeepGEMM runner, and non-128×128 block sizes), plus a Blackwell-only end-to-end regression test `test/manual/quant/test_compressed_tensors_fp8_block_ue8m0.py` (skips unless SM100 + DeepGEMM).

Gated by `should_deepgemm_weight_requant_ue8m0()` (requires SM100 + `DEEPGEMM_SCALE_UE8M0`), so it is a no-op on non-Blackwell hardware and non-DeepGEMM backends.

## Accuracy Tests

`poolside/Laguna-M.1-FP8`, 8×B200, `--tp 8`, default GEMM backend, GSM8K (1319, greedy):

| | before | after |
|---|---|---|
| GSM8K | 0.00% (empty output) | 92.80% |

92.80% matches the same checkpoint on H200 (FP8, 93.25%).

The added unit tests assert the weight scales are requantized to UE8M0 and that the layer output is finite and within tolerance of a bf16 dequant reference (pre-fix: NaN). Passes on B200.

## Speed Tests and Profiling

No new kernels — this only fixes weight-scale preparation at load time, so the steady-state GEMM is unchanged. The fix restores the fast default (DeepGEMM) path on Blackwell; the pre-existing `--fp8-gemm-backend triton` fallback also produces correct output but is slower, so before this fix the only way to run the model produced either NaN (default) or degraded throughput (triton).

|---|---|---|---|---|---|---|

The default DeepGEMM path is **+25.8%** output throughput at concurrency 32 and **+54.8%** decode throughput single-stream versus the `triton` fallback. No profiling delta is expected since no kernels change; the win is purely from using DeepGEMM instead of the triton GEMM fallback.
