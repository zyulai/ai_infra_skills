## 正文(PR 描述)

Reopens #54714 (accidentally closed by a bad force-push that orphaned the branch history; GitHub would not let it reopen). Same single commit, with @njhill's review addressed: `awaiting_kvs` gating with tests for the abort seed and `num_external_tokens == 0` readback, plus the cosmetic comments (condensed comments, collapsed tuple assignment).

## Purpose

`_read_blocks` returns early when the local block list is empty — D already holds the KV, so only the producer needs telling — and it returns without recording anything. `get_finished` builds `done_recving` from `_recving_transfers` and `_failed_recv_reqs`, so the request is named in neither.

The scheduler has no other way to release it:

```python
if request.status == RequestStatus.WAITING_FOR_REMOTE_KVS:
    if request.request_id not in self.finished_recving_kv_req_ids:
        return False
```

There is no timeout. The request stays in `skipped_waiting` — a queue counted in neither `num_running_reqs` nor `num_waiting_reqs` — holding the blocks it was allocated, for the life of the process.

Recording an empty transfer list is enough: `_pop_done_transfers` already treats a request with no outstanding handles as complete. This does it whether or not the notification lands, since the KV is local either way and a failed notification only costs the producer a timeout before it frees its own blocks, which is what the existing message says.

## How it showed up

A 10-prefill/3-decode deployment under saturation. Restarting peers made `send_notif` fail 122 times in half an hour, and each of those requests was abandoned. The three decode workers ended up holding 73–85% of their KV cache with zero running and zero waiting requests and no traffic anywhere on the deployment, until their liveness probes killed them. Only a restart cleared it.

The state is hard to see from outside: with the requests parked in `skipped_waiting`, both queue-depth gauges read zero while most of the cache is spoken for.

## Test Plan

`test_full_prefix_cache_hit_is_reported_finished`, parametrised over the notification succeeding and failing, asserts the request reaches `done_recving`.

## Test Result

Against the unpatched worker the request is reported in neither case; patched, in both.
