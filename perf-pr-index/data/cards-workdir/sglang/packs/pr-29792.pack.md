## Motivation
For Mamba, each decode forward decides whether to track a recurrent state by building `mamba_track_mask` from the batch-local `seq_lens_cpu` snapshot. However, the result-processing side previously checked the track boundary using `Req.kv_committed_len`, which is shared mutable request state.

Under overlap scheduling, the scheduler launches the next batch before processing the previous batch result. Therefore, when result processing for batch A runs, the same Req object may already have been advanced by `prepare_for_decode()` for batch B.

Example with `mamba_track_interval` = 128:

- Batch A forward runs with `seq_len` = 127.
  Its `mamba_track_mask` is false, so batch A does not write a tracked Mamba state.

- Before batch A result is processed, overlap scheduling prepares and launches batch B.
  `prepare_for_decode()` advances `Req.kv_committed_len` from 127 to 128.
  Batch B's `mamba_track_mask` is true, so batch B is the batch that should write the tracked Mamba state.

- Batch A result processing then reads `Req.kv_committed_len` and sees 128.
  It incorrectly concludes that batch A crossed the Mamba track boundary, even though batch A's own forward did not.

This makes Mamba post-decode bookkeeping run for the wrong batch. In lazy extra-buffer mode, that can advance/free/update the ping-pong track slot and record `mamba_last_track_seqlen` with a state that does not correspond to batch A's forward. Later cache-hit replay can then load a Mamba state that is inconsistent with the cached prefix, causing KL divergence regressions.

Why waiting on the forward stream appears to avoid the bug:
This is not a staged write-back kernel bug. The staged path only made an existing Mamba overlap-scheduling bug easier to reproduce.Adding a wait on the forward stream does not fix the semantic bug. It only hides it.

The wrong result-processing path is still being executed for batch A using batch B's advanced boundary state. However, if result processing waits for the forward stream, batch B's forward has usually finished writing the Mamba track state by the time the incorrect post-decode bookkeeping runs. As a result, the incorrectly early bookkeeping often observes a completed state instead of an in-flight or stale slot, so the KL regression disappears.

In other words:

- Without the wait: batch A result processing may incorrectly touch batch B's Mamba track slot while batch B forward is still producing it.
- With the wait: batch A result processing still incorrectly touches batch B's track slot, but only after batch B forward has completed, so the state is more likely to be valid.

That is why wait_stream can make the test pass, but it is only a synchronization workaround. The correct fix is to make result processing use the same per-batch snapshot that the forward used:

    batch.seq_lens_cpu[i]

instead of the mutable shared request field:

    req.kv_committed_len

This keeps Mamba boundary detection aligned with the exact forward whose result is being processed, and avoids adding a global forward-stream wait on the result-processing path.




Before this fix, `req.mamba_next_track_idx` was used for two different meanings:

1. the next ping-pong slot that a future forward pass should write to;
2. the ping-pong slot that currently contains the last valid Mamba state and should be kept/donated to the prefix cache.

These two meanings are not always the same under overlap scheduling. With lazy extra buffer, a later batch can update `mamba_next_track_idx` during prepare/prealloc before the previous batch result is fully processed and inserted into the cache. As a result, cache insertion may call `get_mamba_ping_pong_keep_idx(req)` and keep the future/preallocated slot instead of the slot that actually contains the last written Mamba state.

That makes cache-hit loadback restore an incorrect Mamba state. The model can still run, but the restored state is numerically wrong, so KL divergence becomes unstable or exceeds the threshold.

The fix introduces `req.mamba_last_track_idx` to separate the two concepts:

- `mamba_next_track_idx`: producer-side pointer, meaning the next slot to write.
- `mamba_last_track_idx`: consumer-side pointer, meaning the last slot that actually contains valid Mamba state.

`get_mamba_ping_pong_keep_idx(req)` should use `mamba_last_track_idx` when lazy extra buffer is enabled, because cache insertion needs the last committed state, not the next write target.

A stream wait workaround can hide this issue by changing the overlap timing and reducing the chance of observing the wrong slot, but it does not fix the underlying ownership/indexing bug and can also hurt performance. The correct fix is to preserve the committed Mamba state slot explicitly.
