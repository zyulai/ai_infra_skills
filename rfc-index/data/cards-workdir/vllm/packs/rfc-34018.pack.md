## 正文(PRD / 提案全文)

### Motivation.

This RFC proposes adding **Helix (Context + Tensor) Parallelism** to vLLM, based on [NVIDIA's Helix paper](https://arxiv.org/abs/2507.07120) (July 2025). Helix enables efficient long-context decoding by combining Context Parallelism (sequence sharding) with Tensor Parallelism (head sharding), eliminating KV cache duplication that occurs in traditional Tensor Parallelism when `TP > num_kv_heads`.

**Paper results (NVIDIA):**
- Up to **1.5× decode latency reduction** at fixed batch size
- Up to **32× more concurrent users** at same latency target
- Communication overhead **O(B × H)**, independent of sequence length

**Key benefits for vLLM:**
- **Eliminates KV cache replication** when TPA > num_kv_heads, improving memory efficiency
- **Reduces memory pressure** for long-context workloads (256K+ tokens)
- Enables scaling MLA (DeepSeek) and GQA (Llama, Qwen) models more efficiently

## Motivation

### The Problem: KV Cache Duplication

Modern LLMs increasingly use **MLA** (Multi-head Latent Attention) or **GQA** (Grouped Query Attention) to reduce KV cache memory. However, these architectures have few KV heads:

| Model | Attention | KV Heads | Problem with TP=8 |
|-------|-----------|----------|-------------------|
| DeepSeek-V2/R1 | MLA | 1 (effective) | 8× KV duplication |
| Llama-3 70B/405B | GQA | 8 | 1× at TP=8, 4× at TP=32 |
| Qwen2.5 | GQA | 4-8 | 2-8× duplication |

When `TP > num_kv_heads`, traditional TP must **duplicate** the KV cache across GPUs, wasting memory bandwidth during decode.

### vLLM's Current DCP and KV Cache Efficiency

vLLM's Decode Context Parallelism (DCP) helps by sharding KV cache along the sequence dimension. DCP works functionally with any TP/DCP combination, but there's a **KV cache efficiency** consideration:

In standard DCP with TP=32, K=8, DCP=4:
- Each DCP rank has TPA=8 Q heads but only HKVP=2 KV heads
- AllGather Q brings all 32 Q heads to every rank
- Each rank computes attention for all 32 Q heads against its 2 local KV heads
- This effectively replicates each KV head 4× across TPA

This KV replication increases memory pressure for long-context workloads. The replication factor grows as TPA/K increases.


### Proposed Change.


## Proposed Solution: Helix (Context + Tensor) Parallelism

Helix decouples attention and FFN parallelism, allowing the same N GPUs to "twist" between two configurations each layer:

```
Attention Phase:  KVP × TPA  (KVP = sequence sharding, TPA = head sharding)
FFN Phase:        TPF × EP   (standard tensor/expert parallelism)
```

### Key Difference from DCP

| Aspect            | Standard DCP                | Helix                           |
| ----------------- | --------------------------- | ------------------------------- |
| Communication     | AllGather Q + ReduceScatter | **All-to-All + LSE**            |
| Q distribution    | AllGather to all ranks      | Distributed by TPA              |
| KV efficiency     | Replicates when TPA > K     | **No replication**              |
| GQA at TP=32, K=8 | Works but 4× KV replication | ✅ No replication (TPA=8, KVP=4) |

### Data Flow

```
Input → QKV Proj → FlashAttn (local KV) → All-to-All → LSE Reduction → Output Proj → AllReduce
        (redundant)  + LSE                 (exchange)   (exact softmax)
```

The All-to-All exchanges partial attention outputs with their log-sum-exp (LSE) values, enabling mathematically exact attention reconstruction across KVP ranks.

## Roadmap

| Phase | Description | Dependencies |
|-------|-------------|--------------|
| **1. Core Helix (MLA)** | All-to-All + LSE reduction for MLA models | None |
| **2. GQA Support** | Extend Helix to GQA models beyond KV head constraint | Phase 1 |
| **3. A2A Optimization** | Optimized All-to-All implementation | Phase 1 |

Phase 1 is the prerequisite; Phases 2 and 3 can proceed in parallel.

## Design Principles

1. **Minimal new parameters** - Single `helix_mode` flag; reuse existing `tensor_parallel_size` and `decode_context_parallel_size`
2. **Reuse DCP infrastructure** - KV interleaving, slot mapping, rank groups all compatible
3. **Feature parity** - Support same models/backends as DCP

## API Design

```python
from vllm import LLM

# Enable Helix for long-context MLA model
llm = LLM(
    model="deepseek-ai/DeepSeek-V2-Lite",
    tensor_parallel_size=8,
    decode_context_parallel_size=4,  # KVP = 4
    helix_mode=True,                 # Enable Helix (All-to-All)
)

# For GQA model beyond KV head limit (Phase 2)
llm = LLM(
    model="meta-llama/Llama-3-70B",
    tensor_parallel_size=32,
    decode_context_parallel_size=4,  # Would not work with standard DCP
    helix_mode=True,                 # TPA=8, KVP=4
)
```

## Alternatives Considered

### 1. Extend DCP to support TP > num_kv_heads

Would require duplicating KV heads across ranks, defeating the purpose of context parallelism.

### 2. Ring attention

Higher latency for decode phase due to sequential send/recv chain. All-to-All provides lower latency when all GPUs have direct connectivity (NVSwitch).

- **Helix Paper:** [arXiv:2507.07120](https://arxiv.org/abs/2507.07120) - Original Helix parallelism paper (NVIDIA, July 2025)
- **vLLM DCP:** Existing decode context parallelism in vLLM

  - [#26133](https://github.com/vllm-project/vllm/issues/26133) - Context Parallelism with Fully Sharded KV Cache and Ring Attention

**Differentiation:** While #22693 and #26133 use ring attention for context parallelism, Helix uses **All-to-All** communication which provides lower latency on NVSwitch-connected systems and removes the `TP ≤ num_kv_heads` constraint for GQA models.
