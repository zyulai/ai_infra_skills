## Motivation

Fixes #50722.

#46586 (c81230bffe) made `TokenizerManager._stream_one_response` call `await request.is_disconnected()` before **every streamed chunk**; before it, only non-streaming outputs ran that check. Since then, high-concurrency streaming throughput has dropped 10-25% across models and platforms. On gpt-oss-120b TP4 / GB200 at 8k-in/1k-out, concurrency 256, the drop is -22% at c81230bffe and -23% on today's `main`. Bisecting nightly CI landed on c81230bffe. This PR removes the cost while keeping the abort-on-disconnect behaviour #46586 added.

### Root cause: what one `is_disconnected()` call costs

`Request.is_disconnected()` does not just read a flag. Starlette implements it as a `receive()` inside an already-cancelled anyio `CancelScope`:

```python
with anyio.CancelScope() as cs:
    cs.cancel()
    message = await self._receive()
```

Under uvicorn that `receive()` waits on `message_event`. Each call therefore:

1. Suspends the stream's task.
2. Waits one full event-loop pass for anyio's `call_soon` to deliver `Task.cancel()`.
3. Unwinds a `CancelledError` through `receive -> is_disconnected -> CancelScope.__exit__`.

The default `stream_interval` is 1, so this runs once per token per stream. It all lands on the single TokenizerManager event loop, which also serves HTTP, tokenizes 8k-token prompts and fans out outputs.

In a FastAPI/uvicorn microbenchmark (256 SSE streams fed by one shared decode-step ticker, server pinned to one GB200 Grace core):
- Server CPU per chunk rises from 14 to 42 us.
- The highest sustainable chunk rate drops from ~68k/s to ~24k/s.
- Each probe takes ~5.4 ms of wall time, one loop pass.

On the GPU, the scheduler is unaffected: its decode logs show ~28.6k tok/s at ~253 running requests in both builds. The loss is between the scheduler and the client. Client ITL rises 35%, and average scheduler occupancy drops from 126.5 to 114.8 running requests.

### Why streams do not need per-chunk polling

The HTTP response layer already detects a disconnected stream, without polling:

- **uvicorn (httptools and h11) and Granian, the two servers SGLang ships with, report ASGI `spec_version` 2.3.** Starlette's `StreamingResponse` runs `listen_for_disconnect()` alongside the body. On `http.disconnect` it cancels the body iterator, and `generate_request`'s cleanup (`_release_req_states_on_failure`) aborts the request.
- **ASGI spec >= 2.4.** A failed `send()` raises, and #46586's `_ClosingStreamingResponse` closes the iterator.
- **gRPC streams.** `_send_with_backpressure` returns `False` once the callback reports a closed stream, and `_run_generate` then calls `aclose()`.

The GPU runs below confirm it. **Every** build, including the parent of #46586 that has no per-chunk probe, frees a dropped stream within 0.14 s on `/v1/completions`, `/v1/chat/completions` and `/generate`. The per-chunk probe never made streaming aborts faster on these servers.

## Modifications

`_stream_one_response` now runs the per-output disconnect poll **at most once per `SGLANG_REQUEST_STATE_WAIT_TIMEOUT`** (default 4 s) instead of before every chunk.

That interval already governs the other polled path: a request waiting without output polls on the `asyncio.wait_for` timeout. Non-stream text requests are aborted on that path, because intermediate non-stream outputs do not wake the waiter; that is why #46586 measured 4.2 s for non-stream. With this change, a request with an HTTP client polls on one time-based cadence whether or not tokens are flowing.

- The first output still polls (`next_disconnect_poll = 0.0`), so a client lost while queued or during prefill is caught before any token goes out. The existing `test_streaming_disconnect_aborts_before_next_chunk` passes unchanged.
- A long stream is still re-polled every wait timeout. Deployments where the ASGI server or a proxy never signals a disconnect keep the bounded fallback #46586 wanted.
- Per stream, the cost drops from one probe per token to roughly one per 4 s. For 1k-token outputs that is about 99% fewer probes.

### Why not simply revert, and why not other options

- **Revert c81230bffe's tokenizer_manager hunk** (no poll for streams). That would also give up the fallback for a stream whose disconnect is never reported. The remaining throttled polls cost at most ~1.3%, within run-to-run noise (see the controls below), so keeping the fallback is cheap. The rest of #46586 (`_ClosingStreamingResponse`, closing the inner generator in `_generate_chat_stream`, aborting only while the request still owns its rid) stays as is. Those are the event-driven pieces that actually stop disconnected streams.
- **Make the probe itself cheap.** ASGI has no non-blocking way to ask whether a disconnect is pending. Starlette's cancelled-scope `receive()` is the portable form. The only alternative is a concurrent per-request `receive()` watcher task, which races Starlette's own `listen_for_disconnect()` for the same `http.disconnect` message and behaves differently across ASGI servers.
- **A new tuning knob.** Not needed. `SGLANG_REQUEST_STATE_WAIT_TIMEOUT` is already documented as the per-request wait-loop poll interval (`rust_server/parity.py`), so no new constant or env var is introduced.

## Accuracy Tests

No change to model outputs; this only changes how often the HTTP disconnect is polled.
