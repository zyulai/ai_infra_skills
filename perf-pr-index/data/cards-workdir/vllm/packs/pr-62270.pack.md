## Overview

Unlocks `--attention-config '{"indexer_kv_dtype":"fp8"}'` for MiniMax-M3 on ROCm gfx942 (MI300-series, CDNA3). gfx950 (MI350-series) keeps its fp8 routing through the AITER indexer, and CUDA behavior is unchanged.

## Claims

- fp8 indexer cache now selects on gfx942: Triton scorers get an e4m3**fnuz** cache instead of bf16, with correct saturation in both index-cache writers.
- +32% KV cache capacity for the same GPU memory.
- Serving throughput is neutral at short context and better at long context; GSM8K is unchanged.
- gfx950 keeps the pre-patch routing (fp8 via the AITER indexer, e4m3fn/OCP convert); NVIDIA keeps e4m3fn, `constexpr` 448.

## Details

Root cause, three pieces:

- `select_indexer_impl_cls` refused `indexer_kv_dtype="fp8"` on every ROCm platform, although the Triton scorers are flavour-agnostic (fp8 x fp8 accumulated in fp32).
- The index cache was pinned to e4m3**fn** (`torch.float8_e4m3fn`), which gfx942 cannot convert.
- The fused qknorm/rope/kv-insert writer picked its convert with `#if defined(HIP_FP8_TYPE_OCP)` — the macro is always defined (to 0 or 1), so gfx942 took the OCP branch and emitted OCP-labelled bytes that read back as wrong fnuz values (e.g. 1.1 -> 1.0, 0.77 -> 0).

The fix: the cache takes `current_platform.fp8_dtype()` (fnuz on gfx942, fn on gfx950/CUDA as before), the selector admits fp8 on ROCm gfx942 via the platform's `on_gfx942()` predicate, and the writer picks the flavour per target (`__gfx942__` -> fnuz) with saturation at `quant_type_max_v` (224 for fnuz, 448 for e4m3fn). Host checks expect the device's own flavour via the existing `is_fp8_ocp()`, and the Triton index-cache insert (AITER sparse-PA path) saturates at the same bound instead of producing NaN for out-of-range keys. gfx950's fp8 path keeps going through the AITER indexer (`SUPPORTED_ARCHS=("gfx950",)`), selected before this fallback is consulted.

Not a duplicate: the closest open PRs touching this area (#60930 CuTe prefill scorer, #59979/#59980 FMHA/MSA) are NVIDIA-side work; none enable the fp8 index cache on gfx942
