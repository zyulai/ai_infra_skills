## 正文(PR 描述)

## Overview

On ROCm, `hipMemGetInfo` counts every allocation as at least 2 MB, so after warmup the extensible KV cache (#56492) sizes itself from free memory that looks a few GB smaller than it is. This PR adds that memory back once, at the final sizing, using amdgpu's exact VRAM count. Only unpartitioned discrete ROCm GPUs are affected.

**Root cause.** The amdgpu driver rounds each allocation up to 2 MB in the free memory it reports, on purpose (commit 1ac354beecfd, "drm/amdgpu: Pessimistic availability based on rounded up allocations"), unless the GPU's memory is kept in system memory (`apu_prefer_gtt`). Its own allocation check uses exact sizes. The many small kernel code objects loaded during warmup therefore hide a few GB. The sysfs counter `mem_info_vram_used` counts exact sizes for the whole device.

## Claims

- On an unpartitioned discrete ROCm GPU, the extensible KV cache sizes itself from exact device memory use. On Llama 3.1 8B / R9700 the KV cache went from 51,712 to 76,288 tokens, with no OOM and no failed requests (one run per config).
- The correction is never more than what is physically free and never negative. Other processes' allocations are not added back.
- Integrated GPUs, partitioned GPUs, a missing or mismatched sysfs count, and all non-ROCm platforms keep the current behaviour (no-op platform hooks).

**Limitations.**
- `gpu_memory_utilization` now bounds exact use on unpartitioned discrete ROCm GPUs.
- Several instances on one GPU: with the extensible cache on, `request_memory` skips the startup check. An earlier instance's rounding is already in a later instance's baseline and is never added back, so a later instance gets a smaller cache, depending on start order. This doesn't cause OOM.
- KFD's page-table reserve and RAS pages are not in the exact count (about 80 MB on R9700). The 3 GB ROCm margin floor (#65418) covers them.
- Tested on R9700 (gfx1201) only. CDNA should behave the same according to the driver code, but this is unverified. In AMD CI, `tests/v1/worker` runs on `mi355_dpx` (partitioned, so it falls back), but other jobs run on `mi300_1` / `mi355_1`. I don't know whether those pools are partitioned. If they aren't, this path runs there untested, and the correction could be limited to validated GPUs.
- The V1 runner and `--no-enable-extensible-kv-cache` are unchanged.

**Not a duplicate.** I found no other open PR correcting ROCm's 2 MB-rounded free memory. #65413 (merged) corrects UMA free memory and is the fallback inside the new hook. #55828 (open) changes which memory counts as this process's own and only takes effect on NVML. No runtime overlap and either merge order works.

**Related:** #56492 (extensible KV cache), #65413 (UMA free-memory correction), #65418 (ROCm 3 GiB margin floor), #55828 (process-scoped KV sizing), #60121 (asynchronous VRAM release on ROCm).

**Note:** From my understanding, `amdsmi_get_gpu_memory_usage` reads the same `mem_info_vram_used` so `amdsmi` and `sysfs` should be the same but if it can't be read then it will ask KFD and will again use 2MB rounded values that hipMemGetInfo reports.

+    """Free bytes by the exact VRAM count, or None where there is none.

+        if used is None or used_after is None:

+            "VRAM count.",

+            hidden / (1 << 30),
+        )
