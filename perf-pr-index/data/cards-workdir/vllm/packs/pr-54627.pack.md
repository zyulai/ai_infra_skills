## PR body

## Purpose

`prefill_schedule_interval` defers new prefills to every Nth engine step, so that decode
runs in longer uninterrupted stretches instead of meeting prefill on most steps. Today it
only takes effect under data parallelism: `DPEngineCoreProc._should_throttle_prefills()`
drives the cadence from a `step_counter` shared across ranks, while the base
`EngineCore._should_throttle_prefills()` returns `False` unconditionally. Setting the
option on a single engine is silently a no-op, with no warning.

This applies the same interval in the scheduler when `data_parallel_size == 1`. Without
peers there is nothing to align to, so the interval is measured from the last step that
carried prefill rather than against a global grid, which means no shared counter is
needed. Data-parallel deployments are untouched and keep their rank-aligned cadence.

As with the existing DP gate, prefill is deferred only when a running request can decode
in its place (`any(not r.is_prefill_chunk for r in self.running)`), so the interval never
leaves the model idle. The default interval of `1` disables the gate, leaving admission
behavior unchanged.

The motivating deployment is a single engine using decode context parallelism
(`--decode-context-parallel-size 8`). DCP is parallelism *within* one engine, so the
existing DP-only wiring never reaches it, even though the workload benefits from the
cadence as much as a DP deployment does.

## Why this is not duplicating an existing PR

No open PR touches `prefill_schedule_interval` or `_should_throttle_prefills`. The only
open PR matching `throttle_prefills` is #52969, an unrelated fix for aborted requests.

Two open PRs are adjacent but solve different problems:

- **#49075** (`max_num_partial_prefills` / `max_long_partial_prefills` in V1) bounds *how
  many* prefills run concurrently. This PR controls *how often* a step carries prefill at
  all. The two compose, and neither subsumes the other. Note that #49075 edits both
  scheduling loops, so a textual conflict is possible depending on merge order.
- **#53571** (SLO-aware scheduling policy) reorders the waiting queue by TTFT target,
  changing *which* request is admitted. This PR changes *whether* prefill is admitted on
  a given step, and does not reorder anything.

Checks run (`gh` was not authenticated in my environment, so these were run against the
public search API; the equivalent `gh` invocations are):

## Serving results

### Kimi-K3

Kimi-K3 FP4, 8x MI355X, a single engine with DCP=8 and LMCache KV offload, replaying an
agentic-coding trace over a 3600s measured window. Interactivity is per-user output speed
at the 90th percentile; higher is better.

The measured configuration enables this PR's `prefill_schedule_interval=33` together with
the cache-aware admission window from #54625 (`--cache-aware-admission-window 64`). The
baseline is the same build with both options absent. The figures below are therefore for
the two options together, not for this change in isolation.

**p90 interactivity (tok/s/user)**

| concurrency | baseline | with both options |
| --- | --- | --- |
| 44 | 11.94 | 17.28 (+44.7%) |
| 48 | 11.32 | 16.33 (+44.3%) |

Interactivity improves by roughly 44% at both concurrencies — the same trade-off the
option already offers under DP, now reachable without it.

Throughput is close to unchanged over the same runs, as expected for a change that
reorders admission rather than removing work: 9,617 to 9,390 tok/s/GPU at concurrency 44
(−2.4%) and 10,537 to 10,103 at concurrency 48 (−4.1%).

An earlier revision of this section reported a `prefill_schedule_interval` sweep at
concurrency 52 against the `vllm-simple` KV offload backend. That backend is no longer
what we run; these numbers replace it.

No accuracy eval was run. Neither the model computation nor sampling is touched; the
change affects only which requests are admitted on a given step. Batch composition does
change, as with any scheduling change, so outputs are not bit-identical. I am happy to
run `tests/evals` or a gsm8k pass if reviewers would like that confirmed.

### Workload shape

Both models replay the same public agentic-coding trace set
(`semianalysis_cc_traces_weka_062126`): multi-turn tool-calling traffic with
long, highly repetitive contexts. It is worth stating the sequence lengths
explicitly, because they are what makes `prefill_schedule_interval` matter and
they are nothing like a chat workload.

| | MiniMax-M3 agentic | Kimi-K3 agentic |
| --- | --- | --- |
| input length, mean | 104k tokens | 134k tokens |
| input length, p50 / p90 | 77k / 183k | 93k / 266k |
| output length, mean | 687 tokens | 851 tokens |
| output length, p50 / p90 | 288 / 1,524 | 317 / 1,987 |
| input : output ratio | ~151 : 1 | ~158 : 1 |

Requests are prefill-dominated by roughly 150:1 on both models. The practical
consequence: at `--max-num-batched-tokens 32768`, a mean 104k-token prompt is
about 4 prefill chunks and a p90 183k-token prompt about 6, and each chunk
waits for the prefill interval before it can run. The interval is therefore
paid several times per request before that request's first token — which is why
a value tuned on one model should not be assumed to carry over to another with
different prompt lengths.

(Sequence-length distributions only; the two models were measured at different
concurrencies and topologies, so their latency figures are not comparable to
each other.)

### MiniMax-M3

A second model, so the result is not specific to the one MoE the option was
tuned against. MiniMax-M3 MXFP4 on MI355X, **tensor parallel 4**, **prefix
caching enabled**, no KV offload (`offloading=none`), replaying the same
agentic-coding trace set over a 1200s measured window.

Prefix caching being on is load-bearing rather than incidental: #54625 is a
cache-aware admission policy, so with prefix caching disabled there is nothing
for it to be aware of. These runs sustain an 81-90% server-side prefix-cache
hit rate, against a 96.2% theoretical ceiling for this trace set.

**On the absence of KV offloading.** This is a limitation of the MiniMax-M3
numbers rather than a free choice, and it matters for how they are read. The
Kimi-K3 figures above were taken **with** LMCache, and this option is worth
considerably more behind an async KV connector than without one — which is
consistent with the failure mode @hyukjlee described on this PR, where requests
parked in connector lookup make `schedule()` return empty and the pre-fix code
counted those calls against the interval.

We were unable to measure that configuration on MiniMax-M3. With LMCache
enabled, warmup stalls at the same point every time: `num_requests_running=0`
alongside `num_requests_waiting=1`, i.e. a single request parked on the
connector and never admitted, with the GPUs loaded and idle. Two LMCache builds
were tried — `0.5.3` (aborts there) and `0.5.6.dev146+rocm7.2` (hangs there) —
and both the baseline and the treated arm behave identically, so this is not
the scheduler policy. The published MiniMax-M3 agentic CI also runs
`offloading=none` on every job.

So the MiniMax-M3 figures below come from the configuration where this option
has the **least** to offer. They should be read as a lower bound, not as a
like-for-like comparison with the Kimi-K3 numbers.

Server flags follow the published MiniMax-M3 agentic configuration unchanged
(`--enable-chunked-prefill --max-num-batched-tokens 32768`,
`--enable-prefix-caching`, `--max-num-seqs $((2 * CONC))`, fp8 KV cache, EAGLE3
speculative decoding). Both arms run the same image and the same flags; the
only difference is:

```
with both options:  --prefill-schedule-interval 25
                    --cache-aware-admission-window 64
                    --cache-aware-admission-threshold 0
baseline:           neither flag passed
```

Both options default to off, so the baseline is the unpatched behaviour of the
same binary. The flags were read back off each running server to confirm the
only difference is scheduler policy.

**p90 interactivity (tok/s/user)**

| concurrency | baseline | with both options |
| --- | --- | --- |
| 24 | 130.43 | 140.72 (+7.9%) |
| 28 | 143.47 | 165.90 (+15.6%) |
| 32 | 122.37 | 129.15 (+5.5%) |
| 48 | 101.83 | 107.97 (+6.0%) |

Three of the four points sit between +5.5% and +7.9%, with concurrency 28 an
outlier at +15.6%. The effect is therefore consistent rather than
concurrency-dependent over this range.

These figures are not tuned. A single setting --
`prefill_schedule_interval=25`, `cache_aware_admission_window=64` -- was used
at every concurrency; the interval was chosen once from a sweep at concurrency
48, and the window is the value carried over from the Kimi-K3 runs. Neither was
re-tuned per concurrency, and no search was done over the two together. Since
the sweep at a single concurrency already moved p90 interactivity between +1.6%
and +7.3% depending on the interval alone, per-concurrency tuning should be
expected to do better than this. Treat these numbers as a floor for what the
options can deliver on this model, not a ceiling.

Total throughput over the same runs is close to unchanged -- between -3.2% and
-0.1% tok/s/GPU across the four points. That is what this kind of change should do: it
reorders admission rather than removing work.

Concurrencies follow the published agentic configuration for this model,
which validates `conc-list: [32, 48]`.

No accuracy eval was run for this model either, for the same reason as above:
neither model computation nor sampling is touched.
