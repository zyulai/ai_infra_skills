## Motivation

On hybrid models, linear-chain speculative verify (EAGLE chain, MTP, DFLASH, DSPARK, standalone) calls `causal_conv1d_update` with an intermediate conv window. The window lets the conv state of the accepted prefix be restored after verify.

On CUDA and ROCm, `MambaPool` stores this window deduplicated. Each slot holds one `[dim, T + K - 2]` row, exposed as an overlapping `[T, dim, K - 1]` view whose step stride equals its window stride.

The kernel still writes the window per token, with three lane-strided element stores per draft token. Each column is therefore written up to three times by narrow scattered stores. On GB300 (dim 10240, bf16, T = 8, bs 128), the verify conv takes 106 us with the deduplicated window, against 39 us with a dense window.

## Modifications

- **`_causal_conv1d_update_kernel`**: adds a `DEDUP_CONV_WINDOW` path.
  - Step t's window is columns t..t+2 of the row `[state[1], state[2], x_0, ..., x_{T-1}]`.
  - The kernel writes that row once, as a `[BLOCK_N, next_pow2(T + 2)]` tile before the token loop, and skips the per-token window stores.
  - The tile mask covers exactly the T + 2 columns the per-token path writes.
  - Padded rows still exit before any store.
  - Two `tl.static_assert`s keep the branch from being compiled for a conv width other than 4 or together with a tree mask, so the kernel is safe without relying on its caller.
- **`causal_conv1d_update`**: takes the tile path only when all three hold:
  - the window view's step stride equals its window stride;
  - the verify is a chain (no tree mask);
  - the conv width is 4.

  With step stride == window stride == s, the per-token stores write column t + w of the row at (t + w) * s, and the tile writes column c at c * s: the same addresses and the same values, for any layout with those strides. MambaPool's deduplicated view is one such layout. There are no new arguments, and callers are unchanged. Kernels that do not take the tile get `NP2_WINDOW_COLS=1`, so no extra variants are compiled.
- **Test**: `test_causal_conv1d_update_dedup_window_matches_per_token`.
  - It runs the kernel on a dense window (per-token path) and on the deduplicated view (tile path).
  - It checks bitwise that the shared rows, the windows read through the view and the conv state match a reference row built in torch.
  - It checks that slots of padded rows are untouched.
  - It compares the conv output with the file's update tolerances.
  - Coverage: T in {2, 3, 8, 16} (T + 2 pads to tiles of 4, 8, 16 and 32), a `num_accept_tokens` state offset, MambaPool's axis-0 window layout seen transposed, fp32 and bf16, a dim that leaves a partial channel block, with and without padded rows.
- A comment in `MambaPool` is updated to describe the new write.

## Scope

This path is used by every chain verify (topk <= 1) whose conv window uses `MambaPool`'s deduplicated layout. Examples are GDN models (Qwen3.5/3.8) and Mamba2, on CUDA and ROCm.

These are unchanged and keep the per-token stores:
- dense windows: `UnifiedMambaPool`, KDA / Kimi-Linear, tree verify;
- deduplicated windows of a conv width other than 4 (for example LFM2, width 3).

## Accuracy Tests

- The new test passes, and so does the full test file (270 tests at 8eb01f2c9, which adds the tree-mask assert and the accept-offset, axis-0 and odd-T cases).
- The test is sensitive: a tile that ignores `num_accept_tokens` fails exactly the accept-offset cases, and forcing the tile together with a tree mask fails at compile time on the new assert.
- compute-sanitizer memcheck, racecheck and initcheck are clean on the tile test as of 8177311a1 (T in {2, 4, 8, 16}); besides comments and tests, 8eb01f2c9 adds only a compile-time assert and `NP2_WINDOW_COLS=1` for launches without the tile. - chain verify, bf16 mamba state, overlap scheduling on, `--max-running-requests 128`;
- SPEED-Bench first turns, T = 1, top_p 0.95, top_k 20, up to 4096 output tokens;
- mean of 3 interleaved runs.

Decode tok/s = per-request decode rate (output tokens after the first / time after the first token), times concurrency; c1 is the single-request decode rate.

| concurrency | main | this PR | change |
|---|---|---|---|
| 64 | 6048 | 6361 | +5.2% |
| 128 | 6992 | 7329 | +4.8% |

Acceptance length is 3.59-3.63 in all six runs.

At c128 the running cap equals the concurrency, so about one request waits in the queue. https://github.com/sgl-project/sglang/pull/46182 shows that this setup reads 7-15% higher at that level than a larger cap, on both sides, so compare c128 only within this table.

Single runs at lower concurrency: c8 2031 -> 2104 (+3.6%), c32 4723 -> 4973 (+5.3%). At c1 the change is within noise: 332 -> 321, with acceptance length 3.70 vs 3.60 from sampling; per accepted token the rate differs by under 0.5%. Greedy (single runs): c1 357.0 -> 357.1 with identical acceptance length and output tokens, c64 6746 -> 7145 (+5.9%).

The end-to-end runs used the first commit; the two later commits add compile-time asserts, comments and tests, and pass `NP2_WINDOW_COLS=1` to kernels that skip the tile, with no runtime change on the tile path.

## Related upstream work

- sgl-project/sglang#38897 adds a separate packed variable-length kernel, `causal_conv1d_update_varlen`, to the same file. It writes the intermediate window per token with three stores per step, the pattern this PR replaces. There is no textual conflict (it is a new function), but if both land, packed verify through that kernel does not get the tile store. https://github.com/sgl-project/sglang/pull/46189 takes the other route: it adds packed rows to this kernel, so the tile store covers them too.
- This PR does not depend on any open PR.

## Notes

- Only GB300 was tested; ROCm takes the same path but has not been run.
