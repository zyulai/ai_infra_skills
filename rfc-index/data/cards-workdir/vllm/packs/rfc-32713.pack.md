## 正文(PRD / 提案全文)

### Motivation.

LLMs fundamentally are token-in, token-out models. For them to be useful, we need to parse from text into tokens ("tokenization") and parse from tokens into useful responses ("detokenization", reasoning parsing, tool calling parsing).

Due to legacy reasons, vLLM has separate entrypoints for reasoning parser / tool calling parser, as the need for a reasoning parser did not arise until deepseek R1

*Current State of the World*
- For input tokenization, we use chat template jinja, which is defined from the model spec.
  - OpenAI harmony is separate
  - Deepseek v3.2 also has a special tool parser
- For detokenization / responsesAPI parsing, we have
  - tokenization from the model spec, called via _preprocess_chat()
  - Abs_reasoning_parsers
  - Abstract_tool_parser

OpenAI Harmony is a special case, in which tokenization / detokenization happen separately.
- For tokenization, we use _make_request_with_harmony
  - get_encoding().render_conversation_for_completion goes from message -> tokens
- For detokenization
  -From token IDs -> OpenAI harmony messages, [context.py](http://context.py/) HarmonyContext runs self.parser.process()
  - For openAI harmony messages -> responsesAPI items, _make_response_output_items_with_harmony converts HarmonyMessage -> ResponseOutputItem. 

The issues with the current set up are the following
- OpenAI Harmony is a forked code path, which requires separate development. We further needed to fork for DeepSeek v3.2 not using a jinja template
- We have three code entrypoints for a lot of similar logic (_preprocess_chat() for tokenization, tool parsing, and reasoning parser

### Proposed Change.

We present this RFC with the following proposals
- few possibilities for configuration mistakes (ie why would you want to use a Llama reasoning parser on a deepseek model, or having incongruent tool calling / reasoning parsers)
- flexibility: 
- future proof: if in the future there is another type of parsing, it could be added within the proposed class.

With the above in mind, we propose a single unifed class, known as a `Parser` which can handle tokenization, and detokenization via reasoning parsing, tool calling parsing, and support for future features such as interleaved reasoning and parallel tool calls.

```
class Parser():

    # GPT-OSS / custom models can tokenize here

  def extract_reasoning()

  def extract_tool_calls()
    # self.tool_parser.extract_tool_calls()
```

This class would have the flexibility of supporting both:
- legacy flows: tokenization via jinja template, calling the reasoning / tool calling subclasses
- custom implementations: Deepseek v3.2 tokenizer can enter via tokenize() and GPT-OSS tokenization / de-tokenization can enter via the parser class too.

So in the long term, we can remove the tool calling / reasoning parser as it should be inherited by default based on the model :) 
```
vllm serve MiniMaxAI/MiniMax-M2   
--tensor-parallel-size 4   
--tool-call-parser minimax_m2   # remove this flag
--reasoning-parser minimax_m2 # remove this flag
--enable-auto-tool-choice  # remove this flag
--trust-remote-code
```
