## 正文(PR 描述)

## Motivation

Fixes #22249

The Anthropic API entrypoint (`serving.py`) uses `time.time()` (wall clock, epoch-based) for `received_time`, while downstream metrics computation in `req_time_stats.py` calculates deltas against `time.perf_counter()` (monotonic). This clock mismatch produces large negative values  in Prometheus histograms (`time_to_first_token_seconds` and `e2e_request_latency_seconds`).

The OpenAI entrypoint (`serving_base.py`) was already fixed to use `monotonic_time()` in PR #17640, but the Anthropic entrypoint was missed.

We discovered this bug in production where Anthropic API requests consistently produced negative TTFT and e2e latency values in Grafana dashboards.

<img width="1840" height="696" alt="image" src="https://github.com/user-attachments/assets/a461fea6-5a4c-40ac-971e-ef03d1e6a82e" />

## Modifications

- Changed `received_time = time.time()` to `received_time = monotonic_time()` in both `_handle_non_streaming` and `_handle_streaming` methods.
- Added import for `monotonic_time` from `sglang.srt.observability.req_time_stats`.

Note: `received_time_perf` is intentionally kept — it serves a different purpose (computing `validation_time` locally), while `received_time` is passed to `req_time_stats` for Prometheus metrics.

## Accuracy Tests

N/A — This change only affects Prometheus metrics collection, not model outputs.

## Speed Tests and Profiling

N/A — `monotonic_time()` wraps `time.perf_counter()` which has equivalent performance to `time.time()`.
