```markdown
## Motivation

With MTP (NEXTN) speculative decoding under spec-v2 overlap scheduling, each decode step consists of three CUDA graphs:

```
[draft graph]   NEXTN draft model, k autoregressive passes -> draft-token chain
[verify graph]  target model, one forward over the draft tokens (TARGET_VERIFY)
[extend graph]  draft model backfills KV for the accepted tokens (DRAFT_EXTEND)
```

Between the graphs live eager "seams": accept sampling, cache-slot assignment, attention-metadata rebuild, next-step draft input preparation. At low concurrency (bs=1 to small batches) these seams, host-side Python dispatch and per-step synchronization the GPU cannot overlap, become GPU idle time.

### Host run-ahead, and what pins it

<img width="1948" height="1158" alt="image" src="https://github.com/user-attachments/assets/43ee9baf-a579-4288-8dbb-fbdf19c5e62c" />

sglang's `event_loop_overlap` is designed so that while the GPU executes step N, the host is already assembling and enqueuing step N+1; the host stays off the critical path iff **host loop time < GPU step time**. The `FutureMap` keeps cross-step data (next tokens, new_seq_lens, draft seeds) GPU-resident, relayed by pool index between graphs, so the host can launch the next step without ever seeing accept results, launch-queue depth grows to ~1 full step of run-ahead:

<img width="2624" height="1452" alt="image" src="https://github.com/user-attachments/assets/f81c46ee-7d6f-48d0-a0b0-7fc2327fcab5" />

Several per-step host costs, however, still pin the host to the GPU's progress and shrink that run-ahead back toward lockstep:

1. **A blocking per-step seq_lens D2H stream sync for KDA hybrids.** `KDAAttnBackend` never declared `needs_cpu_seq_lens`, inheriting the base-class `True`, which forces `FutureMap.resolve_seq_lens_cpu` onto the blocking path (`fwd_prepare_d2h_stream.synchronize()` every step). In bs=1 MTP traces of a KDA-hybrid model this stall measured ~0.5 ms/step median — the host waits for the previous verify to finish on GPU, zeroing run-ahead. GDN / Mamba2 / ShortConv siblings already declare `False` and run the same base-class metadata code.
2. **Hybrid wrappers drop the verify-buffer hooks.** `HybridLinearAttnBackend` never forwarded `get/update_verify_buffers_to_fill_after_draft`, so every hybrid-linear MTP model takes the `[None, None]` fallback: the draft stage cannot write the tree mask / positions straight into the full-attn child's captured verify buffers and instead allocates a fresh `custom_mask` each step — sized `bs * max_context_len` once the GPU-only seq_lens path nulls `seq_lens_sum`.
3. **An eager end-offset add in verify prep.** `eagle_prepare_for_verify` extends every row by exactly `draft_token_num` tokens, yet materialized `seq_lens + draft_token_num` on the host (a fresh tensor + a dispatch per step) for the generic cache-locs kernel, which then re-derived per-row output offsets with O(bs) cross-row prefix-sum loads.
4. **A 5-7 dispatch replay-prep chain.** `_replay_metadata` refreshed `state_indices_list` via separate aten ops (zero padded `req_pool_indices` rows → mapping gather → v2p translate → `-1` padding sentinel → `copy_` into the static buffer) on every mamba-backend CUDA-graph replay.

**The host seam is a serial chain** — single-point savings do not add up: remove A and the CPU immediately hits B. What ultimately hides the host is the combination plus the overlap scheduling itself, not any single item. The latency payoff therefore lands as a bundle; each fix is nonetheless independently correct and independently revertible.

### Provenance

These items were developed and measured in a bs=1 MTP decode optimization campaign on a KDA-hybrid MoE model (4× B200, TP4, NEXTN speculative decoding), whose end state reached **~90% GPU busy per step** with the host fully hidden behind the GPU — the per-item trace measurements quoted in this PR (the ~0.5 ms/step D2H stall) come from that campaign. This PR upstreams the model-agnostic host-seam subset; every item passed the campaign's correctness gate (byte-exact 256-token greedy output + accept length invariance) before it stayed.

## Modifications

One commit per item, bit-identical by construction (scheduling / fusion only — no numerical path changes):

- **`Opt KDA backend out of the per-step seq_lens_cpu D2H sync`** — `KDAAttnBackend` declares `needs_cpu_seq_lens = False`, matching GDN/Mamba2/ShortConv. Safety: the shared `MambaAttnBackendBase` metadata never reads the spec-v2 CPU mirror for KDA — replay padding always comes from `forward_batch.num_padding`, and the replayssm track-flush mask reads are `not is_kda`-gated. With the full-attn siblings (trtllm_mla / fa3 / flashmla / triton) already `False`, the OR over spec-v2 backends can now stay `False` for KDA hybrids and the per-step stream sync disappears.
- **`Forward verify-buffer hooks through HybridLinearAttnBackend`** — `get` delegates to the full-attn child (the linear side consumes no mask); the draft stage now writes directly into the captured verify buffers and the per-step mask allocation disappears. `update` forwards to both children with an explicit no-op on `MambaAttnBackendBase` (mamba plan-time metadata is draft-output independent); children without an implementation keep the fail-loud `NotImplementedError`, so an unvetted plan-stream combination fails loudly instead of silently reading stale buffers.
- **`Fuse the uniform verify-prep cache-locs end offsets into the kernel`** — new `assign_extend_cache_locs_uniform`: end offset computed in-kernel (`start + draft_token_num`), output offset a direct `pid * draft_token_num`. NPU / CPU fall back to the end_offset-tensor reference path unchanged; the non-uniform call site (`move_accept_tokens`) keeps the reference kernel.
- **`Fuse the mamba replay-prep state-indices chain into one launch`** — `_fused_state_indices_kernel` does the gather + sentinel + store in a single triton launch, preserving the reference chain's side effect of zeroing padded `req_pool_indices` rows (captured kernels gather with that buffer). Gated to CUDA + the static hybrid pool whose v2p translate is the identity + replayssm off; unified-pool / replayssm configs keep the reference chain.
- **`Add bit-exact reference test for _fused_state_indices_kernel`** — see Accuracy Tests.

Compatibility: no API / flag changes; NPU, CPU, unified-memory pool, and replayssm behavior unchanged (explicit gates / fallbacks); plan-stream fail-loud contract preserved.

## Speed Tests and Profiling

These changes remove host-side work whose payoff is latency at low concurrency and compounds with sibling optimizations (serial chain):

- Item 1 removes a measured ~0.5 ms/step median blocking stream sync (bs=1 MTP trace, KDA-hybrid lineage) once a KDA-hybrid spec-v2 config is active; it is inert (flag read only by `decide_needs_cpu_seq_lens`) for all other configs.
- Item 2 removes a per-step `bs * max_context_len` bool-mask allocation for every hybrid-linear MTP model.
- Items 3-4 replace 6-8 per-step host dispatches with 2 kernel launches.

Byte-identical outputs above double as the no-regression evidence. A bundle-level TPOT A/B on Blackwell for the KDA-hybrid MTP target is part of the follow-up series and will be reported there.

This is one part of hybrid-linear model optimazations, with which GPU utils increase from 67% to 95% in MTP.
```

```diff
+"""fused_replay_state_indices must be bit-identical to the unfused prep.
+
+The unfused reference is the exact op sequence ``_replay_metadata`` used to
+launch for the static hybrid pool:
+
+    req_pool_indices[valid_bs:total_bs] = 0        # zero padded rows (side effect)
+    mamba_indices = mapping[req_pool_indices]      # get_mamba_indices gather
+    # identity v2p translate (static pool)
+    mamba_indices[valid_bs:] = -1                  # padding sentinel
+    state_indices[:total_bs].copy_(mamba_indices)
+
+The two paths must agree bit-for-bit, INCLUDING the side effect of zeroing the
+padded rows of the static ``req_pool_indices`` replay buffer — captured kernels
+gather with that buffer, so a non-zeroed padded row is a delayed illegal memory
+access, not a visible diff. Both paths run on guard-padded buffers across a
+bs x num_padding matrix (non-power-of-two sizes exercise the BS_UPPER masking):
+
+1. the produced state indices are identical over the whole ``[0, total_bs)``
+   range (padding sentinel rows included);
+2. the ``req_pool_indices`` buffer ends up identical (padded rows zeroed);
+3. neither buffer is written beyond ``total_bs`` (guard tails stay intact).
+"""
+
+import unittest
+
+import torch
+
+from sglang.kernels.ops.mamba.mamba_state_indices_triton import (

+_GUARD_SENTINEL = -7777

+_OUT_POISON = -12345

+_MAMBA_POOL_SIZE = 4096
+
+
+def _reference_chain(
+    req_pool_indices: torch.Tensor,
+    mapping: torch.Tensor,
+    out_buf: torch.Tensor,
+    valid_bs: int,
+    total_bs: int,

+    """Replicates the _replay_metadata reference ops, in order, in place."""
+    req_pool_indices[valid_bs:total_bs] = 0
+    mamba_indices = mapping[req_pool_indices[:total_bs]]
+    # static pool: _translate_mamba_indices is the identity
+    mamba_indices[valid_bs:] = -1
+    out_buf[: len(mamba_indices)].copy_(mamba_indices)
```
