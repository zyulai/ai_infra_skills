## PR body
```markdown
## Purpose

On ROCm AITER MLA, MTP verification decode (qlen = `num_speculative_tokens + 1`, so 4 for MTP3) was sized as ordinary qlen=1 decode: `get_mla_metadata_info_v1` received `qo_len=1` and the kernel recomputed metadata internally for qlen>1. The verification logits come out wrong, the accept/reject step drifts from the target distribution, and accuracy drops. Passing q/kv dtypes (#46997) does not fix this on its own.

Fix: size the decode metadata from the real MTP qlen and the actual Q/KV dtypes (FP8 Q when the KV cache is FP8). qlen ≤ 4 keeps a native dense layout with persistent per-request causal boundaries; qlen > 4 falls back to qlen=1 split rows; CUDA-graph pad rows get synthesized `seq_lens`/`qo_indptr`.

Scoped to `rocm_aiter_mla.py` (ROCm AITER-only) plus its unit test. The draft-side MTP pieces (local-argmax `get_top_tokens`, `spec_step_idx` threading, attention head-count grouping) are a separate concern and are not in this PR.

## Test Result

- Unit test: 11 passed (CPU, kernels mocked). Covers the qlen policy, native vs split routing, FP8 metadata sizing, CUDA-graph pad synthesis, and the split-path page-index expansion values — `_expand_mtp_decode_page_indices_kernel`'s output is now checked against hand-derived per-row causal indices, not just its launch grid.
- GSM8K (openai/gsm8k test, exact-match, n=200): 0.835 without the fix, 0.970 with it, on current upstream `main` — same build, only the Python differs. Re-run on this branch (MI300X, TP8, MTP3): 0.98 strict-match.
- Without the fix the 3rd MTP position collapses to ~0 acceptance and output degenerates; with it, per-position acceptance stays healthy (≈0.80 / 0.50 / 0.30) and completions are coherent.

Multi-GPU serving accuracy was run manually, not in CI.
