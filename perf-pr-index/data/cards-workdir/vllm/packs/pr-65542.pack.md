## Overview

Part of #65560.

Remove INT8 and FP8 activation support (W4A8) from the dense and MoE Marlin kernels. Marlin becomes a 16-bit-activation kernel, and Humming covers 8-bit activations. Independent of #65540 (Marlin PTX-only build); this PR leaves the fp16/bf16 Marlin arch lists alone.

## Claims

- Removes Marlin's W4A8-INT8 (GPTQ/AWQ INT4) and W4A8-FP8 (GPTQ/AWQ INT4, MXFP4) paths: the sm89 FP8-activation kernels and their SM89/SM12x build targets, the INT8-activation instantiations, the 8-bit paths in both templates, the `marlin_int4_fp8_preprocess` op, `a_scales` on `marlin_gemm`/`moe_wna16_marlin_gemm`, and `is_a_8bit` on the repack ops. Net −2039 lines.
- `VLLM_MARLIN_INPUT_DTYPE` is removed, and setting it raises an error with a migration hint. The replacement is `--quantization humming` with `VLLM_HUMMING_INPUT_QUANT_CONFIG='{"dtype":"int8"}'` (or `float8e4m3`), documented in `docs/features/quantization/README.md`.
- Compressed-tensors W4A8-FP8 checkpoints on SM89/SM12x, which previously fell back to Marlin, now select `HummingLinearKernel`.
- No change for FP8-weight Marlin (W8A16, MXFP8) or any 16-bit-activation format.

I checked that the Humming runs actually quantize activations by reading the loaded layer config: `a_dtype=int8, as_dtype=float32`. Note that `--linear-backend humming` with the same env var does **not** quantize activations for GPTQ/AWQ (`a_dtype=float16`), which is why the docs point to `--quantization humming`. Setting `VLLM_MARLIN_INPUT_DTYPE` now fails at startup with: `ValueError: VLLM_MARLIN_INPUT_DTYPE has been removed. Marlin no longer supports 8-bit activations. Use --quantization humming and set the activation dtype with VLLM_HUMMING_INPUT_QUANT_CONFIG, e.g. '{"dtype":"int8"}'.`

```bash
VLLM_HUMMING_INPUT_QUANT_CONFIG='{"dtype":"int8"}' vllm serve Qwen/Qwen2.5-3B-Instruct-GPTQ-Int4 --quantization humming --max-model-len 8192
python tests/evals/gsm8k/gsm8k_eval.py --port 8000 --num-questions 100
```

## Details

- On main, the Marlin 8-bit path was already narrow. For linear layers it only worked with GPTQ symmetric INT4: AWQ + `VLLM_MARLIN_INPUT_DTYPE=int8` fails at load with "W8A8 is not supported by marlin kernel". FP8-weight + FP8-activation was plumbed in Python but never instantiated.
- Template changes are constant folding of `is_a_8bit == false`, so the 16-bit kernels compile to the same code. The `mma` helpers lose the k=32 path and the `k_size`/`idx` params, and the repack kernels lose their `is_a_8bit` template param.
- `MarlinLinearKernel.can_implement` rejects 1-byte activation types, so selection falls through to Humming. `ConchLinearKernel` now also rejects non-16-bit activations; it had no activation check and sits between Marlin and Humming in the CUDA list.
- `int_wna16` MoE conversion returns 8 entries instead of 10 (the INT8 input global scales are gone). Every in-tree caller is updated.
- Not validated: Humming W4A8 MoE end to end. Marlin MoE W4A8 was only reachable through the removed env var.
- Deprecation: `VLLM_MARLIN_INPUT_DTYPE` is removed without a deprecation cycle. Setting it is now a hard error, raised from `validate_environ` via a new `envs.removed_environment_variables` map, and the message points to `--quantization humming` with `VLLM_HUMMING_INPUT_QUANT_CONFIG`. Without the error, a user who set it would silently fall back to W4A16. Covered in `tests/config/test_config_generation.py::test_unrecognized_env`.

Superseded open PRs that extend Marlin W4A8: #58326, #48926, #38066, #50096, #59895, #61405, #49039, #57091. No open PR removes these paths (searched "VLLM_MARLIN_INPUT_DTYPE", "marlin w4a8", "marlin int8/fp8 activation", "remove marlin").
