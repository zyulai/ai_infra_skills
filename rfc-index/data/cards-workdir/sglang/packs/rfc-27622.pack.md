# Host-Backed Deferred Device KV Allocation for PD Disaggregation

## Summary

This RFC proposes a PD direct-to-host decode KV transfer path for disaggregated serving.

Today, decode-side preallocation reserves device KV cache before the prefill-to-decode KV transfer completes. For agentic long-context workloads with high HiCache hit rates, this can cause many preallocated and in-transfer requests to occupy decode GPU memory before they are ready to run, reducing the device KV capacity available to the active decode batch.

The proposal is to stage transferred KV cache in pinned host memory on the decode node and delay device KV allocation until the request is close to decode execution. The decode node then asynchronously moves KV cache from host to device before admitting the request into the running batch.

This shortens device KV residency for preallocated and in-transfer requests, separates transfer staging capacity from active decode execution capacity, and can improve running batch size under decode-side device KV pressure. The tradeoff is an additional host-to-device staging step, which may increase TTFT in uncongested cases.

## Motivation

Agentic workloads often have very long input contexts and high HiCache hit rates. In this setting, the prefill node can process many concurrent long-input requests and sustain very high input-token throughput. In a PD disaggregated deployment, however, each of these requests still needs decode-side destination KV capacity before the prefill-to-decode KV transfer can complete.

This makes decode-side preallocation scale with prefill input throughput, not just with the number of requests that are actually ready to run decode. Compared with traditional shorter-context workloads, agentic workloads can therefore reserve a much larger amount of decode GPU memory for preallocated and in-transfer requests, squeezing the memory available to the active running batch.

This creates several issues.

### 1. Long Device KV Residency for Preallocated and In-Transfer Requests

A large portion of decode GPU memory can be occupied by requests that have not entered the running batch yet. In agentic long-context workloads, this effect is amplified because high prefill input throughput continuously creates new decode-side preallocation demand. As a result, the active running batch size can stay far below the configured upper bound even when decode compute still has headroom.

#### Example on H20e

Consider an H20e decode node with a device KV pool of about `5M` tokens. For requests with roughly `100K` input tokens, the pool has a nominal capacity of about `50` request-contexts before accounting for output growth, fragmentation, and scheduler constraints.

In production traces, however, requests in this input-length range show that about `33%` of decode-side device KV residency is spent before the request enters the active running batch, including preallocation, transfer in-flight, and post-transfer waiting. In capacity terms, this means that a significant fraction of the `5M` token pool can be occupied by requests that are not yet generating tokens.

With a `33%` pre-running residency share, the effective KV budget available to active decode is:

```text
5M * (1 - 0.33) = 3.35M tokens
```

At `100K` tokens per request, this corresponds to roughly `33` active running requests, instead of the nominal `50` request-contexts. The remaining capacity is not wasted permanently, but it is temporarily held by requests that are still being prepared for decode execution. For long-context workloads with high prefill throughput, this temporary residency can be large enough to keep the running batch well below its configured limit even when decode compute still has headroom.

### 2. Decode-Side Prealloc Queueing Can Increase TTFT Under Device KV Pressure

When decode-side device KV is scarce, requests may wait in the prealloc queue before KV transfer can proceed. In those congested cases, queueing directly increases time-to-first-token. In uncongested cases, direct device transfer may still have lower TTFT because it avoids the extra H2D staging step.

### 3. Transfer Staging Capacity and Active Decode Capacity Become Tightly Coupled

The scheduler must balance memory reserved for preallocated or in-transfer requests against memory available for active decode execution.

If too little memory is available for preallocation, not enough requests can be prepared to keep decode compute busy. If too much memory is occupied by preallocated or in-transfer requests, the running batch cannot grow large enough to saturate the GPU. This makes KV capacity implicitly control compute concurrency.

The core observation is that a request does not need to occupy device KV memory for the entire period between decode-side preallocation and actual decode execution. By staging transferred KV in host memory and allocating device KV only before H2D, we reduce each request's device-memory residency window. This reduces aggregate decode-side device KV pressure and can improve active running batch size for long-context workloads, while trading off an additional host-to-device staging step.

## Proposed Changes

Introduce a new decode-side transfer mode, tentatively called **PD direct-to-host**.

### Current Path

```text
decode prealloc queue
  -> allocate device KV slots
  -> prefill node transfers KV to decode device KV
  -> transfer complete
  -> request enters decode waiting/running batch
```

### Proposed Path

```text
decode prealloc queue
  -> allocate pinned host transit KV slots
  -> prefill node transfers KV to decode host memory
  -> transfer complete
  -> decode node allocates device KV slots
  -> async H2D copy
  -> H2D complete globally across TP ranks
  -> request enters decode waiting/running batch
```

### Main Changes

- Add decode-only `--enable-pd-direct2host` mode.
- Add a pinned host transit KV pool on the decode node.
- Register host KV buffers with the transfer backend when direct-to-host is enabled.
- During decode preallocation, allocate host KV slots instead of device KV slots.
- After prefill transfer completes, allocate device KV only when H2D is ready to start.
- Use a dedicated CUDA stream for host-to-device KV copy.
- Keep requests in the transfer queue until H2D is complete across all TP ranks.
- Free host transit slots after H2D completion.
- Preserve existing fallback behavior when direct-to-host is disabled.

This change does not reduce the final device KV requirement of an active decode request. Instead, it reduces the amount of time a non-running request occupies device KV memory.

## Usage

Example decode-side options:

```bash
--disaggregation-mode decode \
--enable-pd-direct2host \
--pd-direct2host-host-ratio 2.0
```

Optional fixed host pool size:

```bash
--pd-direct2host-host-size <GB>
```

### Expected Constraints

- Decode mode only.
- Mutually exclusive with decode KV cache offload in the initial implementation.
- Mutually exclusive with hierarchical cache in the initial implementation.
- Requires enough pinned host memory on decode nodes.
- Transfer backend must support registering and writing to host buffers.

### Expected Effects

- Reduce decode-side device KV residency for preallocated and in-transfer requests by staging transferred KV in host memory and allocating device KV only before H2D.
- Increase active running batch size for long-context workloads.
- Lower TTFT when decode-side prealloc queueing is the bottleneck, at the cost of an extra H2D staging step in uncongested cases.
- Better separate transfer staging capacity from active decode execution capacity.

## Known Deployment Caveat

In current testing, PD direct-to-host may require setting:

```bash
export NCCL_GRAPH_MIXING_SUPPORT=0
```

The direct-to-host path introduces non-CUDA-graph H2D work on a dedicated stream while normal decode may still use CUDA graph replay. Disabling NCCL graph mixing has been necessary in the current test environment to make graph and non-graph execution coexist reliably.

This is treated as a deployment caveat for the initial implementation, not a settled long-term requirement. We still need to evaluate its impact on correctness, performance, NCCL scheduling behavior, and mixed graph/non-graph production workloads.

## Roadmap

### 1. Prototype Direct-to-Host Transfer Path

Implement host transit KV pools, host buffer registration, decode-side H2D scheduling, and request lifecycle handling.

### 2. Add Metrics and Observability

- Host transit pool usage.
- H2D in-flight request count.
- H2D latency.
- Prealloc queue time.
- Transfer queue time.
- Device KV residency time.

### 3. Evaluate Performance

Benchmark long-context workloads, focusing on:

- Running batch size.
- TTFT.
- ITL.
- Throughput.
- GPU utilization.
- Host memory usage.
- H2D bandwidth overhead.

## Open Questions

- What should the default host transit pool size be: fixed GB, ratio to device KV pool, or dynamically computed from traffic shape?
- How much pinned host memory is acceptable in production deployments, and should the feature degrade gracefully when host memory is insufficient?
- What is the impact of disabling `NCCL_GRAPH_MIXING_SUPPORT`? In current testing, graceful coexistence between CUDA graph and non-CUDA graph execution requires turning this off. We need to evaluate its effect on correctness, performance, NCCL scheduling behavior, and mixed graph/non-graph workloads in production.
