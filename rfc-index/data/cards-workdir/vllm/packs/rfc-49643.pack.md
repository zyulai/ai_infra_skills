## 正文(PRD / 提案全文)

### Motivation.

MoRIIO supports two KV-transfer modes for P/D disaggregation:
- WRITE (producer pushes KV to the decode node): decode runs with FULL CUDA graphs.
- READ (decode pulls KV from the prefill node): decode runs with PIECEWISE CUDA graphs with #48534.

READ is forced to piecewise because it posts per-layer RDMA reads at the start of the decode forward and must block per layer until that layer's KV has landed before running that layer's attention. That barrier (wait_for_layer_load) is a Python wait that runs between attention layers. A FULL CUDA graph captures the whole forward as one replayable graph with no host code in the middle, so on replay the barrier is silently skipped. Attention then races ahead of KV that has not arrived yet, producing garbage decode output that worsens with concurrency. #48534 makes the barrier real (correctness) and sets requires_piecewise_for_cudagraph = True, which downgrades the decode engine to PIECEWISE.

PIECEWISE pays per-op kernel launch overhead on every decode step. We want READ decode to run under full CUDA graphs for best performance, matching WRITE.

A full-CUDA-graph READ-mode pull connector implementation already exists for reference. vLLM's NIXL pull mode is also READ-based (decode pulls KV), yet it runs under full CUDA graphs with no per-layer barrier. It achieves this with an async KV-load gate:
    - get_num_new_matched_tokens returns async = True
    - The request parks in WAITING_FOR_REMOTE_KVS (blocks are allocated but forward not allowed yet)
    - the request is promoted to RUNNING only after the whole KV has landed (per-request done_recving) --> KV READ no longer within forward pass
    - By the time the decode forward runs, all KV is already resident, so the forward needs no mid-graph wait (fully CUDA-graphable)

MoRIIO WRITE already uses exactly this gate on its consumer side (async whole-request completion), which is why WRITE decode is full-graph. READ chose a synchronous contract (async = False, request goes straight to RUNNING, reads consumed within the same forward), and that is what forces the mid-forward barrier and the piecewise downgrade.


### Proposed Change.

Make MoRIIO READ adopt the same async-load gate that MoRIIO WRITE and NIXL PULL mode use.
(1) get_num_new_matched_tokens (READ): return async = True
    - request parks in WAITING_FOR_REMOTE_KVS
(2) Put reads outside of the forward path
    - start_load_kv already runs every step, including the no-forward path (kv_connector_no_forward), so reads for a           parked request get posted without a forward
    - Report per-request completion via get_finished → done_recving (_pop_done_transfers already computes per-request completion but currently discards it on the READ path)
(3) wait_for_layer_load reverts to a no-op.
    - The barrier added in #48534 is no longer needed as the KV is fully present before the decode forward runs
(4) requires_piecewise_for_cudagraph → False for READ, restoring full CUDA graphs.


Tradeoff
- Async-gating trades a one-time latency for a per-step saving: the request waits for the whole KV to land before its first decode step, instead of overlapping reads with the forward. Because start_load_kv posts reads a step ahead and runs every step, request N's reads overlap other requests' decode compute, so at steady-state concurrency the pipeline bubble is largely hidden. WRITE and NIXL already accept this trade, and full CUDA graphs remove per-op launch overhead on every subsequent decode step.


Relationship to #48534
#48534 is the correct fix for the current piecewise design: it makes the barrier real so READ produces correct output today, and explicitly marks READ as requiring piecewise. This RFC proposes the longer-term design in which the barrier becomes unnecessary (KV load gated before forward), enabling full CUDA graphs for READ decode. 

Suggested sequencing: land #48534 first (correctness now), then implement this RFC to recover full-graph performance.
