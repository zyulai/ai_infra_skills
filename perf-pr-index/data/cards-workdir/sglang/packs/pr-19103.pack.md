## Summary

This PR does two separate things:

1. **AOT-to-JIT migration**
   - Move `downcast_fp8`, the fused KV-cache BF16/FP16 to FP8 E4M3 downcast kernel, from the AOT `sgl-kernel` extension into the SGLang JIT kernel framework.
   - This is primarily an integration and build-simplification change.
   - It preserves the original kernel semantics and is not counted as the source of the performance improvement.

2. **JIT-kernel performance optimization**
   - Starting from the migrated **JIT scalar baseline**, optimize the kernel for H200 memory bandwidth.
   - The main optimizations are vectorized memory access, a 2D grid with fixed 256-thread blocks, and `__restrict__` pointer qualifiers.

The key point is that **AOT -> JIT alone does not materially improve performance**. The performance gain comes from the optimizations applied after the JIT baseline.

### Final result on H200

| Metric | JIT Scalar Baseline | Optimized JIT Kernel |
|---|---:|---:|
| Peak effective bandwidth | ~917 GB/s | ~4.2 TB/s |
| Peak H200 nominal-bandwidth utilization | ~19% | ~87% |
| Active-warp threshold ratio, `h=32,d=128` | `0.5 / 3.55 = 0.14x` | `16 / 3.55 = 4.51x` |
| Bytes-adjusted Little's-Law coverage, `h=32,d=128` | `(0.5 * 2 B) / (3.55 * 16 B) = 0.018x` | `(16 * 16 B) / (3.55 * 16 B) = 4.51x` |
| End-to-end latency | baseline | up to 61x lower |
| Additional large-shape gain from `__restrict__` | N/A | up to +17% |

The final kernel moves `downcast_fp8` from a scalar, under-exposed memory kernel into a vectorized, grid-parallel JIT kernel that is close to the practical H200 HBM bandwidth ceiling.

## Scope and Baseline Terminology

To avoid attributing performance gains to the wrong change, this PR uses the following terminology:

| Term | Meaning | Used for Performance Attribution? |
|---|---|---:|
| **Legacy AOT scalar kernel** | The old `sgl-kernel` implementation before this PR. | No. Used as a legacy reference and migration-equivalence check. |
| **JIT scalar baseline** | The direct JIT port before performance optimizations. It keeps the same scalar memory-access pattern and loop-based work assignment. | Yes. This is the performance baseline. |
| **Optimized JIT kernel** | The final JIT kernel after vectorization, 2D-grid parallelism, and `__restrict__`. | Yes. This is the optimized result. |

The AOT-to-JIT migration by itself is treated as performance-neutral. It is valuable because it reduces build complexity and moves this lightweight kernel into the JIT framework, but the interview-relevant performance story starts from the **JIT scalar baseline**.

## Motivation

`downcast_fp8` converts KV-cache tensors from BF16/FP16 to FP8 E4M3. It performs scaling, clamping, and FP8 conversion in a single GPU pass.

The previous implementation lived in the AOT `sgl-kernel` build path. Migrating it to the JIT framework reduces build complexity and aligns with the broader direction of moving lightweight SGLang kernels into JIT.

After migration, profiling showed that the scalar JIT baseline still had the same performance bottlenecks as the old scalar implementation:

```text
1. Low bytes per memory instruction.
2. Low exposed warp-level parallelism.
3. Conservative compiler code generation due to pointer aliasing assumptions.
```

This PR therefore separates the engineering migration from the performance work:

```text
AOT scalar kernel
      |
      |  migration only; no meaningful performance win counted here
      v
JIT scalar baseline
      |
      |  performance optimization starts here
      v
Optimized JIT kernel
```

## Optimization Details

### Stage 1: Vectorized memory access

#### Problem

The JIT scalar baseline performs scalar BF16/FP16 loads and FP8 stores. The accesses are already coalesced at the warp level, so the main issue is not transaction over-fetch. The issue is that each thread moves too little useful data per memory instruction:

```text
scalar load:     2 B/thread
vectorized load: 16 B/thread
```

This causes low bytes per memory instruction and a high dynamic memory-instruction count.

#### Change

Use 128-bit vectorized accesses:

```text
kVecSize = 16 / sizeof(T)
```

For BF16/FP16:

```text
kVecSize = 16 / 2 = 8 elements/thread
```

Each thread loads one vector of K, one vector of V, converts the elements, and stores vectorized FP8 output.

#### Result

<img width="965" height="296" alt="image" src="https://github.com/user-attachments/assets/c20e3e3c-173a-4805-87ce-ab7c98b6d462" />

#### Observations
- Kernel latency reduced by **4.0×–8.8×** across tested shapes
- Peak effective bandwidth increased by **~4.0×** (`917 → 3646 GB/s`), with the full range improving from **15–917 GB/s** to **99–3646 GB/s**
- Gains come from higher bytes/instruction, fewer load/store instructions, and more bytes in flight
- Nsight Compute then showed the next bottleneck: low occupancy (`~0.5 warps/block`), addressed in Stage 2

The kernel is still below the Little's-Law saturation threshold because the launch geometry exposes only `0.5` active warps/token for `h=32,d=128`.

---

### Stage 2: 2D grid over `head * dim`

#### Problem

After vectorization, the remaining bottleneck is low exposed warp-level parallelism.

The scalar/loop-based launch ties block size to `dim / kVecSize`:

```text
block = dim / kVecSize
```

For `dim = 128` and `kVecSize = 8`:

```text
block = 128 / 8 = 16 threads = 0.5 warps/block
```

Although the total work is over `head * dim`, that work is handled by an inner loop rather than being exposed through the CUDA grid.

#### Change

Flatten `head * dim` into a vector space and expose it through `grid.y`:

```cpp
const int num_vecs = head * dim / kVecSize;

dim3 grid(input_num_tokens, ceil_div(num_vecs, 256));
dim3 block(256);
```

For `head = 32`, `dim = 128`, and `kVecSize = 8`:

```text
num_vecs = 32 * 128 / 8 = 512
grid.y   = ceil(512 / 256) = 2
block    = 256 threads = 8 warps
```

So each token exposes:

```text
active warps/token = 2 * 8 = 16
```

#### Result

<img width="1648" height="513" alt="image" src="https://github.com/user-attachments/assets/2f05034c-583a-4cc0-b542-1a1d0be0d09e" />

#### Observations

- Additional **1.4×–6.8×** speedup over the vectorized implementation
- Effective bandwidth reaches approximately **4.2 TB/s**
- Largest gains occur on smaller workloads where low occupancy was the dominant bottleneck
- The optimized launch exposes `head * dim` parallelism directly to the CUDA grid instead of processing it through an inner loop


Together with vectorization, the bytes-adjusted Little's-Law coverage moves from:

```text
0.018x -> 4.51x
```

This is the main reason the kernel moves into a near-HBM-bound regime.

---

### Stage 3: `__restrict__` pointer qualifiers

#### Problem

Once memory width and exposed parallelism are fixed, remaining inefficiencies come from generated code.

Without `__restrict__`, the compiler cannot prove that these pointers reference independent memory regions:

```text
cache_k, cache_v, k_scale, v_scale, output_k, output_v, loc
```

This can lead to redundant reloads of values such as `k_scale[0]` and `v_scale[0]`.

#### Change

Add `__restrict__` to kernel pointer arguments:

```cpp
const T* __restrict__ cache_k,
const T* __restrict__ cache_v,
const float* __restrict__ k_scale,
const float* __restrict__ v_scale,
fp8_e4m3_t* __restrict__ output_k,
fp8_e4m3_t* __restrict__ output_v,
const int64_t* __restrict__ loc
```

#### Result

`__restrict__` does not increase Little's-Law coverage. Instead, it helps the compiler keep invariant scale values in registers and generate better code. The gain is small on tiny latency-bound shapes but reaches up to +17% on large bandwidth-bound shapes.

## Kernel Semantics

The JIT kernel preserves the original `downcast_fp8` semantics:

```text
Input:
  k, v      : [input_num_tokens, head, dim], BF16/FP16
  k_scale  : [1], FP32
  v_scale  : [1], FP32
  loc      : [input_num_tokens], INT64

Output:
  k_out, v_out : [output_num_tokens, head, dim], UINT8 storage for FP8 E4M3
```

For each token and each KV element:

```text
out = cast_to_fp8_e4m3(clamp(input / scale, -FP8_MAX, FP8_MAX))
```

Destination indexing is preserved through:

```text
out_seq_idx = loc[token_idx]
out_offset  = (out_seq_idx * mult + offset) * head * dim
```

The platform-specific FP8 E4M3 clamp range is:

```text
CUDA E4M3:       FP8_MAX = 448.0
ROCm FNUZ:       FP8_MAX = 224.0
ROCm E4M3:       FP8_MAX = 448.0
```

## Benchmark Methodology

The benchmark should make the migration-vs-optimization split explicit:

```text
Legacy AOT scalar kernel    # sanity reference only
JIT scalar baseline         # performance baseline
JIT + vectorized access
JIT + vectorized access + 2D grid
JIT + vectorized access + 2D grid + __restrict__
```

Speedups are reported against the **JIT scalar baseline**, not against the act of migrating from AOT to JIT.

Effective bandwidth uses a first-order K/V traffic model:

```text
BW_eff = bytes_moved / latency
```

For BF16/FP16 input and FP8 output:

```text
bytes_moved ~= 2 * input_num_tokens * head * dim * (sizeof(input_dtype) + sizeof(fp8))
```

Since BF16/FP16 is 2 bytes and FP8 is 1 byte:

```text
bytes_moved ~= 2 * input_num_tokens * head * dim * 3 B
            = 6 * input_num_tokens * head * dim B
```

The leading factor of 2 accounts for K and V. Scale and `loc` reads are small relative to K/V tensor traffic and are ignored in this first-order model.

### Table 3. Little's-Law saturation coverage by optimization stage

This is the key benchmark-side metric for this PR.

Little's Law gives the intuition:

```text
required_bytes_in_flight ~= target_bandwidth * memory_latency
```

For bandwidth-oriented kernels, it is not enough to reduce arithmetic. The kernel must expose enough useful memory work to the memory system. I report two related ratios:

```text
active_warp_threshold_ratio = active_warps_per_token / active_warp_threshold

bytes_adjusted_ll_coverage =
    (active_warps_per_token * bytes_per_thread)
  / (active_warp_threshold * 16 B)
```

For the representative `head = 32, dim = 128` case:

```text
kVecSize = 16 / sizeof(BF16/FP16) = 8
active_warp_threshold ~= 3.55 active warps/token
```

| Variant | Bytes/thread | Active warps/token | Active-warp threshold ratio | Bytes-adjusted LL coverage | Interpretation |
|---|---:|---:|---:|---:|---|
| JIT scalar baseline | 2 B | 0.5 | `0.5 / 3.55 = 0.14x` | `(0.5 * 2) / (3.55 * 16) = 0.018x` | Far below threshold. Both memory width and exposed parallelism are insufficient. |
| JIT + vectorized access | 16 B | 0.5 | `0.5 / 3.55 = 0.14x` | `(0.5 * 16) / (3.55 * 16) = 0.14x` | Memory width is fixed, but launch geometry is still below threshold. |
| JIT + vectorized access + 2D grid | 16 B | 16 | `16 / 3.55 = 4.51x` | `(16 * 16) / (3.55 * 16) = 4.51x` | Crosses the modeled saturation threshold. The kernel can now become HBM-bound. |
| JIT + vectorized access + 2D grid + `__restrict__` | 16 B | 16 | `4.51x` | `4.51x` | Little's-Law coverage is unchanged; improvement comes from compiler code generation. |

Interpretation:

```text
JIT scalar baseline coverage = 0.018x
vectorized-only coverage     = 0.14x
2D-grid coverage             = 4.51x
```

This metric is not a direct speedup predictor. It is a bottleneck classifier:

```text
LL coverage < 1x:
  The kernel likely does not expose enough useful memory work.

LL coverage > 1x and bandwidth utilization is high:
  The kernel is likely near bandwidth-bound.

LL coverage > 1x but bandwidth utilization is still low:
  Look for codegen, instruction mix, register pressure, memory transaction efficiency, or aliasing issues.
```

For this PR, the coverage ratio explains the optimization sequence:

```text
0.018x  -> scalar baseline is far below saturation
0.14x   -> vectorization fixes memory width but not exposed parallelism
4.51x   -> 2D grid crosses the saturation threshold
4.51x   -> __restrict__ does not change MLP; it improves generated code
```

<summary>Appendix A: Detailed Little's-Law Derivation</summary>

## A.1 First-order bandwidth model

For one token, one head, and one dimension element, the kernel reads one K element, reads one V element, writes one K FP8 element, and writes one V FP8 element.

For BF16/FP16 input and FP8 output:

```text
K input read:    2 B
V input read:    2 B
K output write:  1 B
V output write:  1 B
Total:           6 B per element
```

Therefore:

```text
bytes_moved ~= input_num_tokens * head * dim * 6
```

## A.2 Vectorization ratio

Before vectorization:

```text
bytes/thread = sizeof(BF16/FP16) = 2 B
```

After vectorization:

```text
kVecSize = 16 / sizeof(T) = 8
bytes/thread = 8 * 2 B = 16 B
```

Therefore:

```text
bytes/thread ratio = 16 B / 2 B = 8x
```

## A.3 Active-warp ratio for `head = 32, dim = 128`

Before the 2D-grid rewrite:

```text
block = dim / kVecSize
      = 128 / 8
      = 16 threads
      = 0.5 warps
```

After the 2D-grid rewrite:

```text
num_vecs = head * dim / kVecSize
         = 32 * 128 / 8
         = 512

grid.y = ceil(num_vecs / 256)
       = ceil(512 / 256)
       = 2

block = 256 threads = 8 warps
```

Therefore:

```text
active warps/token before = 0.5
active warps/token after  = 2 * 8 = 16
active-warp ratio         = 16 / 0.5 = 32x
```

Using the active-warp threshold from the memory-saturation model:

```text
active_warp_threshold ~= 3.55 active warps/token
```

The threshold ratio changes from:

```text
0.5 / 3.55 = 0.14x
```

to:

```text
16 / 3.55 = 4.51x
```

This isolates the Stage-2 launch-geometry effect.

## A.4 Bytes-adjusted Little's-Law coverage

To include both launch geometry and memory width, use:

```text
bytes_adjusted_ll_coverage =
    (active_warps_per_token * bytes_per_thread)

```

This is a bottleneck-removal metric, not a direct speedup predictor.

exposure_ratio ~= bytes/thread ratio * active-warp ratio
               ~= 8x * 32x
               ~= 256x
```

This explains why the optimized kernel can move from below-threshold execution to a near-HBM-bound regime.

+__global__ void fused_downcast_kernel(

+    const int64_t* __restrict__ loc) {
+  using namespace device;
+
+  constexpr int kVecSize = 16 / sizeof(T);
+  using vec_t = AlignedVector<T, kVecSize>;
+  using out_vec_t = AlignedVector<fp8_e4m3_t, kVecSize>;
+
+  const int token_idx = blockIdx.x;
+  const int vec_idx = blockIdx.y * kBlockSize + threadIdx.x;
+  const int num_vecs = head * dim / kVecSize;

+  T v_scale_inv = static_cast<T>(1.f) / cast<T>(v_scale[0]);

+

+  k_vec.load(in_k_base, vec_idx);
+  v_vec.load(in_v_base, vec_idx);

+def _ref_fp8(x: torch.Tensor, scale: torch.Tensor) -> torch.Tensor:
+    """Reference: replicate kernel precision — scale_inv in dtype T, then to fp8.
+
+    Mirrors the kernel logic:
+      scale_inv = cast<T>(1.0f) / cast<T>(scale[0])
+      out[j]    = cast<fp8_e4m3_t>(clamp(x[j] * scale_inv))

+    dtype = x.dtype
+    scale_inv = x.new_ones(1) / scale[0].to(dtype)
+    x_scaled = (x * scale_inv).clamp(-_FP8_E4M3_MAX, _FP8_E4M3_MAX)
