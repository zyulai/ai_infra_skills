## 正文(PR 描述)

## Motivation

In multi-turn usage, SGLang radix cache currently only reuses the original prompt tokens, but **does not reuse the previous turn’s generated tokens**. This forces unnecessary prefill over already-generated continuation tokens in the next request and significantly hurts multi-turn performance.

### Repro (minimal)

* Round 1: prompt=100 tokens, generated=50 tokens
* Round 2: input=200 tokens (100 prompt + 50 generated + 50 new tokens)

  * **Expected cache hit**: 150 (prompt + generated)
  * **Actual cache hit**: 100 (only prompt)

Example log (before fix):

```
Round 1: Prompt=100, Output=50, Cached=0
Round 2: Input=200, Cached=100  (only prompt) ❌
```

After fix:

```
Round 1: Prompt=100, Output=50, Cached=0
Round 2: Input=200, Cached=150  (prompt + generated) ✅
```

## Modifications

### Root cause

In `sglang/srt/mem_cache/radix_cache.py::cache_finished_req()`:

* `token_ids` is correctly computed as `(req.origin_input_ids + req.output_ids)[:kv_committed_len]`
* However, the code uses `req.fill_ids` as the cache insertion key:

  * `fill_ids` is set at `init_next_round_input()` time (before decode), so it **does not include** `output_ids`
  * As a result, radix cache only stores/matches the prompt prefix, not the generated continuation

### Fix

Use `token_ids` (prompt + output, up to committed KV length) as the insertion key:

```python
keys = convert_to_bigram_key(token_ids) if self.is_eagle else token_ids
```

This keeps the EAGLE bigram-key behavior intact while fixing the non-EAGLE path regression.

## Accuracy Tests

N/A. This change only affects radix cache key selection for KV reuse and does not modify model forward / sampling behavior, so model outputs are unchanged.

## Benchmarking and Profiling

I did not run full end-to-end throughput benchmarks in this PR. However, the repro script shows `cached_tokens` increases from `prompt_only` to `prompt + previous_generation`, which directly reduces the amount of prefill work in multi-turn scenarios.
