## Motivation

For the measured Kimi-K3 TP1/PP8 prefill workload, FlashInfer 0.7.1's 16K-token MoE candidate enumeration exposed token tiles 192 and 256. A supported tile128/config0 tactic, discovered through smaller-shape candidate enumeration and then executed at the real 16K shape, performed better on captured early/late-layer routing.

This ports the tile128 approach to the repository's pinned **FlashInfer 0.7.2**, using its existing cache-loading API. Re-enumeration on B30Z identified **tile128/config4**, and real captured-input replay verified that tactic and the new record. The older 0.7.1/config0 record is not installed or accepted. Tactic IDs are version-specific; no dependency downgrade or version-check bypass is included.

## Modifications

- Seed one serving-derived 16K MoE tuning bucket during startup, before the user's persistent cache is loaded. Explicit user-cache entries retain precedence; disabling cache reuse keeps fresh tuning behavior.
- Restrict loading to Kimi-K3, TP1/PP8/EP1, chunk16K, BF16 model dtype, SM103 and FlashInfer 0.7.2. FlashInfer's full environment metadata check further restricts the bundled record to the measured B30Z/CUDA/library combination.
- The cache key includes both activation/weight formats, local/global expert counts, top-k, hidden/intermediate dimensions, activation and weight layout, plus the unpacked routing representation.
- Fix the existing target/draft CUDA cache-phase fixture to supply the runner field read by the startup guard.
- Use the existing `load_configs` mechanism; do not replace `AutoTuner.choose_one`, add a process-wide monkey patch, or add a new configuration switch.

The record follows FlashInfer's tuning-bucket semantics. It is not a universal tile128 policy for arbitrary sequence lengths, models, hardware, EP or decode workloads. Existing explicit cache choices can override it.

## Accuracy Tests

- **2 unit tests passed**, with subcases rejecting other model types, parallelism, chunk sizes, dtypes, hardware and unvalidated FlashInfer 0.7.1/0.7.3.
- On B300/B30Z, loaded this branch's record with the real FlashInfer 0.7.2 `AutoTuner`, then replayed captured Kimi-K3 input `[16384, 3584]`, original expert weights, scales and top-k routing. The real operation selected **(128, 4)** and output was **bitwise equal** to the captured service reference.
- Loaded an explicit user record afterwards: the same real operation selected **(192, 4)**, confirming user-cache precedence; output again matched the reference bitwise.
- Ruff, isort, AST/JSON parsing, registered-test lint, and `git diff --check` passed.

The 0.7.2 Python wheel and its matching NVIDIA kernels were tested in an isolated overlay, retaining version checks; the installed 0.7.1 package was not modified. These verify the policy, public cache adapter and actual MoE operation.

Full-model serving validation now passes for these production changes on the common upstream `main` base `592754fc5e`, with FlashInfer 0.7.2; the standalone and repeated combined results are reported below. The current six full-service runs each pass 12 fixed greedy output checks covering input lengths 1,024 / 16,383 / 16,384 / 16,385 / 32,768 / 65,536, each repeated twice. All 60 comparisons against A1 match output token IDs and input SHA256 hashes. An additional eight C4 concurrent fixed-input checks match between A2 and B2. These are finite output-regression checks, not logits-level equality or a full task-accuracy benchmark.
