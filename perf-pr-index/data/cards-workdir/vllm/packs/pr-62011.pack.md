```markdown
## Purpose

`attention_config.indexer_sparse_logits` (#56254) lets DeepSeek-V4.1's candidate-consuming indexer layers score only the candidate blocks with DeepGEMM's sparse MQA-logits kernels instead of dense logits over the whole context. Today it requires the MXFP4 indexer cache (`indexer_kv_dtype="mxfp4"`), so with the default FP8 cache the flag fails at startup:

```
ValueError: attention_config.indexer_sparse_logits requires the MXFP4 indexer cache
```

The restriction dates from before #61149: the FP8 cache then stored one fp32 scale per token, while the sparse kernels take UE8M0-packed (granularity-32) scales. Since #61149, the SM100 FP8 indexer cache stores each token's power-of-two scale as four equal UE8M0 bytes, which is exactly the MXFP8 layout DeepGEMM expects, and DeepGEMM's sparse kernels already have an FP8 (`float_e4m3_t`, `SM100_MMA_MXF8F6F4_SS`) variant for both the contiguous (prefill) and paged (decode) paths. Its paged accessor reads the same page layout as vLLM's FP8 cache (`PAGE_KV x 128` value bytes, then `PAGE_KV` uint32 scales).

This PR wires the FP8 cache into the existing sparse path, so the decode speedup no longer requires trading the K cache down to 4 bits.

## Results

DeepSeek-V4.1-Flash, TP4, 4x B300, `--kv-cache-dtype fp8 --no-enable-prefix-caching`, greedy decoding. Decode and prefill throughput from a linear fit of wall time against output length (256 / 1024 / 2048 output tokens), each point run twice
```
