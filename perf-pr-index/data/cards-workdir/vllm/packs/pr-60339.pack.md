## Overview

`method="suffix"` today needs Arctic Inference, runs on the CPU, forces Model Runner V1 and disables async scheduling. With this PR it runs on Model Runner V2 with a GPU speculator, with async scheduling and without Arctic; V1 keeps using Arctic. This is the "suffix" item in #47172. The speculator builds on `ngram_gpu` (#40704) and borrows from #52097 (thanks @zip95297). Related fix on main: #61509 (adaptive verification's startup profiling was counted as CUDA graph memory). @njhill rebased this onto the speculator config refactor and simplified it: seeded requests are no longer special-cased, and the runner hooks are `BaseSpeculator` methods.

## Claims

- `method="suffix"` runs on Model Runner V2: GPU-resident, no host sync on the propose path, async scheduling, no Arctic dependency. V1 is unchanged except for the default `num_speculative_tokens` (below).
- Acceptance is on par with Arctic: 1.937 tokens per step vs Arctic's 1.923 (k=8) and 1.948 (k=24) on a 21K-request replay.
- With adaptive verification, throughput matches or beats Arctic on V1 at every concurrency for Qwen2.5-7B (offline and online serving) and for Qwen2.5-1.5B from concurrency 64 up; at 1.5B concurrency 8 and 32 Arctic is ahead (below). Without adaptive verification, verifying every slot loses from concurrency 32 up, as with `ngram_gpu`.
- GSM8K accuracy matches no speculation.
- `num_speculative_tokens` now defaults to 8 for suffix decoding (was `suffix_decoding_max_tree_depth`, 24), because V2 verifies every slot.

## Details

**How it works**
- **Own history:** the longest suffix match within the request's prompt and output, up to `suffix_decoding_max_tree_depth`. Same kernel layout as `ngram_gpu`.
- **Cross-request corpus:** finished responses go into a GPU token ring (`suffix_decoding_corpus_tokens`, default 1M). A hash index on each request's last 2 and last 4 tokens returns up to 16 candidate positions. Each is verified and extended to its full suffix match, so the index is only an entry point for suffix matching, and hash collisions or overwritten documents only cost a candidate.
- **Frequency vote:** for each candidate match length, the candidates matching at least that long vote on the continuation, as in SuffixDecoding. The highest-scoring chain wins, ties going to the longer match; then the longer of the own-history and corpus matches wins.
- **Adaptive verification** (`enable_adaptive_verification`): per-slot confidences, learned online by source, match length and position, let the runner trim slots that aren't worth verifying.
- **Ingestion:** one GPU program per (document, block). Each program replays the batch's placement to find its offset and skips positions that a later document of the same batch overwrites. Every position is written by exactly one program, so the result is exact and order-independent even when a burst is larger than the ring. A 256 × 4,096-token burst at the default 1M ring takes 0.58 ms.
- **TP consistency without collectives:** finished ids are ingested in sorted order, index inserts use `atomic_max` over `(document << 32 | position)`, and the statistics are integer counters.
- **Memory at the defaults:** 36 MB (4 MB corpus plus a 32 MB index). Suffix decoding also keeps the runner's token history on the GPU (`max_num_seqs × max_model_len × 4` bytes, e.g. 32 MiB at 256 × 32K).

<summary><b><ins>How a corpus lookup works (diagram)</ins></b></summary>

```
Request history:  ... "report" "the" "camera" "at" "the" "north" "gate"
                                          └──── last 4 ────┘
                                                       └─ last 2 ┘

1) LOOK UP          hash(last 4), hash(last 2) -> buckets, 8 slots each
                    (slot = newest occurrence in each of the last 8 documents)

2) EXTEND BACKWARDS each candidate against the request (up to 24 tokens):
   request:   report the camera at the north gate
   corpus:    log:   the camera at the north gate     -> match length 6
   stale or colliding candidate -> length 0, dropped

3) VOTE + DRAFT     candidates matching >= L tokens vote on the next k tokens;
                    the chain with the highest summed probability wins

4) COMPARE          with the longest match in the request's own history;
                    the longer match wins, empty slots get the last token
```

Ingestion when a request finishes: `[last 3 prompt tokens | response]` is appended to the ring, and each position with at least 2 (4) tokens before it in the document is indexed under them: `table[hash][doc % 8] = max(existing, (doc, pos))`.

**Why a hash index**

| Index | Propose cost (L4) | Notes |
|---|---|---|
| Suffix tree (Arctic, V1) | CPU, per request | Host sync, so no MRV2 or async scheduling |
| Suffix array (#52097) | 1.3–4.5 ms as an eager library call (prototype measurement on a shared L4); #52097 reports 0.4–1.9 ms with its CUDA-graph path (L20, k=16) | Background rebuilds, epochs and a CPU collective for TP |
| Brute-force GPU scan | 0.3–1.2 ms at batch 128 (prototype measurement) | Exact; cost grows with batch × corpus |
| **Hash index + vote (this PR)** | **11–35 µs** GPU time for batch 1–256 (CUDA-graph microbenchmark), the same at 1M and 4M corpus tokens. As the engine runs it (eagerly): 89–95 µs per step at 4K context for batch 1–256, 231 µs at 128K context with 32 requests (`ngram_gpu`: 75–78 and 111 µs) | No rebuilds. The index alone is within 0.4% of an exact longest-match search; with the vote, about 1% below exact search + vote |

One difference from Arctic: corpus matches need at least 2 tokens (so `suffix_decoding_max_tree_depth` must be at least 2 for the corpus), while own-history matches can be 1. Storing the last 3 prompt tokens with each response lets a response's first tokens be drafted from the corpus.

**Taken from #52097 and @zip95297's MRV2 port** (`zip95297/vllm-dev`, branch `zip95297/suffix-gpu-mrv2`): GPU cross-request matching with no host sync; an `on_requests_finished` hook in `finish_requests` that ingests from `RequestState` and skips preempted requests (from the MRV2 port); sorting finished ids for TP consistency; the replay-based acceptance evaluation.

**Changes outside the speculator**
- `SuffixSpeculatorConfig` (`suffix/config.py`): suffix's default `num_speculative_tokens` is `min(8, suffix_decoding_max_tree_depth)` on both runners. On V1 it caps Arctic's dynamic draft length; set 24 for the previous V1 behavior.
- `BaseSpeculator`: new no-op `add_request`, `on_requests_finished` and `reset_state` methods, which the runner and MRV2's kernel warmup call directly. The suffix speculator uses them to reset per-slot stats, ingest finished requests, and drop the warmup requests from the corpus. Dense `all_token_ids` for suffix.

**Limitations**
- Seeded sampling isn't reproducible with suffix decoding: drafts come from previously finished requests, and with adaptive verification the number of verified slots depends on the batch. The same seeded request sent alone twice gave identical output 0/4 (fp32; 4/4 without speculation). With `suffix_decoding_corpus_tokens: 0` and adaptive verification off it's 4/4.
- The corpus is shared across requests regardless of `cache_salt` or LoRA adapter, like Arctic's global tree on V1 (documented; set `suffix_decoding_corpus_tokens: 0` to isolate).
- Adaptive verification needs full CUDA graphs and an attention backend that replays variable-length decode batches. On L4 that is `TRITON_ATTN`: vLLM's FA2 backend declares uniform-batch support only. Until #61509 lands, its startup profiling also costs KV capacity, which matters at long context.
- Under async scheduling a finished request can carry up to about 2k+1 tokens past the stop point into the corpus.

## Open questions

1. **Adaptive verification by default?** It is what makes suffix decoding pay off from concurrency 32 up. It isn't on by default here because it fails at startup on backends that can't replay variable-length decode graphs (FA2, the pre-Hopper default), so a default needs a fallback to off. Happy to add that here, or in a follow-up.
2. **Low-concurrency trimming.** Adaptive verification trims too much at low concurrency on small models: Qwen2.5-1.5B at concurrency 8 is 1.29x with it vs 1.47x verifying every slot (7B: 1.36x vs 1.32x). Tune it here (for example with a more optimistic prior) or later?
3. **Corpus default.** 4M tokens adds about 2–3% acceptance, but the index grows from 32 MB to 128 MB.
4. **Tokens past the stop point.** Pass the scheduler's final length down to ingestion?
5. **Arctic-only options** (`max_spec_factor`, `min_token_prob`) are ignored on V2 (documented). Warn as well?

+
+On Model Runner V2, `method: "suffix"` runs on the GPU, works with async scheduling and does not need Arctic Inference. It builds on [`ngram_gpu`](n_gram.md):

+def _local_draft(hist, k, depth):
+    """Continuation of the longest, rightmost earlier occurrence of a suffix
+    of ``hist`` within ``hist`` (empty if no token matches)."""
+    best_len, best_pos = 0, 0
+    for i in range(1, len(hist)):
+        m = 0
+        while m < depth and i - 1 - m >= 0 and hist[i - 1 - m] == hist[-1 - m]:
+            m += 1
+        if m > 0 and (m, i) >= (best_len, best_pos):
+            best_len, best_pos = m, i
+    return [int(t) for t in hist[best_pos : best_pos + k]] if best_len else []
+

+def _follows_in_corpus(docs, hist, draft, n=2):
+    """Draft continues some occurrence of hist's last n tokens in a doc."""
+    tail = [int(t) for t in hist[-n:]]
+    for doc in docs:
+        for i in range(n, len(doc)):
+            if doc[i - n : i] == tail and doc[i : i + len(draft)] == draft:
+                return True
+    return False

+    spec = SimpleNamespace(

+def _propose(spec, req_states, slots, num_sampled=None, num_rejected=None):
+    n = len(slots)
+    max_reqs = req_states.total_len.gpu.shape[0]
+    last_sampled = torch.zeros(max_reqs, 1, dtype=torch.int64, device=DEVICE)
+    for s in slots:
+        last = int(req_states.total_len.gpu[s]) - 1
+        last_sampled[s, 0] = req_states.all_token_ids.gpu[s, last]
+    batch = SimpleNamespace(
+        num_reqs=n,
+        idx_mapping=torch.tensor(slots, dtype=torch.int32, device=DEVICE),
+        idx_mapping_np=np.array(slots),
+    )

+    if num_rejected is None:

+        None,
+        None,
+        None,
+        None,

+        torch.tensor(num_rejected, dtype=torch.int32, device=DEVICE),
+        last_sampled,
+        None,
+        None,
+        None,
+    )
+    return drafts.cpu().numpy(), spec.num_valid[:n].cpu().numpy()

+_HASH_MUL = 0x9E3779B97F4A7C15 - (1 << 64)

+def _s64(x):
+    x &= (1 << 64) - 1
+    return x - (1 << 64) if x >> 63 else x

+def _ref_ingest(state, docs, cap, num_buckets, slots=8):
+    """Python model of ingestion: documents placed one after another, wrapping
+    to 0 when they don't fit, each position indexed by its 2 and 4 tokens."""
+    corpus, table = state["corpus"], state["table"]
+    for doc in docs:
+        doc = doc[-(cap - 1) :]
+        n = len(doc)
+        if state["head"] + n + 1 > cap:
+            state["head"] = 0
+        head, seq = state["head"], state["doc_seq"]
+        for j in range(n):
+            corpus[head + j] = doc[j]
+            hv = 0
+            for d in range(4):
+                t = doc[j - 1 - d] if j - 1 - d >= 0 else 0
+                hv = _s64((hv ^ t) * _HASH_MUL)
+                b = ((hv >> 29) ^ hv) & (num_buckets - 1)
+                if (d == 1 and j >= 2) or (d == 3 and j >= 4):
+                    t_idx = (1 if d == 1 else 0, b, seq % slots)
+                    table[t_idx] = max(table[t_idx], (seq << 32) | (head + j))
+        corpus[head + n] = -1
+        state["head"] = head + n + 1
+        state["doc_seq"] = seq + 1
+
