## Motivation

<!-- Describe the purpose and goals of this pull request. -->

This PR fine-tuned the channelwise FP8 GEMM tile table on SM120 (RTX PRO 5000), sweeping `BLOCK_M × BLOCK_N × BLOCK_K × num_warps × num_stages` per weight shape and per M bucket; that lifts MiniCPM5-2.6B decode throughput to the level of the latest vLLM version.

| output tok/s (ITL) | c=1 | c=8 | c=32 |
|---|---:|---:|---:|
| vLLM 0.33 | 218 (4.53 ms) | 1574 (4.81) | 3928 (7.32) |
| SGLang, channelwise CUTLASS baseline (this PR off) | 138 (7.19) | 968 (7.92) | 2851 (9.76) |
| **SGLang, tuned channelwise tiles (this PR on)** | **229.9 (4.30)** | **1467.3 (5.10)** | **3644.7 (7.32)** |

Here's a summary of our experimental results:

- **Kernel level**, over the five weight shapes the tables carry, M = 1 to 4096: 74 of the 123 M buckets ship a tuned tile and run **1.03×–2.81× faster** than the SM120 dispatch; the other 49 keep CUTLASS.
- **End to end** on MiniCPM5-2.6B, same binary and flags, tables absent vs present: output throughput **+66.5% / +52.2% / +28.0%** at concurrency 1 / 8 / 32, ITL **−40.2% / −36.0% / −25.0%**, TTFT unchanged (prefill does not use these shapes).
- **Relative to the per-tensor SM120 route merged in #38006**, which closes the same SM120 gap for checkpoints that carry per-tensor scales: on our channelwise checkpoint the tuned tile is **1.02×–1.95× faster** in each of the 74 buckets it ships(same weights, inputs and harness), and it keeps the per-token dynamic activation scales the checkpoint ships instead of a calibrated static one. Nothing here touches that route: per-tensor weights still take `torch._scaled_mm` unchanged and never consult these tables.

## Modifications

<!-- Detail the changes made in this pull request. -->
We close that gap **by tuning, not by adding kernels**: one table per weight shape, fine-tuned offline for this GPU, riding the mechanism that is already merged for L40S (#34331) — a device-named JSON per `(N, K)`, nearest-M lookup, `null` where CUTLASS wins. The tables are keyed on `device_name=NVIDIA_RTX_PRO_5000_72GB_Blackwell`, so any other GPU returns `None` and keeps its own dispatch. No dispatch, kernel, model or launcher code is touched.

## End-to-end serving

**MiniCPM5-2.6B** (42 layers, hidden 2048, intermediate 6144, vocab 130560), `compressed-tensors` FP8 channelwise checkpoint (per-channel weights, per-token dynamic activations), served by `sglang.launch_server --quantization compressed-tensors` on RTX PRO 5000. One wave per cell, 1500-token input and exactly 500 output tokens (`ignore_eos`), 5 repeats, server restarted between arms. Same binary, same server args; the tables are absent in the baseline arm and present in the tuned arm. The bf16 arm in the accuracy section is the same checkpoint before quantization.

| concurrency | output tok/s orig SGLang → tuned | delta | ITL orig SGLang  → tuned | delta | TTFT orig SGLang  → tuned |
|---:|---:|---:|---:|---:|---:|
| 1 | 138.2 → 230.0 | **+66.5%** | 7.19 → 4.30 ms | **−40.2%** | 33.2 → 29.9 ms |
| 8 | 968.4 → 1473.5 | **+52.2%** | 7.92 → 5.07 ms | **−36.0%** | 150.7 → 150.6 ms |
| 32 | 2849.3 → 3648.1 | **+28.0%** | 9.76 → 7.32 ms | **−25.0%** | 384.3 → 382.5 ms |

Spread within a cell is under 1%; an A/B/A re-run of the dispatch arm after the tuned arm lands within 0.02% of its first measurement at c=32, so the deltas are not drift. TTFT is unchanged — prefill does not use these shapes — which is the
expected shape of a decode-only win. The server log confirms the tables were found: `grep -c "channelwise FP8 GEMM"` → 0 for the dispatch arm, 5 for the tuned arm.

## Relationship to the per-tensor SM120 path (#38006)

#38006 routes FP8 linear layers on SM120 to a **per-tensor** path: the per-channel weights are requantized to one scale per tensor at load time and the GEMM goes to `torch._scaled_mm` (cuBLASLt / nvjet) instead of the channelwise CUTLASS
GemmUniversal. That measurement reproduces here — against the untuned dispatch the per-tensor route is 1.4×–2.1× faster in the decode range — so both changes go after the same SM120 gap from different starting points: #38006 changes the weight precision so the GEMM can use the nvjet path, this PR keeps the checkpoint's per-channel scales and sizes the tile instead. They serve different checkpoints rather than competing, and which one applies is decided by the weight-scale shape, not by a flag. Measured on the same weights, the same activations and the same harness:

| shape (N, K) | per-tensor vs dispatch | tuned vs per-tensor, buckets with a tile | rel RMS, channelwise | rel RMS, per-tensor |
|---|---|---|---|---|
| 2560 × 2048 | 1.65× best (M=64) / 0.55× worst (M=512) | 1.29×–1.64× | 0.0264 | 0.0377 |
| 2048 × 2048 | 1.96× best (M=64) / 0.57× worst (M=640) | 1.23×–1.74× | 0.0267 | 0.0375 |
| 2048 × 6144 | 2.10× best (M=1) / 0.53× worst (M=640) | 1.26×–1.53× | 0.0265 | 0.0373 |
| 12288 × 2048 | 1.40× best (M=8) / 0.72× worst (M=1024) | 1.04×–1.87× | 0.0265 | 0.0375 |
| 130560 × 2048 | 1.21× best (M=48) / 0.67× worst (M=320) | 1.02×–1.95× | 0.0264 | 0.0376 |

For a checkpoint that is already per-tensor, #38006 is the route to take and these tables are simply not consulted. For one that ships per-channel scales — like the model measured here — three differences decide it:

* **Speed.** A tuned channelwise tile is 1.02×–1.95× faster than the per-tensor route in each of the 74 buckets it ships, so there is nothing to gain by requantizing this checkpoint. In the 49 buckets left on CUTLASS the per-tensor route is slower in 40 (by 0.7%–90%) and 1.1%–2.9% faster in the other five (all on the 130560×2048 shape, at M=64/80/96/128 and M=1024, where a 267 MB weight does not fit in L2 and no tile covers those lookup cells), so on a channelwise checkpoint neither route gains much there.
* **Accuracy.** Requantizing per-channel weights to a single scale each moves the error against an FP32 GEMM of the same inputs from 0.0265 to 0.0375 relative RMS, because a per-tensor scale has to cover the widest channel. That is the intended trade of the per-tensor design; for a checkpoint that already has per-channel scales, sizing the tile reaches the same speed without paying it.
* **Deployment.** The per-tensor route needs a calibrated static activation scale; keeping per-channel weights also keeps the per-token dynamic activation scales the checkpoint ships. Going channelwise → per-tensor is possible, not the reverse, which is why this PR adds the channelwise side of the SM120 problem instead of moving checkpoints over.

+"""Tests for the tuned per-token x per-channel (channelwise) FP8 GEMM tables.
+
+The JSON files under ``sglang/kernels/ops/gemm/configs`` are pure data consumed
+by ``get_w8a8_channelwise_fp8_config()``; there is no code path that validates
+them. A malformed table either silently disables tuning (wrong filename) or
+hands ``triton_scaled_mm`` a tile it cannot run, so the tests below cover:
+
+* table shape: filename matches N/K, every bucket has the expected keys and
+  values that the kernel accepts;
+* lookup semantics: nearest-M snapping, and a ``null`` bucket keeps its own M
+  point instead of being skipped in favour of a neighbouring bucket;
+* numeric validity: a tuned tile reproduces the exact dequantized FP32 result.
+"""

+import os
+import re
+import sys
+from unittest import mock

+    os.path.dirname(os.path.abspath(fp8_kernel.__file__)), "configs"

+@pytest.mark.parametrize("N,K", _RTX_SHAPES, ids=[f"N{n}K{k}" for n, k in _RTX_SHAPES])
+def test_tuned_tile_matches_fp32_reference(rtx_pro_5000, N, K):
+    """Each table's smallest bucket reproduces the exact dequantized product."""
+    if not torch.cuda.is_available():
+        pytest.skip("requires CUDA")
+    if torch.cuda.get_device_capability() < (8, 9):
+        pytest.skip("FP8 GEMM requires SM89+")

+    configs = fp8_kernel.get_w8a8_channelwise_fp8_configs(N=N, K=K)
+    M = min(m for m, entry in configs.items() if entry is not None)
+    entry = configs[M]
+
+    device = "cuda"
+    a = torch.randn((M, K), dtype=torch.float16, device=device).mul_(0.2)
+    w = torch.randn((K, N), dtype=torch.float16, device=device).mul_(0.2)
+    scale_a = a.abs().amax(dim=1, keepdim=True).float()
+    scale_b = w.abs().amax(dim=0, keepdim=True).float().T
+    scale_a = scale_a.div_(448.0).clamp_min_(1e-6)
+    scale_b = scale_b.div_(448.0).clamp_min_(1e-6)
+    qa = (a / scale_a).to(torch.float8_e4m3fn)
+    qw = (w.float() / scale_b.T).to(torch.float8_e4m3fn)
+

+        num_stages=entry["num_stages"],
