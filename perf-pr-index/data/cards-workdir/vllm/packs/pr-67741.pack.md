## Overview

Use FlashInfer's `gvr_2` top-k for the Qwen4Exp QSA indexer on SM100-family GPUs, for decode and prefill: **1.3–2.3×** faster top-k for long-context decode and **1.1–2.5×** for prefill chunks of 256+ tokens (GB300 kernel time), and **+2.4% output throughput** end to end at 128k input. AI assistance (Claude Code) was used.

## Claims

- On SM100, QSA top-k uses `gvr_2` wherever it can run (k ∈ {512, 1024, 2048}, logits width a multiple of 4); everything else keeps the cooperative/persistent chain, unchanged.
- QSA honors `kernel_config.sparse_indexer_topk_backend`: `auto` prefers `gvr_2`, `flashinfer_gvr2` forces it, `cooperative` restores the previous chain, `persistent` forces persistent for decode.
- Startup warmup compiles every `gvr_2` shape serving can hit and the prefill `row_starts` buffer is allocated at model init, so neither CUDA-graph capture nor serving compiles or allocates.

## Details

**Decode/prefill kernels.** Decode uses `gvr_2`'s varlen kernel, which compiles per exact logits width; QSA's decode width is fixed (full block-table width). Prefill chunk widths vary, so prefill uses the windowed kernel, which compiles per power-of-two width bucket, with an all-zero `row_starts` (every QSA window starts at column 0).

**No row threshold.** Decode runs in CUDA graphs, so dispatch sees the row count but not context lengths. Below ~150 rows, `gvr_2` costs 1–2 µs per call on short contexts but saves 4–7 µs on long ones, so `auto` always prefers it. `sparse_indexer_topk_backend=cooperative` restores the previous behavior.

**Limitations.**
- `gvr_2` latency depends on the score distribution; the kernel numbers use random q/K.
- Warmup adds up to ~24 s to startup.
- Only measured on GB300; B200 is covered by CI correctness tests only.
