## 正文(PR 描述)

## Purpose

It appears some changes to the config parsing for Mistral Large 3 degraded accuracy. These changes try to remediate.

### Root cause

Mistral-Large-3 ships a Mistral-format `params.json` with

```json
"yarn": {"factor": 36, "beta": 32, "alpha": 1, "original_max_position_embeddings": 8192, "apply_scale": false},
"llama_4_scaling": {"beta": 0.1, "original_max_position_embeddings": 8192}
```

i.e. YaRN frequency interpolation **without** YaRN's magnitude correction (mscale), plus
llama4-style position-dependent attention scaling. vLLM serves it as
`MistralLarge3ForCausalLM`, a subclass of `DeepseekV3ForCausalLM`, so the DeepSeek
attention code runs on a config synthesized by the Mistral adapter
(`vllm/transformers_utils/configs/mistral.py`).

Commit `c191787a68`, "[Bugfix] Align vLLM YaRN with Transformers and stop re-scaling
max_model_len" (#56446, merged 2026-09-11).

Mistral-Large-3 is the only model that both goes through the Mistral remap and asks for
YaRN without magnitude scaling, which is why nothing else moved. Verified by loading the
checkpoint's config through `get_config(..., config_format="mistral")`: on `main` the
resulting `rope_parameters` has `attention_factor: 1.0` and no `apply_yarn_scaling`.

## Test Plan

Start server with `vllm serve` and evaluate on GSM8K.

Identical for both arms (TP1 / DP4 / EP4, default MoE backend, which resolves to
FlashInfer TRTLLM for this checkpoint):

```bash
vllm serve \
    /models/Mistral-Large-3-675B-Instruct-2512-NVFP4 \
    --tensor-parallel-size 1 --data-parallel-size 4 --enable-expert-parallel \
    --moe-backend auto --tokenizer-mode mistral --language-model-only \
    --max-model-len 5120 --max-num-seqs 128 --max-num-batched-tokens 16384 \
    --gpu-memory-utilization 0.95 \
    --no-enable-prefix-caching --no-enable-flashinfer-autotune --seed 42 --port 8000
```

Testing is done using the gsm8k eval, launched with the helper script: `tests/evals/gsm8k/gsm8k_eval.py` from the vLLM checkout against the running server, five
times back to back per arm (only `--save-results` changes between passes, we ran multiple times to reduce variance):

```bash
python /workspace/vllm/tests/evals/gsm8k/gsm8k_eval.py \
    --host http://127.0.0.1 --port 8000 \
    --num-questions 1319 --num-shots 5 --max-tokens 256 \
    --temperature 0 --seed 42 --max-concurrency 128 \
    --save-results gsm8k-rep<N>.json
```

## Test Result

(accuracy, %)

| arm | pass 1 | pass 2 | pass 3 | pass 4 | pass 5 | mean | sd |
|---|---|---|---|---|---|---|---|
| `main-no-fix` (`4c6c1a40b3`) | 87.41 | 87.72 | 87.49 | 87.87 | 89.76 | 88.05 | 0.97 |
| `fix` (`265b1c54e3`) | 92.49 | 92.72 | 92.95 | 92.80 | 92.19 | 92.63 | 0.30 |

Difference: **+4.58 points** for the fix (about 60 more correct answers per pass of 1,319).
Welch t = 10.1 on 5 vs 5 passes; the per-pass binomial noise floor at this accuracy is
0.81 points. Invalid-answer rate was 0.00% in every pass except one fix pass at 0.08%
(one question). The fixed arm matches the 92.2 / 92.8% measured on 2026-09-10, before
#56446 was merged.
