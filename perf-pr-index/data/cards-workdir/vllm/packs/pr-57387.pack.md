## Purpose

Transformers ships `glm5_next` as of **v5.16.1** and `qwen4_exp` as of **v5.16.0**, so the vendored copies can go. Raises the `transformers` floor in `requirements/common.txt` from `>= 5.10.4` to `>= 5.16.1` — CI already pins `transformers==5.16.1` exactly in `requirements/test/{cuda,rocm,xpu}.in`, so this only makes the declared minimum match what is already tested.

Removed:

- `vllm/transformers_utils/configs/glm5_next.py` (420 lines)
- `vllm/transformers_utils/processors/glm5next.py` (953 lines)
- `vllm/transformers_utils/configs/qwen4_exp.py`
- `vllm/models/qwen4_exp/config.py`

Net **-1961 lines**.

### Not a straight deletion

The upstream classes are not drop-in replacements, so the model code moves to their spellings:

| vLLM read | upstream ships |
|---|---|
| `mla_nope` | `mla_use_nope` |
| `num_experts_per_token` | `num_experts_per_tok` |
| `moe_renormalize` | `norm_topk_prob` |
| `mhc_num_residual_streams` | `hc_mult` |
| `mhc_sinkhorn_iterations` | `hc_sinkhorn_iters` |

`is_moe` / `is_kda_layer` / `is_linear_attn` now derive from `layer_types`, and text-level reads go through `hf_text_config` now that the top-level config no longer mirrors its `text_config` via `__getattribute__`.

I verified the rename table by loading the real `zai-org/GLM-5.3-Flash` `config.json` through upstream's `Glm5NextConfig` and diffing the resolved attribute surface against every attribute the model tree reads.

### Behaviour deliberately preserved

Three things in the vendored code were intentional divergences, not schema, and are kept with their explanations:

1. **Vision `rms_norm_eps` stays 1e-6.** The checkpoint ships 1e-5 and upstream honours it; the vendored config force-overrode it because 1e-5 "produces repetitive/degraded image descriptions". Now a named constant at its single call site.
2. **The frame sampler moves to `Glm5NextVideoBackend._sample_frame_indices`**, its only consumer, rather than being replaced by upstream's `sample_frames`. See the open question below — this one is worth a second look.
3. **The `NotImplementedError` guards** for config options this implementation lacks move into `_validate_supported_config`, called from `Glm5NextModel.__init__`.

Three GLM-5.3 values have no source in either the checkpoint or the upstream config, so they become named constants rather than silently-missing attributes: `mhc_tau` (0.05), `mhc_post_mult_value` (2.0), `logit_scale` (1.0).

### Hybrid layer accounting

Both vendored configs supplied a `layers_block_type` property that mapped their sparse-attention layer type onto `"attention"`. Without it, `ModelConfig.get_num_layers_by_block_type` falls through to its `layer_types` branch, which only recognised `"full_attention"` — so both models would have counted **zero** attention layers. It now counts `deepseek_sparse_attention` and `qwen_sparse_attention` too, which is what both properties did.

`_get_full_attention_layer_indices` in the turboquant config has the same blind spot, but it already checks `layer_types` first and so is unchanged by this PR. Flagging it as a separate pre-existing issue rather than widening scope here.

### Open question: the frame sampler

This PR keeps vLLM's own frame sampler, but I am not confident that is the right call and would like a view on it.

The sampler's docstring justifies diverging from the reference implementation by noting that the linspace variant "cost 4 points on video grounding evals". That comment describes only the **short-clip** branch (`total_frames < extract_t`), which requires `fps < 2`; I could not construct a case where that branch differs from upstream at all.

The branch that does differ is the common one, for an unrelated reason: vLLM walks at `1/(temporal_patch_size * target_fps)` (0.25s), collecting ~2x the candidates, then re-spreads them with `linspace`. Upstream walks at `1/target_fps` (0.5s) and keeps its picks. Over a sweep of realistic sources, **38/53 cases differ** — same frame counts, different indices:

| case | vLLM | upstream |
|---|---|---|
| 30s @30fps | `0, 15, 30, 45, 60, 76, 91, 106` | `0, 15, 30, 45, 60, 75, 90, 105` |
| 3 frames @2fps | `0, 1, 2, 2` | `0, 1` |

vLLM's spacing drifts off the target fps and short sources pick up a duplicated tail frame from the odd-parity pad. There is also no consistency argument for keeping our own: `create_hf_metadata` sets `do_sample_frames = len(valid_frame_indices) == source.total_frames_num`, so whenever the backend sub-samples the processor is told not to re-sample, and the backend's choice is authoritative either way.

So switching to upstream's `sample_frames` would delete the last vendored piece and looks more correct on the merits — but it changes frame selection for nearly every video, so it needs a video eval that I could not run. Keeping ours (what this PR does) preserves exactly what ships today at no eval cost. Happy to switch if a reviewer with a GPU wants to take the eval.

### Dropped code left over from Qwen3-Next — please sanity-check

`Qwen4ExpDecoderLayer` selected between a MoE block and a dense `Qwen3NextMLP`:

```python
mlp_only_layers = getattr(config, "mlp_only_layers", [])
num_experts = getattr(config, "num_experts", 0) or 0
absolute_layer_id = self.layer_idx + 1
is_moe_layer = self.layer_idx not in mlp_only_layers and (
    num_experts > 0 and absolute_layer_id % config.decoder_sparse_step == 0
)
```

This is a verbatim lift of `qwen3_next.py:479-485`, which arrived with the original support PR (#53896) — Qwen4Exp derives from Qwen3-Next and still subclasses `Qwen3NextAttention` and `Qwen3NextSparseMoeBlock`. `decoder_sparse_step` and `mlp_only_layers` are Qwen3-Next concepts; upstream's `Qwen4ExpTextConfig` declares neither, and neither appears anywhere in `Qwen/Qwen3.8-Flash-Next` or `...-FP8`. They only resolved because the vendored config subclassed `Qwen3NextConfig` and inherited them, which is why nothing ever flagged the branch as dead.

Evaluating the original expression against both checkpoints with the old vendored config gives `is_moe_layer` **True for 48/48 layers**, no dense layers: with `mlp_only_layers=[]`, `num_experts=512` and `decoder_sparse_step=1` it reduces to `True` for any layer index. So this PR builds the MoE block unconditionally and drops the branch, its guards and the `Qwen3NextMLP` import (`-38/+6`).

Worth a second opinion, since it is a deletion rather than a rename: a hypothetical future checkpoint setting `mlp_only_layers` or `decoder_sparse_step` would previously have been honoured and now would not. Upstream's `qwen4_exp` has no dense path at all (neither key appears in the model, and `validate_architecture` requires `num_experts > 0`), so such a checkpoint would not load in transformers either — which is why I think dropping it is right. Happy to restore it as `getattr(config, "decoder_sparse_step", 1)` with only the dead `else` removed if a reviewer would rather keep the guard.
