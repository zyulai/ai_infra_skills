## Overview

Reflection Beam-1.0 FP8 on H200 runs TP8 with `--moe-backend triton`, as in its recipe. There is no tuned config for its fused MoE shape (`E=256, N=320`, fp8_w8a8), so every layer uses the default config. This PR adds a tuned H200 config for that shape. It also lets `benchmark_moe.py` time the per-token activation / per-channel weight FP8 path that Beam's compressed-tensors checkpoint runs, and parse `BeamForCausalLM`. Follow-up to #62074.

## Claims

- Fused MoE on 1xH200, Beam-1.0 TP8 shape, per-token FP8 path: 3-19% faster at 96-512 tokens when replaying top-k ids recorded from Beam's real weights, and 9-45% faster at 96-1536 tokens with uniform random routing. At 1024 tokens the kernel goes from 31% to 57% of the HBM bound.
- One TP8 rank of Beam-1.0 FP8 on 1xH200 (all 52 layers, dummy weights, uniform simulated routing): a decode step at 128 and 256 requests takes 9.4% and 16.7% less time.
- Up to 64 tokens and from 2048 tokens the file holds the default config, so small-batch decode and prefill do not change. With DFlash2 (recipe: 7 draft tokens), a verify step has 8 rows per request, so 12-192 requests land in the range that gets faster.
- `benchmark_moe.py` now times the kernel variant the model runs: for compressed-tensors checkpoints with `strategy: token` input activations it uses per-token activation and per-channel weight scales. Before, it always timed per-tensor FP8.

## Validation

### Correctness

Only Triton tile parameters change. At the Beam shape and M = 96, 128, 256, 1024 and 1536, the output with this file and with the default config both have a mean relative error of 1.41-1.44% against the per-column reference in `tests/kernels/moe/test_triton_moe_ptpc_fp8.py` (its threshold is 5%). Both configs use `BLOCK_SIZE_K=128`, and the outputs were the same.

`benchmark_moe.py --model reflection/Beam-1.0-501B-A23B-FP8 --tp-size 8 --dtype fp8_w8a8 --batch-size 1 128 1024` runs on this branch and prints `Benchmarking per-token activation and per-channel weight FP8.` before the timings (checked on an L4, which has no config file and uses the default config). The tuning run above used the same `benchmark_config` path.

## Details

- Dummy weights route almost every token of a step to the same 8 experts, so each expert sees many rows and larger M tiles win. Without uniform simulated routing, the proxy above shows this file 9.8% and 13.0% slower at 128 and 256 requests. The recorded real routing sits much closer to uniform than to that.
- Per-tensor and per-token FP8 read the same config file name. For this shape, configs tuned on the per-tensor path time within 1% of these on the per-token path.
- The search space was pruned to keep tuning near half an hour: `BLOCK_SIZE_M` 16 up to 128 tokens, 16-32 up to 512, 16-64 above; `GROUP_SIZE_M` in {1, 16, 64}. The pruning was in my tuning script, not in `benchmark_moe.py`.
- Not covered: H100, TP4 (`N=640`), DFlash2 verify, and the full model. 503 GB FP8 needs 8xH200, which I did not run. The recorded routing comes from 3 early MoE layers; later layers may route differently.

Not a duplicate: no open PR adds a fused MoE config for `E=256,N=320`, and none adds per-token FP8 to `benchmark_moe.py`. The open `benchmark_moe.py` PRs change model parsing or error handling (#62526, #49088, #50711, #51353), or add zipf-skewed expert loads (#57100), which is a separate axis from the quantization path here. #61688 (runtime Triton autotune, draft) would make static configs less important if it lands.

AI assistance (Claude Code) was used to write the change, run the tuning and the measurements above, and draft this description.
