## 正文(PR 描述)

> **Note:** @zjy0516 wrote this description and the current approach (commits from `21e3b27` onward, pushed as maintainer edits). The PR's original revision, by the PR author, bounded the gather to 256 MiB chunks; see "Previous revisions" below.

## Overview

`copy_kv_cache_blocks_inplace` (`vllm/v1/worker/utils.py`) ran `blocks[dst] = blocks[src]`, which gathers every source block into one device temporary before scattering it. KV cache blocks can be tens of MiB (Mamba state, or blocks spanning all layers), so a wave of copy-on-write copies for partial prefix-cache hits asks for GiBs that a deployment near `gpu_memory_utilization` does not have, and OOMs. On GPU, this PR copies the blocks with one Triton kernel that moves each contiguous byte run straight from source to destination, with no temporary.

## Claims

- GPU block copies no longer allocate block-sized temporaries; only the descriptor table (24 bytes per run) goes to the device.
- The copy runs 21-28x faster on the GPU than the indexed copy (about 3.2 TB/s vs 117 GiB/s), and host submission stays about 1 ms with thousands of runs.
- Qwen3.5-35B-A3B under async scheduling: copy-on-write waves finish 17% faster than `main` (median 1148 ms vs 1383 ms).
- No change for CPU caches or chained copies (a block that is both a source and a destination): they keep the indexed copy.

## Details

**Root cause.** The right-hand side of `blocks[dst] = blocks[src]` is a materializing gather of `len(src)` blocks. Profiling and warmup never run a copy-on-write, so no memory is reserved for it.

**Implementation.** Each cache view's copies are split into contiguous byte runs (trailing contiguous dims fold into one run), which covers padded, strided, overlaid and kernel-block-split views and the ReplaySSM trackers. All runs go to one Triton launch on the current stream, in the widest word that divides every address and size, so it stays ordered after block zeroing and before the forward pass, like the indexed copy it replaces. Kernel warmup compiles the kernel when prefix caching is enabled, so the first copy-on-write does not JIT mid-serving.

**Chained copies.** The kernel copies runs concurrently, so a block that is both a source and a destination falls back to the indexed copy, which reads all sources first. Copy-on-write destinations are freshly allocated blocks, so this does not happen in serving today.

**Limitations.** Overlaid views of one storage may write the same destination bytes twice with identical data; block-level disjointness assumes no two views of one storage are shifted against each other, which no allocator produces today. ROCm runs the same Triton kernel but was not tested locally (the AMD mirror of the V1 Worker CI step runs these tests). XPU and CPU keep the indexed copy.

**Previous revisions.** This PR first bounded the gather to 256 MiB chunks, which still needs unreserved memory and keeps the slow indexed copy, then tried `cuMemcpyBatchAsync`, replaced for the reasons above.

+def _block_copy_runs(blocks: torch.Tensor, block_ids: np.ndarray) -> np.ndarray:
+    """Split copies between the `[2, num_copies]` source and destination
+    `block_ids` of `blocks` into contiguous runs.
+
+    Returns:
+        An int64 array of shape `[3, num_runs]` holding source addresses,
+        destination addresses and sizes in bytes.
+
+    """
+    shape, strides = list(blocks.shape[1:]), list(blocks.stride()[1:])
+    run_len = 1
+    while shape and (shape[-1] == 1 or strides[-1] == run_len):
+        run_len *= shape.pop()
+        strides.pop()
+    offsets = np.zeros(1, dtype=np.int64)
+    for size, stride in zip(shape, strides):
+        offsets = (offsets[:, None] + np.arange(size) * stride).ravel()
+    elements = (block_ids[:, :, None] * blocks.stride(0) + offsets).reshape(2, -1)
+    addresses = blocks.data_ptr() + elements * blocks.element_size()
+    sizes = np.full((1, addresses.shape[1]), run_len * blocks.element_size())
+    return np.concatenate([addresses, sizes])
