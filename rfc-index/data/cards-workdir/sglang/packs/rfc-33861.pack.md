## 正文(PRD / 提案全文)

## Summary

The three PD transfer backends (mooncake, nixl, mori) each implement the full bootstrap + transfer control protocol independently: ZMQ socket loops, message dispatch, room/state lifecycle, staging glue, TP/DCP slice orchestration, timeouts, failure handling. They describe the same protocol but have drifted apart.

This RFC proposes a **target end state** where the protocol exists once and a backend only implements data movement. It is an early proposal: the interface below is a sketch, and whether the end state is reachable exactly as drawn is open.

## Why

The divergence is not cosmetic -- each copy is missing something the others have. Examples from comparing the three:

- mori's decode manager never starts the heartbeat checker thread, so a dead prefill peer is never detected (mooncake and nixl both start it).
- nixl's sender never enforces the bootstrap timeout, and prefill-side transfer failures are not propagated to decode -- requests hang until the generic waiting timeout instead of failing fast.
- The transfer-info message swaps two frame positions between mooncake and nixl; both frames hold integers, so a mismatch would silently exchange two fields rather than fail cleanly.

Every protocol fix or feature is currently written up to three times (staging exists in mooncake+nixl only, DCP relayout in mooncake+nixl only, session blacklisting in mooncake only), and the per-backend classes are dispatched through an enum-keyed `get_kv_class` table that erases static typing.

## Target end state (sketch, open to change)

One concrete set of protocol classes -- `KVManager` / `KVSender` / `KVReceiver` / `KVBootstrapServer` -- with no backend subclasses. Socket loops, parsing/dispatch, room lifecycle, staging, chunking, TP/DCP slice math, timeouts, heartbeat, failure propagation live there, once. A backend provides only a transport object, injected at construction:

```python
class BaseTransport(ABC):
    def init_engine(self): ...
    def register_memory(self, kv_args): ...
    def local_desc(self) -> bytes: ...            # opaque, carried in the register message
    def open_peer(self, session_id, desc: bytes) -> Peer: ...
    def submit(self, peer, blocks) -> Handle: ... # blocks = [(src_ptr, dst_ptr, len)]
    def poll(self, handle) -> KVPoll: ...
```

Boundary: protocol decides which bytes go where and when; transport moves `(src_ptr, dst_ptr, len)` and names remote memory. Backend directories shrink to thin wrappers around their engines (today mooncake calls 5 engine methods, nixl 14, mori 8). `get_kv_class` / `KVClassType` are replaced by a typed `make_transport(backend)`. The `fake` backend becomes a null transport, which also makes the whole protocol layer testable in CPU-only CI.

There is no big-bang refactor implied: the intended path is many small PRs -- behavior alignments (individually reviewable fixes) and mechanical hoists of already-identical code. Wire-format unification goes last and needs its own migration story, since there is no version negotiation today.

## Open questions

- Completion signaling: mooncake/mori report status to decode over ZMQ; nixl uses in-band transport notifications with a passive decode side. Which model should the unified layer own?
- Is the 6-method transport interface sufficient? (nixl's prepped descriptor lists need per-peer cached state; mixed VRAM/DRAM pools are nixl-only today.)
- `is_dummy` / abort-ack / guard-frame semantics differ subtly across the three; each needs a call on which behavior is intended.
- Wire migration: flag day vs a version frame with a dual-parse window.

Feedback from the mooncake / nixl / mori owners is the main ask -- especially whether this target shape conflicts with anything planned for the backends.
