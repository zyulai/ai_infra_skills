## 正文(PRD / 提案全文)

### 🚀 The feature, motivation and pitch

### Context
RFC #8913 proposes decoupling checkpoint formats from kernel integrations by standardizing how weights are represented at runtime and allowing kernel-specific repacking/preprocessing as a separate concern. This RFC scopes that same idea specifically to quantized linear methods (e.g., GPTQ/AWQ/FP8/FP4 linear integrations) where kernel selection is currently constrained by checkpoint packing/layout assumptions.​

### Problem

Many quantized linear “methods” implicitly encode checkpoint layout requirements in their weight-loading paths (often via specialized create_weights implementations), so the checkpoint format effectively selects the kernel. This causes:

- Duplicated create_weights logic across methods that differ only by kernel/backend.
- Kernel integrations that are hard to mix-and-match with alternate checkpoint layouts.
- Layout/packing details leaking into create_weights rather than `process_weights_after_loading` concern.
- The Kernel abstraction(#27814, #11785) is already largely format-agnostic in spirit: kernel selection is based on a kernel/layer configuration. However, weight-loading still bakes in checkpoint packing/layout assumptions, which ends up constraining which kernels can run.

### Proposal

Formats map to separate LinearMethods via get_quant_method; instead, we want format-specific weight creation functions and move format/config into the kernel abstraction so dispatch can pick a kernel that matches both constraints and format.
```python
# Assume we only have CompressedTensorsW8A8Fp8Params and AWQ formats:
# CompressedTensorsW8A8Fp8Params needs:

# AWQ needs:
# 1- weight(PackedvLLMParameter)

        ...
    def verify_weight_scales(self):
        ...

    def verify_input_scales(self):
        ...
    
    def verify_zero_points(self):
        ...

    def get_params(self) -> dict[str, torch.nn.Parameter]:                                                                
        params = {                                                                                                             
            "weight": self.weight,                                                                                             
            "weight_scale": self.weight_scales,                                                                                
        }                                                                                                                      
        if self.input_scales is not None:                                                                                      
            params["input_scale"] = self.input_scales

            params["qzeros"] = self.zero_points                                                                                
        return params

# Quantization Configurations

class AWQConfig(QuantizationConfig):
    def create_linear_params(self, config):
        # load the weights
        return LinearParams(weights, weight_scales, zero_points=zero_points)

        # load the weights
        return LinearParams(weights, weight_scales, input_scales=input_scales)
```

The main flow of this proposal is summarised as follows:

1. Define a canonical internal weight representation for quantized linear layers 
2. Loader/runtime converts checkpoint tensors (diverse layouts) → canonical representation.
3. Kernel integrations consume canonical weights, and may implement an optional preprocessing hook (repack/transpose/reorder) to produce kernel-optimal buffers.


### Open questions / constraints

- Memory overhead: canonicalization + repacking must avoid OOM risk (extra buffers, dtype changes, transposes).
- Mixed-precision kernels: some kernels have tightly coupled packing logic; we may need careful choice of canonical layouts to minimize conversions.
- API shape: whether parameter creating belongs in quantization config vs. quantization method(we prefer to completely remove all linear quantization methods), but the intent remains aligned with RFC #8913’s separation of concerns.​

### Implementation Plan
Some legacy methods are slated for deprecation (#30136), so this refactor will focus on linear methods that are expected to remain supported and already use the kernel abstraction. Over time, we expect the remaining Methods to migrate to the same abstraction as well. Therefore we want to focus our effort on the following classes:

- [ ] Fp8LinearMethod
- [ ] ModelOptFp8LinearMethod
- [ ] CompressedTensorsW8A8Fp8
- [ ] QuarkW8A8Fp8
- [ ] QuarkW8A8Int8
- [ ] CompressedTensorsW8A8Int8
- [ ] GPTQMarlinLinearMethod
- [ ] CompressedTensorsW4A8Fp8
- [ ] CompressedTensorsW4A8Int
- [ ] CompressedTensorsWNA16



### Alternatives

- Do nothing: Keep the current design where checkpoint packing/layout implicitly selects the linear Method and, by extension, the kernel. This avoids short-term refactors, but continues to couple kernel integrations to specific checkpoint formats, leading to duplicated weight-loading code, limited kernel reuse across formats/backends, and slower iteration when adding new kernels or supporting new checkpoint layouts.
