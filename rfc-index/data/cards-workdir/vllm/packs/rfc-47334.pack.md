## 正文(PRD / 提案全文)

## Summary

Port all vLLM-built Hopper and Blackwell CUDA C++ kernels from in-tree C++/CUTLASS implementations to CuTeDSL where feasible.

The goal is a build-free development install for common Hopper and Blackwell environments: contributors should be able to install vLLM and iterate on kernels without local vLLM CUDA C++ builds.

This builds on the motivation from [#17419 Kernel Library Restructure / Packaging Split](https://github.com/vllm-project/vllm/issues/17419): vLLM source builds are too slow, and most development does not require rebuilding `csrc`.

## Motivation

vLLM source builds are expensive, largely because of custom CUDA/C++ kernels. This slows down local setup, ordinary development, kernel experiments, and CI/debug cycles.

The problem is growing for Hopper and Blackwell as vLLM adds more SM90, SM100, SM103, SM120, and SM121-specific kernels. CuTeDSL gives us a path to keep optimized architecture-specific kernels while reducing the amount of CUDA/C++ code built directly by vLLM.

## Proposal

Port all vLLM-built Hopper and Blackwell CUDA kernels to CuTeDSL where technically feasible. The target end state is that Hopper/Blackwell development installs do not require local vLLM CUDA C++ builds and raw CUDA performance remains competitive.

## Scope

This RFC covers Hopper and Blackwell kernels built by vLLM. The main targets are quantized GEMMs, MoE kernels, sparse/compressor kernels, and attention-adjacent kernels where CuTeDSL or FA4 is the expected long-term path.

The warmup/cache/JIT-monitoring infrastructure needed to avoid JIT compilation during serving and the resulting ITL spikes will be discussed in a subsequent RFC.

This RFC does not propose porting Ampere kernels to CuTeDSL. It also does not propose rewriting kernels without performance validation or investing in FA3-specific CuTeDSL work expected to be superseded by FA4.

For Hopper attention, the expected direction is to replace FA3 with FA4 once FA4 decode performance is sufficiently optimized. CuTeDSL work should target the forward-looking FA4 path rather than duplicating long-term effort on FA3.

## Benchmarking Requirements

Each port should report raw CUDA kernel time and end-to-end serving impact, cold-JIT and warmed behavior, and Hopper and Blackwell results separately.

## Success Criteria

This effort is successful if common Hopper/Blackwell development installs do not require local vLLM CUDA C++ builds and wheel build time is meaningfully reduced. Raw CUDA performance should be competitive with existing native kernels, end-to-end serving performance should not regress, and runtime JIT should not occur during serving.

## Risks

### Startup Time Increase

CuTeDSL can move cost from install time to runtime, so startup time may increase. We should keep warmups close to what the deployment will require at runtime. We may also want to look at producing JIT caches ahead-of-time.
