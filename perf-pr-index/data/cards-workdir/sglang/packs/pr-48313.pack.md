## Motivation

With plain TP (`--tp 8` or `--tp 4`, no `--ep`), GLM-5.3-Flash runs its routed experts through the Triton fused MoE and looks up:

- `E=289` for the target layers, since the shared expert is fused into the routed experts by default.
- `E=288` for the NextN/MTP draft layer, and for any run with `--disable-shared-experts-fusion`.

#45089 added H20 configs for these shapes, tuned with the stock `tuning_fused_moe_triton.py`, which picks one config per batch size for both GEMMs. There is no `_down` file, so serving logs `Down MoE config file not found ...; reusing the tuned up-projection config without TMA` and runs the down GEMM with the up config, without TMA.

`tuning_fused_moe_triton_sep.py` tunes the two GEMMs separately and writes a `_down` config next to the up config; #45591 shipped such files for H200 (`E=72,N=2048`). This PR does the same for the four H20 shapes. The up configs are re-tuned together with the down configs, so they replace the four files from #45089.

## Modifications

Eight Triton 3.8.0 configs (main pins torch 2.14.1, which ships Triton 3.8.0): an up-projection config and a `_down` config for each shape below, all with `device_name=NVIDIA_H20,dtype=fp8_w8a8,block_shape=[128, 128]`. The four up configs replace #45089's; the four `_down` configs are new.

| Shape | Used by |
| --- | --- |
| `E=289,N=256` | TP8, target layers |
| `E=288,N=256` | TP8, MTP draft layer / shared-expert fusion disabled |
| `E=289,N=512` | TP4, target layers |
| `E=288,N=512` | TP4, MTP draft layer / shared-expert fusion disabled |

Tuning:

- `benchmark/kernels/fused_moe_triton/tuning_fused_moe_triton_sep.py --enable-tune-up-tma`: it tunes the down GEMM first, then the up GEMM, writing the up output in the layout the chosen down config reads.
- Routing from `--topk-ids-dir`: top-k ids captured from GLM-5.3-Flash serving on H20 (TP4, 3 ShareGPT prompts of about 8k tokens, all 42 MoE layers). `E=288` drops the 9th column, the fused shared expert.
- The full default search space (1,280 configs after the `BLOCK_SIZE_K` filter) and the default 18 batch sizes, one GPU per batch size. The script's single-GPU path skips that filter and saves nothing, so I called its `tune()` with the filtered space and saved with its `save_configs_sep()`.
- `E=289` needs #43647's one-line `common_utils.py` change, which I applied locally as for #45089. #43647 was closed unmerged, and main's tuner still writes only `E=288` for this model. This PR leaves the tuner alone.

The down GEMM uses TMA in all 72 entries, the up GEMM in 70 (not at M=4096 for `N=256`). `BLOCK_SIZE_M` is 16 for M ≤ 512, 32 for M = 1024–3072, and 64 at M=4096 (32 for `E=288,N=512`). Each `_down` entry uses its up entry's `BLOCK_SIZE_M`, which the loader requires. 71 of the 72 up entries differ from #45089's.

## Setup

- Tuned on three 8× H20 96 GB nodes. Measured on two of them: on one node, the kernel benchmark on GPUs 0–3 and numerics on GPU 0, then TP4 serving on GPUs 4–7; TP8 serving on the other node. No GPU throttled (per-case median SM clock 1965–1980 MHz).
- Image `lmsysorg/sglang:nightly-dev-cu13-20261115-7b5fb39b` (torch 2.14.1+cu130, Triton 3.8.0), with `PYTHONPATH` set to a source tree: main `22e1cb6d98` vs this PR's head, which is main plus the eight files.

## Serving

Each pair uses the same node, image and flags; the arms differ only in the source tree. For each shape the server runs (`E=288` only with MTP), main's log shows `Down MoE config file not found ...; reusing the tuned up-projection config without TMA`, and this PR's shows `Using MoE kernel config from` for both files plus `Up MoE TMA is enabled` and `Down MoE TMA is enabled`.

- Common: Triton MoE (auto-selected), BF16 KV cache, default DSA backends, `--disable-radix-cache`, `--reasoning-parser glm45 --tool-call-parser glm47`.
- MTP: `--speculative-algorithm EAGLE --speculative-num-steps 5 --speculative-eagle-topk 1 --speculative-num-draft-tokens 6`.
- TP4, on GPUs 4–7: `--tp 4 --mem-fraction-static 0.92 --max-running-requests 16 --cuda-graph-max-bs-decode 16 --chunked-prefill-size 4096 --context-length 32768`.
- TP8: `--tp 8 --mem-fraction-static 0.85 --max-running-requests 64 --cuda-graph-max-bs-decode 64 --chunked-prefill-size 8192 --context-length 163840`.
- Load: `python -m sglang.benchmark.serving --dataset-name random-ids --tokenize-prompt --random-range-ratio 1.0 --request-rate inf --seed 42`, 2048 input tokens, 4× concurrency prompts (8 at concurrency 1), after one warm-up run per server start.

## Accuracy

GSM8K 20-shot, 500 questions (`sglang.test.run_eval --eval-name gsm8k --api completion --num-shots 20 --num-examples 500 --max-tokens 512`, 128 client threads), on the servers without MTP above:

| Layout | Main | This PR |
| --- | --- | --- |
| TP4 | 0.924 | 0.926 |
| TP8 | 0.938 | 0.932 |

The arms differ by 0.2 (TP4) and 0.6 points (TP8) here, and by 0.1 and 0.3 points averaged over the MTP runs above. Repeated runs of the same arm differ by up to 1.6 points (TP8 main with MTP: 0.938 and 0.922), and one 500-question score has a standard error of about 1.1 points.

Numerics (one GPU): with fixed random FP8 weights and the captured routing (M from 1 to 2048), the two arms' `fused_moe` outputs differ by at most 1.1e-3 (relative L2) on all four shapes. Against a float32 reference (dequantized weights, unquantized activations, M ≤ 64), both arms have a relative error of 4.2e-2 to 4.6e-2, and their errors differ by at most 2e-5.
