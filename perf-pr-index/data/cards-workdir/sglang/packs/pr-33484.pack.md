## Motivation

A DeepSeek-V4 C4 token is 584 bytes, but it is **not one contiguous range**. A page row holds 64 values of 576B followed by 64 scales of 8B:

```
/// Paged C4 cache layout:
/// VALUE 0, VALUE 1, ..., VALUE 63,
/// SCALE 0, SCALE 1, ..., SCALE 63,
/// [Padding to align to 576 bytes]
```

So the ROCm swap-in copies a token with two `transfer_item_warp` calls, 576B then 8B. On wave64 that is three wavefront passes — 64 value words, 8 value words, then 1 scale word — and only the first keeps the whole wavefront busy.

The passes also do not overlap. `item_size_bytes` reaches `transfer_item_warp` as a runtime argument, so the compiler keeps the value copy as a rolled loop with the wait inside the body. Disassembling the gfx950 code object:

```
global_load_dwordx2 v[30:31], v[22:23]
s_waitcnt vmcnt(0)
global_store_dwordx2 v[24:25], v[30:31]
s_cbranch_execnz ...                       <- second value pass
...
global_load_dwordx2 v[22:23], v[22:23]     <- scale
s_waitcnt vmcnt(0)
global_store_dwordx2 v[24:25], v[22:23]
```

Three serialized host round trips per miss, on the decode critical path: `swap_in_selected_pages` runs once per C4 layer per decode step, on the main stream, between that layer's indexer and its attention.

The CUDA branch does not have this problem — `device::hisparse::transfer_item` already moves the value tail and the scale together. It is unusable on ROCm only because its warp logic is hardcoded to 32 lanes.

## Modifications

Adds `transfer_dsv4_item_warp`, used by the ROCm `IsDsv4Layout` miss copy in place of the two `transfer_item_warp` calls. It walks the token as one 73-word space so the value tail and the scale land in the same pass, and stages every load before any store. The pass count is a compile-time constant, so the copy unrolls and both loads issue before either store:

```
global_load_dwordx2 v[22:23], v[24:25]
global_load_dwordx2 v[20:21], v[18:19]
s_waitcnt vmcnt(0)
global_store_dwordx2 v[16:17], v[22:23]
s_waitcnt vmcnt(0)
global_store_dwordx2 v[14:15], v[20:21]
```

One exposed round trip instead of three. No API, config, or template change. CUDA behavior untouched; the generic (non-DSv4) path is untouched.

## Benchmarking and Profiling

MI355X (gfx950), DSv4 paged-layout swap-in, `miss_rate=0.2`, `hot_buffer_size=4096`, `top_k=2048`.

**Methodology.** Both variants are compiled into a single kernel and selected at runtime, with reps alternating between arms inside one process. This matters here: comparing two separate builds moves identical code paths by up to 14% on this kernel, which is more than the effect being measured. Medians of 15 reps × 5 timed rounds, two independent runs.

| batch | before | after | delta |
|---|---|---|---|
| 1 | 102.4 / 105.7 us | **87.8 / 87.9 us** | -14.2% / -16.9% |
| 10 | 122.8 / 119.8 us | **97.2 / 96.2 us** | -20.9% / -19.8% |
| 24 | 136.9 / 136.1 us | 125.2 / 125.2 us | -8.5% / -8.0% |
| 100 | 468.6 / 467.5 us | 451.7 / 451.5 us | -3.6% / -3.4% |

The copy is worth optimizing: dropping `miss_rate` from 0.2 to 0.001 on the unmodified kernel takes batch 1 from 110.7 to 20.5 us, so **82% of the swap-in is the miss copy**. The gain fades at high batch because the kernel becomes bandwidth-bound rather than latency-bound, and round-trip count stops mattering there.

### A one-pass variant was tried and is worse

576B is exactly 36 × 16B, and both the page stride (37440) and the value stride (576) are multiples of 16, so the value is always 16B-aligned and the whole token fits in a single pass: lanes 0–35 move one 16B vector each, lane 36 moves the scale. Despite needing fewer passes it lost at every batch size, and was slower than the baseline at batch 1:

| batch | two-pass 64-bit | one-pass 128-bit |
|---|---|---|
| 1 | -14.2% / -16.9% | +3.6% / +1.0% |
| 10 | -20.9% / -19.8% | -4.9% / -4.3% |
| 24 | -8.5% / -8.0% | -4.7% / -4.3% |
| 100 | -3.6% / -3.4% | -1.1% / -1.0% |

The two-pass form engages all 64 lanes on its first pass; the one-pass form only 37. For these host reads, full wavefront occupancy at 64-bit beats partial occupancy at 128-bit even when the wider form needs fewer round trips. This is the same effect that gates the widening in #33085.

## Accuracy Tests

Adds `test_load_cache_to_device_buffer_dsv4_fused_copy_multi_miss`: several misses in one launch at varying source and destination page offsets, including the second page, so the value/scale seam does not always fall at the same address. It takes the destinations from the kernel output rather than assuming an eviction order, and checks that slots the kernel never wrote keep their fill.

Suppressing the scale half of the copy fails both the new test and the existing `dsv4_mla_miss_copy_layout` case, so the coverage has teeth.

Full file on MI355X: 10 passed, 2 skipped (the 2 skips are the CUDA-only DSv4 paged cases).
