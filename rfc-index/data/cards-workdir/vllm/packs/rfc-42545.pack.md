## 正文(PRD / 提案全文)

### Motivation.

vLLM's Triton kernels load data and store results via raw pointer arithmetic (`tl.load(ptr + offset, mask=…)`). Triton's newer structured memory-access API — `tl.make_tensor_descriptor` (TD) — is the replacement API upstream Triton is steering toward (`tl.make_block_ptr` is officially deprecated) and the path to architecture-accelerated memory on modern hardware: TMA on NVIDIA Hopper, 2D block loads on Intel Xe. Adopting TD in vLLM kernels unlocks significant E2E speedups where backend lowering is mature (Intel Battlemage: +38–83%), creates headroom where lowering is still catching up (NVIDIA Blackwell today), and positions the code base ahead of the deprecation rather than behind it.

This RFC proposes a **strategy for adopting TD across vLLM's Triton kernels**: opt-in TD paths behind a single env var (`VLLM_TRITON_USE_TD`) with per-kernel constexpr gating, a platform-aware default, and graduation criteria that gate every future conversion and every default-on flip. The strategy has been applied to `triton_unified_attention.py` (the unified attention kernels used by the `TRITON_ATTN` backend) in PR [#40327](https://github.com/vllm-project/vllm/pull/40327) as the pilot that validates the approach; follow-up PRs extend TD to the remaining XPU-invocable Triton kernels under the same framework, each justified by per-kernel benchmarks meeting the graduation criteria below.

#### Triton surface area in vLLM

vLLM has **245 `@triton.jit` functions** in mainline today. The subset that is **invocable on Intel XPU** — either as default path or via documented opt-in env vars / backend selectors — is our primary scope:

| Category | Count | Invocation path (XPU) |
|---|---|---|
| **Unified attention (pilot)** | 3 | `--attention-backend=TRITON_ATTN` — PR [#40327](https://github.com/vllm-project/vllm/pull/40327) |
| **Other attention ops on the TRITON_ATTN path** | ~20 | `TRITON_ATTN` backend: `triton_decode_attention`, `triton_prefill_attention`, `chunked_prefill_paged_decode`, `triton_reshape_and_cache_flash`, `prefix_prefill`, `common.py` token merge, `turboquant_*`, `dcp_alltoall` |
| **MLA Triton kernels** | ~9 | `--attention-backend=TRITON_MLA` (auto-selected for MLA models), plus `xpu_mla_sparse` |
| **LoRA Triton path** | ~16 | `XPU_USE_TRITON_KERNEL=1` env var — routes `PunicaWrapperXPU` through Triton kernels instead of SYCL |
| *(Helpers / pure-compute in same files)* | ~15 | N/A — no memory I/O to wrap with TD |
| **XPU-invocable subtotal** | **~50** | This is the RFC's XPU scope |
| Not currently XPU-invocable (CUDA/ROCm-only today) | ~160 | fused_moe, quantization, sample/spec_decode, mamba, FLA, rotary, deepseek_v4_ops — XPU delegates to SYCL (`vllm-xpu-kernels`) or has no Triton path. Covered by this strategy *if* the ecosystem later adds XPU paths. |
| *(Helpers / pure-compute, other)* | ~20 | Excluded from scope |
| **Total** | **245** | |

This RFC's strategy applies to all 245 kernels in principle, but the empirical evidence and near-term work focus on the ~50 XPU-invocable kernels where Intel has both the data and the motivation to drive conversion. NVIDIA / ROCm conversions of the remaining ~160 kernels are free to follow under the same framework and the same graduation criteria.

#### Why this matters now

1. **XPU enablement gap.** Current raw-pointer Triton attention kernels are functional on Intel XPU (Battlemage) but perform below hardware potential. Measured impact of TD on Battlemage: **+38% to +83% throughput** on Qwen3-4B-Thinking-2507 and Llama-3.1-8B-Instruct across prefill-heavy and decode-heavy workloads.

2. **NVIDIA Hopper TMA path underutilized.** On Hopper (H100/H200), TD lowers to Tensor Memory Accelerator (TMA) instructions, unlocking hardware memory throughput otherwise inaccessible to raw-pointer kernels. We do not include Hopper benchmarks in this RFC; community runs are welcome.

3. **NVIDIA Blackwell: opt-in bridges the gap.** On B200, the TD path currently underperforms raw pointers (–33% to –60% E2E). We attribute this to implementation-level factors — per-tile descriptor reconstruction overhead, autotune configs not yet tuned for TMA — rather than a structural property of the API. `tl.make_tensor_descriptor` carries strictly more information than raw pointers (explicit shape, strides, and block layout), so in principle the backend can always lower it to at least parity. The opt-in design lets Blackwell users take the fast path today and adopt TD later as these optimizations land, without a second kernel migration.

   The asymmetry between the Battlemage speedup and the B200 regression is consistent with the fraction of forward-pass FLOPs each model spends in the attention block. Computed at a representative decoding shape (`seq_q=1, seq_kv=4096`) from public HF configs, the attention block (QKV + QK + AV + O) accounts for ~25% of forward FLOPs on Qwen3-4B, ~22% on Llama-3.1-8B, and ~14% on Qwen2-7B. On Battlemage, Xe 2D block loads make the TD path substantially faster in the attention kernel itself, and the E2E gain tracks this share (+83% / +55% / TD-neutral respectively). On B200, the current Triton→TMA lowering has not closed the gap to the highly tuned raw-pointer path, so the same attention-share multiplier works against the TD kernel rather than for it.

4. **Alignment with Triton's direction.** `tl.make_block_ptr` is officially deprecated in Triton: as of 2026-03-06, it emits a runtime deprecation warning explicitly directing users to `tl.make_tensor_descriptor` (or the `TensorDescriptor` class) as its replacement ([triton-lang/triton#9667](https://github.com/triton-lang/triton/pull/9667)). TD is the API Triton upstream is steering toward for lowering to accelerated memory paths — TMA on Hopper, 2D block loads on Xe. Adopting TD in attention kernels aligns with this direction and gives every backend a single API to optimize against, rather than requiring per-platform rewrites as block pointers phase out.

5. **Zero regression by design.** TD is off by default on all NVIDIA platforms. When disabled, the kernel compiles to the exact same code path — same autotuning, same performance, bit-exact output. Enabling TD is a single env-var flip (`VLLM_TRITON_USE_TD=1`) that users can benchmark on their own hardware before committing. This change adds capability; it removes nothing. The engineering cost of converting attention to TD is paid once — every backend benefits as its lowering improves, without a second kernel migration.

6. **Adjacency to [RFC #40458](https://github.com/vllm-project/vllm/issues/40458).** A parallel RFC (#40458) proposes converting simple element-wise kernels (SwiGLU, MRoPE, etc.) to **block pointers**, and asks maintainers: *"`tl.make_block_ptr` vs `tl.make_tensor_descriptor`?"* Given the deprecation of `tl.make_block_ptr` (see point 4) and the fact that on tiled-memory and TMA-capable architectures (Intel XPU, NVIDIA Hopper) TD is the API steering toward the accelerated memory paths while block pointers are not, this RFC complements #40458 by empirically answering that question for attention kernels: **block_ptr and TD are both useful for different kernel classes; for heavy kernels on tiled-memory and TMA-capable HW, TD is the path forward**.

### Proposed Change.

#### Pilot kernel (PR [#40327](https://github.com/vllm-project/vllm/pull/40327))

The pilot that validates the strategy is `vllm/v1/attention/ops/triton_unified_attention.py`. PR [#40327](https://github.com/vllm-project/vllm/pull/40327) refactored the file so that the previously separate 2D and 3D attention kernels are now a single unified kernel with two opt-in TD gates; the refactor also added four TD-path `@triton.jit` helpers:

| `@triton.jit` function | Role | TD path status |
|---|---|---|
| `kernel_unified_attention` | Main kernel — prefill / decode / segmented decode in one entry | **Opt-in TD available** (`USE_TD` for K/V cache tile loads, `USE_TD_QO` for Q load + output store). |
| `reduce_segments` | Post-processing kernel (online softmax reduction of per-segment outputs) | Not yet wrapped; access is already contiguous, trivial candidate for follow-up. |
| `_cast_kv_tile` | Helper — cast/dequant K/V tile data | N/A (operates on in-register tile data post-load). |
| `_load_q_td`, `_load_kv_tile_td`, `_store_output_td` | TD-path loaders/storer helpers | **Part of the TD path**; active only when `USE_TD` / `USE_TD_QO` are set. Dead-code-eliminated at compile time otherwise. |

Plus Python helpers (`_is_gemma3_attention`, `_get_tile_size`, entry point `unified_attention`) that are not `@triton.jit` and are not impacted by this RFC.

#### Mechanism

Two independent opt-in constexpr flags at the kernel level:

- **`USE_TD`** (bool, default `False`): TD path for K/V cache tile loads inside the per-tile loop.
- **`USE_TD_QO`** (bool, default `False`): TD path for Q load at kernel entry and output store at kernel exit.

A Python-side env var controls the TD path with **tri-state semantics**:
- unset (default): **auto** — TD on for Intel XPU (where Battlemage evidence shows consistent net-positive impact), off elsewhere;
- `1`: force TD on regardless of platform (used by NVIDIA users who want to evaluate TD on their own HW — Hopper users are the most likely candidates);
- `0`: force TD off regardless of platform (useful for A/B testing and for platforms where TD may be selected by default in the future but the user wants to stay on raw pointers).

The tri-state makes platform-aware defaults the norm without removing user control.

PR [#40327](https://github.com/vllm-project/vllm/pull/40327) shipped this as `VLLM_TRITON_ATTN_USE_TD` — specific to the attention pilot. As the strategy extends to other Triton kernels under the same opt-in pattern, we propose **renaming the env var to `VLLM_TRITON_USE_TD`** in a follow-up PR so that a single flag gates the TD path across all kernels (consistent with the single-flag, no-subsystem-subflags design below). The tri-state semantics stay unchanged.

No subsystem subflags. A single flag is enough for the strategy's scope and keeps the interface simple. If finer granularity is ever needed, it can be introduced as a follow-up without breaking this interface.

#### TD path for K/V cache — how paged KV is handled

vLLM's paged KV cache introduces a 2-level indirection: `seq_offset // BLOCK_SIZE → block_table[…] → physical_block_idx → cache_offset`. `tl.make_tensor_descriptor` requires its base pointer (and strides) to be known at descriptor construction time, which conflicts with per-tile dynamic lookups.

The proposed approach is a **hybrid**:

1. Perform block-table lookup with raw pointer (unchanged).
2. Extract scalar `physical_block_scalar = tl.min(physical_block_idx, axis=0)`; this is valid because **all tiles within one block share the same physical block index** when `BLOCK_SIZE % TILE_SIZE == 0`.
3. Construct TD per tile iteration with base `= cache_ptr + physical_block_scalar * stride_cache_0 + kv_head_idx * stride_cache_2`, then load via `desc.load([offset_in_block, 0])`.

#### Required preconditions

The TD path requires:
- `BLOCK_SIZE % TILE_SIZE == 0` (enforced via `tl.static_assert` in the kernel);
- Triton ≥ 3.4.0 (first release shipping the non-experimental `tl.make_tensor_descriptor`; the experimental predecessor in 3.3.x is not sufficient). For XPU, `triton-xpu` ≥ 3.6.0 includes this API.
- Tile caller must clamp `TILE_SIZE` to `BLOCK_SIZE` when `USE_TD=True`.

When these do not hold, the non-TD path (raw pointer + mask) is selected — **no functional regression**.

#### Code layout

TD path is structured as three `@triton.jit` helpers called from `kernel_unified_attention` when the corresponding constexpr flag is set:
- `_load_q_td` — Q load at kernel entry (used when `USE_TD_QO=True`),
- `_load_kv_tile_td` — K/V cache tile load inside the per-tile loop (used when `USE_TD=True`),
- `_store_output_td` — output store at kernel exit (used when `USE_TD_QO=True`).

The raw-pointer path remains inline in `kernel_unified_attention` under the `else` branches of the same constexpr ifs.

Both paths co-exist in the source, but only one is compiled per kernel specialization. `USE_TD` is a `tl.constexpr` parameter, so Triton specializes the kernel per unique value. When `USE_TD=False`, the TD branch is never visited during AST-to-TTIR translation (see [`python/triton/compiler/code_generator.py`](https://github.com/triton-lang/triton/blob/main/python/triton/compiler/code_generator.py), `visit_If`: after `_unwrap_if_constexpr`, only the active branch is emitted) — the inactive code path is absent from the generated Triton IR and therefore from all downstream artifacts (LLVM IR, PTX, SPIR-V). The compiled binary contains no runtime branch and no instructions for the disabled path. This is a property of Triton's specialization mechanism, applied uniformly across all backends. Long-term, as TD becomes the default across platforms, the raw-pointer path can be removed, simplifying the kernel back to a single code path.

#### Planned kernel conversions beyond the pilot

The strategy proposed here applies uniformly to further kernels; each conversion lands as its own PR, using the same `VLLM_TRITON_USE_TD` env var, the same constexpr-gating pattern, and the graduation criteria below. Near-term targets (all XPU-invocable under the paths in the table above):

1. **Rest of the `TRITON_ATTN` path** in `v1/attention/ops/` — `triton_decode_attention` (4), `triton_prefill_attention` (1), `chunked_prefill_paged_decode` (2), `triton_reshape_and_cache_flash` (3), `prefix_prefill` (2), `common.py` token-merge (~3), `turboquant_*` (5), `dcp_alltoall` (2). ~22 memory-I/O kernels total.
2. **MLA Triton kernels** (`triton_mla.py`, `xpu_mla_sparse.py`) — ~9 kernels, invocable on XPU via `--attention-backend=TRITON_MLA` or the XPU-specific MLA sparse backend.
3. **LoRA Triton kernels** in `lora/ops/triton_ops/` — ~16 kernels, invocable on XPU via `XPU_USE_TRITON_KERNEL=1`.

Non-XPU-invocable kernels (MoE, sampling, spec_decode, mamba, FLA, standard quantization, rotary, DeepSeek V4 ops — ~160 total) are covered by this strategy in principle but are currently routed away from Triton on XPU (delegated to `vllm-xpu-kernels` SYCL ops or simply not supported). Their conversion is open to CUDA / ROCm maintainers under the same framework if and when it makes sense for their platforms.

*Explicit non-goal:* blanket, unconditional conversion of all Triton kernels. The evidence (B200 regression) does not support in-place replacement. Every PR that lands a TD path must be backed by per-kernel, per-backend benchmarks meeting the graduation criteria, and every default-on flip (per platform) requires the same evidence.

#### Validation approach

1. **Numerical equivalence.** Per-kernel tests (`tests/kernels/attention/test_triton_unified_attention.py`) comparing TD and non-TD paths across shapes, dtypes (fp16, bf16), and GQA ratios. Implemented in PR [#40327](https://github.com/vllm-project/vllm/pull/40327).
2. **End-to-end throughput.** `vllm bench throughput` on a representative model set spanning standard attention (Qwen3-4B, Llama-3.1-8B) and non-power-of-2 GQA (Qwen2-7B) × three workloads (ShareGPT, random-prefill, random-decode). Standard `vllm bench throughput` CLI, no custom harness.

#### Evidence: cross-platform impact

TD is not a single-platform feature — its value depends on how each backend lowers it today and where it is headed. We organize results by impact category.

##### 1. Hardware where TD helps today

**Intel Battlemage**, `TRITON_ATTN` backend, `VLLM_TRITON_ATTN_USE_TD=1`.

Throughput median (req/s, 3 runs) vs `TRITON_ATTN` baseline (TD=0):

| Model | Architecture | GQA | random-decode | random-prefill | sharegpt |
|---|---|---|---|---|---|
| Qwen3-4B-Thinking-2507 | standard attn | 4:1 | 3.51 → **6.41** (+83%) | 3.50 → **6.41** (+83%) | 5.02 → **8.52** (+70% R1; +38–39% R2/R3 medians) |
| Llama-3.1-8B-Instruct | standard attn | 4:1 | 2.83 → **4.38** (+55%) | 2.83 → **4.37** (+55%) | 5.42 → **7.48** (+38%) |

Measured by the Intel XPU team across Battlemage SKUs (B60 and B70). Numbers are expressed as relative deltas; the trend across SKUs is consistent.

Default (flash-attn) backend varies ±1.6% across same runs — TD effect is isolated to the Triton backend.

##### 2. Hardware where TD is safe and neutral

**Qwen2-7B (GQA 7:1) on Intel Battlemage** — TD=0 and TD=1 produce identical throughput (2.28 req/s on random-decode, 4.29 → 5.32 on sharegpt within noise). Confirms TD introduces no regression on non-power-of-2 GQA configurations. The `TRITON_ATTN` vs. default gap on this model is shared by both paths — an autotuning limitation of `TRITON_ATTN` for the 7:1 shape, not a TD issue.

##### 3. Hardware with headroom for future gains

**B200 (NVIDIA Blackwell)** — TD currently underperforms raw pointers (–33% to –60% across Qwen3-4B, Llama-3.1-8B, Qwen2-7B). This reflects implementation-level factors — per-tile descriptor reconstruction, autotune configs not yet tuned for TMA — rather than a structural property of the API. TD is off by default on NVIDIA; Blackwell users pay no cost. As these optimizations land in the Triton backend or kernel-side tuning, Blackwell users can opt in without a kernel migration.

**NVIDIA Hopper (H100/H200).** We expect TD to lower to TMA on Hopper, which is the accelerated memory path there. We do not include Hopper benchmarks in this RFC — community runs are welcome and would help map the strategy to Hopper, but they are not required for the decision proposed here: the opt-in design means Hopper users pay no cost until they choose to enable the TD path and validate on their own setup.

#### Graduation criteria for default-on adoption

TD remains opt-in per platform until all three criteria are met on that platform's representative hardware:

1. **Numerical equivalence.** Per-kernel tests pass on TD vs raw-pointer paths across shapes, dtypes, and GQA ratios.
2. **Performance parity or better.** E2E throughput at parity or above the raw-pointer path on ≥3 models spanning different attention configurations (e.g., standard attention, GQA, non-power-of-2 GQA).
3. **Compilation cost.** No autotune-time regression exceeding 2× the raw-pointer baseline.

When a platform meets these criteria for the pilot kernel, a follow-up PR flips its default in `VLLM_TRITON_USE_TD`. Intel Battlemage meets all three today. The same framework applies to every subsequent kernel conversion and every subsequent default-on flip — this is the single bar under which TD spreads across vLLM Triton kernels. Intel holds itself to the same bar, and NVIDIA graduation is expected as Triton-backend optimizations land — a *when*, not an *if*.
