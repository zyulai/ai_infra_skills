## PR body
```markdown
Fixes #57016

## Purpose

With `VLLM_BATCH_INVARIANT=1`, a MoE model served with `--quantization fp8` (online per-tensor FP8, Triton experts) still produces output that depends on which other requests share its batch: greedy tokens flip within the first ~10 positions and prefix-cached K/V differs depending on who wrote it. Dense layers are invariant; only the experts are not.

Two things were wrong:

1. `Fp8PerTensorOnlineMoEMethod` (and `Fp8MoEMethod` for FP8-serialized per-tensor checkpoints with dynamic activations) quantize the expert inputs with one dynamic scale over the whole activation tensor (`kFp8DynamicTensorSym`), i.e. the max over every token of every co-batched request. Under batch-invariant mode this PR selects `kFp8DynamicTokenSym` and passes `per_act_token_quant=True`, mirroring what `Fp8LinearMethod` already does for dense layers.
2. Switching to per-token activations exposed a latent launcher bug: `invoke_fused_moe_triton_kernel` passed `stride_bse=0` for 1-D `[E]` weight scales (and `stride_bsn=1` for the singleton dim of `[E, 1, 1]`), so the kernel's `per_channel_quant` branch read expert 0's scale for every expert or indexed past the buffer. The combination tests already skipped "per-tensor weights + per-token activations" for the Triton experts as NYI, although `TritonExperts._supports_quant_scheme` advertises the pair. This PR passes the expert stride unconditionally and broadcasts singleton scale dims, and narrows the NYI gate to the still-unsupported "per-channel weights + per-tensor activations" case so the combination suite covers the fixed pair.

The bf16 Triton expert path is already invariant on `main` (`get_default_config`/`get_moe_configs` pin the tile config under the flag); the reporter's bf16 mismatch was on 0.27.1.

## Test Plan

- New `tests/v1/determinism/test_batch_invariance.py::test_online_fp8_moe_logprobs_bitwise_bs1_vs_bsN` (granite-3.1-1b-a400m-instruct, `--quantization fp8_per_tensor`, greedy, BS=1 vs BS=8 bitwise tokens+logprobs). Fails on `main`, passes with this PR.
- `tests/kernels/moe/test_modular_kernel_combinations.py`: the per-tensor-weight + per-token-activation FP8 config is no longer skipped for `TritonExperts` / `BatchedTritonExperts` / `TritonOrDeepGemmExperts`.
- Reporter's reproducer (co-batch and writer-suffix modes) against a running server.
- Kernel check: `fused_experts` vs `tests.kernels.utils.torch_experts`, E=32, N=1024, K=2048, M=128, topk=4, per-tensor `[E,1,1]` weight scales: max abs err 0.010 with per-tensor activations, 0.003 with per-token activations (before the launcher fix the per-token case returned values in the thousands).
- Existing suites: `tests/kernels/moe/test_block_fp8.py`, `tests/kernels/moe/test_moe.py::test_fused_moe`, pre-commit, `mypy-3.12`.

Hardware: RTX 5090 (sm_120), WSL2, torch 2.13.0+cu130. The modular kernel combination suite itself does not run on this WSL2 machine (spawned worker fails with `CUDA error: invalid resource handle` on unmodified `main` too), so that part relies on CI and on the independent H20 run linked below.

## Test Result

- Reporter's probe, `VLLM_BATCH_INVARIANT=1 --quantization fp8`, before: A-alone vs A-with-B first token flip at 11 (logprob gap 0.166), warm-vs-cold flip at 11 (gap 0.347). After: every comparison identical, both rounds.
- gsm8k 5-shot, 1319 questions, granite-3.1-1b-a400m-instruct `--quantization fp8 --enforce-eager` (tests/evals/gsm8k/gsm8k_eval.py): default (no flag) 34.1%, `VLLM_BATCH_INVARIANT=1` on `main` 34.3%, `VLLM_BATCH_INVARIANT=1` with this PR 32.7%. Per-token activation quantization is strictly finer than per-tensor, and the kernel-level error is lower, so the small delta is sampling noise from a 1B model.
- New e2e test: PASS with the PR, FAIL on `main` ("logprobs are not bitwise equal between BS=1 and BS=8; max abs diff 2.2e-01").
- Independent cross-architecture validation by @CarrotSwordsman on H20 (sm_90, real Linux GPU, driver 535), [comment](https://github.com/vllm-project/vllm/pull/57092#issuecomment-5730213177): the same e2e test FAILS on a clean 0.28.0+cu129 wheel (max abs diff 2.8e-01) and PASSES with this PR's files applied, reproducing and eliminating the #57016 symptom on Hopper. Their `test_modular_kernel_combinations.py` run on the patched wheel was 8 passed / 2 failed / 1 skipped, the two failures being `deep_gemm`'s `NVCC >= 12.3` assert in a container pinned to 12.1. As they note, that suite does not discriminate against a release wheel (the pre-PR NYI skip is not present there to be removed), so the e2e pair is the evidence in that setup.
- `tests/kernels/moe/test_block_fp8.py` (non-DeepGEMM): 164 passed, 20 skipped. `tests/kernels/moe/test_moe.py -k test_fused_moe`: 241 passed. pre-commit and `mypy-3.12` clean on all changed files.

> Note: since #53585, online per-tensor FP8 is selected with `--quantization fp8_per_tensor`; commands above that use `--quantization fp8` predate that change.

Not a duplicate: no open PR references #57016 (checked with `gh pr list --search "57016 in:body"` and by searching open PRs for "batch invariant moe"); #55881 is the XPU MoE variant and does not touch the CUDA Triton path or FP8 activation quantization.

AI assistance (Claude Code) was used for the investigation and drafting; every line was reviewed and every test run by the submitter.
```
