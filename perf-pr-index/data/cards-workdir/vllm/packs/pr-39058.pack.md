## PR body
```markdown
## Purpose

Implements `ReLUSquaredActivation.forward_cuda` with a dedicated CUDA kernel, replacing the `# TODO: implement cuda kernels` placeholder that delegated to `forward_native` (running `torch.square(F.relu(x))` as two separate kernel launches).

The kernel (`relu_squared_kernel<T>`) uses the existing `LAUNCH_ACTIVATION_KERNEL` macro and follows the exact pattern of `gelu_new`, `gelu_fast`, and `gelu_quick` — the other elementwise activations that already ship custom CUDA kernels. `relu_squared` was the only one left unimplemented.

**Dispatch behavior:**
- With `torch.compile`/Inductor active, `custom_ops` defaults to `none` → the fused `forward_native` path is used (no change).
- With custom ops enabled (eager mode), the op now runs the kernel instead of two unfused ops.
- CPU/XPU fall back to `forward_native` via the base class (this PR scopes to the CUDA kernel only).

## Performance

Microbenchmark added: `benchmarks/kernels/benchmark_relu_squared.py`.
**Setup:** A100-SXM, bf16, `triton.testing.do_bench_cudagraph` (median; launch overhead excluded). The script asserts the kernel output matches `torch.square(F.relu(x))` for every config, so these runs double as a correctness check — all pass.

<img width="2170" height="1452" alt="image" src="https://github.com/user-attachments/assets/23279c11-78c5-4cd1-9a9b-cb2309d187d8" />


**Takeaways (at realistic, memory-bound sizes):**
- **~20% faster than `torch.compile`-fused native** (e.g. 128×1024×12288: 3.84 ms vs 4.72 ms).
- **~2× faster than eager native** (the unfused relu→square, two kernels).
- Tiny shapes (≤64 tokens) are noise-dominated and roughly comparable.

**Methodology note:** `do_bench_cudagraph` excludes per-launch overhead — the fair basis for the torch.compile comparison. Eager mode runs *without* CUDA graphs, so the real-world eager benefit is at least what's shown (plus the saved second launch).

**Benchmark size cap:** the sweep stays under 2³¹ elements. The shared `activation_kernel` computes the per-token offset `blockIdx.x * d` in 32-bit, which overflows for tensors >2³² elements (pre-existing; affects `gelu_*` too) — can be addressed in a separate fix.
