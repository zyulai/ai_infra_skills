## Purpose
Fix related to issue: #32588 

The bug occurs when transcribing long audio (> 30s) using vLLM whisper, the timestamps of which become increasingly inaccurate (up to 1s per chunk). This happens because the old approach assumes split_audio cuts exactly at 30s, but actually will search within 1-second window before the expected value. So it could land anywhere within that, 29.2 or 29.8 for example. This means the error accumulates and after 10 chunks you could be ~5s off. 

The fix is to switch to a cumulative approach, so each chunk we add to where the last chunk ended. So we simply pass the sum to start time.  

This fix also sets seek in TranscriptionSegment to an int instead of a float in prototcol.py as seek position can be rounded down

AI (Claude Code) was used for understanding and some code generation
