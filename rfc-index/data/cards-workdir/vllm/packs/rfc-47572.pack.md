## 正文(PRD / 提案全文)

### Motivation.

## Summary

[ReplaySSM](https://dao-lab.ai/blog/2026/replayssm/) is a memory-bandwidth optimization for the decode kernels of state space model (SSM) and linear attention layers. It is a collaboration between Dao AI Lab and NVIDIA; a concurrent cross-framework implementation is in the [TensorRT-LLM PR](https://github.com/NVIDIA/TensorRT-LLM/pull/14203).

SSM decode is memory-bound: today each step reads and writes back the full recurrent state. ReplaySSM instead caches recent inputs, reconstructing the state only when needed and otherwise computing the output directly from the cache. This keeps most steps read-only and writes the full state back only once every L steps. 

ReplaySSM provides three benefits:

1. Memory-traffic reduction in a bandwidth-bound kernel: the per-step state write is replaced by a small input append.
2. Cheap rollback for speculative decoding: caching recent SSM inputs makes rollback a buffer pointer move, avoiding the separate per-draft-token state the current implementation keeps.
3. Parallel verification for speculative decoding: on non-flush steps the output is read directly without materializing the state, so a draft window is verified in one shot instead of by a serial recurrence.

Implementation: we have opened a draft PR (#47576) implementing ReplaySSM in vLLM, based on the [ReplaySSM reference repository](https://github.com/Johnny-Liou/ReplaySSM). 

We are aware of the existing feature request #46187, which tracks ReplaySSM in vLLM and is assigned to us as the ReplaySSM authors. This RFC and the accompanying draft PR are the upstream contribution we committed to.

## Motivation

Two problems motivate ReplaySSM.

1. In hybrid models, the SSM (linear-attention) layers are the decode bottleneck at short-to-medium output lengths (Fig 2 in the blog post). SSM decode is memory-bound and its per-step state read/write dominates HBM traffic.
2. Speculative decoding must roll back rejected draft tokens, but the SSM state update is irreversible: once history is summarized into the recurrent state, a token cannot be subtracted back out. To support rollback, the current implementation keeps a separate recurrent state per draft token, which costs extra memory traffic and extra HBM footprint (about (1 + num_spec)× the state), hurting both latency and maximum concurrency.

ReplaySSM addresses both by caching inputs instead of state. It keeps a single checkpoint state S0 and caches the recent SSM inputs in a ring buffer; on a flush step (once every L steps) it folds the cached inputs into the checkpoint, and on every other step it computes the output directly from the checkpoint plus the cached inputs without materializing the full state.

For standard decode, writing the state back only once every L steps (instead of every step) roughly halves the dominant memory traffic. For speculative decode, caching recent inputs makes rollback a ring-buffer pointer move, cutting the per-step rollback cost from O(T) to O(1) (`T = num_spec_tokens + 1`) and removing the per-draft-token state storage, which improves both latency and maximum concurrency.

ReplaySSM speeds up the SSM kernel most at large serving batch sizes, where the kernel is fully memory-bound (small batch is not a relevant operating point: there the kernel is overhead-bound rather than memory-bound, and e2e latency is dominated by the MLP layers). For hybrid models it gives the largest end-to-end speedup at short-to-medium output lengths, where the SSM layers dominate latency.

### Proposed Change.

## Proposed Change

We propose adding ReplaySSM to vLLM as an opt-in decode path for hybrid SSM models, covering both SSM families and both decode modes, with the baseline path unchanged when the feature is off.

### Scope
- Mamba2 and Gated DeltaNet (GDN) SSM layers.
- Standard and speculative decode.
- New Triton kernels plus the vLLM integration (mixer dispatch, attention-metadata cursors, state-shape sizing). The conv path reuses vLLM's existing `causal_conv1d_update` unchanged.

### Integration and backward compatibility
The feature is opt-in through config flags that all default to off; when off, the decode path is byte-for-byte the baseline. The ReplaySSM caches are added as extra tensors on the existing paged mamba state, so they reuse vLLM's paged-block allocation and block-table indexing (continuous batching, per-request allocation and eviction).

### Config flags (all default off)
- `--use-replayssm`: Mamba2/GDN standard cached decode.
- `--use-replayssm-spec`: speculative cached decode (requires speculative decoding and `--mamba-cache-mode none`).
- `--replayssm-buffer-len`: history buffer length (default 16).
- `--replayssm-route` (Mamba2 standard only): `output_only` (default) or `state_and_output`; a temporary knob for the precision study, planned for removal (see Open questions).

### Key integration points
- Paged cache: the input caches and the checkpoint state live in the paged KV block, indexed per request by physical block id; only small per-block cursors live in the metadata builder.
- CUDA graphs and continuous batching: speculative decode uses two device-routed launches (verify and flush) with the flush decision and rollback computed on-device, so the launch sequence is fixed and one captured graph per batch size covers the path.
- What we cache: only the state-building inputs; the output read vector (Mamba2 C, GDN q) is taken from the current activations and never cached.
- Flush decision (spec): we flush when `history + T > B`, where `B` is the history buffer length, and size the ring buffer to `B + T`. This is a slight change from the formulation in the blog post.

### Validation
Correctness is checked at three levels (per-kernel vs an exact reference, prefill-vs-decode equivalence over full sequences, and engine-level parity via `check_logprobs_close`), plus a speculative-decode acceptance-length match on GSM8K. Performance covers standard decode (kernel and end-to-end) and speculative decode (throughput and maximum concurrency). Full numbers are in the draft PR.

## Performance
Please check the detailed experiment results in the draft PR (#47576). Here are brief results.

### Standard decode
Whole-model per-step speedup (baseline / ReplaySSM), fp32 state, buffer length 16:

| Model (SSM, HW) | bs 1 | bs 32 | bs 128 | bs 512 |
|---|---|---|---|---|
| Nemotron-Nano-4B (Mamba2, H100) | 0.99 | 1.17 | 1.40 | 1.55 |
| Qwen3.5-4B (GDN, H100) | 0.99 | 1.08 | 1.21 | 1.31 |
| Nemotron-Super-120B (Mamba2, B300) | 0.98 | 1.10 | 1.27 | 1.67 |
| Qwen3.5-122B (GDN, B300) | 0.98 | 1.07 | 1.14 | 1.20 |

### Speculative decode
End-to-end throughput at (B, T) = (16, 4), on B300 with an MTP drafter. `c/std` = ReplaySSM-spec / baseline-spec throughput; `c/AR` = ReplaySSM-spec / no-spec autoregressive throughput.

ReplaySSM-spec vs native-spec (`c/std`):

| Model | bs 1 | bs 32 | bs 256 |
|---|---|---|---|
| Nemotron-Super-120B (Mamba2) | 1.09 | 1.07 | 1.88 |
| Qwen3.5-122B (GDN) | 0.99 | 1.19 | 1.80 |

ReplaySSM-spec vs no-spec AR (`c/AR`):

| Model | bs 1 | bs 32 | bs 256 |
|---|---|---|---|
| Nemotron-Super-120B (Mamba2) | 2.12 | 1.90 | 2.21 |
| Qwen3.5-122B (GDN) | 1.90 | 1.93 | 1.85 |

## Work in progress
1. Tensor parallelism test files (e.g., TP1==TP2) and evaluation.
2. Evaluation on lower-precision (fp16/fp8) state. Current evaluation focus on FP32 state (default in most hybrid models)
3. Numerical-precision benefit: because reconstruction is FP32 and the state is written back only on flushes, a low-precision checkpoint (e.g. FP16) is re-quantized ~`L`× less often than the per-step baseline. Reference: [NVIDIA Nemotron-3-Ultra Technical Report](https://research.nvidia.com/labs/nemotron/files/NVIDIA-Nemotron-3-Ultra-Technical-Report.pdf), Section 4.5.
